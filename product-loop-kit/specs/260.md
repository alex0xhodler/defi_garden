### Measured mechanism — and it refutes the ticket's own hypothesis

The BACKLOG row proposes the fix is "a min-width/flex-shrink discipline on the byline or a
truncation-with-title on the project slug". Geometry says the byline is **not** the growing party.
Exact boxes (`getBoundingClientRect()`, list view @768px, row grid `40px 246px 110px 130px 120px`,
12px column-gap):

| element | left | right | width | clientW | scrollW |
|---|---|---|---|---|---|
| `.pool-context-inline` | 98.9 | **336.6** | 237.8 | 246 | 406 (clipped — ellipsis working) |
| `.pool-apy-section` (its 110px track) | **348.2** | 454.6 | 106.3 | 110 | 110 |
| `.pool-apy-hero` | **311.5** | 454.6 | **143.1** | 148 | 148 |

The byline stops exactly at its own track edge (336.6 ≈ 348.2 − 12px gap). The **hero escapes its
own 110px track by 36.7px leftward**: `white-space: nowrap` (shipped by 246) plus no width
discipline makes its box intrinsically sized at 143.1px, and `align-items: flex-end` sends the
excess left, into the byline's column.

Instance (ii) is the **same mechanism**, rotated: `.pool-tvl-section` is a 128.7px grid item whose
content needs 148px (`.tvl-label` 21 + gap 5.8 + `.tvl-value` 121.5 = 148.3); `.tvl-value` is
`nowrap` with `min-width: auto`, so it cannot shrink and its box runs to right=222.3, past the
section edge (202.7) and into `.pool-cta-section` (left=210.7) — an 11.6px overlap.

**Unified statement of the class:** a `nowrap` numeral cell has no width discipline relative to its
container, so when its intrinsic width exceeds the track it was allotted, its box escapes into a
neighbouring column. 246's `nowrap` rules cured the wrap defect and, for out-of-track magnitudes,
converted it into an overflow defect. Note the existing check D (`scrollWidth <= clientWidth`)
is structurally blind to this: the element's own box grows to fit its text, so nothing is clipped
*inside* it — it is the box that is oversized relative to its track.

## Hypothesis

We believe giving each numeral cell's own container a **yield order — non-numeral labels shrink
before the numeral escapes** will eliminate the numeral-vs-control collision class (instance ii)
without truncating any number, because the deficit in that container (19.6px) is smaller than the
slack its label holds (21px). Confidence: **validated-pattern** — trialled against the live
rendered UI before speccing (see below), not reasoned about.

### Which predicate check E uses, and the weaker one it is NOT (RAZOR, added after verifier round 1)

**Chosen: neighbour-intersection** — "no numeral cell's border box intersects any other rendered
text-bearing leaf box of the same card", with the neighbour set *derived* from the rendered card
(246 finding 1b) and, as of this item, no exclusion.

**The weaker predicate the evidence supports: containment** — "every numeral cell's border box is
contained within its own section's content box (`.pool-apy-section` / `.pool-tvl-section`)".
Containment is **strictly weaker and strictly larger in extension**: it is magnitude-independent and
neighbour-independent, so it catches an escape even when no neighbour happens to sit next to it at
that magnitude and viewport. It strictly contains instance (i), instance (ii), **and** the
`tvlUsd: 950e18` escape that the shipped intersection check cannot see (the verifier's finding 1).

**Why it is not adopted in this item, stated rather than hidden:** under containment, instance (i)
goes RED immediately — its hero is un-contained by 36.7px — so adopting it requires the same
human-gated decision instance (i) is blocked on (see Open questions), plus known-open treatment for
the ~131px numeral-vs-control residual above. Adopting a check that is red on day one for two
defects the item may not fix would ship a permanently-red suite. This is the RAZOR "narrow fix, class
stated with a number" escape hatch used deliberately and named: **the shipped guard is the stronger,
narrower predicate, and it is known to be blind to escapes with no adjacent neighbour.** The
containment predicate is the correct next step and is the natural shape of any follow-up item.

## Open questions

**Instance (i) is BLOCKED on a human decision — the loop must not guess it.** Four constraints are
jointly unsatisfiable for an unbounded numeral width: (1) never truncate a numeral (trust rail);
(2) never wrap a numeral (246's shipped rule); (3) list rows keep row-to-row column alignment —
each `.pool-card` is its OWN grid with an identical fixed template, so any content-driven track
sizing (`max-content`) misaligns the one anomalous row against every other row and against the
`.pool-columns` header; (4) the numeral's box must not overlap a neighbour. Its container holds no
slack to yield (the APY section stacks two numerals vertically; there is no label to shrink), so
only two fixes exist and BOTH exceed this item's authority:

- **(a) Shared column sizing** — make `.pools-list` one grid with `subgrid` rows so `max-content`
  resolves across all rows at once (the byline column absorbs the loss via its existing ellipsis).
  This is a layout-system change to the **approved** list view, which standing decision 2026-08-05
  reserves for screenshot-first increments approved by the human one at a time.
- **(b) Bound the displayed above-rail APY** (e.g. a capped notation for values over
  `APY_SANITY_LIMIT`). This changes how a flagged anomalous number is presented — trust-rail-adjacent,
  and NORTH_STAR reserves anomaly-flag decisions to the human.

Recorded per RAZOR rather than guessed. Not filed as a new ticket (the `specs/246-notes.md`
"no ticket invented" precedent); surfaced to the human in this run's report.

## Territory notes

- `.pools-list .tvl-label { display: none }` (`style.css` ~4080) — the label this fix makes
  shrinkable is hidden entirely in list view, so change 1 is **grid-view-only in effect**; list
  view keeps its approved rendering. Confirmed empirically: candidate A introduced zero new list
  failures at any viewport or theme.
- `.tvl-value`'s `flex-shrink: 0` is a declaration of intent, not a behaviour change — as a flex
  item with `min-width: auto` and `nowrap` text, its min-content size already equals its full text
  width, so it could never shrink. Stated so the yield order is readable at the call site.

  or it produces a false green (recorded trap, `specs/246-notes.md` methodology note).
