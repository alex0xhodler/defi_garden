## The goal, in one paragraph

Item 226 shrank Google's sitemap view from 4,851 URLs to 329 — a curated head of demand-plausible
pages — on the human's Q3b authorization ("generator effort moves from width to depth"). It closed
with an unticketed admission: *"130 head pages now carry the entire Google bet and 0 of them have
received depth work."* This item is that directive's first funded instance. It adds one data-derived
section to the head token pages, and nothing else.

## The intuition

The GSC evidence behind the whole agent-first pivot was 18,555 pages *Crawled — currently not
indexed*. That verdict is Google declining thin content on a no-authority domain. The width half of
the answer already shipped (fewer pages in the sitemap). The depth half is: give the surviving pages
something to say that a scraped table doesn't.

The trick is that "something to say" has to be **derived**, not written. 102 head token pages × 2
languages cannot be hand-authored, and hand-authored copy would drift from the data the next morning.
So the section says things that are true *because they were computed from the same railed pool set
the page already displays*: how wide the rate spread is, how today's rate compares to the 30-day mean,
how much of the headline is incentive yield that decays, how many pools carry impermanent-loss risk.
Those are the four things a cautious saver would actually want before picking a pool — and each one is
a number the page already had in hand and was throwing away.

## What changed, in reading order

**`generate-token-pages.js`**

1. `rateBehaviourFor(rec)` — the data builder. Filters `rec.pools` through `isQualifyingPool` (the
   same rail `yieldHeadlineFor` already uses), then computes the aggregates and per-pool rows.
   Returns `null` when no eligible pool remains — a token with nothing honest to say gets no section
   rather than an empty one.
2. `renderRateBehaviourHtml` / `renderRateBehaviourMarkdown` — both consume the SAME `behaviour`
   object and make the SAME `t(...)` calls. This is item 212's fact-parity rule enforced structurally:
   there is no second derivation that could drift, so the `.md` twin an agent reads and the HTML a
   human reads cannot state different numbers.
3. `renderRateBehaviourStyle(isHead)` — the three scoped `.tp-depth` rules, emitted only on head
   pages. (This existed unconditionally in the first draft; see "What the delta caught" below.)
4. `opts.isHead` threaded into `renderTokenPage` and `renderTokenPageMarkdown`, defaulting to false —
   so every pre-existing caller's output is byte-identical to before.
5. `main()`: `selectHeadTokens(pools)` hoisted out of `if (args.sitemap)`. One Set now feeds both the
   sitemap filter and all four render call sites. This is the mirror rule (RAZOR side 2, item 212's
   precedent): a second call, or a re-derived predicate, is exactly the drift this repo has been bitten
   by, so head-ness is computed once from the exported predicate and passed down.

**`translations.js`** — 10 new `tcpDepth*` keys, EN + KO together. The column header for the 30-day
mean reuses the existing `apyMean30d` key rather than minting a duplicate.

**`test_token_depth_section.js`** — 27 assertions, population-derived (see below).

**`package.json`** — the new test registered in `test:serial`.

## Why the trust rails cannot be bypassed here

The section renders a field this page never rendered before — `apyMean30d` — which is precisely the
field item 144 caught rendering `36,452.38%` as a trusted "30d Mean APY" card while the pool's total
APY of `0.24` kept it un-flagged. So the rail is applied **per field, at every render site**:
`mean30dSane()` — item 144's own fix, a mirror of `PoolDetail.js:285`. A mean that fails it renders an
em dash — omitted, never clamped, never cleaned. The test's positive control is item 144's real value.

Reusing it by `require()` was the first approach and had to be reverted: `run-tests.js` classifies
test lanes by a **static** require scan, so the edge into `generate-pool-pages.js` (which requires
`audit-app.js`, the "browser" marker) re-laned 21 files and dropped the plain lane from 52 to 31.
The predicate therefore lives locally — a **third** copy, after `PoolDetail.js` and
`generate-pool-pages.js` — and per RAZOR side 2 a mirror ships with a test that proves it cannot
drift: `test_mean30d_mirror.js` asserts agreement with the original **in both directions** over a
749-member derived population (738 real snapshot pools + 11 crafted boundary values), asserts both
modules read the same `APY_SANITY_LIMIT`, and was mutation-proved to go red naming the exact
disagreeing case (`exactly APY_SANITY_LIMIT: apyMean30d=1000`). The verifier's view, recorded because
it's right: a shared leaf module would have been the structurally correct fix, and this is the
cheaper one made safe.

## The measurement that actually verifies this

Not `git diff`. A **controlled regen delta** (`playbooks/seo-surface-regen-delta.md`): one shared live
CI-shaped fixture (15,600 pools), the baseline regenerated from `origin/main` in an isolated worktree,
this tree regenerated from the same fixture, 2,078 pages each side.

- `sitemap-token-pages.xml` and its `-ko` sibling: **byte-identical**. Selection is provably untouched.
- Changed pages: **102 EN html, 102 EN md, 102 KO html, 102 KO md** — and in all four, the changed set
  **equals the sitemap head set exactly**.
- Tail pages changed: **0** of 1,976 (× 2 languages × 2 formats).
- Re-run against the FINAL code after the mirror change: same numbers, and the rendered output is
  **byte-identical to the earlier verified render** — which is what proves that refactor was
  behaviour-neutral rather than believed to be.

## What the delta caught that a green test suite did not

Three defects, all invisible to the builder's 22-green suite and all visible in the rendered estate:

1. **`tokens/aave.html` read "1 of 8 pools blend in incentive…"** — three EN strings agreed their verb
   with the denominator instead of the subject. Now keyed on the numerator.
2. **Every one of 1,976 tail pages differed from baseline** by three lines of `.tp-depth` CSS for a
   section they never render. Now gated. This is what turns "only head pages changed" from
   approximately true into exactly true.
3. **The KO string used `USDC은(는) …`** — the only ambiguous-particle pair in the entire catalog
   (`grep -c` was 1, and that 1 was new). The house convention avoids it structurally. Item 190
   shipped two KO strings that were English; a slashed particle pair is the same class of "nobody read
   the Korean" defect, so it was treated as a defect, not a nit.

Each fix carries its own non-vacuity proof (mutate → RED → byte-identical restore → GREEN), and each
of the four rules was neutered **separately**, so "four working rules" is distinguishable from "one
working rule and three dead ones".

## The class this does NOT close, with the number

The head lives in two disjoint sitemaps: `sitemap-token-pages.xml` (130 `<loc>`s = 102 token detail
pages + 28 hub/A–Z) and `sitemap-chain-pages.xml` (29 = 28 chain detail pages + 1 hub). **159 head
URLs total.**

This item depths **102 of them — every token detail page**, EN+KO, html+md. The **28 head chain
detail pages get nothing**: `generate-chain-pages.js` is untouched, and none of this item's
set-equality assertions are scoped to it, so nothing here would catch the gap. Hub and A–Z URLs
aren't depth candidates — they're navigation indexes with no pool set of their own.

So: **102/159 = 64% of head URLs**, or **102/130 = 78.5% of the detail pages depth can apply to**.
Filed for the next heartbeat rather than claimed closed.

Watch the coincidence, because it is what produced the original error: `sitemap-token-pages.xml` has
**130 `<loc>`s** (102 detail + 27 A–Z + 1 hub), and the total detail-page count across *both*
sitemaps is **also 130** (102 token + 28 chain). Same number, different sets. The "102/130" above is
the second one.

(The first draft of this section said "29 of 130 head URLs, ~22%, remain undepthed." That asserted
29 ⊂ 130 when the two are disjoint sitemaps — the verifier caught it and it is corrected above. The
error is left on the record here rather than quietly overwritten, because a wrong denominator is the
exact failure mode the "class open, WITH THE NUMBER" rule exists to prevent.)

Nor is anything claimed about Google. Whether depth moves indexing is settleable only by the human's
GSC read (~08-23+, the item 013 precedent). The loop claims build-leg facts only.

## A claim this PR made and had to withdraw

The build's own territory notes led with what was billed as the constraint that would otherwise have
shipped a production-blank section: *the CI fixture is projected through a 13-field whitelist, so
`sigma`/`mu`/`apyPct30D` "do not survive" and anything built on them renders empty in prod.*

**That was false, and the verifier falsified it on attempt 2.** `generate-pools-snapshot.js` writes
two artifacts: the committed `data/pools-snapshot.json` (projected through `FIELDS` — the APP's
snapshot) and the `--seo-out` transient CI actually feeds the generators, which is raw and
full-field by explicit design. On this item's own fixture, `sigma` and `mu` are present on
15,600/15,600 pools and `apyPct30D` on 12,560/15,600.

The correction is the more useful fact: those fields are **live in production and unrailed**, so a
future depth section that renders them publishes unbounded figures — the item-122/144 class — rather
than rendering blank. This section is safe because of what it chose to read, not because anything
stripped the alternatives.

It is corrected in **four** surfaces, and the fourth is the one that matters most. The first pass
fixed the three documents and said so — "corrected in all three documents" — which was itself an
overstatement: the same false claim was also sitting in the doc-comment directly above
`rateBehaviourFor` in `generate-token-pages.js`, the first thing the next author of a depth section
will read, telling them `sigma`/`mu`/`apyPct30D` are safe to add because they "render empty in
production". The verifier caught that on the third pass, having extended the claim's population from
"the three documents I checked" to "the shipped source the claim was written to justify". Correcting
a headline and leaving the error in a subordinate clause is the exact failure mode of a
documentation-only fix, and this item demonstrated it before it fixed it.

Worth naming plainly: the note was written from reading `FIELDS` and the CI workflow, and never
checked against the fixture that was sitting on disk the whole time — a blindspot pass with its own
blind spot, in an item where every other claim was measured against real output.
