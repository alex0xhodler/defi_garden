**Status at pickup:** promoted by the build loop 2026-07-26. No takeable READY item existed
(148 is READY on `main` but already in flight as open PR #306, human-gated on the NEVER
list). Promoted from documented evidence in `specs/154-notes.md` §"Things noticed but
deliberately NOT fixed", which flagged this failure explicitly "for the verifier/operator
to triage separately".

**Score: 6.8.** Under the 2026-07-23 PRE-TRAFFIC MANDATE the loop's primary job is product
quality, and `audit-app.js` is the instrument that job runs on. Its `number-sanity` P0 check
is the *only* automated detector for the 122 bug class (absurd numbers on a real render —
the `−900,719,925,474,097.9` rate-stability score a human found by hand). That detector's
one positive control has been failing since at least 2026-07-25, and the test file holding

and 149 (4.0, shipped) because a detector whose proof-of-life is dead makes every
"0 findings" heartbeat line unearned — 154 removed the scanner's *structural* blindness,
this restores its *proof*.

## Evidence

1. `specs/154-notes.md` — the 154 builder ran `node test_audit_app.js` before touching
   anything and recorded, verbatim, `1 passed, 1 failed` with case 2 failing; it noted the
   failure was out of 154's scope and asked for separate triage.
2. Reproduced on `origin/main` @ `e60b31cf6` this run:
   ```
   $ node test_audit_app.js
     ✓ clean run: covers pool-detail + dead-pool, ZERO P0/P1, writes signals JSON
     ✗ positive control: injected −900T renders into pool-detail → P0 number-sanity finding
       expected a P0 number-sanity finding for pool-detail; got: []
   test_audit_app.js: 1 passed, 1 failed
   ```
3. **Root cause (diagnosed this run, not in 154's notes).** Item 144 shipped a rail on the
   injected field: `PoolDetail.js:161-164` computes `mean30dSane` (finite, `>= 0`,
   `<= APY_SANITY_LIMIT_LOCAL`) and `PoolDetail.js:1290` gates the whole "30d Mean APY" card
   on it. An out-of-rail `apyMean30d` therefore renders *nothing at all* — so the test's
   injected value never reaches `document.body.innerText` and the scanner has nothing to
   catch. The product is behaving correctly; the control is stale. The test's own root-cause
   comment (`test_audit_app.js:72-75`, "gated only on `typeof pool.apyMean30d === 'number'`,
   with no sanity clamp") describes the pre-144 code and is now factually wrong.
4. **Probe (4 real Chromium renders through `runAudit`, this run)** — which absurd fields
   actually reach rendered text:

   | injected field (magnitude `9.007e14`) | `number-sanity` findings |
   |---|---|
   | `apyMean30d` | **0** — suppressed by 144's rail |
   | `apyBase` (with `apyReward > 0`) | **7**, incl. `astronomical value "900,719,925,474,097.9"` |
   | `apyReward` (with `apyBase > 0`) | **7** |
   | `tvlUsd` | 0 — `formatUsd` abbreviates with a `K/M/B/T` suffix, which the detector
     deliberately skips as legitimate house style |

   So the **detector itself is alive and correct**; only the injection point rotted.
5. `test_audit_app.js` does not appear in `package.json`'s `test` script (only
   `test_audit_runner.js` and `test_seo_surface_audit.js` do), which is why a red positive
   control survived two loop runs unnoticed.

## Change

Test-and-wiring only. `audit-app.js`'s detector logic is **not** touched — the probe proves
it works, and changing a detector to make its own control pass would be backwards.

1. **Restore the positive control (case 2).** Re-point the injection at a pool-detail field
   that still renders verbatim: `apyBase` set to the 122 magnitude with `apyReward` forced
   `> 0` (both cards at `PoolDetail.js:1210/1236` are gated on
   `pool.apyBase > 0 && pool.apyReward > 0` only). Assert ≥1 finding with
   `surface === 'pool-detail'`, `check === 'number-sanity'`, `severity === 'P0'` whose
   `detail` quotes the magnitude. Replace the now-false root-cause comment with the real
   one, citing the render sites.
2. **Convert the stale case into a negative control (new case 3).** Inject the same
   magnitude into `apyMean30d` and assert the scanner reports **zero** `number-sanity`
   findings for `pool-detail` — i.e. 144's rail holds. This keeps the old case's evidence
   working *for* us: if a future change removes `mean30dSane`, this case goes red instead of
   the absurd number quietly reaching production.
3. **Wire `test_audit_app.js` into `npm test`**, immediately after `test_audit_runner.js`.
4. **Remove the tracked-file side effect** that made wiring unsafe: today every run of
   `test_audit_app.js` rewrites the committed
   `product-loop-kit/signals/audit-findings.json` — and its final "restore" run covers only
   3 surfaces, so a `npm test` run would replace the heartbeat's 16-surface signal artifact
   with a 3-surface one. Route every `runAudit` call in this test to a temp `outPath`,
   assert the documented shape from that temp file, and drop the restore run.
