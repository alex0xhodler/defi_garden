# Spec 217: pool-detail cancels the fixed footer's clearance — the bottom band of the north-star surface is permanently occluded

Spec written by the build loop 2026-08-03 (the BACKLOG row 217 was filed by the
heartbeat's human-report triage — `docs(loop): triage 217`, merged as #379 —
with no spec file; build.md's "no spec file → write specs/<ID>.md from
documented evidence, commit it in the same PR" path applies).

## Evidence

**Human report, 2026-08-03, with screenshot** (BACKLOG row 217, score 8.0):
iPhone 1170×2532, dark theme, `morpho-blue`/`SIRLOINUSDC`/Base. The hero card's
rate-steadiness note is sliced mid-sentence — *"Steady so far: across the 21 days
we've tracked it, this pool's rate has"* — and the footer (*"Powered by Defillama
API…"* + Browse tokens/chains) is painted over the rest.

**Root cause, two rules that contradict each other** (read this run, line numbers
verified on `origin/main` @ `3584d54200`):

| File:line | Rule | Effect |
|---|---|---|
| `style.css:849-853` | `.app { padding-bottom: 80px; /* Space for footer */ }` | the app-wide clearance that lets a fixed footer coexist with content |
| `style.css:2513-2524` | `.app-footer { position: fixed; bottom: 0; z-index: 100; background: var(--color-background); }` | OPAQUE, fixed, above content |
| `pool-detail-styles.css:1066-1068` | `.app.pool-detail-view { padding: 0; }` | **wipes that clearance on exactly one page** |
| `pool-detail-styles.css:682-684` | `.pool-detail-container { padding: 20px 16px 16px 16px }` (≤768px) | 16px of bottom padding vs a 58–69px footer — does not restore it |

**Rendered measurement, this run** (Playwright + real Chromium, fixture-routed
per the 2026-07-12 standing decision; `?pool=747c1d2a…` lido/STETH, the house
fixture pool). Page scrolled to the TRUE bottom (`scrollY` pinned, `atBottom`
asserted), viewport 390×844 dark — the human's device class:

```
footer.top      = 786   (height 58, occupies 786–844)
.pool-detail-container.bottom = 802     <-- 16px BELOW the footer's top edge
.app.pool-detail-view padding-bottom = 0px
.app.pool-detail-view rect.bottom = 844 (flush with the viewport — zero clearance)
```

So **at maximum scroll the last 16px of page content sits behind an opaque fixed
footer and can never be scrolled into view.** Measured footer heights: **58px** at
≤768px, **69px** at 1280px. Measured across the design bar: overlap present at
360, 360-dark, 768 and 1280 (the 1280 leaf-level margin was the smallest but the
container-level occlusion is the same defect at every width).

**Why this matters more than a normal cosmetic bug:** pool-detail is the surface
NORTH_STAR.md names as the north star (`pool_click{source ∈ garden_cta,
protocol_link}`). This is the one page in the product where the app-wide footer
clearance was cancelled.

**Class precedent:** item 179 filed the identical occlusion class on bare `/`
and it was fixed there only — the lesson was never ported to pool-detail. The
audit (`audit-app.js`) has **no occlusion signal at all** (BACKLOG row 217:
"a class the audit has never checked").

## Hypothesis

We believe **restoring `.app`'s own 80px footer clearance on the pool-detail
view** will make the bottom band of the north-star surface reachable at every
viewport in the design bar, because the defect is a single declaration
(`padding: 0`) cancelling a clearance the rest of the app relies on, and nothing
else in `.app`'s cascade sets padding (grep-verified: `.app`'s ONLY padding
declaration in the whole design system is `style.css:852`). Confidence:
**validated-pattern** — the same clearance already works on every other view
served by the same footer.

## Change

**Smallest version.** `pool-detail-styles.css:1066-1068` currently reads:

```css
/* Pool Detail View Override for App */
.app.pool-detail-view {
  padding: 0;
}
```

The `padding: 0` shorthand exists ONLY to cancel `.app`'s `padding-bottom: 80px`
— grep-verified that `.app` carries no other padding at any breakpoint
(`style.css:849` and `style.css:5227` are the only `.app {` rules; the latter is
a `transition` declaration only). So the fix is to **stop cancelling it** rather
than to restate the number: no new value, no new token, no one-off. The
`.app.pool-detail-view .container { max-width: none; padding: 0; }` rule directly
below is untouched — that one is doing real work.

Because the site loads the MINIFIED sheet (`home.html:167` injects
`pool-detail-styles.min.css` in analytics mode), `npm run minify` must be re-run
and the regenerated `pool-detail-styles.min.css` committed, or the fix ships
dead — the exact trap `test_mobile_cta_clip.js`'s header documents for item 136.

**Explicitly OUT of scope:**
- Changing `.app-footer` itself (position, height, opacity) — it is shared by
  the analytics grid and the landing page; touching it risks two surfaces to fix
  one. Not needed: the clearance is the documented mechanism.
- Making the footer non-fixed / sticky-at-end on mobile — a layout redesign, not
  a bug fix.
- An `audit-app.js` occlusion signal. BACKLOG row 217 correctly notes the audit
  has never checked this class, but building a new audit signal is a separate
  item's worth of work (the row asks for rendered ACCEPTANCE here, not a new
  daily scanner check). **Filed as a follow-up candidate in `217-notes.md`.**
- Mid-scroll occlusion. An opaque fixed footer necessarily paints over content
  that is scrolling past it; that is true on every view in the product and is
  the design. The defect fixed here is the END-OF-SCROLL case, where content is
  occluded at *every* scroll position and therefore unreachable.

## Territory notes

Blindspot pass, this run (pool-detail CSS is familiar territory — items 136/210/
214/216 — but the footer/clearance interaction is not):

1. **`.app` has exactly one padding declaration in the entire design system.**
   `grep -n '\.app {' style.css pool-detail-styles.css` → `style.css:849`
   (`padding-bottom: 80px`) and `style.css:5227` (a `transition` rule, no
   padding). There is no breakpoint override. This is what makes "delete the
   canceller" strictly equivalent to "restore 80px", with zero duplication.
2. **The footer is rendered twice in `app.js`** — `:2981` inside the
   `pool-detail-view` branch and `:3533` for the analytics grid — but both use
   the same `.app-footer` class, so there is one style source. No JS change is
   needed or wanted.
3. **The static crawler footer (`.seo-hub-links`) is `display:none` in analytics
   mode** (`style.css:2586-2589`, and duplicated as critical inline CSS in
   `home.html`'s head per the 131 note). Measured `display: none` on the
   rendered pool-detail page this run — so it contributes no height and is not
   part of this defect. **Do not touch it**; the 131 note requires the two
   copies of that selector stay identical.
4. **Minified-asset trap.** `home.html:167` injects `pool-detail-styles.min.css`,
   NOT the raw sheet. `test_mobile_cta_clip.js`'s header records this as the
   reason item 136's fix had to reach the min file. `npm run minify`
   (`minify-assets.js`) regenerates it; `test_minified_assets.js` guards
   raw↔min sync.
5. **Test registry invariant (spec 205).** A new `test_*.js` that is not in
   `package.json`'s `test:serial` string is invisible to the only gate this repo
   has, and `test_test_registry.js` asserts (a) no orphans. The new test file
   MUST be appended to that chain in the same commit.
6. **Port allocation.** Highest `const PORT` currently in use across `test_*.js`
   is **8871**; the new test takes **8872** to avoid a collision in the serial
   chain.
7. **Measured footer heights** (this run, real render): 58px at 360/390/768
   (the `@media (max-width: 768px)` `.app-footer { padding: var(--space-12)
   var(--space-16) }` rule at `style.css:2767-2773`), 69px at 1280. Both are
   comfortably under the restored 80px clearance, which is why no
   breakpoint-specific clearance value is needed.
