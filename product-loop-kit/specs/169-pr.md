# 169 — explainer (risk tier HIGH)

> Full walkthrough for the human, per the HIGH-tier rule in `NORTH_STAR.md`. Goal → intuition → what changed
> and why → diff in reading order → deviations → 5-question quiz (answers base64 at the bottom).

## Goal

Give `prescanTextSurfaces()` — the audit's `llms.txt`/`llms-full.txt` pass — a signal that can see **links**.
It had four signals and every one of them was a number-or-emptiness check, so it scored a confident
`suspectCount: 0` on the exact two files that were carrying **32 mis-targeted links** at that moment.

## The intuition, in one paragraph

A generated text surface makes several *kinds* of claim: a rate, a size, a name — and a **destination**.
Items 159/160 built detectors for the rate and the size, because 159 was a rate bug. Nobody built one for the
destination, so when item 166 found 32 links that didn't go where they claimed, the checker had been green
the whole time. That is the third time this repo has been bitten by the same meta-bug: **148 → 159/160 →
166/167**, "the checker's signals are drawn from the last bug found, so the next bug lands in the class
nobody has been bitten by yet." Item 167 fixed it for pool *targets*. This is its text-surface twin, for
*claims*.

## What changed

One new signal, `link-target-integrity` (**P1**), inside the existing pass — no new pass, no new surface, no
product file, no generator, no regenerated SEO byte. Three sub-rules, each emitting at most one suspect per
file:

| rule | asks | fired on the pre-166 bytes |
|---|---|---|
| **(a)** unrouted query key | is every query key on every `defi.garden` link a real router param? | `?search=` — **7** links in `llms.txt`, **10** in `llms-full.txt` |
| **(b)** pool row → bare origin | does a row *about a specific pool* link only to the homepage? | **15** rows in `llms-full.txt` |
| **(c)** one URL, two figure sets | do two pool rows stating different figures share one destination? | 1 URL (2 figure sets) in `llms.txt`; the bare origin (15 figure sets) in `llms-full.txt` |

**Rule (a) reads the allowlist out of `home.html:77-78` at scan time** — the router's own `ANALYTICS_PARAMS`
and `PLANNER_PARAMS` arrays, parsed by regex, never executed, plus `lang` (which is read by
`translations.js`, not the router, and is live in real URLs). A second hardcoded copy of the param list
would have been the very drift bug the signal exists to catch, so the coupling is proved by a test that
appends a param to a *copied* `home.html` and shows a URL using it flip from suspect to clean.

## The diff, in reading order

1. **`audit-app.js:208`** — `TEXT_SURFACE_SIGNALS` gains `'link-target-integrity': 'P1'`. The one edited
   pre-existing line in the file, and it is an addition to an object literal; the four existing signals'
   detection blocks are byte-identical (verifier re-derived this).
2. **`audit-app.js:~228-288`** — the new pure helpers, inserted between `parseMoney()` and the pass:
   `TEXT_DEFI_GARDEN_URL` (captures the path+query suffix, `undefined` for the bare origin),
   `extractQuotedArray()`, `loadRouterAllowedParams()` (returns `{allowed, error}` — never throws),
   `urlQueryKeys()`, `isBareOriginSuffix()`.
3. **`audit-app.js:~290`** — inside `prescanTextSurfaces()`, before the file loop: parse `home.html` **once**
   per scan (both files share one router), so a broken `home.html` prints its skip note once and rules
   (b)/(c) plus all four old signals keep working.
4. **`audit-app.js:~372-443`** — the three sub-rules, appended strictly *after* the existing `empty-surface`
   block. Rule (a) scans the whole file (a `?chain=` link in a non-pool section carries a query key too);
   rules (b) and (c) reuse the existing `TEXT_POOL_LINE_APY`/`TEXT_POOL_LINE_TVL` pool-line predicates
   verbatim.
5. **`test_audit_text_surfaces.js`** — 20 new cases in the existing file (no second test file; already wired
   into `test:serial` at position 96, so `package.json` needed no change).
6. **`test-fixtures/pre166/`** — the positive-control bytes, with provenance headers.

Everything else in the repo is untouched. `package.json` is byte-identical (checked structurally, not by eye).

## Why the fixtures are real bytes

The positive control is the **actual pre-166 artifact** — `git show 3935e8d05:llms.txt` /
`:llms-full.txt`, the commit immediately before `aff271c79` (166's fix) — not a hand-written imitation. That
matters: a fixture is written from your mental model of the bug, and that mental model is the same one that
missed the bug for four items. `llms.txt` (76 lines) is committed in full; `llms-full.txt` is 209KB, so the
committed fixture is a **verbatim line-range excerpt** carrying all 10 `?search=` lines and all 15
bare-origin rows, preserving the full measured counts. A second, *opportunistic* test reconstructs the full
originals via `git show` inside try/catch — stronger where git exists, still non-vacuous where it doesn't.

## The verifier's find, and the fix on top

The verifier PASSed 12/12 and then produced a synthetic fixture with **two independent** conflicting-URL
groups. Rule (c) `break`ed at the first one and reported it with no count and no `+N more` — the second,
equally real conflict was **invisible**. Rules (a) and (b) aggregate their true totals; (c) did not.

That is this item's own thesis one level down — a detector shipping an un-exercised blind spot — so it was
fixed before shipping rather than filed as a follow-up: collect every conflicting group, pick a
deterministic worst (most figure sets, ties to first-encountered, strict `>`), still emit exactly one
suspect, but lead the `detail` with the true total and append `(+N more conflicting URLs)`. The pinning test
asserts the *number*, not a substring — the old code's leading number would have been the winning group's
figure-set count, which a looser assertion would have matched.

Ground truth on the two real historical files is unchanged (1 conflicting URL each): the gap was a
correctness bug in the aggregation, **not** an undercount on those specific files.

## Deviations from the spec

1. **One pre-existing fixture edit.** Item 160's negative-control case built two pool lines through a helper
   that hardcodes one URL, and its two lines state different figures — a genuine rule-(c) hit once rule (c)
   existed. Fixed the fixture's URL diversity; the assertion (zero suspects) is unchanged. The verifier
   reverted the edit and confirmed the test genuinely fails without it, so this is a real interaction, not a
   mask.
2. **Up to 3 suspects per file share the signal name** (one per sub-rule), which reads against one
   acceptance bullet taken alone but is the only reading consistent with the spec's Change section and its
   other bullets. Flagged by the verifier as a genuine spec-internal ambiguity, resolved transparently.
3. **`(+N more)` on rule (a) counts distinct offending keys**, not offending links — the leading number
   already states the link total.

## Known limitations (disclosed, not buried)

- No URL is fetched or resolved. A link to a slug that doesn't exist is a different, more expensive check and
  is deliberately not attempted.
- Non-`defi.garden` links are out of scope.
- Rule (c) reports one worst group per file; additional groups are counted but not individually quoted.
- The browser lane was not run this session.

## Compound step

`playbooks/detector-signal-coverage.md` (new): when adding a signal to any checker, enumerate what the
surface **asserts** rather than what it contains, cross off the claims that already have a detector, and the
leftovers are where the next bug already is. Includes two traps this session hit for real — `runAudit()`
overwrites the committed `signals/audit-findings.json` unless `AUDIT_OUT` is set, and one-suspect-per-file is
a reporting cap, never a scanning cap.
