## The goal in one line

The product audit could see the planner's front door and nothing behind it. This
walks it into the room where the planner does arithmetic.

## The intuition

`audit-app.js` is a Playwright scanner that loads real rendered pages and looks
for the bug classes the human keeps finding by hand — NaN, `$undefined`, absurd
magnitudes, dead CTAs, page errors, KO pages with no Hangul, horizontal scroll at
360px. It is the automation behind the PRE-TRAFFIC MANDATE: with ~0 traffic, the
loop's job is a product that is genuinely not-broken.

Item 162 pointed it at the planner for the first time. But the planner is a
seven-step conversation (`planner.js:3902`):

```
goal → funding-mode → deadline → monthly → horizon → temperament → bloom
```

and 162's driver asserts on **step 1** — a screen of goal chips. Chips are
static labels. Every number the planner *derives* — the capital you'd need, the
forever number, the projection, the checkout price — renders at step 2 and after,
and above all at `bloom`.

So the number detectors were running against a page with no numbers on it. Real,
functioning, pointed at nothing.

We already know what that costs. Item 146 (fixed 2026-07-26): `mixStats()` read
the TARGET goal `iphone`'s $1,100 **item price** as a $1,100 **monthly
subscription**, and `foreverNumber()` turned that into ~$155k–$220k of capital
the user never entered — rendered verbatim as `≈$155,000 working at 8.5% ·
$1,100/mo covered forever`. A human found it. Nothing automated could have,
because nothing automated had ever rendered that screen.

162's own notes said so and declined to file the ticket itself
(`specs/162-notes.md:170-180`). This is that ticket.

## What changed and why

Three changes, all in `audit-app.js`, all detectors — no product file is touched.

**1. A new surface kind `bloom`.** It loads a *deep-linked* plan URL rather than
hand-driving seven steps. That choice matters twice over:

- It is robust. `planner.js:4246-4257`'s "shared plan fast-forward to bloom"
  effect takes a URL carrying goal + persona + the archetype's amount field
  straight to `bloom`, and `test_plan_checkout_cta.js` already proves those exact
  URLs land on `.gp-checkout-panel` in real Chromium. Reused verbatim, not
  reinvented.
- It audits a second surface for free. A deep-linked plan URL **is** what a share
  recipient opens (standing decision 2026-07-11: the plan share is "a UNIQUE
  WORKING LINK … that reproduces the sender's exact setup one-tap on open").
  Auditing bloom audits the viral surface.

The checks reuse the existing vocabulary exactly — `dead-end` P1 on readiness,
`number-sanity` P0 via the existing `auditText()`, `dead-cta` P1 on
`.gp-checkout-cta`, `page-error` P0 via the existing error sink, `responsive` at
360 only, `i18n` P2 on the KO surface only. No new detector was invented; the
point of the item is *where* the existing detectors point, not what they detect.

**2. Five surfaces appended after `planner-ko`** — the three archetypes from
`CLAUDE.md` (GROWTH `retirement`, TARGET `iphone`, SUBSCRIPTION `claude`), plus a
360 and a KO. `iphone` is deliberate: it is item 146's exact goal, so the scanner
now has permanent coverage on the screen that bug rendered on. Appended, never
inserted — the heartbeat diffs the `surfacesCovered` list, so a rename or reorder
would read as a regression.

**3. One interactive check on the existing `planner` surface.** The old check
asserted a goal chip is *visible*. A chip that renders and does nothing is
invisible to that check and is a dead CTA on the planner's single most important
control. The new check clicks the first chip and polls for `.gp-thread-row` —
`planner.js`'s `ThreadRow`, pushed only when `step !== 'goal' && answers.goal`
(`planner.js:4376-4377`). That is a *rendered DOM* signal that exists only past
the goal step, not internal React state, per the spec's explicit instruction.

The builder verified the signal holds for every archetype the first chip could
be: `pickGoal()` never jumps `goal → bloom` directly (subscription →
`temperament`, target → `funding-mode`, growth → `monthly`;
`planner.js:4260-4277`), and the thread container only stops rendering at
`bloom` (`planner.js:4836`) — so the row always appears after a chip click.
That check-the-edge-case reasoning is the difference between a check and a
flake.

Scoped to the 1280/EN surface only (`s.width > 360 && !s.ko`) — one flake
surface, not three.

## The diff in reading order

1. `audit-app.js` header comment — records 164 alongside 154/162 in the list of
   what the scanner covers.
2. `audit-app.js` `main()`, `kind: 'planner'` branch — the chip-visibility `if`
   becomes `if / else if` so the click only fires on a chip that is actually
   there. Deliberate: clicking a zero-match locator throws, and a `driver threw:`
   page-error would mask the specific `dead-cta` the old check reports.
3. `audit-app.js` `main()`, new `kind: 'bloom'` branch — readiness, then the
   checks above.
4. `audit-app.js` `runAudit()` surface rotation — five entries appended after
   `planner-ko`.
5. `test_audit_planner_flow.js` (new) — source-level assertions on the surface
   definitions plus real-Chromium integration cases.
6. `package.json` — one line: the new test appended to the `test:serial` chain.
   `dependencies`/`devDependencies` byte-identical.

## Deviations from the spec

Two, both recorded in `164-notes.md` and both conservative:

1. The chip-visibility check was restructured to `if`/`else if` rather than the
   click being added as an unconditional follow-on — so a missing chip still
   reports the specific `dead-cta` rather than a generic driver throw.
2. `.gp-checkout-panel` was used as the readiness selector rather than
   `.gp-bloom`. The spec offered either; the builder took the one
   `test_plan_checkout_cta.js` already proves works in real Chromium.

## What this item does NOT claim

- **It found no bugs.** All five surfaces came back clean, including
  `plan-bloom-target`. That is not the scanner missing item 146 — 146 was fixed
  on 2026-07-26 (`LOG.md:249`, `isMonthly === true` guard). The clean result is
  the first automated confirmation that the fix holds. An honest null result.
- **It does not drive the conversation end-to-end.** Bloom is reached by deep
  link. The intermediate steps (`funding-mode`, `deadline`, `monthly`,
  `horizon`, `temperament`) still render numbers no scanner has ever seen. That
  is the natural next item, and it is stated here rather than quietly left out.
- **It moves no funnel metric.** Detector coverage, not a user-facing change —
  the 084/098/162 disclosure pattern. The honest measure is `surfacesCovered`
  going 20 → 25, and the leading indicator is the next hand-found planner number
  bug being caught by `audit-app.js` first.

## Quiz

1. The audit's number detectors (`scanNumbers`/`auditText`) already ran on the
   planner before this item. Why did that not catch item 146's `≈$155,000`?
2. Why does the `bloom` kind use a deep-linked URL instead of clicking through
   the seven conversation steps — and what second surface does that choice
   audit for free?
3. The new chip check polls for `.gp-thread-row` rather than reading React
   state. Why was `.gp-thread-row` specifically safe for *every* archetype the
   first chip might be?
4. Why were the five new surfaces appended after `planner-ko` rather than
   grouped with the other planner entries?
5. All five new surfaces reported zero findings. Give the reason that is a
   meaningful result rather than evidence the scanner is broken — and name the
   coverage gap this item still leaves open.
