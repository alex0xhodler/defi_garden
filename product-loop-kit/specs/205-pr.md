# 205 — PR explainer (HIGH tier)

**What shipped:** the seven `test_*.js` files that existed on disk but were never in `package.json`'s
`test:serial` chain are now wired in, the one gate defect that would have made a wire-in permanently red
is fixed, and a new guard test makes disk↔chain parity self-reporting from here on.

---

## Goal

Restore seven real behaviour guards to the only test gate this repo has, and make the class of failure
that lost them impossible to repeat silently.

## Intuition — why "a test file exists" and "a test runs" are different claims here

`run-tests.js` was written (item 163) so that `npm test` would be *observable*: lanes, per-file results,
no `&&` chain aborting at file 5 of 94. It made one deliberate design choice that this item turns on:

> `package.json`'s `test:serial` script is the ORIGINAL … chain, verbatim, untouched. This runner
> PARSES that string for its file list (never a second hardcoded copy — see `parseFileList()`)
> — `run-tests.js:5-6`

Single-sourcing the list was correct. But it means **membership in that one string is the entire
definition of "a test that runs."** A `test_*.js` file absent from it isn't red and isn't skipped — it is
unobserved, which looks exactly like healthy from the outside. And there is no second gate to catch the
slip: `.github/workflows/` holds only `sitemap-update.yml`, which runs generators, never `npm test`. The
loop's own pre-merge run *is* the gate.

Measured on `main` @ `a4dbd99cd`: **120 listed, 127 on disk.**

| orphan | lane | what was going unguarded |
|---|---|---|
| `test_seo_src_attribution.js` | browser | item 203's `src=` attribution rail on `?pool=` deep links — the guard on whether north-star arrivals are attributable at all |
| `test_earnings_dedup.js` | browser | pool-detail earnings surface — the north-star page |
| `test_nav_rail_ia.js` | browser | spec 093 nav-rail IA, 10 rendered assertions incl. KO filter labels |
| `test_list_polish.js` | browser | spec 095 list-view polish, 6 computed-style assertions |
| `test_audit_768_lens.js` | browser | the 768px audit lens surfaces |
| `test_llms_shared_source.js` | plain | `generate-llms.js` shared-source rails |
| `test_helpers_parser.js` | plain | the parser helper its two consumers import |

`playbooks/test-gate-observability.md` step 4 already told humans to prevent exactly this by hand —
"If you add a test file, append it to `test:serial`; nothing else needs touching." That is a
memory rail with nothing enforcing it, and it had been violated seven times.

## What changed, in reading order

**1. `package.json` — one line, the `test:serial` value.** Seven files inserted next to their topical
neighbours (`test_seo_src_attribution.js` beside `test_seo_app_link_attribution.js`, the two other
`_lens` audit tests get `test_audit_768_lens.js`, `test_list_polish.js` follows `test_list_default.js`
whose server it clones verbatim, and so on — full placement reasoning in `205-notes.md` §1), plus the new
guard test appended last so every other wiring decision is already reflected in the file it reads. The
pre-existing 120 steps are preserved **byte-identical and in their original relative order**, proved by a
scripted subsequence check (`120/120`) rather than by eye. Nothing else in `package.json` moved: a
structural comparison parsing both JSONs and diffing every key except `scripts["test:serial"]` reports
`rest identical: true`. **No dependency change.**

**2. `test_list_polish.js` — 3 lines, the one blocker.** This file printed `✓ 6/6 list-polish assertions
passed` and then exited **1**. Not a failing assertion — lines 246-249 set `process.exitCode = 1` because
its `pageErrors` array had collected `net::ERR_CONNECTION_RESET` on `https://icons.llamao.fi/icons/...`.
Its `IGNORABLE_ERROR_PATTERN` (line 32) omitted `icons\.llamao\.fi`, which **both** sibling browser tests
already include (`test_nav_rail_ia.js:31`, `test_earnings_dedup.js:40`). Browser-originated HTTPS is
blocked at the proxy in this sandbox (standing decision 2026-07-12), so the reset is guaranteed on every
run. Wiring the file unfixed would have installed a step that can never exit 0 — the playbook's own trap,
*"a permanently-red gate is worse than an unobservable one,"* because it gets ignored. The fix reuses the
sibling's pattern rather than inventing a mechanism. Also replaced: a hardcoded `SCRATCH` constant
pointing at **another session's UUID scratch directory**, which exists on no other machine, with
`os.tmpdir()`. **All six assertion bodies are byte-identical to `origin/main`** — the diff is the `os`
require, the `SCRATCH` line, and the `IGNORABLE_ERROR_PATTERN` line, nothing else.

**3. `test_test_registry.js` (new, 158 lines) — the compound move.** Five cases against the real repo:
(a) no orphans, (b) no ghosts, (c) no duplicates, (d) parse integrity, and (e) a **self-defeat** case.
(a)–(c) are pure functions shared with (e), so (e) proves the same logic (a) trusts rather than a second
copy of it. It reuses `run-tests.js`'s already-exported `parseFileList()`/`readSerialChain()` — **no
export was added; `run-tests.js` is completely untouched.**

The subtle part is lane classification. `run-tests.js` flags a file as browser-lane if the file's own raw
text contains the browser-driver package name, *then* follows local requires transitively. `run-tests.js`
names that package many times over, so a bare literal `require('./run-tests.js')` would match
`LOCAL_REQUIRE_RE` and drag this plain little file into the 600s browser lane. It loads the runner by a
**computed path** instead, which that regex cannot match — the trap `test-gate-observability.md` records
as "a program that scans its own repository can misclassify itself." Verified: `--list --lane=plain`
lists it as `plain`.

**4. `playbooks/test-gate-observability.md` — step 4 updated in place, never duplicated.** It keeps the
original human-checklist rule verbatim, adds the measured fact (7 of 127, ~6 months of accumulation),
names the now-enforcing test, and tells a future reader that a red from it means the checklist step was
violated again. One provenance line appended in the file's existing style.

## Deviations from the spec

None that change scope or behaviour. Three judgment calls, all recorded in `205-notes.md`: step placement
where no obvious topical neighbour existed (`test_nav_rail_ia.js` appended per the spec's own "otherwise
append"); `os.tmpdir()` chosen over `fs.mkdtempSync(...)` as the smaller diff, since `shot()` already
swallows its own errors and had no cleanup lifecycle to preserve; and diffing against `origin/main`
rather than the spec's literal `main`, because local `main` is stale.

## Honest limits

- **Two of the seven newly-wired tests were not re-run on the branch**: `test_nav_rail_ia.js` (10/10) and
  `test_earnings_dedup.js` (4/4) were executed green by the operator on this checkout *before* the branch
  existed, and neither the builder nor the verifier re-ran them within the 5-minute-per-command timebox.
  Their green status rests on that earlier run, not on one performed against the final diff. Stated
  rather than smoothed over, per `test-gate-observability.md` step 3.
- **The full browser lane (86 files) was not run** and is not claimed. It cannot finish inside the
  foreground timebox.
- **This ships coverage, not a product fix.** No user-visible behaviour changes; no product file was
  touched. If any of the seven newly-wired guards goes red on a future run, that red is a *finding this
  item made visible*, not a regression this item caused.
