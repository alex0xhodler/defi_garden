# 231 — PR explainer: the occlusion lens must SEE a permanent defect on (nearly) every run

## Goal

`audit-app.js`'s `occlusion` lens flagged a **permanently broken** page on only 3 of 20 runs (item 221),
and this session re-measured **2 of 10** with item 230's fix mutated away. The page was reliably broken;
only the detection was intermittent. That makes every "0 blocking findings" tick a much weaker claim than
it reads — and the lens visits 83 surfaces per tick, so the weakness is everywhere at once, not on one
surface.

## The intuition

The lens resizes the viewport to 780px before measuring. On the React surfaces that resize **re-mounts**
the subtree, which **restarts** the entry animations — `style.css:4605` declares
`.animate-on-mount { opacity: 0 }`, and the per-section rules (`style.css:4610-4670`) each carry a
staggered `--entry-delay-base * N` delay. The lens then waited a flat **150 ms** and measured.

`occlusionPassEval`'s visibility gate is
`checkVisibility({ visibilityProperty: true, opacityProperty: true })`. So an element that is *mid-fade-in*
is **invisible to the lens** — while being plainly visible, and plainly broken, to a user a moment later.
The lens was reading the page during the exact window in which the victims did not officially exist.

The dead-pool alternatives grid stacks up to 10 staggered `.pool-card.animate-on-mount` entries: up to
`400 ms + 450 ms` of delay before the *last* card's own `400 ms` fade even starts. Genuine settle ≈
**1250 ms**. The lens was measuring at 150 ms — about **8× too early** — which is why the result was
essentially a coin flip on the animation's tail.

## How that was established (not argued — measured)

Instrumenting `occlusionPassEval` at increasing delays past the existing settle, 3 isolated runs, identical
in all three:

| t past the existing 150 ms settle | occlusions reported |
|---|---|
| 0 ms | **0** |
| 100 / 200 / 400 / 800 / 1600 ms | 6 |

At t=0 the victims were **already 100% covered**, with `elementFromPoint` at their centres **already
resolving to `FOOTER.app-footer`**. Geometry and hit-test both said "occluded"; the pass still returned
zero. That is what ruled out every render-race explanation and named the visibility filter as the gate —
and it corrects the hypothesis carried in the backlog row ("the settle races the alternatives-grid
render"): the render is *finished*; what the settle races is the **opacity ramp**.

Two rival explanations were already ruled out by item 221 and were not re-litigated: the CSS-load race
(15/15 probe runs had `style.min.css` applied) and content variance (`getEmptyStateAlternatives` draws
from the in-memory snapshot, deterministic).

## What changed, in reading order

1. **`audit-app.js` — `quiescenceSampleEval(args)`** (new, page-realm, self-contained like
   `occlusionPassEval` because Playwright serialises it via `toString()`): returns
   `{animCount, geometry}`. `animCount` counts **running** CSS animations/transitions, **excluding
   `iterations === Infinity`** — spinners and pulses never settle, and a lens that waits for them would
   hang every surface. Guarded behind `typeof document.getAnimations === 'function'`. `geometry` is a
   byte-comparable signature of the rounded rects of the visible fixed/sticky overlays plus the occlusion
   candidate victims.
2. **`audit-app.js` — `waitForQuiescence(page, budgetMs)`** (new): polls via the house `pollFor()` helper
   until **both** (a) `animCount === 0` and (b) two geometry samples ≥100 ms apart are identical. Bounded
   by `OCCLUSION_QUIESCENCE_BUDGET_MS = 3000`. It never decides to skip a measurement — it only reports
   readiness.
3. **`audit-app.js` — `checkOcclusion`**: the flat `await page.waitForTimeout(150)` is replaced by
   `waitForQuiescence` before the at-rest pass, and a second call is added before the bottom-of-scroll
   pass (scrolling can start new animations and reveal lazily-mounted content). On timeout it pushes a
   **P2 advisory naming the numbers** (budget, animation count, whether geometry is still changing, which
   pass) and **measures anyway** — the lens's standing rule is that it must never go silent, and a
   readiness wait that could silently skip a pass would just move the false negative one layer down.
4. **`audit-app.js` — kill switch** `opts.occlusionQuiescence:false` / `AUDIT_OCCLUSION_QUIESCENCE=0`,
   default **ON**, falling back to the exact pre-231 150 ms path. It exists so the acceptance test can run
   the old path as a **positive control in the same session** without editing source.
5. **`audit-app.js` — `opts.injectStyle`**, applied via `page.addStyleTag` after both `page.goto` sites.
   Test-injection only, never set by the CLI. This is what lets the test re-create a known-permanent
   defect on a real surface without touching the committed stylesheets — necessary because item 230
   *fixed* the dead-pool defect, so the old positive control no longer exists on `main`.
6. **`test_audit_occlusion_lens_reliability.js`** (new): the rate harness. Legs A/B/C against the real
   `dead-pool` surface through the real `runAudit()` driver, plus three fixtures (D/E/F) that prove each
   quiescence condition is separately load-bearing.
7. **`package.json`**: registered in `test:serial` (browser lane, auto-classified by `run-tests.js`).

## Results

| Leg | Condition | Result | Required |
|---|---|---|---|
| A | quiescence ON + permanent defect injected | **20/20** flagged | ≥19/20 |
| B | positive control: quiescence OFF, same defect | **0/20** flagged | ≤8/20 |
| C | quiescence ON, no-op injected style | **0** findings / 5 iterations | 0 |

Budget-honesty and leg-isolation fixtures:
- **(D)** an **infinite** CSS animation does not hang and raises no advisory — the `Infinity` exclusion works.
- **(E)** a fixture whose geometry never stabilises **does** advise *and* still reports the real P1 occlusion.
- **(F)** *(added after the verifier's attempt-1 FAIL — see below)* isolates the **animation-count** leg:
  static geometry from the first frame, with a finite, opacity-only animation on an element parked
  off-screen at `top/left:-9999px` so it cannot enter the geometry signature (it fails both the
  viewport-intersection gate and the interactive-or-text-bearing gate) and is visible only to
  `document.getAnimations()`. Mid-animation `waitForQuiescence` must return
  `{reached:false, animCount≥1, geometryChanged:false}` — that third field is what proves the geometry leg
  cannot explain the result — then `{reached:true}` once the animation ends, with the real occlusion still
  reported.

Leg B footnote: the builder measured **0/20**; the verifier's independent N=20 re-run measured **1/20**.
Both are on the record. The re-run nudging toward the historical ~15% supports the sample-variance reading
over "the control measures something subtly different".

## What the verifier caught (attempt 1 → FAIL)

Worth reading, because it is the second time in two days this exact gap has appeared. The verifier neutered
the two quiescence conditions **separately**:

| Mutation | Result |
|---|---|
| M1 — whole `waitForQuiescence` returns `{reached:true}` | RED (legs A and A-vs-B fail) |
| M3 — geometry leg neutered | **(E) RED** — geometry leg proven load-bearing |
| M2 — animation-count leg neutered | **everything GREEN, 9/9** |

M2 stayed green because `.pool-card.animate-on-mount` uses `fadeInUp` (`style.css:4568-4578`), which
animates `transform: translateY(20px)→0` — so the rect **moves** for the whole animation and the
geometry-stability leg alone gated the dead-pool fixture correctly, masking a completely dead animation leg.
"Waits until BOTH hold" was an unproven claim about shipped code. Fixture (F) closes it: with M2 applied
(F) goes RED and nothing else does; with M3 applied (E) goes RED and (F) does not. `audit-app.js` restored
byte-identical after every mutation (`md5sum 31f16b3ee21a0b4b0137377166db3382`).

This is the item-230 precedent — one mutation proves only that *at least one* rule is live — and it was
named in this item's own new playbook (`detector-detection-rate.md`, Trap 3) before the item fell into it.

## The cost, stated rather than left to inference

Reliability is not free. Measured across 4 real surfaces via `runAudit`
(`grid-token`/`pool-detail`/`dead-pool`/`grid-chain`): **11,369 ms with quiescence vs 5,660 ms without**
— roughly **+1.4 s per surface**, so **~+2 minutes across an 83-surface tick** against
`DEFAULT_TIME_BUDGET_MS = 300 s`. The consequence is that item 192's rotation guard will truncate more
pool-rotation picks per tick: this item trades some **breadth** for **reliability**. The truncation is
graceful and already printed by the runner, but the trade is real and belongs on the record.

Expect the next tick to be **noisier**, by design: surfaces that were previously "clean" only because the
lens was blind will now flag. That is the fix working, not a new outbreak.

## Deviations from the spec

1. `checkOcclusion` could not take a 4th parameter — `test_audit_occlusion_lens.js` pins the literal
   source string `function checkOcclusion(page, s, findings)`, and that test is required to stay green. The
   kill switch reaches it via `ctx.occlusionQuiescence` → `main()` stamping `s.occlusionQuiescence`, the
   same "enrich the surface object" pattern `s.vpLabel` already uses.
2. Advisory wording extends the spec's example with the viewport, a pass label, and "— measuring anyway".
   Every number the spec named is present verbatim.
3. The sampler never short-circuits on `animCount > 0`; it always takes both samples, so the timeout
   advisory always carries a real `geometryChanged` value rather than a stale one.
4. `quiescenceSampleEval` omits the `bottomAnchor` overlay exclusion that `occlusionPassEval`'s pass 2
   uses — deliberately the weaker predicate, since "has anything moved" should not ignore an overlay just
   because that overlay would be excluded from a *measurement*.
5. **Leg B measured 0/20 where history says ~15-20%** (221: 3/20; this session's own pre-build re-measure:
   2/10). It satisfies the ≤8/20 bound and is strictly below leg A, but it is a bigger swing than expected
   and is recorded as an open question rather than restated as "reproduced the known rate". Candidate
   causes: ordinary sample variance at n=20, and the harness measuring in-process at 1280px against the
   historical separate-process measurements.

**232**. Shipping the narrow fix is allowed; claiming it closed the class is not.
