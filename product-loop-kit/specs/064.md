# Spec 064: X-spotlight → waitlist attribution + cadence

## Evidence
- Daily session_start is decaying post-launch: 07-09 **167** → 07-10 80 → 07-11 80 → 07-12 **21** (complete days, 2026-07-13 Mixpanel). Traffic — not perf — is the binding constraint (LOG 2026-07-12), and it is visibly shrinking.
- North star `waitlist_submitted` = 0; the funnel is wired end-to-end in the prod bundle (2026-07-13 audit) → 0 is a distribution problem, nothing is reaching the funnel.
- Weekly theme (human 2026-07-12): "Distribution + card funnel — X protocol-spotlight engine … and waitlist conversion toward the card."
- 060 SHIPPED `generate-spotlight.js`: emits a per-pool tweet draft + a working example-garden share URL `SITE_URL/plan.html?goal=…&monthly=…&pace=…&chain=…&token=…` (buildShareUrl, generate-spotlight.js:223). That URL carries **no source/attribution param** → any garden or waitlist opened from a spotlight is invisible in Mixpanel.

## Hypothesis
We believe adding a stable `src`/`utm` attribution param to the spotlight share URL (and threading it into the planner's existing `source` plumbing) will make `plan_created`/`waitlist_opened` from X spotlights attributable, because the planner already reads `?src=` and the waitlist calls already accept `{ source }` (planner.js:3513) — so attribution is a param-wiring change, not new instrumentation. Confidence: supported.

## Change
`generate-spotlight.js` only (+ its test):
- `buildShareUrl` adds `src=x_spotlight` and a stable per-pool ref (e.g. `ref=<project>-<chain>-<symbol>`, slugified) to the emitted `plan.html?…` URL. Keep all existing params.
- Confirm the planner surfaces this `src` on downstream events: the SEO auto-open path already tags `trackWaitlistOpened({ source })` from `urlParams.get('src')`; verify a spotlight-origin session that later opens the waitlist inherits `source=x_spotlight` (if the Bloom-modal waitlist call doesn't pass a `source`, thread the arriving `src` through to it — smallest change, no new events).
- Emit a **cadence/coverage doc** as part of the pack output (or a companion `spotlights/CADENCE.md`): the running list of pools already spotlighted + the next N candidates (biased to SMALL collaboration-keen protocols, Curve = upper bound, per the 2026-07-12 decision), so the human's weekly posting is systematic and non-repeating.
- OUT of scope: the Canva video, posting, and committing live `spotlights/` output (human-owned, network-gated npm run). No planner UX change beyond threading an existing param.

## Acceptance criteria
- [ ] `generate-spotlight.js` output share URL contains `src=x_spotlight` and a stable per-pool `ref`; all prior params (goal/monthly/pace/chain/token) unchanged
- [ ] A garden opened from a spotlight URL that then opens the waitlist fires `waitlist_opened` with `source=x_spotlight` (asserted via the fixture-routed Playwright pattern of `test_waitlist_seo_entry.js`)
- [ ] Cadence/coverage artifact is produced by the generator (list of covered + next candidates); deterministic given the same pool set
- [ ] Instrumentation: `waitlist_opened` / `plan_created` carry `source=x_spotlight` on spotlight-origin sessions; no new event names added
- [ ] Tests: `node test_planner.js && node test_protocol_parsing.js && node test_qualifier_fix.js` exit 0; spotlight test exits 0; no new deps
- [ ] Any user-facing string (none expected) would go through translations.js EN+KO — confirm none added

## Measurement
Metric: `waitlist_opened` / `plan_created` count with `source=x_spotlight` (attribution existence, not yet a conversion claim). Window: 14 days from first human post. Decision rule: keep (it's plumbing — attribution enabling the next distribution decision); the real read is which spotlights drive funnel entrants once the human posts. Minimum sample: ≥30 before any per-source conversion claim (NORTH_STAR.md).

- `Bloom`'s `source` scope: `Planner()` reads `waitlistSrc = urlParams.get('src')` (planner.js:3529, already used by 062's SEO quick-waitlist path) but `Bloom(props)` (planner.js:1236) is a separate component that only sees what's passed as props — `waitlistSrc` was NOT already in scope there. - Both `trackWaitlistOpened` call sites live inside `Bloom`: the checkout-panel CTA (`.gp-checkout-cta`, reachable, ~planner.js:2639) and `ctaElement` (~planner.js:2381) — the latter is pre-existing dead code, never mounted into any render branch (confirmed by grep; matches backlog 061's notes flagging it as a future-item candidate). Threaded `source` through both for consistency/safety, didn't fix the dead-code issue itself (out of scope).
- `trackPlanCreated` (analytics.js) had no `source` field before this change — added one (see specs/064-notes.md Deviations) since the spec's acceptance criteria requires `plan_created` to carry `source=x_spotlight` too, not just `waitlist_opened`.
- `plan.html` loads `planner.min.js`, not `planner.js` directly — regenerated via `npm run minify` and verified via `test_minified_assets.js` (the exact staleness gap 061 hit with `translations.min.js`).
