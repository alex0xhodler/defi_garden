## Root cause (read from the code this run, file:line)

1. `landing.js:244` gives the landing root `<div>` `className: 'landing-app'` —
   **not** `.app`.
2. `landing.js:356` renders the shared `e('footer', { className: 'app-footer' }, …)`
   inside it, so the landing route gets the OPAQUE, `position: fixed; bottom: 0;
   z-index: 100` footer from `style.css:2513-2524`.
3. `grep -n "\.landing-app" style.css` → **zero matches**. The app-wide clearance
   `.app { padding-bottom: 80px; /* Space for footer */ }` (`style.css:849-853`)
   is class-scoped to `.app`, so the landing route **never inherited it** — this
   route was never wired to the shared clearance in the first place.

This is the third recurrence of one class: item **179** filed it on bare `/`,
item **217** on pool-detail (`padding: 0` cancelled the clearance), item **218**
on the north-star CTA. 219's BACKLOG row names it explicitly: *"item 179's class
still live, because `landing.js:244`'s `.landing-app` root never got `.app`'s
clearance"*.

## The fix — REUSE item 218's pattern, do not invent a new one

**Clearance alone is NOT sufficient here, and the spec pre-registers why.**
Adding `padding-bottom` to `.landing-app` would only lengthen the document; it
cannot move finding (1)'s victim, which sits at `y 760.5` in a 780px viewport
*at scroll 0* — mid-document content under a fixed overlay. That is exactly the
argument `pool-detail-styles.css:1080-1112` already records for item 218:

> "The overlap is content-dependent … so no clearance value fixes the class — the
> fix has to remove the overlay on this view instead."

So apply 218's shipped, verifier-passed pattern to the landing route: the footer
**joins document flow** on this view only.

- `.landing-app` is ALREADY `display: flex; flex-direction: column; min-height: 100vh`
  (`landing-styles.css:4-11`), so `margin-top: auto` on the now-in-flow footer is
  the same flex sticky-footer idiom 218 used — **no new layout mode, no new token,
  no new value**. On a viewport where the content is short the footer still sits at
  the bottom edge; on a long page it sits after the content instead of over it.
- The rule belongs in `landing-styles.css` (the landing route's own sheet), scoped
  `.landing-app .app-footer`, so no other view can be affected. Do NOT edit
  `style.css`'s `.app-footer` block — the fixed footer is still correct for the
  analytics grid.
