# Spec 049: Cross-surface internal linking — token ↔ chain ↔ category (supersedes 043)

## Evidence
Direct grep, 2026-07-12: `grep 'href=".../chains/"' tokens/1inch.html` → **0**. Token pages link only to related *tokens* (023's `relatedFor`); they never link to the `/chains/<slug>` pages (041) or to any pool-type category. Chain pages symmetrically link only to related chains. The two surfaces are topically disconnected islands.
- 2026 SOTA: hub-and-spoke / pillar-cluster is the dominant architecture; bi-directional links concentrate topical authority; LLM crawlers read internal-link topology as a topical-authority signal; programmatic templates should cap links per page (~30–100). A `<TOKEN>` page that names a chain in every row but never links to that chain's page wastes the strongest available internal-linking signal.
- Supersedes the pre-existing **043** (semantic clustering by pool-type category): 043's "group related-links/intros by category" is the content layer of this same cross-linking idea. Fold 043 in here rather than build both.

## Hypothesis
We believe adding token→chain, chain→token, and page→category cross-links (derived from data already on the page) will strengthen the topical graph and improve indexation/authority flow across the two SEO surfaces, because they're currently disconnected and each page already contains the entities (chains, pool types) it fails to link. Confidence: **supported** (grep-confirmed absence + documented 2026 internal-linking consensus).

## Change
Additive internal links, derived from on-page data, respecting the per-template link cap:
1. Token pages: add a small "Chains" nav linking each chain that appears in the token's pool table to its `/chains/<slug>` page (dedup, cap ~8).
2. Chain pages: add a "Top tokens on <chain>" nav linking the highest-TVL tokens present on that chain to their `/tokens/<slug>` pages (cap ~8).
3. Category dimension (folds in 043): group/annotate the related-links or add a compact "By category" set of links keyed on the pool-type categories already computed for the sitemap (Lending / LP-DEX / Staking / Yield-Farming). If category landing/hub pages don't exist yet (they don't — see 045's phase 2), link to the existing `?token=<SYM>&poolTypes=<cat>` app views as an interim target, or defer the category leg until 045's pillar pages land (builder's call; note the dependency).
4. All links must point at pages that actually exist (a generated `/chains/<slug>` or `/tokens/<slug>`) — no links to un-generated slugs (would create soft-404s). Verify against the generated set.

OUT of scope: building new hub/category pages (that's 045); changing ranking, canonical, trust rails, or the pool table.

## Acceptance criteria
- [ ] Token pages render internal links to each distinct chain in their pool table that has a generated `/chains/<slug>` page (deduped, capped); chain pages render internal links to top tokens present on that chain that have a generated `/tokens/<slug>` page. Verified on fixtures where the cross-target set is known.
- [ ] No link points at a slug that isn't in the generated page set (no soft-404 links). Verified programmatically against the generated slug list.
- [ ] Total links per page stay within a sane cap (~30–100 including existing related-links + table + nav). 
- [ ] 043 reconciled: BACKLOG 043 marked superseded-by-049 (or built as this item's category leg).
- [ ] No ranking/canonical/trust-rail change; tests added to `test_token_pages.js`/`test_chain_pages.js` for the cross-links + the no-dead-link invariant, in the `npm test` chain.

## Measurement
Metric: GSC indexation/authority flow across the two surfaces (proxy once 026 unblocks); Window 2–6wk. Decision rule: keep (structural internal-linking correctness).
