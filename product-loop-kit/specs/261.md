# Spec 261: the machine-readable agent surface states a trust rail that is 100× wrong

## Evidence

Read on `main` @ `13712adc4e`, **after** item 227 merged (`d4f7b3cf3c`, PR #425):

- `openapi.json:17` — `"…curated DeFi yield pools matching your criteria with TVL >= $10M and APY <= 1000%."`
- `tools/get_curated_pools.json:5` — `"…filters for safe, substantial pools with TVL >= $10M and APY <= 1000%."`
- The product's actual floor: `app.js:801` `DEFAULT_MIN_TVL = 100000` (**$100K**), re-exported by
  `trust-rails.js` and now *enforced* server-side by the API those two documents describe —
  `edge/api-core.js` requires `../trust-rails.js`, and `edge/API.md:50` states the real numbers
  (`DEFAULT_MIN_TVL = 100000`). So the repo now states the floor **two different ways in two documents
  describing the same endpoint**.
- Provenance of the drift: `6fceca79bb` moved `DEFAULT_MIN_TVL` from `10000000` to `100000` (an authorized
  human trust-rail relaxation). Backlog **254** fixed the nine hand-typed `$10M` strings it stranded — in
  `generate-llms.js`, `generate-stories.js`, `translations.js`, `home.html`. Its population was the *prose*
  stating-sites. **The two machine-readable stating-sites were never in it**, and they are the two an agent
  actually parses.
- Item 227 shipped the API and did not touch either file (`git show --stat d4f7b3cf3c` — 11 files, neither
  present). This is residue of 254, surfaced by 227, owned by neither.

Consequence, stated plainly: an agent that installs `tools/get_curated_pools.json` as a function-calling
manifest, or reads `openapi.json`, is told this API only returns pools above **$10M TVL**. It returns pools
above **$100K**. An agent that trusts the manifest will present a $150K-TVL pool to a user as having cleared
a $10M bar. The rail is not weakened in code — it is **misreported to the one audience that cannot see the
code**.

## Hypothesis

We believe **correcting both stated figures and guarding the whole class with a derived-value test** will
remove a false claim from the agent surface and stop the class from recurring, because the numbers exist in
exactly one machine-readable source (`trust-rails.js`) and nothing currently compares any published
statement against it. Confidence: **validated-pattern** — this is the third time this exact drift has been
found (254's nine prose sites, `test_rail_floor_derivation.js`'s existing guard, now these two), and the fix
that worked before was derivation plus a test, not a careful edit.

## Change

**Leg A (the defect + the class guard) — required.**
1. `openapi.json:17` and `tools/get_curated_pools.json:5`: `$10M` → the real floor. The written string must
   equal `formatTvlFloor(DEFAULT_MIN_TVL)` from `trust-rails.js` (`"$100K"`), not a hand-typed guess.
2. New `test_agent_surface_rail_claims.js` (plain lane, registered in `package.json`'s `test:serial`):
   - **Population derived at test time** by globbing the agent-facing set above — never a hand-typed file
     list; the test prints the file count and the claim count it found.
   - **Claim-shaped scan, not a whole-file number scan**: a TVL-floor claim is a money figure adjacent to a
     floor phrase (`TVL >= …`, `TVL of at least …`, `minimum TVL …`); an APY-limit claim is a percent
     adjacent to a ceiling phrase (`APY <= …`, `capped at …`). This is what keeps `llms.txt`'s hundreds of
     legitimate per-chain TVL figures (`Ethereum ($86.9B TVL)`) out of the population without excluding the
     file — an exclusion list would be exactly the too-narrow check RAZOR warns about.
   - Every found claim is asserted equal to the derived value (`formatTvlFloor(DEFAULT_MIN_TVL)` /
     `APY_SANITY_LIMIT`), with the file:line in the failure message.
   - **Anti-vacuity, in-file**: the test fails if it finds **fewer than 2** TVL claims or fewer than 2 APY
     claims across the population — a scan that silently matches nothing must not read as green.

**Leg B (stated, NOT built in this item).** `openapi.json` also declares a path set that disagrees with what
the Worker routes: it declares `POST /planner` (which `edge/api-core.js` does not implement) and omits
`/api`, `/health`, `/pools/{id}` and `/forever-number` (which it does — `edge/api-core.js`'s `ENDPOINTS`
table routes exactly 5 paths: `/api`, `/api/health`, `/api/pools`, `/api/pools/:id`, `/api/forever-number`;
only `/api/pools` has an `openapi.json` analog). That is **4 undocumented endpoints and 1
documented-but-missing one, out of 5 routed** — the same false-claim class, different axis. Not fixed here:
aligning it means writing response schemas for three endpoints and deciding whether `POST /planner`'s
`x-payment-info` block (item 234's groundwork) is deprecated or removed — a judgement the human owns. Filed
as backlog **262**.

**Explicitly OUT of scope**: `llms.txt` advertising of `/api` (item 227 deliberately deferred it while the
Worker is undeployed — that decision stands and is not reopened here); any change to `edge/api-core.js`,
`edge/agent-log.mjs` or any product render path; any trust-rail VALUE change.

  machine-surface counterpart. Read it first and match its style rather than inventing a second idiom.
