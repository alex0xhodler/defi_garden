# 245 — PR explainer

**Risk tier: HIGH** (re-tiered from the spec's LOW guess — see "Why HIGH, not LOW" below).

## Goal

Item 239's PR (#399) sat open for ~15 hours with a complete, verified-in-its-own-notes build and **zero
signal anywhere** that it was stuck: not merged (correctly — no verifier verdict existed), not PARKED, not
BLOCKED, nothing scheduled to finish it. The only reason a human found it was manual inspection. This item
builds the detector that makes that state visible on every heartbeat tick, going forward, without the loop
ever needing to remember to look.

## Intuition

Two small, boring facts, chained:
1. `build.md` step 7 already writes a status word (SHIPPED/IN_REVIEW/PARKED/BLOCKED) into BACKLOG.md for
   every item, every time — it's the one place status is recorded structurally, as opposed to living in a
   PR title someone might forget to edit.
2. A PR's title usually starts with its BACKLOG item id (`245: ...`), or its branch name does
   (`claude/loop-245`).

Chain them: given an open PR, recover its item id, look up that id's row in BACKLOG.md, and read the
**leading word** of the status BACKLOG.md itself already has (why *leading* word specifically, not
anywhere in the cell, is Round 2's finding — see below). If that word is PARKED or BLOCKED, the PR has a
recorded reason it's still open. If it's anything else (READY/IN_PROGRESS/IN_REVIEW/SHIPPED/DONE/GATED —
i.e. no PARKED/BLOCKED/CULLED marker), nobody has recorded why this PR is stuck, and it's an ORPHAN.

The one wrinkle: 4 real PRs in item 245's own evidence (#393, #332, #309, #316) are legitimately
human-gated (waiting on a rail relaxation, a screenshot review, etc.) but there's no BACKLOG status for
that — the closest, BLOCKED, means something else (an unanswered *design* question, not a built-and-verified
change awaiting a merge action). A generic "does the text mention the word 'human'" fallback was tried
and discarded (Round 2, below) once it was shown to break the tool's own positive control. Today those 4
PRs fall through to ORPHAN — safe (surfaced, not hidden) but not precisely labeled; the gap is documented,
not silently solved.

## What changed and why (diff in reading order)

1. **`product-loop-kit/pr-orphan-detector.js` (new, 314 lines)** — the library + CLI.
   - `parseStatusLegend(backlogMarkdown)`: parses the 9 legend words (READY, IN_PROGRESS, IN_REVIEW,
     SHIPPED, DONE, PARKED, BLOCKED, CULLED, GATED) out of BACKLOG.md's own `# Statuses:` comment block —
     never a hand-typed copy, so the legend can't drift silently out from under the classifier (this is
     what closes item 212's class of bug for THIS detector specifically).
   - `MARKER_CLASS_MAP`: the explicit, reviewable mapping from each of those 9 words to a PR-classification
     bucket (or `null` if that status carries no PR-terminal meaning — e.g. GATED self-resolves, per
     NORTH_STAR: "never pings the human"). Its keys are tested for set-equality against
     `parseStatusLegend()`'s live output on the *real* BACKLOG.md, both directions — a future legend
     addition fails this test until the map is updated, rather than being silently unclassified.
   - `parseBacklogStatusById` / `extractItemId`: the plumbing to go from a PR record to its BACKLOG row.
     `parseBacklogStatusById` uses `splitMarkdownRow()`, not a naive `line.split('|')`, so a literal
     backslash-escaped pipe inside an earlier cell (real example: row 166's `` `pool.url \|\| meta.baseUrl` ``)
     doesn't desync the column count (Round 2 fix — see below).
   - `classifyPR` / `classifyAll`: BACKLOG lookup, ORPHAN otherwise — `leadingStatusWord()` reads only the
     Status cell's FIRST word (Round 2 fix, replacing an earlier whole-cell scan). Every result carries a
     human-readable `reason` string.
   - `computeNextId` / `detectIdCollisions`: Leg B — the ID-collision guard described below.
   - A CLI (`--prs=<path>`) so the heartbeat can invoke this as `node pr-orphan-detector.js --prs=prs.json`
     against data it already fetched — the module itself never calls GitHub.
2. **`product-loop-kit/test_pr_orphan_detector.js` (new, 251 lines)** — 21 assertion groups: legend
   parsing (including a "does not leak table-row prose into the legend" negative case), the legend/map
   set-equality guard, id extraction (including the #309 shape — no parseable id at all), all 5
   classification buckets individually, the required non-vacuity pair (all-terminal → 0 orphans, #399
   shape → exactly 1), Leg B's collision guard with its own red/green self-defeat case, and a static check
   that the module never touches the network.
3. **`product-loop-kit/prompts/heartbeat.md` (+22 lines, new §2c)** — the numbered step: fetch open PRs +
   BACKLOG.md, run the classifier, append the orphan count/list to the signals snapshot, treat a non-zero
   count as a report line, and stay triage-only (never merge/re-verify/renumber from inside the heartbeat).
4. **`product-loop-kit/specs/245-notes.md`** — the design record: why BACKLOG-row lookup instead of
   PR-text scanning (verified against the real 11 open PRs during design — pure text scanning would have
   missed #332 entirely), the named gap in the human-gated fallback, and the mutate→red→restore→green
   non-vacuity proof (byte-identical `md5sum` before/after).

## Round 2 — verifier FAIL, two real bugs found against LIVE data, one design reversal

The first verifier pass didn't just re-run the fixture suite (21/21 green, reproduced) — it ran the
shipped CLI against the real, live 11 open PRs + real BACKLOG.md, which the fixture-only build had never
done, and found two bugs:

1. A whole-cell scan for legend words matched a **negated** mention — row 239 (#399's own row) says
   *"...not PARKED, not BLOCKED, no owner..."*, and `\bPARKED\b` doesn't know the difference, so the
   tool's own required positive control classified as `PARKED` (hidden) instead of `ORPHAN` (surfaced) —
   the unsafe direction.
2. A literal escaped pipe inside an earlier cell (row 166's Title, `` `pool.url \|\| meta.baseUrl` ``)
   desynced `line.split('|')`'s column count, landing the "Status" read on a Title-cell fragment.

**Fix:** rather than patch (1) with a hand-typed negation-word list — a narrower, more fragile version of
the same mistake — the matching rule was rebuilt around the actual writing convention `build.md` step 7
already uses ("item → SHIPPED (or IN_REVIEW / PARKED / BLOCKED)"): the marker **leads** the cell.
`leadingStatusWord()` reads only the first token; a legend word anywhere else in the prose no longer
matches at all. `splitMarkdownRow()` fixes (2) by treating `\|` as a literal pipe.

**Second-order finding, only visible after fixing (1):** re-running the real-data check exposed that the
"scan for the word 'human'" fallback (the original answer to the human-gated gap) is itself unsafe —
measured against all 12 real PR bodies, "human" appears in **8 of 12**, including #399's own body
("...in the human's screenshot..."), flipping the positive control to a false `human-gated`. The fallback
was removed rather than narrowed. Net effect on live data (`node pr-orphan-detector.js --prs=<real 12
open PRs>`): `#399 → ORPHAN` ✓ (the required outcome); **9 of 12** open PRs classify ORPHAN overall —
checked individually, not waved away: several (`#396`, `#331`, `#322`) have BACKLOG rows that already
progressed to SHIPPED via a *different* branch since their PR opened (stale, safe to close); `#332`/`#316`
had their ids renumbered out of BACKLOG since opening; `#393` is a real, currently-unresolved
human-review-failed PR the tool now correctly surfaces for the first time. Full account:
`specs/245-notes.md` "Round 2".

## Why HIGH, not LOW (deviation from the spec's own risk-tier guess)

The spec guessed LOW on the assumption the diff would land "well under 150 lines." It's 651 (mostly the
new library + its test, both intentionally documentation-heavy — the header comment in
`pr-orphan-detector.js` records the weak-hypothesis reasoning per RAZOR, which the spec itself models in
`specs/245.md`). NORTH_STAR.md: *"when in doubt → HIGH. Misclassifying risk is itself a verifier FAIL."*
The diff still touches **zero** product code, trust rails, render paths, or generated SEO surface — every
file is under `product-loop-kit/`, matching the spec's own scope guard ("if the diff leaves
`product-loop-kit/`, the tier is wrong") — but the line count alone crosses the stated LOW threshold, so
this explainer is written at HIGH's bar rather than argued down to LOW's.

## Deviations from spec

- Risk tier LOW → HIGH, per above.
- "Human-gated" detection: a single-word heuristic (`\bhuman\b`) was built, then REMOVED after Round 2
  showed it misclassifies the tool's own positive control on live data. `human-gated` is now reachable
  only via a BACKLOG row leading with `CULLED`; the 4 real human-gated PRs in the spec's evidence fall
  through to `ORPHAN` instead — documented, not silently solved. See `245-notes.md`.
- Marker matching narrowed from "anywhere in the Status cell" to "the cell's leading word only" (Round 2
  fix for the negation bug) — a stricter, more structural rule than the spec's own phrasing implied, kept
  because the looser version is demonstrably unsafe on live data.
- Test file placed at `product-loop-kit/test_pr_orphan_detector.js`, not the repo root — this is loop
  tooling, and the repo root's `test_*.js` convention is reserved for the site's own `test:serial` gate
  (enforced by `test_test_registry.js`); adding a file there would have required editing `package.json`,
  which is itself outside `product-loop-kit/` and would have made the LOW/HIGH scope guard fail for real.

## Quiz

1. Why does the detector look up the PR's item id in BACKLOG.md's Status column instead of scanning the
   PR's own title/body text for words like "PARKED" or "BLOCKED"?
2. What happens if BACKLOG.md's legend gains a 10th status word tomorrow and nobody updates
   `MARKER_CLASS_MAP`?
3. Why does `classifyPR` treat a BACKLOG row status of `CULLED` as `'human-gated'` rather than `'ORPHAN'`,
   given `CULLED` isn't literally in the required 5-class output list as its own bucket?
4. Why was the "scan PR title/body for the word 'human'" fallback removed entirely instead of being kept
   as a secondary signal, and what did measuring it against live data show?
5. Why does `computeNextId` need the list of ids claimed by open PR branches, not just BACKLOG.md's own
   max id on `main`?
