# 175 — explainer (HIGH tier)

## Goal in one sentence
Teach the SEO scanner to notice a link that is *perfectly well-formed and goes nowhere* — the defect class
that shipped four consecutive times (148 → 159 → 166 → 173) because every link check we had only ever asked
"is this query key one the router recognises?"

## The intuition (this is the whole item)
`?chain=Cardano` is a routed link. Every param on it is real. The router accepts it, the app renders, no
error appears anywhere. It just returns **zero pools**, because the app's default floor is $10M and Cardano
has no $10M pool. The page was right. The app was right. The **contract between them** was broken — and
that is precisely the kind of defect a checker built from the last bug's shape cannot see.

So a link check has three levels, and we only had the first:

| level | question | who built it |
|---|---|---|
| 1 **routed** | is the query key one the app recognises? | item 172 (from 166's bug: a stale `?search=`) |
| 2 **resolvable** | does the *value* name a real entity — a project slug, a preset key? | **this item** |
| 3 **non-empty** | does the target, under its own default filters, return what the page claims? | **this item** |

Level 3 is the only one that catches two internally-consistent surfaces with a broken contract. All 1,749 of
item 173's dead CTAs lived there.

## The hard part, and the trap that makes it hard
Level 3 needs a pool population to simulate the filter against — and picking the wrong one produces a
detector that is confidently, catastrophically wrong. We know the exact figure: validating generated `?pool=`
ids against `data/pools-snapshot.json` once reported **4,233 of 4,989 links dead, all false** (the true
number against a live fetch was 15). The token pages draw from the ~16,000-pool feed at a $100K floor; the
snapshot is the ≥$10M, 747-pool set. Comparing one against the other is nonsense.

The resolution is not "be careful", it is a rule that turns on **completeness at a floor** (Territory note
T1):

> `data/pools-snapshot.json` is not a *sample*. Its `minTvlUsd` field says it is **every** pool at or above
> that floor. Therefore:
> - link's effective floor **≥** `snapshot.minTvlUsd` → the snapshot is a **complete** population at that
>   floor → simulate against it, with **zero** false-positive risk.
> - link's effective floor **<** `snapshot.minTvlUsd` → the snapshot is **incomplete** → it must never be
>   used. Use the population the link's generator actually drew from, or declare the link **indeterminate**
>   and *report the count you skipped*.

And where does the sub-$10M population come from, offline, with no network? **The generated page already
contains it.** Both SEO generators render their pool set into a table — one `<tr>` per pool carrying a
`tp-pool-link`/`cp-pool-link` anchor and a TVL money cell. The page carries the $100K set that exists nowhere
else in the repo (Territory note T2).

That is why every pre-173 CTA (no `minTvl` → floor $10M → snapshot-complete regime) is checkable, and every
post-173 CTA (`minTvl=100000` → below it → page's own rows) is checkable, by two different routes that are
each exactly correct for their regime.

## What changed, in reading order

**`audit-app.js`** — one new shared helper block (inserted between 172's `ownedPathResolvesToFile()` and the
static-prescan section) used by **both** prescans, no second copy:

| helper | what it does | why it exists |
|---|---|---|
| `loadDefaultMinTvl(appJsPath)` | regex-reads `const DEFAULT_MIN_TVL = 10000000;` out of **app.js:801** | the value is never re-typed — a second copy of the truth is itself the drift bug the detector exists to catch |
| `loadPlannerPresetKeys(plannerJsPath)` | regex-reads the top-level keys of `var PRESETS = {…}` out of **planner.js:1119** | `PRESETS` is *not* exported; `audit-app.js` already regex-reads planner.js for the same reason (172's `loadPlannerAllowedParams`), so we did **not** add an export to product code |
| `loadSnapshotPopulation(path)` | returns `{pools, minTvlUsd}` | `minTvlUsd` is the floor at which the population is *complete* — the crux of the rule above |
| `linkQueryPairs(suffix)` | first-occurrence key→**decoded** value map | 172's `urlQueryKeys()` only needed keys; levels 2/3 need values |
| `effectiveMinTvl(map, dflt)` | mirrors **app.js:927** | present → `parseInt`; absent → default. An explicit floor **below** the default is honoured, never clamped up |
| `symbolMatchesTokenMirror` | substring, case-insensitive, on `pool.symbol` | mirrors **app.js:835** (vault tickers embed the base asset: `STEAKUSDC` matches `USDC`) |
| `countQualifyingPools` | the filter simulation: token / chain / protocols / poolTypes / tvl / minApy | `getPoolType` is **lazy-required** from `generate-sitemap.js` in a try/catch; if unavailable the poolTypes constraint is dropped **and the drop is reported**, never silently ignored |
| `parsePageOwnPools(html)` | the page's own row TVLs | takes the **LAST** `<td class="num">` cell, not a fixed index — the two generators order their columns differently (chain: Token/Protocol/APY/TVL; token: Protocol/Chain/APY/TVL) |

Then, in **both** `prescanTextSurfaces()` and `prescanStaticPages()`: a one-time-per-scan setup block (each
source with its own stderr-once-per-scan degrade note, mirroring the existing `routerParams` convention),
a **level-2** block, and a **level-3** block — appended after the existing (a)/(b)/(c) rules, one suspect per
sub-rule per file, same leading-count + ≤3-examples + `(+N more)` detail voice as 169/172.

**Two safety properties worth naming:**
- **0.5% downward tolerance on the floor.** Rendered TVL is rounded to ~3 significant digits (`$2.55B`), so
  the comparison is `tvl >= floor * 0.995`. This can only ever make the check *more* conservative — fewer
  flags, never more.
- **The anti-vacuity rail (T8).** A page that has pool-row anchors but yields **zero** parseable rows emits a
  suspect saying *the level-3 population was unparseable* — it does not go quiet. Fires on 0 of 2,200 pages
  today; the day a template change breaks the row markup, the scanner says so instead of going dark. This is
  the guard against the one failure mode this whole item exists to break: a check that dies silently.

**Tests** — `test_audit_prescan.js` +15 cases, `test_audit_text_surfaces.js` +16 cases: red→green per level
on both surfaces, the `?pool=`-liveness non-goal asserted explicitly (the 4,233 trap), the below-default
`minTvl` semantics asserted directly, level-1 regression guard, the anti-vacuity rail, and three degrade
paths.

## Proof it is not vacuous
This is the criterion the spec cares most about, because a link checker that reports 0 is
indistinguishable from a healthy corpus. Measured against **real historical bytes** (a `git worktree` at
`cc243611b^` — the 2,200 pages as they stood before 173 fixed them), not a hand-written fixture:

| corpus | pages | level-3 flagged pages | flagged links |
|---|---|---|---|
| pre-173 (`cc243611b^`) | 2,200 | **1,878** | 4,020 |
| post-173 (HEAD) | 2,186 | **0** | 0 |

Bar was ≥1,700. A run reporting 0 on the pre-173 corpus would have been an automatic FAIL.

## The finding this shipped with — and what we did NOT do about it
On its first run, level 3 found **63 real dead links on the text surfaces**: 62 in `llms-full.txt`'s
`## Chain Pages` section (`/?chain=Cardano`, `/?chain=Celo`, …, each with no `minTvl` so each resolves at
$10M where those chains have zero pools) and 1 in `llms.txt` (`/?poolTypes=Staking&minApy=10`, published as
*"High APY staking"*). This is item 173's defect one surface over, unfixed.

Fixing generated link targets is out of 175's scope by the spec's own non-goals, so it is **filed as item
180**, not silenced and not quietly patched. The consequence was handled explicitly rather than papered over:
`test_audit_text_surfaces.js`'s "zero suspects on the real committed surfaces" assertion was **narrowed to
the sub-rules it was actually written for** (levels 1/2/(b)/(c) — still exactly zero), and a **separately
named case pins the 63 findings as a KNOWN, FILED defect citing item 180**, with exact counts so that 180
landing will re-fail the pin loudly instead of passing silently. The assertion was never relaxed, never
deleted, and `generate-llms.js` was never touched.

`audit-app.js` will now exit non-zero on a clean tree, because 63 real P1 findings exist. That is the signal
working. The merge gate is unaffected: `npm test` → `run-tests.js` runs the audit's *unit tests*, not the
audit.

## Deviations from spec (full log in `175-notes.md`)
1. **`poolTypes` is not applied on the static-page population.** The spec's Change section lists `?poolTypes=`
   among level-3 links. The page's rows carry only a TVL figure — no `symbol`/`chain`/`project` in a form
   worth re-parsing — so running the full filter there would make every real token page collapse to zero and
   fire everywhere. Static-page level 3 applies the TVL floor only; the token/chain constraint is already
   satisfied by construction, since the page's row set *is* the pre-filtered population its generator drew
   from for that exact token/chain. The full filter (including `poolTypes` via `getPoolType`) *is* applied on
   the text surfaces, where a real pool population exists.
2. **1,878/4,020 vs the prototype's 1,879/4,024.** The 0.5% display-rounding tolerance the spec directs is
   the whole delta — a strictly more-conservative direction.
3. **Nine pre-existing assertions narrowed** (5 + 4). Each was narrowed to its own sub-rule's detail phrase —
   the convention rule (c)'s own negative controls already used — with the freed scope re-asserted in a new
   named case. None deleted, no fixture content changed.
4. **`effectiveMinTvl` resolves a present-but-`NaN` value to the default** rather than propagating `NaN` as
   app.js:927 literally would. Same practical outcome (a malformed floor never quietly qualifies anything)
   via an explicit path; the spec's own helper contract asked for this.

## Pre-existing reds, baselined not excused
- `test_seo_cta_targets.js` — 7 dead CTAs (`ankravax`, `gitc`, `mchc`, `n3xt`, `wmetax`, `zeal`, `zro`).
  Reproduced **identically in an isolated `git worktree` at `origin/main` (96fb8c751)** with none of 175's
  changes present. Cause: live pool-population drift since 173 shipped — those tokens' pools fell below
  $100K. Real, on `main` right now, and not 175's doing → filed as item **181**.
- `test_seo_surface_audit.js` criterion 2 (a real Chromium render) fails in this sandbox on render timing.
- Note: the builder initially baselined against a **stale** local `origin/main` ref (`d755df0a2`) and
  concluded main "predates `audit-app.js`". The operator re-fetched (`origin/main` = `96fb8c751`) and redid
  the baseline properly. Recorded because a baseline claim resting on a stale ref is exactly the kind of
  thing that makes "pre-existing" unfalsifiable.

## Quiz (5 questions — answers base64 at the bottom)

**Q1.** `?chain=Cardano` passes level 1 (routed) and level 2 (the value names a real chain). Why does it
still fail level 3, and what makes that failure invisible to *both* of the surfaces involved?

**Q2.** Validating generated `?pool=` ids against `data/pools-snapshot.json` once reported 4,233 of 4,989
links dead when the true number was 15. State the rule that prevents this, and explain why it makes level 3
safe for a `?chain=Cardano` link but unsafe for a `?token=USDC&minTvl=100000` link.

**Q3.** `parsePageOwnPools()` takes the **last** `<td class="num">` cell of a row rather than index `[3]`.
What would break if it used a fixed index, and on which pages?

**Q4.** Level 3 found 63 real dead links in `llms*.txt`, which invalidated a test asserting "zero
`link-target-integrity` suspects on the real committed surfaces". Three responses were available: relax the
assertion, fix `generate-llms.js`, or narrow-and-pin. Why is narrow-and-pin the only correct one — and what
specifically would fixing `generate-llms.js` have destroyed?

**Q5.** The anti-vacuity rail fires on 0 of 2,200 pages, so it currently detects nothing. Argue why shipping
it is not dead code, referencing the failure mode named in
