# Spec 013: Sitemap quality threshold — only emit URLs with real content

## Evidence
specs/010-diagnosis.md ranks this #013 among the GSC fixes: "Discovered — currently not indexed" (10,585) and part of "Crawled — currently not indexed" (22,877) trace to a 20,831-URL sitemap with weak per-URL quality signals — Google rations crawl budget on programmatic sitemaps and skips thin/near-duplicate pages. Today's `generate-sitemap.js` filters at the *pool* level only (`tvlUsd >= 1000`, `apy > 0.01%`, valid symbol regex) — it never checks that a URL's own combined result set is substantial. A token can enter `sitemap-tokens-all.xml` off a single $1,000 pool. Separately, `app.js`'s own default view (no `minTvl` param) filters to `DEFAULT_MIN_TVL = $10M` (app.js:730) — so a sitemap URL that doesn't clear that bar renders through the "no pools" empty state per 012's honest-empty-state logic (noindex'd) to any crawler using default params. The sitemap is currently advertising URLs its own homepage would refuse to index.

## Hypothesis
We believe raising the per-URL sitemap inclusion bar to mirror the app's actual default rendering threshold — at least 2 live, non-anomalous pools **and** combined TVL ≥ `DEFAULT_MIN_TVL` ($10M) for that exact URL's filter (token alone, token+chain, token+category) — will shrink the sitemap to only URLs that render real, substantial content by default, reducing crawl-budget waste and the Discovered/Crawled-not-indexed classes over the next validation cycle. Confidence: supported — this makes the sitemap generator's notion of "valid" match the app's own trust-rail default exactly, closing the gap diagnosis identified. Not a proxy metric; it's the same predicate the live page already uses.

## Change
`generate-sitemap.js` only:
1. Add an anomaly guard matching app.js's trust rail: `const APY_SANITY_LIMIT = 1000;` and treat a pool as disqualified from the "quality" pool count if `(pool.apyBase||0)+(pool.apyReward||0) > APY_SANITY_LIMIT` (mirrors `isAnomalousApy` in app.js — do not change app.js).
2. Add `const SITEMAP_MIN_TVL = 10000000;` (= app.js's `DEFAULT_MIN_TVL`, duplicated here since this script has no import of app.js — comment noting the two must stay in sync).
3. For each candidate URL family, compute the exact pool subset that URL's default query would show (same fields the app filters on: symbol match for `?token=`, chain match for `&chain=`, category/poolType match for `&poolTypes=`), restricted to pools with `tvlUsd >= SITEMAP_MIN_TVL` and not anomalous. Only emit the URL if that subset has **≥ 2** pools:
   - `sitemap-tokens-all.xml` (`?token=X`): qualify token X only if ≥2 qualifying pools across all chains.
   - `sitemap-chain-*.xml` (`?token=X&chain=Y`): qualify the combo only if ≥2 qualifying pools for that exact token+chain pair.
   - `sitemap-category-*.xml` (`?token=X&poolTypes=Y`): qualify the combo only if ≥2 qualifying pools for that exact token+category pair.
   - Chain landing pages (`?chain=Y` alone, one per chain sitemap) and the 3 main-sitemap threshold pages (`?minTvl=`, `?minApy=`) are unaffected — they aggregate across many tokens and already clear volume; leave as-is.
4. Existing per-pool prefilters (`tvlUsd >= 1000`, `apy > 0.01%`, symbol regex) stay as the token/chain *discovery* pass (unchanged) — the new ≥2-pools-at-$10M-TVL check is an additional gate applied when deciding whether to emit each URL, not a replacement.
5. Log a summary line (`console.log`) of how many candidate URLs were dropped by the new threshold per sitemap family, so the change is auditable from CI output.
6. Regenerate the sitemap files (`npm run sitemap`) and commit the output — this script has no build step; the generated XML files are the deliverable along with the script change.

OUT of scope: app.js/home.html (011, 012 own those), new static landing pages (014), the apex/referral redirect (015), sitemap file structure/naming, robots.txt.

## Open questions
None blocking — the $10M floor is not a new number, it's DEFAULT_MIN_TVL already established as the app's own default rendering threshold (app.js:730); reusing it here is the point of the fix, not a new policy decision.

## Territory notes
- `generate-sitemap.js` has no dependency on app.js (separate Node script, no shared imports) — the sync between `SITEMAP_MIN_TVL`/anomaly logic here and `DEFAULT_MIN_TVL`/`APY_SANITY_LIMIT` in app.js is by convention + comment, not by import. A future refactor could extract a shared constants file, but that's out of scope for this surgical fix.
- Pool-to-symbol splitting logic already exists (`pool.symbol.split(/[-_\/\s]/)`) and is reused for the qualifying-pool count — do not re-derive tokens differently than `extractValidCombinations` already does.
- Sandbox cannot reach `yields.llama.fi` per 010-diagnosis; running `npm run sitemap` requires live network — if the sandbox blocks it, run with best-effort and note in `013-notes.md` if before/after counts couldn't be captured live (do not fabricate numbers).
