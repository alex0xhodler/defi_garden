# 170 — The browser lane is structurally unrunnable: make it safely parallel

**Status**: READY → IN_PROGRESS (2026-07-28)
**Score**: 7.0 · **Risk**: HIGH (diff size; loop tooling, no product surface)
**Promoted by**: the build loop, 2026-07-28. No takeable READY item existed — 148 reads READY on `main`
but has been in flight as human-gated PR #306 since 2026-07-26 (NEVER-list question, unanswered), and the

## The evidence (all pre-existing in this repo, re-measured this run)

`run-tests.js:200` forces the browser lane to one worker:

```js
function defaultJobsFor(lane, jobsOverride) {
  if (lane === 'browser') return 1; // forced — fixed-port real-Chromium files must serialize.
```

`--jobs` is accepted but **silently discarded** for that lane. The lane holds **64 of 100** files
(`node run-tests.js --list` → `TOTAL files=100 plain=36 browser=64`). Measured this run on this
checkout: `test_default_sort.js` = **28.3s** wall-clock. At that rate the serial lane is **~30 minutes**,
and it is worse than that in practice — `specs/163-notes.md:180` records `test_smoke.js` blowing a 120s
cap and `test_search.js` needing ~550s.

Consequence, recorded verbatim by five consecutive build runs in `LOG.md` and their notes files:

> **Browser lane (~63 files) NOT run — 5-minute timebox; stated unrun, never implied green.**
> — `LOG.md`, item 169 entry (and 166, 165, 163, 162 before it)

So the rendered half of the merge gate — every Playwright test that guards the actual product surface —
has not executed on any shipped item for a week. Items merge on a hand-picked `--only` subset. The
2026-07-11 standing decision ("UX items: acceptance = rendered product behavior") is being satisfied
per-item and violated per-regression: nothing checks that item N did not break item N-30's surface.

**The stated blocker is real, not folklore.** Browser test files hard-code a listen port, and the
literals collide across files. Extracted this run (`const PORT = <n>` per file):

| port | files sharing it |
|---|---|
| 8796 | `test_kpi_momentum`, `test_kpi_sharpe_sort`, `test_mean30d_sanity`, `test_pool_logo`, `test_report_share`, `test_token_loading_state`, `test_waitlist_seo_entry` (7) |
| 8799 | `test_default_sort`, `test_growth_capital_projection`, `test_hero_copy`, `test_kpi_seo_enrichment`, `test_plan_clean_url` (5) |
| 8795 | `test_analytics_host_gate_render`, `test_kpi_track_record`, `test_landing_return`, `test_list_polish`, `test_tend_reminder` (5) |
| 8819 | `test_earnings_dedup`, `test_ko_pool_money_honesty`, `test_protocol_cta_fallback`, `test_repeat_cta` (4) |
| … | 8801 (4), 8794/8797/8798/8802/8803 (3 each), 8793/8800/8815 (2 each), plus ~20 singletons |

Two files run concurrently on the same port produce `EADDRINUSE` or, worse, a green run against the
*other* file's server — a false pass in the merge gate. That is why the constraint exists.

## The fix

Do **not** rewrite 59 test files. Teach the runner the constraint instead: a **conflict-aware
scheduler** that runs browser files concurrently *except* where they contend for the same resource.

1. **Static port extraction** — for each file, scan its source (the way `classifyLane()` already scans
   `require`s) for port literals and return a set. Recognise the declaration form actually used in this
   repo (`const|let|var <NAME containing PORT> = <digits>`) and any `localhost:<digits>` /
   `127.0.0.1:<digits>` literal.
2. **Conflict keys** — a file's key set = its ports, plus one extra shared-resource key for the two
   files that write `audit-findings.json` (`test_audit_app.js`, `test_audit_runner.js`). That file is
   `audit-app.js`'s `DEFAULT_OUT` and is committed to the repo; `specs/169-notes.md` records a run
   silently overwriting it. They must never run concurrently with each other.
3. **Unknown-port files are exclusive.** A browser file from which no port literal can be extracted may
   be opening a port through a helper. It runs **alone** (scheduler drains in-flight work first, starts
   nothing else while it runs). Conservative by construction: an undetected port can never collide.
4. **Scheduling** — the queue picks the next file whose key set is disjoint from every in-flight file's
   key set; if none is eligible it waits for a slot rather than reordering into a conflict. Ordering
   otherwise stays the `test:serial` order, so output remains comparable run to run.
5. **Default jobs for the browser lane** = `max(1, min(3, cpus - 1))` (3 on this 4-core box), overridable
   by `--jobs`. `--jobs=1` must reproduce today's exact serial behaviour.

Non-goals: changing any test file's port; making `test_search.js`/`test_smoke.js` faster; touching the
plain lane's existing scheduler; `package.json` script changes.

## Acceptance criteria

1. `defaultJobsFor('browser', …)` no longer returns a forced 1; `--jobs=N` is honoured on the browser
   lane, and `--jobs=1` yields byte-comparable behaviour to `origin/main` (same files, same order, one
   at a time).
2. Port extraction is correct on the real corpus: a test asserts the 8796 group (7 files) and the 8799
   group (5 files) above are each detected as sharing a port, from the real files on disk, not fixtures.
3. **No two files with an overlapping key set are ever in flight simultaneously.** Proven
   deterministically: a unit test drives the scheduler with a stub runner that records
   start/stop intervals and asserts zero overlap between conflicting pairs — and asserts non-conflicting
   pairs *do* overlap (so a scheduler that silently serialised everything would FAIL this test).
4. Unknown-port browser files run exclusively — asserted by the same interval test.
5. A **real** measured run: ≥8 browser files spanning at least two conflict groups (including two files
   that share a port) execute under `--lane=browser --only=…` with the new default jobs, all pass, and
   wall-clock is materially below the serial sum. Both numbers recorded in `170-notes.md`. The full
   64-file lane is NOT required (5-minute timebox) — if it is not run, say so plainly.
6. `node run-tests.js --lane=plain` stays green (36 files), and `test_run_tests.js` continues to pass in
   full.
7. Trust rails, `home.html` router, `?token=/?chain=/?pool=`, generated SEO surface, `package.json`
   dependencies: byte-untouched (grep-proved in the notes).

## Measurement / decision rule

No Mixpanel funnel metric — loop tooling under the 2026-07-23 pre-traffic quality mandate (142/154/163/
166/169 disclosure pattern). The honest proxy: the **next** build run can state a browser-lane result
instead of "NOT run — timebox". If three consecutive runs still cannot run the lane inside the timebox,
the item did not achieve its purpose and the follow-up is per-file port de-collision, not more scheduling.

## Open questions

None that change the architecture. The conservative choices (unknown-port ⇒ exclusive; default jobs 3,
not cores) are deliberately reversible in one constant each.
