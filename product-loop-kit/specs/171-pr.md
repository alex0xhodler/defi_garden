# 171 — a prescan alarm must respect its own rendered verdict

**Risk tier: HIGH** (verifier-assigned independently: 269-line code diff vs the LOW lane's 150-line
cap, and the change alters the blocking semantics of `audit-app.js`'s exit contract — the repo's own
red gate). Verifier **PASS, 10/10 criteria**, every one independently re-derived. NEVER list clean.

Full explainer + quiz per the HIGH gate. Build notes: `specs/171-notes.md`. Spec: `specs/171.md`.

---

## The goal, in one sentence

Stop the product-audit scanner from reporting a blocking P0 for a defect that its own rendered check
just disproved — without weakening any alarm that is genuinely red.

## The intuition

`audit-app.js` works in two stages. First a **prescan**: a fast, browser-free sweep over the pool
snapshot and the 2,181 static SEO pages, looking for data that *smells* wrong. Prescan can't see the
product, only the data, so its job is not to accuse — it is to **promote**: pick the suspicious ones
and force them into the rendered sample so a real Chromium pass can look at the actual page.

That second stage is the one that knows the truth. And we were throwing its answer away.

The prescan emitted its aggregate finding — severity and all — *before the browser ever opened*
(`audit-app.js:690` for static, `:926` for pools). Nothing downstream ever revisited it. So the
scanner could promote a pool, render it, find nothing wrong, and still report a blocking P0 about it.

## What was actually happening

Measured on a clean `npm ci` checkout of `main`, 2026-07-29:

```
[audit] findings: 6 total, 6 blocking (P0/P1)
exit=1
```

Five of those six are item **148**'s junk token pages (`<h1>8OCT2026 DeFi Yields</h1>` and friends).
Those are correctly red: the product really does ship them, and the fix is sitting in human-gated
PR #306. **This item does not touch them.**

The sixth was not real:

> `pool-prescan:mean30d-rail-breach` **P0** — `201e5f6e (balancer-v2/WSTETH-AAVE)`:
> `apyMean30d = 27421.09636` exceeds the 1000% rail

That value is upstream DefiLlama garbage — 27× `APY_SANITY_LIMIT`. But **the product already handles
it correctly.** Item 144 added `mean30dSane` (`PoolDetail.js:161-164`), and a `grep -n apyMean30d`
across every product file shows `PoolDetail.js` is the only place the field is ever rendered, with
all five of its read sites behind that gate:

| `PoolDetail.js` | what it renders | gated? |
|---|---|---|
| `:1298` | the "30d Mean APY" card | ✅ `mean30dSane &&` |
| `:1384` | 071 rate-volatility note | ✅ |
| `:1412` | 088.1 track-record note (negated) | ✅ |
| `:1460` | 103 momentum note (negated) | ✅ |
| `:1506` | 104 TVL-trend note (negated) | ✅ |

The audit had *already proved this itself*: the same run promoted that pool, rendered it as
`pool-detail:201e5f6e`, ran the full pool check battery against it, and returned **zero findings**.
Then it reported the P0 anyway.

**Why that is worth a HIGH-tier change and not a shrug.** `audit-app.js:1702` is
`process.exit(blocking.length > 0 ? 1 : 0)` — a gate. This particular P0 can never go green: the
snapshot regenerates daily from the same feed, the pool keeps its garbage mean, 144's gate keeps
correctly suppressing it. A detector that permanently accuses the product of a defect its own
verification disproved is the `ci-signal-honesty` failure mode. It teaches every future reader to
discount the number, and a genuinely new P0 arrives inside a count that was already non-zero.

## What changed, in reading order

**1. Two builders now hand back the list they counted from** — `buildStaticSurfaces()` returns
`prescanSuspects` (`:673`, `:684`, `:739`), `buildPoolSurfaces()` returns `poolPrescanSuspects`
(`:917`, `:928`, `:993`). Same anchor-excluded suspect arrays the aggregate findings were already
tallied from; previously they were computed, used for a count, and dropped.

**2. One shared helper, `reconcilePrescanFindings()`** (`:1496-1557`, exported). For each aggregate
`<prefix>:<signal>` finding it downgrades severity to `P2` **iff**:

- every suspect carrying that signal was **promoted**, **and**
- every one of those promoted surfaces was **covered by this run**, **and**
- every one of them produced **zero** rendered findings.

Otherwise severity is untouched. The detail string gains an explicit reason naming the surfaces that
cleared it, so the downgrade is never silent.

The pool and static legs share the helper verbatim — the spec required this so they can't drift —
with two tiny adapters for the two suspect shapes: `suspectKey()` (a slug vs. a full pool id) and
`keyToSurface()` (`static-page:<slug>` vs. `pool-detail:<8-char-prefix>`).

**3. Two call sites in `runAudit()`** (`:1726-1753`), placed deliberately **after** the `opts.only`
allowlist filtering and **after** the render loop — it needs `surfacesCovered` and the real
per-surface findings to reconcile against.

**4. `blockingFindings()` is untouched.** It already filters `P0|P1`, so `P2` is non-blocking for
free. The finding is still emitted, still counted in `findings.length`, still written to
`signals/audit-findings.json`. **Nothing is hidden — it stops being an alarm.**

## The rule that carries the weight

> **Unverified is not clean.**

If even one suspect was never promoted (promotion cap, promotion disabled, `opts.only` scoping the
render away), severity stays exactly where it was. A downgrade is only ever earned by a render that
actually happened and actually came back empty.

This is what protects item 148. Its 7 junk-slug suspects exceed the promotion cap — only 4 were
promoted — so `allPromoted` is false and it stays **P1 and blocking**, with its detail string
untouched. The alarm the product deserves survives; the one it doesn't, doesn't.

## Deviations, disclosed

Five, all in `171-notes.md`. The two worth naming here:

- **The new fixtures drive the exported helper directly rather than through Chromium.** The live
  A1/A2 run is the end-to-end control that the wiring is right; the fixtures buy the branch coverage
  a single live run can't reach, at zero added browser time.
- **`buildStaticSurfaces` is newly exported but no test consumes it.** A one-line, zero-runtime
  addition, symmetric with `buildPoolSurfaces` already being exported. The verifier called this the
  closest call in the diff and judged it an in-scope micro-addition rather than a drive-by.

## What was NOT run

The remaining **56 of the 64 browser-lane files** (`node run-tests.js --list` → 64 browser / 36
plain). They exceed the 5-minute foreground timebox. Their status on this branch is **unmeasured** —
stated, not implied green.

What *was* run: `--lane=plain` **36/36**; all seven `test_audit_*` files individually **87/87**; and
`test_seo_surface_audit.js` **5/5** — the eighth `require('./audit-app.js')` consumer, which the
verifier ran because the builder had not.

## Scope and safety

`git diff --name-only origin/main` → `audit-app.js`, `test_audit_pool_prescan.js`,
`test_audit_prescan.js`, `product-loop-kit/signals/audit-findings.json`.

No product file. `PoolDetail.js` / `app.js` / `planner.js` / `home.html` absent from the diff.
`git diff -S APY_SANITY_LIMIT origin/main` empty — no trust rail moved (the rails are what the
prescan *mirrors*; they are unchanged). `package.json` byte-identical, no new dependency. No SEO
surface deleted or de-indexed. `telegram-bot/`, `whatsapp-bot/`, `workers/` untouched. **NEVER list
clean.**

`signals/audit-findings.json` is `DEFAULT_OUT` — every CLI run overwrites it unconditionally,
including the runs A1 and A8 mandate. The verifier judged it legitimately in scope: its diff carries
only `generatedAt`, a playwright version bump, date-seeded rotation churn, and the one intended
P0→P2 flip. Leaving a stale artifact that contradicts the code on disk would be the very thing this
item exists to prevent.
