# 140 — PR explainer (HIGH tier)

## Goal
Revive the snapshot fast path in production. Spec 059 built a committed, trust-railed static snapshot (`data/pools-snapshot.json`) so pool data paints instantly instead of waiting on the live `yields.llama.fi/pools` fetch. A freshness gate (`SNAPSHOT_MAX_AGE_MS`) protects against serving a stale snapshot. That gate was set to **15 minutes**, sized for a ~5-min snapshot cadence that **never materialized** — so it rejected an otherwise-valid snapshot ~85–90% of the day and dropped nearly every visitor onto the slow live fetch.

## Intuition
The snapshot's real refresh cadence is set by whatever writes the committed file. Two candidates:
- The **109 poller** — writes **Cloudflare D1**, NOT the repo file. Irrelevant to this gate.
- The **`sitemap-update.yml` CI** — actually bakes `data/pools-snapshot.json`. Git log on `data/pools-snapshot-meta.json` shows ~8 bakes/24h → a real cadence of **~1.5–3h**.

A 15-min gate against a 1.5–3h cadence is guaranteed to be stale most of the time. The fix is to size the gate to the real cadence, keeping the original "3× to cover a missed run" spirit: **6h ≈ 2× the slowest observed gap.**

## What changed and why (diff in reading order)

1. **`app.js`** — `SNAPSHOT_MAX_AGE_MS`: `15 * 60 * 1000` → `6 * 60 * 60 * 1000`. The comment now states the real CI-bake cadence and explicitly that the 109 poller writes D1, not this file (killing the "~5-min cadence" myth the old comment propagated). The gate logic itself (`age > SNAPSHOT_MAX_AGE_MS → return false → loadLive()`) is unchanged — only the threshold.

2. **`planner.js`** (documented deviation — see 140-notes.md) — the byte-identical `SNAPSHOT_MAX_AGE_MS = 15 * 60 * 1000` gate on the bare-`/` planner path (spec 059 C1). The planner is the DEFAULT surface; leaving it at 15 min would leave the largest chunk of sessions on the dead fast path, directly undercutting the spec's hypothesis. Same value, same rationale, no behavioral change beyond gate width.

3. **`app.compiled.js`, `app.compiled.min.js`, `planner.min.js`** — regenerated via `npm run compile && npm run minify` (house rule since 052/053; source is the edit surface). Folded constant `216e5` (= 21,600,000 = 6h) verified present; old `9e5`/`15*6e4` gone.

4. **`test_snapshot_first.js`** — `staleTs` 1h → 7h (1h no longer clears the 6h gate). New `withinTs` (3h) + scenario **(c2)**: a 3h-old snapshot — which the OLD gate would have rejected — is now served with the live endpoint aborted (asserts 0 live requests). Scenario count 7 → 8.

## What did NOT change (trust-rail & routing safety)
- `?pool=` deep links ALWAYS go live (`snapshotEligible = !urlParams.pool && …`) — gate width is irrelevant to them.
- Escape-hatch refetch on sub-floor `minTvl` — unchanged (scenario (e) still green).
- Snapshot content is already `$10M`-railed; APY staleness ≤ bake gap was accepted when 059 shipped. No `APY_SANITY_LIMIT` / `DEFAULT_MIN_TVL` / anomaly / haircut touched. Nothing on the NEVER list; no out-of-scope dirs.

## Deviations from spec
One: extended the identical fix to `planner.js` (justified above, detailed in 140-notes.md). Also documented two PRE-EXISTING test failures reproduced at HEAD with the diff stashed — scenario (f) planner-hero flake and `test_minified_assets` plan.html/planner.js — neither caused by this diff.

## Measurement
`data_load_time` events with `source=snapshot` ÷ all `data_load_time` (prod). 14-day window. Keep if snapshot share rises materially above the pre-ship ~10–15% eligibility window; revert only on error-rate rise or a data-staleness complaint. At current traffic the count may close INCONCLUSIVE — the rendered test (c2) is the functional gate.
