# Spec 044: Verify the SEO-surface instrumentation actually fires on a real render (039 static pages + 020 `?pool=` landings)

## Evidence
From `signals/2026-07-12.md` (live Mixpanel, 14d, project 4042048):
- `page_view` total 330, broken down by path: `/`=224, analytics search/chain paths≈106, **`/tokens/*` = 0**, **`/pool/*` = 0**.
- `pool_view` total 3, **all `source=card_click`; `source=url_direct` = 0**.
- 039 (PR #131) instrumented all 2,045 `/tokens/<slug>` pages with `page_view`; 020 (PR #104) added `pool_view` `source=url_direct` on `?pool=` deep-link landings. Both were verifier-PASS on **fixture-string assertions only** — per LOG, Playwright never ran against a real rendered page in this sandbox (node_modules/network blocked), so live-page firing was never observed, only the injected snippet's byte-identity to home.html's working pipeline.

The zero could be the expected null (no organic SEO traffic yet — GSC indexing is a 2–6wk cycle just begun) OR a silent instrumentation failure (the snippet is present but never emits on a real load). These two are indistinguishable in the Mixpanel data and must be separated before the SEO theme's ROI can ever be read.

## Hypothesis
We believe a real headless render of one generated `/tokens/<slug>` page and one `?pool=<id>` URL will emit `page_view` (path `/tokens/<slug>`, `page_type=token`) and `pool_view` (`source=url_direct`) respectively — confirming the shipped instrumentation is sound and the Mixpanel zeros are a traffic problem, not a wiring problem. Confidence: supported (byte-identity to a known-working pipeline was verified at ship) — but unobserved on a live render, which is exactly the gap 017's post-mortem warned about (fixtures passed, product behavior unverified).

## Change
Verification-only. Add a Playwright check (extend `test_token_pages.js`/`test_stories.js` pattern or a new `test_analytics_fires.js`) that:
1. Serves a freshly generated `/tokens/<slug>.html` locally, loads it in headless Chromium with the Mixpanel network call stubbed/intercepted, and asserts a `page_view` track call is made with `page_type=token` and the correct path.
2. Loads the app at a `?pool=<id>` URL (local-vendored React + fixture pools, the established sandbox pattern from test_search.js/024/042) and asserts `pool_view` fires with `source=url_direct` exactly once (not double-firing vs card_click).

OUT OF SCOPE: any product-behavior change, new events, waiting on organic traffic, GSC. If the render shows the event does NOT fire, this spec's build loop fixes the wiring (that becomes the real work); if it fires, close as verified and the Mixpanel zeros are officially attributed to "no SEO traffic yet — measure via GSC once 026 unblocks."

## Acceptance criteria
- [ ] A headless render of a generated `/tokens/<slug>` page issues exactly one `page_view` Mixpanel track call with `page_type` (or equivalent) = token and `path` = the page's own path — asserted by intercepting the network/track call, not by grepping the HTML source.
- [ ] A headless load of a `?pool=<id>` URL issues exactly one `pool_view` track call with `source=url_direct`, and a subsequent internal card click issues `source=card_click` — no double-fire on the landing path.
- [ ] If either fails: the wiring is fixed and the same check passes green; the fix diff touches only the generator (`generate-token-pages.js`) and/or `app.js`'s `?pool=` landing effect, no trust rails.
- [ ] Tests: new/extended assertions added to the `npm test` chain; timeboxed to the 5-min foreground cap per standing decision.
- [ ] Instrumentation: no new events introduced — this verifies existing `page_view`/`pool_view` only.

## Measurement
Metric: pass/fail of the live-render assertions (a verification item, not an A/B). If it forces a wiring fix, follow-on metric = `/tokens/*` `page_view` count and `pool_view source=url_direct` count begin appearing once organic traffic arrives (read via GSC/Mixpanel over the SEO validation cycle). Window: n/a for the verification; the traffic read is gated on 026 (GSC connector) + organic indexing. Minimum sample per NORTH_STAR.md for any later traffic claim (≥30 events).

## Risk tier (builder's guess — verifier assigns independently)
LOW — a verification harness plus, at most, a small additive wiring fix to already-shipped instrumentation (no trust rails, no new deps, diff expected well under 150 lines). NOTE: if the fix touches `generate-token-pages.js` (SEO-surface generator) or `app.js`'s router-adjacent `?pool=` effect, the verifier may re-tier to HIGH per NORTH_STAR's "generated SEO surface" / parameterized-URL rules — respect that.
