# 120 — Explicit UTM / referrer acquisition capture on analytics events

Human 2026-07-22: the "undefined referrer" in Mixpanel looked like a bug; fix per proper Mixpanel
implementation. Investigated + shipped the real, correct improvement.

## Finding (the honest diagnosis — NOT a referrer-stripping bug)

- `Referrer-Policy: strict-origin-when-cross-origin` (vercel.json:51) is the standard modern policy — it
  does NOT strip `document.referrer`; a real Google/X referral still populates it (origin at minimum).
- The app loads the official Mixpanel lib (`mixpanel-2-latest.min.js`) which **auto-captures** `$referrer`,
  `$referring_domain`, and `utm_*` campaign params (confirmed from source: `_.info.campaignParams` in
  mixpanel-js `src/utils.js`, registered in `src/mixpanel-core.js`). `track_pageview:false` does NOT
  disable this — it only suppresses the auto pageview event.
- `analytics.js` also already sends `referrer: document.referrer || 'direct'` on every event — never
  literally undefined.

**Conclusion:** the `undefined $referrer` the loop saw on the 07-2x sessions is the CORRECT value for
referrer-less bot/direct traffic — it corroborates the crawler read, it is not a capture bug.

## The real gap this fixes (forward-looking, for distribution)

The app relied SOLELY on the library's auto-captured super properties and added no acquisition props of
its own. Item 064 makes the 069 spotlight links carry `utm_*`/`ref`; to attribute that traffic robustly
under stable, queryable names on our OWN events (`waitlist_opened`, `session_start`, …) — independent of
the lib's super-property/proxy behavior and surviving SPA navigation that clears the query string — the
app should capture acquisition explicitly. This is what makes 064/069 attribution bulletproof the moment
real campaign traffic arrives.

## Change (additive only — analytics.js)

- `captureAcquisition()`: parse the landing URL's `utm_source/medium/campaign/term/content`, `ref` (the
  064 param), and common ad click-ids (`gclid/fbclid/twclid`), plus `referring_domain` from
  `document.referrer`. Every key OMITTED when absent (never an empty/"undefined" string); fully guarded
  (try/catch, bad referrer → no throw); values capped at 200 chars.
- `init()`: capture ONCE at landing (window `load`, before SPA navigation clears params); store on
  `this.acquisition` for the whole session.
- `getBaseContext()`: spread `...this.acquisition` so every event carries it. Existing `referrer` and all
  other props untouched.

Session-scoped (matches the loop's session analysis); the lib keeps its own first-touch super props.
No new event, no trust-rail/SEO surface, no credentials. `analytics.js` ships unminified (no min regen).

## Risk
LOW-MEDIUM — measurement surface, but purely additive event enrichment behind a single guarded method;
the host-gate (096) and all existing events are unchanged. A throw is swallowed (never breaks tracking).

## Honesty note for the human
This does not "recover" the undefined values on the current bot traffic — those are correctly empty. It
makes real referral/campaign traffic attributable going forward, which is exactly what's needed before
069 goes out. If you want to confirm capture end-to-end, hit a preview with
`?utm_source=test&ref=abc` and check the event props (localhost is host-gated to no-send by 096, so use a
prod-host preview).
