# 220 — explainer: the landing page's footer was painting over its own content

**Tier: HIGH** (render-path change on the product's DEFAULT surface, bare `/`).
Full walkthrough + quiz per NORTH_STAR.md's risk policy.

## Goal

Bare `/` — the landing route, the first thing every cold arrival sees — had its
bottom band of content permanently covered by its own footer. This ships the fix
and a rendered regression gate so it cannot come back silently.

## The intuition, in one picture

The app has ONE footer component, `.app-footer`. It is **opaque**, **`position:
fixed`**, pinned to `bottom: 0` with `z-index: 100`. A fixed element is lifted out
of the document — it floats above everything and the page below has no idea it is
there. So every view that renders it must *manually* reserve space for it. The
design system does that with one shared rule:

```css
.app { padding-bottom: 80px; /* Space for footer */ }   /* style.css:849-853 */
```

That rule is scoped to the class `.app`. The landing route's root element is
`<div class="landing-app">` (`landing.js:244`) — a **different class**. It renders
the same footer (`landing.js:356`) but was never wired to the clearance:
`grep -n "\.landing-app" style.css` returns **zero matches**. So on this one route
the footer floated over the content with nothing holding the content clear of it.

## Why this is the third time we've paid for this

This is one defect class, not three incidents:

| item | route | what cancelled/missed the clearance |
|---|---|---|
| 179 | bare `/` | filed, fixed on one route, never ported |
| 217 | pool-detail | `.app.pool-detail-view { padding: 0 }` cancelled it |
| 218 | pool-detail | the `garden_cta` CTA sat mid-page under the fixed footer |
| **220** | **landing** | **`.landing-app` never inherited it in the first place** |

Item 219 built the machine that finally caught it: an **occlusion lens** in
`audit-app.js` that, on every audited surface, measures at `scrollY = 0` and at
bottom-of-scroll and reports a victim only when geometry *and* `elementFromPoint`
agree. 219 shipped the lens and deliberately fixed nothing it found. This item is
the fix for the finding on the default surface.

## The evidence (measured, not argued)

Reproduced this run on unmodified `origin/main` at 768×780, real Chromium:

**At rest, `scrollY = 0`** — before the user touches anything:
```
footer  <footer class="app-footer">   rect {x:0,     y:722,   w:768,   h:58}
victim  <span> "Live DefiLlama data"  rect {x:449.7, y:760.5, w:110.9, h:18}
elementFromPoint(victim's lower band) -> <footer class="app-footer">
```
100% covered, and the hit-test proves the footer was intercepting the *click*, not
merely painting over the text.

**At true bottom of scroll** (`scrollTop 100 + innerHeight 780 = 880 = scrollHeight`
— confirmed reached, not assumed):
```
victim  <p> "Clear entry points, honest numbers, and a next step that makes sense."
        rect {x:24, y:704, w:254.3, h:36}   -> 50% covered, hit-tests to the footer
```
Content a user could never scroll into view.

## What changed, in reading order

### 1. `landing-styles.css` (+44, −0) — the whole fix is two declarations

```css
.landing-app .app-footer {
  position: static;
  margin-top: auto;
}
```

The other 40 lines are the comment block explaining it, in the same style as the
217/218 blocks in `pool-detail-styles.css`.

**Why not just add `padding-bottom` to `.landing-app`?** This is the load-bearing
decision, and it is pre-registered in the spec rather than discovered afterwards.
Clearance works by *lengthening the document* so its last pixels fall past the
footer's band. That fixes an end-of-document overlap. But finding (1) is **mid-document
at scroll 0** — the trust-rail text sits at `y 760.5` inside a 780px viewport while
the fixed footer occupies `722-780`. No amount of padding at the *end* of the page
moves an element that is already inside the fixed band at rest. Item 218 hit exactly
this wall on the `garden_cta` CTA and recorded the conclusion in
`pool-detail-styles.css:1080-1112`:

> "The overlap is content-dependent … so no clearance value fixes the class — the
> fix has to remove the overlay on this view instead."

So this reuses 218's shipped, verifier-passed pattern instead of inventing a fourth
approach: **the footer stops being an overlay on this view.** `position: static`
puts it back in normal document flow, where nothing it sits below can be occluded
or click-intercepted at *any* scroll position on *any* viewport.

`margin-top: auto` is the standard flex sticky-footer idiom, and it introduces no
new layout mode: `.landing-app` is **already** `display: flex; flex-direction:
column; min-height: 100vh` (`landing-styles.css:4-11`). On a short page the footer
still sits at the bottom edge; on a long page it sits after the content.

Reuse-before-inventing (standing decision 2026-07-10) is satisfied literally: **no
new class, no new colour, no new shadow, no new radius, no gradient, and no new
numeric value.** The rule is scoped `.landing-app .app-footer`, so `style.css`'s
`.app-footer` block and `.app`'s own clearance are untouched and the fixed footer
stays correct for the analytics grid and every other view.

### 2. `test_landing_footer_occlusion.js` (new, 430 lines) — the gate

Rendered Playwright, driving the real landing route — never a source grep, per the
2026-07-11 standing decision that layout defects need rendered proof. 21 assertions:

- **at rest** and **at true bottom of scroll**, at **360×780 / 768×780 / 1280×780 /
  768×780 dark** — no landing content element's box intersects the footer's box;
- **hit-tests, not paint-tests** — `elementFromPoint` at each victim's lower band
  returns the content element, never `.app-footer`;
- **the footer is still there and still works** — present, non-zero size, and both
  hub links (`/tokens`, `/chains`) hit-test to themselves. This criterion exists so
  the fix cannot "succeed" by hiding the footer;
- **positive control** — in an isolated page, `position: fixed !important` is
  re-applied and the same measurement *does* report occlusion. A check that cannot
  fail is not a check;
- **page-error clean**, using `test_landing.js`'s established
  `IGNORABLE_ERROR_PATTERN` allow-list (external hosts are fixture-routed; the
  sandbox blocks browser-originated HTTPS).

### 3. `package.json` (1 line) — wiring

The new test joins `test:serial` immediately after `test_cta_at_rest_occlusion.js`,
its sibling. `run-tests.js` derives its registry from that chain, and
`test_test_registry.js` enforces the two agree (5/5 green, including its own
no-orphans check).

## Deviations from the spec (both documented, both verified)

1. **`npm run minify` not run.** The spec's Territory Notes flagged the item-061
   trap — copy that shipped nowhere because a `.min` twin was never regenerated.
   Checked rather than assumed: `home.html`'s mode-conditional injector loads the
   **raw** `landing-styles.css` synchronously for landing mode, `minify-assets.js`'s
   `CSS_FILES` list does not include it, and no `landing-styles.min.css` exists on
   disk. There is nothing to regenerate.
2. **No companion `padding-bottom: 0` rule** (218 needed one). 218 had to cancel the
   80px clearance 217 had just restored, since an in-flow footer makes it dead space.
   The landing route never carried that padding at all, so there is nothing to
   cancel. Recorded explicitly so the absence doesn't read as an omission.

## What this does NOT do

- It does not fix the other three item-219 findings (`grid-360` P0/P1,
  `grid-token`/`grid-chain` P0/P1 — all quarantined in `test_audit_app.js:106`).
  Separate tickets.
- It does not touch the `seo-hub-links` rule, `home.html`'s IA router, any
  parameterized URL, any trust rail, or `.landing-footer`'s dead CSS.
- It claims **no funnel metric**, and that is the honest answer rather than a gap.
  At 85 sessions/14d the ≥30-events rule makes any conversion claim
  insufficient-data, and there is no `landing_*` event this could be attributed to.
  This ships under the 2026-07-23 PRE-TRAFFIC MANDATE, where product quality is the
  loop's job. The regression rail is **machine-watched instead**: zero `occlusion`
  findings on `landing-*` in the daily `audit-app.js` tick, plus 21 assertions in CI.

   Why did the landing page still have zero footer clearance?

2. The at-rest defect put content at `y 760.5` in a 780px-tall viewport, with the
   footer occupying `722-780`. Explain why adding `padding-bottom: 80px` to
   `.landing-app` would NOT have fixed that specific finding.

3. Item 218 shipped `position: static; margin-top: auto;` **and** a companion
   `padding-bottom: 0`. This item ships only the first two. Is that an omission?
   Why or why not?

4. The new test asserts the footer is still present and that its two hub links
   hit-test to themselves. What class of bogus "fix" does that criterion exist to
   catch?

   does the hit-test catch that a geometry-only comparison would miss?
