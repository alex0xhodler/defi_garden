# PR explainer — 062: waitlist entry point on the static SEO pages

HIGH tier (NORTH_STAR.md risk policy: touches the SEO-surface generators and
planner.js's waitlist-open path). Full walkthrough + quiz per the ship
policy's HIGH-tier requirement.

## Goal
North star (2026-07-12) is `waitlist_submitted` — the card funnel. The 2,131
generated `/tokens/<slug>` + `/chains/<slug>` SEO pages are the site's
traffic engine, but had zero path into that funnel: every link on those
pages went to `?token=`/`?pool=`/`?chain=` (the analytics app), never to the
waitlist. This item builds the missing bridge.

## Intuition
Two halves, one URL contract between them:
1. **The generators** (`generate-token-pages.js`, `generate-chain-pages.js`)
   add one honest CTA block per page: a short pitch ("A card that spends
   your `<TOKEN>` yield — never your `<TOKEN>` itself") + a button reusing
   the exact same disclosure copy the app already uses
   (`ctaWaitlistMicro`: "Free to join • Card doesn't exist yet..."), linking
   to `plan.html?waitlist=1&src=seo_token` or `src=seo_chain`.
2. **`planner.js`** reads that URL on load and opens a waitlist modal
   immediately — no plan required. That's the interesting design decision:
   the *existing* waitlist modal (inside `Bloom`) only exists once a user
   has answered goal/monthly/persona and the app has computed a curated pool
   set. A visitor arriving straight from a token page has none of that. This
   build does NOT synthesize a fake plan to reuse Bloom's modal (that would
   show a personalized-looking plan the visitor never asked for — dishonest
   by this product's own trust-rail standard). Instead it adds a small,
   standalone modal at the top of `Planner()` that reuses the same
   `gp-waitlist-*` CSS classes and copy keys, minus the parts that need plan
   context (step 2's share/download actions become a plain confirmation).

## What changed and why (diff in reading order)
- **`translations.js`**: 5 new flat, top-level keys (`tcpWaitlistPitchToken`,
  `tcpWaitlistPitchChain`, `tcpWaitlistHeading`, `tcpWaitlistCta`,
  `tcpWaitlistMicro`), EN+KO. They're flat (not nested under the client
  app's `planner: {...}` key) because the Node-side generators'
  `createTranslationFunction` only does a single-level lookup — every other
  generator-facing string in this file (`tcpTokenCta`, `tcpTrustNote`, ...)
  already follows this convention for the same reason. `tcpWaitlistHeading`/
  `Cta`/`Micro` are deliberate copy-duplicates of the client app's
  `waitlistTitle`/`ctaWaitlist`/`ctaWaitlistMicro` — same voice, same
  honesty disclosure, different (flat) storage location.
- **`generate-token-pages.js`**: two new exported helpers,
  `renderWaitlistCtaHtml(pitch, cssPrefix, source, t)` (the CTA block markup)
  and `renderWaitlistCtaStyle(cssPrefix)` (its scoped CSS, reusing
  `var(--color-surface)`/`var(--neuro-shadow-raised)`/etc. — no new colors).
  `pitch` is escaped with `escapeHtml()` before interpolation (see "verifier
  finding" below). Wired into `renderTokenPage` right before the trust-note
  paragraph, with `source='seo_token'`.
- **`generate-chain-pages.js`**: imports and reuses the same two helpers
  (this file already imports most of its shared logic from
  generate-token-pages.js — same pattern), wired into `renderChainPage` with
  `source='seo_chain'`.
- **`planner.js`** (`Planner()`): reads `?waitlist=1`/`&src=`, seeds a new
  `quickWaitlistOpen` state from it, fires `Analytics.trackWaitlistOpened({source})`
  once on mount if set, and renders a small modal (email input → Formspree
  POST → confirmation) using the same `gp-waitlist-*` classes Bloom's modal
  already uses. Rendered as a sibling of `PlannerHeader`/`main` in the final
  `gp-app` return, so it's visible regardless of conversation step.
- **`analytics.js`**: `trackWaitlistOpened`/`trackWaitlistSubmitted` both
  gained an optional `source` field (submitted wasn't strictly required by
  the spec, but makes the `seo_* → submitted` conversion rate directly
  computable).
- **`test_waitlist_seo_entry.js`** (new): Playwright test driving the real
  rendered `plan.html` UI — auto-open on `?waitlist=1&src=seo_token`/`seo_chain`,
  `trackWaitlistOpened` fires with the right `source`, no auto-open on a
  plain load. Wired into `npm test`.
- **`test_token_pages.js`/`test_chain_pages.js`**: new "062" assertion
  groups (CTA count/copy/per-record pitch text/neuro-tokens-only/EN+KO
  coverage/escaping).

## Verifier finding, fixed
First verifier pass: FAIL. `renderWaitlistCtaHtml` interpolated the pitch
line without `escapeHtml()`, unlike every other interpolation in these
files. Chain names (unlike tokens) have no character-safety regex and come
straight from the live DefiLlama API — an adversarial chain name could have
injected markup into a public SEO page. Fixed in a follow-up commit
(`escapeHtml(pitch)`), with a regression test added to both page-generator
test files. Second verifier pass: PASS.

## Deviations from the spec
1. Standalone waitlist modal instead of reusing Bloom's, as explained above
   under "Intuition" — the spec's phrase "open the waitlist modal" read as
   if it meant the existing one; in practice that would require either
   faking a plan (rejected, dishonest) or a much larger refactor hoisting
   Bloom's plan-dependent state up to `Planner()` (rejected, out of
   proportion to "small planner.js addition").
2. `trackWaitlistSubmitted` also gained `source` (spec only asked for it on
   `trackWaitlistOpened`) — trivial, symmetric, and needed to compute the
   `seo_* → submitted` conversion rate the spec's own metric section names.
3. Real `/tokens/`/`/chains/` pages carrying the CTA land on the next
   `sitemap-update.yml` CI run (no live-network production run made in this
   build's sandbox — same precedent as every prior token/chain-page item,
   e.g. 060/041/050).

   - B) Bloom's modal depends on a completed plan (goal/persona/pools) that

   - C) React doesn't allow reusing a modal defined inside another component
   - D) The spec explicitly required a brand-new component

2. Why does `generate-token-pages.js` use new flat top-level translation
   keys (`tcpWaitlistHeading`/`Cta`/`Micro`) instead of reusing the client
   app's existing `waitlistTitle`/`ctaWaitlist`/`ctaWaitlistMicro` keys
   directly?
   - A) Because Korean translations were missing for those keys
   - B) Because those strings are too long for static pages
   - C) Because those keys are nested under translations.js's
     `planner: {...}` object, and the Node-side `createTranslationFunction`
     the generators use only does a flat, single-level lookup — it can't
     reach nested keys
   - D) Because the spec required unique per-page copy

3. What real bug did the verifier catch on the first review pass, and how
   was it fixed?
   - A) The Formspree endpoint leaked API keys — fixed by moving it to an
     env var
   - B) `renderWaitlistCtaHtml` interpolated the pitch line into HTML
     without `escapeHtml()`, so an adversarial chain name (sourced from the
     live DefiLlama API, no character-safety regex) could inject markup —
     fixed by wrapping it in `escapeHtml()`
   - C) The waitlist modal double-fired `trackWaitlistOpened` on every
     render — fixed with a ref guard
   - D) The CTA link used `http` instead of `https` — fixed by hardcoding
