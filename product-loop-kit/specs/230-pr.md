## Goal

A user who opens a `?pool=<id>` deep link for a pool DefiLlama no longer returns gets an honest
"this pool is no longer tracked" page with live alternatives (spec 072). On that page, at first
paint, the alternatives you are meant to click were **under the footer** — and not just visually:
`document.elementFromPoint` at their lower band returned `.app-footer`, so the footer was eating
the clicks. This PR puts the footer back into normal document flow on that one state.

## Intuition in one paragraph

The site has one shared footer: opaque, `position: fixed`, `bottom: 0`, `z-index: 100`. Because it
floats over the page, every view that renders it needs **clearance** — and there is exactly one
clearance rule, `.app { padding-bottom: 80px }`. Clearance is a padding, and padding can only push
the **end of the document** out from under a floating bar. It does nothing for content sitting
mid-document at the exact height the bar happens to float. That is the whole class: five previous
items (179 → 217 → 218 → 220 → 221) are the same bar hitting the same wall on different routes,
and the two most recent ones stopped trying to add clearance and instead took the bar **out of the
fixed layer on that view**. This PR is the sixth member, on the last `.app` state with real content
that none of the five fixes could reach.

## Why this state was unreachable by the earlier fixes

`app.js` decides two things with two different predicates:

- **`app.js:3001`** — the root element's class: ``app ${(selectedToken || (chainMode && selectedChain)) ? 'has-results' : ''}``
- **`app.js:3299`** — whether to render the whole `.results-section`: `(selectedToken || (chainMode && selectedChain) || deadPoolResolved)`

They are two copies of one idea ("are we showing results?") and they disagree on exactly one term:
`deadPoolResolved`. So the dead-pool view renders full results markup while its root stays `.app`
**without** `.has-results`. Every shipped fix keys on a class it does not carry —
`.app.pool-detail-view` (218), `.landing-app` (220), `.app.has-results` (221). Grepping for a rule
that *cancelled* the clearance finds nothing, because nothing did: the clearance is inherited
correctly here and is simply the wrong tool.

## Measured, before and after

Independently reproduced this run with real Chromium at rest (`scrollY = 0`), **10 of 10 runs,
zero clean** — the defect is deterministic, only the daily audit's detection of it is not (that is
item 231):

| viewport | victim | covered | hit-test |
|---|---|---|---|
| 1280×780 | `calculate-yield-btn-new` ×3 | 33.5–33.8% | `.app-footer` — **P0, CTA click-intercepted** |
| 1280×780 | `tvl-label` ×3 | 100% | footer `<p>` |
| 768×780 | `calculate-yield-btn-new` | **100%** | `.app-footer` — **P0** |
| 360×780 | `pool-card` | 22.8% | `.app-footer` |
| 1280×900 | `pool-symbol` ×2 | 93.8 / 99.9% | `.app-footer` |

After: zero victims at 1280×780, 768×780, 360×780 **and** 1280×900 (the last one is outside the
test matrix — an operator check that this is not a 780-height artifact).

## What changed, in reading order

**1. `style.css` — two declarations (the entire behavioural change)**

```css
.app:not(.has-results):has(.results-section) .app-footer { position: static; }
.app:not(.has-results):has(.results-section) { padding-bottom: 0; }
```

- **Why `:has()` and not a new marker class in `app.js`.** The obvious alternative was to emit a
  `dead-pool-view` class next to `has-results`. That would be a **mirror** — a second hand-kept
  copy of a predicate that already exists at `app.js:3299`, and item 212's lesson is that a guard
  watching a *resemblance* of the real mechanism is worse than no guard. `:has(.results-section)`
  reads the defining mechanism itself: *this view rendered a results section*. A future branch that
  renders results without setting `has-results` is covered with no code change. `:has()` is not new
  here — `style.css` already ships it, and it survives minification.
- **Why `padding-bottom: 0` is not a revert of the clearance.** Once the footer is in flow it
  protects nothing; leaving the 80px would render dead background beneath a footer that carries a
  top box-shadow. 218 shipped the same pairing for the same reason. The bottom-of-scroll case that
  the clearance used to protect is asserted separately and still green.
- **What was measured and rejected.** `margin-top: auto` — the flex sticky-footer idiom — is
  genuinely live here (unlike 221's block-layout case), so it was a real candidate and was measured
  rather than argued about, against a pre-registered decision rule. Both variants clear all
  occlusion. On a short-content fixture (all alternatives below the $10M floor, so the grid is
  empty) `margin-top: auto` keeps the footer pinned to the viewport bottom but top-aligns the
  empty-state message: **Δy = −300.4px**, against **+5.7px** for `position: static` alone. The rule
  said "smaller change to today's rendered geometry", so `position: static` alone shipped.
- **One consequence, stated rather than buried:** in flow, the footer is a centred flex item, so it
  becomes a 356px-wide block instead of a full-width bar. That is not new visual language — the
  shipped pool-detail fix (218) already renders it at **exactly** `{x:462, w:356, h:69}` at 1280,
  the same numbers this state now produces.

**2. `style.min.css` — regenerated via `npm run minify`.** `home.html` serves the MIN sheet; a
raw-only fix ships dead (item 136's trap). `test_minified_assets.js` asserts the two are in sync.

**3. `test_dead_pool.js` — 7 new criteria, extending spec 072's existing gate** (reuse over invent:
same server, same fixture, same routing; also no `package.json` registry churn). The occlusion
helper derives its population **from the DOM at test time** — every non-zero-area element inside
`.empty-state` / `.empty-state-alternatives` — so the six victims that motivated the item are the
*positive control*, not the definition. Each element is checked both ways, geometry **and**
`elementFromPoint`, because a paint-only assertion cannot see click interception. The
bottom-of-scroll cases loop `scrollTo` and **assert arrival** before asserting anything, so a
silently failed scroll cannot pass vacuously. One case runs in the opposite direction: the bare
analytics search-home (`?app=analytics`, no `.results-section`) must still report
`position: fixed` and `padding-bottom: 80px` from `getComputedStyle` — proof the new selector is
scoped and did not leak.

## Non-vacuity

Green (12/12) → mutate the **shipped** `style.min.css` back to `position: fixed` → **RED with the
real occlusion signature** (20 named victims at 1280×780, several with `hitTest=INSIDE .app-footer`
— not a timeout, not a different error) → restore → `md5sum` byte-identical
(`2a6e441d1b96e05839e3e3fcc9f1f3de`) → green (12/12). Full transcript in `230-notes.md`.

**Read this before trusting "9/9 criteria met": one of the two shipped declarations is invisible to
the gate that ships with it.** The verifier neutered them separately. Removing `position: static`
turns the suite RED with the real signature — load-bearing. Removing `padding-bottom: 0` leaves it
**GREEN, 12/12**. The declaration still earns its place (once the footer is in flow, the inherited
80px protects nothing and would leave a band of dead background under a footer carrying a top
box-shadow), but that is a *dead-space* claim while every assertion here is an *occlusion* claim,
so the suite cannot see the difference. Logged as a coverage gap rather than dropped or glossed —
the item-222 precedent. The missing assertion, for whoever extends this: measure the gap between
the last `.empty-state*` element's bottom and the footer's top, and assert it is not ~80px larger
than the in-flow spacing.

## What this does NOT close, with numbers

1. **`.app.has-results` — the `?token=`/`?chain=` grid — is still occluded on `main.`** Item 221
   measured `calculate-yield-btn-new` **98.8%** covered at 1280×780 there. 221's CSS exists and its
   verifier confirmed all seven product criteria, but it is PARKED at its 3-attempt budget with
   **PR #386 open**, awaiting a human decision (its three failures were documentation, never the
   CSS). This PR deliberately does not touch that selector — a second run building 221 is the
   2026-07-26 double-build failure mode. **That surface family is the largest in the indexed
   estate, and its P0 stays open until #386 merges.**
2. **The audit's `occlusion` lens sees this deterministic defect 3 times in 20 isolated runs
   (15%).** A lens that leaky under-reports the class on all 83 surfaces it visits per tick, which
   makes every "0 blocking findings" line weaker evidence than it reads. Ticketed as **item 231**
   (READY, 8.5) with 221's characterisation carried over.
3. **The predicate split at `app.js:3001` vs `:3299` is untouched.** `:has()` routes around it
   rather than collapsing it. Collapsing it would hand the dead-pool view the `.has-results` grid
   layout and `padding-top: 160px` meant for the Google-header results view — and land it inside
   gap 1's still-broken footer state. Recorded in `230-notes.md`, not built.

## Risk

**HIGH.** Small diff, no trust rail touched, no new dependency — but it is a shared-stylesheet
change on a render path, and `style.min.css` is served to every analytics-mode URL including the
sacred `?token=` / `?chain=` / `?pool=` family. NORTH_STAR says "when in doubt → HIGH". Guarded by
`test_smoke.js` (11/11, both router paths) plus the scoped-selector collateral assertion above.
**Needs human visual spot-check** per the standing post-merge rule.
