# Item 146 — explainer (HIGH tier: full walkthrough + quiz)

## Goal in one line
A user who builds a **one-time-purchase** plan (iPhone / sneakers / watch) and finishes the waitlist
got a share card that said **"🌱 My yield covers `iphone` — forever · ≈$155,000 working at 8.5% ·
$1,100/mo covered forever"**. Every part of that is wrong. This item makes the post-waitlist share
path tell the truth, and gives it the plan link it never carried.

## The intuition
The planner has three goal archetypes: SUBSCRIPTION (a recurring bill), TARGET (a one-time item), and
GROWTH (a horizon). They share one data structure — `GOALS[]` — and one field name, `target`. For a
subscription that field means **dollars per month** ($20/mo for Claude Pro). For a one-time item it
means **the item's price** ($1,100 for an iPhone).

One helper, `mixStats()`, reads that field and assumes the first meaning. Its own doc comment says it
only resolves "GOALS (subscription archetype)" — but the code never checked the archetype. So an
iPhone became "a $1,100/month subscription," and the "forever number" needed to fund it became
$1,100 × 12 ÷ APY ≈ **$155,000–$220,000 of capital the user never mentioned.**

That bogus figure then flowed into the post-waitlist share surface, because those two functions
(`doWaitlistShare`, `doWaitlistDownload`) were written for subscriptions and never got the
archetype branching that the *main* share button (`doShare`) has had all along.

## What changed and why, in reading order

**1. `planner.js` — `mixStats()`, the root cause (~line 285).**
```js
- if (g && typeof g.target === 'number') monthly = g.target;
+ if (g && g.isMonthly === true && typeof g.target === 'number') monthly = g.target;
```
This restores the function's own documented contract. Every one of the 19 `archetype: 'subscription'`
goals carries `isMonthly: true`; none of the 3 TARGET goals does, and the 2 GROWTH goals have no
`target` at all. So the subscription path is provably unaffected and only the misreading stops.
*(The verifier re-derived this by reading the whole `GOALS` array, not by trusting the claim.)*

**2. `planner.js` — the mix-seed effect (~line 1684).** It ran `setSelectedSubs([goal])` for *every*
archetype, so a TARGET plan carried a bogus one-item "subscription bundle" from first render. Now
gated to `archetype === 'subscription'`. This was unambiguously unintended: `selectedSubs` is already
gated to the subscription archetype everywhere it is *persisted* (planner.js ~1934, ~1962).

**3. `planner.js` — `buildShareCopy()` extracted from `doShare()` (~line 2008).** `doShare` already
had the correct four-way archetype branch (subscription-capital / subscription-monthly / target /
growth) returning `{headline, subline, rowLabel, featured, drawChart}`. Rather than write a third
variant of that logic, it is lifted into one helper — the 2026-07-10 REUSE directive. It stays inside
the same `Bloom(props)` closure, so every variable it reads (`heroDate`, `foreverDate`, `targetDate`,
`liveProjection`, `slideCapital`, `subCapital`, `isCapitalPath`, `monthly`, `slideYears`, `pk`, `apy`)
is unchanged in scope and evaluation order. **`doShare`'s output is byte-identical** — the extraction
is pure variable renaming.

**4. `planner.js` — `doWaitlistDownload()` / `doWaitlistShare()` archetype-branch.** TARGET/GROWTH now
route through `buildShareCopy()`. SUBSCRIPTION deliberately does **not** — see the deviation below.

**5. `planner.js` — the waitlist card now carries the plan link.** `doWaitlistDownload` passes
`url: encodePlanToUrl(...)` and `shareText`, the same argument list `doShare` uses.
`renderShareImage` already had the machinery (native file-share, else clipboard-copy); this surface
simply never opted in — its code comment literally read *"No plan URL supplied (e.g. the waitlist card
download) — unchanged pre-005 behavior: just deliver the image."* That is a standing-decision
violation (2026-07-10: *"every share path must carry the plan URL or it can't close the loop"*;
2026-07-11: *"the link that rebuilds the garden is the primary artifact"*), now closed.

**6. `planner.js` — the raw-id leak.** Label loops fell back to the **raw internal id** when an id
wasn't in `SUBSCRIPTION_LADDER` (`return found ? t(found.labelKey) : id`), which is why the card and
the tweet said `iphone` instead of "iPhone". Now `goalLabel(t, id)`. Side benefit: `rent` and
`phonebill` (subscription goals that aren't ladder rungs) also stop leaking raw ids.

**7. `planner.js` — the waitlist email payload.** `msgSummary` claimed *"covers iphone (~$1,100.00/mo)
for ~$220,000"* in the operator's Formspree inbox for every TARGET plan. Now archetype-branched;
subscription keeps its string verbatim. Deliberately untranslated — it is an operator-only payload,
not user-facing UI.

**8. `translations.js` — one new key pair, EN + KO.** `shareTweetGeneric(headline)`. The existing
`shareTweet` is hardcoded subscription phrasing ("My yield pays for X — **forever**"), meaningless for
a one-time purchase; the new key wraps the already-translated archetype-correct headline.

**9. Instrumentation.** `share_link_created` now fires with `method: 'waitlist_card'` when the link
attaches — a **new, disjoint** value (existing values: `image`, `copy`, `native`), so no existing
series is polluted. `analytics.js` itself is untouched.

**10.** `package.json` gains the new test; `planner.min.js` / `translations.min.js` regenerated.

## Deviation from the spec (the one reviewable judgment call)
Spec item 3 said to call `buildShareCopy()` from **all three** call sites. The builder's first cut did
exactly that, and it was **wrong** — caught mid-build before verification.

`doShare`'s subscription-capital branch derives its bundle from `coveredBundle(subCapital, apy, goal)`
— *"every ladder rung the parked capital's yield already covers."* The pre-146 waitlist functions
derived theirs from `selectedSubs` — *"exactly what the user toggled on in the mix UI."* Those two
coincide only while the mix is untouched. The moment a user toggles Spotify into the mix without the
capital covering Spotify's forever number, they diverge — and the "reuse" would have silently dropped
Spotify from the user's own share card.

**Resolution:** the subscription branch keeps its original `selectedSubs` logic byte-for-byte (only the
raw-id fallback is fixed inside it); only TARGET/GROWTH — the actually-broken part — routes through the
new helper. A dedicated test case (`AC3b`) toggles Spotify into the mix and asserts the card and tweet
still reflect the full selection. Both the builder and the verifier proved this case is byte-identical
to pre-146 behavior by running it against a `git stash`ed true baseline.

Lesson, now codified in `playbooks/dual-source-logic-divergence.md`: **collapsing duplicated logic is
only safe if both copies read the same source — two copies that read different sources are not a fork,
they are two different features that happen to look alike.**

## Verification
New rendered-Playwright test `test_waitlist_share_archetype.js` (real `plan.html`, real Chromium,
fixture-routed pools, routed Formspree 200), 6 assertions, wired into `npm test`. Card content is read
by spying `CanvasRenderingContext2D.prototype.fillText` — the strings actually drawn, not a fixture.

**Non-vacuity proved twice, independently.** On a `git stash`ed baseline the test goes red with the
exact defect signatures: `mixStats(['iphone'],8)` → `{count:1, combinedMonthly:1100,
neededCapital:165000}`; card text `🌱 iphone … ≈$155,000 working at 8.5% · $1,100/mo covered forever`;
tweet `My yield pays for iphone — forever`; clipboard URL `null`. The verifier reproduced all of it
with its own separately-written probe rather than trusting the builder's.

Regression subset all green: `test_planner.js` (208), `test_subscription_mix_seed.js` (4/4),
`test_share_mix_roundtrip.js` (5/5), `test_plan_checkout_cta.js` (13/13), `test_report_share.js` (8/8),
`test_translations_fallback.js` (8/8).

**Two pre-existing failures, proven pre-existing by both agents via identical stashed-baseline runs,
NOT caused by this change and NOT fixed here (out of scope):** `test_waitlist_funnel.js` (3 cases; the
SEO quick-waitlist entry path, a surface this diff never touches) and `test_minified_assets.js` (2 of
9; a structural statement about `home.html`/`plan.html`'s own `<script>` tags — the long-documented
gap from items 125/136/139). Because `npm test` is a single `&&` chain, it halts at
`test_minified_assets.js` on **every** run including unmodified `main` — so the full aggregate script
cannot reach this item's test, and each test in the spec's Tests criterion was run individually
instead. Timebox honored: `timeout 295 npm test` exits in ~2 minutes at that pre-existing failure.

**Verifier verdict: PASS, 9/9 criteria, risk tier HIGH** — independently assigned, agreeing with the
builder. Nothing on the NEVER list is touched: no trust rail weakened (this only *removes* fabricated
figures), no SEO surface deleted, no credentials/money, nothing under `telegram-bot/`,
`whatsapp-bot/`, `workers/`.

**Needs human visual spot-check:** this is a render-path merge and the smoke gate (backlog 003) does
not cover the share-card canvas. Worth eyeballing a TARGET plan's downloaded card once.

## Quiz (5 questions — answers base64 at the bottom)

**Q1.** `GOALS[].target` means "$/month" for a subscription goal and "the item's price" for a TARGET
goal. Why was adding `g.isMonthly === true` to `mixStats` safe enough to ship without touching any of
the ~5 other call sites that read `target`?

**Q2.** The mix-seed effect ran for every archetype. What evidence inside the existing code proves
that seeding a TARGET plan's mix was unintended rather than a deliberate design choice?

**Q3.** The spec told the builder to call `buildShareCopy()` from all three share functions. Following
that instruction literally would have introduced a regression. Describe the exact user action that
would have exposed it, and what the user would have seen.

**Q4.** On the unmodified baseline, the two subscription assertions (AC3, AC3b) *timed out* instead of
failing with a content mismatch. Why — and why does a timeout there fail to prove what the criterion
needs, so that a second, separate probe was required?

**Q5.** `npm test` never reaches `test_waitlist_share_archetype.js`. Explain why, and why that is not
evidence that this item broke the test suite.
