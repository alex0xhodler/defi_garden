# Spec 186: A6b's comment/string stripper is not a JS tokenizer — and it is already eating real code

## Evidence

Item 185 (shipped 2026-07-30, `c46ed5164`) fixed A6b in `test_audit_prescan.js` by counting **real**
invocations of `reconcilePrescanFindings(` instead of raw-text mentions. It does that with a
hand-rolled character scanner, `stripJsCommentsAndStrings()` (`test_audit_prescan.js:313-345`), which
tracks three states: line comment, block comment, string/template literal. It does **not** track a
fourth: the JavaScript **regex literal**.

The 185 builder disclosed the gap in prose (`specs/185-notes.md` §7). The 185 **verifier** turned that
prose into a working proof of concept — a regex character class containing a literal `/*`, e.g.
`/[/*]/`, makes the scanner believe a block comment opened; it never finds a closing `*/`, swallows the
rest of the file, and any genuine call site added afterwards goes uncounted, leaving A6b **green on
exactly the event it exists to catch**. That became BACKLOG row 186 (score 4.2, READY, no spec), filed
deliberately because item 185 existed only because item 184's "filed as such" ticket never was.

The row calls the blind spot **dormant** — `grep` finds only `/[?#]/` and `/[가-힣]/` in `audit-app.js`,
neither containing `/` or `*`. **That is measured, and it is also incomplete.** Re-measured at the top
of this run by running 185's exact stripper over `audit-app.js` (`c46ed5164`) with instrumentation
recording every span it consumes:

So the blind spot is **not dormant — it is live, and has been since 185 shipped**. It has not yet
produced a wrong number only because none of the spans it currently eats happens to contain a

now hit five times (166 `--only` vacuous green; 175 a signal scoring 0 on 1,749 real defects; 183 a
check blinded by an upstream repair; 185 a positive control anchored to a deleted file; this).

The row offers three fix shapes and calls the third "cheapest and probably right": (1) teach the
scanner regex-literal state, (2) replace the count with a real parse, (3) a guard test asserting no
regex literal in `audit-app.js` contains `/` or `*` inside a character class. **The measurement above
retires option 3**: it only covers the `/`/`*` shape the verifier happened to demonstrate, and would
have scored zero on the quote-in-character-class shape that is eating code *today*. Option 2 (a real
parse — acorn/espree) means a new dependency in the merge gate for one counter. Option 1 is built here.

## Hypothesis

We believe **teaching `stripJsCommentsAndStrings()` regex-literal state, plus a tail-survival invariant
that makes any future whole-file swallow loud**, will **close A6b's silent-undercount path and stop the
live mis-tokenization of `audit-app.js:324/771/811`**, because the defect is mechanical, fully measured
above, and the fix is verifiable in both directions on scratch copies. Confidence: **high** — no open
architectural question; the one real risk (regex-vs-division ambiguity) is bounded by the fact that the
count on the real file must stay exactly 3 and 185's two existing non-vacuity directions must stay green.

## Change

One leg, one file: **`test_audit_prescan.js`. No product code. `audit-app.js` is not touched.**

### Leg A — regex-literal state in `stripJsCommentsAndStrings()`

Add a fourth state to the scanner. On encountering `/`, decide **regex literal vs division** by the
last emitted significant character (the standard heuristic, which is exact for all code shapes present
in this repo):

- A `/` starts a **regex literal** when the previous significant (non-whitespace) emitted character is
  one of `( , = : [ ! & | ? { } ; + - * % ~ ^ < >` or `return`/`typeof`/`case`/`in`/`of`/`new`/
  `delete`/`void`/`do`/`else`/`yield`/`await` ends there, or nothing has been emitted yet.
- Otherwise it is **division** (or the `/=` operator) and is emitted as an ordinary character.

Inside a regex literal, consume until the closing unescaped `/`, honouring two sub-states: `\` escapes
the next character, and `[` … `]` is a character class inside which `/` does **not** terminate the
literal. Then consume trailing flag characters. The whole literal is dropped from the output (same
treatment as a string — its contents are not source structure), so a `reconcilePrescanFindings(`
appearing inside a regex is correctly not counted.

Ordering matters: the regex check must run **before** the `//` and `/*` comment checks fail over to
them, i.e. when the previous-significant-character test says "regex position", `/*` and `//` are regex
starts, not comment starts. When it says "division position", the existing comment logic is unchanged —
`a // b` cannot occur in valid JS at a division position, and `x /* c */ / y` still strips correctly.

### Leg B — a tail-survival invariant: any whole-file swallow becomes loud

The distinguishing symptom of every mis-tokenization in this class is that the scanner consumes to
end-of-file. Assert that the stripped output still contains a marker from the **last** statement of
`audit-app.js` (`process.exit(unresolved ? 3 : 2)`, `audit-app.js:3201`, the file's final executable
line — 3,203 lines total). This is one assertion that catches *any* future tail-swallowing shape — not only the two shapes
measured above — and it fails loudly rather than silently under-counting.

The marker is read from the file's own tail at run time and asserted present in the source first, so
the invariant cannot rot into a vacuous truth if the last line is ever rewritten.

## Risk

Author's guess: **LOW** — one test file, no product code, no new dependency, no change to what the merge
gate blocks on (the gate's *assertion* is unchanged; only the counter's tokenizer is corrected).
The verifier assigns independently and should weigh one argument for HIGH: this file *is* the merge
gate's own machinery (154/157/163/166/169/172/184/185 precedent), and a regex-vs-division heuristic that
guesses wrong in the *other* direction could swallow real code and make A6b under-count — which is why
criteria 3/4/5 exist and why the count on the real file must stay exactly 3.
