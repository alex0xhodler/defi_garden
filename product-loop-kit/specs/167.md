# 167 — The product audit renders ONE pool out of 740, and it is the flagship

Status: READY · Score 7.2 · Risk HIGH (size; audit tooling only) · Promoted by the build loop
2026-07-28 (no READY items existed — 148 is in flight as human-gated PR #306, 166 is PARKED as
open PR #322).

## Problem

`audit-app.js` renders **five** pool-detail surfaces every run — `pool-detail`,
`pool-detail-360`, `pool-detail-dark`, `pool-detail-ko` and the dead-pool control — and **all
five point at the same hardcoded pool**:

```js
// audit-app.js:88-91
// North-star pool-detail surface (lido stETH). Verified present in the snapshot
const PREFERRED_POOL_ID = '747c1d2a-c668-4682-b9f9-296708a3dd90';
```

`audit-app.js:1065-1068` uses it verbatim when present (it is), falling back to `pools[0]` only
if absent. `data/pools-snapshot.json` carries **740 pools**. Coverage of the product's north-star
surface is therefore **1/740 = 0.14%**, and the one pool chosen is Lido stETH — the most
blue-chip, most-certain-to-be-fine row in the dataset.

This is verbatim item **154**'s finding ("the scanner audits ONE hand-picked SEO page out of
2,167 — the flagship page, the one most certain to be fine"), which was diagnosed, fixed and
shipped for the **static SEO** surface (154 anchor+rotation, 157 prescan+promotion) and **never
applied to the app's pool-detail surface** — the surface NORTH_STAR.md names as the north star.

## Evidence (all re-derived this run, not quoted from a prior report)

1. **The blind spot is live and it has a live true positive.** The committed snapshot contains
   exactly one pool whose `apyMean30d` breaches `APY_SANITY_LIMIT`:

   ```
   $ node -e "…snapshot…"
   pools: 740
   out-of-rail total APY (>1000): 0
   apyMean30d>1000: 1 [ '201e5f6e-cf75-4d0e-b07f-d58da3cee23a', 'balancer-v2', 30282.5457 ]
   ```

   30,282.55% is 30× the rail. That pool id is *the same pool* items **144** and **145** were
   filed about. The scanner renders Lido stETH five times a day and has never once rendered it.

2. **Every pool-detail bug in the backlog's history was hand-found on a non-flagship pool.**
   122 (rate-stability score rendering −900T, balancer-v2) · 144 (`apyMean30d` unclamped,
   `201e5f6e-…`) · 145 (KPIs derived from out-of-rail history, `201e5f6e-…`) · 165 (an out-of-rail
   rate compounding to a $49-quintillion projection, zeebu ZBU). **Not one is Lido stETH.** The
   scanner could not have caught any of them, by construction — not because its checks are wrong
   (`number-sanity` is P0 and exists for exactly this class) but because they are never pointed at
   a pool that can fail.

3. **Today's full run confirms the shape.** `node audit-app.js` (this session, 26 surfaces):
   5 findings, all the known 148 `junk-slug` class; `textSurfaces.scanned: 2`; the five
   `pool-detail*` entries in `surfacesCovered` are all one pool. Plain test lane green
   (`node run-tests.js --lane=plain` → 34/34).

4. **The precedent is shipped and proven.** `buildStaticSurfaces()` (`audit-app.js:421-540`)
   already implements anchor + seeded rotation + prescan-driven promotion with a kill switch, a
   cap, and aggregate `static-prescan:<signal>` findings. This item mirrors that shape for pools.
   Related: **155** (the audit's only P0 positive control is dead) is the same family — a check
   that cannot fire is not coverage.

5. **LEARNINGS 2026-07-27, takeaway 2:** *"A filter that returns zero is not evidence of health
   until you have proven it can return non-zero."* Five clean pool-detail surfaces a day on one
   flagship pool is precisely that vacuous green.

## Goal

Point the audit's existing pool-detail checks at pools that can actually fail, using the shipped
154/157 pattern, without changing any product code.

## Design

Add a **snapshot prescan + promotion + seeded rotation** for the pool-detail surface, mirroring
`buildStaticSurfaces()` as closely as the data shape allows.

1. **`prescanPools(pools, opts)`** — pure, exported, no I/O beyond the already-read snapshot.
   Returns `{ scanned, suspects, bySignal }`. Signals (severity mirrors `PRESCAN_SIGNALS`'s
   single-source-of-truth shape — define `POOL_PRESCAN_SIGNALS`):

   | signal | severity | predicate |
   |---|---|---|
   | `apy-rail-breach` | P0 | `(apyBase\|\|0)+(apyReward\|\|0) > APY_SANITY_LIMIT` |
   | `mean30d-rail-breach` | P0 | `typeof apyMean30d === 'number' && apyMean30d > APY_SANITY_LIMIT` |
   | `kpi-nonfinite` | P0 | any numeric `kpis.*` present and non-finite (NaN/±Infinity) |
   | `absurd-magnitude` | P0 | any numeric field (incl. `kpis.*`) with `Math.abs(v) >= ABSURD_MAGNITUDE` |
   | `missing-tvl` | P1 | `!(tvlUsd > 0)` |

   Reuse the module's existing `APY_SANITY_LIMIT` and `ABSURD_MAGNITUDE` constants — **do not
   redefine them** (a rail mirror is a trust-rail edit; this item may not touch rails).

2. **`buildPoolSurfaces({ pools, ... })`** — replaces the `PREFERRED_POOL_ID`-only block at
   `audit-app.js:1065-1068`:
   - **Anchor unchanged**: `PREFERRED_POOL_ID` (Lido stETH), same fallback to `pools[0]`, and the
     four existing surface **names must not change** (`pool-detail`, `pool-detail-360`,
     `pool-detail-dark`, `pool-detail-ko`) — `surfacesCovered` is read by the heartbeat and by
     `test_audit_app.js`; a rename is a regression.
   - **Promotion**: up to `DEFAULT_POOL_PRESCAN_MAX` (default **2**) suspect pools, P0-first, tie
     broken by `sampleBySeed` so successive days work through a backlog rather than re-rendering
     the same pool forever (157's exact rationale). Named `pool-detail:<pool-id-prefix>` —
     self-describing, and it must never collide with the four anchor names.
   - **Rotation**: fill the remaining budget (`DEFAULT_POOL_SAMPLE`, default **2**,
     `MAX_POOL_SAMPLE` cap **6**) from the non-suspect pools by `sampleBySeed`, excluding the
     anchor and every promoted pool.
   - Promoted/rotated surfaces run at 1280px, `kind: 'pool'` — i.e. the **existing** pool driver
     and all its existing checks, unmodified.
   - **Aggregate findings**: one `pool-prescan:<signal>` finding per tripped signal, at that
     signal's severity, mirroring `static-prescan:<signal>` verbatim in shape and wording style
     (`"N of M snapshot pools match <signal> — examples: …"`).

3. **Kill switches / overrides**, mirroring 154/157 naming exactly:
   `AUDIT_POOL_IDS` (explicit comma-separated override; replaces anchor+rotation entirely and
   turns prescan OFF, like `AUDIT_STATIC_PAGES`) · `AUDIT_POOL_PRESCAN=0` · `AUDIT_POOL_SAMPLE` ·
   `AUDIT_POOL_PRESCAN_MAX` · reuse the existing seed (`AUDIT_STATIC_SEED` → same
   `defaultStaticSeed()`; namespace the derived seeds as `${seed}:pools` / `${seed}:poolprescan`).

4. **`runAudit()` JSON gains `poolPrescan: { scanned, suspectCount, bySignal, promoted }`**,
   sibling to the existing `prescan` and `textSurfaces` blocks. `signals/audit-findings.json`
   picks it up for free.

## Non-goals (do NOT do these here)

- **No product-code change.** `PoolDetail.js`, `app.js`, `planner.js`, `home.html` untouched.
- **No new checks in the pool driver.** This item aims existing checks at new targets. If a
  promoted pool produces a real finding, that is a **candidate ticket** recorded in
  `167-notes.md` and the run report — one item, one change (162/164's precedent).
- **No trust-rail edit.** Reuse `APY_SANITY_LIMIT` / `ABSURD_MAGNITUDE`; do not redefine, relax,
  or re-derive them.
- **No fix for item 155's dead positive control** — separate, already-ticketed item.
- Do not modify `test_seo_surface_audit.js` / `test_audit_prescan.js` (154/157's determinism
  tests) — if their assumptions collide, change *this* item's defaults, not their file (157's
  own recorded rule).

## Acceptance criteria

Rendered-product acceptance per the 2026-07-11 standing decision: these are Playwright renders of
the real UI via `audit-app.js` itself, not unit fixtures alone.

- **A1 — the blind spot is closed, provably.** A full `node audit-app.js` run's `surfacesCovered`
  includes at least one `pool-detail:<id>` entry that is **not** `747c1d2a-…`, and
  `poolPrescan.promoted` contains `201e5f6e-cf75-4d0e-b07f-d58da3cee23a` (the live
  `mean30d-rail-breach` pool). Show the JSON.
- **A2 — the promoted pool is actually rendered.** That pool's surface appears in
  `surfacesCovered` and the run reaches a verdict on it (a finding, or a clean render) — not a
  `driver threw:` and not a skip. Show the surface's outcome either way.
- **A3 — non-vacuity, the 155 lesson.** With a fixture snapshot whose one pool trips
  `apy-rail-breach`, `prescanPools()` returns exactly that suspect and `runAudit()` emits the
  `pool-prescan:apy-rail-breach` P0 aggregate finding. Then **delete the signal's predicate** and
  show the assertion goes red. A check that has not been shown to fail is not shipped.
- **A4 — no surface regression.** The four existing names (`pool-detail`, `pool-detail-360`,
  `pool-detail-dark`, `pool-detail-ko`, plus `dead-pool`) still appear, still point at the anchor
  pool, and `test_audit_app.js` + `test_audit_runner.js` + `test_audit_prescan.js` +
  `test_seo_surface_audit.js` + `test_audit_planner_flow.js` are green (run them; if the browser
  lane exceeds the 5-minute foreground timebox, run this subset via
  `node run-tests.js --lane=browser --only=…` and report exactly what ran and what did not).
- **A5 — determinism.** Same snapshot + same seed → identical `poolPrescan.promoted` and identical
  rotation picks across two runs. Different seed → the *rotation* may differ; **promotion must
  not** (promotion is suspicion-driven, not seed-driven, when suspects ≤ cap).
- **A6 — kill switches work.** `AUDIT_POOL_PRESCAN=0` → no promotion, no `pool-prescan:*`
  findings, anchor+rotation intact. `AUDIT_POOL_IDS=<id>` → exactly that pool, prescan off.
- **A7 — bounded cost.** Full-run surface count grows by at most `MAX_POOL_SAMPLE` (6); report the
  before/after wall-clock of `node audit-app.js`.
- **A8 — new test wired in.** `test_audit_pool_prescan.js`, added to `package.json`'s test chain
  in the audit-suite neighbourhood, asserting A3/A5/A6 on fixtures.
- **A9 — rails untouched, mechanically shown.** `git diff` contains no line touching
  `APY_SANITY_LIMIT`'s or `ABSURD_MAGNITUDE`'s definition, and no product file appears in
  `git diff --stat`.

## Open questions

None that change the architecture. The promotion cap (2) and rotation size (2) are cost knobs
with env overrides, chosen to mirror 154/157's defaults; a builder may adjust them with a recorded
rationale if A7 shows the cost is wrong.

## Measurement

Not a growth item — no funnel metric. Success is coverage, and it is measurable directly:
pool-detail surfaces per run go 1 → up to 7 (1 anchor + ≤2 promoted + ≤2 rotated, ×viewport
variants unchanged), and the daily `signals/audit-findings.json` gains a `poolPrescan` block whose
`suspectCount` is the standing count of pools that could render a bad number. Decision rule: if
30 days of runs promote pools and never produce a finding, the pool driver's checks — not its
targets — are the next thing to question.
