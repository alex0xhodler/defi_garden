# 177 — lower the analytics app's default TVL floor to $100K, without a silently false floor

**Risk tier: HIGH — and on the NEVER list.** This relaxes `DEFAULT_MIN_TVL`, one of NORTH_STAR's
named trust rails ("never weakened; only the human relaxes these"). Permitted ONLY because of a
live human directive, 2026-07-29: *"Lower the app floor to 100k"*, reaffirmed as *"C and A"* after
the operator laid out the three options and their costs. **Do NOT auto-merge** — per NORTH_STAR,
the loop's standing autonomy does not extend to rail relaxations even when authorized: the
authorization covers the DECISION, and the human has not yet seen the IMPLEMENTATION. Full
explainer + quiz per the HIGH gate. Build notes: `specs/177-notes.md`. Spec: `specs/177.md`.

---

## The goal, in one sentence

Lower the analytics grid's default minimum-TVL filter from $10M to $100K — the human's call — while
making sure the app actually serves $100K-floored data at that default, not a $10M-floored snapshot
wearing a $100K label.

## The intuition

`DEFAULT_MIN_TVL` looked like one constant with one job: "the TVL floor." It was actually doing
**two unrelated jobs** that happened to share a value:

1. The **user-facing default** — what the TVL filter starts at, and what gets left out of the URL
   when the user hasn't changed it.
2. The **snapshot-eligibility threshold** — whether this pageview may be served from
   `data/pools-snapshot.json`, a small pre-baked file that item 059 built specifically because it is
   **physically floored at $10M** (`generate-pools-snapshot.js` never bakes a pool below that into
   the file, full stop).

As long as both jobs pointed at $10M, nobody had to notice they were different jobs. The moment the
human asks for job #1 to move to $100K, the naive fix — rename the one constant — silently breaks
job #2 in a way that reads as fixed:

- `urlParams.minTvl >= DEFAULT_MIN_TVL` → `100000 >= 100000` → still true → the app still thinks a
  bare pageview may use the snapshot.
- It fetches `pools-snapshot.json` — which still only contains pools ≥ $10M, because that file's own
  floor was correctly left alone.
- The UI says "$100K floor." The data underneath is $10M-floored. **The floor claim is now false**,
  and it is false in the specific direction that erodes the thing this product sells: honest numbers.
- Worse: the escape hatch that exists *precisely* to rescue "snapshot floor and requested floor have
  diverged" uses the SAME renamed constant, so it never fires either. The one mechanism built to
  catch this exact mismatch is disabled by the same one-line edit that creates the mismatch.

That's the trap. This item's entire job is separating the two constants so each keeps doing only its
own job.

## What changed, in reading order

**1. `app.js:806` — `DEFAULT_MIN_TVL` → `100000`.** Comment rewritten: this is now explicitly "the
analytics grid's default filter value, human-relaxed 2026-07-29 from $10M."

**2. `app.js:816` — new `const SNAPSHOT_MIN_TVL = 10000000;`.** Not a new rail — a name for a
property `generate-pools-snapshot.js:52` already has and this item leaves untouched. Comment points
at that exact line.

**3. Both snapshot guards re-keyed to `SNAPSHOT_MIN_TVL`, nothing else about their logic touched:**

| | before | after |
|---|---|---|
| eligibility (`app.js:1173`) | `urlParams.minTvl >= DEFAULT_MIN_TVL` | `urlParams.minTvl >= SNAPSHOT_MIN_TVL` |
| escape hatch (`app.js:1199`) | `minTvl >= DEFAULT_MIN_TVL` (skip) | `minTvl >= SNAPSHOT_MIN_TVL` (skip) |

`grep -n DEFAULT_MIN_TVL app.js` now shows it used only for the filter's initial state, the clean-URL
comparison, and (new) deriving copy — never again for snapshot routing.

**4. `formatMinTvlLabel()` (`app.js:818-828`), new.** A pure copy helper: a number in, a short label
out (`100000` → `"$100K"`). Exists so the empty-state strings below can say the TRUE active floor
instead of a hardcoded number that would go stale the next time this constant moves.

**5. Five `translations.js` strings stop hardcoding `$10M`, EN + KO together, each now taking a
`floor` argument derived from the RIGHT source:**

- `emptyStateExplanation(token, floor)` / `emptyStateExplanationChain(chain, floor)` — describe why
  the grid is empty, which depends on the user's own chosen `minTvl`. Call sites (`app.js:3276/3277`)
  pass `formatMinTvlLabel(minTvl)` (the live React state) — if a user picked `$1M+` and got zero
  results, the copy now honestly says $1M, not a stale constant.
- `poolNotFoundExplanation(floor)` / `emptyStateAltHeadingChain(chain, floor)` /
  `emptyStateAltHeadingStable(floor)` — describe the "honest alternatives" list, which is ALWAYS
  filtered at the fixed `DEFAULT_MIN_TVL` (`getEmptyStateAlternatives`'s `passesTrustRails`,
  `app.js:2400`, unchanged logic), never the user's relaxed choice. Call sites pass
  `formatMinTvlLabel(DEFAULT_MIN_TVL)` accordingly.
- `tvlTrendShrinking` — its only call site lives in `PoolDetail.js`, which is frozen byte-identical
  (see "Scope and safety"). No way to plumb a derived value through a file this item cannot touch, so
  the text was hardcoded `$10M` → `$100K` instead, and that constraint is stated plainly rather than
  worked around.
- `trustFloor` (landing.js's static marketing copy, no filter state to read at all) — hardcoded to
  `$100K`, same reasoning. Persona descriptions (`personaStableDesc` TVL ≥ $50M, `personaDegenDesc`
  TVL ≥ $10M — the planner's own personas, a different product's floors) deliberately untouched.

**6. `home.html` — NOT CHANGED. Byte-identical to `main`.** The spec (§3) asked for one edit here,
calling `home.html:220` a JSON-LD `description`. **That was a misidentification by the spec's author.**
`:220` is the `description` of the in-page `search_yield_pools` MCP tool exposed to browser AI agents,
and that tool's own `execute` at **`home.html:239`** contains an independent third floor —
`if (p.tvlUsd < 10000000) return false;` — which this item does not touch.

So editing the description to `$100K` would have made it FALSE about the tool it describes: a UI
claiming a floor the code does not apply, which is the exact bug class this whole item exists to
close, reproduced at small scale on a sacred, HIGH-risk file. **Caught by the verifier on attempt 1
(FAIL, 11/12); the edit was reverted rather than shipped.** The surviving `$10M` string at `:220` does
not breach acceptance criterion 5, because the tool at `:239` genuinely still applies a $10M floor.

Open for the human, deliberately not decided by the loop: **should the in-page MCP tool's floor track
`DEFAULT_MIN_TVL`?** Changing `:239` would be a second rail relaxation on a second surface, and the
2026-07-29 directive named the analytics grid's default. Filed as a candidate ticket.

**7. Compiled assets regenerated** — `npm run compile && npm run minify`; `app.compiled.js` /
`app.compiled.min.js` / `translations.min.js` committed. `PoolDetail.compiled.*` and `planner.min.js`
are untouched (their sources are untouched).

**8. 27 test files.** One rendered end-to-end file extended with the acceptance proof
(`test_snapshot_first.js`, +2 scenarios); two fixture files had a sub-floor test pool that crossed
from below-$10M to above-$100K, so their sub-floor value moved down to stay genuinely sub-floor
(`test_dead_pool.js`, `test_token_vault_match.js`); one file's every assertion literally checked for
the string `minTvl=10000000` and needed the same string updated to `100000`
(`test_minttvl_clean_url.js`); the rest are comment-accuracy fixes on fixtures already sized well
above either floor. Full per-file reasoning — including every file checked and found to need NO
change — is in `specs/177-notes.md`.

## The proof this actually closes the trap

`test_snapshot_first.js` gained two rendered scenarios:

- **(h)** — bare `?token=USDC`, no `?minTvl=`. A live-only pool at $500K (between the two floors,
  impossible to exist in the $10M-floored snapshot fixture) must render, and no snapshot-only pool
  may render alongside it. **This is the literal acceptance test for "the default now loads live, not
  the $10M snapshot."**
- **(i)** — `?minTvl=10000000` (still snapshot-eligible; snapshot serves, zero live hits), then click
  the real `$100K+` TVL chip in the rendered UI. The escape hatch must fire and surface the $500K
  live-only pool. **This is the literal acceptance test for "the rescue mechanism still works."**

Both were mutated to reproduce the trap and watched fail, then restored byte-identical:

| mutation | scenario | result |
|---|---|---|
| re-key eligibility guard back to `DEFAULT_MIN_TVL` | (h) | **fails**: snapshot cards render, live never hit |
| re-key escape-hatch guard back to `DEFAULT_MIN_TVL` | (i) | **fails**: escape hatch never fires after relaxing the chip |

`md5sum app.js` matched before and after each mutation/restore cycle. Neither new assertion passes by
construction.

## The bill the human agreed to pay

The default view's load path flips from the ~65KB snapshot fast path (item 059) to a full live fetch.
Measured, not guessed:

- **Payload size** (captured via `curl`, which reaches `yields.llama.fi` in this sandbox even though
  browser-originated HTTPS doesn't): live `/pools` is **11.0MB uncompressed / 2.26MB gzip**; the
  committed snapshot is **332KB / 69KB gzip**. **The live fetch is ~33x the gzip size of the fast
  path it replaces on every default load.**
- **Parse/render cost, isolated from network** (both payloads served with zero artificial latency, so
  only JSON.parse + filter + render differs): time-to-first-card averaged **717ms** on the small
  snapshot vs **767ms** on the full live payload — a measured **+50ms**, in a sandbox that cannot
  reproduce real transfer time. The ~33x gzip-size ratio is the part of the bill that will actually
  show up on a real connection; this sandbox can only measure the smaller, parse-side piece honestly.

## Deviations, disclosed

Two worth naming here (all in `specs/177-notes.md`):

- **`home.html` ended up entirely unchanged — a deviation from the spec, resolved against the spec.**
  The builder made the edit §3 asked for and logged the resulting inconsistency honestly in
  `177-notes.md`; the verifier then FAILED the item on it, correctly noting that the explainer (the
  human's actual review surface for a NEVER-list relaxation) described it only as "one surgical string
  edit" and omitted that the tool's own filter at `:239` was unchanged. A human reading the explainer
  alone would have merged an undisclosed false claim. Fix applied: revert `:220`, leaving `home.html`
  byte-identical to `main`, and document the misidentification at its source. See item 6 above.
  The `:239` floor question goes to the human as a candidate ticket, undecided by the loop.
- **KO's `trustFloor` switched from a Korean-numeral style (`"$1,000만"`) to ASCII (`"$100K"`)**,
  matching the dominant convention already used for $100K elsewhere in this file (the
  `generate-token-pages.js`-consumed strings), rather than inventing a `"$10만"` form that exists
  nowhere else for this figure.
