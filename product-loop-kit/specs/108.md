# Spec 108 — Data-layer DB leg: Cloudflare Worker Cron + D1 (stack decided 2026-07-15)

Covers the human keystone (108) and the two build tickets it unblocks (109 poller, 110 read-from-DB).
Foundation: docs/feasibility-data-layer.md (058 §2/§5/§7), the shipped 059 snapshot + 087 file-history.

## Decision (human 2026-07-15)

Stack = **Cloudflare Worker (Cron Trigger) + D1**, NOT Turso. Reasoning:
- Cloudflare is already in the stack; a Worker gives a RELIABLE intraday scheduler GitHub Actions cron
  cannot (no SLA, 5-20min late).
- The Worker writes history to D1 WITHOUT a repo commit → eliminates the 081/083 Vercel deploy-churn
  problem entirely (every GH-Actions poll that committed = a deploy).
- 058 picked Turso only to avoid Workers when the FE reads the DB live. It does NOT — KPIs bake into the
  static snapshot at CI time (087), so the DB is a poller/CI store, never a request-path backend. The FE
  stays 100% static; the no-backend tenet holds on the read path.

## Why this leg at all (scope honesty)

087's committed `data/history/<date>.json` already gives DAILY granularity for 30 days and feeds every
shipped KPI. This leg is worth building ONLY for (a) intraday history or (b) windows >30 days. If daily
is enough, do not build it. Not urgent.

## Architecture

```
CF Worker (cron hourly) --fetch--> yields.llama.fi/pools --trust rails--> INSERT OR REPLACE --> D1
GitHub Actions (daily sitemap-update.yml) --GET /history?days=90--> compute-kpis.js --bake--> pools-snapshot.json (committed)
Browser --reads--> static pools-snapshot.json  (live-DefiLlama fallback unchanged, 058 §7)
```

D1 schema (`schema.sql`):
```sql
CREATE TABLE pool_history (
  pool_id TEXT NOT NULL,
  ts      INTEGER NOT NULL,   -- unix seconds
  apy     REAL NOT NULL,      -- apyBase+apyReward, post trust-rail
  tvl_usd REAL NOT NULL,
  PRIMARY KEY (pool_id, ts)
);
CREATE INDEX idx_pool_ts ON pool_history(pool_id, ts);
```

## 109 — BUILD the poller (Worker) — SHIPPED code 2026-07-16 (deploy pending human 108)

`wrangler.toml` (binding `DB` → the D1 database; `[triggers] crons = ["0 * * * *"]`) + `src/poller.js`
(ESM Worker) + `src/poller-core.js` (pure CJS logic, unit-tested by `test_poller.js`):
- `scheduled()`: fetch pools → `railedRows()` → `INSERT OR REPLACE` in ≤100-row batches → retention prune.
- **Trust rails (CORRECTED from this spec's original sketch — the build caught the bug):** the $10M
  `DEFAULT_MIN_TVL` floor is the ONLY drop. Anomalous pools (total APY > `APY_SANITY_LIMIT`=1000) are
  **KEPT** with their real (unclamped) APY, mirroring the shipped snapshot exactly
  (generate-pools-snapshot.js:75-77 filters on TVL only; "show flagged, never hide"). The earlier
  sketch's "drop apy > 1000, anomalous NEVER stored" was WRONG — it would have diverged the history
  population from the snapshot the KPIs annotate. `apy = round(apyBase+apyReward, 4)` via the exact
  compute-kpis.js `round()` (byte-equivalence for 110).
- `fetch()`: `GET /history?days=N` (cap 365), Bearer-guarded by `READ_TOKEN`, **fails closed** (503) when
  `READ_TOKEN` is unset — never open. Returns `[{pool_id, ts, apy, tvl_usd}]` ascending by ts.
- Retention: `DELETE FROM pool_history WHERE ts < retentionCutoff(now, RET_DAYS)` (default 90), same cron.

## 110 — BUILD read-from-DB (compute-kpis.js)

- Replace the `readHistory()` file-glob with a fetch of `${HISTORY_ENDPOINT}?days=90` using `HISTORY_TOKEN`.
- Group the flat rows into the SAME `{date/bucket → {pool_id:[apy,tvl]}}` shape `buildSeriesByPool()`
  already expects — everything downstream (KPI math, baking into snapshot + slices) is UNCHANGED.
- Guard: if the endpoint is unreachable/empty, fall back to the local `data/history/*.json` (no KPI
  regression, honest degrade) — do NOT fail the CI build.
- `sitemap-update.yml` daily commit cadence untouched; the `data/history/*.json` files can be retired
  once the DB path is proven (keep them as the fallback initially).

## Trust rails (binding, verbatim intent 058 §5)

$10M TVL floor applied at WRITE time in the Worker — the DB is another enforcement point, NEVER a place a
rail is relaxed OR changed. **Anomalous pools (>1000% APY) are KEPT with their real APY** (flagged
downstream — "show flagged, never hide"), mirroring the shipped snapshot exactly
(generate-pools-snapshot.js:75-77 filters on TVL only; compute-kpis.js never re-filters). Storing the
SAME population the snapshot/file-history holds is what preserves 110's byte-equivalence — dropping
anomalous pools here would silently diverge the DB path from the file path. KPIs rank within passing
pools only, never override a flag. Attribution ("Powered by Defillama API") stays.
(HISTORICAL NOTE: an earlier draft of this section said "anomalous never stored" — that was WRONG and the
109 build corrected it; see specs/109-notes.md.)

## Acceptance criteria (109/110, verifier-checkable)

- [ ] Poller applies the $10M TVL floor before insert (sub-floor pool never appears in D1) AND KEEPS
      anomalous >1000% pools with their real APY (mirrors the snapshot) — testable against a fixture.
- [ ] `GET /history` is Bearer-guarded (401 without the token) and window-capped.
- [ ] compute-kpis.js produces byte-identical KPI fields from the DB path vs the file path on the same
      data (equivalence test), and falls back to files when the endpoint is down.
- [ ] No request-path backend introduced — the FE still reads only the static snapshot; grep proves no
      new client fetch to the Worker/D1.
- [ ] Trust rails + attribution untouched; `node test_compute_kpis.js` (+ new poller test) exit 0.
