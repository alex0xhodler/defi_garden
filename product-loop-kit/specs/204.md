## 1. The evidence (measured on this checkout, not recalled)

Item 202 shipped the **capture** half of `src` (`analytics.js:41-54` reads it into
`this.acquisition`, which `getBaseContext()` spreads onto *every* event including
`pool_click` — the north star). Item 203 shipped the **emit** half on the estate's
`?pool=` deep links. CI has since regenerated the estate (`997e09228`), so the tags
are live on disk.

Counted this run over the committed estate (`tokens/*.html` + `chains/*.html`,
`grep -ohE 'href="https://www\.defi\.garden/\?[^"]*"' | uniq -c`):

| link family | count | carries `src`? |
|---|---|---|
| `/?pool=<id>` | 4,324 | **yes** — `&src=seo_token` / `&src=seo_chain` (203) |
| `/?token=<SYM>&minTvl=…` | 4,491 | **no** |
| `/?chain=<name>&minTvl=…` | 214 | **no** |

So on one and the same rendered page — `tokens/usdc.html`, verified by eye this run —
the 8 pool links are attributed and the 5 app links are not:

```
href="https://www.defi.garden/?pool=d783c8df-…&src=seo_token"      <-- tagged (203)
href="https://www.defi.garden/?token=USDC&minTvl=100000"            <-- untagged
href="https://www.defi.garden/?token=USDC&minTvl=100000&poolTypes=Lending"   <-- untagged
```

**Why this is the larger half, not the leftover half.** The `?pool=` link lands a
visitor directly on pool-detail; the `?token=` link lands them on the analytics grid,
which is the *browse* path into the same surface (grid card → pool-detail → the two
north-star CTAs). Today a `pool_click{garden_cta}` that originated on a static SEO page
is attributable **only if** the visitor took the direct-deep-link path. If they took the
browse path — the bigger link population, 4,491 vs 4,324 — the click arrives with
`src` absent, indistinguishable from a cold direct hit. `reports/2026-08-01.md:3` has
been reporting `src` = `undefined` × 47 for 20 days; 202 made the property populatable
and 203 populated one of the two paths into the north-star surface.

**The taxonomy is ratified, not invented**: `seo_token` / `seo_chain` are the values
`analytics.js:41-54` already names and 203 already emits, and the same two values
already tag this estate's waitlist links (`generate-token-pages.js:793`,
`generate-chain-pages.js:240`, items 062/066/075).

**The gate that would have blocked this is already open**: 203's Leg A taught
`audit-app.js`'s `link-target-integrity` rule (a) to union in the keys parsed from
`analytics.js`'s capture list, so `src` on a link target no longer fires a P1. That was
the estate-wide blocker for 203; it is shipped, so this item does not re-pay it.

**SEO-safe by an existing mechanism**: `canonical.js:33`'s `CANONICAL_PARAMS` =
`['token','chain','pool','poolTypes','protocols','minTvl','minApy']` — `src` is absent,
so every tagged URL self-canonicalises to its clean form. It cannot manufacture the
indexable-duplicate class of items 010/188.

## 2. Territory notes (blindspot pass — read the code before spec'ing, build.md §2)

The emit sites, all four of them, exactly:

| file:line | what | value |
|---|---|---|
| `generate-token-pages.js:886` | `<a class="tp-cta" href="${appUrl}">` — the main "open in app" CTA | `seo_token` |
| `generate-token-pages.js:789` | `categoryLinksFor(rec.pools, appUrl)` → up to 4 `&poolTypes=<cat>` nav links | `seo_token` |
| `generate-chain-pages.js:329` | `<a class="cp-cta" href="${appUrl}">` | `seo_chain` |
| `generate-chain-pages.js:236` | `categoryLinksFor(rec.pools, appUrl)` | `seo_chain` |

**THE TRAP, and the reason this is not "tag `appUrl` where it is built":** the `appUrl`
*variable* (`generate-token-pages.js:719`, `generate-chain-pages.js:161`) has two other
consumers that must stay clean:

1. `renderItemListJsonLd(rec.pools, appUrl, language)` (`:755` / `:195`) passes it as the
   ItemList fallback `url`. 203 **pre-registered** that JSON-LD `url`s stay canonical
   (Google wants canonical item URLs in an ItemList) and its verifier proved **0 of 40
   real `ld+json` blocks carry `src=`**. Tagging `appUrl` at its definition would silently
   reverse that decision on every page in the estate.
2. `poolHrefFor(p, appUrl, 'seo_token'|'seo_chain')` (`:805` / `:248`) uses it as the
   *fallback* branch for a pool row with no `pool` id — that branch is already tagged
   correctly by 203's third argument. Tagging `appUrl` too would double-tag it
   (`…&src=seo_token&src=seo_token`).

Therefore: **`appUrl` is not modified. The tag is applied at the four visible render
sites only.**

Also checked rather than assumed, before spec'ing:

- `categoryLinksFor` (`generate-token-pages.js:289`) is used by **exactly** the two page
  generators and their tests — `grep -n categoryLinksFor *.js`. `generate-sitemap.js`
  does **not** import from `generate-token-pages.js` (only `generate-llms.js` does, for
  `tokenSlug`), so the sitemap's own category URLs (item 189's fork) cannot inherit a
  `src` tag from this change. **No sitemap, no `llms*.txt`, no canonical URL is touched.**
- Hub and A–Z pages (`tokens/index.html`, `tokens/az/*.html`, `chains/index.html`) emit
  **0** `?token=`/`?chain=`/`?pool=` links (measured this run) — nothing to tag there.
  Their waitlist CTAs already carry `seo_tokens_hub` / `seo_tokens_az` / `seo_chains_hub`.
- The KO estate (`ko/tokens/*.html` × 2,055, `ko/chains/*`) is rendered by the **same two
  generators**, so the fix reaches it with no KO-specific code. The tag value stays
  `seo_token`/`seo_chain` in both languages — language is already carried separately
  (`?lang` / the `/ko/` path), and forking the taxonomy per language would fragment the
  Mixpanel breakdown for no gain.
- Estate-internal links (`/tokens/<slug>`, `/chains/<slug>`, `/ko/…`) are **deliberately
  out of scope**: `analytics.js` is loaded on the static pages too (item 039), so tagging
  estate→estate navigation would book internal page-to-page browsing as fresh
  *acquisition*. Only the estate→app boundary — the same boundary 203 and the waitlist
  links already tag — is an arrival.

## 3. The change

1. Add a tiny shared helper in `generate-token-pages.js` (exported):
   `withSrc(url, src)` — returns `url` byte-identically when `src` is falsy; otherwise
   appends `src=<encodeURIComponent(src)>` with the correct `?`/`&` separator.
   Refactor `poolHrefFor`'s existing tail to call it (behaviour must stay byte-identical
   — 203's tests are the regression net).
2. Tag the four visible render sites above with `seo_token` / `seo_chain`.
3. `appUrl`'s definition, `renderItemListJsonLd`, and `poolHrefFor`'s signature are
   unchanged.
4. New test file `test_seo_app_link_attribution.js`, wired into `package.json`'s
   `test:serial` chain (the list `run-tests.js:67` parses) next to
   `test_seo_src_attribution.js`.
5. **No regenerated HTML is committed** (021/041/045/050/174/203 convention) — the 4,360+
   pages pick the tags up on the next `sitemap-update.yml` CI run.

## 4. Acceptance criteria (verifier checks each independently)

1. **Main CTA tagged, both generators.** Real `renderTokenPage` / `renderChainPage`
   output over a real fixture: the `.tp-cta` href is exactly
   `<appUrl>&src=seo_token` and the `.cp-cta` href is exactly `<appUrl>&src=seo_chain`.
2. **Category nav tagged, both generators.** Every `?token=…&poolTypes=` /
   `?chain=…&poolTypes=` href in rendered output ends with `&src=seo_token` /
   `&src=seo_chain`; the count of tagged category links equals the count
   `categoryLinksFor` returned (no link skipped, none double-tagged).
3. **No double-tagging anywhere.** No rendered href in either generator's output
   contains `src=` more than once. (`(href.match(/src=/g)||[]).length <= 1` over every
   `href="…"` in the page.)
4. **JSON-LD stays canonical — 203's invariant survives.** No `ld+json` block in either
   generator's output contains `src=` anywhere in the block (scanned whole-block, not
   per item), and every ItemList `url` matches `^https://www\.defi\.garden/\?pool=[^&]+$`
   or the clean untagged `appUrl`.

   `''`, `null` and `0`; and `poolHrefFor(p, fallback)` with no third argument returns
