# 218 — the north-star CTA is behind the fixed footer at rest on small viewports

- **Backlog row**: 218, score 9.0, status READY at pickup, risk HIGH, no spec file existed — this spec was written by the build run of 2026-08-03 from documented in-repo evidence (BACKLOG row 218, `specs/217-notes.md`, `playbooks/fixed-overlay-occlusion.md`, LOG.md 2026-08-03 build | 217) plus the operator's own rendered re-measurement recorded under **Evidence** below.
- **North star**: `pool_click{source ∈ {garden_cta, protocol_link}}` on pool-detail. `garden_cta` cannot fire from a button the user cannot see or press.

## Problem

`.app-footer` (`style.css:2513-2524`) is `position: fixed; bottom: 0; z-index: 100` with an **opaque** `background: var(--color-background)`. It therefore covers the bottom 58px (≤768px) / 69px (1280px) of the viewport **at every scroll position, including `scrollY = 0`**.

`.app { padding-bottom: 80px }` (`style.css:849-853`, "Space for footer") is the app-wide clearance that keeps the **end of the document** out from under it — that is the mechanism item 217 restored for this view. Clearance protects the document's last pixels. **It cannot protect an element in the middle of the document that happens to land inside the footer band at rest**, and the pool-detail hero's `garden_cta` anchor does exactly that at the narrowest width in CLAUDE.md's design bar.

Item 217's verifier found it (attacking an unproven claim in `specs/217-notes.md`), the operator re-measured it on the human's own pool, and it was filed rather than absorbed because the fix is footer *behaviour*, not clearance — a different change with its own risk call. It is **pre-existing**: 217's verifier measured identical CTA geometry with 217's fix mutated back out.

## Fix (decided, and validated in-page before this spec was written)

On the pool-detail view only, the footer **joins the document flow**:

```css
.app.pool-detail-view .app-footer { position: static; margin-top: auto; }
.app.pool-detail-view            { padding-bottom: 0; }
```

- `position: static` removes the overlay layer from this surface, so **no** content element — CTA, prose, or the last pixel of the page — can be occluded or click-intercepted at any scroll position or viewport. This is strictly stronger than 217's clearance mechanism, which it replaces on this view.
- `margin-top: auto` is the flex sticky-footer idiom. `.app.pool-detail-view` is **already** `display:flex; flex-direction:column` (via `.app:not(.has-results)`, `style.css:856+` — pool-detail carries no `has-results` class), so this needs no new layout mode. It keeps the footer at the bottom of the screen if pool-detail content is ever shorter than the viewport (e.g. the 072 dead-pool state), instead of floating mid-page. Verified inert when content overflows: geometry at 1280×2400 is identical with and without it.
- `padding-bottom: 0` removes the now-vestigial fixed-footer clearance, which would otherwise render 80px of dead background **below** an in-flow footer that carries a top box-shadow.

### This is NOT a revert of 217

`.app.pool-detail-view { padding-bottom: 0 }` restates the declaration 217 deleted, and a reviewer must be able to tell the difference:

- 217 removed the clearance canceller **while the footer was still an opaque fixed overlay**, so the page's last band was permanently behind it. That was a real defect and 217's fix was correct for the mechanism then in place.
- 218 removes the overlay. With the footer in flow, clearance protects nothing — the footer is *after* the content, not on top of it — and 80px of padding below it is pure dead space.
- **The outcome 217 asserted must still hold and is re-asserted here**: at the true bottom of scroll, at 360/768/1280 + dark, `.pool-detail-container` is not occluded by `.app-footer`. `test_footer_occlusion.js`'s four geometry cases stay green, unmodified.
- Only that test's **positive control** changes, because its mutation (`padding-bottom: 0 !important`) can no longer produce occlusion once the footer is in flow. It is replaced by a **stronger** control that reproduces the full pre-217/pre-218 state (`position: fixed` restored **and** clearance cancelled) and asserts occlusion returns. A control that cannot go red is not evidence of health; a control that mutates a mechanism the product no longer uses is worse — it passes while measuring nothing.

## Out of scope (filed, not silenced)

The same opaque-fixed-footer overlay still applies to the analytics grid and landing surfaces. Per `playbooks/fixed-overlay-occlusion.md`, occlusion of a *scrolling list* mid-scroll is not the defect class — the defects are content occluded at every scroll position (217) and content occluded **at rest** (218). Neither is currently proven on those surfaces, and item **219** (READY, 8.5) exists to give the audit a general occlusion lens that would find them systematically. Widening this diff to those views would be scope creep on the north-star surface's fix.
