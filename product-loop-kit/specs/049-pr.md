# 049 — Cross-surface internal linking (token ↔ chain ↔ category)

HIGH tier (generated SEO surface + cross-surface link generation with a real
correctness constraint — a wrong link creates a soft-404, the exact GSC
class 011-013 fought). Verifier PASS, 5/5 criteria, no failures.

## Goal

Token pages (`/tokens/<slug>`, backlog 014/021) and chain pages
(`/chains/<slug>`, backlog 041) were topically disconnected islands: a token
page names the chains its pools run on in every table row, but never links
to that chain's own page — and vice versa. 2026 SOTA (hub-and-spoke /
pillar-cluster architecture) treats this as the single strongest unused
internal-linking signal a programmatic SEO template has: the entities are
already on the page, they're just not linked. This item wires that up, plus
folds in the separately-proposed 043 (cluster by pool-type category) as a
third leg, since it's the same underlying idea — link the entities already
present on the page.

## Intuition

Every generated page already computes a `rec` (a token's or chain's ranked
record, with its displayed `pools` array). The fix is: for each `rec`, look
at what's already sitting in `rec.pools` — the chains a token trades on, the
tokens present on a chain, the pool-type categories represented — and turn
each into a link, but ONLY if the target actually exists as a real page.
"Actually exists" is the load-bearing constraint: the two generators
(`generate-token-pages.js`, `generate-chain-pages.js`) run independently and
each computes its OWN ranked/gated set (a token or chain can fail the
$100K-TVL floor, the anomaly-exclusion trust rail, or the all-0%-APY quality
gate and simply not get a page) — so before token pages can link to
`/chains/<slug>`, something has to compute "which chain slugs will actually
have a page this run" and pass that set in as a filter.

## What changed and why (diff in reading order)

1. **`generate-sitemap.js`** — exported the existing `getPoolType()`
   classifier (Lending / Staking / LP-DEX / Yield Farming) that the category
   sitemaps already used internally. One-line export, no logic change —
   this diff's category leg reuses it instead of re-implementing pool-type
   detection a third time (standing "reuse before inventing" decision).

2. **`generate-token-pages.js`**:
   - `chainLinksFor(rec, generatedChainSlugs, cap)` — walks `rec.pools`,
     slugifies each pool's chain, keeps only slugs present in the caller-
     supplied `generatedChainSlugs` Set, dedupes, caps at 8.
   - `categoryLinksFor(pools, baseAppUrl, cap)` — walks `pools`, classifies
     each via `getPoolType`, dedupes, builds `${baseAppUrl}&poolTypes=<cat>`
     links (a REAL, working app view — not a static page, so no
     ungenerated-slug risk for this leg specifically).
   - `renderLinkNavHtml(items, ariaLabel, heading, extraNavClass)` — one
     shared nav-block renderer, reusing the pre-existing `.related`/
     `.related-links` CSS via an ADDED class token (see deviation #4 below)
     instead of writing new CSS for three more nav variants.
   - `renderTokenPage` gained a 4th param `chainLinks`; renders the Chains
     nav + a By-category nav (always present — every token page has pools
     with at least one category) right after the existing related-tokens
     nav.
   - `main()`: after ranking tokens, lazily `require('./generate-chain-
     pages.js')` to get `rankTopChains(pools, 0)` on the SAME already-
     fetched `pools`, builds the real `generatedChainSlugs` Set, and passes
     `chainLinksFor(rec, generatedChainSlugs)` into each page render.
   - **`module.exports` moved above the `require.main` block** — see
     deviation #3, this is a prerequisite bug fix, not a stylistic change.

3. **`generate-chain-pages.js`** — the mirror image:
   - `topTokensOnChain(rec, generatedTokenSlugs, cap)` — walks `rec.pools`,
     splits each pool's (possibly multi-token) symbol via the token
     module's `tokenSymbols`, aggregates on-chain TVL per token, keeps only
     tokens in `generatedTokenSlugs`, sorts by that TVL, caps at 8. No lazy
     require needed here: this module already imports the full token module
     (`tp`) unconditionally at its own top level (it did before this diff,
     for the analytics/formatting helpers), so `tp.rankTopTokens(pools, 0)`
     is already reachable from `main()` with zero new dependency edges.
   - `renderChainPage` gained a 4th param `tokenLinks`; renders the "Top
     tokens on `<Chain>`" nav + the same By-category nav pattern.
   - `main()`: computes `generatedTokenSlugs` from `tp.rankTopTokens(pools,
     0)` on its own already-fetched `pools`, passes `topTokensOnChain(rec,
     generatedTokenSlugs)` into each render.

4. **`test_token_pages.js` / `test_chain_pages.js`** — new tests for both
   directions: dedupe + cap behavior, exclusion of a slug outside the given
   generated set, rendering (nav present/absent), and — the important one —
   a "real cross-fixture ranking" invariant test that requires the OTHER
   module and asserts every emitted link's slug is actually in that
   module's real ranked output on the same shared fixture pools. This is
   what the verifier specifically checked and ran itself.

## Deviations from spec (also in `specs/049-notes.md`)

1. Category leg uses the interim `?token=/chain=&poolTypes=<cat>` live app
   view, not a deferred no-op — the spec explicitly left this to the
   builder pending 045's (not-yet-built) category pillar pages.
2. Cross-links only consider the DISPLAYED pool table (`rec.pools`, already
   sliced to top-`POOLS_PER_PAGE`-by-TVL), not the full qualifying pool set
   — consistent with 033's existing "only count what's shown" gate
   philosophy.
3. Fixed a latent ordering bug: `generate-token-pages.js` had `if
   (require.main === module) { main()... }` textually BEFORE `module.exports
   = {...}`. Harmless before this diff (nothing ever required this module
   from inside its own `main()`), but 049's token→chain direction needs
   exactly that (a lazy require of `generate-chain-pages.js`, which
   requires this module right back) — with the old ordering, that circular
   require observed `module.exports` still at its default `{}`, and
   `rankTopChains` blew up with `isQualifyingPool is not a function`.
   Reordering (4 lines moved, no other change) fixes it; verified via a
   from-scratch repro before touching the real files.
4. New cross-link navs use `class="related xlink-chains"` /
   `"related xlink-tokens"` / `"related xlink-category"` — a second class
   token, not a replacement — so the existing `.related`/`.related-links`
   CSS keeps applying (CSS class selectors are token-based) while the
   pre-existing tests asserting on the exact literal `class="related"`
   (the original related-tokens/chains-only nav) keep passing.

## Risk / trust rails

No change to `APY_SANITY_LIMIT`, `DEFAULT_MIN_TVL`/`MIN_POOL_TVL`, anomaly
exclusion, canonical logic, or ranking. Every new link is either (a)
filtered against a real generated-slug set computed from the SAME live
data the target generator itself gates on, or (b) a live app URL (never a
static file, so never a dead link by construction).

## Quiz

1. Why does token→chain linking require a *lazy* require of
   `generate-chain-pages.js` inside `main()`, instead of a top-level
   require?
   - A) Because chain-pages.js already requires token-pages.js at its top
     level, so a top-level reverse require would create a load-time
     circular dependency where one side observes an incomplete exports
     object.
   - B) Because lazy requires execute faster in Node.
   - C) Because ES modules forbid circular imports.

2. What pre-existing bug did this diff have to fix as a prerequisite, and
   why did it only surface now?
   - A) `module.exports` was assigned in `generate-token-pages.js` AFTER
     the `require.main` block; harmless before because nothing ever
     required this module from inside its own `main()`, but 049's lazy
     require does exactly that.
   - B) `generate-chain-pages.js` was missing a sitemap export.
   - C) `tokenSlug` produced invalid slugs for chain names.

3. Why do `chainLinksFor`/`topTokensOnChain` only consider the DISPLAYED
   (top-N-by-TVL) pool set, not every qualifying pool for a token/chain?
   - A) Performance — scanning every pool would be too slow.
   - B) It's a known gap to be fixed in a follow-up.
   - C) Consistency with 033's existing quality-gate philosophy: the page's
     own quality gate only looks at what's shown, so cross-links follow the
     same "derived from on-page data" rule.

4. Where does the category leg (folding in 043) link to, and why not a
   dedicated category hub page?
   - A) A new `/categories/<slug>` static page generated by this diff.
   - B) The existing `?token=<SYM>&poolTypes=<cat>` (or `?chain=...`) live
     app view, because no category hub page exists yet (045 only shipped
     token/chain hubs) and the spec explicitly left this choice to the
     builder.
   - C) DefiLlama's own category pages.

5. How do the new cross-link nav blocks avoid breaking the pre-existing
   tests that assert on the exact string `class="related"`?
   - A) They use an entirely different, hand-rolled CSS class with
     duplicated styles.
   - B) They add a SECOND class token (e.g. `class="related xlink-chains"`)
     — CSS class selectors are token-based so `.related` styling still
     applies, but the attribute value no longer equals the literal string
     `"related"` the old related-tokens/chains-only tests check for.
   - C) The old tests were deleted and rewritten for this diff.
