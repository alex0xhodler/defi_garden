# 212 — PR explainer (HIGH tier: full walkthrough + quiz)

## The goal, in one sentence

Stop the site telling an AI agent that asks about **one pool** the same thing it tells an agent that asks
about **the whole site**, and give the 2,154-page static estate — the only genuinely agent-readable
content this product has — a markdown address it can actually be fetched at.

## The intuition

Content negotiation on this site was one line long: *if the request wants markdown, serve `llms.txt`.*
That rule was attached to `source: "/"`, and here is the thing that makes it a bug rather than a
simplification — **Vercel matches the path, and a query string is not part of the path.** So `/`,
`/?token=USDC` and `/?pool=43641cf5-…` are, to that rule, the same URL. All three returned the identical
6,641-byte site index. Measured again this session, unchanged.

Now put yourself at the other end. An agent asks for one Jupiter pool with `Accept: text/markdown`. It
gets back a 200, a `text/markdown` content type, and a well-formed document with proper headings. Nothing
in that response says "this is not what you asked for." So the agent answers the user from the homepage
index. **A confidently-wrong parse is indistinguishable from a correct one at the consumer's end** — which
is why this is worse than returning nothing at all.

Meanwhile the inverse failure sat next to it: `/tokens/usdc`, a real server-rendered page full of exactly
the facts an agent wants, returned 18,814 bytes of `<!DOCTYPE html>` to a markdown request. So agents
parsed HTML where markdown would have worked, and got wrong markdown where no facts existed at all.

## What changed, in reading order

### 1. `vercel.json` — the `/` markdown rule stops answering for URLs it knows nothing about

The existing `/` → `/llms.txt` rewrite gains a `missing` array: 17 `{"type":"query","key":…}` entries.
If **any** of them is present, the rule does not match, and the request falls through to the ordinary
`/` → `/home` rewrite — the normal HTML app. Bare `/` still serves `llms.txt`, which was always the one
correct case and must not regress.

Vercel cannot express "no query string at all" — `source` is path-only and `has`/`missing` predicates are
per-key — so the list has to be enumerated, and enumerated lists rot. The 17 keys are exactly the members
of `home.html`'s two router arrays: `ANALYTICS_PARAMS` (`token`, `chain`, `pool`, `poolTypes`,
`protocols`, `minTvl`, `minApy`, `app`) and `PLANNER_PARAMS` (`goal`, `monthly`, `years`, `pace`,
`preset`, `fresh`, `capital`, `fm`, `dl`). Nothing is excluded by hand: `lang`, `src`, `ref`, `mix`,
`pitch` and `waitlist` are simply not members, so they need no justifying comment.

Rot is handled by a **drift-guard test that derives from the router itself** — it parses those two array
literals out of `home.html` and asserts **exact set equality** with the `missing` list on both the rewrite
and the header rule, in both directions. Those arrays *are* the definition of "this query string changes
what `/` serves," so equality with them is the right invariant. This matters more than it sounds: the
first version of this guard scanned for literal `.get('key')` calls instead, and was structurally blind to
`app` — which the router reads via `ANALYTICS_PARAMS.some(k => params.has(k))` and which `planner.js`
links as `/?app=1` from the header's analytics icon. The verifier caught the resulting live defect; the
guard was rebuilt around the mechanism rather than around something that resembled it. A third check
sweeps `home.html` for any literal `params.has('key')` call outside those arrays and finds none, so the
two arrays are provably complete.

The identical `missing` array goes on the matching `/` **header** rule too. Without that, `/?pool=…`
would return the HTML app labelled `Content-Type: text/markdown`.

### 2. `vercel.json` — path-aware negotiation for the estate

Four new rewrites: `/tokens/:slug([^/.]+)`, `/chains/:slug([^/.]+)` and their `/ko/` twins → the sibling
`.md`, gated on the same `Accept: text/markdown` predicate already used elsewhere in the file.

Two details are load-bearing:

- **The `([^/.]+)` constraint is not decoration.** A bare `:slug` matches `[^/]+`, dots included, so
  `GET /tokens/usdc.md` would itself match and rewrite to `/tokens/usdc.md.md` → 404. An agent following
  the twin's own URL would get nothing. No generated slug contains a dot (verified across all 2,079 token
  and 87 chain slugs), so the constraint is free and excludes every extension by construction.
- **Four passthrough rewrites sit *before* them**: `/tokens/index`, `/chains/index` and the `ko/`
  equivalents → their `.html`. Those paths match `:slug`, have no twin, and would have 404'd — violating
  the very rule this item is here to establish. Rewrites are first-match-wins, so an earlier unconditional
  rule short-circuits them. `/tokens/az/<letter>` is three segments and never matched; that is asserted
  rather than fixed.

Headers: negotiated markdown responses get `Content-Type: text/markdown; charset=utf-8`, `Vary: Accept`
and `X-Robots-Tag: noindex`; direct `.md` requests get the same via a `/(.*)\.md` rule; the four estate
paths get an unconditional `Vary: Accept` so no shared cache can hand a markdown body to a browser.

**The indexing decision, argued** (the spec left this open): **both** — out of every sitemap *and*
`X-Robots-Tag: noindex`. A `.md` twin is by design a duplicate of an indexed page. Sitemap absence alone
leaves it discoverable by link or crawl and able to create precisely the duplicate-content pair that
item 211 exists to remove. The header is the belt to the sitemap's braces, and neither alone is enough.

### 3. The generators — twins written in the same run as the HTML

`generate-token-pages.js` gains `renderTokenPageMarkdown()`; `generate-chain-pages.js` gains
`renderChainPageMarkdown()`. Each is called in the **same loop iteration**, from the **same** `rec` and
the **same** `genDate`, as its HTML sibling. That is the whole design: fact parity is not maintained by
discipline, it is impossible to violate.

Everything the markdown states is reused, never re-derived — `buildAnswerAndFaq()` for the opener and FAQ
(never re-worded), `poolHrefFor()` for the `/?pool=<id>` deep links with the same `src` attribution the
HTML uses, `formatUsd()`/`formatApy()` for every number (en-US pinned, per CLAUDE.md), and `MIN_POOL_TVL`
for the TVL-floor claim. **No floor literal is re-typed anywhere** — the 159/174 rule — and a scratch-run
test patches the constant and asserts the markdown moves with it. Output is a real table with labelled
columns plus `#`/`##`/`###` headings, not prose lists.

Both languages come out of the same function via its `lang` argument, through existing `translations.js`
keys — no new keys were needed, and all of them were verified resolving to real English and real Hangul.

Stale-file cleanup, which removed only `*.html`, now removes `*.md` too at all six cleanup sites. Without
that, a token later dropped by the 030 yield gate would lose its page and keep its twin forever — a
markdown document describing a page that no longer exists, which is the drift this item exists to prevent.

### 4. `/plan.html` — a non-defect, and the reason it is worth saying so

The spec listed `/plan.html` returning `Redirecting...` as a fourth defect. It is not one. That is
`"cleanUrls": true` issuing a 308 to `/plan`, which returns the real 8,778-byte planner page — and it
happens for every `.html` URL regardless of `Accept`. The spec's probe caught the redirect stub instead
of following it. `/plan` already does exactly what the new rule requires. **No change was made**; chasing
this would have meant altering `cleanUrls` site-wide for a non-problem. It ships as assertions instead.

## Why the twins are not in this diff

They cannot be, without breaking the fact-parity criterion they exist to satisfy. The committed
`tokens/*.html` were written by CI from one live DefiLlama fetch; `.md` generated here would come from a
different fetch and state different APYs beside them on day one. Parity is structural only within a single
run — and that run is CI's: `sitemap-update.yml` already lists both generators in its `push` paths, so
**merging this PR is the trigger.** Same convention as items 045/050/051.

The cost, stated plainly: for the length of one CI run, `Accept: text/markdown` on `/tokens/<slug>`
returns **404** rather than markdown. That is an honest "nothing here" — the outcome leg 3 is arguing
for — instead of today's confidently-wrong index, and it lasts minutes.

## Measurement — there isn't one, and that is the honest answer

There is **no server-log access in this stack, and no client-side event can fire for an agent that never
runs JS**. Agent reads of these twins are **structurally unmeasurable with current instrumentation**. This
item is a **capability bet**, recorded as such — not an experiment with an expected lift. No traffic effect
will be reported for it in any window. The nearest honest proxies, checkable later, are GSC impressions on
the estate and any future appearance of a non-`undefined` `src`/`ref`. If someone wants this measured
properly, the item to file is **edge or server-side request logging by `Accept` header** — a different
item, and the honest prerequisite for ever claiming an effect here.

## Risk

**HIGH**, and the builder and operator agree on why: `vercel.json` is named explicitly on NORTH_STAR's
HIGH list (config/infra), and this edits the same rewrite table that routes `/` to the planner and every
parameterized URL to the analytics app — the SEO lifeline. Mitigations actually run: `test_smoke.js`
(the both-router-paths gate) **PASS in 130.7s** on the branch; 63 offline assertions walking the real
rewrite table in order; and a **30/30 byte-identity proof** that generated `.html` is unchanged against
`origin/main` from the same fixture. Nothing on the NEVER list is touched — no trust rail, no credential,
and nothing de-indexed (the only `noindex` added is on `.md` twins that have never been indexed and must
never be).
