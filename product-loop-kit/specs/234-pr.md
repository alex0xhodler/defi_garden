## Goal

The agent pillar's chain is 224 (edge telemetry) → 227 (railed read API) → 228 (MCP server) → **234**.
227 and 228 shipped this week, so there is finally something to sell. This item adds the layer that can
charge an agent for a read — and, just as important for north-star leg (A), the layer that can tell a
*real* agent from a crawler heuristic, because a request carrying a payment or a signature is a real agent
by construction.

The human's boundary, verbatim (NORTH_STAR standing decision 2026-08-05): *"free stops at getting the apy
data, not the historical ones that we are computing and all other computed kpis."*

## Intuition in one paragraph

x402 is just HTTP `402 Payment Required` with a machine-readable body: the server answers "here is what
this costs, in this asset, on this network, pay to here", the agent retries with an `X-PAYMENT` header,
and the server serves the data. Web Bot Auth is the identity half — RFC 9421 HTTP Message Signatures over
Ed25519, so an agent can prove *who* it is. The interesting engineering here is not the protocol; it is
making sure the free/paid split can never drift, and that nothing on the surface claims more than the code
actually does.

## What changed, and why

**1. A price schedule as data, with the default pointing the safe way.** `edge/x402-core.js` holds one
table: `/api`, `/api/health`, `/api/pools`, `/api/pools/:id`, `/api/pricing` are **free**;
`/api/forever-number` is **paid** — it is the only computed-KPI route that exists today, and the human's
directive names forever-number math explicitly. The load-bearing part is not the list, it is
`DEFAULT_TIER = 'paid'`: an existing route that nobody priced classifies as paid, so a future Sharpe or
history endpoint cannot ship free by omission.

**2. The dispatcher became the single source of routes** (this is the fix the verifier forced; see
Deviations). `edge/api-core.js`'s `if (path === '…')` chain is now a declarative `ROUTES` table.
`ENDPOINTS` derives from it, `matchRouteId()` walks it, and `x402-core.js`'s `matchRoute()` delegates to
that — so the payment gate's population is the code that *actually dispatches*, not a list that describes
it. A three-way set-equality test (dispatcher ids ↔ `ENDPOINTS` ↔ `PRICE_SCHEDULE`, both directions per
pair, each with its own self-defeat case) keeps them married.

**3. MCP is gated through the same schedule, not a second list.** `edge/mcp-core.js`'s `TOOLS` already
carry a declarative `route` field, so `classifyMcpTool()` derives a tool's price from the route it
delegates to. `forever_number` is paid; `find_pools`, `get_pool`, `explain_rails` are free. Gating `/api`
while leaving `/mcp` open would have been a free bypass of the same data.

**4. Fail closed, everywhere.** Live mode accepts a payment only when the configured facilitator returns
an explicit `isValid: true`. No facilitator, a non-OK response, an unparseable body, a thrown fetch, or
`isValid: "true"` as a string → 402. Test mode accepts a structurally-matching payload on a test network
only, and says so in the response header.

**5. Identity is telemetry, never a key.** A Web Bot Auth signature is verified and logged
(`verified` / `unverified` / `invalid`, never silently upgraded), but it does not unlock paid data — a
verified agent with no payment still gets a 402. Anyone can generate a keypair; that must not be a payment.

**6. Telemetry gained three columns without risking the two that already work.** `agent_reads` gets
`agent_identity`, `identity_status`, `payment_status` via `ALTER TABLE` — which the human runs by hand.
Until they do, a 12-column INSERT would fail on every write and, because logging failures are swallowed by
design, 224/227's telemetry would go *silently* dark. So the Worker tries the extended INSERT and falls
back to the original 9-column statement.

## Deviations from the spec

- **wrangler**: the spec asks for acceptance "in local dev (wrangler)". There is no wrangler in this
  sandbox and browser-originated HTTPS is blocked at the proxy, so the tests import `edge/agent-log.mjs`
  and call its default export's `fetch()` with real `Request` objects — the technique `test_api_worker.js`
  already uses, and the reason that file is `.mjs`.
- **"without payment/identity → 402"**: read conservatively as payment-only. Identity does not unlock.
- **No settlement, and the surface says so.** `verifyPayment()` calls the facilitator's `/verify`, never
  `/settle`. `X-PAYMENT-RESPONSE` therefore reports `settled=false` on every branch — including live mode,
  where it reports `verified=true`; test mode reports `verified=false; checked=structural`, because
  nothing verified it. Both the "no settle" and "no replay/nonce protection" gaps are stated in
  `edge/X402.md`'s residue section rather than papered over.
- **Docs on llms.txt / md twins were NOT regenerated** (spec Change §4). Regenerating pulls live pool data
  into a large SEO diff; pricing discovery is served instead by `/api/pricing` plus the `pricing` block on
  `GET /api`. Residue, stated as such.

## Class honesty

This item does **not** close its class. Open, with numbers: the free/paid boundary is restated in prose on
**4** hand-typed sites against **1** machine source (`edge/X402.md`, `edge/MCP.md`, `edge/API.md`, and
`buildPricingDoc()`'s `boundary` sentence) — filed as **backlog 267**. Also open and documented in
`edge/X402.md`: no facilitator `/settle` call; no replay/nonce protection on a spent `X-PAYMENT` header;
no Web Bot Auth key discovery (env keyring only); no RFC 8941 header combining or RFC 9421 component
parameters.

## Verifier round 1 found three P1s. What they were, because they are the useful part

1. **The default that the whole design leaned on was unreachable.** `matchRoute()` derived route ids from
   the price schedule's own keys, so a route added to the dispatcher alone returned `null` and was served
   **free with the gate on** — five test files stayed green while the verifier proved it with an injected
   `/api/sharpe`. Fixed at the root by the `ROUTES` refactor above. Distilled into
   `playbooks/detector-signal-coverage.md` as axis 7 (population *provenance*: the guard enumerated the
   declaration, not the executor — the same shape as item 212).
2. **A paid 200 was `Cache-Control: public, max-age=300`** with no `Vary`, so a shared cache could hand
   paid data to unpaid requests. Gated 200s are now `no-store`; free routes keep their 300s caching.
3. **`settled=true; mode=live`** was emitted although nothing settles. Now `settled=false` on every branch.

Plus four smaller ones: CORS did not allow `X-PAYMENT` or expose `X-PAYMENT-RESPONSE`; `API.md` claimed
all non-2xx responses were `no-store` (404s are not); "byte-identical to pre-234" overstated what the test
could witness; `MCP.md` promised three tools stay free "forever" rather than "under the current boundary".

## Verifier round 2 found three more. What they were

1. **`edge/DEPLOY.md` still claimed live mode settles.** `:336` said `"live"` "verifies against a real
   facilitator and can move real value"; `:352` said to flip `X402_MODE` to `"live"` "once ready to actually
   settle" — both false, contradicting `edge/X402.md`'s own correct residue notes in the runbook a human
   actually follows. Restated in `X402.md`'s honest words (verifies, never settles, no `/settle` call
   anywhere in `edge/`); a third instance (`:339`, "the wallet/handle payments settle to") fixed the same
   way while sweeping the rest of the file. Guarded going forward by a new `test_edge_docs_settlement_claims.js`:
   population = every `edge/*.md` file, read from `fs.readdirSync` (never a hardcoded list); predicate (as
   WIDENED in verifier round 3, below — the round-2 version this bullet originally described was weaker than
   this) = a chunk is a violation iff it claims settlement/value-movement AND the claim is not excused — excused
   means a negation token appears BEFORE the claim within the same chunk, or is directly ATTACHED to the claim
   as its predicate value (`` `settled` is `false` ``); "a negation token appears anywhere in the chunk" is
   NOT sufficient (that weaker rule is what round 3 found two misses in — see below). Self-defeat proves it
   fires on an injected claim, including the verbatim pre-fix wording.
2. **The MCP gate priced the DECLARED route, the dispatch used the DISPATCHED pathname** — axis 7 one layer
   below round 1's own defect (`detector-signal-coverage.md`'s new section on this item, provenance not
   population): `edge/agent-log.mjs`'s `/mcp` gate classified a `tools/call` via `tool.route`
   (`x402Core.classifyMcpTool`), but `edge/mcp-core.js`'s real dispatch serves whatever
   `tool.argsToRequest(args).pathname` builds. A future tool (`budget_helper`) declaring the free
   `/api/pools` route while its `argsToRequest` resolved `/api/forever-number` served the full paid body,
   200, gate on, no payment — reproduced end-to-end and fixed by classifying BOTH the declared route and the
   dispatched pathname (via the same `apiCore.matchRouteId` `/api` itself walks) and gating on whichever is
   stricter. If the dispatch probe throws or resolves to no route, the gate falls back to the DECLARED
   classification only — a malformed-args call to a free tool still gets its ordinary `-32602` JSON-RPC
   error, never a fabricated 402.
3. **`explain_rails` couldn't see its own pricing state.** `edge/mcp-core.js` called `handleApiRequest`
   without the `pricing` field `/api` itself receives, so with the gate live MCP's `explain_rails` still
   reported the DARK default (`enabled:false, mode:'test'`) for the same env, same instant `GET /api`
   correctly reported `enabled:true, mode:'live'` — falsifying `X402.md`'s "can never claim a state it
   cannot actually see" and `mcp-core.js`'s own "delegates verbatim to GET /api". Fixed by threading the
   Worker's already-computed `x402Core.readConfig(env)` state through `handleMcpMessage` to
   `handleToolsCall`'s call into `handleApiRequest` — `mcp-core.js` stays pure, taking the state as an
   input, never reading `env` itself.

## Verifier round 3 found three advisory (non-blocking) findings on an already-PASSED branch

1. **The settlement-claim guard was weaker than every description of it (P2).** Round 2's
   `test_edge_docs_settlement_claims.js` split clauses only when the character AFTER `.`/`!`/`?`/`;` looked
   like a new sentence, and treated a chunk's negation as "present anywhere in it". Two constructions using
   the guard's own core verb slipped through: `` `X402_MODE` "test" never settles; live mode can move real
   value.`` (the `;` was followed by a lowercase `l`, so it never split — "never" from clause 1 excused
   clause 2) and `Live mode settles the payment, and no retry is needed.` (no comma-conjunction split
   existed — "no", negating an unrelated "retry", excused the whole chunk). Fixed at the predicate: splitting
   is now unconditional on `.`/`!`/`?`/`;`+whitespace and also cuts on `, but`/`, and`/`, so` (never inside a
   backtick-delimited inline-code span, so `` `settled=false; verified=false` `` stays one atomic token); a
   negation now only excuses a claim if it appears BEFORE the claim within the same chunk, or is directly
   ATTACHED to the claim as its predicate value (`` `settled` is `false` ``). Both misses are now permanent
   self-defeat cases, verbatim. The three docs that described the round-2 predicate as clause-level/
   negation-scoped (this file, `234-notes.md`, and the test's own header) now describe the round-3 predicate
   instead. A residual gap is stated honestly in the test header (conjunctions outside `but`/`and`/`so`, and
   negation vocabulary outside the fixed token list, are not solvable by a regex predicate) — confirmed
   against the real `edge/*.md` population: zero sentences trip it today.
2. **An undocumented purity assumption (TOCTOU) in the MCP gate (P3).** Round 2's fix evaluates
   `tool.argsToRequest` TWICE for a gate-eligible call — once in the Worker's probe (`edge/agent-log.mjs`),
   once again in the real dispatch (`edge/mcp-core.js`) — and silently assumed the two agree. An impure
   `argsToRequest` (e.g. one alternating its output) could show the probe a free pathname and the real
   dispatch a paid one: reproduced end-to-end (200, full paid body, gate ON, no payment). Exploiting it still
   requires committing code into `TOOLS`, same prerequisite as finding 2 above. Fixed by adding a purity
   guard to `test_x402_core.js` §G2b — calls `argsToRequest` twice per REAL tool with identical args and
   asserts the pathname AND search params agree, with self-defeat cases for a drifting pathname, drifting
   params, and a throw. `edge/agent-log.mjs`'s gate comment now states the assumption explicitly instead of
   claiming the stricter-of rule alone closes it.
3. **The runbook's "exhaustive" delta list missed a fourth difference (P3).** `edge/DEPLOY.md`'s
   byte-identity paragraph enumerated three surfaces that gained new response BODIES but never mentioned that
   `Access-Control-Allow-Headers` (now includes `X-PAYMENT`) and `Access-Control-Expose-Headers:
   X-PAYMENT-RESPONSE` changed on EVERY `/api/*` and `/mcp` response, already documented at `edge/API.md`'s
   CORS section. Fixed by scoping the byte-identity claim to response bodies and adding the CORS change as an
   explicit fourth, orthogonal difference.
