# 168 — The AI-discovery surface must describe the Garden Planner (HIGH tier explainer)

## The goal in one line

`llms.txt` / `llms-full.txt` are the files that tell an LLM what this product *is*,
and they described a DefiLlama-style yield screener — the planner, the product's
front door, appeared **zero** times — so this item adds a `## Garden Planner`
section built from live, rail-passing data and corrects the homepage description
of both faces.

## The intuition

Item 166 (shipped hours before this one) fixed where this surface's links *go*.
168 fixes what the surface *says*. Same two files, adjacent failure modes: 166's
rows pointed somewhere that could not address the pool they quoted; 168's file
answered "what is DeFi Garden?" with a description of the one product we
deliberately are not.

The measured before-state, from live prod:

```
$ grep -icE "planner|garden plan|savings|goal|subscription|forever number" llms.txt
0
```

Zero — against `CLAUDE.md`'s own definition ("Garden Planner — the DEFAULT
feature") and the 2026-07-12 business-model decision ("the planner's SUBSCRIPTION
archetype / forever-number flip is the product's front door"). An LLM can only
cite what the surface says exists. Ours said "yields, by token and chain", which
is precisely the query space where a DefiLlama-shaped competitor already wins.

## What changed and why

### 1. One rail predicate, not two (`generate-llms.js`)

`pickHighYield()` inlined its filter. That filter is the 159 trust rail
(`tvlUsd >= $10M && apy > 0 && isFinite(apy) && apy <= 1000`), and this item needed
the *same* rail for a second purpose — deriving a rate. Copying it would have
created the exact second-source-of-truth pattern that items 148, 159 and 166 each
punished in turn. So it was extracted to `isRailPassing(pool, minTvlUsd)` and
`pickHighYield()` now calls it. Semantics unchanged — 159's suite still passes.

### 2. `plannerRate(pools)` — the only number the new section publishes

Returns `{ medianApy, eligibleCount }`, or `null` when nothing passes the rails.

Two deliberate choices, both narrower than they had to be:

- **Median over the FULL rail-passing set**, not over `pickHighYield()`'s top-15.
  The top-15 is sorted APY-descending — a leaderboard, not a typical rate.
  Publishing a leaderboard mean as "the blended rate" would be the optimistic,
  trust-eroding direction.
- **No forever-number dollar figure is published at all.** The section states the
  formula (`forever number = annual bill ÷ blended rate`) and stops. A capital
  figure computed off a market-wide median would understate what a saver actually
  needs, and the acceptance criteria forbid invented inputs — so the formula is
  the citable content and the plan supplies the inputs.

When `plannerRate()` returns `null` the section still renders — prose, archetypes
and URLs intact, rate lines omitted. Never `undefined`, `NaN`, or `$0`.

### 3. `buildPlannerSection()` — one emitter, both files

`buildConcise()` and `buildFull()` both call it. Two hand-maintained copies of the
same copy is how the two files drift apart.

### 4. The URLs, and why these three

Only URLs that were verified to route **and** to do what the sentence says:

| URL | Why it is safe to publish |
|---|---|
| `/plan.html` | `home.html:80` — the planner path, unconditionally |
| `/?preset=tomoko`, `/?preset=kevin` | real `PRESETS` (planner.js:1119-1122); `preset` ∈ `PLANNER_PARAMS`; carry no invented numbers |

Deliberately **not** published: `?goal=<id>` on its own.
`decodePlanFromUrl()` (planner.js:1080-1113) returns `null` without both `goal`
and `pace` plus `monthly`-or-`capital`, so such a link would silently land on an
empty goal picker while the text promised a filled plan. That is 166's defect
class and it was kept out by construction.

## The two corrections made during review — the interesting part

Both were caught after the build agent reported green, and both are the same
species as the bug this item exists to fix: **a sentence that the product does
not honour.**

### Correction 1 — "bare `/` is the planner" is false

The first draft's homepage TL;DR read *"https://www.defi.garden/ is the goal-first
Garden Planner"*, and the section TL;DR called the planner *"the default
experience at the bare site root"*. Both follow `CLAUDE.md`. Neither is true of the
running code. `home.html:82`:

```js
window.__APP_MODE = needsAnalytics ? 'analytics' : (needsPlanner ? 'planner' : 'landing');
```

Bare `/` matches no analytics param, no planner param and is not `/plan.html`, so
it resolves to `'landing'` — the search-first surface in `landing.js`, which links
*out* to `plan.html` (`landing.js:260/282/329/339`). This is the 2026-07-15 landing
pivot; **`CLAUDE.md`'s "bare `/` → planner" line is stale relative to the code.**
That divergence is flagged for the human here, not silently edited.

Confirmed in a real browser, not by reading the router (operator spot-check,
headless Chromium against the local server):

```
/?preset=tomoko  → mode=planner,  .gp-app rendered, 0 page errors
/?preset=kevin   → mode=planner,  .gp-app rendered, 0 page errors
/plan.html       → mode=planner,  .gp-app rendered, 0 page errors
/                → mode=landing,  planner NOT rendered
```

### Correction 2 — "a plan's own rate is usually lower" is also false

The same draft hedged the published market-wide median with *"a plan's own rate is
usually lower: the planner picks a smaller, more conservative pool set."* It reads
like appropriate caution. It is backwards. `curatePools()` (planner.js:604-671)
filters to a temperament band and then sorts **APY-descending**, taking the top
three — so a plan's blended rate is typically **higher** than the median across
everything that clears the rails.

The rendered proof, same spot-check:

```
/?preset=tomoko → "Retirement $1,000/mo … grows to $162,000 in 10 yrs
                   Blended APY 5.78%"
```

5.78% against the file's market-wide median. The direction claim was removed
rather than reversed — the honest statement is that the two numbers are computed
over different sets, which is what the shipped copy now says. This is the
`dual-source-logic-divergence` playbook's shape, caught by rendering the product
instead of trusting the prose.

## Diff in reading order

1. `generate-llms.js` — `isRailPassing()` extraction, `plannerRate()`,
   `buildPlannerSection()`, both homepage TL;DR lines, two planner query examples
   in `## Common Search Patterns`, `main()` wiring, exports.
2. `test_llms_planner_section.js` (new) — see below.
3. `package.json` — the new test inserted into `test:serial` immediately after
   `test_llms_rails.js` (that string is the single source of the file list;
   `run-tests.js` parses it).
4. `llms.txt`, `llms-full.txt` — regenerated from a live DefiLlama fetch.

## What is deliberately NOT in this diff

- **`translations.js` / Korean.** The EN+KO rule was **checked, not skipped**:
  `llms*.txt` is a single English machine-readable artifact with no KO
  counterpart, and this item adds no user-facing UI string, so the rule is not
  engaged. Recorded here because a reviewer should see the check happened.
- **`CLAUDE.md`.** Its stale bare-`/` claim is reported above for the human, not
  edited by the loop.
- **No new instrumentation.** The planner funnel is already instrumented
  (`plan_created`, `plan_saved`, `waitlist_*`); this change can only affect *who
  arrives*, so there is nothing new to emit.
- Anything in `planner.js`, `plan.html`, `home.html`, `app.js`, `PoolDetail.js`,
  the sitemaps, `stories/`, or the token/chain pages.

## Risk tier: HIGH

Regenerates committed AI-discovery/SEO surface (NORTH_STAR's HIGH list) and it is
the surface that speaks for the product, so wrong copy here is a trust problem,
not a cosmetic one. **Not** on the NEVER list: no rail weakened (the rails are
reused and now have one fewer copy), nothing de-indexed, no credentials, no money.
