# 174 — the 2,200-page false safety floor (HIGH-tier explainer)

## Goal

Every generated SEO page — 2,207 English `tokens/*.html` + `chains/*.html`, plus their KO twins —
answered the question *"Are these rates safe?"* with:

> Every rate shown passes **DeFi Garden's trust filters — a $100K minimum TVL** and exclusion of
> anomalous (>1000% APY) pools.

The product's floor is **$10M** (`app.js:801`, `DEFAULT_MIN_TVL`; CLAUDE.md: *"`DEFAULT_MIN_TVL = $10M`
everywhere"*). The sentence did not scope the claim to the page — it asserted a property of *DeFi Garden's
trust filters*, in answer to a safety question. A reader, human or LLM, came away believing our safety
floor is **1/100th** of what it is.

This is item 159's defect one surface over: 159 was two text files, this was 2,234 pages.

## The intuition

The `$100K` floor on these pages is **real and deliberate** — a human directive from 2026-07-11 says the
SEO surface deliberately reaches below the app's caution floor to capture long-tail search. Nothing about
that is dishonest. What was dishonest was the *sentence*: it took the page's own listing bar and sold it as
the product's safety guarantee.

So the fix is not to move a floor. It is to make each page **describe the floor it actually applied**, and
to stop laundering a listing bar into a safety claim.

## What changed, in reading order

### 1. `translations.js` — 13 keys, EN + KO, string → function

`tcpFaqA3` and `tcpTrustNote` (the two in the evidence) plus **eleven more** that carried the same re-typed
`$100K`: `tcpTokenDescription`, `tcpChainDescription`, `tcpTokenIntro`, `tcpChainIntro`, `tcpSubLine`,
`tcpDatasetTokenDescription`, `tcpDatasetChainDescription`, `tcpAnswer`, `tcpFaqA2`, `tcpTokenHubIntro`,
`tcpChainHubIntro`.

Each is now `(floorStr) => …`, and every call site passes `formatUsd(MIN_POOL_TVL)`. Two shapes of edit:

- **De-attribution.** *"clear **DeFi Garden's** $100K TVL floor"* → *"clear **this page's** `${floorStr}`
  TVL floor"*; hub intros' *"filtered through **our** $100K floor"* → *"a `${floorStr}` TVL floor"*.
- **Scoping.** The safety answer now reads: *"Pools listed on this page clear a `${floorStr}` minimum TVL
  and exclude anomalous (>1000% APY) rates — that is this page's listing bar, **not a safety guarantee**."*
  The anomalous-APY half was true and is kept verbatim.

Proof there is no second literal left:

```
$ grep -n '100K' translations.js generate-token-pages.js generate-chain-pages.js
… code comments only, plus `const MIN_POOL_TVL = 100000;` itself
```

### 2. `generate-token-pages.js` — forever numbers rest only on pools that actually yield

`yieldHeadlineFor()` blends `rec.pools` into the *"park $X and it could run a $20/mo Claude Pro
subscription, **forever**"* line — the SUBSCRIPTION archetype's trust-critical output. It now filters to
`isQualifyingPool(p) && formatApy(poolTotalApy(p)) !== '0.00%'` before blending, and returns `null` (no
claim rendered) when nothing survives. A forever number is a promise about capital; it may not be dragged
by a pool paying nothing.

The chain generator reuses this same function — there is no second copy to drift.

### 3. Both generators — no `0.00%` row under a "DeFi Yields" heading

`rankTopTokens` / `rankTopChains` now display the top `POOLS_PER_PAGE` **visibly non-zero** qualifying
pools, backfilling from further down the TVL ranking instead of shrinking the table.

**The load-bearing detail:** the 030/032/033 eligibility gate is left evaluated on the *pre-filter*
`shown = rec.pools.slice(0, POOLS_PER_PAGE)` slice, byte-for-byte as before. Filtering first and then
gating would have admitted tokens whose top-8-by-TVL are all zero but which have a yield at rank 9 — i.e.
it would have *minted new pages*. Keeping the gate where it is means the set of generated pages is
provably unchanged; only the rows inside them move.

### 4. Regenerated surface

`tokens/` (2,099 + hub + 27 A–Z), `chains/` (88 + hub), both KO mirrors, `sitemap-*.xml`, `llms*.txt`, OG
images — all via the npm/CI generator commands against a live 16,024-pool fetch. Nothing hand-edited.

## Measured before / after

| | before (`origin/main` pages) | after |
|---|---|---|
| pages claiming "DeFi Garden's trust filters" | **2,234** | **0** |
| `0.00%` rows in a yields table | **902** rows / **457** pages | **0 / 0** |
| pages making a "…subscription, forever" claim | 2,120 | 2,186 |
| token page set (same fixture, old code vs new) | 2,099 slugs | **2,099 — `diff` empty** |
| chain page set (same fixture, old code vs new) | 89 | **89 — `diff` empty** |

**The forever-claim count went UP, and that is worth arguing about.** Previously the claim vanished
whenever the median happened to land on a 0.00% pool — an accident, not a rail. With zero-yield pools out
of the blend, more pages produce an honest median, so more pages make the claim. Each surviving claim is
now derived only from rail-passing, actually-yielding pools, and sits on a page that now discloses its own
listing bar. The deeper question — whether a forever number should rest on $100K–$10M pools at all — is
the spec's **open question for the human** (below), not something a loop should decide.

## Deviation from the spec

The spec named `tcpFaqA3`/`tcpTrustNote`. The first build pass fixed exactly those and flagged the rest as
a judgment call; the eleven other keys carrying the same re-typed `$100K` (four of them attributing it to
*DeFi Garden*) were then swept in the same commit, because acceptance criterion 2 is *"no re-typed literal
anywhere in the templates"* and because fixing only the sentence in the evidence would have left the
100×-false claim on the same pages in a different paragraph.

## Verification

- `test_token_pages.js` **96 ✓** · `test_chain_pages.js` **87 ✓** · `test_hub_pages.js` **42 ✓**
  (main baseline: 88 / 79 / 42)
- `run-tests.js --lane=plain` **38/38**. Baseline on `origin/main` was **37/38** — the one red
  (`test_seo_cta_targets.js`, *"8 of 2205 pages have a dead primary CTA"*, live-data drift since #330's
  regen) was proven pre-existing in an isolated worktree at `origin/main` **before** this work, and is
  cleared by this regeneration.
- Browser lane **not run** (5-minute timebox; 8 known reds on `main`, ticketed as 176). Justified here
  rather than assumed: `grep` confirms the 13 changed `tcp*` keys have **no consumer outside** the two
  generators and their tests — no app runtime path reads them.
- Non-vacuity: a scratch harness copies both generators to `os.tmpdir()` with `MIN_POOL_TVL` mutated to
  `250000`, renders a token page, a chain page and both hubs, and asserts every floor mention reads
  `$250K` with zero `$100K` remaining. Proven RED against the pre-change source, GREEN after.
- `git diff origin/main -- app.js planner.js` → **empty**. `DEFAULT_MIN_TVL`, `APY_SANITY_LIMIT`, anomaly
  flags and the degen haircut are byte-identical. `MIN_POOL_TVL`'s value is unchanged.

## Risk tier: HIGH

Regenerates the whole SEO surface, changes user-facing copy in two languages, touches the numbers behind a
trust claim, diff far exceeds the 150-line LOW cap. **Not** on the NEVER list: no rail is weakened — the
change makes the published claim match the rails and constrains the forever number *more* tightly — and
nothing is de-indexed (page set provably identical on a fixed fixture).

## Open question for the human (does not block; the fix is correct either way)

Should `/tokens/` + `/chains/` exist at the `$100K` floor at all, or be rebuilt at the product's `$10M`?
At `$10M` the surface collapses from ~2,200 pages to roughly 450 — far less SEO surface, but every page
would agree with the app by construction. Note this now interacts with **PR #332 (item 177)**, which
lowers the *app's* `DEFAULT_MIN_TVL` to `$100K` and is waiting on you: if #332 merges, the app and these
pages converge on the same floor and this question largely dissolves.
