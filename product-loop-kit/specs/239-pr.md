# 239 — PR explainer: the flagship list led with rows that yield nothing

Risk tier: **HIGH** (ranking behaviour on the sacred analytics surface).

## Goal

The default browse — `/?chain=Popular`, headed **"Popular DeFi Yields"** — was ranking `0% — No supply
yield` rows into its top slots. In the human's own screenshot, 3 of the 9 visible rows were zero-yield
collateral pools (WSTETH/sparklend $2.4B, CBBTC/morpho-blue $2.4B, WEETH/aave-v3 $2.3B) sitting above
every yield-bearing pool. A yield-finder whose flagship list opens with no-yield rows reads *broken* to
the cautious saver we build for. UX audit F4.

## The intuition

Three things had to line up for this to be invisible until a human looked at the live site:

1. **The demotion existed — in the wrong branch.** Item 092 already taught the app that a
   no-supply-yield pool must never top the browse. It wired that into the `sortBy === 'tvl'` branch of
   the comparator. The **Risk-Adjusted** (`sortBy === 'sharpe'`) branch never got it.
2. **Risk-Adjusted degenerates into a plain TVL sort today.** Look at what that branch actually does:
   anomaly partition, then numeric `kpis.apySharpe` descending, nulls last, `b.tvlUsd - a.tvlUsd` as
   the tie-break. Pools accrue a Sharpe only after ≥8 history points; today essentially none have one.
   So **every** pool is null-Sharpe, every comparison falls through to the tie-break, and the toggle
   silently behaves as "TVL descending, with no yield partition."
3. **The biggest pools by TVL are exactly the ones that pay nothing.** Collateral assets — wstETH,
   cbBTC, weETH parked in lending markets — are enormous and yield zero to the supplier. A pure TVL
   sort doesn't just occasionally surface them; it puts them first, deterministically.

So the bug wasn't a ranking that was slightly off. It was one sort mode quietly reverting to the
pre-092 behaviour, on the one screen most likely to be a stranger's first impression.

## What changed, in reading order

### 1. `app.js` — one hunk, 12 lines, one comparator

Inside the default-view block (`!selectedToken && (selectedChain === 'All' || selectedChain ===
'Popular')`), in the `sortBy === 'sharpe'` branch:

```js
if (anomA !== anomB) return anomA - anomB;   // pre-existing anomaly rail — untouched
const noA = hasNoSupplyYield(a) ? 1 : 0;     // ← 239
const noB = hasNoSupplyYield(b) ? 1 : 0;     // ← 239
if (noA !== noB) return noA - noB;           // ← 239
const shA = …                                 // Sharpe comparison — untouched
```

Three details carry the whole change:

- **`hasNoSupplyYield` is reused, not re-typed.** It is the same function (`app.js:814`) that decides
  whether a card renders the "No supply yield" tag (`app.js:~2915`). The demoted row and the labelled
  row are the same row *by construction*; they cannot drift apart in a later edit.
- **Placement is after the anomaly rail, deliberately.** Anomalous pools (APY > `APY_SANITY_LIMIT`)
  must stay demoted below everything, including zero-yield rows. Putting the new partition first would
  have let a 5,000% anomaly outrank an honest 0% pool — a trust-rail weakening dressed up as a UX fix.
  Final order: **sane-yielding → zero-yield → anomalous**.
- **Nothing is filtered.** Every pool that rendered before still renders, still shows its honest
  `0.00%` and its "No supply yield" label. TVL browsing stays possible; it just stops being the
  headline. This is a reordering, not a removal — no floor, no limit, no flag touched.

### 2. `test_zero_yield_demote.js` — the gate

Extended rather than duplicated: 092's rendered Playwright gate already owned this class, so the new
phases live beside it (and the test registry stays unchanged). All four pre-existing assertions survive
untouched. Added:

- a fixture switch (`activeFixture`) so one page instance can be served three different populations;
- **Population A** — `/?chain=Popular`, 9 pools (the page size, so DOM order *is* the full ranking):
  6 yielding at $20M–$90M, 3 zero-yield at $2.2B–$2.4B. For each of the three sort toggles, asserts
  (a) every zero-yield row ranks after every yielding row, (b) the rendered symbol set still equals the
  fixture (nothing filtered), (c) exactly 3 honest "No supply yield" tags render;
- **Population B** — adds one anomalous pool (`apyBase: 5000`) and asserts the three-tier order, i.e.
  the trust rail still outranks the new partition;
- **Population C** — population A through `/?token=USDC`, asserting the highest-TVL zero-yield pool is
  *still first there*: the scope pin for the spec's "token/chain views byte-order-unchanged" criterion;
- constant-mirror checks: the test's `0.01` / `1000` literals are parsed back out of `app.js` at test
  time and asserted equal, so the mirror can't drift silently.

Partitions are derived from the fixture at test time (`apyBase+apyReward < 0.01`), never from a
hardcoded symbol list.

### 3. `app.compiled.js` / `app.compiled.min.js` — regenerated

`home.html` loads the minified compiled bundle, not raw `app.js` (item 052/053). `npm run compile &&
npm run minify`; `test_compiled_assets.js` + `test_minified_assets.js` confirm byte-parity with source.
This also matters for the evidence below: measuring red/green without recompiling would have been
measuring stale output.

## Evidence

1. **Red first.** Test written before the fix, run against unmodified `app.js` → 13/15, the two
   Risk-Adjusted assertions failing on real rendered order:
   `["WSTUSDC-A7","CBUSDC-A8","WEUSDC-A9","USDC-A6",…]`.
2. **Green.** Fix + recompile → 15/15.
3. **Neutered → red.** The single `if (noA !== noB)` line commented out, recompiled → 13/15 again,
   same two failures. So the gate is not vacuous, and it is *that line* it depends on.
4. **Restored → green,** byte-identically: `md5sum app.js` = `b5a93366b28ef0c744ce90251521ee26` before
   and after; `git diff --stat app.js` = 12 insertions, 0 deletions.

## Deviations from the spec

- The spec implied three code fixes (one per sort toggle). Only the `sharpe` branch needed code: `tvl`
  already had 092's partition, and `apy` satisfies the invariant structurally (the predicate is a
  threshold on the exact quantity that branch sorts by). All three toggles are still *asserted* in the
  rendered test — behaviour covered without duplicated comparators.
- The test file was extended rather than a new one created (reuse-before-inventing; registry unchanged).

## The class is NOT closed — and here is the number

Spec criterion 3 deliberately scopes this to the default view, so comparators #2 (`?chain=<name>`) and
#3 (`?token=<SYMBOL>`) still rank huge-TVL zero-yield pools first under Risk-Adjusted. That is **247
pools, $30.1B TVL, 28 chains** still exposed, on the SEO landing surfaces. Filed as **backlog 242**
with that number, and pinned by the Population C test so it stays visible instead of merely unsaid.

## Quiz

1. The Risk-Adjusted toggle is supposed to rank by rate-stability Sharpe. Why did it behave as a plain
   TVL sort — and why does that matter more today than it will in six months?
2. The new partition is placed *after* the anomaly check rather than before. What concrete
   misordering would the other placement produce, and which standing rule would that violate?
3. Why is reusing `hasNoSupplyYield` (rather than writing `apy < 0.01` inline) a correctness argument
   and not just a style preference?
4. The test asserts all three sort toggles, but only one branch of the comparator was edited. Why is
   asserting the other two *not* redundant padding?
5. Population C asserts that the token view still ranks a zero-yield pool first — pinning behaviour we
   consider wrong. What makes that the honest thing to ship rather than a quiet acceptance of the bug?
