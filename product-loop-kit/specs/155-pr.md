Short explainer per the LOW fast lane: tests + one `package.json` *test-script* clause + kit docs.
No product code, no dependency change, no render path, 82 insertions / 33 deletions across two files.

## Goal

`audit-app.js`'s `number-sanity` P0 check is the only automated detector for the item-122 bug class —
an absurd number reaching a real rendered page (`−900,719,925,474,097.9` as a "rate-stability score",
found by a human, by hand). Its single positive control had been failing since at least 2026-07-25,
and the file holding it was not in `npm test`. Every "0 findings" line in the heartbeat rested on a
detector nobody could show still worked.

## What was actually wrong

Not the detector. Item 144 shipped a rail on the exact field the control injected into:
`PoolDetail.js:161-164` computes `mean30dSane` and `:1290` gates the whole "30d Mean APY" card on it,
so an out-of-rail `apyMean30d` now renders **nothing**. The scanner had nothing to catch, and the
test's own root-cause comment ("gated only on `typeof … === 'number'` … with no sanity clamp") had
silently become a description of pre-144 code.

Four real Chromium probes settled which fields still reach rendered text:

| injected `9.007e14` | `number-sanity` findings |
|---|---|
| `apyMean30d` | **0** — 144's rail |
| `apyBase` (with `apyReward > 0`) | **7** |
| `apyReward` (with `apyBase > 0`) | **7** |
| `tvlUsd` | 0 — `formatUsd`'s K/M/B/T suffix is deliberately skipped as house style |

Detector alive; injection point rotted.

## The diff, in reading order

1. `test_audit_app.js` case 2 — injection re-pointed to `apyBase` (with `apyReward` forced `> 0`,
   because `PoolDetail.js:1210/1236` gate both APY cards on `apyBase > 0 && apyReward > 0`). Asserts
   a P0 `number-sanity` finding on `pool-detail` quoting the injected magnitude. The stale root-cause

2. `test_audit_app.js` case 3 (new) — the same magnitude in `apyMean30d` must produce **zero**
   `number-sanity` findings. The rail that broke the old test is now the thing the test protects: drop
   `mean30dSane` and this goes red instead of an absurd number reaching production.
3. `test_audit_app.js` plumbing — every `runAudit` call routed to an `os.tmpdir()` `outPath`, and the
   trailing "restore a clean signals file" run deleted. Previously each run overwrote the committed
   `product-loop-kit/signals/audit-findings.json`, and that restore run covered only 3 surfaces — so
   wiring the file into `npm test` would have replaced the heartbeat's 16-surface artifact with a
   3-surface one on every test run.
4. `package.json` — `node test_audit_app.js` inserted into the `test` chain after
   `test_audit_runner.js`. `dependencies`/`devDependencies` byte-identical.

`audit-app.js` is deliberately untouched: changing a detector so its own control passes would be
backwards.

## Proof it isn't vacuous

Both kills run by the builder, both restored byte-clean:

- Neuter `scanNumbers`' absurd-magnitude branch → **case 2 goes red** (`got: []`).
- Remove the `mean30dSane &&` gate at `PoolDetail.js:1290` → **case 3 goes red**, quoting
  `astronomical value "900,719,925,474,097.9"`.

Kill B surfaced something worth keeping: editing `PoolDetail.js` alone changed nothing, because
`home.html` loads `PoolDetail.compiled.min.js`, not the raw source (backlog 052/053). The mutation only
reached the render after `node compile-app.js && node minify-assets.js`. Any future rendered proof that
skips the rebuild is measuring the old bundle — and a mutation that "fails to kill" for that reason is
indistinguishable from a vacuous test. Written into `playbooks/pre-existing-red-triage.md`.
