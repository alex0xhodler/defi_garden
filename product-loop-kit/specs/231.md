# Spec 231: Make the `occlusion` lens detect a PERMANENT defect reliably (3/20 → ≥19/20)

## Evidence

## Hypothesis
We believe replacing `checkOcclusion`'s FIXED 150ms settle wait with a condition-based wait (readiness of the surface's content root — e.g. the alternatives-grid populated / layout stable across two consecutive rAF-spaced measurements) will raise detection of a known-permanent occlusion from 3/20 to ≥19/20, because the two rival explanations are already ruled out by 221 (CSS-load race: 15/15 probe runs had `style.min.css` applied; content variance: `getEmptyStateAlternatives` draws from the in-memory snapshot, deterministic), leaving the render race with the fixed 150ms wait as the leading mechanism. Confidence: supported (characterisation measured twice, rivals ruled out) — but the MECHANISM is still a hypothesis; if the condition-based wait does NOT move the detection rate, that falsifies it and the item returns to characterisation, not to a bigger timeout.
- Instance of: fixed-duration settle waits racing async renders in `audit-app.js` — the population is EVERY lens/check that sleeps a constant then measures (grep `waitForTimeout` / hardcoded ms constants in audit-app.js and treat each as a member).
- Class closed by this item: no — this item fixes the `occlusion` lens's wait; other fixed-wait sites in the scanner remain, count them in the notes and leave the number here.

## Change
Smallest version: make the settle wait in `checkOcclusion` condition-based (bounded by a generous ceiling so a truly-dead page can't hang the scanner), leaving predicate, geometry math, severity mapping, and quarantine handling byte-untouched. OUT of scope: any change to what counts as occluded, any quarantine-list edit, any new lens, product code of any kind.
