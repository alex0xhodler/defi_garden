# Spec 057: Compress OG images (hero + generated per-page cards)

## Evidence
- BACKLOG 057: "Perf: optimize og-image.png (280K) + generated OG PNGs (051) — compress/resize/modern format." Score 5.5, LOW risk, no spec existed — written here from documented evidence per build.md's no-spec fallback.
- Measured in-repo, 2026-07-12: `og-image.png` (hero share/SERP card, referenced by every page as `og:image`/`twitter:image` fallback) is 286,318 bytes. The generated per-token/chain cards from backlog 051 (`og/tokens/*.png`, `og/chains/*.png`, 2,113 files) total ~93MB, averaging ~44KB each — this dwarfs the hero image as the real repo-bloat/byte-cost driver.
- `NORTH_STAR.md` commands: no lint pipeline, `npm test` chain, static site (no build step). Neither `@napi-rs/canvas` (051's renderer, already a dependency) nor Chromium (already a devDependency via `playwright`, pre-installed in CI/this environment) needs a new package to switch encoders — JPEG output is natively supported by both.
- Verified empirically this session:
  - `@napi-rs/canvas`'s PNG/JPEG encoders ignore `compressionLevel`/`quality` config (Skia backend uses its own fixed settings — confirmed identical byte counts across quality 0.01–0.9). Its JPEG output is still ~22% smaller than its PNG output for the same card (44,609B PNG → 34,784B JPEG) — a real, if modest, per-card win with zero new dependency.
  - Playwright/Chromium's `page.screenshot({type:'jpeg', quality})` genuinely respects quality (confirmed: q90=143KB, q85=120KB, q80=106KB, q70=89KB for the hero card, vs 286KB currently committed as PNG). Visually inspected the q85 render — neumorphic shadows and text stay crisp, no visible banding/artifacts. q85 gives ~58% size reduction with no visible quality loss.

## Hypothesis
We believe switching both OG image paths (the shared hero card + 051's per-page generated cards) from PNG to JPEG will cut social/SERP share payload weight substantially (~58% on the hero card, ~22% on the 2,113 generated cards) with no visible quality loss, because these are near-photographic gradient+text cards where JPEG's DCT compression beats PNG's deflate, and because JPEG is displayed identically to PNG by every social/search og:image consumer. No funnel metric isolates this (perf/asset change, same disclosure pattern as 052–056) — the proxy is total repo/page byte weight, measured directly here.

## Change
1. `og-image.build.mjs`: render via `page.screenshot({type: 'jpeg', quality: 85, clip: {...}})` and write `og-image.jpg` (drop the PNG output — Chromium's JPEG quality knob is the one real lever available without a new dependency).
2. Commit the regenerated `og-image.jpg` (built in-sandbox from the existing `og-image.source.html`, no network needed — confirmed this session).
3. `generate-og-images.js` (051's per-page card renderer): switch `canvas.toBuffer('image/png')` → `canvas.toBuffer('image/jpeg')`; `ogRelPath()` returns `og/<kind>/<slug>.jpg`; `FALLBACK_REL_PATH` becomes `'og-image.jpg'`; the stale-file sweep checks `.jpg` instead of `.png`.
4. `generate-token-pages.js` / `generate-chain-pages.js`: `OG_FALLBACK_REL_PATH` (defined once in generate-token-pages.js, imported by generate-chain-pages.js) → `'og-image.jpg'`; the two hardcoded `${SITE_URL}/og-image.png` no-data/hub-page literals → `.jpg`.
5. `generate-stories.js`, `home.html`, `plan.html`: update the hand-maintained/generator-template `og:image`/`twitter:image`/JSON-LD `logo` literals from `og-image.png` → `og-image.jpg`.
6. `test_og_images.js`: update every `.png` assertion for og-image/og-card paths to `.jpg`.

### Explicitly NOT done (scope guard)
- The 2,113 already-committed `og/tokens/*.png` / `og/chains/*.png` files are NOT regenerated here — `generate-token-pages.js`/`generate-chain-pages.js` need live DefiLlama pool data (network-blocked in this sandbox, same precedent as 040/044/045/048/051-056). They regenerate as real `.jpg` files on the next `sitemap-update.yml` CI run, same pattern as every prior generated-surface change in this backlog.
- The legacy `og-image.png` (286KB) file is **kept, not deleted**. Every already-generated static page this loop does not touch (`tokens/*.html`, `chains/*.html`, `stories/*.html`, `ko/**`) still references it by filename until its own next CI regen; deleting it now would 404 their `og:image` in the interim. A follow-up item can remove it once a full regen cycle confirms nothing still points at it.
- No resizing (1200×630 is the OG/Twitter-recommended minimum, already at spec) and no further format (WebP/AVIF) — social platforms' og:image support for those is inconsistent in 2026; JPEG is universally safe and is the only lever that's both real and dependency-free here.

## Acceptance criteria
- [ ] `og-image.jpg` exists, is a valid 1200×630 JPEG, and is smaller than the current `og-image.png` (286,318 bytes) by a wide margin (target: ≤150KB).
- [ ] `home.html`, `plan.html` reference `og-image.jpg` for `og:image`/`twitter:image` (and the JSON-LD `logo` in home.html); `og-image.png` still exists in the repo (not deleted).
- [ ] `generate-og-images.js`'s `renderOgCard` emits a JPEG buffer; `ogRelPath('tokens'|'chains', slug)` returns a `.jpg` path; `FALLBACK_REL_PATH === 'og-image.jpg'`; a fresh render of a fixture record is smaller than the equivalent PNG render was before this change.
- [ ] `generate-token-pages.js`'s `OG_FALLBACK_REL_PATH === 'og-image.jpg'`; no remaining hardcoded `og-image.png` literal in generate-token-pages.js, generate-chain-pages.js, or generate-stories.js.
- [ ] `npm test` passes (test_og_images.js updated to `.jpg` expectations, no regressions in test_token_pages.js / test_chain_pages.js / test_stories.js / test_sitemap_xml.js).
- [ ] No trust-rail, canonical, or ranking change; the APY/pool-count data feeding the per-page card (051's `Math.max(...rec.pools.map(poolTotalApy))`) is untouched — this is a pure encoder/extension change.

## Measurement
Metric: total OG-image byte weight (proxy for social/SERP share payload + repo size). Baseline: hero 286,318B; generated-card average ~44KB × 2,113 ≈ 93MB (measured this session). Target: hero ≤150KB (~58%+ reduction, achieved); generated cards ~22% smaller once the next CI regen replaces the PNG set with JPEGs (not independently re-measurable here without network). No Mixpanel funnel step — proxy is direct byte measurement + Core Web Vitals/PageSpeed on next live measurement, same disclosure pattern as 052-056.

## Risk tier (builder's guess — verifier assigns independently)

The 2,113-file regeneration is deferred to CI (same precedent as every other generated-surface item), so this PR's own diff stays small even though its downstream effect is large.
