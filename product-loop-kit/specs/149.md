# Spec 149: `audit-app.js` must not fail silently in a fresh clone

## Evidence
From the 2026-07-26 heartbeat, first-hand:

```
$ node audit-app.js
Error: Cannot find module 'playwright'
Require stack:
- /home/user/defi_garden/audit-app.js
    at Function._resolveFilename (node:internal/modules/cjs/loader:1383:15)
    ...
```

`playwright` **is** correctly declared (`package.json` → `devDependencies: { "playwright": "^1.61.1" }`), but a fresh clone has no `node_modules`, and the cloud-routine environment this loop runs in starts from a fresh clone every session. Playwright 1.56.1 is installed globally at `/opt/node22/lib/node_modules`; re-running as `NODE_PATH=/opt/node22/lib/node_modules node audit-app.js` succeeded and produced the real result (10 surfaces covered, 0 findings).

Why this matters more than a missing-dependency papercut: `audit-app.js` (item 142) mechanizes the **primary job of every pre-traffic heartbeat** (NORTH_STAR standing decision 2026-07-23 + `heartbeat.md` §2b). When it crashes it writes **no** `signals/audit-findings.json` at all — so a stale findings file from a previous run stays on disk, and the crash exit is easy to mis-read as "the audit ran and found nothing." A heartbeat that records "audit clean" off a crashed run has silently skipped its main responsibility for that day.

## Hypothesis
We believe making the failure loud and self-healing will prevent a future heartbeat from recording a false "audit clean" — because the only thing standing between a crash and a wrong report today is the operator noticing a stack trace. Confidence: **supported** (the failure mode was observed live this tick; the mis-read is one careless step away).

## Change
Smallest version, in `audit-app.js` only:

1. Resolve `playwright` with a global fallback instead of a bare `require`: try `require('playwright')`, and on `MODULE_NOT_FOUND` retry via the global root (`/opt/node22/lib/node_modules/playwright`, or the path from `execSync('npm root -g')`). Log which one was used.
2. If neither resolves, exit non-zero **after** writing `signals/audit-findings.json` with an explicit failure shape — e.g. `{ "generatedAt": "...", "status": "DID_NOT_RUN", "reason": "playwright unresolvable", "surfacesCovered": [], "findings": [] }` — so the artifact can never be confused with a clean run.
3. Write that same `status: "OK"` field on successful runs, so the heartbeat has one field to check rather than inferring health from an empty array.

**Explicitly OUT of scope:**
- Adding, removing, or bumping any dependency in `package.json` (NORTH_STAR risk policy: dependency changes are HIGH and this item does not need one — the dep is already declared).
- Running `npm install` from inside the script, or any network access at audit time.
- Any change to the audit's check logic, surface rotation, or findings format beyond the added `status` field.
- Any product file. `audit-app.js` is loop tooling and reads the product read-only; that property must hold.

## Acceptance criteria
- [ ] `node audit-app.js` completes successfully in a checkout with **no** `node_modules` present (simulate: `mv node_modules /tmp/nm-stash`, run, restore). Its output JSON carries `"status": "OK"` and a non-empty `surfacesCovered`.
- [ ] With playwright unresolvable from **both** local and global roots (simulate by pointing the global-root lookup at an empty dir), the script exits **non-zero** and `signals/audit-findings.json` contains `"status": "DID_NOT_RUN"` and `"surfacesCovered": []`.
- [ ] A successful run still exits non-zero when any P0/P1 finding exists (the item-142 contract is unchanged) — assert this is not regressed.
- [ ] The script writes no file outside `product-loop-kit/signals/` and modifies no product file — verify with `git status --porcelain` after a run (only the findings file may appear).
- [ ] Tests: a small `test_audit_runner.js` covering the two paths above (resolves-globally, and fails-loudly). Must be non-vacuous — show it red against the current `audit-app.js` before the change.
- [ ] Full `npm test` chain green, or every failure proven pre-existing against a stashed baseline.
- [ ] Instrumentation: **none.** This is loop tooling; it emits no product events and touches no user-facing surface.

## Measurement
Metric: the next heartbeat runs `node audit-app.js` with no special environment and gets either a real result or an unmissable failure. Window: next 3 heartbeat ticks (to **2026-07-29**).
Decision rule: keep if the next tick's audit runs unassisted; revert-candidate if the fallback resolves a playwright version that behaves differently enough to change findings (compare `surfacesCovered` against this tick's 10).
No traffic metric applies — this is loop infrastructure, closed on functional verification per the 020/048 precedent.

## Risk tier (builder's guess — verifier assigns independently)
**LOW.** Single non-product file (`audit-app.js`) plus one new test; no dependency change, no user-facing surface, no trust rail, no SEO surface, no router. Diff should land well under the 150-line LOW cap. The one thing that would push it HIGH is touching `package.json` — which this spec forbids.

## Territory notes

- Do not "fix" this by having the heartbeat run `npm install` first: that is a several-minute network install on every tick, in an environment where external HTTPS is partially blocked (standing decision 2026-07-12), to obtain a package that is already present globally.
- Global playwright is 1.56.1 while `package.json` asks for `^1.61.1`. The fallback is therefore a *degraded* path, not an equivalent one — log the resolved version in the findings JSON so a future tick can tell which engine produced a finding.
