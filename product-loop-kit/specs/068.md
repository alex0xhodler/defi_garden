# Spec 068: Planner hero-copy CRO test (SPLITSTREAM audit — outcome headline, mechanism sub, live proof anchor)

## Evidence
- External CRO audit (SPLITSTREAM, 2026-07-13) flagged the planner hero as feature-named, not outcome-named. The hero is the top of the `waitlist_submitted` funnel — every entrant reads it before any goal is picked, so a copy lift here compounds through the whole funnel.
- Current strings (translations.js): `planner.title` = "Garden Planner" (feature name), `planner.tagline` = "Plant a goal. Watch it grow." (metaphor, no mechanism), `planner.splashHook` = "Park money once — its yield pays the bill forever, and you keep every dollar." (already on-message but no number).
- Render sites: title/tagline in the header (`t('title')`/`t('tagline')`); `splashHook` at planner.js:3981 (`gp-splash-hook`). The live blended APY is already computed and rendered elsewhere (`blendedBadge`, planner.js:2117/2257 via `formatApy(apy)`), so a live-derived proof number in the hook is feasible with the existing calc path — no new number source.

## Hypothesis
We believe naming the OUTCOME in the headline, the MECHANISM in the sub-headline, and anchoring the hook with a live-derived proof number will lift `waitlist_submitted` per session, because the ICP (cautious retail saver) thinks in life outcomes and trusts concrete live numbers over metaphor. Audit-estimated lift: headline +2–4%, sub-headline +1–3%, hook proof-anchor +1–2% (unvalidated external estimate; ship measurable, decide on our own funnel). Confidence: guess (no A/B infra yet — this is a pre/post copy swap, not a split test).

## Change (three SPLITSTREAM variants)
- **V01 — outcome headline.** `planner.title`: "Garden Planner" → an outcome frame ("Pay Your Bills With Yield, Forever" / audit wording, refined to the ICP + copy ban-list). Keep it a header string; do NOT break the header-icon route into the analytics app.
- **V02 — mechanism sub-headline.** `planner.tagline`: "Plant a goal. Watch it grow." → mechanism frame ("Tell us what you need. Live DeFi yield covers it automatically." / refined).
- **V03 — quantified proof anchor.** `planner.splashHook`: swap the static line for one that carries a **live-derived** rate and an honest timeframe. Audit's literal "8-15% APY … within months" is a STARTING POINT ONLY — see guardrail; the shipped string must render the real blended rate and a real time-to-cover, not a hardcoded range.
- EN + KO both, in the same commit (hard rule). Copy ban-list for in-reach framing still applies ("save up", "afford", "budget").
- OUT of scope: any layout/visual change; the analytics-app hero; new A/B tooling.

## Trust-rail guardrail (non-negotiable — the reason this is HIGH)
- V03's proof number MUST be the live blended APY already computed in planner.js (through `APY_SANITY_LIMIT=1000%` / `DEFAULT_MIN_TVL=$10M` / anomaly exclusion / degen ⅓ haircut) and formatted via `formatApy`. A hardcoded "8-15%" string = automatic FAIL.
- Any timeframe ("within months") must reflect the app's real time-to-cover math for a stated subscription, or be dropped. No fabricated urgency, no fake availability of the card.
- If the live rate is unavailable at render time, the hook must degrade to an honest number-free line (never a placeholder or stale hardcoded figure).
