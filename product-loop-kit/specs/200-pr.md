# 200 — explainer (HIGH tier): completing the lens matrix on the landing / planner / bloom funnel

## Goal in one line

The audit renders the pool-detail page at 360px, in dark mode and in Korean. It renders the **rest of the
funnel** — the landing page, the planner, the bloom/checkout screen — at 1280px, light, English, and
nowhere else. This item closes that hole with five surface entries and the two checks the landing driver
was missing.

## The intuition

There are two ways a checker can be blind, and this item is about the second one.

The obvious way is **not looking at a thing**. That's what items 183 / 191 / 192 / 196 / 197 fixed — which
members get audited, how many per tick, whether the picker remembers, whether the population is even fully
enumerated.

The subtle way is **looking at a thing under only one set of conditions**. A page is not one artifact. It's
a different artifact at 360px than at 1280px, a different artifact in dark mode, a different artifact in
Korean — different enough that item **136** was a P0: the primary "Garden this pool" CTA and the TOTAL APY
value were *clipped invisible* at 360px, light and dark both, on a page that audited perfectly clean at
1280px. Item 199 named this the **LENS axis** and fixed it for the pool-detail rotation.

Here's the trap 199 left behind, and it's the interesting part of this item: **fixing the lens axis on one
surface makes the whole checker read as lens-covered.** You look at `audit-app.js`, you see
`pool-detail-360`, `pool-detail-dark`, `pool-detail-ko`, plus 199's whole rotating lens apparatus, and you
conclude the file takes rendering conditions seriously. It does — on one surface kind out of five.

The measurement that settles it is one grep:

```
$ grep -n "dark: true" audit-app.js
2920:    dark: { width: 1280, dark: true },     <- 199's LENS_SHAPE, pool-detail rotation only
3777:    { name: 'pool-detail-dark', … },       <- the hardcoded anchor pool
```

**Two lines in 4,257.** Both pool-detail. Every surface between a visitor arriving and `plan_created` —
landing, planner, bloom — had never been rendered in dark mode by any signal, cheap or rendered. And the
landing page, bare `/`, the product's *default face* since the 2026-07-15 pivot, had exactly one audited
entry in the entire file: 1280px, light, English. No 360px. No dark. No Korean.

That this went unnoticed for 13 items is itself the lesson, and it's the same shape item 197 hit one day
earlier: *"the three `-ko` surfaces that do appear are app routes via `?lang=ko` — which is exactly why the
gap read as covered."* A partially-filled matrix reads as a filled one when you spot-check it instead of
building it.

## Why these surfaces, and why now

- **CLAUDE.md, hard rule, verbatim:** *"Must be flawless at 360/768/1280px and in dark mode."* The audit
  was proving that for one hardcoded pool.
- **NORTH_STAR.md's 2026-07-23 pre-traffic mandate** names the bug classes the human keeps finding by hand:
  *"…format/i18n bugs, dead CTAs, **responsive/dark**."*
- **Precedent 136** — the P0 above — was reachable *only* because pool-detail had a 360px lens.
- **Precedent 179** — *"the static `.seo-hub-links` crawler footer is occluded and unclickable on bare
  `/`"* — is this exact class, on this exact surface, and it was found **by hand**. The audit never
  originated it and could not have.
- This item was **promoted** by the build loop: `BACKLOG.md` had no READY item at pickup (197 and 198, the
  two rows the 2026-08-01 report filed, both shipped overnight). Per build.md's no-READY rule the evidence
  came from the repo — specifically **spec 199's own "Out of scope" section**, which names this item:
  *"lens coverage for the static estate or **the planner/bloom surfaces** — same idea, separate population,
  separate item if the numbers justify it."*

## What changed, in reading order

### 1. `audit-app.js:3362, 3370-3378` — the landing driver gains the two checks it lacked

Read this leg **first**, because without it the second leg is decorative.

The `kind === 'landing'` driver did a readiness wait, `auditText`, a `.landing-search-submit`
presence/visibility check, and a console-error sink. It had **no `checkResponsive()` call and no Hangul
check** — unlike the `planner` driver (`:3420-3421`) and the `bloom` driver (`:3468-3475`), which have
both.

That absence was *correct* in item 162, which built the driver: a surface that only ever renders at 1280px
in English has no use for a 360px clip check or a "did any Korean render?" check. It stops being correct
the moment you add those lenses. Ship the surfaces alone and you get two extra renders that assert exactly
what the 1280px/EN render already asserted — coverage on paper, nothing on the ground. That is precisely
the failure mode item **198** was filed for (a gate implementing half its own predicate) and item **199**
before it (checks pointed at a sample of one). So both legs ship together or neither does.

```js
-      await auditText(page, s, findings);
+      const text = await auditText(page, s, findings);
       …
+      // i18n — backlog 200, same "KO surface rendered no Hangul text" check
+      // the planner/bloom drivers already run, scoped to the -ko surface only.
+      if (s.ko) {
+        const hasHangul = /[가-힣]/.test(text);
+        if (!hasHangul) findings.push(finding(s.name, s.vpLabel, 'i18n', 'P2', 'KO surface rendered no Hangul text'));
+      }
+
+      // responsive — backlog 200, 360 surface only, against the primary control.
+      if (s.width <= 360) await checkResponsive(page, s, findings, '.landing-search-submit');
```

Three things worth noticing:

- `auditText`'s **return value was being discarded**. The planner and bloom drivers already capture it as
  `const text`; the landing driver didn't need it until now. One-word change, easy to miss in review.
- The checks are copied in **shape** from the sibling drivers rather than re-invented — same severity
  (`P2`), same detail string, same position in the driver (after the CTA block, before the `errors.length`
  push). A checker whose two implementations of "is there Korean on this page?" drift apart is a bug
  factory.
- `checkResponsive` is passed `.landing-search-submit` — the landing page's own primary control, the same
  selector the driver's existing dead-CTA check uses. The helper is shared and unmodified; only the call
  site is new.

### 2. `audit-app.js:3804-3822` — five surfaces, strictly appended

```js
    { name: 'landing-360',     url: '/',          kind: 'landing', width: 360  },
    { name: 'landing-dark',    url: '/',          kind: 'landing', width: 1280, dark: true },
    { name: 'landing-ko',      url: '/?lang=ko',  kind: 'landing', width: 1280, ko: true },
    { name: 'planner-dark',    url: '/plan.html', kind: 'planner', width: 1280, dark: true },
    { name: 'plan-bloom-dark', url: '/plan.html?goal=retirement&pace=stable&monthly=500&years=10',
                                                  kind: 'bloom',   width: 1280, dark: true },
```

The matrix, before and after:

| surface | 1280/light/EN | 360px | dark | ko |
|---|---|---|---|---|
| `landing` | ✅ | ✗ → **✅** | ✗ → **✅** | ✗ → **✅** |
| `planner` | ✅ | ✅ | ✗ → **✅** | ✅ |
| `bloom` | ✅ ×3 archetypes | ✅ growth | ✗ → **✅** | ✅ growth |

Four decisions inside those five lines:

- **Appended after `plan-bloom-ko`, the end of the list.** `surfacesCovered` is a positional artifact that
  gets committed to `signals/audit-findings.json` and read across ticks; 167 / 183 / 192 all carry the same
  standing constraint, stated in the file's own comments at `:3779` and `:3786`. Inserting the landing
  lenses next to `landing` would have read better and shifted every downstream entry. Appending is correct
  and slightly ugly; correct wins.
- **`plan-bloom-dark` reuses `plan-bloom-growth`'s URL byte-for-byte** rather than retyping it — 164's own
  "reused verbatim from `test_plan_checkout_cta.js`" precedent. Same archetype, new lens; two archetype
  URLs that drift apart by a typo would silently audit two different plans.
- **`landing-ko` is `/?lang=ko`, and that really is landing mode** — verified against the router, not
  assumed. `home.html:76-78`: `ANALYTICS_PARAMS = ['token','chain','pool','poolTypes','protocols','minTvl','minApy','app']`,
  `PLANNER_PARAMS = ['goal','monthly','years','pace','preset','fresh','capital','fm','dl']`. `lang` is in
  neither and the path isn't `/plan.html`, so `__APP_MODE === 'landing'`. Had `lang` been an analytics
  param, this surface would have quietly audited the analytics grid while claiming to audit the landing
  page — a false green, the worst possible outcome for a coverage item.
- **No new budget knob, deliberately, against the file's other convention.** Every other count in this file
  has one (`AUDIT_POOL_SAMPLE`, `AUDIT_STATIC_SAMPLE`, `AUDIT_POOL_LENS_SAMPLE`), and a reviewer expecting
  symmetry will look for `AUDIT_FUNNEL_LENS_SAMPLE`. Those knobs govern **sampled populations**, where "how
  many per tick" is a genuine policy question traded against wall-clock. Five fixed surfaces are not a
  population — they're siblings of `planner-360` and `plan-bloom-ko`, which have no knob either. Adding a
  sixth knob would have been the scope creep, not the omission. `opts.only` / `--only` already gives
  per-surface control and the existing time-budget guard already sheds work on a slow run. The reasoning is
  written into the comment block above the entries so the next reader doesn't re-litigate it.

### 3. `test_audit_funnel_lens.js` (new, 11 tests) + `package.json`

Two-layer shape, copied from `test_audit_planner_surface.js`: source-level assertions that **cannot** be
skipped for an environment gap, plus a real-Chromium `runAudit()` leg whose assertions sit **outside** the
environment-gap catch — per item 160's post-verifier lesson, *"a check that cannot go red is not a check."*
Registered in `test:serial` immediately after `test_audit_pool_lens.js`, its sibling.

The load-bearing assertion is criterion 5(b), and it's worth reading closely:

> *property: every funnel kind (landing/planner/bloom) has ≥1 dark surface, and landing has a 360px, a dark
> AND a ko surface*

It asserts against the **parsed surface array**, as a property of the matrix — not as a list of five
hardcoded names. That distinction is the whole point. A name list is green the day it's written and green
forever after, including the day someone deletes `landing-dark`. A property re-fails the moment any future
edit reopens the hole, on a surface that doesn't exist yet.

### 4. `product-loop-kit/playbooks/detector-signal-coverage.md` — the compound step

The playbook's fourth axis (LENS) gains a subsection: **ask the lens question once per surface KIND, not
once per checker**, build the matrix rather than spot-checking it, assert it as a property, and watch for
the paired "a lens that cannot see" trap. Additive docs, same commit, per build.md step 6.

## Deviations from the spec

**None.** Every shape the spec fixed — surface names, URLs, kinds, widths, flags, append position, driver
call-site position, the no-knob decision, the `test:serial` insertion point, the two-layer test shape — was
implemented as written. No product defect surfaced by the new lenses was fixed here, per the spec's own
"Out of scope" rule (one item, one scope).

## What it cost, and the honest null result

- Two paired end-to-end runs: branch **199.1s**, `origin/main` baseline **198.3s** — five extra renders,
  ~0.8s, against a 300s cap. A programmatic array diff proves the branch's `surfacesCovered` is the
  baseline's **plus exactly the five new names**, same order, nothing renamed or moved.
- **Zero new findings** on the five new surfaces. Both runs report the same single pre-existing
  pool-prescan aggregate (`201e5f6e`, `mean30d-rail-breach`, auto-downgraded by 171), unrelated to the
  funnel.

That null result is stated plainly rather than dressed up. It is **not** evidence the funnel is
defect-free — it's five surfaces on a largely-clean codebase, the same reason 199 found nothing in its
first six draws. The deliverable of this item is that a 136-shaped clip on the landing search CTA, or a
dark-mode occlusion anywhere in `landing → planner → bloom`, is now **reachable at all**. It wasn't
yesterday.

The claim that the two new checks can actually fire is not left to assertion: both were mutated to force a
false negative and shown producing real findings — `responsive` on `landing-360`, `i18n` on `landing-ko` —
then restored byte-exact.

**UNRUN, not implied green:** `npm run test:browser` (the full ~40-file lane, up to 600s/file) does not fit
the 5-minute foreground timebox alongside two ~200s end-to-end runs and two real-Chromium probes. Every
audit-family file named in the build brief was run individually: `test_audit_funnel_lens.js` 11/11,
`test_audit_app.js` 3/3, `test_audit_pool_lens.js` 7/7, `test_audit_planner_surface.js` 8/8, plus
`npm run test:fast` 39/39.
