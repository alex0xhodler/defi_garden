# 160 — PR explainer: the product audit learns to read the text surfaces

Written at HIGH-tier depth deliberately. The spec's own rule ("escalate to HIGH
on size alone if `audit-app.js` grows past the 150-line cap") trips here: the
hand-written diff is **+172 / −3** in that file. Nothing else about the change
is HIGH-shaped — no product surface, no trust rail, no dependency — but the rule
is the rule, so this is the full walkthrough plus the quiz.

## The goal

Two P0/P1-class defects on public surfaces in two consecutive days were both
found **by hand**, and both were structurally invisible to the automated scanner:

- **2026-07-26, item 148** — junk token pages minted from Pendle expiry-date
  fragments. `audit-app.js` scored "10 surfaces, 0 findings" the same day.
  (Structurally fixed since, by 154/157: the scanner can now see generated HTML.)
- **2026-07-27, item 159** — `llms.txt` publishing **353,114.2% APY** live on
  prod with no `APY_SANITY_LIMIT` applied. That tick's scanner run was clean.

The scanner was clean both times because it only ever drove *rendered HTML*.
`llms.txt`, `llms-full.txt`, `sitemap-*.xml` and `og/*.png` are equally
committed, equally served, equally generator-produced — and nothing automated
read a byte of them. This item closes the first of those families.

## The intuition

`prescanStaticPages()` (item 157) already proved the cheap shape: pure `fs` +
regex over 2,197 HTML leaf pages in ~480 ms, emitting **one aggregate finding
per signal** rather than one per file. Text surfaces are the same job at 1/1000th
the scale — there are two files. So this is not a new mechanism; it is the
existing mechanism pointed at a family of surfaces it never covered.

## What changed, in reading order

### 1. `audit-app.js` header — one new env override

`AUDIT_TEXT_SURFACES=0` disables the pass, documented alongside
`AUDIT_STATIC_PRESCAN` and friends. Same convention, same block.

### 2. The rail import (top of file)

```js
const { APY_SANITY_LIMIT } = require('./src/poller-core.js');
```

**This is the one judgment call worth arguing about.** `generate-llms.js` also
exports `APY_SANITY_LIMIT`, and it is the nearest neighbour — but it is *the
generator this pass audits*. An auditor that reads its threshold from the thing
it audits is self-fulfilling: weaken the generator's copy and the audit follows
it down in silence. `src/poller-core.js:18` is an independent mirror of the same
`app.js` constant, dependency-free, already test-covered. The number `1000` is
not written anywhere in the new code.

### 3. Constants (`~line 154`)

`TEXT_SURFACE_FILES` (the two files) and `TEXT_SURFACE_SIGNALS` (signal →
severity), the latter playing exactly the role `PRESCAN_SIGNALS` plays for the
static prescan: one source of truth shared by the suspect records and the
aggregate findings. Four regexes and a `parseMoney(numStr, suffix)` helper
(K/M/B/T) shared by both TVL readings — the floor claim and the listed figures
are parsed by the same code, so they cannot disagree about what "$10M" means.

### 4. `prescanTextSurfaces(opts)` — the pass itself

Never throws; a missing/unreadable file gets a stderr note and does **not** count
toward `scanned` (exact parallel of the static prescan). Four detectors per file:

| signal | sev | what it catches |
|---|---|---|
| `apy-rail-breach` | P0 | any `<figure>% APY` **strictly** above the rail — 159's detector |
| `tvl-floor-claim` | P1 | stated `TVL ≥ $X` disagrees with the smallest figure listed **in that section** |
| `broken-number-literal` | P0 | `NaN`/`Infinity`/`undefined`/`null` where a number belongs — reuses the existing constant, not a copy |
| `empty-surface` | P1 | zero pool-shaped lines — the soft-404 equivalent |

Two details that are load-bearing rather than incidental:

- **`apy-rail-breach` emits one suspect per FILE**, quoting the highest figure
  plus up to two others. A systemic breach must not flood the findings list —
  that is the 157 aggregate discipline restated at the file level.
- **`tvl-floor-claim` is scoped to the floor's own markdown section** (floor
  line → next `## ` heading → EOF). File-wide, it false-positives on the first
  run: `## Top Chains by TVL` lists *aggregate chain* TVLs, which are not claims
  about the per-pool floor stated further down the file. A test pins this.

Suspects are sorted P0-first then by file, same comparator shape as the static
prescan, so output is order-stable regardless of fs ordering.

### 5. `runAudit()` wiring

Computed **before** the browser launches (it is pure `fs`, so it costs nothing
and cannot be lost to a render failure). Aggregate findings are shaped exactly
like `static-prescan:<signal>` — `text-surface:<signal>` on a `text-surfaces`
surface, ≤10 examples. The result object gains a `textSurfaces:
{ scanned, suspectCount, bySignal }` block beside `prescan`, with a constant
empty shape when the pass didn't run, so consumers never null-check.

`'text-surfaces'` is pushed into `surfacesCovered` — the spec asks for a named
entry, and unlike `static-prescan` this one gets it.

### 6. Two gates that exist because of the existing test suite

- The `opts.only` allowlist is applied to these findings, matched on
  `f.surface`, exactly as it already is for prescan findings. Without it,
  `test_audit_app.js`'s clean-run case (scoped to app surfaces, asserts ZERO
  P0/P1) would pick them up through the back door.
- The pass is **off under `opts.staticOnly`**. `test_audit_prescan.js:221-223`
  asserts a default `staticOnly` run covers `<= 7` surfaces; an unconditional
  entry makes that 8 and turns a green legacy test red for reasons unrelated to
  what it tests. `staticOnly` is test-support-only and means "static surfaces
  only", so gating there is honest. Item 157 made the same call on the same flag.

### 7. `test_audit_text_surfaces.js` (new) + one `package.json` line

15 cases, fs-only except one integration case. Positive control (a fixture
reproducing pre-159 `llms.txt`), negative control, both boundary directions
(`1000.0%` silent / `1000.1%` red), `empty-surface`, two `broken-number-literal`
cases, aggregate-shape cap, three `tvl-floor-claim` cases including the
cross-section negative, missing-file, and a `< 1000 ms` runtime assertion.

One case worth naming: **the positive control uses a fixture, and a *separate*
case asserts the real committed files are clean today.** Item 159 merged before
this was picked up, so the live file no longer breaches. Testing only the live
file would have silently degraded from true-positive to vacuous the moment 159
landed — the spec's Territory note called this out in advance.

The integration case (`runAudit({ only: ['text-surfaces'] })`) was kept rather
than dropped: chromium *is* runnable in this sandbox (playwright 1.56.1 from the
global root).

## Non-vacuity

Rail comparison neutered to `!(val > Infinity)` → **3 red**, and exactly the
three rail-dependent cases (positive control, `1000.1%` boundary, aggregate
shape); the other 12 stayed green, which is the correct blast radius. Restored
from a pre-edit copy, verified byte-identical with `md5sum -c`, re-ran **15/15**.
Full transcript in `160-notes.md`.

## What this does NOT do

`sitemap-*.xml` and `og/*.png` stay uncovered — named in the spec as deliberately
deferred (sitemaps already have `validate-sitemaps`, 112/112; OG images need
image decoding, a different cost class). One surface family per item. And this
item does not fix 159 — 159 shipped first; this is the gate that keeps it fixed.

## Honest limit

This would have caught 159 on day one. Whether it catches the *next* unknown
class is the actual open bet, and nothing here settles it — four named detectors
catch four named shapes. The spec says so; so does this.

## Quiz

1. Why does the new code import `APY_SANITY_LIMIT` from `src/poller-core.js`
   when `generate-llms.js` exports the same constant and is the more obvious
   neighbour?
2. `tvl-floor-claim` compares the stated floor only against TVL figures in the
   floor's own markdown section. What concrete false positive does that avoid,
   and where in `llms.txt` does it live?
3. The pass is disabled whenever `opts.staticOnly` is set. Which existing test
   forced that decision, and what would have gone red without it?
4. Item 159 merged before this item was built. Why does that make the
   fixture-based positive control mandatory rather than merely convenient — and
   what would testing the live file alone have degraded into?
5. Under the neutered-rail non-vacuity run, exactly 3 of 15 cases went red.
   Why is "3 red, 12 green" the *right* result, and what would a run where all
   15 went red have told you about the test file?
