# 206 — PR explainer (HIGH tier)

**What shipped:** `audit-app.js`'s pool-detail rotation stopped drawing its candidate population from
`data/pools-snapshot.json` (736 pools) and now draws from the **union of the snapshot and the SEO
estate's own `?pool=` deep links** (3,985 ids, 3,984 reachable after the anchor exclusion). Sub-rail
pools — the 88.6% the scanner could never reach — render against an additive LIVE-shape fixture built
from the live pool records the run already fetches.

---

## Goal

Make the audit look at the pool-detail pages users can actually arrive on, instead of the richest
11.4% of them.

## Intuition — why "the audit found nothing" was a claim about the wrong population

The audit has one pool population, and it came from the file that happened to be lying around:
`data/pools-snapshot.json`. That file is not a neutral list of pools. It is railed to `DEFAULT_MIN_TVL`
($10M) for a completely unrelated reason — item 059 shrank it to keep the front-end payload small.

Meanwhile the generated SEO estate floors at **$100K** (human directive, 2026-07-11) and emits
**3,669 distinct `?pool=<uuid>` deep links**. Only **420** of those are in the snapshot. So:

| population | count | share |
|---|---|---|
| generated `?pool=` deep links | 3,669 | 100% |
| in the snapshot → rotation could pick it | 420 | 11.4% |
| absent → rotation could **never** pick it | 3,249 | 88.6% |

Two floors, set for two different and individually correct reasons, and the audit silently inherited
the wrong one as its idea of "all pools." The floors are not the bug. Inheriting one as a population is.

The consequence is not that the audit was wrong — it is that **every "pool-detail clean" claim this
loop has ever made was scoped to the richest 11.4%**, and nothing in the output said so. The first
SEO-lander → pool-detail journey on record this tick (`/tokens/jitosol` → `/?pool=fdcccd6a-…`,
kamino-liquidity SOL-JITOSOL, **TVL $1,500,009**) landed squarely in the unreachable 88.6%. And every
hand-found pool-detail bug in this backlog's history — 122, 144, 145, 165 — was on a non-flagship pool.

This is `detector-signal-coverage.md`'s rule on its fourth axis. Items 167/183 fixed pool *selection*,
191/192/196 fixed *throughput and memory*, 197 fixed the *static* population — all four took the pool
population itself as given.

## What changed and why, in reading order

**1. One extractor, hoisted — `extractDeepLinkPoolIds()` (`audit-app.js:1377`).**
The `?pool=` id extraction already existed, buried inside `prescanStaticPages()`'s backlog-184 liveness
block, only running when liveness ran and only for non-`ko/` pages. It is now a named helper called from
both places. The spec's rule was explicit — *reuse it, do not write a second extractor* — because two
copies of an extraction rule drift, and a drifted population is the exact failure this item exists to
fix. `prescanStaticPages()` returns `deepLinkPoolIds` additively; `emptyPrescanResult()` carries the same
key zeroed, so no caller has to null-check. Cost measured: **1,025 ms over 4,304 pages**.

**2. `loadLivePoolIds()` additively returns `pools`.**
It already called `cta181.loadPools()` and threw away everything but the ids. The records are needed to
build a fixture for sub-rail pools, and re-fetching them would have been a second multi-MB request per
run. One fetch, two consumers.

**3. `runAudit()` reordered** so liveness + the static prescan resolve *before* `buildPoolSurfaces()`.
The final `surfaces` array order is byte-identical to before — `staticResult.surfaces` is still
concatenated in the same position, and the extra pool surfaces are still spliced behind
`pool-detail-ko`. No `surfacesCovered` entry moved or was renamed.

**4. The widening itself, in `buildPoolSurfaces()`:**

```
candidates = snapshot ids  ∪  (deepLinkPoolIds  ∩  livePoolIds)
```

The `∩ livePoolIds` is the load-bearing part, and it is a safety rule rather than an optimisation. A
pool id with no live record has **no fixture record**, so its surface would render the honest empty
state and the scanner would report a dead-end that does not exist in production. Intersecting with the
live feed makes that structurally impossible instead of merely unlikely. On real data the intersection
costs nothing: 3,669 of 3,669 deep-linked ids resolve live.

Rotation machinery is otherwise untouched — same `sampleBySeed`, same `computeRotation`, same
`audit-rotation.json` memory, same `rotationPick`/`lensPick` markers, same wall-clock guard. The new ids
join the existing rotation rather than running a parallel one.

**5. `ROTATION_SEEN_CAP` 2,000 → 12,000.**
This one is easy to miss and would have silently defeated the whole item. The never-audited-first
rotation remembers which pools it has seen; the cap truncates that memory drop-oldest. A cap *below* the
candidate population means `unseen` can never reach zero, so `computeRotation()`'s wrap branch becomes
permanently dead code and the cycle counter never advances. 2,000 < 3,984. This is the identical trap
`STATIC_ROTATION_SEEN_CAP`'s own comment (`:422`) documents from item 196.

**6. The fixture, deliberately per-surface (`subRailLiveBody`, `audit-app.js:4207-4231`).**
`liveBody` is left byte-unchanged and still served to every pre-existing surface. A *second* body —
the same snapshot-derived array plus live records for this tick's sub-rail picks, in the LIVE shape
`{status:'success', data:[…]}` — is served only to surfaces carrying `subRail: true`. Building one
merged body would have been a smaller diff and would have changed what `grid-loading` (the one
`forceLive` surface) sees. `poolsById` gets the same records so the pool-detail driver's project lookup
resolves instead of silently returning null.

**7. Reporting, so a future reader can tell coverage from luck.** `poolRotation` gains `snapshotIds`,
`deepLinkIds`, `union`, `reachable`, `subRailPicked`, `deepLinkSource`; the CLI prints a population-split
line. When the deep-linked leg degrades to zero — fetch error, `poolLiveness:false`, prescan off, or a
shape-valid-but-not-live id — it says so on stderr and in `deepLinkSource`. It never silently widens to
pools it has no fixture for. The verifier probed all four degrade paths independently.

## Deviations from spec

1. **`deepLinkIds` reports net-new, not the raw intersection.** So `union === snapshotIds + deepLinkIds`
   holds cleanly (3,985 = 736 + 3,249). The raw 3,669 is not lost — `deepLinkSource` still prints it.
2. **`opts.deepLinkPoolIds` accepted as a direct override on `runAudit()`.** Required by the spec's own
   test §5; matches the existing `opts.livePools` / `opts.rotationState` convention. The production path
   still defaults to `staticResult.prescan.deepLinkPoolIds`.
3. **`poolLiveness: false` added to 8 pre-existing `runAudit()` calls in `test_audit_cta_provenance.js`.**
   The risky one, and the verifier tested it adversarially rather than accepting the explanation: running
   `origin/main`'s *unmodified* test file against the *branch's* `audit-app.js` gives 31/35, the two extra
   failures being real production uuids displacing the file's `p00000xx` fixture picks. With the kill
   switch: 33/35, exactly matching `origin/main`'s own 33/35. It is fixture isolation, not silencing — no
   assertion was weakened, reordered, or removed.

## Verification

Verifier verdict **PASS, 9/9 criteria, tier HIGH**, every criterion independently re-derived rather than
read from the notes — including its own scoped `runAudit()` forcing three *real* deep-linked non-snapshot
pools (uniswap-v2 `0004a5d4` $862,985; vvs-flawless `00062f7e` $168,541; uniswap-v3 `000d8ece` $1,868,566)
through the rotation: `status: "OK"`, `truncated: false`, all three rendered, **zero findings of any kind**
(0% dead-end against a 10% cap — the render proof that the LIVE-shape fixture reaches sub-rail pools).

The mandatory positive control is non-vacuous **structurally**, not by assertion: the test's tiny snapshot
contains only the anchor pool, so the synthetic pool's numbers can only have come from `subRailLiveBody`.
Injected run → P0 number-sanity citing the injected `9.01e+14` magnitude, zero dead-end. Control run
(same pool, sane `apyBase`) → zero P0/P1, zero dead-end, same surface.

20 audit-test files run on the branch and the reds re-run against an `origin/main` worktree: **5
pre-existing reds, zero new ones.** Two of those five (`test_audit_planner_flow.js`,
`test_seo_surface_audit.js`) the builder never ran and never mentioned — corrected in `206-notes.md`.

## Residual

- 5 pre-existing reds, unrelated, deliberately not drive-by-fixed.
- `audit-rotation.json` can grow to ~480 KB of daily-committed state at the new cap. Honest price of the
  memory covering the widened population; the fix, if it ever matters, is a compact id encoding — never a
  cap below the population.
- At the unchanged 32 picks/tick, a full cycle over 3,984 candidates takes ~125 daily ticks (~4 months),
  against ~23 before. Raising the sample budget trades against the wall-clock cap and is a separate call.
