# Spec 226: Google head-curation — sitemaps shrink to a demand-plausible head; soft-404 class dies; estate stays live for agents

## Evidence
GSC (human screenshots, 2026-08-04): 3,274 indexed vs 38,124 known-not-indexed; `Crawled - currently
not indexed` **18,555** (Google fetched and declined — the scaled-content verdict); Soft 404 **3,246**;
sitemap index 109 children processed successfully. Mixpanel 60d (`3b2555fb`): **zero google.com
referrals ever**; bing-family ~14 (IndexNow works); perplexity.ai 2.
Human authorization (interview Q3b, standing decision 2026-08-04): de-LIST the tail from sitemaps,
delete nothing, keep the full estate live for agents + IndexNow engines.

## Hypothesis
We believe presenting Google a small, demand-plausible head (~300-500 URLs) while the tail leaves the
sitemaps will (a) stop the scaled-content signal from suppressing the head and (b) concentrate crawl
on pages that can actually earn impressions — because Google is already declining 85%+ of the estate
and indexes-but-never-ranks the rest, and a curated sitemap is the strongest de-prioritization signal
we control without deleting agent surface.
Confidence: guess for (a) — Google may still ignore the head (authority-gated); supported for (b) and
for soft-404 elimination (3,246 known-harmful pages).
- Instance of: audience-contract divergence — one artifact set serving two consumers (Google vs agents)
  with opposite size preferences; population = all ~4,400 generated leaf pages × their sitemap entries.
- Class closed by this item: yes for the sitemap contract; head-page DEPTH (making the 300 good pages
  genuinely deep) is follow-up work, left open deliberately — ticket count stated at ship.

## Change
1. Generators gain ONE head-selection predicate (single source of truth, exported): a token/chain page
   is HEAD iff it clears demand-plausibility — top-N tokens by railed TVL + recognizable majors,
   chains with ≥K railed pools, all hubs/categories (target total 300-500; N/K derived from live data
   at generation, not hardcoded page counts).
2. `sitemap-*.xml` + IndexNow-to-Google surface only HEAD pages. **Bing/IndexNow keeps the full estate**
   (separate submission list — IndexNow engines respond, and they feed answer-engine indexes).
3. Soft-404 class: a page whose railed pool set is empty at generation is NOT emitted (and existing
   empty ones stop regenerating — they fall out on the daily regen; no manual deletion). llms.txt/md
   twins keep the full live estate.
4. `robots.txt`/noindex: UNCHANGED this item (sitemaps-only lever first; measure before escalating).
OUT of scope: deleting any live page (NEVER list); head-page depth content (follow-ups); canonical.js.

## Acceptance criteria
- [ ] Sitemap URL count (entity count — `<loc>` extraction per playbook class 13, never line-grep) drops
      from ~2,2xx to the 300-500 head; every head URL renders non-empty railed content live.
- [ ] Full estate still served: sampled tail pages → 200 + present in llms surface; IndexNow full-estate
      submission list intact for Bing-family.
- [ ] Zero generated pages whose main table is empty (the soft-404 predicate, run over the whole output).
- [ ] Head-selection predicate exported + tested as the single source (mirror rule — sitemap generator
      and any other consumer read THE predicate, no second copy).
- [ ] Regen delta separated from churn per `seo-surface-regen-delta.md`; the delta report proves ONLY
      tail pages left the sitemaps.
- [ ] Non-vacuity: force the predicate to accept-all in scratch → sitemap count test goes red; restore →
      green. Population: predicate tested against the live generation set, not fixtures.

## Measurement
Metric: GSC index-coverage classes (human-read); informational: bing-family referrals, head-page
impressions when the human next shares GSC. Gate: human GSC readout (their cadence — no calendar
window). Decision rule: soft-404 elimination keeps unconditionally; head-curation reverts only on human
call (re-adding sitemap URLs is cheap and non-destructive).

**Two different gates already exist and they are 20× apart.** `generate-token-pages.js` mints a page at
`MIN_POOL_TVL = $100K` / `MIN_QUALIFYING_POOLS = 1` / `DEFAULT_LIMIT = 0` (no cap) → 2,085 token pages,
87 chain pages on today's pull. `generate-sitemap.js` gates its app-view URLs at `SITEMAP_MIN_TVL = $10M`
/ `≥2` qualifying pools (item 013). The $100K-floored page estate IS the scaled-thin-content mass Google
declined; the $10M rail is the head-sized gate already in the repo. Head-selection therefore does not
need a new quality idea — it needs the EXISTING $10M rail applied to the static-page sitemaps.

Measured on today's pull (rails = `isQualifyingPool`: `tvlUsd ≥ $10M` ∧ `apyBase+apyReward ≤ 1000`):
- tokens with ≥2 railed pools: **107**, of which **102** have a generated static page;
- chains with ≥2 railed pools: **28** (≥3 → 23, ≥5 → 16, ≥10 → 8); all 28 have a generated page;
- A–Z hub groups: 27.

Head budget that lands inside the spec's 300-500 with NO new threshold invented:
102×2 (token pages en+ko) + 28×2 (chain pages en+ko) + (1+27)×2 (token hubs) + 2 (chain hubs) + 11
(main) = **~329**.

**Consequence: the app-view families are the tail.** Keeping any of `sitemap-tokens-all` / `-chain-<X>` /
`-category-<X>` blows the 500 ceiling (329 + 520 = 849) AND re-submits exactly the class most likely
behind GSC's Soft-404 3,246: they are client-rendered filter views, and item 188 already proved a
filter-only query renders the empty search hero rather than a grid. They leave the sitemaps; they stay
live, self-canonical (human 2026-07-11) and linked from every static page's "view in app" CTA, so
nothing is orphaned and nothing is deleted.

**Traps found in the territory:**
1. `cleanupStaleSitemaps()` (`generate-sitemap.js:52`) deletes every root `sitemap-*.xml` this run did not
   write, except `FOREIGN_PAGE_SITEMAPS`. Ceasing to emit a family therefore removes its files — correct
   (an unreferenced child would be an orphan), and it is an artifact deletion, never a page deletion.
2. ~~CI (`.github/workflows/sitemap-update.yml:163`) `git add`s only `sitemap.xml` + the four foreign page
   sitemaps — `sitemap-main.xml` has never been staged by CI.~~ **WRONG — corrected at build time
   (2026-08-05).** The line immediately after the named list is `git add -A -- 'sitemap*.xml'`, which
   already stages `sitemap-main.xml` AND (via `-A`) the deletions of the suppressed app-view children.
   The builder caught this and reported it rather than quietly implementing the brief; the redundant CI
   edit was reverted, so `.github/workflows/` — HIGH-risk config under the risk policy — is untouched by
   this item. No CI change is needed for the head set to deploy.
3. `indexnow-ping.js` derives its submission list FROM `sitemap-token-pages.xml`. Shrinking that sitemap
   would silently shrink Bing/Yandex submission to the head — the exact opposite of Q3b. The fix that
   cannot drift: derive IndexNow's list from the SERVED estate on disk (`tokens/`, `ko/tokens/`,
   `chains/`, `ko/chains/`), not from a sitemap.
4. The soft-404-at-generation predicate is already structurally satisfied: `rankTopTokens`/`rankTopChains`
   admit a record only with ≥1 railed pool, and chains additionally require a visible non-zero APY
   (030/032/033). So the expected count of empty-table pages is **0** and the honest claim is "the
   invariant is now machine-checked", NOT "we killed the 3,246" — GSC's soft-404 population is not
   readable from inside the loop.
5. `data/pools-snapshot.json` is the $10M-railed 739-pool app snapshot, NOT the SEO fixture. Per
   `playbooks/seo-surface-regen-delta.md` the SEO pipeline uses a $1,000-floored raw transient from
   `generate-pools-snapshot.js --seo-out`. Using the wrong one silently regenerates a tiny surface.
6. `playbooks/seo-surface-regen-delta.md`'s trap #4 ("removing sitemap URLs hits the NEVER list → leave
   BLOCKED") predates the 2026-08-04 Q3b authorization and is superseded FOR THIS CLASS only; the
   playbook is updated in this item's commit.
7. Require-cycle hazard: `generate-token-pages.js` requires `generate-sitemap.js`, and
   `generate-chain-pages.js` requires `generate-token-pages.js`; `generate-sitemap.js` extracts
   `getPoolTypeShared` from `PoolDetail.js` at require time. A new top-level `head-selection.js` requiring
   `generate-sitemap.js` for the rails while `generate-sitemap.js` requires it back would cycle — so the
   head predicate lives IN `generate-sitemap.js`, beside the rails it reuses, and is exported from there.
