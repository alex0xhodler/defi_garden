# PR explainer — item 237: exactly one primary "Garden this pool" CTA per pool-detail page

Risk tier: **HIGH** (verifier-confirmed) — this touches the north-star pool-detail CTA
surface (`pool_click{source=garden_cta}`, the metric NORTH_STAR.md tracks) and adds a new
analytics payload field. Not on the NEVER-auto-merge list: no trust-rail code touched, no
credentials/money/org-admin, no SEO deletion.

## Goal

The pool-detail page is the surface the north-star metric lives on: two conversion clicks,
"Garden this pool →" and "Start Earning on `<protocol>`". A UX audit (F2) found the page
rendering the FULL "Garden this pool" pair TWICE — once in the hero, once again at the bottom
of the earnings calculator — both at identical full visual weight (same filled green button,
same 54px height). That's a known anti-pattern (item 008: one action per intent level on a
page), and worse, it splits the north-star click event across two render sites with no way to
tell which one drove a given click — until this item added that segmentation.

An earlier round (225/247, "design world") had already TRIED to fix this and left a comment
claiming the repeat had been "reduced to a slim contextual echo — spec 237's intent". That
claim was false on the actual render: the echo kept the exact same `.cta-button-primary` CSS
class as the hero, so it computed to byte-identical visual weight. This item is the fix that
actually lands.

## Intuition

If a page has two buttons that both say "click here to do the main thing," a user's eye can't
tell which one is "the" action — and neither can the analytics event that fires when either one
gets clicked. The fix is not just "delete the extra button" — the earnings calculator's
post-calculation moment is a real, valuable second chance to convert (it's where the user
typed their own dollar amount and saw a concrete projection), so removing it entirely would
lose that. Instead: keep the calculator's CTA as an **echo** — same destination, same event —
but make it *look* like an echo. A plain underlined text link, not a filled button.

## What changed, in reading order

1. **`PoolDetail.js` — the hero CTA** (`ctaButton-primary`, unchanged markup): its click handler
   gained one field, `ctaPosition: 'hero'`, in the analytics context object it already builds.

2. **`PoolDetail.js` — the earnings-block echo** (previously: a second full `.cta-button-primary`
   button plus a second "Start Earning on `<protocol>`" `.cta-button-protocol` link, wrapped in
   the same two-column layout as the hero): replaced with a single `<a className="cta-echo-link">`
   — no button chrome, just the concrete projection text ("Garden this pool → ~$1,114 in 5y")
   as an underlined link. It navigates to the exact same `gardenThisPoolHref` the hero uses (same
   JS constant — guaranteed identical by construction, not by a separate equality check). Its
   click handler adds `ctaPosition: 'calculator'`. The protocol link is gone from this position
   entirely — it now renders exactly once, at the hero, matching the spec's "appears once (hero)".

3. **`analytics.js` — `trackPoolClick`**: gained one additive field, `cta_position:
   context.ctaPosition || null`. Every other emitter of `pool_click` (the yield-calculator CTA,
   the defillama fallback, etc.) simply gets `null` here — nothing about the existing
   `source`/`ctaPlacement` fields changed, so no saved Mixpanel report breaks.

4. **`pool-detail-styles.css` — new `.cta-echo-link` rule**: underlined text in the same green
   accent family the rest of the page uses (`--cert-green`), no background fill, no fixed
   height — deliberately NOT reusing `.cta-button-primary` or `.cta-button-protocol`, which are
   now reserved for the one-of-each hero pair.

5. **Compiled/minified assets** (`PoolDetail.compiled.js`, `PoolDetail.compiled.min.js`,
   `pool-detail-styles.min.css`): regenerated from source via the repo's own build scripts —
   `test_compiled_assets.js`/`test_minified_assets.js` confirm byte-identical to a fresh build.

6. **`test_repeat_cta.js`** — rewritten. The old version literally asserted the anti-pattern
   this item removes (`expected exactly 2 .cta-button-primary`). New version asserts: exactly
   one of each CTA class; the echo's href matches the hero's; both click payloads carry the
   correct `cta_position`; the SAME contract holds after a `card_click` entry (grid → click a
   pool card → detail), because the spec names both entry paths explicitly; and a live
   non-vacuity check — inject a second `.cta-button-primary` into the real DOM, prove the count
   assertion goes red, remove it, prove it goes green again.

7. **`test_pool_detail_anomaly_projection.js`** and **`test_ko_pool_money_honesty.js`**: two
   small, unrelated-looking edits. Both files used to grab "the repeat CTA" by indexing into
   `.cta-button-primary`'s NodeList at position `[1]` — that index no longer exists (there's
   only one `.cta-button-primary` now), so both were updated to read `.cta-echo-link` instead.
   No other assertion in either file changed.

## Deviations from the spec

- The spec offered the builder a choice for the echo's click behavior: "scroll-to-hero or
  direct navigate." Direct navigate was chosen — scroll-to-hero would have thrown away the
  calculator's own concrete "~$X in 5y" projection label, which the spec separately requires
  the echo to keep.
- No copy/translation changes were needed — the echo reuses the exact same `t('gardenThisPoolCta')`
  / `t('gardenThisPoolCtaConcrete')` EN+KO keys the old repeat CTA already used.

## Class audit (per the spec's "audit other surfaces" instruction)

Grepped the rest of the product for the same shape — two simultaneously-rendered elements
sharing a primary-CTA class. One candidate: `planner.js`'s checkout screen has two elements
with the class `gp-primary-cta gp-checkout-cta` in its source, but they're a
`checkoutPoolPrimary ? <a> : <button>` ternary — mutually exclusive, never both mounted.
**0 live instances of this anti-pattern found outside pool-detail.** Pool-detail itself: closed.
