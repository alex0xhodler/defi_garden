# Spec 207: item 105's kpi backfill was built for SEO arrivals and reaches 11.4% of them — and the honest fallback note is trapped inside the gate it should catch

## Evidence

All measured on `origin/main` @ `c72c90cf6`, 2026-08-02. Numbers verbatim from `signals/2026-08-02.md`.

- **105's stated purpose, verbatim from its own comment** (`app.js:1242-1251`): *"a direct `?pool=<id>` SEO
  deep link always loads LIVE `/pools` (no kpis — `snapshotEligible` is false when `urlParams.pool` is
  set), so the trust-signal notes (088.1 rate-track-record, 103 rate-momentum) that read `pool.kpis.*`
  would hide for exactly the SEO arrivals we most want to convert."*
- **Its remedy** (`app.js:1253-1273`): fetch `/data/pools-snapshot.json`, `snap.pools.find(p => p.pool ===
  poolId)`, merge `match.kpis`. The snapshot is the **$10M-railed 736-pool set**.

| population | count | share of deep links |
|---|---|---|
| generated `?pool=` deep links | 3,669 | 100% |
| present in snapshot → **105 can fire** | **420** | **11.4%** |
| absent → **105 cannot fire, by construction** | **3,249** | **88.6%** |

- Snapshot kpi health is not the limiter: **736/736** snapshot pools carry a `kpis` object and **714** have
  `historyPoints ≥ 7`. The miss is purely population.
- **Three notes hide** for the 88.6%: `PoolDetail.js:1508` rate track-record (088.1), `:1556` rate momentum
  (103), `:1602` TVL trend (087) — all gated on `pool.kpis && …`.
- **The honest fallback already exists and is unreachable.** `translations.js` `rateTrackRecordNew`
  (*"We're still building this pool's rate history — not a long enough track record yet to judge how steady
  it is."*) renders only **inside** the `pool.kpis && … historyPoints >= 1` gate (`PoolDetail.js:1508`). A
  pool with **no kpis object at all** falls out before reaching it, so the page renders **nothing** — not a
  wrong number, a blank.
- **Live corroboration:** the one real SEO→pool-detail arrival on record this tick
  (`/tokens/jitosol` → `/?pool=fdcccd6a-…`, prod `page_view` 7d, query `1636e90e`) is a $1,500,009-TVL
  Kamino pool — in the 88.6%. It got the blank version of the north-star page. 0 CTA clicks (n=1, **no
  conversion claim is made**; the ≥30 rule binds).
- **Root cause is upstream:** `compute-kpis.js` derives its history series *from*
  `data/pools-snapshot.json` (header `:9-11`), so no history exists for sub-rail pools to back-fill from.
  That structural half is **208**, deliberately not this item.

## Hypothesis

We believe **rendering an honest "we don't have rate history for this pool" note when `pool.kpis` is absent
on a live `?pool=` arrival** will **make the north-star page state its own limits instead of silently
omitting them on 88.6% of arrivals**, because the product's trust posture is that honest omission is
disclosed, never blank (122/144 precedent: null the value, say so — do not render a fabricated or empty
slot). Confidence: **supported** — the disclosure pattern is established and shipped (088.1's three tiers);
what is missing is the tier for "no data at all". Not validated as a *conversion* lever, and this spec does
not claim it is one.

## Change

Smallest version that tests the hypothesis:

1. `PoolDetail.js`: add a **fourth tier** to the existing rate-track-record block — when the pool has **no
   `kpis` object** (the live-arrival case) render a new calm note instead of nothing. Reuse the existing
   `.rate-track-record` element, class names and neumorphic styling **exactly** — no new component, no new
   CSS (NORTH_STAR 2026-07-10: reuse components, keep design tidy).
2. `translations.js`: **new copy, EN + natural KO together**, e.g. EN *"We don't have a rate history for
   this pool yet — we track the larger pools daily, and this one is below that line. The rate above is live
   from DefiLlama."* The wording must NOT be `rateTrackRecordNew` reused: *"we're still building this
   pool's history"* implies we will, and for a sub-rail pool we currently won't. **Saying the true thing is
   the whole point of the item** — a fallback that mis-describes why the data is missing is worse than the
   blank.
3. Ordering/mutual-exclusion unchanged: the new tier yields to the 071 volatility note exactly as the
   existing tiers do, and never renders alongside another track-record tier.

**OUT of scope, explicitly:**
- Any change to `DEFAULT_MIN_TVL`, `APY_SANITY_LIMIT`, anomaly flags, the degen haircut, the grid, the
  planner, ranking, or which pools the product displays. `?pool=` deep links already render these pools
  today by design (`app.js:1144`); this item changes only what the page *says* about one it already shows.
- Widening the kpi/history population → **208**.
- The audit's rotation population → **206**.
- Any claim that this moves the north star. It is a pre-traffic quality item under NORTH_STAR's 2026-07-23
  mandate.

## Risk tier (builder's guess — verifier assigns independently)

**HIGH.** It is user-facing beyond copy/styling (a new render gate on the north-star surface), which
NORTH_STAR's policy puts in HIGH outright, and it touches the page whose trust posture is the product's
whole proposition. The specific way this goes wrong is **copy that mis-states why the data is absent** —
which would be a trust-rail-adjacent regression on the exact surface the rails exist to protect, so the
"distinct key, honest wording" criterion is not cosmetic.

## Open questions

None blocking — the item ships under the standing EN+KO rule. One judgment the builder must make and state
in `207-pr.md`: whether the note names the reason (*"below the size line we track daily"*) or stays generic
(*"no rate history for this pool"*). Naming the reason is more honest and is the recommendation; if it
reads as disparaging a pool the product is simultaneously showing, the generic form is acceptable — but the
choice must be argued in the explainer, not made silently.
