## What shipped
- `planner.js`:
  - `poolSharpe(pool)` — null-safe read of `pool.kpis.apySharpe`; returns the value only when a
    finite number, else `null` (missing `kpis`/`undefined`/non-numeric → null). Current prod = all null.
  - `sharpeTieBreak(a, b)` — near-tie-break comparator. `eps = Math.max(0.10, 0.02 * Math.max(apyA, apyB))`
    (0.1pp absolute floor OR 2% of the larger rate, whichever is greater). Outside the epsilon → returns
    `0` (Sharpe has NO say; primary APY order wins → never leapfrog a materially-higher-APY pool). Inside
    the near-tie: both-null → `0` (keep prior order); one null / one numeric → numeric wins; both numeric →
    `sb - sa` (higher Sharpe first).
  - All THREE `eligible.sort` branches (`preferTypes`, `rwaAllowlist`, plain `else`): the trailing
    `return poolTotalApy(b) - poolTotalApy(a)` became `var byApy = …; var tb = sharpeTieBreak(a,b); return tb !== 0 ? tb : byApy;`.
    Membership keys (`ap-bp` / `ar-br`) still return first, unchanged.
- `test_planner_sharpe_pick.js` (new, 8 tests, all green): near-tie Sharpe wins; material-gap no-leapfrog;
  numeric-beats-null; undefined/missing-kpis no-crash; null-vs-null stable; and the **all-null no-op** —

pair, so each sort reduces EXACTLY to the current `poolTotalApy(b)-poolTotalApy(a)` (plus the unchanged
membership keys). The new test's oracle proves `curatePools` output order + `blendedApy(curated)` are
byte-identical to the pre-change behaviour on a fixed fixture. The change is invisible until pools accrue
≥8 daily history points and Sharpe lights up (~2026-07-22) — the same "land now, activates as data
accrues" pattern as 117.1/117.2.
