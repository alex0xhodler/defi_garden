- Step 3 of `playbooks/fixed-overlay-occlusion.md` finds no canceller — `.app`'s 80px clearance IS

- The five shipped fixes for this class (179 → 217 → 218 → 220 → 221) all key on a class this
  view does not carry: `.app.pool-detail-view`, `.landing-app`, `.app.has-results`. **This is the

## Hypothesis

We believe taking `.app-footer` out of the fixed layer on **every `.app` state that renders a
`.results-section` without `.has-results`** will remove at-rest occlusion and click interception
from the dead-pool empty state, because the footer then occupies flow instead of floating over
mid-document content — the mechanism 218 and 220 already proved on two other routes.
Confidence: **validated-pattern** (the same fix shape has resolved this class twice; the failure
mode of the alternatives — layout tweaks, bigger clearance — was measured and disqualified in 218).

- **Instance of:** *fixed-overlay-occlusion* — the shared opaque `position: fixed` `.app-footer`
  painting over and click-intercepting content on a route whose root does not match a fix. Sixth
  member (179 → 217 → 218 → 220 → 221 → **230**). The narrower population this item's guard
  covers: **every `.app` state that renders `.results-section` while its root lacks
  `.has-results`** — today exactly one (`deadPoolResolved`), and the selector is derived from the
  rendered `.results-section` itself, so a future member is covered without a code change.
- **Class closed by this item:** **no.** Two named gaps, both with numbers:
  1. **`.app.has-results` (the analytics grid) is still fixed-footer-occluded on `main`** — item
     221 measured `calculate-yield-btn-new` 98.8% covered at 1280×780 on `?token=`/`?chain=`.
     221's CSS is written and verifier-confirmed but **PARKED at its 3-attempt budget, PR #386
     open and unmerged, pending a human decision**. This item deliberately does not touch
     `.app.has-results .app-footer` — that would be a second run building 221 (the 2026-07-26
     double-build failure mode). **`?token=` / `?chain=` = the largest indexed surface family in
     the estate; the P0 there stays open until #386 merges.**
  2. **The `occlusion` lens under-reports a deterministic defect at 3/20 (15%)** (221's verifier).
     A lens that sees a permanent defect 15% of the time under-reports this class *everywhere*,
     not just here. Not fixed by this item; ticketed as **item 231** in BACKLOG.md, with 221's
     leading hypothesis (the fixed 150ms settle wait in `checkOcclusion` racing this surface's
     alternatives-grid render) carried over so the fixer starts from the characterisation.

## Change

**In scope**

1. `style.css` — one rule, placed with the `.app-footer` block, taking the footer out of the fixed
   layer for the state that renders results without `.has-results`:

   ```css
   .app:not(.has-results):has(.results-section) .app-footer { position: static; }
   .app:not(.has-results):has(.results-section)            { padding-bottom: 0; }
   ```

   `:has()` is chosen over a new marker class (e.g. `app.js` emitting `dead-pool-view`) because it
   is derived from the **defining mechanism** — the rendered `.results-section` — instead of a
   hand-maintained mirror of the predicate at `app.js:3299` (RAZOR side 2, item 212's precedent).
   Prior art in this repo: `style.css:2155` already ships `:has()` and it survives minification.
   `padding-bottom: 0` is not a revert of the shared clearance: once the footer is in flow it
   protects nothing and would render 80px of dead background under a footer carrying a top
   box-shadow (218's reasoning).

2. `style.min.css` — regenerate via `npm run minify`. `home.html` serves the MIN sheet; a raw-only
   fix ships dead (item 136's trap).

3. `test_dead_pool.js` — extend spec 072's existing rendered gate (reuse over invent: same server,
   same fixture, same routing; also avoids a `package.json` `test:serial` registry edit) with an
   at-rest occlusion criterion at **1280×780, 768×780, 360×780**, asserting geometry AND
   `elementFromPoint` for every rendered element of the alternatives grid.

**Explicitly OUT of scope**

- `.app.has-results` / `.app.has-results .app-footer` — item 221's territory, PR #386 open.
- Unifying the `app.js:3001` root-class predicate with the `app.js:3299` results-render predicate.
  It is the deeper defect (two copies of one predicate that disagree on exactly `deadPoolResolved`),
  but routing dead-pool into `.has-results` would (a) hand it the grid layout + `padding-top: 160px`
  intended for the Google-header results view, and (b) land it in the still-broken `.has-results`
  footer state of gap 1. Recorded in `230-notes.md`, not built.
- Fixing the `occlusion` lens's 15% detection rate (item 231).
- `margin-top: auto` on the footer — see the pre-registered measurement below.

## Pre-registered variant choice (measure, do not assume)

`.app:not(.has-results)` is `display: flex; flex-direction: column; justify-content: center`
(`style.css:857-862`), so — unlike 221's `.has-results` block-layout case — `margin-top: auto`
on the footer WOULD be live here. It is therefore a real candidate and must be **measured, not
assumed**, exactly as 221 measured and disqualified its Options A/B:

- **Variant 1 (default):** `position: static` only.
- **Variant 2:** `position: static; margin-top: auto`.

Both must be measured at **1280×780 with the shipped fixture** (long content, `scrollHeight` ≈1387
— free space is zero, so the two variants must be identical there) **and at 1280×1400 with a
short-content fixture** (all alternatives below `DEFAULT_MIN_TVL`, so the grid is empty and free
space exists).

**Decision rule, fixed in advance:** ship the variant that (a) leaves zero at-rest occlusion in
both cases, and (b) causes the smaller change to the short-content empty state's current rendered
geometry. Today the empty-state message is vertically centred with the footer pinned to the
viewport bottom; Variant 1 makes the message+footer group centre together (footer floats
mid-page), Variant 2 top-aligns the message and pins the footer. Record BOTH measured `.empty-state`
`getBoundingClientRect()` values and the footer's, in `230-notes.md`, with the loser's numbers —
a disqualification without numbers is not a disqualification.

## Territory notes

- `.app-footer` is rendered **twice** in `app.js` (`:2981` in the pool-detail branch, `:3533` in the
  main analytics branch); only the second is inside the `.app` root whose class is computed at
  `:3001`. The new selector must therefore be verified from the RENDER, not from source reading.
- `@media (max-width: 768px)` re-declares `.app-footer { padding: … }` (`style.css:2858`) but never
  its `position`, so the fix needs no mobile counterpart — confirm from `getComputedStyle` at 360
  and 768 rather than by reading the cascade.
- `style.css:2155` (`.pools-list .pool-apy-section:has(.pool-apy-tag) …`) is the existing `:has()`
  precedent, and it is present in `style.min.css` — minifier support is established, not assumed.
- The alternatives grid wraps 3-per-row at 1280px (`getEmptyStateAlternatives` returns up to 5
  top-TVL stablecoin pools above `DEFAULT_MIN_TVL`), which is why three CTAs are occluded at once
  on the wide viewport and one at 768.
