## Goal

Make A6b — the assertion in `test_audit_prescan.js` that counts real invocations of
`reconcilePrescanFindings(` in `audit-app.js` — count what is actually there, instead of what a
hand-rolled scanner *believes* is there.

## Intuition (the one-paragraph version)

Item 185 fixed A6b by counting real call sites instead of raw-text mentions. To find "real" call sites
it strips comments and string literals with a small character scanner. JavaScript has a fourth thing
that scanner has to know about and didn't: the **regex literal**. A regex is delimited by `/`, so a
scanner that doesn't track regex state will misread the characters inside one. Two shapes bite:
`/[/*]/` looks like a block comment opening (and if nothing closes it, the scanner eats the rest of the
file — so a call site added afterwards is never counted, and A6b stays green on exactly the event it
exists to catch); and a `"` inside a regex character class looks like a string opening (so the scanner
eats real code up to the next quote anywhere in the file).

## What changed, and why

### The premise was re-measured, and it changed the fix

The BACKLOG row for 186 (written by item 185's verifier) says the blind spot is **dormant** — `grep`
finds only `/[?#]/` and `/[가-힣]/` in `audit-app.js`, neither containing `/` or `*`. That is true and
it is incomplete. Running 185's exact stripper over `audit-app.js` with instrumentation that records
every span it consumes shows seven consumed spans that are not comments or strings at all:

| `audit-app.js` | consumed | what it actually is |
|---|---|---|
| `:324` | 643 chars | `const TEXT_DEFI_GARDEN_URL = /https:\/\/(?:www\.)?defi\.garden(\/[^\s)\]"'<>]*)?/g;` — the `"` inside `[^\s)\]"'<>]` opens a phantom string |
| `:771` | 1,188 chars | same shape |
| `:811` | 1,185 chars | same shape — this one swallows a real `while ((m = re.exec(text)) !== null)` loop |
| `:841`, `:856`, `:863` | 308–509 chars | same shape |

So the blind spot is **live, and has been since 185 shipped**. It has not produced a wrong number yet
only because none of the eaten spans happens to contain a `reconcilePrescanFindings(` call site — the
definition at `:2837` and both call sites at `:3059`/`:3068` survive, hence today's correct count of 3.
The distance between "silently wrong" and "correct" is where the next contributor puts a line.

**This retires the fix the backlog row called "cheapest and probably right"** — a guard test asserting no
regex literal contains `/` or `*` inside a character class. That guard covers only the shape the 185
verifier happened to demonstrate and would have scored **zero** on the quote-in-class shape that is
eating code today. The row's option 2 (a real parse via acorn/espree) means a new dependency inside the
merge gate for one counter. Option 1 — teach the scanner regex state — is what shipped.

### Leg A — regex-literal state (`test_audit_prescan.js`, `stripJsCommentsAndStrings`)

A `/` is either a regex delimiter or division, and which one is decided by what came before it. The
standard heuristic: it opens a regex when the previous significant emitted character is one of
`( , = : [ ! & | ? { } ; + - * % ~ ^ < >`, or the emitted text ends in `return`/`typeof`/`case`/`in`/
`of`/`new`/`delete`/`void`/`do`/`else`/`yield`/`await`, or nothing has been emitted yet. That lives in
the new `isRegexPosition()`, backed by `REGEX_PREV_PUNCT` and `REGEX_PREV_KEYWORDS`.

Inside a regex the scanner honours two sub-states — `\` escapes the next character, and `[` … `]` is a
character class in which `/` does **not** terminate the literal — then consumes trailing flag letters
and drops the whole literal, exactly as it drops a string.

Two details are load-bearing and were **not** in the spec:

1. **`//` and `/*` always fall through to the comment branches, regardless of position.** The build
   agent found this the hard way: without the `src[i+1] !== '/' && src[i+1] !== '*'` guard, every `//`
   line comment following a `;` or `}` was parsed as an empty regex and the file was corrupted. The
   justification is a fact about JavaScript, not a hack: an empty regex body (`//`) and a bare leading
   `*` quantifier (`/*`) are both invalid, so neither can legally *open* a regex.
2. **An unterminated regex bails at the newline**, so a heuristic misfire can damage at most the rest of
   one line — it can never run away to EOF, which is the failure mode this item exists to remove.

### Leg B — a tail-survival invariant

Every mis-tokenization in this class ends the same way: the scanner consumes to end-of-file. So assert
that the stripped output still contains a marker from `audit-app.js`'s **own** final executable line
(`process.exit(unresolved ? 3 : 2)`, `audit-app.js:3201`). The marker is derived at run time by
`deriveTailMarker()` — reading the file's last `process.exit(` line rather than hardcoding it — and is
asserted present in the raw source first, so the invariant cannot rot into a vacuous truth if that line
is ever rewritten. One assertion; catches *any* future tail-swallowing shape, not just the two measured.

### The proof structure (this is the part worth reading)

A fix to a counter can always be "green because the counter got looser". Three devices prevent that:

- **`legacyStrip()`** — 185's pre-fix scanner, copied verbatim from `origin/main` and frozen in the test
  file with a comment saying so. Its only job is to prove the *old* code was silently wrong: on the
  mutation fixtures it returns **3** (green, wrong) where the fixed scanner returns **4**. Without this,
  the new tests could pass for reasons unrelated to the fix.
- **Both shapes mutated on scratch copies** of `audit-app.js` in `os.tmpdir()`, with the real file's md5
  asserted unchanged before and after every case.
- **The division direction tested explicitly** — `a / b`, `a /= b`, `(x + y) / 2`, and a division with a
  real call site on the far side — because a heuristic that guesses "regex" at a division position would
  swallow real code and make A6b **under**-count, which is worse than the bug being fixed.

## Deviation from the spec, and the conservative choice

Criterion 2's prose says to insert the mutated regex "**before** the existing call sites". The builder
places both mutation fixtures immediately **before the tail marker** instead, and disclosed it. The
reason is mechanical, and the verifier reproduced it rather than accepting it: `audit-app.js`'s last
literal `*/` sits at byte offset 171,689, and all three real call sites sit at 156,628–170,081 — i.e.
*before* it. Inject the mutation early and `legacyStrip`'s runaway search finds that later `*/`,
recovers, and counts **4** — the same answer as the fixed scanner, which would make criterion 3
**unfalsifiable**. Only an injection after the last `*/` forces the pre-fix scanner to run to true EOF
and reproduce the reported defect (old **3**, new **4**).

The honest consequence, stated in the notes rather than glossed: the "swallows the rest of the file"
symptom **depends on no closing `*/` following the injected regex**. Where one does follow, the damage
is bounded to that span instead — still real (that is exactly what `:324`/`:771`/`:811` do today) but
not unbounded. The verifier judged the placement necessary rather than convenient, and the disclosure
not overstated.

## What is NOT proven (carried forward honestly)

- The heuristic is verified against every shape present in `audit-app.js` today plus the synthetic
  division cases. It is **not a JS parser** — e.g. post-increment-then-regex ambiguity is unhandled
  (absent from this repo). Same class of caveat 185 carried, one level more precise.
- The verifier's own finding, worth recording: under a deliberately broken heuristic that treats *every*
  `/` as a regex start, the real file's A6b count still came out at 3 and only the explicit synthetic
  division test caught the regression. So the safety net for the division direction is carried by that
  test, not by the real-file count — which passes partly by luck of the current file shape. Accepted:
  the `\n` bail bounds any misfire to one line, and the gap is disclosed rather than papered over.
