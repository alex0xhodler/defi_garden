# 117.3 — Planner "prefer steadier yield": Sharpe near-tie-break (HIGH-tier explainer)

## Goal
Make the planner's automatic pool auto-pick lean toward steadier-yield pools — but ONLY among
candidates whose headline APY is already effectively equal. This is the last of the three 117 surfaces
(117.1 pool-detail annotation #268, 117.2 analytics "Risk-adjusted" sort #270, 117.3 planner blend). It
quantifies 088's "steady 6% beats spiky 20%" thesis at the exact point plans are built — the plan-creation
funnel that the 2026-07-19 organic session (first prod `plan_created` since 07-10, via the SEO-lander →
pool-detail → planner path) just validated end-to-end.

## Intuition
`curatePools` already sorts rail-passing candidates by APY (after a persona-membership key) and takes the
top few, project-deduped. 117.3 adds ONE more comparator key, applied last: when two pools' total APY are
within a small epsilon (a "near-tie"), prefer the one with the higher rate-stability Sharpe
(`kpis.apySharpe`, shipped by the 117 compute leg). It is a **tie-break, not a re-rank** — it can only
reorder pools whose rates are already near-equal, so it can never lower or inflate the honest blended
headline, and it never demotes a materially-higher-APY pool. In current prod every pool's Sharpe is null,
so the tie-break is a pure no-op until pools accrue ≥8 daily history points (~2026-07-22) — the same
"land now, lights up as data accrues" pattern 117.1/117.2 used.

## What changed (in reading order — `planner.js`)
1. **`poolSharpe(pool)`** (after `poolTotalApy`, ~L84): null-safe read of `pool.kpis.apySharpe`; returns
   the value only when a finite number, else `null` (missing `kpis` / `undefined` / non-numeric → null).
2. **`sharpeTieBreak(a, b)`**: computes both total APYs; `eps = Math.max(0.10, 0.02 * Math.max(apyA, apyB))`
   (0.1pp absolute floor OR 2% of the larger rate, whichever is greater). Outside the epsilon → returns
   `0` (Sharpe has no say → the primary APY order stands → no leapfrog on rate). Inside the near-tie:
   both-null → `0`; one null / one numeric → the numeric wins; both numeric → `sb - sa` (higher Sharpe first).
3. **The three `eligible.sort` branches** (`preferTypes`, `rwaAllowlist`, plain `else`): the trailing
   `return poolTotalApy(b) - poolTotalApy(a)` became
   `var byApy = poolTotalApy(b) - poolTotalApy(a); var tb = sharpeTieBreak(a, b); return tb !== 0 ? tb : byApy;`.
   The persona-membership keys (`ap-bp` / `ar-br`) still return first in the two banded branches — unchanged.
4. **`test_planner_sharpe_pick.js`** (new, 8 tests): the four ordering rules + the all-null no-op oracle
   (asserts order AND `blendedApy` byte-identical to the pre-change behaviour for the `else` and
   `preferTypes` branches). Wired into `package.json` `test` after `test_planner.js`.
5. **`planner.min.js`** regenerated (`npm run minify`) — byte-identical to a fresh minify of the new
   `planner.js` (`test_minified_assets.js` planner assertion green).
