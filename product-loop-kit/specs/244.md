# Spec 244: the analytics grid has no ordering guarantee against its deferred globals — it can boot with `React is not defined` and render zero pool cards

## Evidence

`audit-app.js` full run, `generatedAt` **2026-08-06T07:15:06.317Z**, 83 surfaces, 8 findings / 7 blocking.
Two of them, one surface, one causal event:

```
[P0] grid-token :: page-error :: pageerror: React is not defined
     | console.error: TypeError: Cannot read properties of undefined (reading 'some')
       at getPoolTypeShared (PoolDetail.compiled.min.js:1:1510)
[P1] grid-token :: dead-end  :: valid grid query rendered no .pool-card within 10s
```

First occurrence on record: `grep -rl "React is not defined"` over `product-loop-kit/signals/`,
`reports/`, `LEARNINGS.md`, `BACKLOG.md` matches only today's `audit-findings.json`.

**Reproduction rate, measured, both numbers stated:** 1 of 1 in the contended 83-surface run;
**0 of 6** isolated `runAudit({ only: ['grid-token'] })` repeats (each of those instead produced
grid-token's usual 2 occlusion findings, so the surface itself was healthy in isolation). The defect is
contention-dependent and is NOT reproducible on demand today.

**Mechanism — read off the error signature, not from resemblance.** `PoolDetail.compiled.min.js` line 1 is
a single comma-separated `var` statement:

```js
var{useState:useState,useEffect:useEffect}=React,LENDING_PROTOCOLS=[…],DEX_LP_PROTOCOLS=[…],
    STAKING_PROTOCOLS=[…],YIELD_DERIVATIVES_PROTOCOLS=[…],RWA_PROTOCOLS=[…]
```

If `React` is not yet defined the destructuring throws, so **every later declarator in that same statement
never assigns**, while `function getPoolTypeShared(pool)` — a hoisted function declaration — stays
callable. Its first array read is `RWA_PROTOCOLS.some(…)` (verified in the minified body). That predicts
exactly the observed pair, in exactly the observed order. The two errors are one event.

**Why `React` can be missing at that moment:**
- `home.html:178-179` — `<script defer src="./react.production.min.js">` / `react-dom.production.min.js`
- `home.html:350-364` — an inline script at the end of `<body>` does
  `document.createElement('script'); s.src='PoolDetail.compiled.min.js'; document.body.appendChild(s)`,
  then chains `app.compiled.min.js` off its `onload`.

Dynamically inserted scripts are **async by default**. The `onload` chain the comment at
`home.html:343-347` describes orders `PoolDetail.compiled.min.js` before `app.compiled.min.js` — and
nothing whatsoever orders either of them against the **deferred** React / ReactDOM / `translations.min.js`
tags. `onload` fires on a script that threw, so `app.compiled.min.js` then loads on top and calls in.

Surface: `?token=` / `?chain=` — the sacred SEO landing surfaces and the entry path to the north-star
pool-detail CTAs. When it fires, the page renders **no pool cards at all**.

## Hypothesis

We believe **giving the dynamically-inserted analytics bundles an explicit readiness barrier against every
global they consume** will eliminate this failure mode, because the failure is a pure ordering race with no
guard in the tree — the loader today relies on the deferred tags happening to win a download race they are
not sequenced with. Confidence: **supported** (mechanism confirmed by the error signature; the missing
guarantee is visible in `home.html` and admitted by its own comment, which claims ordering only between the
two compiled bundles).

- **Instance of:** *a dynamically-inserted script that reads a global supplied by a `defer` tag, with no
  barrier between them.* The population is not one file — it is **every consumer of every deferred global
  in the analytics-mode boot path**: `React`, `ReactDOM`, and `translations.min.js`'s exports, consumed by
  `PoolDetail.compiled.min.js` and `app.compiled.min.js`. A fix that only guards `React` for
  `PoolDetail.compiled.min.js` re-commits the item-212 error (a guard aimed at the instance, launders the
  rest as covered). Enumerate the deferred globals and the consumers **from the files**, do not re-type a
  list.
- **Class closed by this item:** yes for the analytics-mode boot path, IF the guard is derived from the
  actual `<script defer>` set in `home.html` rather than a hand-written list. State the count of deferred
  globals guarded and the count of dynamically-inserted consumers covered. Planner mode
  (`__APP_MODE !== 'analytics'`) does not use this loader — say so with the grep that shows it.

## Change

Smallest version that removes the race rather than narrowing its window:

- In `home.html`'s analytics-mode loader, do not append the compiled bundles until the deferred tags have
  executed. The cheapest correct barrier is to start the chain from an event that is **defined** to fire
  after all `defer` scripts have run (`DOMContentLoaded`), rather than from parse time — but the builder
  chooses the mechanism; the criterion below is what must hold, not the technique.
- Whatever the mechanism, it must cover **all** deferred globals the appended bundles read, not just
  `React`.

**Explicitly OUT of scope:**
- Any change to `app.js` / `PoolDetail.js` source, the compiled artifacts, or the compile/minify pipeline.
  `*.compiled.min.js` are generated — never hand-edit (`home.html:341-343`).
- Trust rails, the `__APP_MODE` router's mode *decision*, `ANALYTICS_PARAMS`, and every URL behavior:
  byte-untouched. This item changes **when** the analytics bundles execute, never **whether** a URL
  resolves to analytics mode.
- The four open `.app-footer` occlusion findings (item 221) and the `planner-768` P2 (item 235).
- Perf tuning. If the barrier measurably delays first paint, say so with the number and stop; do not
  trade the fix for it.
