# 197 — explainer (HIGH tier)

## Goal, in one line

The audit that guards our SEO estate had only ever been *told about half of it* — the 2,180-page
Korean estate (`ko/tokens/`, `ko/chains/`) was invisible to every signal we have. This item hands the
existing machinery the other two directories.

## The intuition

Picture a night watchman with a good, well-tested routine: he walks the ground floor every night,
checks every door, writes down which rooms he's already done so he doesn't repeat himself. Item 154
hired him, 157 taught him where to look first, 183/191/192 tuned his route, 196 gave him the notebook.

Nobody ever told him the building has a second floor.

That's the whole finding. `listLeafPages()` — the function that enumerates what to check — is called
in exactly two places, and in both it is called with `'tokens'` and `'chains'` and nothing else:

- `audit-app.js:1398` — the cheap fs+regex prescan over *every* page
- `audit-app.js:2016-2017` — the expensive rendered rotation, ~6 pages a tick

`grep -n "/ko/" audit-app.js` returned **no path-level match at all**. The proof is the audit's own
output: the 2026-08-01 tick reported `surfacesCovered: 60`, and
`JSON.stringify(surfacesCovered).match(/\/ko\//g)` → `null`.

The second floor is not a copy of the first. `cmp tokens/usdc.html ko/tokens/usdc.html` → differ
(18,698 B vs 19,887 B); the KO page carries `<html lang="ko">` and real Hangul body copy; and we have
submitted **2,215 KO URLs** to Google via `sitemap-token-pages-ko.xml` + `sitemap-chain-pages-ko.xml`.
This is live, indexed, publicly-reachable surface.

And the class of bug that lives there is not hypothetical: **item 190 was a KO-only defect on these
exact landers** (`landing.footerPoweredBy` / `landing.footerMadeWith` rendering English on Korean
pages). It was caught by a `translations.js` dictionary diff — a completely different checker. The
estate scan could not have found it then, and could not have found it today.

## What changed, and why

The honest framing, which the spec insisted on and which held up: **this is a missing argument, not a
missing mechanism.** `listLeafPages(dir)` already takes a directory. `prescanStaticPages` already takes
an `opts.pages`. `computeRotation()` + the persisted never-audited-first state already shipped in 196.
Applying all of it to a sibling population is a *call*, not a *build* — that is the transplant rule
from `playbooks/detector-signal-coverage.md`.

Diff in reading order:

### 1. The cheap prescan learns about two more directories (`prescanStaticPages`)

```js
const rawPages = opts.pages || listLeafPages('tokens').concat(listLeafPages('chains'))
  .concat(listLeafPages('ko/tokens')).concat(listLeafPages('ko/chains'));
```

`opts.pages` override behaviour is untouched. Population goes 2,180 → **4,360** on today's checkout.

### 2. A per-family breakdown, so "clean" stays a readable claim

`scanned` stays one combined total; a new `scannedByFamily = {tokens, chains, koTokens, koChains}`
rides alongside it into the findings JSON. Without this, `scanned` silently doubling from 2,186 to
4,372 would make it impossible for the next reader to tell *EN-clean* from *KO-clean* — the number
would move for a reason nobody could reconstruct.

Measured on this run: `{tokens: 2093, chains: 87, koTokens: 2093, koChains: 87}` — an exact match to
`fs.readdirSync` counts.

### 3. One sub-rule deliberately does NOT get transplanted

The level-2 `?pool=` link-liveness check stays **EN-only**, guarded `if (poolLinkRan && !rel.startsWith('ko/'))`
and stamped `scope: 'en'` in the output.

This is the interesting decision. 196's rule is *"port the part whose precondition holds"* — and here
the precondition fails: spec evidence 5 measured the KO half emitting an **identical** `?pool=` id set
(42,604 links, 3,696 distinct ids, same numbers as EN). Re-resolving the same ids a second time buys
zero coverage and duplicates every finding. The omission is stamped into the JSON rather than left as
a silent narrowing, because a scan that quietly checks less than its name implies is exactly the
failure mode this lineage of items exists to prevent.

### 4. Two more rotation legs, mirroring the two that exist (`buildStaticSurfaces`)

`koTokens` / `koChains`, each with its own `seen` set, its own seed namespace (`${seed}:koTokens`),
its own candidate list, its own entry in `staticRotation` / `staticRotationState`. Design option (a)
from the spec, over the merged-list alternative (b), for one reason worth naming: under (a) the
seen-cap invariant reads *"the cap exceeds THIS leg's own disk population"* — checkable per leg, and
each future language is its own independently-sized leg. Under (b) it degrades to *"the cap exceeds
the combined population"*, a weaker statement that loses headroom every time the estate grows.

### 5. The budget is raised so EN is not quietly robbed to pay for KO

`DEFAULT_STATIC_SAMPLE` 6 → 12, `MAX_STATIC_SAMPLE` 12 → 24. The remaining budget splits EN-half /
KO-half *before* the pre-existing 2:1 token:chain ratio is applied within each half:

```js
const enSampleSize = Math.ceil(remainingSampleSize / 2);
const koSampleSize = remainingSampleSize - enSampleSize;
```

At the new default: EN half = 6 → 4 tokens + 2 chains — **byte-identical to what shipped yesterday** —
and KO gets that same 4 + 2 for the first time. The `ceil()` goes to EN on purpose, so an odd remainder
can never shrink the pre-197 population below its old throughput.

Verified end-to-end in the real CLI run: `static-page:ko/tokens/{zeus,dydx,min,stapt}` +
`static-page:ko/chains/{mantle,zksync-era}` appeared in `surfacesCovered` alongside the unchanged EN six.

### 6. The state file grows two legs without breaking the one on disk

`readStaticRotationState()` now normalizes four legs through the *same* `normalizeRotationLeg()` helper
196 factored out. Today's committed state file has only `tokens`/`chains`; `parsed.koTokens` is
`undefined`, and that helper's pre-existing fallback already degrades it to a fresh cycle-0/empty-seen
leg — **without touching the EN legs.** No special-casing was needed, and `schemaVersion` stays `1`
because the change is purely additive.

### 7. The ordering detail that is actually load-bearing

`routeToLeg()` — which files the anchor and prescan-promoted pages into the right leg's `seen` — must
test `ko/chains/` and `ko/tokens/` **before** the bare `chains/` / `tokens/` prefixes:

```js
if (rel.startsWith('ko/chains/')) …
else if (rel.startsWith('ko/tokens/')) …
else if (rel.startsWith('chains/')) …
else … // tokens/
```

`startsWith('chains/')` never matches `ko/chains/…`, which looks harmless — but the *fallthrough* is
`else → tokens`, so bare-prefix-first ordering would have silently filed every KO page into the EN
tokens leg's memory. The audit would then believe it had audited EN pages it never opened, and would
skip them. Wrong-but-plausible bookkeeping is worse than no bookkeeping; the same ordering rule is
applied to `scannedByFamily`'s classification.

## Deviations from the spec

Two, both recorded rather than smoothed over:

1. **The spec's population figures were one day stale.** It specifies "4,372 (2,186 EN + 2,186 KO)".
   The estate churns daily and today's real count is **4,360** (2,093 + 87 per side). This is exactly
   why the acceptance criterion demanded a disk-derived count and forbade a literal — the tests derive
   their expectations with `listLeafPages`'s own predicate, so estate churn breaks nothing.
2. **Cost attribution is honest about not reusing item 192's number.** The spec offered 192's
   ~0.19s/rendered-surface as the sizing basis; that figure was measured on *pool-detail*, a different
   and faster surface class. The measured full-CLI delta here is 118.9s → 196.8s for ~6 extra static
   renders, consistent with this file's own documented ~10s-per-static-page load in this sandbox — so
   the constants are justified by *this* run's measurement, with 192's figure labelled a secondary
   cross-check only.

## The result nobody should oversell

The KO estate scanned **clean** — zero suspects, matching the spec's own pre-registered expectation
(evidence 5). This item found no bug today. What it delivers is that the render-only classes
(dead CTAs, i18n leaks, 360px clipping, console errors) reach Korean pages for the first time, and
that every *future* signal covers the whole estate by construction instead of half of it. Coverage,
not a catch — and the spec said so in advance, which is the only reason the clean result can be read
as a true negative rather than as a checker that isn't looking.

Wall-clock: full `node audit-app.js` 118.9s → 196.8s, `status: "OK"`, against a
`FOREGROUND_CAP_MS` of 300s — inside the cap with ~34% headroom, and the revert trigger is stated in
the spec's measurement section.
