# 203 — PR explainer (HIGH tier: full walkthrough + quiz)

## Goal, in one sentence

Make an arrival at the north-star page distinguishable from a cold direct hit when it came from our own
2,180-page SEO estate — and, to do that at all, fix the reason it couldn't be done: the merge gate's link
rule believes only two things in this product read a query param, and there are three.

## The intuition (read this part even if you skip the rest)

Item 202 (yesterday) taught `analytics.js` to **capture** `src` — the tag our own internal links carry. It
rides every event, including `pool_click`, the north star. But the biggest surface that points at pool-detail
— every `tokens/*.html` and `chains/*.html` page — emits **3,677 `?pool=` deep links wearing no tag at all**.
So the heartbeat's "`src` = `undefined` × 47, 21st straight day" isn't a finding about distribution. It's a
breakdown of a property almost nothing can populate.

The filed follow-up (`specs/202-notes.md:155-184`) described this as a one-line change: both generators funnel
every pool link through one helper, `poolHrefFor`, so add `&src=` there and you're done.

**That one-line change would have turned the entire SEO estate red.**

Here's why, and it's the whole item. `audit-app.js` — our own merge gate — has a rule (a) under
`link-target-integrity` that says: *every query key on every owned link must be a key this product actually
routes on*. It builds that allow-list by parsing `home.html`'s two router arrays:

```js
return { allowed: new Set([...analyticsParams, ...plannerParams, 'lang']), error: null };
```

`src` is on neither array. Add `&src=seo_token` to a home-path link and rule (a) fires a **P1 on all 4,360
pages**. Leg B alone isn't a small change needing care; it's a broken change.

And the fix is a sentence the file had already written about itself. Look at that `'lang'` on the end, and
its comment:

> `'lang'` is read by **translations.js, not the router**, so it never appears in either array — a real, live
> query key, so it is allowed explicitly rather than fudged in by loosening the parse.

`src` is that same sentence's second instance: read by **`analytics.js`**, not the router. Rule (a) models the
query-param consumers of this product as *exactly two routers*. There is a third — the analytics capture list
— and the gate has never known it exists. `src` is just the first key to walk into the gap.

**The generalisable move:** when a gate rejects something correct, the honest question is not "how do I get my
value past the gate" but "what does the gate believe about the world, and is it true?" Here it believed
*routers are the only consumers of query params*. Widening an allow-list to make your own change pass is how
you quietly break a detector; correcting a false belief it holds — and deriving the correction from the real
source so it can't rot — is how you strengthen one. Which of the two you did is decided entirely by whether
the gate still catches things afterward, which is why criterion 4 (non-vacuity) was the hard gate on this item
and why attempt 1's verifier ran three of its own mutations rather than trusting the builder's.

## What changed, in reading order

### 1. `audit-app.js` — the gate learns the third consumer (Leg A)

**`extractForEachQuotedArray(text)`** (new, sits beside the existing `extractQuotedArray`). `analytics.js`'s
key list is an inline `[...].forEach((k) => {...})` literal, not a `var X = [...]` declaration, so there's no
variable name to anchor a regex on; this anchors on the `.forEach(` that follows the array. Same hard contract
as its sibling: **returns `null` on any parse failure, never a wildcard**.

**`loadRouterAllowedParams(homeHtmlPath, analyticsJsPath)`** gains a second source and unions the parsed
attribution keys in beside the two router arrays and `'lang'`.

The one rule that mattered while writing this: **the keys are parsed, never typed.** No `'src'` literal exists
anywhere in `audit-app.js` (criterion 6 greps for it; the single grep hit is a pre-existing comment at
`:1133`). A hardcoded copy is precisely the bug class item 166 shipped and spec 169 re-flagged — a second copy
of a list that drifts from the real one and silently allows a key nothing reads any more. Remove a key from
`analytics.js` and the gate must start flagging it again; attempt 1's verifier proved exactly this by deleting
`'ref'` (not `'src'`) and watching real `?ref=` usage get caught.

Failure behaviour is inherited, not invented: unreadable or unparseable `analytics.js` returns
`{allowed: null, error}` — the identical shape the `home.html` path already returned — so the caller's existing
"print the note once, skip rule (a), keep rules (b)/(c) and the four other signals running" handling covers the
new failure mode with **zero new caller-side branching**. A gate that dies loudly on its own broken input is
worse than one that degrades to the checks it can still make.

Both call sites (`prescanTextSurfaces`, `prescanStaticPages`) pass the new path with an `opts.analyticsJs`
override, mirroring the existing `opts.homeHtml`/`opts.plannerJs` test convention. `'lang'` and its comment are
byte-identical — deliberately not "tidied", because `translations.js` has no parseable array to derive it from.

### 2. `generate-token-pages.js` / `generate-chain-pages.js` — the estate tags its links (Leg B)

```js
function poolHrefFor(p, fallbackUrl, src) {
  const url = p.pool ? `${SITE_URL}/?pool=${encodeURIComponent(p.pool)}` : fallbackUrl;
  if (!src) return url;
  const sep = url.includes('?') ? '&' : '?';
  return `${url}${sep}src=${encodeURIComponent(src)}`;
}
```

Three deliberate details:
- **Optional third argument.** Absent or falsy → byte-identical to the pre-203 function. That's not politeness;
  it's the mechanism that keeps the JSON-LD clean (below) and it's directly asserted for `undefined`/`''`/`null`/`0`.
- **Both branches tagged.** A row whose pool has no id falls back to the token/chain app view. That's the same
  attribution question, so it must not silently go untagged.
- **Separator computed, not assumed.** `?` vs `&` is derived from the target URL, never hardcoded to `&`.

Call sites: the **visible row links only** — `'seo_token'` in the token generator, `'seo_chain'` in the chain
generator. One function edit covers both files because the chain generator already imports the helper.
Language-independent: KO pages emit the same tag, matching the shipped `renderWaitlistCtaHtml` convention on
these same pages. The page's own URL already records the language; a `_ko` suffix would be a second taxonomy
for a fact already written down.

### 3. The tests

Criterion 5 required the two pre-existing 046 assertions to come out **strictly stronger**, not merely
adjusted. Before, each asserted `html.includes(\`href="${items[i].url}"\`)` — the clean URL shows up as some
href. Now each asserts the ItemList url is clean **and** the rendered row href is *exactly*
`cleanUrl + sep + 'src=' + tag`. That pins the separator logic and the exact tag value, which the substring
check never did. Weakening either would have been an automatic FAIL, so this is the assertion to look at
hardest.

`test_seo_src_attribution.js` (new) carries criteria 3/4/6/7. All of it runs in `fs.mkdtempSync` temp dirs
under `finally { fs.rmSync(...) }` — it never writes into the real `tokens/`.

## The one deviation, pre-registered before the build

The filed note said to add the tag in the shared helper, which would tag the **ItemList JSON-LD** too (it calls
the same helper). **This ships the tag on the visible `href` only; the JSON-LD `url` stays clean.** Reasons,
recorded in spec 203 §6 *before* the code was written rather than justified afterward:

1. Google's ItemList guidance is that `url` names the canonical item page. A tracking param there points the
   structured data at a URL the page itself canonicalises away.
2. 046's invariant is *anti-drift* — same pools, same order, same target. That survives, pinned harder than
   before by the criterion-5 rewrite.
3. The optional-argument design makes "JSON-LD is unchanged" a provable claim, not a hopeful one.

Verified on real production-snapshot output, not fixtures: **0 of 40 `ld+json` blocks contain `src=`.**

## Why this is SEO-safe (the question a reviewer should ask)

Adding params to 3,677 internal links is exactly how you manufacture the indexable-near-duplicate class that
item 010 was opened for and item 188 re-found. It doesn't happen here, and the mechanism was already in place
before this item: `canonical.js:33`'s `CANONICAL_PARAMS` does not include `src`, so `/?pool=X&src=seo_token`
self-canonicalises to `/?pool=X`. Re-checked against the current file rather than quoted from memory.

Also checked rather than assumed — the three other things that parse these same links all use proper param
splitting and tolerate the extra key: item 184's liveness extractor, rule (b)'s shape check, and the
finding→url mapping. `generate-llms.js` builds its own URLs and stays clean, so `llms.txt` is untouched.
Sitemaps emit no `?pool=` URLs at all.

## What this does NOT do — read this before believing a number tomorrow

**This is an attribution fix, not a traffic fix.** No page in production carries a tagged link until the next
`sitemap-update.yml` CI run regenerates the estate — no regenerated HTML is committed here, per the standing
convention (021/041/045/050/174). And even after that, nothing walks those links until distribution lands.
The honest prediction: **the next heartbeat will still report zero tagged arrivals**, and that is not a
regression or a failed change. What changed is that the question "did this arrival come from our SEO estate?"
now has an answer at all — on `page_view`, `pool_view` and `pool_click` alike, because 202's `this.acquisition`
rides every event. At 25 straight days of a zero north star there is nothing to A/B; this is the pre-traffic
mandate's "make it measurable before there's anything to measure."

## Residuals — noticed, deliberately not fixed here

1. **`extractForEachQuotedArray` is anchored positionally.** It binds to the *first* `[...].forEach(` in
   `analytics.js`. There is exactly one today (verified), so it is correct — but a future edit adding an
   earlier `.forEach` would silently rebind it to the wrong array. The likely failure direction is loud (a red
   gate from a too-small list) rather than silent, which is why this ships as-is; anchoring the search inside
   `captureAcquisition`'s own body is the tightening, and it deserves its own item.
2. **Rule (a)'s diagnostic string** (`audit-app.js:1688`) still reads "ANALYTICS_PARAMS ∪ PLANNER_PARAMS ∪
   {lang}" and doesn't mention the third source. Cosmetic, message-text only; flagged by the build agent.
3. **Process, not code:** scratch probe pages written into `tokens/` during ad-hoc verification are one
   careless `git add -A` away from publishing a junk page into the SEO estate — this run caught exactly that
   in its own staging area before pushing. A `.gitignore` guard for `_audit_probe_*.html` is the fix; it is
   deliberately NOT smuggled into this diff as a drive-by.

distinguishes "correctly taught the gate a true fact" from "quietly broke the gate," and say why the builder's
own passing tests could not have settled it.

**Q4.** The ItemList JSON-LD `url` stays clean while the visible `href` gets tagged. What repo invariant does

weakening of it?
