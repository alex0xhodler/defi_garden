# Spec 022: IndexNow ping on token-page / sitemap changes

## Evidence
BACKLOG row 022 (score 6.5) + `reports/2026-07-11-seo-2026.md`: "IndexNow (Bing/Yandex; Google still not official) instantly notifies engines of new/changed URLs — cheap win for freshly generated token pages." `sitemap-update.yml` already pings Google/Bing's legacy `/ping?sitemap=` endpoint (fire-and-forget, no ack, no per-URL granularity) after every regen. IndexNow is the modern protocol both Bing and Yandex actually document for this: a single POST with an explicit URL list, authenticated by a key file hosted on the domain, gets URLs into their crawl queue directly instead of waiting for a full re-crawl of the sitemap.

021/014 already produced 2,028 real `/tokens/<slug>` pages generated fresh in CI daily — exactly the "freshly generated" URLs IndexNow targets. Same env wall as 021: `api.indexnow.org` is unreachable from the loop sandbox (same class of block as `yields.llama.fi`), so the actual submission must run in the networked CI (`sitemap-update.yml`), which already POSTs `git push` and pings Google/Bing from that job. The payload-construction logic is pure and fully unit-testable offline.

## Change
1. **Key file** (root, static, one-time): `${KEY}.txt` containing exactly `${KEY}` (32-char hex, generated once, committed) — served at `https://www.defi.garden/${KEY}.txt` by Vercel's default static-file handling (no `vercel.json` rewrite touches arbitrary root `.txt` files, confirmed by reading `vercel.json`'s rewrite list). This is the ownership proof IndexNow requires.
2. **New `indexnow-ping.js`** (mirrors `generate-token-pages.js`'s CLI/module pattern — pure functions + `require.main` guard):
   - `buildIndexNowPayload(urls, host, key, keyLocation)` — returns the exact JSON body IndexNow's API spec requires: `{ host, key, keyLocation, urlList }`. Pure, testable, no I/O.
   - `collectUrls(sitemapPaths)` — parses one or more sitemap XML files (regex on `<loc>...</loc>`, same lightweight approach `test_token_pages.js`/`generate-sitemap.js` already use for XML — no new XML-parsing dependency) and returns a deduped URL array, capped at IndexNow's documented 10,000-URL-per-submission limit (currently ~2,028 from `sitemap-token-pages.xml`, well under the cap; if `sitemap.xml`'s own URLs are ever added the cap still protects a single oversized POST).
   - `submitToIndexNow(payload)` — the only network call (POST to `https://api.indexnow.org/indexnow`, JSON body, matches the documented single-endpoint fan-out to Bing+Yandex); isolated behind a `--dry-run` flag so CI logs the payload without submitting when explicitly asked, and so tests never touch the network.
   - `main()`: reads the key from `${KEY}.txt` on disk (single source of truth — no hardcoded duplicate of the key inside the script), reads `sitemap-token-pages.xml` (default; `--sitemap <path>` can add more), builds the payload, submits unless `--dry-run`.
3. **Workflow** (`sitemap-update.yml`): new "Ping IndexNow" step after the existing "Ping Google about sitemap update" step, same `if: steps.verify-changed-files.outputs.changed == 'true'` guard (only runs when the regen actually produced a diff) — runs `node indexnow-ping.js`.
4. **Trust rails**: untouched — this ticket only announces already-generated, already-gated URLs; it computes no numbers and gates no content.

## Acceptance criteria
- [ ] `buildIndexNowPayload` returns `{host, key, keyLocation, urlList}` exactly per the IndexNow spec shape, given a urls array/host/key/keyLocation
- [ ] `collectUrls` extracts every `<loc>` from a fixture sitemap XML, dedupes, and truncates to the 10,000 cap (assert on a fixture crafted with a duplicate and one that would exceed a small test cap)
- [ ] Key file `${KEY}.txt` exists at repo root, its content is exactly the key, and `main()` reads the key from that file (not a hardcoded duplicate) — a mismatch is a bug this generator can't silently ship
- [ ] `--dry-run` builds and logs the payload without calling `https.request`/`https.get` (no network I/O) — verifiable by running it in this offline sandbox
- [ ] Workflow step added after the Google/Bing ping step, gated on the same `changed == 'true'` condition; YAML valid
- [ ] `node indexnow-ping.js --dry-run` + the full existing test chain (`npm test`, all 5-min timeboxed) exit 0
- [ ] No changes to trust rails, ranking/eligibility gates, or the existing `?token=`/`/tokens/<slug>` canonical split

## Territory notes
- `generate-token-pages.js` (`renderTokenSitemap`/CLI parsing) and `generate-sitemap.js` (`https` GET pattern) are the direct precedents mirrored here.
- IndexNow's API is a single well-known public endpoint (`api.indexnow.org`) that fans out to Bing + Yandex; Google does not participate in IndexNow as of this writing (per the `reports/2026-07-11-seo-2026.md` scan) — the existing `bing.com/ping` + `google.com/ping` calls in the workflow stay untouched, this is additive.
- `api.indexnow.org` is unreachable from this sandbox (confirmed via `curl`, same 403 wall as `yields.llama.fi`/CI-only network) — real submission can only be verified after a human triggers the "Update Sitemap" Action, same residual pattern as 021.
