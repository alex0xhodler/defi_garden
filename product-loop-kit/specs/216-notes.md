- New constant `POOL_ARTIFACT_UUID_RE` (byte-identical pattern to `generate-pool-pages.js`'s
  `UUID_RE`) placed next to `APY_SANITY_LIMIT`/`DEFAULT_MIN_TVL`.
- `tryLoadSnapshot(startTime, requiredPoolId)` now returns a discriminated object instead of a
  bare boolean:
  - `{ applied: true }` — snapshot loaded, `setPools` already ran, caller returns immediately
    (unchanged success case, just a differently-shaped truthy value).
  - `{ applied: false }` — every pre-216 decline reason (meta 404/`schemaVersion!==1`/stale per
    `SNAPSHOT_MAX_AGE_MS`/snapshot 404/empty-or-malformed pools) — **identical trigger
    conditions to before**, so every one of these still falls straight to `loadLive()`.
  - `{ applied: false, poolAbsent: true, snapshotPools: snap.pools }` — the NEW case: the
    snapshot itself was fresh and valid, but `requiredPoolId` wasn't in it. Only reachable when
    `requiredPoolId` is truthy and the two-way match (`pool.pool === id ||
    \`${project}-${symbol}-${chain}\` === decodeURIComponent(id)`) misses.
- New `tryLoadPoolArtifact(startTime, requiredPoolId, snapshotPools)`: fetches
  `/pools/<id>.json`, validates `schemaVersion===1`, `pools.length===count`,
  `pools.length===1`, the same `SNAPSHOT_MAX_AGE_MS` age gate on `generatedAt`, and the same
  two-way id match. On success: `setPools(snapshotPools.concat([record]))`,
  `poolsSourceRef.current = 'snapshot'` (keeps the 059-B3 escape hatch armed exactly as the
  snapshot path does), and `Analytics.trackPerformance('data_load_time', ..., { pools_count,
  source: 'pool-artifact' })` — reusing the exact emitter 214 repaired (`analytics.js` untouched;
  its existing `context.source !== undefined` forwarding already handles any string value).
  On ANY failure (404, non-OK, throw, or any validation miss) returns `false`.
- `fetchPoolsInBackground()`: after `tryLoadSnapshot` declines with `poolAbsent` AND
  `urlParams.pool` clears the `POOL_ARTIFACT_UUID_RE` shape gate, tries
  `tryLoadPoolArtifact(...)` before falling to `loadLive()`. Every other branch
  (non-pool-absent decline, shape-gate miss, artifact-fetch failure) reaches `loadLive()`
  exactly as it did before this item — **today's exact path**, unconditionally, on any failure.
- No change to `loadLive`, the 059-B3 escape-hatch effect, the pool-detail-resolution effect, or
  any render-time trust-rail filter (`app.js:1893/1982/2082`-equivalent `tvlUsd >= minTvl` gates —

## Deviations from spec / conservative choices
- **Discriminated result shape**: the spec says "give it a discriminated result" without naming
  the shape. Chose `{ applied, poolAbsent?, snapshotPools? }` over a bare string enum so the
  success path's payload (nothing extra needed) and the poolAbsent path's payload (the snapshot's
  own pools array, needed by the caller to concat) are both carried on the same return value
  without a second lookup/refetch.
- **`tryLoadPoolArtifact`'s malformed-shape check** additionally verifies `art.pools.length ===
  art.count` (not explicitly named in the spec's bullet list, which says "an array of exactly the
  pools it claims" — read as requiring exactly this check) and `art.pools.length === 1` (the
  spec states `count is 1` for a well-formed artifact; a well-formed-but-multi-pool artifact
  should never be trusted for a single-pool paint, so this is treated as a malformed-shape
  decline, not a new failure mode outside the spec's list).
- **Extended `test_pool_twins.js` instead of creating a second generator-test file** for the
  Leg 1 acceptance criterion — it already spawns the real generator into a scratch dir via
  `execFileSync` and computes `snapshotById`/`twinIds`; adding a "criterion 7" section reuses that
  setup directly rather than re-deriving it in a new file (the 2026-07-10 reuse directive read as
  applying to test infrastructure, not just product code). `test_pool_twins.js` was already
  registered in `test:serial` by item 213, so no registry change was needed for it.
- **Positive-control budget**: used a single `BUDGET_MS = 6000` constant for both scenario (a)'s
  success wait and scenario (b)'s expected-failure wait, so "the SAME budget" in the acceptance
  criterion is literally the same named constant, not two independently-chosen timeouts that
  happen to be similar.
