# 166 — The AI-discovery surface's links must go where they claim (HIGH tier explainer)

## The goal in one line

`llms.txt` / `llms-full.txt` exist to tell an LLM where to send its reader, and
every pool row in them pointed somewhere that could not address the pool it had
just quoted — so this item makes each row deep-link to `/?pool=<id>`, the
north-star surface, which the file had **never once linked to**.

## The intuition

The file was not broken in the way broken files usually are. Every URL returned
HTTP 200. Nothing 404'd, nothing looked wrong in a crawl. It was broken in the
sense that matters for a referral surface: **the link did not correspond to the
sentence above it.**

Three separate mechanisms produced that, and they are worth separating because
only one of them looks like a bug on inspection:

```
- uniswap-v3 · WETH-USDC — 95.55% APY, $110,825,218 TVL — https://www.defi.garden
- uniswap-v3 · WETH-USDC — 31.72% APY, $10,187,107 TVL — https://www.defi.garden
```

Two different pools. Two different rates. One URL, and that URL is the homepage.
An LLM citing our own data could quote the 95.55% pool and send its reader to a
page with no way to find it.

**Class 1 — `pool.url || meta.baseUrl`.** The tell is that this reads like a
fallback and is not one. No DefiLlama payload has a `url` field: not the
snapshot (`pool, chain, project, symbol, tvlUsd, apyBase, apyReward,
apyMean30d, poolMeta, exposure, ilRisk, underlyingTokens, kpis`), not the live
`/pools` shape (which adds `apy`, not `url`). So `pool.url` is `undefined` on
100% of rows, always, and the `||` branch is not a safety net — it is the only
branch that has ever executed, for the life of the surface. 15 rows on live prod.

**Class 2 — `?search=<protocol>`.** `search` is not a router param.
`home.html:77` lists `ANALYTICS_PARAMS = ['token','chain','pool','poolTypes',
'protocols','minTvl','minApy','app']` and `:78` `PLANNER_PARAMS`; `search` is in
neither, so `__APP_MODE` resolves to `'landing'` and `landing.js` reads only
`lang`. `?search=lido` renders a landing page with an empty search box — the
query is silently dropped. 17 rows. The routed param that does the job,
`?protocols=`, already existed.

**Class 3 — `?token=<symbol>&chain=<chain>` on pool rows.** These resolve, so
they are not dead. They simply cannot address *a pool* — only a grid — which is
why the two WETH-USDC rows above collapse onto one URL.

The through-line is the one number worth remembering: `grep -c "?pool="
llms.txt llms-full.txt` → **0 and 0**. Every record in the payload carries the
pool id. `/?pool=<id>` has been the north-star surface since the 2026-07-23
standing decision. The file built to serve AI discovery — the only growth
channel that needs no human posting — had never linked to it.

## What changed, in reading order

**1. A new exported helper, `generate-llms.js:44-57`.**

```js
function poolUrl(pool, baseUrl) {
  if (pool && typeof pool.pool === 'string' && pool.pool.length > 0) {
    return `${baseUrl}/?pool=${encodeURIComponent(pool.pool)}`;
  }
  return `${baseUrl}/?token=${encodeURIComponent(pool && pool.symbol || '')}&chain=${encodeURIComponent(pool && pool.chain || '')}`;
}
```

The id path is the norm; the `?token=&chain=` grid link survives only as the
genuine fallback for a record with no id. Note what is *absent*: `pool.url` is
not read, and the comment says why, so the next person does not reintroduce it.
Exported (`module.exports`) so tests can call it directly — the house pattern
already used for `pickHighYield`, `APY_SANITY_LIMIT`, `MIN_TVL_USD`,
`formatTvlFloor`.

**2. Both pool-row emitters call it.** `buildConcise` ("Current Top Yields",
~:505) dropped its inline `searchUrl`; `buildFull` ("Live High-Yield
Opportunities (by Chain)", ~:618) dropped `const poolUrl = pool.url ||
meta.baseUrl` — note that local shadowed the new helper's name, so removing it
was required, not cosmetic.

**3. `?search=` → `?protocols=` at all three sites** — `buildConcise`'s protocol
rows (~:475), `buildFull`'s (~:589), and the "Pendle opportunities" example
(~:485, now `?protocols=pendle`). We did **not** add `search` to the router.
The fix is to stop emitting a param that does not exist, not to invent one; a
real search param is a larger, separate idea.

**4. `test_llms_link_integrity.js`** (new, 268 lines, 24 assertions), wired into
`test:serial` immediately after `test_llms_rails.js`. Both legs, per 159's
precedent: live-payload-shaped fixtures against `poolUrl()` directly, **and**
assertions against the committed artifacts on disk.

**5. Regenerated `llms.txt` + `llms-full.txt`** via `node generate-llms.js`
against a live 16,008-pool fetch. Generator output, never hand-edited.

## The check that is not a number

The most reusable assertion in the new test is the router-param membership one:
every `?key=`/`&key=` in both committed files must be a member of
`ANALYTICS_PARAMS ∪ PLANNER_PARAMS ∪ {lang}` — **parsed out of `home.html` at
test time**, not hardcoded. A second copy of that list in the test would be a
fresh instance of the same bug class the test exists to catch: a claim that can
silently drift from the thing it describes. If someone renames a router param,
this test goes red on the generated surface rather than the surface quietly
going dead again.

## A link that routes is not a link that works

Worth stating because it was the one place this fix could have replaced one
broken class with another. `?protocols=` is routed — but does it *filter*?

`generate-llms.js:330` builds `topProtocols` from `pool.project`
(`protocolTvl.set(pool.project, ...)`), so the emitted slug (`lido`, `aave-v3`,
`sky-lending`, `sparklend`, `binance-staked-eth`, `morpho-blue`, `pendle`) is
the same string the app matches against. `app.js:1790-1804` tries `friendlyName`
first, then falls back to `pool.project.toLowerCase().includes(selected)` —
which the slug satisfies exactly. Confirmed independently by the verifier, which
wrote a standalone simulation of the match function and checked all seven slugs
both match their own project and exclude an unrelated one.

## Instrumentation: none, deliberately

No new event, and that is the correct outcome rather than an omission.

The metric already exists on the other side of these links.
`pool_view{source=url_direct}` fires on every `/?pool=<id>` landing (item 020,
render-verified by `test_northstar_cta_fires.js`), and the north star itself is
`pool_click{source ∈ garden_cta, protocol_link}` on the page those links now
reach. This change does not create a funnel step to measure — it **routes AI
referrals onto a surface that has been fully instrumented since 2026-07-23**.
Adding a `llms_link_click` event would be both impossible (we do not serve the
click; the LLM does) and redundant with the arrival event we already have.

## The NEVER-list judgment (the reviewable risk)

This regenerates committed SEO surface, which puts it on NORTH_STAR's **HIGH**
list. The question that matters is whether it is on the **NEVER** list —
specifically "deleting or de-indexing SEO surface". It is not, and the evidence
is mechanical:

- `llms.txt` 76 → 76 lines; `llms-full.txt` 5017 → 5017 lines. No row removed.
- All 7 section headers in `llms.txt` and all 16 in `llms-full.txt` identical.
- `Total URLs: 4913` unchanged; `validate-sitemaps.js` → 112/112 valid.
- Zero `<loc>` entries touched — `llms*.txt` are not sitemap files and carry no
  sitemap entries.

The only content deltas are link-target corrections and ordinary daily numeric
drift from the live re-fetch. Contrast item **148**, which genuinely drops 7
sitemap `<loc>` entries and is therefore correctly gated and left open.

159's rails are asserted intact and were re-derived: zero APY figures above
`APY_SANITY_LIMIT` in either file (highest is 86.23%), the `TVL ≥ $10M` claim
still matches `MIN_TVL_USD`, and both constants are byte-unchanged.

## Honest limitations

- **The upside is unmeasurable today.** There is no AI-referral traffic yet
  (14d `src` breakdown: one row, `undefined` = 47) and `pool_view{url_direct}`
  is 1 all-time. Per the 2026-07-27 LEARNINGS takeaway, no 14-day calendar
  window was opened on a zero-traffic funnel: this is evaluated when cumulative
  `pool_view{url_direct}` ≥ 30. The build leg's success criterion is the
  acceptance criteria, which are checkable today. This ships as a correctness
  fix, not a growth experiment.
- **CI overwrites the artifacts daily** (`sitemap-update.yml:110`). The
  generator fix is what persists; the artifact leg gets re-proved by the next CI
  commit. Both are asserted, so a regression in either fails.
- **The param-membership scan is raw text, not a URL parser.** No stray `?word=`
  prose exists in either file today (checked), and a future one would surface as
  a new failing key — the fail-safe direction.
- **`test_llms_shared_source.js` is still not wired into `test:serial`** — a
  pre-existing gap on `main`, verified with `git show origin/main:package.json`,
  not introduced here and out of this spec's scope. It was run manually and passes.
- **The full ~100-file `npm test` chain was not run end-to-end** (5-minute
  timebox). The targeted gate was: `test_llms_link_integrity` 24/24,
  `test_llms_rails` 14/14, `test_llms_freshness` 8/8, `test_llms_shared_source`
  12/12, `validate-sitemaps` 112/112.
- **Two of three verifier attempts failed, and both failures were the
  operator's, not the build's.** Attempt 1: 9/10 — this file did not exist, and
  it is a HIGH-tier merge gate. Attempt 2: all 10 spec criteria met and every
  number here fact-checked accurate, but the verifier read the BACKLOG row and
  LOG entry and caught them asserting "SHIPPED"/"auto-merged" in the past tense
  while `git log origin/main..HEAD` was still empty — the same "claim written
  ahead of the fact it asserts" pattern that failed the parked old-166 three
  times, reproduced by me one item later. Attempt 3: PASS 10/10. Product code
  was byte-identical across all three, which the verifier established by
  diffing against its own saved attempt-1 artifacts rather than taking the
  claim on trust. Recorded because a PR that hides its own failed verdicts is
  the thing this loop exists to not do.
