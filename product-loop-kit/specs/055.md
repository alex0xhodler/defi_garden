# Spec 055: Long-cache Cache-Control for static JS/CSS/fonts in vercel.json

## Evidence
From `product-loop-kit/reports/2026-07-12-pagespeed.md` (finding 4): "No static-asset cache headers. vercel.json sets `Cache-Control` only for `/` and `/home` (`max-age=0`); JS/CSS/fonts get no long-cache." Confirmed by reading `vercel.json`: the `headers` array has entries for `/`, `/home`, and `.well-known/*` JSON files only — no entry matching `*.js`, `*.css`, or `/fonts/*`. Static payload on the analytics/SEO path is ~557K raw (app.js 119K, planner.js 196K, style.css 123K, translations.js 67K, PoolDetail.js 52K — per the same report) plus `fonts/FKGroteskNeue.woff2`, all re-fetched every visit with no cache directive today.

## Hypothesis
We believe adding explicit `Cache-Control` headers for JS/CSS and font assets will reduce repeat-visit payload (PageSpeed's "efficient cache lifetimes" audit, and real repeat-session load time) because the browser can skip re-downloading unchanged bytes on the next visit. Confidence: validated-pattern (standard static-hosting perf practice) — but this repo has NO content-hashed filenames (`app.js`, `style.min.css`, etc. are static names referenced directly in `home.html`/`plan.html`), and this repo's own build loop merges to `main` (→ auto-deploys via Vercel git integration) multiple times per day. An `immutable`/1-year cache on unhashed filenames would serve stale, possibly-broken JS to repeat visitors for up to a year after a deploy — an availability regression, not a perf win. So the change must NOT copy the naive "immutable, max-age=31536000" recipe for the unhashed JS/CSS.

## Change
Add two new `headers` entries to `vercel.json`:
1. **Fonts** (`/fonts/(.*)`) — genuinely static (one font file, never content-modified in this repo's history, no user-facing correctness risk if cached long): `Cache-Control: public, max-age=31536000, immutable`.
2. **JS/CSS static assets** (`/(.*)\.(js|css)`) — matches `app.compiled.min.js`, `PoolDetail.compiled.min.js`, `planner.min.js`, `style.min.css`, `translations.min.js`, `analytics.js`, `brand-icons.js`, and their unminified siblings: `Cache-Control: public, max-age=300, stale-while-revalidate=86400`. 5 minutes fresh (kills the "every page nav re-fetches everything" cost within a session) + 1-day stale-while-revalidate (a visitor who returns within a day gets an instant cached response while the browser silently re-fetches in the background — so a deploy propagates to that visitor's *next* request after the background refetch, not "up to a year later").

Explicitly OUT of scope: content-hashed/versioned filenames (would let us go `immutable` safely on JS/CSS too — real fix, but it's a build-pipeline change touching `compile-app.js`/`minify-assets.js`/every `<script src>` reference across `home.html` + `plan.html`; that's a separate, larger item). Also out of scope: HTML entry points (`/`, `/home`, `/plan.html` — already have their own `max-age=0` headers and must stay revalidate-always, they're the sacred router surface) and any change to `home.html`/`plan.html` markup.

## Acceptance criteria
- [ ] `vercel.json` remains valid JSON (parses with `JSON.parse`).
- [ ] New header rule matching `/fonts/(.*)` sets `Cache-Control: public, max-age=31536000, immutable`.
- [ ] New header rule matching JS/CSS assets sets `Cache-Control: public, max-age=300, stale-while-revalidate=86400`.
- [ ] The existing `/`, `/home`, and `.well-known/*` header entries are untouched (still `max-age=0, must-revalidate` for the two HTML routes).
- [ ] No change to `rewrites`, to `home.html`/`plan.html`, or to any `<script>`/`<link>` tag — this is a `vercel.json`-only diff.
- [ ] Tests: `npm test` still passes (all existing suites; no test currently asserts on Cache-Control headers, so none should newly fail).

None — the naive long-cache approach was rejected in favor of the SWR compromise above precisely to avoid needing to ask "is stale-serving OK"; the chosen values keep worst-case staleness to about a day of background-refreshed responses, not the same-content-forever risk immutable caching on unhashed files would create. ## Territory notes
`vercel.json`'s `headers` array is evaluated as an ordered list of independent rules; Vercel merges headers from every matching rule for a given request rather than taking only the first match (confirmed by the existing file: the catch-all `/(.*)` rule already coexists with more specific `/`, `/home`, and `/.well-known/*` rules, and both sets of headers are expected to apply together — e.g. `/` gets both the security headers from the catch-all AND its own `Cache-Control`/`Vary`). The new JS/CSS and font rules follow the same additive pattern and do not need to exclude `/`, `/home`, or `.well-known/*` since none of those paths end in `.js`/`.css` or live under `/fonts/`.
