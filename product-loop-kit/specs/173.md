# Spec 173: 1,749 of 2,200 SEO pages have a primary CTA that lands on an empty grid

## Evidence
Measured 2026-07-29 by the heartbeat, against **live DefiLlama (`https://yields.llama.fi/pools`, 16,038
pools)** — not the committed snapshot — so the finding does not depend on checkout staleness.

Every generated SEO page ends with a primary CTA into the analytics app. Counting pages whose CTA target
returns **zero** pools at the app's default filter:

| surface | pages | CTA returns 0 pools | share |
|---|---|---|---|
| `chains/*.html` | 88 | **48** | 54.5% |
| `tokens/*.html` | 2,112 | **1,701** | 80.5% |
| **total** | **2,200** | **1,749** | **79.5%** |

Verbatim from `chains/cardano.html`, live on prod:
> Cardano's largest live pool is liqwid (ADA) at 2.16% ($6.13M TVL). **33 pools** across 31 tokens clear
> DeFi Garden's $100K TVL floor, $20.36M in total. … **See live pools on Cardano →**

That button is `href="https://www.defi.garden/?chain=Cardano"`. Live pool count at the app's default floor:
**0**. The page names 33 pools; the click delivers none.

Pages that received prod `page_view`s in the last 7 days (`query_id 471e380a`), with their CTA's live result
count: `/chains/linea` → **1**, `/chains/aptos` → **1**, `/chains/plasma` → 10, `/chains/ethereum` → 406,
`/tokens/buidl` → 9, `/tokens/usdc` → 147. The defect concentrates in the long tail — exactly the pages SEO
exists to serve.

**Root cause — a floor mismatch between a page and its own link, not a data problem:**
- `generate-token-pages.js:60` — `const MIN_POOL_TVL = 100000;      // $100K eligibility floor for a page's pools`
- `generate-chain-pages.js:65` — `if (!isQualifyingPool(p)) return; // trust rail + $100K floor, one gate`
- `app.js:801` — `const DEFAULT_MIN_TVL = 10000000; // $10M default floor`

100×. The page is built at $100K; the CTA target defaults to $10M.

## Hypothesis
We believe **making each generated CTA carry the floor its own page was built with** (`&minTvl=100000`) will
**eliminate the dead-end for all 1,749 pages** because `app.js:927` already honors an explicit param —
verbatim: *"Respect explicit `minTvl=0`; fall back to `DEFAULT_MIN_TVL` only when param is absent"* — so the
link resolves to exactly the pool set the page already lists. Confidence: **validated-pattern**, measured
this tick, not argued:

| CTA | default | `&minTvl=100000` | page's own claim |
|---|---|---|---|
| `?chain=Cardano` | 0 | **33** | "33 pools" — exact |
| `?chain=Celo` | 0 | 16 | — |
| `?chain=Fantom` | 0 | 6 | — |
| `?token=1INCH` | 0 | 17 | — |
| `?token=ACX` | 0 | 2 | — |
| `?token=00` | 0 | 3 | — |

## Change
In `generate-token-pages.js` and `generate-chain-pages.js`, append the generator's own `MIN_POOL_TVL` to
every app-bound `?token=`/`?chain=` grid link the page emits (the primary CTA and any secondary
`&poolTypes=` variants), reading the value from the existing constant — **never a second hardcoded literal**
(the 159 rule). Regenerate `tokens/`, `chains/`, and the sitemap suite via the npm scripts and commit the
regenerated output.

**Explicitly OUT of scope:**
- `DEFAULT_MIN_TVL` and every other trust rail — **byte-untouched**. This changes what a generated link
  *says about itself*; it does not change any default the app applies. Confirmed against the NEVER list.
- `?pool=` deep links on these pages — already correct, they address a pool directly and need no floor.
- The app's own dead-end behaviour when a *user* searches a small token — that is item **133**, which is
  BLOCKED on a human decision about discovery UX at the floor. 173 is the unblocked slice: it stops *us*
  from sending readers into that dead end from our own pages.
- The `$100K` floor itself, and the FAQ copy that misdescribes it → item **174**.
- Which pages should exist at all (junk slugs) → item **148**.

      `?token=`/`?chain=` link carries `minTvl` equal to the generator's `MIN_POOL_TVL` constant.
- [ ] A script (committed, e.g. `test_seo_cta_targets.js`) that, for every generated page, extracts the
      primary CTA and asserts the target returns **≥ 1 pool** when evaluated against the pool set — and it
      must fail if run against the pre-change `chains/`/`tokens/` output (**red→green non-vacuity proof
      required in the notes**, per the 155 precedent).
- [ ] Re-running the heartbeat's measurement gives **0 of 2,200** pages with a zero-result primary CTA
      (down from 1,749). State the exact command and its output in `specs/173-notes.md`.
- [ ] For at least 3 sampled pages, the CTA's live result count **equals the pool count the page's own prose
      claims** (Cardano: page says 33, link must return 33).
- [ ] `grep -c "10000000" generate-token-pages.js generate-chain-pages.js` is unchanged from pre-change, and
      `app.js`'s `DEFAULT_MIN_TVL`/`APY_SANITY_LIMIT` lines are byte-identical — verifier re-derives with
      `git diff`.
- [ ] The floor value in the generated links is read from the existing `MIN_POOL_TVL` constant, not re-typed.
- [ ] Tests: `node test_planner.js && node test_protocol_parsing.js && node test_qualifier_fix.js` green,
      plus `npm test`, plus the new script.
- [ ] SEO regen committed via `npm run sitemap && npm run generate:llms && node generate-stories.js` — the
      `tokens/`/`chains/` output is generated, never hand-edited.
- [ ] Instrumentation: none new. The existing `pool_view`/`pool_click` and `search_success` events already
      measure the downstream effect; a landing that returns pools can produce `pool_view`, one that returns
      zero cannot.

## Measurement
Metric: `search_success` and `pool_view` originating from static-SEO entry (prod `page_view` on
`/tokens/*` or `/chains/*` followed by a grid render). Window: **traffic-gated, not calendar-gated** (the
166/168 precedent) — hold open until **≥ 30 prod `page_view`s land on `/tokens/*` or `/chains/*`**, then
read. Current rate is ~6/week, so expect ~5 weeks.
Decision rule: keep unconditionally — this is a correctness fix, not an experiment; a page that promises 33
pools and delivers 0 is broken at any traffic level. The metric read only tells us whether fixing it moved
anything downstream. Per NORTH_STAR's minimum-sample rule, make no funnel claim below 30 events; below that,
write "insufficient data".

## Risk tier (builder's guess — verifier assigns independently)
**HIGH.** Regenerates the entire 2,200-page SEO surface (diff will be thousands of lines, far over LOW's
150-line cap) and touches generated SEO surface, which NORTH_STAR lists as HIGH. It is **not** on the NEVER
list: no trust rail is weakened — `DEFAULT_MIN_TVL` is untouched and the change makes a link *more* honest,
not a filter looser. The NEVER list forbids *weakening* a rail and *de-indexing* SEO surface; this does
neither (no page is removed, no `noindex` added). The 159 precedent points the same way: applying an
existing constant to a surface that lacked it.

## Open questions
None that block. The one judgment call — whether the linked grid should show the page's $100K set or the
product's $10M set — is settled by the 2026-07-11 standing decision that the static page and the app view
are **two distinct things showing different content**: the static page's job is to deliver *its own* listed
pools, so the link must reproduce the page's set. If the human would rather the pages be rebuilt at the
$10M floor instead (fewer, richer pages), that is a different item and a bigger call — flag it in the
report, do not assume it.
