## The evidence

**1. The playbook names this exact gap as an open candidate extension** —
`playbooks/product-audit.md`, §Automatability, verbatim:

> Known blind spot (144): its number-sanity check is magnitude-only (`ABSURD_MAGNITUDE = 1e11`), so
> out-of-rail **percentages** — the 144 class — pass clean. Candidate extension: a rail-relative percent
> check per the decision rule in class 1 above.

**2. Class 1's decision rule, already written down** (same playbook):

> **any rendered `%` figure > `APY_SANITY_LIMIT` on a pool that is NOT anomaly-flagged is a finding** — the
> rail defines what the product itself calls not-credible, so showing it unflagged is a contradiction.

**3. Code-verified on this checkout (2026-07-29), not read from notes.** `scanNumbers(text)`
(`audit-app.js:1334`) is the **only** number check on the rendered leg — it is called once, from
`auditText()` (`audit-app.js:1438`), for every rendered surface. Its four rules are: broken numeric literal;
`undefined`/`null` in a numeric slot; money not en-US 2dp; absurd magnitude `|value| >= 1e11`. It never
references `APY_SANITY_LIMIT`. Meanwhile the constant IS used at:

- `audit-app.js:323` — text-surface prescan `apy-rail-breach` (llms.txt / llms-full.txt)
- `audit-app.js:1010`, `:1017` — pool-snapshot prescan `apy-rail-breach` / `mean30d-rail-breach`

So the rail-relative check exists on **both non-rendered legs and on neither rendered one**. A
`36,452.4%` figure is only 3.6e4 — it sails straight through the rendered scan while being 36× the rail.

**4. The class has already produced a real P0 and the scanner still cannot see it.** Item 144 —
`apyMean30d = 36452.38798` on balancer-v2 WSTETH-AAVE, rendered as a trusted "30d Mean APY" card on a pool
whose `totalApy = 0.24` kept it un-flagged — was found **by hand**, and would still be invisible to
`audit-app.js` today.

**5. Fourth instance of the documented pattern 148 → 159 → 166 → 172**: a checker's signals come from the
last bug, so the next bug lands in the class nobody has been bitten by yet. The data legs learned the rail;
the rendered leg never did.

## Territory notes (facts established this session — build on these, re-verify, do not re-derive from scratch)

**The product's real anomaly markers** (these are what "anomaly-flagged" means in the DOM):

- `.apy-anomalous` — `app.js:2744`, added to the grid pool-card hero APY when
  `isAnomalousApy(pool)` (`app.js:2336`: `(apyBase||0)+(apyReward||0) > APY_SANITY_LIMIT`). Styled at
  `style.css:5354`.
- `.calc-warning` — `PoolDetail.js:657` and `:1117`, rendered when `isAnomalous` (`PoolDetail.js:250`),
  carrying `t('calcAnomalyWarning')` = "⚠ This rate is anomalous and almost certainly unsustainable."
  (EN, `translations.js:130`; KO counterpart in the same file).
- Pool-detail additionally replaces anomalous derived figures with `—` (`PoolDetail.js:703`, `:738`,
  `:1102` — item 165), so an anomalous pool-detail page renders the marker and no absurd derived number.

**Suppression must be DOM-SCOPED, not page-global.** The analytics grid renders many pool cards at once; a
legitimately flagged anomalous card must not mask an unflagged breach in a different card. Scope each
breaching figure to its nearest `.pool-card` ancestor when one exists, else the page.

**The false-positive that will bite you: the TVL-trend note.** `PoolDetail.js:1531` renders
`_formatNum(Math.round(Math.abs(tvlTrend) * 100)) + '%'` — a deposit-base change, not a rate. A pool that
grew 20× renders a legitimate **"1,900%"**. It is gated only on `|tvlTrend| >= 0.25` and
`historyPoints >= 7`; nothing bounds it above, and nothing should. The same applies to any future non-rate
percentage. **The rule is about APY/rate figures, not about every `%` on the page** — a blanket
"any % > 1000" check is a FAIL.

**KO is not optional.** The audit drives `pool-detail-ko` and `planner-ko`. If the predicate reads labels,
the KO strings must be single-sourced from `translations.js`, never hand-copied or guessed. **Prefer a
structural/DOM predicate over a prose one** if one exists — it is language-proof by construction.

**`apyMomentum` is rendered as an APY-shaped percent** (`PoolDetail.js:1487-1492`, `_formatApy(|mom|)`) and
is only transitively bounded (145 nulls it when a series *endpoint* breaches the rail). Treat it as a rate
figure, in scope for the check. Note the honest consequence in the notes either way.

## Acceptance criteria

Rendered behavior via real Chromium on the real surfaces (the 2026-07-11 standing decision) — unit fixtures
alone are a FAIL for the extraction layer, though a pure exported helper SHOULD carry its own unit cases.

1. **True negative, measured both sides.** A full `node audit-app.js` on this checkout emits **zero**
   findings of the new check across all surfaces, and total findings / blocking are **unchanged** vs an
   isolated `origin/main` worktree run (6 / 5 today). Report both numbers from runs you executed.
2. **Non-vacuity, rendered.** Prove on a REAL Chromium render — not a fixture — that the check can fire:
   drive a mutated-snapshot render in which an out-of-rail APY figure reaches the screen on a pool the
   product does **not** anomaly-flag, and assert a P0 whose `detail` quotes the figure verbatim. If no such
   mutation is reachable because every rate render site is already railed (the honest possibility — say so
   plainly if it is), then instead: (a) prove the rule fires via the pure helper's own cases, AND (b) prove
   the DOM-extraction layer is live on a real render by asserting it collected ≥1 real `%` figure and ≥1
   real anomaly marker from a genuine page. "Returned zero" is never evidence on its own.
3. **Anomaly-awareness (negative control, rendered).** Inject an out-of-rail `apyBase` with `apyReward = 1`
   (`test_audit_app.js:92-98` documents why both are needed to clear the render gate) → pool-detail renders
   the `.calc-warning` marker → the **new check** emits ZERO findings for that figure. Assert on the new
   check specifically; the pre-existing magnitude rule may legitimately still fire.
4. **TVL-trend control.** A pool rendering the growth note at `tvlTrend = 19` (`historyPoints >= 7`) →
   "1,900%" on screen → **zero** findings of the new check. This one is load-bearing; a rendered assertion
   is strongly preferred over a helper-only one.
5. **KO parity.** The check behaves identically on a real `?lang=ko` pool-detail render: no new findings on
   clean data, and criterion 3's suppression still holds. Proven on a real KO render.
6. **Honest artifact.** `product-loop-kit/signals/audit-findings.json` regenerated with local playwright
   present (`npm ci` first — a committed snapshot must not claim a version the repo does not install; the
   172 precedent), and the new signal visible in the emitted shape at 0.
7. **Wiring.** New/extended tests wired into `package.json`'s `test:serial` and classified into the correct
   `run-tests.js` lane. `node test_audit_app.js`, `node test_audit_prescan.js`, `node test_audit_pool_prescan.js`,
   `node test_audit_text_surfaces.js`, `node test_seo_surface_audit.js`, `node test_audit_runner.js`,
   `node test_audit_planner_surface.js`, `node test_audit_planner_flow.js` and `--lane=plain` all green.
   **Timebox: 5 foreground minutes per run.** The full 60+-file browser lane is NOT required — state exactly
   what you ran and what you did not. Never imply green on something unrun.
8. **Scope proof.** `git diff origin/main...HEAD --name-only` touches no product file, no generator, no
   generated page, no CSS. `package.json` dependencies byte-identical, no new dependency. NEVER list clean
