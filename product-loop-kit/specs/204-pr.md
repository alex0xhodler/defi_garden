# 204 — PR explainer: finishing the estate's arrival tag

Tier: **HIGH** (spec's guess; the verifier assigns independently — see the BACKLOG row
for the tier actually assigned). HIGH-tier explainers get the full walkthrough + quiz.

---

## The goal, in one sentence

Every link that carries a visitor from the static SEO estate **into the app** should say
where they came from — and after item 203, only half of them did.

## The intuition

`analytics.js` has an acquisition-capture step (item 202): when the app boots, it reads a
short list of arrival params out of the URL — `utm_*`, `ref`, `gclid`, and, since 202,
`src` — and stashes them. `getBaseContext()` then spreads that stash onto **every**
event the session emits afterwards, including `pool_click`, which is the north star.

So a single query param on an outbound link buys attribution on everything that visitor
does later. Item 203 put that param on the estate's `?pool=` deep links — the ones that
land a visitor straight on pool-detail. It did not put it on the `?token=` / `?chain=`
links, which land the visitor on the analytics grid instead.

Those two are not equivalent paths for one visitor; they are two different *funnels* into
the same north-star surface:

```
  static page ──?pool=…&src=seo_token──────────────► pool-detail ──► garden_cta   [attributed]
  static page ──?token=…──► grid ──► pool card ──► pool-detail ──► garden_cta   [anonymous]
```

The second path was the **larger** of the two by link count. Measured on the committed
estate this run:

| link family | count | carried `src` before this item |
|---|---|---|
| `/?pool=<id>` | 4,324 | yes (203) |
| `/?token=<SYM>&minTvl=…` | 4,491 | **no** |
| `/?chain=<name>&minTvl=…` | 214 | **no** |

On `tokens/usdc.html` you could see both states on the same page: 8 tagged pool links and
5 untagged app links. This item tags the 5.

## What changed, in reading order

### 1. `generate-token-pages.js` — a helper lifted out of existing code

`poolHrefFor` already knew how to append the tag (203 wrote it). That tail is now its own
exported function:

```js
function withSrc(url, src) {
  if (!src) return url;
  const sep = url.includes('?') ? '&' : '?';
  return `${url}${sep}src=${encodeURIComponent(src)}`;
}
```

and `poolHrefFor` calls it. This is a pure extraction — the falsy-`src` early return is
what keeps 203's contract ("byte-identical when no tag is passed") intact, and it is
asserted for `undefined`, `''`, `null` and `0`.

### 2. The four render sites

| site | before | after |
|---|---|---|
| `generate-token-pages.js:901` (`.tp-cta`) | `href="${appUrl}"` | `href="${withSrc(appUrl, 'seo_token')}"` |
| `generate-token-pages.js:804` (category nav) | `href: c.url` | `href: withSrc(c.url, 'seo_token')` |
| `generate-chain-pages.js:333` (`.cp-cta`) | `href="${appUrl}"` | `href="${withSrc(appUrl, 'seo_chain')}"` |
| `generate-chain-pages.js:240` (category nav) | `href: c.url` | `href: withSrc(c.url, 'seo_chain')` |

### 3. What deliberately did NOT change — the load-bearing part

**`appUrl` is not tagged at its definition**, and neither is the shared `categoryLinksFor`
helper. That looks like the obvious one-line fix and it is the wrong one, because `appUrl`
has two other consumers:

- `renderItemListJsonLd(rec.pools, appUrl, language)` uses it as the ItemList fallback
  `url`. Item 203 pre-registered that JSON-LD `url`s stay **canonical** — Google wants
  canonical item URLs in an ItemList — and its verifier proved 0 of 40 real `ld+json`
  blocks carry `src=`. Tagging `appUrl` would have silently reversed that on every page.
- `poolHrefFor(p, appUrl, 'seo_token')` uses it as the fallback branch for a pool row with
  no id — a branch 203 already tags. Tagging `appUrl` too would emit
  `…&src=seo_token&src=seo_token`.

So the tag is applied at the *visible render site*, one level down. The unit assertion
that pins `categoryLinksFor`'s own output as **untagged** (`test_token_pages.js:550`)
staying green is therefore a feature, not an oversight: it proves the shared helper was
left alone.

### 4. Tests

New `test_seo_app_link_attribution.js` (14 assertions) drives the **real** generators over
real fixtures and covers: both CTAs tagged exactly, every category link tagged and none
skipped, no href carrying `src=` twice, no `ld+json` block containing `src=` anywhere,
`withSrc`'s four falsy cases, and a rendered real-Chromium leg asserting the SEO-lifeline
guardrail — `?token=…&src=seo_token` still renders pool cards — with the no-`src` control
rendering identically and emitting no `src` key. Wired into `package.json`'s `test:serial`
chain (the list `run-tests.js:67` parses); no dependency added.

Three pre-existing substring assertions (`test_token_pages.js:558`,
`test_chain_pages.js:500/501`) pinned a category href ending at the closing quote and so
went red — correctly. They were updated to the new exact expected string, **not** relaxed:
they still match to the closing quote, now including `&src=…`. Same treatment item 203
gave the analogous pool-row assertion.

## Deviations from the spec

- The spec said to wire the new test in "right after `test_seo_src_attribution.js`". That
  test turns out never to have been wired into `test:serial` at all (a pre-existing gap
  from 203, found by grep), so there was no such anchor; the new test went in after
  `test_chain_pages.js` instead. **The 203 gap itself is left unfixed rather than
  swept in as a drive-by** — filed here for the operator.
- The spec's file allowlist for the build agent did not include
  `test_token_pages.js`/`test_chain_pages.js`, so the three assertions above were fixed in
  a second, operator-directed pass rather than in the first. That was a spec defect, not a
  builder deviation; recorded in `204-notes.md`.

## Measurement honesty (pre-registered in the spec, before the build)

This ships **attribution, not traffic**. No production page carries a tagged `?token=`
link until the next `sitemap-update.yml` CI regen, and nothing walks it until distribution
lands. **The next heartbeat should still read zero tagged arrivals — that is the expected
outcome, not a failure.** What changed is that the browse path into the north-star surface
is now attributable at all.
