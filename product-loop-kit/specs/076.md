# 076 — OG-image outRoot must follow `--out`: scratch runs of the token/chain generators mutate the repo's committed og/ assets

Status: READY → picked up 2026-07-13 (promoted by build loop — no READY items existed; precedent: 070/074/075 promotions from spec-notes evidence)
Risk: HIGH (SEO-pipeline generator scripts — `generate-*.js` are the sanctioned write path for the generated SEO surface; when in doubt → HIGH)
Score: 6.6

## Evidence (documented, in-repo)

1. **Verifier-found, with demonstrated harm** — `specs/075-notes.md`, "Verifier disclosures appended by the operator": `generateOgImages(..., process.cwd())` at `generate-chain-pages.js:448` ignores `--out`, so ANY run — even one pointed at a scratch dir — rewrites repo `og/chains/*.png`. The 075 verifier's independent scratch regen did exactly that and **briefly deleted `og/chains/metis.png`** (Metis drifted out of the live ranking mid-verification); it had to be restored from origin/main before commit. Explicitly flagged there as "future item candidate".
2. **Same bug in the token generator** — `generate-token-pages.js:926`: `generateOgImages(ranked, 'tokens', rec => rec.symbol, process.cwd())`. Confirmed by grep this session.
3. **Blast radius** — `generate-og-images.js:119-128`: `generateOgImages(records, kind, labelFor, outRoot)` already supports an `outRoot` parameter correctly, and it STALE-DELETES every `og/<kind>/*.png` whose slug is not in the current run's record set. So e.g. a `--limit 5 --out /scratch/tokens` test run deletes ~99% of the committed `og/tokens/*.png` files from the repo working tree. The HTML-page stale-cleanup in both generators is correctly guarded (`outDir !== process.cwd()` / scratch-isolated via `--out`); the OG call is the one path that escapes the `--out` isolation.
4. **Why it matters to the loop system**: every future build/verify cycle that regenerates pages against a fixture or live data in a scratch dir (the established verification pattern for 045/050/051/062/066/075) silently dirties — or deletes from — the committed SEO surface, risking exactly the kind of accidental-deletion commit NORTH_STAR's NEVER list ("deleting or de-indexing SEO surface") exists to prevent.

## Change (smallest that fixes it)

In BOTH `generate-token-pages.js` (main, ~line 926) and `generate-chain-pages.js` (main, ~line 448):

- Resolve `outDir` (`const outDir = path.resolve(args.out)`) BEFORE the OG call (today the OG call comes first — reorder).
- Call `generateOgImages(ranked, <kind>, <labelFor>, path.dirname(outDir))` instead of `process.cwd()`.

Rationale for `path.dirname(outDir)`: the repo layout keeps `tokens/`, `chains/`, `ko/…` and `og/…` as siblings of each other under the repo root, and both generators ALREADY derive the Korean output the same way (`koOutDir = path.join(path.dirname(outDir), 'ko', path.basename(outDir))` — see the in-code comments about `path.resolve()` discarding args). `path.dirname(outDir)` extends that exact sibling convention to `og/`.

**Production invariance**: CI (`.github/workflows/sitemap-update.yml`) runs both generators from the repo root with `--out tokens` / `--out chains`, so `path.dirname(path.resolve('tokens')) === process.cwd()` — byte-identical behavior on the production path. Only runs that point `--out` elsewhere (scratch/verification runs) change behavior, which is the point.

`generate-og-images.js` itself needs NO change (its `outRoot` parameter already works; `test_og_images.js` already exercises it with scratch dirs).
