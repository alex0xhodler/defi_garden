# 216 — explainer (HIGH tier: full walkthrough + quiz)

## Goal in one sentence
A `?pool=` arrival whose pool is **not** in the committed $10M snapshot — that's **88.5%** of the SEO
estate's 3,658 deep links into the north-star surface — used to block its first paint on the multi-MB
`yields.llama.fi/pools` fetch. Now it paints from a ~450-byte per-pool file CI already had the data to
bake.

## The intuition
Item 214 taught the app to paint a pool-detail page from `data/pools-snapshot.json` instead of waiting on
the live feed. But that snapshot is railed to ≥$10M TVL, so it only ever contains **420 of 3,658** of the
pools our own SEO pages link to. For the other ~3,238, 214 changed nothing: the page still waits for a
multi-megabyte download before anything appears.

The awkward part is that the page doesn't *need* the multi-megabyte download. It needs one pool's record —
about 450 bytes. And item 213 already proved that data exists in CI: `generate-pool-pages.js` resolves
every deep-linked id against `seo-pools.json` (the ≥$1,000 transient) and writes `pools/<id>.md` for each
one, 3,656 of which are committed on `main` today.

So this item does not fetch anything new, compute anything new, or schedule anything new. It writes a JSON
sibling next to a markdown file that already ships, and teaches the app to read it.

## Why this is not a trust-rail change (the question to ask first)
A sub-$10M pool record now enters the app's `pools` array earlier than it used to. That sounds like
relaxing `DEFAULT_MIN_TVL`. It isn't, for two independent reasons:

1. **The rail is a render-time filter, not a property of the array.** `app.js`'s grid/search/ranking paths
   all gate on `pool.tvlUsd >= minTvl`. The live path already puts every sub-rail pool in that array today
   (it loads the full ~3,900-pool feed) and the grid still shows only ≥$10M pools.
2. **The record is one the live path already delivers.** This item changes *when* it arrives, not *whether*
   it does, and not what any rail does with it.

Acceptance criterion 4 pins this down on **rendered output**, not state: after a sub-rail artifact paints,
searching that pool's own unique symbol at the default floor renders **zero** cards.

## What changed, in reading order

**1. `generate-pool-pages.js` (+50/−4) — the artifact.**
`require('./generate-pools-snapshot.js')` for `projectPool` and `envelope` — a literal import, not a copy,
so the artifact's record shape is the *same code* that builds a snapshot entry and cannot drift from it.
`buildPoolArtifact()` wraps one projected record in that envelope; `main()` writes `<id>.json` beside every
`<id>.md` in the loop that already exists. Two details that matter:
- **`minTvlUsd` is `1000`, never `10000000`.** The artifact states its own floor honestly. A sub-rail file
  claiming the snapshot's rail would be a false trust claim baked into a data file.
- **The stale-sweep now covers `.json` too.** The generator already deleted orphaned `.md` before writing;
  a pool that leaves the deep-link set must not leave a stale *paint* artifact behind — that would be a
  page painting from data nothing regenerates.

**2. `app.js` (+91/−16) — the read path.**
`tryLoadSnapshot()` returned a bare `true`/`false`, which cannot distinguish *"this snapshot is fine, the
pool just isn't in it"* from *"this snapshot is stale/404/garbage."* Those must be treated differently: the
first is the only case where a per-pool artifact is trustworthy, because we still need the snapshot's own
pools as the base list. So it now returns `{applied}` / `{applied:false}` / `{applied:false, poolAbsent:
true, snapshotPools}`. Every pre-216 decline reason returns the plain `{applied:false}` and falls straight
to live exactly as before.

`tryLoadPoolArtifact()` then applies to the artifact *the same* validations the snapshot gets —
`schemaVersion === 1`, an array matching its own claimed `count`, the same 6h `generatedAt` age gate — plus
the same two-way id match the pool-detail resolver uses, so the artifact can never claim a pool the
resolver would then fail to find. On success it sets `snapshotPools.concat([record])` and keeps
`poolsSourceRef.current = 'snapshot'`, which is what keeps item 059's B3 escape hatch armed (if the
effective `minTvl` later drops below the floor, live is fetched and replaces everything).

A shape gate (`POOL_ARTIFACT_UUID_RE`, the same pattern the generator uses) runs **before** the id is ever
reflected into a fetch path, so a hostile or legacy `?pool=` value cannot steer the request.

**Every failure returns `false` and falls through to `loadLive()`.** 404 is the *expected* state until the
next CI bake, and it costs exactly today's behaviour. That is the whole safety argument: the new path can
only ever make an arrival faster, never worse.

**3. `app.compiled.js` / `app.compiled.min.js` — regenerated.** Production serves these. The verifier
re-ran `minify-assets.js` itself and diffed against the committed output: byte-identical, so it's a genuine
fresh build, not a stale artifact making the change dark.

**4. Tests.** `test_pool_artifact_paint.js` (new, 11 rendered Playwright scenarios) and a new criterion-7
section in `test_pool_twins.js` (41/41), registered in `package.json`'s `test:serial` — item 205's lesson
is that `run-tests.js` does not glob, so an unregistered test file simply never runs.

## Deviations from the spec
All four are documented in `216-notes.md` and none change what was asked for: the discriminated-result
shape was unnamed by the spec and chosen to carry `snapshotPools` without a second fetch; two extra
artifact-shape checks (`pools.length === count`, `=== 1`) were added as malformed-shape declines; the Leg 1
test extended `test_pool_twins.js` rather than creating a second generator-test file, reusing its existing
real-generator harness; and one shared `BUDGET_MS` constant backs both the headline scenario and its
positive control so "the same budget" is literally the same constant.

## What is NOT claimed
- **No conversion claim.** Pre-traffic (n≈0, north star = 0 for 26 days). This closes INCONCLUSIVE at the
  2026-08-17 window like 088.1/207/214. The honest deliverable is the population change (11.5% → ~100% of
  3,658 deep links), verifiable by construction.
- **The artifacts are not in this commit** (212/213 precedent — twins must come from the same CI fetch as
  the snapshot and estate HTML). Merging is the trigger: both `app.js` and `generate-pool-pages.js` are in
  `sitemap-update.yml`'s push paths. Disclosed cost: between merge and that run, `/pools/<id>.json` 404s and
  every arrival takes today's live path.
- **Real Mixpanel ingestion** of `source: 'pool-artifact'` is unprovable in-sandbox (host-gated to no-send
  on localhost); the test asserts the payload at the `Analytics.track` choke point, one hop earlier.

## Verification
Verifier verdict **PASS**, tier **HIGH** independently assigned (not accepted from the spec). It falsified
the headline rather than trusting it: it mutated the **shipped** `app.compiled.min.js` — the file
`home.html` actually serves, a stronger control than the suite's own — to short-circuit the artifact gate,
watched scenario (a) go red with the expected `.pool-detail-view` timeout, and restored the file to an
md5-verified byte-identical state before re-running green.
