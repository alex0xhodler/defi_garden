# 163 — explainer (HIGH tier)

Spec: `product-loop-kit/specs/163.md` · notes: `163-notes.md` · branch: `claude/loop-163`
Verifier: **PASS, 10/10 criteria, tier HIGH** (independently re-derived; see the addendum at the
bottom for what it re-ran and the two mutations it invented itself).

## Goal

Make `npm test` — the automated half of the loop's merge gate — actually observable.

## The intuition, in one paragraph

The standing autonomy decision (2026-07-10, ratcheted to (c)) is *"verifier PASS + **tests green**
→ merge to main, ANY tier."* Half that gate was a claim nobody could check. `npm test` was 94
`node <file>.js` steps joined by `&&`, which means the first non-zero exit kills the other 93. Two
things followed, and both were measured on this checkout rather than assumed:

1. **A fresh clone died at step 5.** Every cloud-routine session starts from a clone with no
   `node_modules`. In that state the non-browser subset ran **19 pass / 17 fail** — every failure a
   raw `MODULE_NOT_FOUND` stack from inside a *generator* the test requires
   (`test_llms_rails.js` → `generate-llms.js:12`, `test_compiled_assets.js` → `compile-app.js:30`).
   The first casualty is position 5, so `npm test` printed a Node module-resolution trace and
   stopped, having executed 4 of 94 files. After `npm ci` (3 seconds) the same subset was
   **34 pass / 2 fail** — the reds were entirely environmental. This is item **149**'s finding
   (`audit-app.js` dying `MODULE_NOT_FOUND: playwright` in a fresh checkout) generalised from one
   file to the ship gate itself.
2. **Nothing after the first red was ever seen.** `specs/158-notes.md` says it in the loop's own
   words: *"no known red remains at positions 1-12; the chain has never been observed past position
   12 in-sandbox."* Positions 9-12 are real-Chromium files that alone blow the 5-minute foreground
   timebox — the 158 verifier needed a 550s cap to get `test_search.js` green. So **82 of 94 files
   had no observed result in any recent build session**, including the trust-rail tests
   (`test_llms_rails.js`, `test_mean30d_sanity.js`, `test_zero_yield_demote.js`,
   `test_kpi_rail_history.js`) that exist precisely to defend the moat.

The fix is not a new test framework. It is a ~390-line runner that refuses to hide: it tells you
when your environment is wrong instead of failing cryptically, it runs every file regardless of
what came before, and it prints a per-file result so "green" is a number you can read rather than
an absence of output.

## What changed and why — the diff in reading order

**1. `package.json` (scripts only, 4 insertions / 1 deletion).**
The original 94-step chain is preserved **byte-identical** as `test:serial`, with exactly one step
appended (`node test_run_tests.js`, the new file). `test` becomes `node run-tests.js`. Two
conveniences added: `test:fast` (= `--lane=plain`) and `test:browser`. `dependencies` and
`devDependencies` are untouched, and so is `package-lock.json` — **no dependency was added or
changed**, which is what keeps this out of the risk policy's dependency clause even though it lands
in the same file.

Why keep the old chain rather than delete it? Because it is the **single source of truth for the
file list**. `run-tests.js` parses `test:serial` out of `package.json` rather than holding a second
copy (`run-tests.js:54-73`). A file therefore cannot be silently dropped from the gate by editing
one place and forgetting the other, and acceptance criterion A1 can assert exact list equality
programmatically instead of by eye.

**2. `run-tests.js` (new).** Four ideas, in the order they execute:

- **Preflight** (`:291`, before any selection or spawn). No `node_modules` → one actionable line,
  ``dependencies not installed — run `npm ci` ``, exit **2**, zero test files executed. The 17
  stack traces above become one sentence that names the fix.
- **Transitive lane classification** (`:79-148`). A file belongs to the browser lane if it *or any
  module it transitively requires* drives a real browser. This is a memoised, cycle-safe,
  depth-limited walk over local `require('./x')` edges — **not** a filename allowlist. The reason
  it must be transitive is concrete and was found the hard way: `test_seo_surface_audit.js`,
  `test_audit_prescan.js` and `test_audit_app.js` contain no mention of the browser driver at all;
  they require `./audit-app.js`, which does. A naive one-level grep (the operator's first probe,
  before the build) put all three in the "plain" lane and then blamed them for timing out.
- **Isolation and bounded concurrency** (`:197-246`). Each file runs in its own child process with
  a per-file timeout; a red never aborts the run. The plain lane runs `min(4, cpus-1)` at a time;
  the browser lane is **forced serial** (`:188`) because `audit-app.js` binds a fixed port (8821)
  and `162-notes.md` records a live `EADDRINUSE` collision between two concurrent sessions.
- **Reporting** (`:327-370`). Per-file `PASS`/`FAIL`/`TIMEOUT` + duration, a `TOTAL` line, the
  failing files' last output lines, and a non-zero exit iff anything failed or timed out.
  `--json=<path>` writes only when asked — a default write would dirty the working tree on every
  run, which is how a test runner ends up in a loop's commit.

**3. `test_run_tests.js` (new).** Local-fixture assertions covering A1 (list equality), A3 (a red
does not abort), A4 (transitivity, including a cycle) and A5 (timeout enforcement). No network, no
browser; it is itself in the plain lane and in the chain.

**4. Post-verification change: lane-aware default timeout.** See `163-notes.md`'s section of that
name. The verifier flagged that a single 120s default would mark legitimately-slow browser files
`TIMEOUT` — `test_search.js` needs ~550s by 158's own measurement — so a default `npm test` would
have exited non-zero forever, which defeats the item. The default is now 120s for the plain lane
and 600s for the browser lane; an explicit `--timeout=` still overrides both. This landed *after*
the PASS and was re-proved separately.

## Deviations from spec

Two, both documented in `163-notes.md` and both accepted by the verifier as necessary:

1. **`require.main === module` guard** (`run-tests.js:373`). `main()` was initially unconditional,
   so `test_run_tests.js` requiring the module to unit-test its exports kicked off a full real
   test-chain run as a side effect — caught live when a throwaway one-liner started spawning
   `test_smoke.js` in the background.
2. **Self-reference workaround in `test_run_tests.js`.** The classifier substring-scans source for
   the browser driver's package name — which `run-tests.js`'s own source necessarily contains. A
   literal `require('./run-tests.js')`, or even spelling that package name in a comment, made the
   *test file* classify itself as browser. Resolved with a computed-path require and a
   runtime-reconstructed marker string. It took two passes; a stray literal survived in a doc
   comment on the first one.

Neither changes what the spec asked for; both are consequences of a program that reads its own
repository.

## What is NOT claimed

The full 61-file browser lane was **not** run — it exceeds the 5-minute foreground timebox by
design, and spec A7 makes an honestly-bounded claim the deliverable rather than a green tick.
**Exactly two** browser-lane files have been driven end-to-end through the runner and come back
green: `test_landing.js` (`PASS` 40.6s, run independently by the verifier) and `test_smoke.js`
(`PASS` 134.4s, run by the delta verifier under the new 600s browser default — the same file that
was `TIMEOUT 120.03s` before the lane-aware change, which is the decisive proof that change was
needed). **The other 59 were not executed.** Their status is unknown, and *that is the point of the
item* — the runner is what will finally make it knowable, one bounded lane run at a time.

No product file, generated SEO surface, dependency, workflow or trust-rail constant was touched.
Nothing on the NEVER list: no rail weakened, no credentials or money, no SEO URL removed or
de-indexed, nothing under `telegram-bot/`, `whatsapp-bot/`, `workers/`.

## Quiz (5 questions)

1. `run-tests.js` could have held its own list of the 94 test files. Why does it parse
   `package.json`'s `test:serial` string instead, and what specific failure does that prevent?
2. `test_seo_surface_audit.js` contains no reference to the browser driver anywhere in its source.
   Why must it still land in the browser lane, and what would a one-level `grep` have done with it?
3. The browser lane is forced to `jobs=1` even when the machine has cores to spare. What concrete,
   previously-observed failure is that guarding against?
4. On a fresh clone the runner exits **2** rather than **1**. Why is a distinct exit code worth
   spending, given that both mean "not green"?
5. The verifier PASSed at 10/10, and a change was made *afterwards* anyway. What was it, and what
   would have been wrong with shipping the version that passed?
