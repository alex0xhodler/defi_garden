# 246 — PR explainer (LOW tier)

**What shipped:** three `white-space: nowrap;` declarations in `style.css` (`.pool-apy-hero`,
`.pool-apy-preview`, `.tvl-value`), the regenerated `style.min.css`, and one new rendered-behaviour
guard, `test_card_numeral_wrap.js`, registered in `test:serial`. No markup, no JS, no tokens, no
geometry, no copy, no translations.

**Why.** Spec 246 batched three C4 findings from `reports/2026-08-06-ux-audit-3screens.md`. That audit
was measured on the **pre-merge 225 branch**; #393/#409/#411/#412/#413 have landed since. Re-measuring
all three on `main` in rendered Chromium (9-pool fixture, both views, both themes, 360/768/1280/1540)
before writing any code changed what the item is:

| Leg | Audit's claim | Measured on `main` today | Shipped |
|-----|---------------|--------------------------|---------|
| (a) `$X.XX/day` wraps to 2 lines | live | **does not reproduce** — the widest string reachable under `APY_SANITY_LIMIT` is ≈`$27.40/day`, ~70px in a 282px card | durability guard only |
| (b) "Underlying Assets" chip renders mono-caps | live | **already closed** — `.pool-token-chip` computed `font-family` === body's stack, `text-transform: none` (247's world rewrite; `PoolDetail.js:1049` says so) | pinned by test, no CSS change |
| (c) last row orphans a single card | live | **live** — 9 pools → rows `[4,4,1]` at 1280 and 1540 | **not fixed** (see below) |

But the same re-measurement found the class's still-live member, which the audit had not named: an
**anomaly-flagged APY hero wraps to two lines** — `⚠ 36,452.38%` splitting the warning glyph from the
number it qualifies, in grid view at 1540/1280/360 and list view at 1280/768. That is a trust-rail
legibility defect on the most consequential cell of the card, and it is what `.pool-apy-hero`'s rule
actually repairs. The other two rules are pre-emptive guards on the two sibling numeral cells that
share that geometry — stated as guards, never as repairs.

**Reading order of the diff.** `style.css` §4156 `.tvl-value`, §4170 `.pool-apy-preview`, §4223
`.pool-apy-hero` — one declaration plus a comment naming the positive control in each. No ellipsis or
truncation anywhere: a truncated number would be a trust-rail violation (CLAUDE.md), so a wrap
discipline is the only admissible shape for this fix. `style.min.css` is `npm run minify` output.
`test_card_numeral_wrap.js` derives its population from the **rendered DOM** at test time — every
`.pool-apy-hero` / `.pool-apy-preview` / `.pool-apy-tag` / `.tvl-value` inside every rendered
`.pool-card` — and asserts one-line rendering + computed `white-space: nowrap` per cell, plus no page
or cell overflow, across 16 view × theme × viewport combinations (414 cells scanned), plus the leg-(b)
chip pin. `package.json` gains the one registry line `test_test_registry.js` requires.

**The overflow risk was measured, not assumed.** List view lays the row out as
`40px 1fr 110px 130px 120px`; a single-line `⚠ 36,452.38%` could have overrun the 110px APY track. It
measures `clientWidth === scrollWidth === 110px` at 768/1280/1540 in both themes — it fits exactly. No
track was widened, so the approved list view is untouched and `test_list_default.js` /
`test_list_polish.js` needed no changes (run anyway: 3/3 and 6/6).

**Deviations from the spec, all deliberate.**
1. Leg (a) is a guard, not a repair — the named instance no longer reproduces. The spec's acceptance
   criterion ("every per-day cell single-line") is met, but it was already met before the change; the
   honest evidence is the non-vacuity transcript, not the green.
2. Leg (b) ships zero CSS. It was already correct; only the pin is new.
3. **Leg (c) is not fixed and the class is left open, with the number.** An orphan row appears whenever
   `N mod cols == 1`; the grid is `repeat(auto-fill, minmax(280px,1fr))` with `max-width: 1200px` and
   `gap: 12px`, i.e. 3 columns at 1024–1279px and 4 at ≥1280px. Every CSS-only remedy inside the spec's
   own constraints ("no layout recomposition", "no new layout system", no behaviour change) trades a
   benign grid remainder for a worse asymmetry (a full-bleed or double-width last card), and the only
   real fix — making the result count divide by the column count — is a behaviour change the spec
   excludes. Shipping the narrow fix is allowed; claiming it closed the class is not.
4. Open sibling instance recorded, not fixed: `.pool-symbol` wraps to 2–3 lines in **list** view at
   768/360px for long chain-suffixed symbols. It is text, not a numeral cell.

**Non-vacuity.** Each of the three rules was deleted separately → the suite went red naming that exact
cell → restored → green, with `md5sum` proving a byte-identical restore; the leg-(b) pin was reddened
by temporarily adding `text-transform: uppercase` to `.pool-token-chip`. Two traps were hit and
recorded rather than papered over: `home.html` loads `style.min.css`, so every trial needs a re-minify
(the first pass produced a false green), and realistic TVL/$-per-day magnitudes cannot stress those two
tracks at all, so the fixture gained two garbage-magnitude pools — grounded, not invented:
`getQuickPreview`'s `$/day` is **not** clamped to `APY_SANITY_LIMIT` and `formatCurrency` has no upper
bound, which is RAZOR.md worked example 2's exact shape. Full transcript: `specs/246-notes.md`.

**Class statement.** A wrap defect in a different numeral cell of a pool card is caught automatically —
the scan is a population scan, not an instance list. Outside `.pool-card` nothing is covered: the
planner, the pool-detail page body and the generated token/chain pages render their own numerals under
other classes and are not guarded. The four-class enumeration is itself finite — a genuinely new
numeral element under a new class name would need adding to `NUMERAL_CLASSES`.

**Why this is not gated by the 2026-08-05 DESIGN QUALITY BAR** (the 2026-08-10 run deferred 246 on
those grounds, and this run overrides that with reasoning rather than silently): that directive governs
the visual-world increments — screenshot-first design passes, each human-approved before the next. This
diff changes no token, no colour, no type scale, no spacing, no geometry and no component structure; it
stops a warning glyph from being orphaned from its number. It is a legibility/trust-rail repair, not a
design increment. The two legs of 246 that *were* design work (the chip restyle and the grid
recomposition) are precisely the two this PR does not perform — one because 247 already did it, one
because it is left open. If the human reads that differently, the revert is three lines.
