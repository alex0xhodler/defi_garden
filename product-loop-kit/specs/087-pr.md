# 087 — PR explainer (HIGH tier): data-layer leg 2, phase 0 — history retention + KPI computation

## Goal
Give DeFi Garden a **poor-man's time series** with zero backend and zero credentials, so item 088 can
surface honest, decision-useful KPIs (rate momentum, rate stability, TVL trend, track record) to the
cautious-saver ICP. This is leg 2 of the human's 2026-07-14 "move off pure client-side DefiLlama calls
toward our own data" directive. Leg 1 (059) built the static, trust-rail-filtered snapshot; this item
retains a slim history of that snapshot over time and computes per-pool KPIs from it. Phase 1 (a real
hosted DB — Turso/libSQL) stays BLOCKED on human-provisioned secrets and is deliberately NOT built here.

## Intuition
KPIs like "is this rate rising or falling?" and "how stable has this pool been?" need history — a single
current snapshot can't answer them. But we have no database and can't handle credentials in a loop. So:
keep the last 30 **slim** daily snapshots (`pool → [apyTotal, tvlUsd]`) as tiny committed JSON files,
and compute KPIs from that retained window in CI, writing the results back INTO the snapshot the FE
already reads. History is a git-committed time series; KPIs are derived numbers, never fabricated.

## The one real hazard, and how it's handled — the "churn trap"
The 059 generator writes `data/pools-snapshot.json` under a freshness gate: if today's fetch is
byte-identical (modulo timestamp) to what's committed, it writes nothing — no commit, no Vercel deploy
(the 2026-07-13 quota crisis). If a *separate* step (compute-kpis.js) writes a `kpis` object into that
committed file, the 059 generator's very next run would produce kpi-**less** content, see it differ from
the kpi-**enriched** committed file, and rewrite it — stripping the kpis — **every single run**. Infinite
daily churn = a daily deploy. The fix (criterion C1): teach the 059 generator's freshness comparator to
**ignore** the `kpis` object, so a kpi-enriched committed file still compares equal to a fresh kpi-less
generation when the underlying railed pools are unchanged. One regex, applied to both sides of the
compare. Independently proven on the real 717-pool dataset by both the builder and the verifier.

## What changed, in reading order

1. **`generate-pools-snapshot.js`** (+15/−2) — `normalizeSnapshotContent` gains one strip:
   `.replace(/,?"kpis":\{[^}]*\}/g, '')`. The `kpis` object is a flat single-level JSON object (numbers,
   null, and short date strings — no nested `}`), so `[^}]*` matches its whole body. Stripped from both
   sides of the freshness compare → the churn trap can't fire. All 9 existing `test_pools_snapshot.js`
   assertions pass unchanged.

2. **`compute-kpis.js`** (new, 316 lines, zero new deps, Node-18) — runs after the 059 step in CI:
   - **History append** (`appendHistory`, criteria A1–A4): builds a slim map `{poolId: [apyTotal,
     tvlUsd]}` from the current snapshot (`apyTotal = round((apyBase||0)+(apyReward||0), 4)`), and writes
     `data/history/<YYYY-MM-DD>.json` **only if that map differs from the most-recent retained point** —
     identical data day-over-day adds no file, no commit (081/083 discipline). Keeps the newest
     `HISTORY_RETENTION = 30`, prunes older (lexicographic on the fixed-width date name = chronological).
   - **KPI computation** (`computeKpis`, criteria B1/B3): for each pool, from its ascending-by-date
     series across the retained window:
     - `historyPoints` — count of retained points (track record length)
     - `firstSeen` — earliest date in the window (pool-age proxy)
     - `apyMomentum` — `round(latest − earliest apyTotal, 2)` pct-points; **null if <2 points**
     - `apyStdev` — population stdev of apyTotal; **null if <2 points**
     - `tvlTrend` — `round((latest − earliest tvl)/earliest, 4)`; **null if <2 points or earliest tvl 0**
     Null is honest ("no track record yet"), never a fabricated 0.
   - **Enrich + write** (`enrich`, criterion B2): writes the `kpis` object INTO the snapshot AND every
     per-chain/per-token slice (so 088 reads one file, whichever it opens), under its own all-or-nothing
     freshness gate. It **never filters, drops, reorders, or re-weights a pool**, and **never reads or
     relaxes the trust rails** — those are applied upstream by 059 and stay byte-untouched (criterion B3,
     grep-confirmed: rail constants appear only in comments). Pure core takes injected dates (no
     `new Date()` inside it) so tests are deterministic.

3. **`test_compute_kpis.js`** (new, 286 lines, 15 assertions) — slim/stdev/kpis math, null-safety,
   appendHistory freshness + 30-file pruning, enrich end-to-end (snapshot + slices gain kpis, pools not
   reordered/dropped), idempotency, missing-snapshot no-op, and the **churn-trap regression** (a
   kpi-enriched snapshot does NOT trigger a 059 rewrite). Added to `package.json`'s test chain after
   `test_pools_snapshot.js` (criterion E1).

4. **`.github/workflows/sitemap-update.yml`** (+7, criterion D) — new "Compute KPIs + retain history"
   step immediately after the 059 snapshot step (before the change/commit steps); `compute-kpis.js`
   added to the `push:` `paths:`. The existing `git add data` line already covers `data/history`, so the
   history point + enriched snapshot ride the existing daily commit — **no extra deploy**.

## Deviation worth knowing (from specs/087-notes.md)
Enriched `data/` artifacts are **not** committed in this PR — the pipeline is code + CI wiring + tests.
Merging to main pushes `compute-kpis.js` (now in the workflow `paths:`), which triggers
`sitemap-update.yml` → live fetch → snapshot → compute-kpis → committed. That keeps this PR focused
(no ~415-file kpi churn from a possibly-stale local snapshot) and lets the first history point carry
live numbers. 088 reads kpis once that run lands. First-day KPIs are honestly all-null (`historyPoints:
1`); the series and real deltas build from there.
