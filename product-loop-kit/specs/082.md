# Spec 082: Harden the planner against `translations is not defined` (funnel-top ReferenceError)

## Evidence
First-ever `error_occurred` event, live Mixpanel (defigarden 4042048), 2026-07-13T23:08:23:
- `error_type` = `ReferenceError`, `error_message` = `translations is not defined`, `error_context` = `global_error`, `can_recover` = true
- `error_stack` = `ReferenceError: translations is not defined\n  at https://www.defi.garden/planner.min.js:1:70405\n  at https://www.defi.garden/planner.min.js:1:70644\n  at Object.useMemo (https://www.defi.garden/react-dom.production.min.js:239:487)`
- `page_url` = `https://www.defi.garden/` (bare `/` → the **planner**, top of the `waitlist_submitted` funnel), Chrome / desktop / en-US
- Source: `planner.js:795` (`makeT()`): `var dict = (translations[lang] && translations[lang].planner) || translations.en.planner;` — also `translations.en.planner` at :796 and `rootT()` at :806/:808. All dereference the **bare global** `translations`.
- Load path (`home.html:143,164`): `translations.min.js` then `planner.min.js`, both `defer` (execution ordered). `translations` is normally defined before `planner.min.js` runs; the throw happens only when `translations.min.js` did not define the global by the time `makeT` runs (transient load failure, blocked/interrupted request, or deploy race). n=1 in the 07-13 window (~48 sessions).

## Hypothesis
We believe adding a defensive guard so the planner degrades gracefully when `translations` is unavailable — instead of throwing an uncaught `ReferenceError` inside `useMemo` — will eliminate this funnel-top error class and keep the planner rendering (English fallback) for the affected sessions. Confidence: **supported** (the stack trace names the exact line; the failure mode is a missing-global dereference).

## Change
Smallest version that removes the uncaught throw at the funnel top:
- In `planner.js`, make the `translations` global access resilient: reference it via a safe accessor (e.g. `typeof translations !== 'undefined' ? translations : (window.translations || <inline en fallback>)`) at the `makeT()`/`rootT()` sites (planner.js:795–808), so a missing/late global yields the English planner strings rather than a `ReferenceError`.
- Keep behavior byte-identical when `translations` IS defined (the normal path) — this is purely additive hardening.
- Regenerate `planner.min.js` (plan.html/home.html load the `.min` — the 061/068 caught-bug precedent: editing planner.js without regenerating the min ships nothing).
- **Out of scope:** changing the load order / making the script non-deferred; any translations.js content change; any EN/KO copy change (no user-facing string added, so this is not a translations-parity item — but if any fallback string is introduced it goes through translations.js EN+KO). Do NOT touch the analytics app (`app.js`) — the error is planner-only.

## Acceptance criteria
- [ ] `makeT()` and `rootT()` in `planner.js` no longer throw `ReferenceError` when the `translations` global is undefined at call time; they fall back to English planner strings and the planner still mounts.
- [ ] Behavior is unchanged when `translations` is defined: existing planner rendering + `test_planner.js` (208 asserts) stays green, plus `test_protocol_parsing.js` and `test_qualifier_fix.js`.
- [ ] New test proves the fallback: a case that invokes `makeT`/`rootT` with the global unavailable returns a usable English string instead of throwing (fixture-level is acceptable — this is a defensive unit path, not a render-behavior change).
- [ ] `planner.min.js` regenerated and committed in the same commit (matches `planner.js`; minify idempotence holds).
- [ ] Full `npm test` chain green in-sandbox (077 made test_smoke.js pass with the fixture-routing fallback).
- [ ] Instrumentation: no new event needed — success = `error_occurred` with `error_message="translations is not defined"` stops recurring. The existing global error handler (`analytics.js:589`) already reports it.
