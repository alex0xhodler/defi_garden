# 082 — Honest llms.txt freshness: content-derived timestamps so no-change CI runs stop committing

Promoted by the build loop 2026-07-14 (no READY items in BACKLOG.md). Source of
evidence: 081's verifier residual, recorded verbatim in the BACKLOG 081 row and
the LOG.md 2026-07-14 entry as "the next promotion candidate".

## Problem (documented evidence)

- `generate-llms.js` stamps unconditional wall-clock timestamps: `sourceTs =
  new Date().toISOString()` at line 177 (DefiLlama fetch time) and
  `updatedAt: new Date().toISOString()` at line 547, rendered into the output
  at three sites — `buildConcise` line 318 (`- Last Updated:`), `buildFull`
  line 418 (`- Last Updated:`) and line 420 (`- Data Sources: … (fetched: …)`).
- The daily CI (`.github/workflows/sitemap-update.yml`) gates its commit on
  **whole-tree** `git status --porcelain`. So even a run where NOTHING changed
  produces a diff in `llms.txt` + `llms-full.txt` (3 changed lines = 6 diff
  lines) and commits → **every daily run costs a Vercel deploy** (free-tier
  quota crisis, standing decision 2026-07-13).
- Live proof: commit `8fee9e9ba` (2026-07-14 04:50 UTC, 18 min after the prior
  run) — verifier-confirmed 1114/1120 changed lines were sitemap `<lastmod>`
  (fixed by 081) and the remaining 6 were exactly these llms timestamp lines.
  With 081 merged, `llms.txt`/`llms-full.txt` are now the ONLY unconditional
  churn left; until they're fixed, 081's "no-change run skips its commit"
  benefit never fires (081-pr.md states this honestly).
- Same dishonesty class as 081's lastmod: "Last Updated" claims fresh content
  daily even when the content is byte-identical — an AI-crawler freshness
  signal (llms.txt exists for AI assistants) that lies routinely is discounted
  the same way Google discounts lying lastmod.

## Change

In `generate-llms.js` only (no workflow change needed — once llms stops
churning, the existing porcelain gate skips the commit by itself):

1. Build the new file content exactly as today.
2. Before writing each file, compare the new content against the existing
   on-disk file **modulo the three volatile timestamp lines** (`- Last
   Updated: …` and the `(fetched: …)` value inside `- Data Sources: …`):
   normalize both sides by replacing those values with a placeholder.
3. If equal modulo timestamps → **skip the write entirely** (old file stays
   byte-identical, its committed timestamps preserved — honest "content as of"
   semantics, exactly 081's lastmod treatment).
4. If different (or no existing file / unparseable) → write with fresh
   timestamps, exactly today's behavior.
5. Log which path each file took (`unchanged — kept committed timestamps` vs
   `content changed — stamped <iso>`), so CI logs stay diagnosable.

Follow the repo's established pattern (080/081): export the new helpers via
`module.exports`, add a fixture-only unit test `test_llms_freshness.js` (no
network), append it to the `npm test` chain in `package.json`.

## Constraints

- No new dependencies. No changes to sitemap generators, the workflow, or any
  user-facing app surface (llms.txt is machine-facing — not a translations.js
  string).
- Content-building logic must NOT drift: given the same inputs, new output ===
  old output modulo the three timestamp lines.
- Keep the safe fallback: missing/unreadable existing file or absent timestamp
  lines → write fresh (pre-082 behavior), never crash the CI pipeline.
- `defiLlamaFetchedAt` may be null (fetch failure renders `unavailable`) — the
  normalizer must handle that line in both forms.

## Acceptance criteria

1. **Unit test** `test_llms_freshness.js` (fixture-only, no network) wired into
   `npm test`, covering at minimum: (a) new content equal-modulo-timestamps to
   the existing file → file NOT rewritten, byte-identical, old timestamps
   preserved; (b) a real content change (e.g. a URL added) → file rewritten
   carrying the new timestamp; (c) no existing file → written fresh;
   (d) existing file without recognizable timestamp lines → written fresh
   (fallback); (e) the `(fetched: unavailable)` form normalizes correctly.
2. **Mutation check** documented in notes: forcing the compare to always
   report "changed" (or always "unchanged") fails the test.
3. **Idempotency proof on real data** (network is open in-sandbox per standing
   decision 2026-07-12): in a scratch copy, run `node generate-llms.js` twice
   against the same committed baseline; the SECOND run leaves `git status
   --porcelain -- llms.txt llms-full.txt` EMPTY. (The first run may legitimately
   rewrite if live content differs from the committed snapshot — if it does,
   the diff must contain real content lines, not only timestamp lines.)
4. **No behavior drift**: on identical fixture inputs, new generator output ===
   old (HEAD) generator output modulo the three timestamp lines.
5. `npm test` chain green in-sandbox up to the documented pre-existing
   failures/timebox precedent (069/071/073/074/077 notes) — nothing NEW broken;
   all runs timeboxed to 5 foreground minutes.
6. No new deps in `package.json` (only the test-chain line changes).
