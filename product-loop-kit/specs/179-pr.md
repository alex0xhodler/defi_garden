# Item 179 — explainer (HIGH tier, full walkthrough + quiz)

Verifier: **PASS, 9/9 acceptance criteria, tier HIGH** (independently assigned; agrees with the spec's own
guess). Verifier ran its own mutations, distinct from the builder's, and checked the SEO-deletion trap on
both crawler paths itself.

## Goal

The two `/tokens` + `/chains` "hub" links — the internal-linking surface spec 045 exists to keep the 2,100+
generated SEO pages from being orphans — were **dead on one route and absent on another**:

- **bare `/`** (the default route, landing mode): the links appeared **twice** in the DOM and one copy could
  never be clicked.
- **`/plan.html`** (the planner, an indexed page at sitemap priority 0.9): the links did not exist at all.

## The intuition

There are two ways this app can put the hub links on a page:

1. a **static** `<footer class="seo-hub-links">` sitting in the raw HTML — this is the copy crawlers see
   without running any JS (spec 045);
2. the mounted React app's own `<footer class="app-footer">`, which is `position: fixed; bottom: 0`.

When a mode does *both*, the fixed footer physically covers the static one — so spec 086 hid the static copy
in that mode: `html[data-app-mode="analytics"] .seo-hub-links { display: none }`.

That rule **enumerates modes**. It named `analytics`, because in 2026 that was the only mode with its own
fixed footer. The 2026-07-15 landing pivot then gave landing mode its own `.app-footer` carrying the same two
anchors (`landing.js:356-367`) — and nobody extended the rule. The rule wasn't wrong; it was *incomplete*.

## Evidence, measured before any code changed

Real Chromium against bare `/`, served the way `test_footer_hub_links.js` serves it:

| | before | after |
|---|---|---|
| `a[href="/tokens"]:visible` on `/` | **2** | **1** |
| `a[href="/chains"]:visible` on `/` | **2** | **1** |
| `.seo-hub-links` computed `display` on `/` | `flex` | `none` |
| Playwright click on the **static** `/tokens` anchor | **`Timeout 3000ms exceeded`** (occluded) | n/a — superseded by design, as in analytics mode |
| `grep -c seo-hub-links plan.html` | **0** | **1** |

The click timeout is the proof, not a guess: Playwright refuses to click an occluded target, so the timeout
*is* the occlusion.

## What changed, in reading order

1. **`style.css:2580-2593`** — the 086 rule now matches landing too:
   `html[data-app-mode="analytics"] .seo-hub-links, html[data-app-mode="landing"] .seo-hub-links {display:none}`.
   The comment above it said *"Planner mode has no fixed .app-footer, so the static links stay visible"* —
   true when written, false about the default route since the landing pivot. Rewritten to state which modes
   render their own footer and which don't.
2. **`home.html:137-153`** — the byte-consistent twin of that rule. Item 131 inlined it as **render-blocking**
   critical CSS because `style.min.css` loads async (`media="print"` + `onload` swap), so the async copy
   cannot hide the static footer before first paint — that flashed a duplicate footer. Both copies must stay
   identical; both were edited, and the comment updated with them.
3. **`plan.html:96-112`** — the static crawler footer, markup identical to `home.html`'s, placed **outside**
   `#planner-root` so React never touches it. `plan.html` sets `window.__APP_MODE` but never the
   `<html data-app-mode>` attribute (the IA router never runs there), so the hide rule cannot match — the
   links stay visible and clickable, which is right, because the planner renders no footer of its own
   (`grep -c app-footer planner.js` = 0).
4. **`planner.js` (+24, one new `useEffect` in `Planner()`, keyed on `[lang]`)** — localizes those two anchors
   after mount so a `?lang=ko` planner doesn't show English link text. It uses the **existing**
   `footerBrowseTokens` / `footerBrowseChains` keys; no new translation keys.
5. **`test_footer_hub_links.js` (+122)** — five new rendered cases (A1, A2, A5, A6, A7). All six pre-existing
   cases still pass with their assertions unchanged in meaning; only their header documentation changed,
   because it claimed `/plan.html` never carries this markup — now false.
6. **`style.min.css`, `planner.min.js`** — regenerated by `npm run minify`. The pages load the minified
   assets; skipping this would ship a fix the browser never sees. The other five minified outputs regenerate
   byte-identically (their sources were untouched), and the verifier re-ran `npm run minify` itself and
   `md5sum -c`'d all seven to prove the committed assets reproduce from source.

## The deviation from the spec, disclosed

The spec said to localize via planner.js's existing `t()`. `t()` (`makeT`) only reads
`translations[lang].planner`, and these two keys live under `translations[lang].landing` — so
`t('footerBrowseTokens')` would have **key-echoed the literal string**, in EN and KO alike. Fixed by reading
`translations[lang].landing` directly with the same `tr.en` fallback shape `makeT`/`rootT` already use, inside
`try/catch` with null guards. The KO acceptance case (A7) caught this on the first real test run before it was
found by hand — recorded in `179-notes.md` so the mechanism is visible, not just the outcome.

## Why this is not SEO deletion (the NEVER-list check)

`display: none` does not remove DOM nodes. Non-JS crawlers never receive `data-app-mode` (the router sets it
at runtime), so the raw anchors remain in the served source of both files — asserted at fs level (A3, A6) and
in the DOM (case b2). A JS-executing crawler renders landing mode and sees the same two anchors **visible**
inside `.app-footer` (case b). Both paths keep the links, so no internal link is lost on any path. The
verifier re-derived both halves independently before agreeing this is off the NEVER list.

## Non-vacuity

Three mutations by the builder, two more by the verifier using different mechanisms (mutating only
`home.html`'s inline copy; renaming the `plan.html` class rather than deleting the block). Every mutation
reddened exactly the cases it should and nothing else; every restore was md5-verified.

| mutation | reddened |
|---|---|
| revert the landing selector in both files + re-minify | A1, A2 only |
| revert **only** `home.html`'s inline copy (verifier) | A2 only — A1 stayed green via the post-swap `style.min.css` |
| delete the `plan.html` footer block | A6, A5 (+A7 as a side effect) |
| rename the `plan.html` class to `…-DISABLED` (verifier) | A5, A7 — A6 correctly stayed green (it asserts anchors, not the class) |
| force the KO lookup to read EN | A7 only |

## Risk tier: HIGH

199 changed lines (176 + 23) against LOW's 150-line cap, and `home.html` is on NORTH_STAR's explicit HIGH
list, and the change alters what renders on the default route. Not NEVER-list (no rail, no credential/money,
no de-indexing).

## Left undone, deliberately

The BACKLOG row's second half asked whether to *keep* the duplication instead. The precedent (analytics),
the crawler-reachability argument, and "a permanently unclickable element is the defect" all point one way,
so leg A ships hidden — and it is one selector in two places if you want it back. `home.html`'s own static
footer is left unlocalized: it is hidden in every mode that renders it, so localizing it would be dead code.
