# Spec 214: snapshot-first paint for snapshot-present `?pool=` arrivals

## Evidence
<!-- heartbeat 2026-08-03, signals/2026-08-03.md -->
- `app.js:1144` — `const snapshotEligible = !urlParams.pool && urlParams.minTvl >= DEFAULT_MIN_TVL;` —
  every `?pool=` arrival is excluded from the snapshot-first path unconditionally, even when its pool IS
  in `data/pools-snapshot.json`, and blocks its first paint on the multi-MB live
  `yields.llama.fi/pools` fetch.
- `app.js:1253-1273` (item 105) then fetches `/data/pools-snapshot.json` on that same arrival ANYWAY —
  post-render, to merge kpis. The instant-paint payload is already being downloaded; it just arrives too
  late to paint from.
- Measured 2026-08-03 (query `4b3dab02`): prod `page_view` **07-29 = 1** on
  `/?token=USDC&chain=Popular&pool=4438dabc-7f0c-430b-8136-2722711ae663` — a pool present in the
  committed snapshot (≥$10M) and linked from `tokens/usdc.html` — with `pool_view` for that URL **absent
  (0)**, and prod-wide `pool_view` = 0 that day. The arrival never saw a rendered pool detail.
- Population: 420 of 3,658 estate deep-linked ids are snapshot-present (11.5%); grid-origin
  share/bookmark `?pool=` URLs are ~always snapshot-present (default grid renders only ≥$10M pools).

## Hypothesis
We believe letting a snapshot-present `?pool=` arrival paint from the committed snapshot first (live
refresh continuing exactly as the snapshot path already does) will stop losing arrivals during the
blocking live fetch, because the one such arrival on record left before that fetch resolved.
Confidence: **guess** on the user-harm link (n=1 — could have been a JS-running crawler); the mechanism
(blocking multi-MB fetch on a page whose data is already committed same-origin) is measured fact.

## Change
Smallest version: in `fetchPoolsInBackground()` (app.js:1138-1156), make `tryLoadSnapshot()` eligible
when `urlParams.pool` is set, and have it fall through to `loadLive()` (today's exact path) when the
requested pool id is NOT in the snapshot payload (or the snapshot is stale per the existing
`SNAPSHOT_MAX_AGE_MS` gate, or the fetch fails — all existing degrade paths unchanged). The `minTvl`
eligibility conjunct stays for non-pool arrivals. Sub-rail arrivals take today's path byte-identically.
OUT of scope: any change to `pool_view`/`pool_click` timing or semantics (the metric definition is
human-owned — NORTH_STAR "Denominator caveat"); any change to trust rails, the 105 kpi merge, the
`?token=`/`?chain=` grid paths, or prefetching beyond what both paths already fetch.

## Acceptance criteria
- [ ] Rendered Playwright (house fixture pattern, fresh-`generatedAt` meta per `product-audit.md` trap 1):
      a `?pool=<snapshot-present id>` arrival renders pool-detail WITHOUT any request to
      `yields.llama.fi/pools` completing (route it with an indefinite delay; the page must still paint
      from `/data/pools-snapshot.json`).
- [ ] Same harness, `?pool=<id absent from snapshot>`: the live fetch IS made and the page renders
      exactly as today (fixture-served live shape) — including the dead-pool empty state for a dead id.
- [ ] Stale snapshot (`generatedAt` older than `SNAPSHOT_MAX_AGE_MS`): pool arrival falls through to
      live, as the non-pool path does today.
- [ ] `pool_view` fires exactly once per pool-detail render on BOTH paths (existing
      `test_northstar_cta_fires.js` passes unmodified; no double-fire when live refresh follows a
      snapshot paint — if the implementation refreshes, it must not re-emit `pool_view`).
- [ ] Trust rails byte-untouched: `APY_SANITY_LIMIT`, `DEFAULT_MIN_TVL`, anomaly demotion logic
      unchanged (grep-diff).
- [ ] Tests: new cases registered in `package.json` `test:serial` (run-tests.js does not glob).
- [ ] Instrumentation: existing `data_load_time` perf event distinguishes `source: 'snapshot'` vs
      `'live'` on pool arrivals (assert it reports `snapshot` on the new path). **Correction
      (attempt 2, verifier finding):** the parenthetical this criterion originally shipped with —
      "it already carries `source`" — was false. It was the spec author's unverified assumption;
      `analytics.js`'s `trackPerformance()` silently dropped `context.source`/`context.pools_count`
      before they ever reached the tracked payload, for every `data_load_time` event ever emitted.
      See Territory notes below. The criterion's *intent* (the delivered event distinguishes
      source) is unchanged and is what attempt 2 made true.

## Territory notes
<!-- Build loop appends findings from the blindspot pass here. -->
- **Attempt 2 (verifier finding, fixed this item):** `analytics.js`'s `trackPerformance(metric,
  value, context)` (analytics.js:352-361 pre-fix) forwarded only `metric_name`, `metric_value`,
  `metric_category`, `page_context` (from `context.page`), `connection_type`, `is_slow_device`
  into the tracked `performance_metric` payload. `context.source` and `context.pools_count` —
  which both `app.js` `data_load_time` call sites (`loadLive`, `tryLoadSnapshot`) have always
  passed — were silently dropped before reaching `Analytics.track`/Mixpanel. This affected
  EVERY `data_load_time` event ever emitted, not just the pool-arrival path this item adds.
  AC7 could not be true without fixing this, so it was fixed here, additively (explicit
  `source`/`pools_count` forwarding, only when present — never a wholesale `context` spread).
  Blast radius checked: `trackPerformance(` has exactly 3 hits repo-wide (excluding
  node_modules/min/compiled) — the definition and the two `app.js` call sites — so this is a
  contained, in-scope fix, not scope creep beyond what AC7 requires.
