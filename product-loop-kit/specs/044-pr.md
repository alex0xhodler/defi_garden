# 044 — PR explainer (HIGH tier, per NORTH_STAR.md pre-merge requirement)

## Goal
Spec 044 asked: is the SEO-surface analytics instrumentation shipped by
items 039 (`page_view` on ~2,045 `/tokens/*` pages + ~88 `/chains/*` pages)
and 020 (`pool_view source=url_direct` on `?pool=` deep links) actually
firing in a real browser, or are the 14-day Mixpanel zeros
(`signals/2026-07-12.md`) just "no organic traffic yet, GSC indexing takes
2–6 weeks"? Both 039 and 020 shipped verifier-PASS on **fixture-string
assertions only** — the generated HTML was grepped for the right function
call text, but no test had ever loaded a generated page (or a `?pool=`
landing) in a real browser and watched whether the tracking call actually
executed. That's the same class of gap 017's post-mortem flagged: fixtures
passing while the product itself stays broken.

## Intuition
A Playwright test that grep's the HTML string `Analytics.trackPageView(...)`
only proves the *text* is present in the file — it says nothing about
whether that code path is reachable at runtime. The only way to know if an
event actually fires is to load the real page in a real browser and watch
for the real function call. So the fix for this item was, first and
foremost, to build that missing observation tool — and only *then* find out
whether there was anything to fix.

## What changed and why (diff in reading order)

1. **`test_analytics_fires.js` (new file).** Renders one real generated
   `/tokens/<slug>` page (via `generate-token-pages.js`'s own
   `renderTokenPage()` — the exact function the live generator uses, not a
   hand-written HTML stand-in) in headless Chromium, patches
   `Analytics.track` before any page script runs (`page.addInitScript`), and
   asserts exactly one `page_view` call fires with the right `path` and
   `page_type`. Run against the **unmodified** generator, this test failed:
   zero events captured. That's the finding — not a traffic problem, a
   wiring problem.

2. **Root cause, found by reading `renderAnalyticsBootstrap()` in
   `generate-token-pages.js`:**
   ```js
   if (window.Analytics && typeof Analytics.trackPageView === 'function') {
     Analytics.trackPageView(...)
   }
   ```
   `analytics.js` declares `const Analytics = {...}` at the top level of a
   plain `<script defer src="analytics.js">` (a *classic*, non-module
   script). In JavaScript, a top-level `const`/`let` in a classic script
   creates a binding in the shared **global lexical environment** — visible
   to *later* classic `<script>` tags on the same page as a bare
   identifier — but it does **not** become a property of the `window`
   object (only `var` and function declarations do that). So
   `window.Analytics` was `undefined` on every single generated page, the
   `if` guard was always `false`, and `Analytics.trackPageView` never ran —
   regardless of traffic. (`app.js` calls `Analytics.trackPageView`
   unguarded, as a bare identifier, which is why the app's own page views
   tracked fine on `/` — this bug only lived inside the generator-injected
   bootstrap's own defensive check.)

3. **`generate-token-pages.js` and `generate-stories.js`** (one line each):
   changed the guard to `typeof Analytics !== 'undefined' && typeof
   Analytics.trackPageView === 'function'`. `generate-chain-pages.js`
   imports `renderAnalyticsBootstrap` from `generate-token-pages.js` rather
   than defining its own copy, so `/chains/*` and the `/tokens`, `/tokens/az/*`
   hub pages are fixed transitively by the same one-line edit.

4. **`package.json`**: appended `test_analytics_fires.js` to the `npm test`
   chain so this class of bug gets live-render coverage going forward.

## Deviations from spec
Spec 044's own contingency (line 19) said: if the live render shows an
event does NOT fire, fixing the wiring becomes the real work of this item,
scoped to `generate-token-pages.js` and/or `app.js`'s `?pool=` effect. That
triggered for the `page_view` half only — `pool_view(source=url_direct)`
was already live-render-verified sound by an existing `test_search.js`
check from item 020, rerun standalone and still green. No other deviation.

## Residual (not fixed by this PR, documented and out of scope)
- The ~2,133 already-committed `tokens/*.html`/`chains/*.html` files still
  carry the broken guard until regenerated. `.github/workflows/sitemap-update.yml`
  triggers on push-to-main touching `generate-token-pages.js`/
  `generate-chain-pages.js` and will regenerate + commit real pages with
  the fix on its next run — this sandbox can't reach `yields.llama.fi` to
  do that regen itself (same constraint every prior SEO item hit).
- `stories/*.html` (3 files) predate item 039 entirely — no analytics
  bootstrap in them at all yet, confirmed by grep. No CI workflow
  regenerates `stories/`; `generate-stories.js` has no offline/fixture
  mode, so it can't run in this sandbox either. Its source now carries the
  same fix; needs a manual `node generate-stories.js` run (with network)
  by a future loop or human.
