**What is claimed:** 08-07's entire engagement set originates from one non-datacenter region on
operator-class devices, on the day the operator shipped four PRs, and **the loop has no instrument that can
separate operator traffic from a genuine Utrecht visitor.** That inability is the finding; the attribution
is the motivating instance. Either reading leaves n=1, far below the ≥30 rule, so no gate opens today.

## Hypothesis

We believe attaching a persisted `insider` flag to every event, and subtracting that population by name in
every gate read, will make gate counts mean what they claim, because the loop's own shipping activity
generates exactly the traffic shape that passes every existing real-user test — and the more the loop
ships, the more contaminated its measurements become. Confidence: **supported**. It pays off in every
future where traffic ever arrives (the count is only ever wrong in the optimistic direction without it),
and it pays off immediately by making today's zero defensible rather than argued. Its payoff does **not**
depend on any unobserved condition, which is why it is scored rather than filed `GATED`.

- **Instance of:** visits that carry **no information we did not already have**. Crawlers fail this
  predicate for want of intent; insiders fail it because we already knew they were looking. The playbook
  currently has a rule for the first and nothing for the second — this predicate is strictly weaker than
  the crawler rule and **contains** it (RAZOR: adopt the hypothesis with the largest extension).
- **Class closed by this item: no.** The flag covers the operator on devices they mark. It does not cover
  an unmarked device, a teammate, or a contractor. Number left open: unbounded and unmeasurable by
  construction — which is why the flag is paired with the geo/device forensic step now written into the
  playbook, and why the acceptance criteria require the *residual* to be reported with a number each tick
  rather than assumed zero.

## Change

Smallest version that tests the hypothesis:

1. **`analytics.js`** — on load, if the URL carries `?insider=1`, persist a flag to `localStorage`
   (alongside the existing `theme` / `defi-garden-lang` / `garden-plan` conventions); if the flag is
   present, attach `insider: true` to the base context that `analytics.js` already builds and stamps onto
   **every** event (the same mechanism that carries `src`/`utm` — `analytics.js:32-56`). Provide
   `?insider=0` to clear it. Events from unmarked visitors carry no `insider` property at all, exactly as
   `src` behaves today — do **not** stamp `insider: false`, which would change the shape of every event
   for no gain.
2. **`playbooks/traffic-quality-classification.md`** — already updated by the 2026-08-08 heartbeat with the
   unifying predicate and the geo/device step; this item adds the query recipe for the filter once it
   exists.
3. **No UI.** No toggle, no banner, no settings entry. The flag is set by visiting a URL once per device.

**Explicitly OUT of scope:** IP allow/deny lists (needs credentials and infrastructure — NEVER-list);
a Mixpanel cohort created through the API (org-admin action, human-owned); any change to what is tracked
for ordinary visitors; retroactive relabelling of the 08-07 events (they stay in the data; the snapshot and
the playbook carry the classification).

## Acceptance criteria

- [ ] Visiting any page with `?insider=1` persists the flag, and **every** subsequently tracked event —
      not just `page_view` — carries `insider: true`. Assert this on **both** router paths (planner-mode
      `/` and analytics-mode `/?token=…`), because `trackPageView` is called only from `app.js` and a
      planner-only or analytics-only check would repeat the 2026-08-02 `src` instrument error verbatim.
- [ ] `?insider=0` clears the flag; subsequent events carry no `insider` property.
- [ ] A visitor who never passes the param produces events with **no** `insider` key (assert absence, not
      `false`).
- [ ] The flag survives a reload and a navigation between the two router modes.
- [ ] Tests: a rendered-Playwright test in the established fixture-routing style (external HTTPS is
      sandbox-blocked; follow `test_analytics_acquisition.js` / `test_analytics_src_attribution.js`, which
      already assert base-context stamping), registered in `test:serial` — an unregistered test file is the
      `test_test_registry.js` failure this repo has already hit once. Plus the NORTH_STAR-mandated
      `node test_planner.js && node test_protocol_parsing.js && node test_qualifier_fix.js`. Exit codes read
      **without a pipe**.
- [ ] Instrumentation: event property `insider` = `true` fires on **every** event emitted by `analytics.js`
      on **both** router paths, for a visitor who has set the flag; absent otherwise.
- [ ] Non-vacuity: remove the base-context stamping line → the test must go RED for both router paths;
      restore, confirm `md5sum analytics.js` byte-identical, re-run green. Separately, break only the
      persistence (never write to `localStorage`) → the reload assertion must go red on its own; a single
      assertion that passes with either half removed is two guards masking each other (item 166's lesson).
- [ ] Population: the test enumerates the events `analytics.js` can emit from the source at test time and
      asserts the property on each, rather than checking one hand-picked event. A check that only ever sees
      `page_view` is blind to exactly the planner-bound path this item exists to measure.
- [ ] `NORTH_STAR.md`'s north-star definition and this repo's gate language gain the word **real** meaning
      "not crawler-classified **and** not `insider`" — documented in the item's notes so the next heartbeat
      reads gates the same way.

## Measurement

Metric: the **integrity** of both north-star legs — this item does not move a funnel, it makes the funnel
counts honest. The observable it changes: every future signals snapshot can state
"N sessions, of which M insider, K crawler, **R real**" with R derived from a property rather than from a
regional forensic argument.
Gate: this item's own build leg is calendar-verified (does the property fire, on both paths, for a marked
device — provable in-session). Its **value** leg opens the first time the operator visits prod after ship:
≥1 event carrying `insider: true` in Mixpanel proves the instrument non-vacuously, and that is the
positive control this repo requires before any zero is read as health (LEARNINGS 2026-07-27).
Backstop: if no `insider: true` event is ever observed within 60 days of ship, close **UNEXERCISED** — and
treat that as a finding about the instrument, not about the operator.
Decision rule: keep if the property fires on both router paths and persists; revert-candidate if it alters
any existing event's shape for unmarked visitors.

## Risk tier (builder's guess — verifier assigns independently)

**LOW.** NORTH_STAR's LOW fast lane names *analytics instrumentation* explicitly; the change is additive
(one persisted flag, one property on an existing base context), touches no trust rail, no `__APP_MODE`
router logic, no parameterized-URL behaviour, no generated SEO surface, and adds no dependency. Expected
diff well under 150 lines.

**Two things that would make the tier wrong, flagged for the verifier:** `analytics.js` is loaded
`defer` in the `<head>` of **both** `home.html` and `plan.html` *before* `planner.js`/`app.js` (CLAUDE.md
records that this ordering was deliberate and that reverting to dynamic injection raced the planner's first
tracking call) — if the builder moves or re-orders that tag, the tier is HIGH and the change is out of
scope. And a new query parameter must not disturb the IA router: `home.html:79` decides mode via
`ANALYTICS_PARAMS.some(k => params.has(k))`, so `insider` must not be added to `ANALYTICS_PARAMS` or
`PLANNER_PARAMS` — verify `/?insider=1` still lands on the planner and `/?token=USDC&insider=1` still lands
on the analytics grid.

## Territory notes
<!-- Build loop appends findings from the blindspot pass here. -->

- **Non-vacuity isolation forces an implementation detail the spec text
  doesn't mention.** The spec's Change section says only "attach `insider:
  true` to the base context ... if the flag is present," but acceptance
  criterion (b) requires that breaking ONLY the localStorage write leaves
  the immediate-marking assertions green while failing ONLY the
  persistence-dependent ones. That's impossible if presence is determined
  by a single `localStorage.getItem` read on every call — the very first
  write-then-read on the marking page would also break. The build adds an
  in-session override (`Analytics._insiderOverride`, set directly from the
  CURRENT load's `?insider=` param, read before falling back to
  localStorage) purely to make this isolation provable. Worth stating
  explicitly in future specs that ask for two independently-provable halves
  of one feature: the requirement itself dictates that the read path can't
  be a single storage lookup.

- **A pre-existing test-harness race, not caused by this item, will bite the
  next test that hard-requires `session_start`.** The established
  `neutralizeHostGate()` pattern (used across `test_analytics_src_attribution.js`,
  `test_analytics_host_gate_render.js`, and now `test_analytics_insider.js`)
  patches `Analytics.isProductionHost` via an `addInitScript`
  `setTimeout(install, 0)` poll, because `const Analytics = {...}` is a
  lexical binding (not a `window` property) and so can't be pre-patched with
  `Object.defineProperty`. `session_start` fires from the page's own `load`
  listener — the earliest possible page-lifecycle hook — and on some runs
  wins the race against that poll, so `track('session_start', ...)` hits its
  normal, correct, spec-096 early return (host still reads as non-production
  at that instant) and the call never reaches the mixpanel stub queue. This
  reproduced in 3/5 raw runs before this test was adjusted to treat
  `session_start` as opportunistic rather than required — `waitlist_opened`
  and `page_view` never raced because they fire from React mount/effect
  passes well after the patch lands. No fix attempted here (belongs in the
  shared harness pattern, not in `analytics.js` or in one test file) — flagged
  for whoever next needs `session_start`'s properties asserted, not just its
  presence as a readiness poll target.

- **`data/pools-snapshot-meta.json`'s committed `generatedAt` was already
  ~6h38m old at build time** (repo clock 2026-08-10T15:44Z vs. snapshot
  2026-08-10T09:06Z), i.e. already past the `SNAPSHOT_MAX_AGE_MS` 6h
  threshold in `app.js` — meaning the analytics-mode test scenario would
  have fallen through to the live `yields.llama.fi` fetch regardless. The
  test still explicitly forces a stale `**/data/pools-snapshot*` fixture
  (mirroring `test_search.js`'s established pattern) so it stays
  deterministic across future re-runs regardless of when the committed
  snapshot was last baked — not something future builders should rely on
  the ambient snapshot age to get right by accident.
