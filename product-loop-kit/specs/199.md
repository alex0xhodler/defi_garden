# Spec 199: the 360px / dark / Korean lenses on the north-star surface have only ever seen ONE hardcoded pool

## Evidence (all measured in-repo, this session, before any change)

The pool-detail page is the north-star surface (NORTH_STAR.md 2026-07-23: `pool_click{garden_cta}` +
`pool_click{protocol_link}`). Three items in a row fixed *coverage* of it:

- **183** fixed **which** pool-details get audited (never-audited-first rotation).
- **191** fixed **how many** (2 → 6 per tick).
- **192** fixed **how many, honestly** (6 → 32, bounded by the clock instead of a constant; measured
  116s against the 300s cap, ~0.19s marginal per rendered pool-detail).
- **196** applied the same never-audited-first memory to the static estate.

The dimension none of them touched is **which lens**. `audit-app.js:3462-3489` builds the surface list:

```js
const poolUrl = `/home.html?pool=${encodeURIComponent(poolId)}`;   // poolId === anchorPoolId
  { name: 'pool-detail',      url: poolUrl,                width: 1280 },
  { name: 'pool-detail-360',  url: poolUrl,                width: 360  },
  { name: 'pool-detail-dark', url: poolUrl,  width: 1280,  dark: true  },
  { name: 'pool-detail-ko',   url: `${poolUrl}&lang=ko`,   ko: true    },
```

and `audit-app.js:2524` resolves that anchor to a **hardcoded constant**:

```js
const PREFERRED_POOL_ID = '747c1d2a-c668-4682-b9f9-296708a3dd90';   // audit-app.js:152
let anchorPoolId = PREFERRED_POOL_ID;                              // audit-app.js:2524
```

Every **rotated** pool-detail is built at one lens only — `audit-app.js:2640`:

```js
extraSurfaces.push({ name: `pool-detail:${poolIdPrefix(id)}`, …, width: 1280, poolId: id, rotationPick: true });
```

no `width: 360`, no `dark`, no `ko`, no `&lang=ko`.

**Committed proof** (`product-loop-kit/signals/audit-findings.json`, generated 2026-07-31, 29 surfaces):

```
pool-detail, pool-detail-360, pool-detail-dark, pool-detail-ko,      <- all four = anchor 747c1d2a
pool-detail:201e5f6e, pool-detail:25171c4c, pool-detail:aa3b8470     <- rotated: 1280px / light / EN only
```

**The population.** `data/pools-snapshot.json` = 737 pools ⇒ ~734 rotation candidates (anchor + promoted
excluded). At `DEFAULT_POOL_SAMPLE = 32` a full 1280px pass takes ~23 ticks. For the **360px, dark and
Korean lenses the pass never completes at all**: 733 of 734 pools have a **0% chance, on every future
tick, forever** of being rendered at 360px, in dark mode, or in Korean. The checks exist and run — checks
7 (`responsive`, `audit-app.js:3319-3331`: horizontal body scroll, zero-area/ancestor-clipped CTA box) and
the KO `i18n` check (`audit-app.js:3112`) — they are simply pointed at a single 2026-vintage constant.

**Why this is the class the mandate names.** NORTH_STAR.md's 2026-07-23 pre-traffic mandate lists the bug
classes the human keeps finding by hand: *"…format/i18n bugs, dead CTAs, responsive/dark"*. Those are
exactly the checks whose sample size is 1. And `LEARNINGS.md` (2026-07-30) states the generalisation test
this item is an application of: *"if this exact defect appeared in a different member of the same
population tomorrow, would anything catch it?"* — for a 360px clip or a KO leak on any pool but
`747c1d2a`, the answer today is **no**.

**Timing headroom is already measured, by 192, on this exact machine class**: 116s used of the 300s cap,
~0.19s marginal per rendered pool-detail. This item spends a small, bounded slice of the remaining 184s.

## Hypothesis

We believe **giving the existing pool-detail rotation a lens dimension** will **make responsive/dark/KO
defects on non-anchor pool-details reachable at all (from 1 pool to 1 + N per tick, cycling)** because
**the lens machinery already exists per-surface (`width` / `dark` / `ko` flags, honoured by the shared
render path) and the only thing missing is emitting the extra surface entries.** Confidence:
**validated-pattern** — this reuses the anchor block's own four-lens shape and 183/191/192/196's rotation
machinery verbatim; no new check, no new detector, no new product code.

Pre-traffic quality mandate: loop tooling on the north-star surface. **No isolable Mixpanel funnel
metric** (0 traffic; same disclosure pattern as 183/191/192/196). Measurement is (a) the surfaces actually
appearing in a real run's `surfacesCovered`, and (b) whether the next ticks originate any finding that was
structurally unreachable before.

## Change

**One file changes: `audit-app.js`.** Plus one new test file and its `package.json` registration. **No
product code. No CSS, no translations, no compiled/minified asset, no new dependency.**

### 1. Lens surfaces, additive, in `buildPoolSurfaces()`

After the existing `rotationPicks` loop (`audit-app.js:2639-2641`, which stays byte-unchanged), append
lens surfaces for the **first `lensSample` rotation picks**, one lens each:

| field | value |
|---|---|
| `name` | `pool-detail:<8-char prefix>@360px` \| `@dark` \| `@ko` |
| `url` | same pool url; the `@ko` variant appends `&lang=ko` (mirrors the anchor's `pool-detail-ko`) |
| `kind` | `'pool'` (same shared render path, same checks) |
| `width` | `360` for `@360px`, else `1280` |
| `dark` / `ko` | `true` on the matching lens only |
| `poolId` | the full id (192's rule: never re-derive from the prefix) |
| `lensPick` | `true` — **a new marker, NOT `rotationPick`** (see §3) |

Lens surfaces are built ONLY from `rotationPicks` — never from `promotedIds` (prescan-promoted surfaces
must stay exactly as 192 left them) and never from the anchor (already four-lens covered).

### 2. Which lens, and it must move across ticks

`LENSES = ['360px', 'dark', 'ko']` (fixed order, module-level). For the i-th lens-sampled pick:

```
lens = LENSES[(i + tickOffset) % LENSES.length]
```

where `tickOffset` is derived deterministically from the SAME seed the rotation already uses
(`opts.poolSeed || opts.staticSeed || AUDIT_STATIC_SEED || defaultStaticSeed()`, i.e. date-derived by
default) through the file's existing string-hash helper — so a run is reproducible for a given seed
(`test_audit_app.js`'s determinism contract), and yet the lens assigned to a given position **changes from
day to day**, so re-picked pools accumulate different lenses over cycles rather than always getting the
same one.

### 3. Budget, ceiling, kill switch — same conventions as every other knob in this file

```js
const DEFAULT_POOL_LENS_SAMPLE = 6;   // lens surfaces per tick
const MAX_POOL_LENS_SAMPLE     = 24;  // ceiling on the env override
```

`AUDIT_POOL_LENS_SAMPLE` (env) / `opts.poolLensSample` override, clamped to `[0, MAX_POOL_LENS_SAMPLE]`;
**`0` disables the leg entirely** and the run is then byte-identical in surface list to today's. The
effective count is additionally clamped to `rotationPicks.length` (never more lens surfaces than pools
picked).

`DEFAULT_POOL_LENS_SAMPLE = 6` is chosen against 192's own measurement: 6 × ~0.19s ≈ ~1.2s marginal on a
116s/300s run. Document that arithmetic in the constant's comment, the way 191/192 documented theirs.

### 4. The bookkeeping that must NOT move (this is where the item can go wrong)

- **`rotationPick` semantics.** `renderedRotationCount` (`audit-app.js:3634`) and the throughput line
  (`:3879`) count `rotationPick` surfaces and divide `candidateCount` by them. A lens surface is a
  **second render of an already-counted pool** — if it carried `rotationPick` it would inflate the
  coverage number the whole 192 item exists to keep honest. Hence the separate `lensPick` marker.
- **`seen` / `thisRunPoolIds` (`audit-app.js:2646`) stays byte-unchanged.** Lens surfaces introduce no new
  pool ids, so rotation memory and `cycle` advance exactly as today.
- **The time-budget guard (`audit-app.js:3632-3641`) must skip lens surfaces too.** Extend the guard's
  eligibility to `s.rotationPick || s.lensPick` so a slow run sheds lens renders as well; count skipped
  lens surfaces in a **separate** counter, never in `skippedRotationIds` (which feeds 192's `seen`
  reconciliation — a lens skip must not strip a pool from `seen`, because the pool WAS rendered at 1280px).
- **`opts.only` filtering (`audit-app.js:3512`) is name-based** and keeps working unchanged; a caller that
  names only `pool-detail` still gets exactly that surface.
- **No existing surface renames or changes position.** Lens surfaces append after the rotation picks
  inside `extraSurfaces`, so every name already in `surfacesCovered` keeps its exact relative order
  (167/183/192's standing constraint).

### 5. Report what it did

- `poolRotation` gains additive fields only: `lensSampleSize`, `lensRendered`, `lensSkipped`, `lenses`
  (the `{poolIdPrefix: lens}` map actually emitted). Existing fields keep their exact meaning.
- The CLI summary prints one extra line, e.g.
  `[audit] pool lenses: 6 rendered (360px x2, dark x2, ko x2) over 6 rotation picks, 0 skipped` — and says
  `disabled` when the sample is 0, never a silent absence.

## Acceptance criteria

1. **A real `node audit-app.js` run in this session** (timeboxed to 5 foreground minutes) completes with
   exit code unchanged in meaning and its `surfacesCovered` contains **≥1 `pool-detail:<prefix>@360px`,
   ≥1 `@dark` and ≥1 `@ko`** entry — pasted verbatim into `199-notes.md`, not summarised.
2. That same run's elapsed time is **stated in seconds** and is **under the 300s cap**, with the
   before/after delta against a same-session `AUDIT_POOL_LENS_SAMPLE=0` run.
3. `AUDIT_POOL_LENS_SAMPLE=0` produces a surface list **identical to `origin/main`'s** for the same seed
   (proven by comparing `surfacesCovered` arrays, not by assertion in prose).
4. `poolRotation.renderedCount`, `.truncated`, `.picked`, `.candidateCount` and the committed
   `audit-rotation.json` `seen`/`cycle` semantics are **unchanged** by the lens leg: same seed + same prior
   state ⇒ same values with the leg on and off.
5. New `test_audit_pool_lens.js`, wired into `package.json`'s `test:serial` chain immediately after
   `test_audit_static_rotation.js`, asserting at minimum: (a) lens surfaces exist with the three lens
   shapes and correct `width`/`dark`/`ko` flags and the `&lang=ko` url; (b) `lensPick` set and
   `rotationPick` NOT set on them; (c) sample clamped by `MAX_POOL_LENS_SAMPLE` and by
   `rotationPicks.length`; (d) `AUDIT_POOL_LENS_SAMPLE=0` ⇒ zero lens surfaces; (e) lens assignment varies
   across two different seeds while staying deterministic per seed; (f) `seen`/`renderedCount` unaffected.
6. **Non-vacuity, demonstrated not asserted**: the builder mutates its own change (e.g. drops the `ko` lens
   from `LENSES`, or sets `rotationPick: true` on lens surfaces) and shows the new test going RED, then
   restores byte-exact. Recorded in `199-notes.md`.
7. `git diff origin/main --stat` touches **only** `audit-app.js`, `package.json`, `test_audit_pool_lens.js`
   and `product-loop-kit/` bookkeeping. Zero lines in any product file (`app.js`, `PoolDetail.js`,
   `planner.js`, `home.html`, `style.css`, `translations.js`), zero trust-rail lines
   (`APY_SANITY_LIMIT`, `DEFAULT_MIN_TVL`, anomaly demotion, degen haircut), no new dependency.
8. Plain lane (`npm run test:fast`) green, or any red proven **pre-existing** on an `origin/main` baseline
   per `playbooks/pre-existing-red-triage.md` — stated, never implied.
9. **If the run originates new findings** (the point of the item), they are reported honestly in
   `199-notes.md` with their severity, and if any is P0/P1 the item says so plainly rather than burying it
   — a real defect found on a lens is a success of this item, and a new blocking finding is a **stated
   cost**, in 192's precedent.
