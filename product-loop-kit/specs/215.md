# Spec 215: run the pool prescan over the union population the rotation already draws from

## Evidence
<!-- heartbeat 2026-08-03, signals/2026-08-03.md -->
- This tick's audit run: `poolPrescan.candidates = 734` (snapshot-only) while the rotation population is
  `snapshot=734, deep-linked-live=3230, union=3964, reachable=3962` (206, shipped 2026-08-02).
- `audit-app.js:2917` — `buildPoolSurfaces()` calls `prescanPools(pools)` where `pools` is the snapshot
  array only. `audit-app.js:1546` — `loadLivePoolIds()` already retains the FULL live pool records
  (`pools` field, kept "so runAudit() can build the sub-rail fixture body… without a second fetch").
  The data needed to prescan the sub-rail 3,230 is in memory every tick; the prescan is not pointed at it.
- Consequence: the rail-relative number checks (`apy-rail-breach`, `mean30d-rail-breach` — the
  122/144/165 class; every pool-detail bug in this backlog's history was hand-found on a non-flagship
  pool) reach 18.5% of the candidate population cheaply; the other 3,230 pools are only ever checked by
  the 32-renders/tick rotation — a ~124-tick (~4-month) full pass for a pure record predicate that needs
  NO render.

## Hypothesis
We believe prescanning the union (snapshot records + live records for sub-rail deep-linked ids) will
surface the absurd-number class on arrival-population pools same-day instead of within ~4 months,
because the predicates are pure record checks and the records are already fetched. Confidence:
**validated-pattern** (157/167 prescan-then-promote, third application).

## Change
Smallest version: in `buildPoolSurfaces()`, build the prescan input as
`pools ∪ (live records for deep-linked ids not in the snapshot)` — the same union/intersection logic the
rotation already computes (reuse it; never a second copy of the set expression — hoist like 206's
`extractDeepLinkPoolIds()`). Per-signal applicability stated in the emitted block: `kpi-nonfinite`
applies only to records that carry `kpis` (live records don't — that is a skip, not a pass; report the
per-leg scanned counts `{snapshot: N, deepLinkedLive: M}` so "clean" carries its denominator). Promotion
into the render sample unchanged (P0-first, seeded), anchor exclusion unchanged. Degrade paths: if the
live leg is degraded (fetch error / kill switch), prescan falls back to snapshot-only AND SAYS SO in the
reported block — exactly 206's degrade contract.
OUT of scope: raising `AUDIT_POOL_SAMPLE` / the render budget (206's row records that as a separate
wall-clock-cap decision); any product-file change; widening `compute-kpis.js` (that is PARKED 208).

## Acceptance criteria
- [ ] A tick's findings JSON reports `poolPrescan.candidates` ≥ the rotation's union count minus
      documented exclusions, with per-leg scanned counts — asserted against the run's OWN rotation
      population figure, never a literal (the 197/206 disk-derived-count rule).
- [ ] Positive control on the NEW leg: inject (opts-level) a sub-rail live record with
      `apyMean30d > APY_SANITY_LIMIT` → it appears as a suspect AND is promoted into the render sample;
      remove it → clean. (LEARNINGS 2026-07-27: a widened population that finds nothing proves nothing.)
- [ ] True negative: today's real feed prescans with the same suspect set as the snapshot-only run
      produced (currently: exactly `201e5f6e`) OR any new suspects are real records verifiable by id in
      the live feed.
- [ ] `kpi-nonfinite` skip semantics: the block distinguishes "checked, clean" from "not applicable (no
      kpis on live records)" — a scan that quietly checks less than its name implies is the 197 trap.
- [ ] Degraded-live tick: prescan reports snapshot-only candidates + the degrade reason string; never
      silently narrower.
- [ ] Tests registered in `package.json` `test:serial`; note the lane (`classifyLane()` is transitive —
      requiring audit-app.js lands in the browser lane).
- [ ] 171's reconciliation (promoted suspect renders clean → auto-downgrade, "undeterminable stays
      blocking") applies to new-leg suspects identically.
