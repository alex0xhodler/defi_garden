# Spec 193: the rendered number-sanity scanner parses base58 token addresses as numbers — 157 fixed this exact bug one surface over

## Evidence

Originated by item 192's measurement run (pool rotation widened to 32). The tick reported a blocking **P0**:

```
pool-detail:3075a746 — number-sanity —
astronomical value "11111111111111111111111111111111111111112" (|value| = 1.11e+40)
```

**The page is correct.** `3075a746-bdd1-4aac-bcd5-b035abee2622` is `sanctum-infinity` INF on Solana
($149,835,182 TVL, 5.72% base APY, `apyMean30d` 5.81) — an ordinary pool. That digit run is the tail of
`So11111111111111111111111111111111111111112`, the wrapped-SOL mint address, which
`PoolDetail.js:1611-1656` renders **raw** as an "Underlying Assets" chip: the truncation branch is gated on
`token.startsWith('0x') && token.length >= 40`, so an EVM address renders as `0xdac1...1ec7 ↗` while a
Solana base58 mint falls through to the `<span>` at `:1645-1656` and lands in `innerText` in full.

**Root cause, exact.** `scanNumbers()`'s absurd-magnitude regex (`audit-app.js:2630`)

```js
const numRe = /(-?)\$?(\d[\d,]*(?:\.\d+)?)\s*([KMBTkmbt])?/g;
```

has **no left-boundary assertion**, so it matches a digit run embedded inside an alphanumeric token.
Its own sibling constant in the same file already carries the fix — `ABSURD_MAGNITUDE_TEXT`
(`audit-app.js:205`) opens with `(^|[^A-Za-z0-9])`, added by spec **157** with the standing comment
*"do NOT revert to the loose form."* The lesson was never ported to the rendered scanner: a textbook
`playbooks/dual-source-logic-divergence.md` case (the 4th instance of the class after 166/183/185/189).

**Measured this run** against the committed 741-pool `data/pools-snapshot.json` (reproduced with
`require('./audit-app.js').scanNumbers`):

| population | count |
|---|---|
| pools whose `underlyingTokens` alone trip `scanNumbers` | **99 / 741 (13.4%)** |
| …of those, pools that render the address **raw** (non-`0x`, or `0x` shorter than 40) | **28 / 741 (3.8%)** |
| digit-leading raw tokens that would survive the fix | **1** — Algorand ASA `1134696561` = 1.13e9, **below** `ABSURD_MAGNITUDE` (1e11), so it does not trip |

Direct reproduction on the unmodified file:

```
scanNumbers('Underlying Assets So11111111111111111111111111111111111111112')
  → ['astronomical value "11111111111111111111111111111111111111112" (|value| = 1.11e+40)']
```

**Consequence, live since 192's merge.** With `DEFAULT_POOL_SAMPLE` at 32 and 28/741 candidates poisoned,
the expected yield is **~1.2 false P0s per tick** — i.e. the heartbeat exits non-zero on the north-star
surface most runs, and the operator's first read of every tick is a wolf that isn't there. That is item
**171**'s lineage: a checker whose noise floor destroys its own signal.

## Hypothesis

We believe **porting 157's left-boundary rule to `numRe`** will **drop the false-P0 rate on the pool-detail
rotation from ~28/741 candidates to 0 without blinding the detector to the real 122 bug class** because
**the false positives are structurally identical — a digit run preceded by an alphanumeric character — and
no genuine rendered figure is ever preceded by a letter or digit.** Confidence: **validated-pattern** —
157 shipped exactly this predicate on exactly this file and measured 0/2,176 false positives afterwards.

## Change

Smallest version: **add a left-boundary assertion to `numRe` in `scanNumbers()` (`audit-app.js:2630`)**, so
a digit run immediately preceded by `[A-Za-z0-9]` is not read as a number.

Implementation constraint — **use a zero-width lookbehind `(?<![A-Za-z0-9])`, not 157's capturing
`(^|[^A-Za-z0-9])` alternation.** Both express the same predicate, but `numRe` is driven in a `/g`
`exec()` loop whose body reads `n[1]` (sign), `n[2]` (digits), `n[3]` (suffix) and reports `n[0].trim()`.
A capturing prefix would shift every index, put the boundary character inside the reported string, and
consume a character the next iteration may need. The lookbehind changes nothing but the match condition.
Node 22 supports lookbehind (`.nvmrc`/CI Node is 22; the file is CommonJS run under plain `node`).
Add a comment at the site naming spec 157 and `ABSURD_MAGNITUDE_TEXT`, and stating why the form differs,
so the next reader does not "unify" the two back into a bug.

Explicitly **OUT of scope**:
- The `moneyRe` and `NaN`/`undefined` checks in the same function — no evidence of a boundary bug there,
  and `moneyRe` requires a `$` prefix.
- `ABSURD_MAGNITUDE_TEXT` and the static prescan — already correct.
- **Changing `PoolDetail.js`.** Rendering a bare 44-character base58 mint as an "Underlying Assets" chip
  (while EVM addresses get truncated to `0xdac1...1ec7 ↗`) is arguably a product-quality wart, but it is a
  *different item*: this one is about the scanner reporting a defect where none exists. File it in notes,
  do not fix it here.
- Any change to `DEFAULT_POOL_SAMPLE` / rotation behaviour (192's territory).

## Measurement

Metric: **count of `number-sanity` P0 findings attributable to address text in
`product-loop-kit/signals/audit-findings.json`** — expected **≥1 per tick → 0**, observable on the very
next heartbeat run. Window: **immediate** (one tick), not 14 days — this is a correctness fix to a checker,
not a growth experiment, so the ≥30-event minimum-sample rule does not apply. Decision rule: if the next
tick still reports a `number-sanity` P0 quoting an address fragment, the fix failed and the item reopens.

Guardrail: the tick must still exit non-zero for a *real* P0. Criterion 7 is the standing proof.

## Risk tier (builder's guess — verifier assigns independently)

**LOW** — a one-regex change plus a new test file, confined to `audit-app.js` (audit tooling, not shipped
product code, not a render path, not the SEO surface), no new dependency, diff well under the 150-line cap.
It touches none of the NEVER list: no trust rail (`APY_SANITY_LIMIT`, `DEFAULT_MIN_TVL`, anomaly flags,
degen haircut), no credentials, no SEO deletion, nothing under `telegram-bot/`, `whatsapp-bot/`, `workers/`.

Counter-argument the verifier should weigh: the scanner *guards* the trust rails, so narrowing a detector
is a blast-radius question, not just a diff-size one. Criteria 3, 4 and 7 exist precisely to bound it — if
the verifier judges them insufficient, the honest tier is HIGH.

## Open questions

None that change the architecture. The fix form (lookbehind vs alternation) is decided above and is an
implementation detail, not an architectural fork.

Known residual, documented not fixed: a **pure-digit** token ≥ 1e11 rendered at the start of a line would
still be read as a number, because at that position there is no preceding alphanumeric character and the
text is genuinely indistinguishable from a magnitude. Measured population today: **0** (the only
digit-leading raw token in the snapshot is Algorand ASA `1134696561` = 1.13e9, an order of magnitude below
the 1e11 floor). Record it in `193-notes.md` rather than pre-building for it.
