# Spec 211: `yield.garden` serves the whole app on a second domain — consolidate it with a 301

## Evidence

Measured live, 2026-08-02, in-session (`curl`; network is open per NORTH_STAR 2026-07-12):

| host | status | serves |
|---|---|---|
| `yield.garden` | 307 → `https://www.yield.garden/` | — |
| **`www.yield.garden`** | **200** | **the full app + the full static estate** |
| `defi.garden` | 307 → `https://www.defi.garden/` | — |
| `www.defi.garden` | 200 | the intended origin |

**The exposure is much smaller than it looks, and the reason is worth recording before anyone panics:**

1. **The 2,154-page static SEO estate already self-canonicalises to the right origin.**
   `curl https://www.yield.garden/tokens/usdc` returns
   `<link rel="canonical" href="https://www.defi.garden/tokens/usdc">` and
   `<meta property="og:url" content="https://www.defi.garden/tokens/usdc">`. The generators bake absolute
   `www.defi.garden` URLs, so the entire indexed estate already tells Google which origin wins. **No fix
   needed there.**
2. **`robots.txt` and every sitemap served from `yield.garden` point at `www.defi.garden`** — verified:
   `Sitemap: https://www.defi.garden/sitemap.xml`, and `sitemap.xml`'s `<loc>`s are all `www.defi.garden`.
   So `yield.garden` submits no URLs of its own.
3. **The actual gap is the app routes, and it is one page.** `home.html` carries a static
   `og:url` (`:29`) but **no static `<link rel="canonical">`** — canonical is injected client-side by
   `canonical.js`, whose `SITE_ROOT` is hardcoded to `https://www.defi.garden/` (`:29`). Correct value,
   delivered only after JS runs. Google renders JS on a deferred second pass, which is exactly why GSC
   reports **`Duplicate without user-selected canonical` = 1 page** for `yield.garden`.
4. **Traffic at stake is negligible:** GSC `yield.garden`, 16 months — **26 impressions, 0 clicks, 0% CTR,
   avg position 10.7**.

**Correcting the premise, because it changes the priority:** Google does **not** issue a duplicate-content
*penalty* for the same site on two domains. It picks one URL as canonical and consolidates. The real costs
are (a) it may pick the wrong origin for some queries, (b) link and engagement signals split across two
hosts instead of compounding on one, (c) crawl budget spent twice on an estate that regenerates daily. Those
are real and worth removing — they are not an emergency, and this item is scored accordingly.

## Hypothesis

We believe **a host-conditioned 301 from `yield.garden`/`www.yield.garden` to the same path on
`www.defi.garden`** will **consolidate all crawl, link and engagement signals onto one origin**, because a
301 is the unambiguous signal Google acts on immediately, versus a JS-injected canonical that only lands on
a deferred render pass and only on pages that have one. Confidence: **validated-pattern** (301 host
consolidation is standard, and the redirect already exists in the apex→www direction on both domains, so the
mechanism is proven on this deployment).

## Change

1. Add a `redirects` entry to `vercel.json` matching `has: [{ type: "host", value: "(www\\.)?yield\\.garden" }]`
   for `source: "/(.*)"`, `destination: "https://www.defi.garden/$1"`, `permanent: true` (308/301).
   **Path and query must be preserved** — a blanket redirect to the root would throw away the exact deep
   links this item exists to consolidate.
2. **Belt-and-braces, independent of the redirect:** give `home.html` a **static** `<link rel="canonical"
   href="https://www.defi.garden/">` in `<head>`, matching the `og:url` already at `:29`. `canonical.js`
   already overwrites the href on every parameterised view (`:104`), so a static default is the no-JS
   floor, not a second source of truth. **Verify `canonical.js` still wins** for `?token=`/`?pool=` views —
   if the static tag were to survive on a parameterised URL, that would collapse thousands of distinct
   canonicals to root, which is far worse than the problem being fixed.

**OUT of scope:** removing the `yield.garden` domain from Vercel or from GSC — **keep both**. GSC
verification is how the redirect gets monitored; deleting the property blinds us to whether it worked.
Also out of scope: `canonical.js`'s `SITE_ROOT` and `CANONICAL_PARAMS` (correct as-is), every generator, and
the static estate's baked canonicals (already correct).

## Acceptance criteria

- [ ] `curl -sSI https://www.yield.garden/` → **301/308** with `location: https://www.defi.garden/`.
- [ ] **Path and query survive:** `curl -sSI "https://www.yield.garden/tokens/usdc"` → location
      `https://www.defi.garden/tokens/usdc`; `curl -sSI "https://www.yield.garden/?pool=<id>&lang=ko"` →
      location preserving both params exactly.
- [ ] `curl -sSI https://yield.garden/` (apex) also lands on `www.defi.garden`, in at most 2 hops.
- [ ] `www.defi.garden` is **unaffected**: root, `?token=USDC`, `?chain=Base`, `?pool=<id>`, `/tokens/usdc`,
      `/chains/solana`, `/plan.html` all still return **200** and render. **Both router paths verified per
      CLAUDE.md: bare `/` → planner, `/?token=USDC` → analytics app with pool cards.**
- [ ] `home.html` serves a static `<link rel="canonical" href="https://www.defi.garden/">` in the raw HTML
      (`curl | grep`, before any JS).
- [ ] **`canonical.js` still overrides it on parameterised views** — rendered check that `/?token=USDC`
      ends with `href="https://www.defi.garden/?token=USDC"` and **not** the root default. This is the one
      way this item could cause real damage; assert it explicitly.
- [ ] `sitemap*.xml`, `robots.txt`, `llms*.txt`, `stories/` and every generated page are **byte-untouched** —
      no regeneration is part of this item.
- [ ] Tests: `npm test` green; `test_canonical*.js` (or equivalent) passes unmodified.
- [ ] Instrumentation: none new. Observable in GSC as `yield.garden` impressions → 0 and its
      `Duplicate without user-selected canonical` count → 0.

## Measurement

Metric: GSC `yield.garden` property — `Duplicate without user-selected canonical` page count (currently 1)
and total impressions (currently 26/16mo) · Window: **6 weeks** (Google needs weeks to reprocess a host
redirect; the standing GSC arrangement is human-checked manually through ~2026-08-23, decision 2026-07-12) ·
Decision rule: **keep** if `www.defi.garden` serves 200 on every route above immediately post-deploy and no
guardrail moves. Success is confirmed later, by `yield.garden` impressions decaying to 0 with **no
corresponding drop** in `www.defi.garden` impressions. **Revert immediately** if any `www.defi.garden` route
regresses — a misconfigured host predicate that matches the wrong domain would take the whole site down, and
that is the only real risk here.

## Risk tier (builder's guess — verifier assigns independently)

**HIGH.** `vercel.json` is named explicitly on NORTH_STAR's HIGH list (config/infra), and a host-matching
mistake in a `/(.*)`  redirect is a whole-site outage rather than a degraded page. The change is small; the
blast radius is not. Note it is **not** on the NEVER list: no page is de-indexed and no SEO surface is
deleted — traffic is *consolidated* onto the canonical origin, which is the opposite of de-indexing. Verify
that reading rather than assuming it.

## Open questions

needed now."* So `www.defi.garden` is the permanent canonical origin and `yield.garden` is a disposable

build it as specced. Two consequences worth stating so a later run does not reopen the question:

- **Direction is settled**, so the builder must not "helpfully" make it configurable or bidirectional.
  A single permanent redirect toward `www.defi.garden` is the whole change.
- **Still keep the domain registered and its GSC property verified.** "Not needed" is about the product,
  not about the monitoring: the GSC property is how we confirm the redirect worked (impressions decaying to
  0 with no matching drop on `www.defi.garden`), and letting the registration lapse would hand an
  app-serving lookalike domain to whoever registers it next. Revisit only after the measurement window
  closes.
