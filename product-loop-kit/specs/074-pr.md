# 074 — PR explainer: fix critical fast-xml-parser vulnerability (v4 → v5)

Risk tier: **HIGH** (package.json dependency change — explicitly HIGH per
NORTH_STAR risk policy; verifier independently agreed). Verifier: **PASS, 5/5
acceptance criteria**, one PASS proven beyond the builder's own argument (see
"The one contested claim" below).

## Goal

Kill the one **critical**-severity `npm audit` finding in the repo:
`fast-xml-parser@^4.4.1`, a *production* dependency, carried six advisories
(DOCTYPE entity-encoding bypass via regex injection, unbounded entity-expansion
DoS, XMLBuilder stack overflow, numeric-entity expansion bypass /
incomplete CVE-2026-26278 fix, falsy-zero expansion-limit bypass, XMLBuilder
comment/CDATA injection). The fix is a breaking major bump to `5.10.0`.

This was flagged in `specs/003-notes.md` on 2026-07-10 with an explicit
"Recommend a new backlog item" — and never filed. The 2026-07-13 build loop
found no READY items and promoted it as item 074 (score 6.8: not a north-star
mover, but a critical-severity finding on the pipeline that feeds the SEO
lifeline guardrail).

## Intuition

Why care about an XML parser in a static site? Because `fast-xml-parser` is
what the **daily `sitemap-update.yml` CI job** uses to read our own sitemap
index (`generate-llms.js` → `llms.txt`/`llms-full.txt`) and to validate all
123 sitemap files (`validate-sitemaps.js`). The SEO surface staying fresh and
valid is a NORTH_STAR guardrail metric. A parser with a DoS-class entity-
expansion bug sitting in that daily pipeline is exactly the kind of quiet
supply-chain risk you clear while it's cheap — and it was very cheap: our two
call sites use only the stable public API, which v5 kept unchanged.

## What changed, in reading order

1. **`package.json`** — one line: `"fast-xml-parser": "^4.4.1"` →
   `"^5.10.0"`.
2. **`package-lock.json`** — regenerated. Resolves `fast-xml-parser@5.10.0`;
   adds six new transitive packages from the author's v5 package split
   (`@nodable/entities@2.2.0`, `anynum@1.0.1`, `fast-xml-builder@1.3.0`,
   `is-unsafe@2.0.0`, `path-expression-matcher@1.6.2`, `xml-naming@0.3.0`) and
   majors `strnum` 1.1.2 → 2.4.1. All six inspected by the verifier:
   MIT-licensed, NaturalIntelligence/nodable (the fast-xml-parser author),
   audit-clean. Total install: 61 → 67 packages.
3. **That's the whole code diff.** The two call sites —
   `generate-llms.js:12` (`new XMLParser({ ignoreAttributes: false })`) and
   `validate-sitemaps.js:22,32` (`XMLValidator.validate(xml,
   { allowBooleanAttributes: true })`) — needed **zero changes**; the spec's
   "adapt only if v5 forces it" clause never triggered.
4. Bookkeeping in this same commit (per standing decisions 2026-07-13/104):
   `specs/074.md` (spec), `specs/074-notes.md` (build notes + post-verification
   corrections), this file, `BACKLOG.md` (074 row → SHIPPED), `LOG.md` entry.

## How it was verified (all independently re-derived by the verifier)

- `npm audit --omit=dev`: **1 critical → 0 vulnerabilities** (full audit also 0).
- **Parse-stage equivalence**: the operator captured a v4 baseline BEFORE the
  bump — the exact `XMLParser` walk `generate-llms.js` does over
  `sitemap.xml` + all sub-sitemaps, yielding 23,599 URLs. Re-run under v5:
  **set- and order-identical** (the only byte diff was a trailing newline in
  the baseline file itself).
- `node validate-sitemaps.js`: "All 123 sitemap file(s) valid", exit 0 — same
  verdict as the v4 baseline.
- `node generate-llms.js` end-to-end with live network (output redirected to
  the scratchpad so committed `llms*.txt` stayed untouched): completed, 23,599
  URLs, 15,404 pools fetched, exit 0.
- Unit chain (`test_planner.js`, `test_protocol_parsing.js`,
  `test_qualifier_fix.js`) exit 0; `test_compiled_assets` (4),
  `test_minified_assets` (9), `test_css_minified_render` (2) all pass.

## The one contested claim

`npm test` fails at `test_smoke.js` (Playwright browser test). The builder
argued this is the documented sandbox browser-network failure (browser HTTPS
blocked at the proxy — NORTH_STAR 2026-07-12) and diff-independent, but only by
grep (fast-xml-parser is imported by exactly the two Node scripts, never
browser-loaded). The verifier **proved** it instead: `git stash` → `npm ci`
from the stashed v4 lockfile (4.5.3 confirmed installed) → `node
test_smoke.js` → **identical failure signature on the clean v4 tree**
(`net::ERR_CONNECTION_RESET`, `.pool-card` never renders), then restored the
tree. Pre-existing, environmental, unrelated to this diff — same precedent as
items 040/044/045/051–056.
