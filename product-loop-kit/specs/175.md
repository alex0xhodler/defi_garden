# Spec 175: give the link checks a level-3 signal — "does the target return what the page claims?"

## Evidence
`audit-app.js` ran this tick (2026-07-29T07:07:15Z, `status: "OK"`, 29 surfaces). `prescanStaticPages()`
scanned **2,200** pages and returned **7 suspects, all `junk-slug`**. Its signal set:
`junk-slug`, `zero-yield-claim`, `broken-number-literal`, `absurd-magnitude`, `link-target-integrity`.

**`link-target-integrity` — shipped this morning as item 172 — scored `0` on 2,200 pages carrying 1,749
dead CTAs** (item 173). Not a bug in 172: it was specced from 166, where "broken link" meant *a query param
the router does not recognise*, so it checks param membership against `ANALYTICS_PARAMS ∪ PLANNER_PARAMS`.
`?chain=Cardano` is a perfectly routed param. It just returns nothing.

The same tick, `prescanTextSurfaces()` scored `0` on both `llms*.txt` for the same reason.

**This is the fourth consecutive instance of one pattern: 148 → 159 → 166 → 173.** The checker's signal set
is always drawn from the shape of the last bug found, so the next bug lands in the class nobody has been
bitten by yet. LEARNINGS records the pattern three times; this spec is the attempt to break it by
generalising instead of patching.

**The generalisation.** A link check has three levels:
1. **Routed** — is the query param one the app recognises? (172 built this; 166 was the bug.)
2. **Resolvable** — does the value name a real entity: a pool id in the snapshot, a project slug, a preset
   key? (Done by hand this tick against `llms*.txt`: 40 links checked, 0 misses. Nothing automates it.)
3. **Non-empty** — does the target, **under its own default filters**, return what the linking page claims?
   (Nothing checks this. All 1,749 of item 173 live here.)

Level 3 is the only one that catches a mismatch between two surfaces that are each internally consistent —
which is exactly what 173 is: the page is right, the app is right, the *contract between them* is broken.

## Hypothesis
We believe **extending `link-target-integrity` to levels 2 and 3 will make the scanner able to find the
173/166 class without a human re-deriving it** because both levels are computable offline from the committed
snapshot plus the generated pages — no browser and no network needed (level 3 is a filter simulation, the
same arithmetic the heartbeat ran by hand this tick in one node script). Confidence: **supported** — the
check has been executed manually and produced the correct answer on a 2,200-page corpus, so the only open
question is codifying it, not whether it works.

## Change
Extend the existing `link-target-integrity` signal in `audit-app.js` (both `prescanStaticPages()` and
`prescanTextSurfaces()` — one shared helper, not two copies) with:
- **Level 2 (resolvable):** `?protocols=<slug>` must be a real `project`; `?preset=<key>` must exist in
  `planner.js`'s `PRESETS`. Unknown value → suspect.
  **`?pool=<id>` liveness stays OUT of the offline prescan** — `playbooks/product-audit.md` class 10 already
  records why: the token pages draw from the full ~16,000-pool feed at a $100K floor while
  `data/pools-snapshot.json` is the ≥$10M 746-pool set, so validating one against the other reported
  **4,233 of 4,989** links dead, all false (true figure against a live fetch: 15, and self-healing on the
  next CI regen). Validate each generated link against **the population its generator drew from**.
- **Level 3 (non-empty):** for `?token=`/`?chain=`/`?poolTypes=`/`?minTvl=` grid links, simulate the app's
  filter — the substring symbol match (`app.js:835`), exact chain match, and the `minTvl` rule from
  `app.js:927` (explicit param wins; absent → `DEFAULT_MIN_TVL`) — and flag any link resolving to **0**
  pools.

Read `DEFAULT_MIN_TVL`, `ANALYTICS_PARAMS` and `PLANNER_PARAMS` from their existing single sources
(`app.js`, `home.html:77-78`) — **never a second hardcoded copy** (166's own rule, and the
`dual-source-logic-divergence` playbook).

**Explicitly OUT of scope:**
- Fixing the 1,749 dead CTAs → item **173**. 175 only makes them *visible to the scanner*. Sequence:
  173 fixes, 175 keeps them fixed. If 175 lands first it will emit ~1,749 findings, which is correct
  behaviour, not a bug — but it will make the audit exit non-zero until 173 lands, so **land 173 first**.
- Rendering the link targets in a browser. Level 3 is arithmetic over the snapshot; a browser would make it
  slow enough to skip, which is how checks die.
- New signal classes beyond link integrity.

## Measurement
Metric: **new-finding yield** — the count of distinct P0/P1 classes the scanner surfaces that the heartbeat
had not already found by hand. Baseline is unambiguous and damning: **four consecutive days (07-26 → 07-29)
of zero scanner-originated findings**, while the heartbeat found 159, 166, 168 and 173 by hand on those same
days. Window: 14 days from ship.
Decision rule: the item MOVED if, within the window, the scanner surfaces **≥ 1** link-class finding before
a human does. If the next link-class bug is again found by hand first, that is evidence the
generalise-the-signal approach does not break the pattern either, and the loop should stop extending
signals and instead invest in the checker's *design* (write it up in LEARNINGS as a REVERT-CANDIDATE
verdict on the strategy, not on this code).

## Risk tier (builder's guess — verifier assigns independently)

### T1. The population question has an exact answer: the snapshot is COMPLETE at and above its own floor
`data/pools-snapshot.json` carries `minTvlUsd: 10000000` and `count: 747` — it is not "a sample of the feed",
it is **every pool at or above $10M**. That makes the class-10 trap precisely characterisable rather than
something to tiptoe around:

- A link whose **effective floor ≥ `snapshot.minTvlUsd`** can be simulated against the snapshot with
  **zero** false-positive risk — the snapshot is a complete population at that floor by construction.
- A link whose **effective floor < `snapshot.minTvlUsd`** must **never** touch the snapshot. That is exactly
  the 4,233-false-positive trap (`playbooks/product-audit.md` class 10): `?chain=Cardano&minTvl=100000` is
  alive on the $100K feed and absent from the $10M snapshot.

Every pre-173 dead CTA carried **no** `minTvl` → effective floor = `DEFAULT_MIN_TVL` = $10M → in the
snapshot-complete regime. Every post-173 CTA carries `minTvl=100000` → below it. So the completeness rule,
not a heuristic, is what makes level 3 both non-vacuous on the old corpus and silent on the new one.

### T2. Second population source, for the sub-$10M regime: the page's OWN listed rows
Both generators render the pool set they drew from into a single table. Row shape (verified on
`chains/ethereum.html` + `tokens/usdc.html`): one `<tr>` per pool carrying exactly one
`cp-pool-link`/`tp-pool-link` anchor and two `<td class="num">` cells, of which the **last** is the TVL money
figure (`$17.8B`, `$259.8K`) — parseable by the `parseMoney()` helper that already exists in `audit-app.js`
for 169. Column *order* differs between the two generators (chain pages: Token/Protocol/APY/TVL; token
pages: Protocol/Chain/APY/TVL) so "last `num` cell" is used rather than a fixed index.

This is the population its generator drew from, per-page, offline, at the $100K floor — the thing the repo
otherwise does not have a copy of.

### T5. Level 2's two universes exist and are clean today
- `?protocols=<slug>`: universe = `new Set(snapshot.pools.map(p => p.project))` → **193** slugs. All 7
  slugs in `llms.txt` and all 10 in `llms-full.txt` are members → the must-not-flag half of criterion 3 is
  satisfiable.
- `?preset=<key>`: `planner.js:1119` declares `var PRESETS = { tomoko, kevin, lucia }` and **does not export
  it** (`module.exports = api`, 37 keys, no `PRESETS`). Do **not** add an export — `audit-app.js` already
  regex-reads `planner.js` for exactly this reason (`loadPlannerAllowedParams()`, 172), so parse the
  `var PRESETS = {` block's top-level keys the same way. Both live values (`kevin`, `tomoko`) are members.

### T6. Prior art to reuse, not re-derive
`test_seo_cta_targets.js` (shipped with 173) already mirrors the app's filter arithmetic —
`symbolMatchesToken` (app.js:835 substring, case-insensitive), exact `pool.chain` equality,
`(tvlUsd||0) >= floor && > 0`, and `APP_DEFAULT_MIN_TVL` as the absent-param resolution. Read it before
writing the simulation; it is the same arithmetic, already reviewed. It cannot be imported (it is a test
that fetches live pools), but its predicates are the reference.

`getPoolType` is exported from `generate-sitemap.js` and is the **one** classifier (`app.js:161` and both
generators route through it). Lazy-require it inside the helper, in a `try/catch`: if it is unavailable the
`poolTypes` constraint is dropped and the drop is *counted and reported*, never silently ignored.

### T7. The audit's exit code will flip to non-zero, and that is the correct outcome
`link-target-integrity` is P1. 63 new real P1 findings on the text surfaces means `audit-app.js` starts
exiting non-zero on the committed tree. `npm test` (`run-tests.js`) does **not** run `audit-app.js` as a
gate — only its unit tests — so the merge gate is unaffected. The heartbeat will see a red audit whose
findings are true; that is the signal, not a regression.

### T8. Anti-vacuity rail (the failure mode this whole item exists to break)
A silent-death path must not be introduced: if a static page has pool-row anchors but **zero** parseable
TVL rows, level 3 must emit a `link-target-integrity` suspect saying *the level-3 population was
unparseable* — never skip quietly. Today that fires on 0 of 2,200 pages, so it costs nothing; the day a
template change breaks the row markup, the scanner says so instead of going dark. Same for the two
degradation paths (`snapshot` unreadable, `getPoolType` unavailable): skip the affected rule, print the
stderr note once per scan, and never throw — the existing never-throws contract.
