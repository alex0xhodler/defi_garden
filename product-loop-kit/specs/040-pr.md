# 040 — JSON-LD structured data (Organization/WebSite, BreadcrumbList, FAQPage)

## Goal
DeFi Garden had zero machine-readable structured data anywhere in the repo —
no `Organization`/`WebSite` entity markup, no `BreadcrumbList` on any page,
no `FAQPage` markup despite `stories/kevin.html` already rendering an actual
visible Q&A block. 2026 SEO/GEO research (cited in specs/040.md) treats
JSON-LD as the highest-leverage, lowest-risk lever for rich-result
eligibility and AI-answer-engine (GEO/AEO) citation — both matter for a
content category (DeFi yield comparison) where AI Overviews already resolve
a majority of queries. This ships the smallest version that adds real,
content-accurate structured data: no visual change, no new dependency, no
trust-rail/canonical/ranking logic touched.

## Intuition
JSON-LD is just a `<script type="application/ld+json">` tag containing a
JSON object that describes the page to a machine reader (search engines, AI
answer engines) using schema.org's vocabulary. It's invisible to a human
visitor — the page looks identical — but it tells a crawler things like "this
page is at position 3 of a breadcrumb trail: Home → Tokens → BTC" or "this
page visibly answers these 3 questions, here's the Q and the A." The one
hard rule everywhere in this space: **the markup must describe what's
actually on the page** — inventing a Q&A pair not shown, or linking a
breadcrumb crumb to a URL that doesn't exist, is exactly what Google calls
spam and can trigger a manual action. So the design constraint driving every
line of this diff was "derive the JSON-LD from the same data/array the
visible HTML already renders from" — never a second, independent source of
truth.

## What changed and why (diff in reading order)

**1. `home.html`** — two static `<script type="application/ld+json">` blocks
in `<head>`, one `Organization` (name, url, logo — reuses `og-image.png`, no
new asset) and one `WebSite` (name, url). Placed as static markup, separate
from the IA router's script — the router only rewrites `<link
rel="canonical">`/`og:url`/`<title>` per mode; the site's brand identity
(Organization/WebSite) doesn't change between planner mode and analytics
mode, so it didn't need router logic.

**2. `generate-token-pages.js`** (`renderTokenPage`) — a `BreadcrumbList`
with 3 positions: Home (linked to site root), Tokens (unlinked — see
deviation below), `<SYMBOL>` (linked to the page's own canonical URL,
matching itself as the current page). Inserted right after the existing
`<link rel="canonical">` tag. Values come from `SITE_URL`/`pageUrl`/
`rec.symbol` — nothing newly computed.

**3. `PoolDetail.js`** — a `<script>` element (via `React.createElement` +
`dangerouslySetInnerHTML`, since this file is UMD `React.createElement`
only, never JSX) rendered as the first child of the pool-detail container,
alongside — not replacing — the existing visual breadcrumb (`Search Results
→ <SYMBOL> Pool`). The JSON-LD mirrors exactly those 2 crumbs; the visual
breadcrumb's own div/spans/onClick handlers are untouched (diff only adds
lines, doesn't modify the existing block).

**4. `generate-stories.js`** (`renderStoryPage`) — a `FAQPage` JSON-LD block
whose `mainEntity` array is built directly from `p.faq` (the same array
`faqHtml` already renders into visible `<h3>`/`<p>` tags a few lines below),
only when `p.faq` exists (currently kevin only — tomoko/lucia have no `faq`
array and correctly emit nothing).

**5. Escaping** — every dynamically-built JSON-LD block (token pages,
PoolDetail) is `JSON.stringify(...).replace(/</g, '<')` before
embedding. This is not HTML-escaping (which would corrupt the JSON values
with literal `&amp;`/`&lt;` entities that never decode back inside a
`<script>` tag) — it's a `</script>`-breakout guard, the standard technique
for embedding arbitrary JSON inside an HTML script tag. `home.html`'s blocks
are fully static strings with no interpolation, so no injection surface
exists there.

**6. Tests** — new assertions in `test_token_pages.js` (BreadcrumbList
shape/values + an XSS-safety check with a malicious symbol),
`test_stories.js` (FAQPage byte-for-byte match to `p.faq`, absence on the
other two personas), and `test_smoke.js` (a static home.html JSON check, plus
a Playwright check that clicks a real pool card and inspects the resulting
DOM for the BreadcrumbList block). `test_smoke.js` also got a pre-existing-
pattern fix (pin `chromium.launch()` to the sandboxed executable, mirroring
`test_search.js`) needed just to get the smoke gate running at all after a
fresh `npm install` in this session.

## Deviations from spec (judgment calls)
1. **"Tokens" breadcrumb has no `item` URL.** There is no `/tokens` hub/index
   page anywhere in this repo (no `vercel.json` rewrite, no generated index).
   Linking it to a URL that 404s would be worse than an honest, unlinked
   label — schema.org's `ListItem.item` is optional. Verifier reviewed this
   independently and concurred it's defensible, not a spec violation.
2. **Sitewide, not planner-mode-only, for Organization/WebSite** — the spec
   left this open; sitewide is correct because the brand entity doesn't
   change by mode.
3. **PoolDetail's breadcrumb is 2 items, not 3** — it mirrors the actual
   visible breadcrumb (no separate "Home" crumb exists in that UI), rather
   than inventing a 3rd level to match the token-page pattern.
4. **Playwright live-DOM verification of PoolDetail.js's JSON-LD was not
   possible in this build session** — this sandbox's network policy blocks
   both `unpkg.com` (React's CDN) and `yields.llama.fi` (the pools API)
   outright, confirmed via `curl` and the proxy status endpoint. The
   pre-existing bare-`/` and `?token=USDC` Playwright checks (present before
   this diff, from spec 003) fail identically for the same reason — not a
   regression. The verifier independently reproduced this and confirmed it's
   a real environment limit, not an excuse. Static/unit coverage (which
   doesn't need the CDN/API) all passed for every other surface touched.

## Verification
Verifier subagent: **PASS**, risk tier **HIGH** (independently assigned,
agreeing with the builder's guess) — touches `home.html` (parameterized-URL-
adjacent), `PoolDetail.js` (pool-detail view), and the generated-SEO-surface
generators, three of NORTH_STAR's explicit HIGH triggers. 7/7 acceptance
criteria met. Full reasoning in the verifier's report; build notes in
`specs/040-notes.md`.

## Quiz

1. Why does the "Tokens" breadcrumb item on a `/tokens/<slug>` page have no
   `item` URL, while "Home" and the symbol itself do?
2. Why is the FAQPage JSON-LD built from the raw (unescaped) `p.faq` array
   rather than the same `escapeHtml(...)` strings used for the visible HTML?
3. What technique does this diff use to stop a malicious token symbol from
   breaking out of its `<script type="application/ld+json">` tag, and why
   is HTML-escaping not the right tool for that job?
4. Why does `PoolDetail.js`'s BreadcrumbList have only 2 items instead of 3
   like the token pages?
5. Why couldn't the builder get a live-browser confirmation that
   PoolDetail.js's JSON-LD actually renders in the DOM, and why is that not
   treated as a blocking gap?
