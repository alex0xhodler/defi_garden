# Spec 050 — PR explainer (HIGH tier)

## Goal
`ko` is a first-class app language (translations.js ships full en/ko, the
planner and analytics app are fully localized), but the 2,108 generated
static SEO pages (`/tokens/<slug>`, `/chains/<slug>`, hubs, A–Z sub-hubs)
were English-only with zero `hreflang` — an untapped international-SEO
surface the existing translation infrastructure already supports. This
item generates a Korean counterpart of every one of those pages, properly
cross-linked via reciprocal `hreflang`, without touching routing, the app
shell, or any trust rail.

## Intuition
The static-page generators (`generate-token-pages.js`, `generate-chain-
pages.js`) already separate "data" (a `rec` object: ranked pools, TVL,
APY — all real, gated numbers) from "template" (the HTML string wrapped
around that data). Adding a language meant threading one new `lang`
parameter through every render function and swapping every hardcoded
English string for a lookup into `translations.js`'s existing catalog
mechanism (`createTranslationFunction(lang)`, already Node-requireable).
Because both language variants render from the *same* `rec` object, pool
data can't drift between them — there's no separate "Korean data path" to
keep in sync, only a separate copy path.

The one design wrinkle: Korean doesn't inflect nouns for plural ("풀"
means both "pool" and "pools"). The English generator pre-computed
`poolWord = count === 1 ? 'pool' : 'pools'` and interpolated it into
sentences — doing the same for Korean would have literally glued an
English word into a Korean sentence. Fixed by moving pluralization inside
each language's translation function, keyed off a raw count instead of a
pre-formatted word.

## What changed (reading order)

1. **`translations.js`** — added a ~60-key `tcp*` (token/chain-page)
   section to both `en` and `ko` catalogs, sibling to the existing
   `planner` sub-object (not nested inside it — an early draft accidentally
   nested it there and the keys silently resolved to `undefined`; caught
   immediately by a smoke-test `node -e` check). Every key that appears in
   a rendered page has a parity partner in both languages (enforced by a
   test). The `$100K` TVL floor and `1000%` APY sanity-limit mentions stay
   literal ASCII in the Korean strings too — CLAUDE.md pins all number
   formatting to en-US with no prose exception, and mixing `$`/acronyms
   into Korean text is already how the rest of the page (APY/TVL column
   headers) works.

2. **`generate-token-pages.js` / `generate-chain-pages.js`** — every
   render function (`renderTokenPage`, `renderChainPage`,
   `renderTokenHubPage`, `renderTokenAzPage`, `renderChainHubPage`,
   `buildAnswerAndFaq`, `renderItemListJsonLd`, `renderFaqBlockHtml`,
   `renderLastUpdatedHtml`, `renderTokenSitemap`, `renderChainSitemap`)
   gained a trailing `lang` parameter, defaulting to `'en'` so every
   existing call site (and every existing test) is unaffected. A new
   `renderHreflangLinks(enUrl, koUrl)` helper emits the three reciprocal
   `<link rel="alternate">` tags on both variants. `main()` now writes a
   full parallel `ko/` tree (`ko/tokens/<slug>.html`, `ko/tokens/index.html`,
   `ko/tokens/az/<letter>.html`, same for chains) alongside the existing
   English output, using the identical `ranked` array so pool-parity is
   structural, plus a `sitemap-*-pages-ko.xml`.

3. **`generate-sitemap.js`** — the sitemap index gained two more
   `fs.existsSync` guards (mirroring the pre-existing en-sitemap guards)
   to list `sitemap-token-pages-ko.xml` / `sitemap-chain-pages-ko.xml`
   when present.

4. **`.github/workflows/sitemap-update.yml`** — the CI commit step's
   `git add` list now includes the new `ko/` directory and the two new
   sitemap files, so the daily/on-push regeneration actually commits the
   Korean output (no new CI *steps* were needed — `main()` already writes
   both languages in one pass).

5. **`test_i18n_pages.js`** (new, wired into `npm test`) — 19 assertions:
   `<html lang>` correctness, hreflang reciprocity in both directions,
   self-canonical URLs, a 21-phrase English-leak denylist run against the
   ko output, en/ko pool-parity (identical rendered numbers, row by row),
   the `$100K`/`1000%` literal-format check, FAQPage JSON-LD/visible-text
   parity per language, and ko sitemap coverage.

## Deviations from spec (all logged in `specs/050-notes.md`)
- **URL scheme**: spec offered `?lang=ko` as the "no vercel.json change"
  default and flagged the subdirectory scheme as needing human
  confirmation if it touched routing. Went with the subdirectory anyway
  because `?lang=ko` genuinely cannot work here — these are pre-generated
  static files, and a query string can't select different static content.
  Then confirmed the subdirectory needs *no* vercel.json change either:
  `cleanUrls: true` is unscoped and already resolves nested paths like
  `/tokens/az/<letter>` with zero explicit rules, so `/ko/tokens/<slug>`
  resolves the same way for free. `vercel.json` is untouched by this diff
  (verified: `git diff origin/main -- vercel.json` is empty).
- **Pluralization redesign**: described above — count-based, not
  pre-pluralized-word-based translation functions.
- **`$100K`/`1000%` reverted to literal**: first draft localized these
  into Korean numeral notation (`$10만`); caught in self-review as a
  CLAUDE.md violation and fixed.
- **Bug fix, not a feature**: `koOutDir` computed via `path.resolve('ko',
  args.out)`, which silently collapses to just `args.out` whenever
  `--out` is an absolute path (Node's `path.resolve` discards earlier
  segments once it hits an absolute one) — would have overwritten the
  English pages instead of writing a sibling `ko/` directory. Fixed to
  `path.join(path.dirname(outDir), 'ko', path.basename(outDir))`. Doesn't
  affect the real CI invocation (`--out tokens`, a relative path), but was
  a live landmine for any future absolute-path invocation.
- **Two English-leak fixes found in self-review** (not anticipated by the
  spec): `renderFaqBlockHtml`'s "Frequently asked questions" heading and
  `renderItemListJsonLd`'s `"X on Y"` JSON-LD name field were both
  hardcoded English in shared helpers the per-page translation pass
  missed on the first pass. Both now take a `lang` parameter.
- **Not committed here**: the real ~2,100 Korean HTML pages themselves.
  `yields.llama.fi` is network-blocked in this sandbox (same precedent as
  021/041/045); the generators only ran here against the offline test
  fixtures for verification. Real output lands on the next
  `sitemap-update.yml` CI run.
