## The blocker (found in code + data, 2026-07-15)

058 §8 was written as an *aspiration* BEFORE 059 actually built the snapshot. 059 built it for a
**different, incompatible axis**: the FE-payload win. The two goals cannot share one snapshot.

**The snapshot is $10M-TVL-railed.** Measured on disk this run:
- `data/pools-snapshot.json`: `minTvlUsd = 10_000_000`, `count = 719`, min actual `tvlUsd`
  ≈ $10.0M, **330 distinct token symbols**. Per-chain/per-token slices (059 A3) are sliced
  FROM this railed set, so they are $10M-floored too. **No sub-$10M pool exists anywhere in
  `data/`.**
- 059 chose $10M deliberately: it is the 97.6%-on-the-wire cut (2,095 KB → 51 KB gzip, 059
  Phase-1 measurement) that justified the whole FE data layer. Lowering the floor re-opens that
  HIGH-risk payload decision.

**The three generators deliberately floor FAR below $10M — to capture long-tail SEO:**
- `generate-token-pages.js`: `MIN_POOL_TVL = 100_000` ($100K), `MIN_QUALIFYING_POOLS = 1`
  (lines 60/63). The header comment records this is a **human directive (2026-07-11)**: the
  app's $10M plan-floor governs *savings plans*; these static pages exist to "capture long-tail
  search traffic from newer tokens, which a $10M floor + 2-pool minimum shut out."
- `generate-chain-pages.js`: reuses the same `isQualifyingPool` ($100K floor) imported from
  `generate-token-pages.js`.
- `generate-sitemap.js`: enumerates token/chain URL candidates down to `tvlUsd >= 1000`
  (line 129, "very low TVL pools for better hygiene"), applying the $10M gate only to
  qualifying-*count* quality checks, not to URL existence.

**Measured impact of sourcing from the $10M snapshot:**
- Committed today: **2,103 token pages** (`tokens/*.html`), **86 chain pages** (`chains/*.html`).
- The $10M snapshot carries only **330 distinct tokens**.
- Result: ~2,103 → ≤~330 token pages, ~86 → far fewer chain pages, and the sitemap's sub-$10M
  token/chain URLs vanish. That is **deleting / de-indexing ~1,770+ SEO pages** plus their
  sitemap entries.

## Question for the human

The 059 snapshot is $10M-railed for the FE-payload win; the SEO generators are $100K/$1000-floored
for long-tail search (2,103 token pages vs 330 tokens in the snapshot). One snapshot can't serve
both without de-indexing ~1,770 pages. **Do you want (A) a new SEO-tier snapshot item promoted as
the shared CI source, or (B) 102 dropped as unbuildable (generators keep their own live fetch)?**
(C) and (D) are off the table (payload regression / NEVER-list). Until you answer, 102 stays
BLOCKED and no generator is repointed.

## Acceptance criteria (would apply ONLY under option A, after human sign-off)

- A new `$1000`-floored (or whatever floor the human confirms) shared snapshot generator, rails
  applied upstream once, byte-idempotent (081/083), `--out` isolation (076).
- The three generators source from it with an unchanged output set: `tokens/`, `chains/`, and
  every `sitemap-*.xml` byte-identical (modulo lastmod) to a live-fetch run over the same data —
  proven by a diff of a snapshot-sourced run vs a live-sourced run (0 dropped pages/URLs).
- Live fallback preserved: snapshot missing/stale in CI → the generators fetch live, no coverage
  change.
- Trust rails byte-untouched in every generator; attribution untouched.
