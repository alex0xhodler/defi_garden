## The blocker (found in code + data, 2026-07-15)

058 §8 was written as an *aspiration* BEFORE 059 actually built the snapshot. 059 built it for a
**different, incompatible axis**: the FE-payload win. The two goals cannot share one snapshot.

**The snapshot is $10M-TVL-railed.** Measured on disk this run:
- `data/pools-snapshot.json`: `minTvlUsd = 10_000_000`, `count = 719`, min actual `tvlUsd`
  ≈ $10.0M, **330 distinct token symbols**. Per-chain/per-token slices (059 A3) are sliced
  FROM this railed set, so they are $10M-floored too. **No sub-$10M pool exists anywhere in
  `data/`.**
- 059 chose $10M deliberately: it is the 97.6%-on-the-wire cut (2,095 KB → 51 KB gzip, 059
  Phase-1 measurement) that justified the whole FE data layer. Lowering the floor re-opens that
  HIGH-risk payload decision.

**The three generators deliberately floor FAR below $10M — to capture long-tail SEO:**
- `generate-token-pages.js`: `MIN_POOL_TVL = 100_000` ($100K), `MIN_QUALIFYING_POOLS = 1`
  (lines 60/63). The header comment records this is a **human directive (2026-07-11)**: the
  app's $10M plan-floor governs *savings plans*; these static pages exist to "capture long-tail
  search traffic from newer tokens, which a $10M floor + 2-pool minimum shut out."
- `generate-chain-pages.js`: reuses the same `isQualifyingPool` ($100K floor) imported from
  `generate-token-pages.js`.
- `generate-sitemap.js`: enumerates token/chain URL candidates down to `tvlUsd >= 1000`
  (line 129, "very low TVL pools for better hygiene"), applying the $10M gate only to
  qualifying-*count* quality checks, not to URL existence.

**Measured impact of sourcing from the $10M snapshot:**
- Committed today: **2,103 token pages** (`tokens/*.html`), **86 chain pages** (`chains/*.html`).
- The $10M snapshot carries only **330 distinct tokens**.
- Result: ~2,103 → ≤~330 token pages, ~86 → far fewer chain pages, and the sitemap's sub-$10M
  token/chain URLs vanish. That is **deleting / de-indexing ~1,770+ SEO pages** plus their
  sitemap entries.

1. **NORTH_STAR NEVER-list, verbatim:** "deleting or de-indexing SEO surface" → BLOCKED for the

2. **Directly contradicts a standing human directive** (2026-07-11, $100K SEO floor is

3. build.md §1: an open question that changes the architecture must not be guessed → BLOCKED.

The only ways to "point the generators at a snapshot" that DON'T delete SEO surface all change
the architecture and belong to the human:
- **(A) A SECOND, SEO-tier snapshot** — a new CI generator emitting a `$1000`-floored (the
  sitemap's URL-enumeration floor, the lowest any generator needs) snapshot as the shared source
  for the three generators, leaving 059's $10M FE snapshot untouched. This is a NEW data-layer
  item (a sibling of 059), not "102 as written." It re-introduces a large committed JSON in CI
  (the 2026-07-13 Vercel-deploy/git-bloat concern 058 §3 flagged for low-floor snapshots) and
  must itself carry the trust rails.
- **(B) Drop 102** — accept that 059's $10M snapshot is an FE-only artifact and the SEO
  generators keep their own live fetch (the "trust-rail filter applied thrice" cost is real but
  small; correctness/coverage dominates).
- **(C) Lower 059's snapshot floor to $1000** — rejected: blows up the FE payload (the entire
  point of 059) and re-opens a HIGH-risk shipped decision.
- **(D) Accept the SEO loss** — rejected outright (NEVER-list). This is the naive "just point
  them at the existing $10M snapshot" path; it is what the table below calls "naive".

## What A vs B mean for SITEMAP COVERAGE (the question that matters)

Headline: **neither A nor B changes a single sitemap URL** — both preserve today's full coverage
(~4,881 `<loc>` across all `sitemap-*.xml`). They differ only in *where the CI data comes from*,
not in what gets indexed. Coverage only collapses under the rejected naive path (D). The
sub-$10M-dependent sitemap families and their fate:

| sitemap family (today's count) | floor that fills it | Option A (new $1000 snapshot) | Option B (keep live fetch) | naive $10M snapshot (D, rejected) |
|---|---|---|---|---|
| `sitemap-token-pages.xml` + `-ko` — **2,131 each** (`/tokens/<slug>`) | $100K, `generate-token-pages.js` | **2,131 — unchanged** | **2,131 — unchanged** | ~330 → **drops ~1,800 URLs** |
| `sitemap-chain-pages.xml` + `-ko` — **86 each** (`/chains/<slug>`) | $100K, `generate-chain-pages.js` | **86 — unchanged** | **86 — unchanged** | far fewer → most chains gone |
| `sitemap-chain-<X>.xml` (per-chain `?token=&chain=` combos, e.g. Ethereum 66, Solana 19) | $1000, `generate-sitemap.js` line 129 | **unchanged** | **unchanged** | combos on sub-$10M tokens vanish |
| `sitemap-category-*.xml` (LP-DEX 14, Lending 35, Yield-Farming 63, Staking 1) | $1000, same enumeration | **unchanged** | **unchanged** | shrinks with the token set |
| `sitemap-tokens-all.xml` — **105** (`?token=` deep links) | already $10M-gated | unchanged | unchanged | unchanged (already $10M) |
| `sitemap-main.xml` — 12 (static core) | n/a | unchanged | unchanged | unchanged |

So the real trade is **not about coverage** (A and B both keep 100% of it):
- **A** buys the CI simplification 058 §8 wanted — one shared, pre-railed data source, fewer live
  DefiLlama calls in CI, the trust-rail filter applied once instead of three times — *while*
  coverage stays byte-identical. The price is a second, low-floor committed snapshot (thousands
  of rows, the git-bloat/deploy cost) plus the work to build+verify equivalence.
- **B** keeps today's exact behavior: three generators each fetch live and filter independently.
  Zero coverage risk, zero new artifact, but the "one source of truth" simplification simply
  doesn't happen — the duplicated-fetch cost 102 set out to remove stays.

## Acceptance criteria (would apply ONLY under option A, after human sign-off)

- A new `$1000`-floored (or whatever floor the human confirms) shared snapshot generator, rails
  applied upstream once, byte-idempotent (081/083), `--out` isolation (076).
- The three generators source from it with an unchanged output set: `tokens/`, `chains/`, and
  every `sitemap-*.xml` byte-identical (modulo lastmod) to a live-fetch run over the same data —
  proven by a diff of a snapshot-sourced run vs a live-sourced run (0 dropped pages/URLs).
- Live fallback preserved: snapshot missing/stale in CI → the generators fetch live, no coverage
  change.
- Trust rails byte-untouched in every generator; attribution untouched.
