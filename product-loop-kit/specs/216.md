  that URL **absent (0)**, prod-wide `pool_view` = 0 that day. n=1 — the mechanism is the finding, not a

- **The data and the generator to close the gap already exist and already ship.** Item 213 added
  `generate-pool-pages.js`, run in CI as `node generate-pool-pages.js --out pools --fixture

- **The trust rail is applied as a render-time filter, not by the contents of the `pools` array.**
  `app.js:1893`, `:1982`, `:2082` all gate on `pool.tvlUsd >= minTvl`, and `minTvl` defaults to

- **Deep-linked pool-detail rendering for sub-rail pools is existing, intended behaviour**, not something
  this item introduces: item 206 widened the audit rotation to the arrival population and item 215's run
  rendered **23 of 32** pool-details on sub-rail pools with **zero findings**.

## Hypothesis
We believe letting a `?pool=` arrival paint from a committed per-pool artifact when the pool is absent from
the railed snapshot will extend instant first paint from 11.5% to ~100% of the estate's 3,658 deep links,
because the payload it currently waits on (the multi-MB live feed) is orders of magnitude larger than the
~450 bytes of pool record the page actually needs to render. Confidence: **measured** on the mechanism
(byte sizes, populations, and the generator's existence are all facts on disk); **guess** on the user-harm
link (n=1 arrival, could have been a JS-running crawler) — 214's stance, unchanged.

## Change

**Leg 1 — `generate-pool-pages.js`: emit a JSON sibling next to every markdown twin.**
- For each deep-linked id it already resolves and writes `<id>.md` for, also write `<id>.json` into the same
  `--out` directory.
- **REUSE, never re-type** (2026-07-10 directive; 213's own reuse posture): the record projection and
  envelope come from `generate-pools-snapshot.js` — `projectPool()` (`:66`, the exact 13-field projection)
  and `envelope()` (`:91`, `{schemaVersion, generatedAt, source, minTvlUsd, count, pools}`). Export them
  from that module if they are not already exported; do not copy their bodies. The artifact is therefore
  **byte-shape-identical to one entry of `data/pools-snapshot.json`**, which is what makes it a drop-in for
  the renderer.
- `count` is 1 and `pools` is `[record]`. `minTvlUsd` must state the artifact's OWN floor honestly (the
  `seo-pools.json` floor of `1000`), not the snapshot's `10000000` — a sub-rail artifact claiming a $10M
  floor is a false trust claim.
- Stale-file cleanup: the generator already removes `*.md` from the out dir before writing
  (`generate-pool-pages.js:517-518`). Extend the same sweep to `*.json` so a pool that leaves the deep-link
  set cannot leave a stale paint artifact behind.
- `--out` isolation and the UUID shape gate (`UUID_RE`, `:61`) are unchanged.

**Leg 2 — `app.js`: use it when, and only when, the snapshot declines *because the pool is absent*.**
- `tryLoadSnapshot()` (`app.js:1126-1159`) currently returns a bare boolean and cannot distinguish "pool not
  in this snapshot" from "snapshot stale / 404 / malformed". Give it a discriminated result so the caller
  can tell those apart. Every existing degrade path keeps today's exact behaviour.
- New path, in `fetchPoolsInBackground()`: when the snapshot was **fresh and valid** (the existing
  `SNAPSHOT_MAX_AGE_MS` = 6h meta gate at `:1131-1133` passed) but the requested id was **absent**, fetch
  `/pools/<id>.json`. On success apply the SAME validations the snapshot gets — `schemaVersion === 1`, an
  array of exactly the pools it claims, and the same 6h `generatedAt` age gate — plus the same two-way id
  match `tryLoadSnapshot` already uses (raw `pool.pool` OR the legacy `project-symbol-chain` composite), so
  the artifact can never claim a pool the pool-detail resolver would then fail to find.
- On success: `setPools(snapshotPools.concat([record]))` and keep `poolsSourceRef.current = 'snapshot'`, so
  the 059-B3 escape hatch (`app.js:1196`) still fetches live if the effective `minTvl` later drops below the
  floor. Emit the existing `data_load_time` perf event with a `source` that names this path distinctly
  (e.g. `'pool-artifact'`) — reusing the emitter 214 repaired, adding no new event.
- On ANY failure — 404 (the expected state until the next CI run), non-OK, malformed, wrong schema, stale
  `generatedAt`, id mismatch, throw — fall through to `loadLive()`, i.e. **today's exact path**. The new
  code must never be able to make an arrival worse than it is today.
- The id is taken from `urlParams.pool` and must be **shape-gated before it reaches a URL** (the same
  `UUID_RE` the generator uses) so a hostile/legacy `?pool=` value cannot be reflected into a fetch path.

**Leg 3 — the estate/SEO surface is untouched.** No sitemap entry, no `llms.txt` entry, no `robots.txt`
change: `pools/<id>.json` is a data artifact for the app, not a page. `vercel.json` needs no rule — the
`.json` files are served as static files, and 213's markdown negotiation rule
(`vercel.json:109`, `/pools/:poolId.md`) is `Accept`-gated and unaffected.

**OUT of scope, explicitly:** any trust-rail change (`APY_SANITY_LIMIT`, `DEFAULT_MIN_TVL`, anomaly
flags/demotion, degen haircut); any change to which pools are eligible for the grid, planner, search or any
ranking (208's HARD invariant — a sub-rail record reaching the array must stay invisible to all of them at
the default floor); any change to `pool_view`/`pool_click` names, sources or timing; the 105 kpi merge;
`?token=`/`?chain=` grid arrivals; `PoolDetail.js`; `planner.js`; `home.html`; `translations.js` (this item
adds **zero user-facing strings** — it changes when existing content paints, never what it says); widening
`data/pools-snapshot.json` or the history/kpi population (that is 208, PARKED on a measured NO-GO).

**Generated artifacts are NOT committed in this PR** — 212/213 precedent: twins generated in this session
would come from a different DefiLlama fetch than the committed snapshot and estate HTML. Merging is the
trigger (`generate-pool-pages.js` and `app.js` are both in `sitemap-update.yml`'s push paths), so CI
produces the `.json` twins alongside the `.md` twins and the snapshot from ONE fetch. Disclosed cost: between
merge and that CI run, `/pools/<id>.json` 404s and every arrival takes today's live path — the degrade this
item is built to make safe.

## Territory notes
<!-- Build loop appends findings from the blindspot pass here. -->
- `SNAPSHOT_MAX_AGE_MS` is **6h** (`app.js:1107`) while `sitemap-update.yml`'s cron is **daily at 02:00
  UTC** (pushes to main also trigger it). So the snapshot-first path — and therefore this item's path, which
  is gated behind the same fresh-snapshot precondition — is active only in the hours after a regen. That is
  a pre-existing property of 214/059, NOT introduced here, and this item must not change the constant to
  make its own numbers look better. Worth a separate row if the human wants the window widened.
- `generate-pools-snapshot.js` writes the snapshot only when the data changed ("No data change — kept
  committed snapshot. Nothing written."), so the meta's `generatedAt` can lag a twin regen. That degrades to
  the live path (stale meta → decline), which is the safe direction.
