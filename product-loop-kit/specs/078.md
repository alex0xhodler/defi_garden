# 078 — Fix the dead sitemap health signal in the daily CI commit message

**Score:** 5.8 · **Risk:** HIGH (`.github/workflows/` = config/infra per NORTH_STAR) · **Promoted:** 2026-07-13 by a build loop (no READY items; qualification judgment recorded below)

## Evidence (all in-repo)

- `.github/workflows/sitemap-update.yml`, "Commit updated files" step: the daily commit
  message line is `Regenerated sitemap.xml with $(grep -c '<url>' sitemap.xml) URLs`.
- `sitemap.xml` has been a `<sitemapindex>` since the category split — verified 2026-07-13:
  `grep -c '<url>' sitemap.xml` → **0**, `grep -c '<sitemap>' sitemap.xml` → **110**.
  The real URLs live in the child `sitemap-*.xml` files (~23k total per LOG.md 2026-07-13).
- Every daily CI commit since the split says "0 URLs" (e.g. `b2debb8a2`).
- LOG.md 2026-07-13 NO-OP entry: a loop run burned an investigation on this exact line
  before concluding it was a message-only miscount ("cried wolf").

## Why this qualifies (overriding the prior run's "heartbeat candidate" call)

The commit-message count is the only per-run health readout of the regenerated SEO
surface, and the SEO surface is a named guardrail ("parameterized analytics URLs keep
rendering pool cards — that's the SEO lifeline"). With the count permanently at 0:

1. a REAL catastrophic regen (empty sitemaps) is indistinguishable from a healthy run —
   the signal is dead, not merely cosmetic;
2. it already produced a false alarm that consumed loop time (documented in LOG.md).

Restoring a truthful count re-arms the signal at near-zero cost.

## Change

In the "Commit updated files" step of `.github/workflows/sitemap-update.yml`, replace the
dead count with an honest two-number readout, e.g.:

```
- Regenerated sitemap index with <N> child sitemaps and <M> total URLs
```

where `N` = `<sitemap>` entries in `sitemap.xml` (the index) and `M` = total `<url>`
entries summed across all root `sitemap*.xml` files. Counting must be per-occurrence
(`grep -o … | wc -l` or equivalent), not per-file-line-count summed naively, and must not
fail the step when a pattern matches zero times (grep exits 1 on no match; the step runs
under Actions' `bash -e`).

## Acceptance criteria

1. The commit-message step no longer derives its count from `grep -c '<url>' sitemap.xml`
   alone; it reports BOTH the index child count and the total `<url>` count across all
   root `sitemap*.xml` files.
2. Running the exact new count command(s) from the repo root against the committed tree
   prints correct, non-zero values that match an independently computed per-file sum.
3. Honesty preserved: if the real total is ever 0, the message says 0 — no fudging, no
   fallback constants. A zero must remain visible; that is the point of the signal.
4. The diff is confined to the commit-message step of `sitemap-update.yml` — the
   `git add` list, change detection, push/rebase-retry logic, and every other step are
   byte-identical.
5. Zero-match safety demonstrated: the count command, run in a scratch dir with an
   index-only sitemap (no `<url>` anywhere), prints `0` and exits without killing a
   `bash -e` script.
6. Tests green (NORTH_STAR commands, 5-min timebox):
   `node test_planner.js && node test_protocol_parsing.js && node test_qualifier_fix.js`.

Not a UX item — no rendered-Playwright acceptance required (workflow-file change only;
nothing user-facing renders differently).
