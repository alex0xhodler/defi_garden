# 199 — explainer: the pool-detail audit gains a lens dimension

Risk tier **HIGH** (`audit-app.js` is the merge gate itself — 154/157/163/166/169/172/183/185/191/192
precedent — even though this item touches zero product code). Full walkthrough + quiz per NORTH_STAR.md's
HIGH-tier rule.

## Goal, in one sentence

Make responsive (360px), dark-mode and Korean defects on **non-anchor** pool-detail pages reachable by the
audit at all — today they are structurally invisible, on every tick, forever.

## The intuition

The pool-detail page is the north-star surface: both `pool_click` CTAs live there. Four items in a row
improved how well the audit covers it —

| item | fixed |
|---|---|
| 183 | **which** pool-details get audited (never-audited-first rotation) |
| 191 | **how many** (2 → 6 per tick) |
| 192 | how many, **honestly** (6 → 32, bounded by the clock, `renderedCount` ≠ `picked`) |
| 196 | the same never-audited-first memory for the static estate |

…and none of them touched **which lens**. The audit renders pool-detail at four lenses — 1280px light,
360px, dark, Korean — but only for one pool: the hardcoded `PREFERRED_POOL_ID`
(`audit-app.js:152`). Every one of the 32 pools rotated per tick is rendered at 1280px, light, English,
and nothing else. So a 360px clip, a dark-mode contrast break, or a Korean copy leak on any of the other
~734 pools had a **0% chance of ever being seen** — not a low chance, a zero one.

That matters because those are precisely the classes NORTH_STAR.md's pre-traffic mandate names as the ones
the human keeps finding by hand: *"format/i18n bugs, dead CTAs, responsive/dark"*. The checks existed and
ran; their sample size was 1.

## What changed, in reading order

**1. `audit-app.js` — three new constants (~line 300).** `LENSES = ['360px','dark','ko']`,
`DEFAULT_POOL_LENS_SAMPLE = 6`, `MAX_POOL_LENS_SAMPLE = 24`. The default is sized against 192's own
measurement (~0.19s marginal per rendered pool-detail; 116s of a 300s cap), and the comment says so — the
file's convention is that every budget number cites the measurement that justifies it.

**2. `buildPoolSurfaces()` — the lens block**, appended directly after the (byte-unchanged) rotation-pick
loop. For the first `lensSampleSize` rotation picks it emits one extra surface each,
`pool-detail:<prefix>@360px` / `@dark` / `@ko`, setting the same `width`/`dark`/`ko` flags the anchor
block already uses, and appending `&lang=ko` for the Korean lens exactly as `pool-detail-ko` does. Lens
surfaces are built **only** from rotation picks — never from prescan-promoted ids, never from the anchor.

**3. The lens rotates across ticks.** `lens = LENSES[(i + tickOffset) % 3]`, with
`tickOffset = hashSeed(`${seed}:poollens`) % 3` — the same date-derived seed the rotation already uses,
namespaced so it can't move in lockstep with `${seed}:pools`. Deterministic for a given seed (the
determinism contract `test_audit_app.js` enforces), different across days, so a re-picked pool accumulates
*different* lenses over cycles instead of always drawing the same one.

**4. `lensPick: true`, and emphatically NOT `rotationPick`.** This is the subtle part, and it is where the
item could have silently undone 192. `renderedRotationCount` and the throughput line
(`N pool-details/tick over M candidates -> full pass ~K ticks`) count `rotationPick` surfaces. A lens
surface is a **second render of a pool already counted once**; had it carried `rotationPick`, the coverage
number would have inflated by up to 6 per tick and the "full pass ~23 ticks" claim would have become a
lie. A separate marker keeps 192's honesty contract exactly where it was.

**5. The wall-clock guard sheds lens renders too** (`runAudit()`'s render loop). Eligibility widened to
`s.rotationPick || s.lensPick`, but a lens skip increments a **separate** `skippedLensCount` and is never
pushed into `skippedRotationIds` — because that array feeds 192's `seen` reconciliation, and a skipped
lens must not strip a pool from `seen`: the pool *was* rendered at 1280px by its own rotation surface
earlier in the same list. Only the extra lens render was shed.

**6. Reporting.** `poolRotation` gains additive fields only (`lensSampleSize`, `lensRendered`,
`lensSkipped`, `lenses`), and the CLI prints one more line —
`[audit] pool lenses: 6 rendered (360px x2, dark x2, ko x2) over 6 rotation picks, 0 skipped`, or an
explicit `disabled (…)` when the sample is 0. Never a silent absence, per this file's standing convention.

**7. `test_audit_pool_lens.js` (new, 7 assertions)** covering the lens shapes/urls/flags, `lensPick` set +
`rotationPick` unset, both clamps (ceiling and `rotationPicks.length`), the `AUDIT_POOL_LENS_SAMPLE=0`
kill switch, per-seed determinism with cross-seed variation, and rotation bookkeeping being identical with
the leg on vs off. Registered in `package.json`'s `test:serial` chain after `test_audit_static_rotation.js`.

## Deviation worth reviewing

**One assertion in `test_audit_pool_prescan.js` was repointed, under an explicit operator authorization
granted mid-build.** Its A6 case asserted `extraSurfaces.length === DEFAULT_POOL_SAMPLE` as a proxy for
"rotation still fills its own budget when promotion is off". Lens surfaces legitimately ride in that same
array, so the length became 38 and the assertion went red — a **stale proxy**, not a real defect: the
guarantee it names still holds exactly (`extraSurfaces.filter(s => s.rotationPick).length === 32`). The
fix is that one filter, plus a `// backlog 199` comment. The builder reported the red rather than
smuggling a fix past its allowlist, which is the behaviour we want; the scope extension was granted
explicitly and is recorded here and in `199-notes.md`.

The builder then proved the repointed assertion is not vacuous by shrinking the fixture's candidate pool
to 5 (too few to fill a 32-pick budget) and watching A6 go red, before restoring byte-exact.

## Evidence

- Paired end-to-end `node audit-app.js` runs from byte-identical fresh rotation state, scratch-redirected:
  **123s** with lenses, **118s** without, both exit 0, both far under the 300s cap.
- The lens-on run's `surfacesCovered` carries 2× `@360px`, 2× `@dark`, 2× `@ko`; the lens-off run's list is
  the lens-on list **minus exactly those six entries** (compared programmatically, not by eye).
- `poolRotation.{cycle,seenCount,candidateCount,picked,wrapped,sampleSize,renderedCount,truncated}`
  identical between the two runs — 192's contract intact.
- `test_audit_pool_lens.js` 7/7 · `test_audit_pool_prescan.js` 14/14 · `test_audit_static_rotation.js`
  13/13 · `test_audit_app.js` 3/3 · `test_audit_runner.js` 9/9 · plain lane 39/39.
- `test_audit_prescan.js` criterion 4 is red and was proven **pre-existing** on an `origin/main` stash
  baseline (probe-collision class) — untouched here, stated rather than implied green.
- **UNRUN**: the full `npm run test:browser` lane (~40 files × up to 600s) does not fit the 5-minute
  foreground timebox; every audit-family file was run individually instead.

## What this does NOT claim

It found nothing. Both runs report `1 total, 0 blocking`, and the lens leg originated **zero** findings in
its first six draws — expected on a small sample against an estate that has been clean for three days. The
item's value is that the next 360px/dark/KO defect on a non-anchor pool is now *findable at all*, which it
was not yesterday. No isolable Mixpanel funnel metric (0 traffic; same disclosure pattern as
183/191/192/196).
