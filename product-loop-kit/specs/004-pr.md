# PR: Surface the share CTA at the bloom moment (backlog 004)

**Risk tier (builder's guess): HIGH** — per the task's own pre-classification and per
NORTH_STAR.md's risk map ("new... anything user-facing beyond copy/styling" → HIGH → PR +
explainer + quiz, wait for the human). This is a new interactive element and a new placement
decision, not a pure copy/styling tweak, even though it reuses 100% pre-existing handlers.
Git is unavailable in this environment, so this file is the PR: no branch, no commit exists —
everything below is working-tree edits reviewable at the paths cited.

## Goal
NORTH_STAR.md's north-star metric is `share_link_opened → plan_created` weekly closures,
currently at **zero closures** because `share_link_created` itself is zero (167 sessions, 5
plans created, 0 shares — 2026-07-10, first active tracking day). Instrumentation was already
code-audited sound (002-notes.md) — the zero is a usage gap, not a tracking gap. Spec 004's
hypothesis: the share affordance is invisible/buried, so nobody engages it. Goal of this item:
make it visible at the moment a plan settles ("blooms"), using the existing share handlers,
smallest possible intervention, no redesign.

## Intuition
The bloom view (`Bloom(props)` component, planner.js:1216) renders a lot: hero number, plan
strip, persona ladder, growth chart, make-it-yours sliders, an "engine room" pool breakdown, an
ask box, caveats — and only THEN, as the very last thing in the whole tree, three small share
buttons. That's not "buried in a menu," but it is buried in scroll depth — a user has to get
through seven other sections to reach it. The fix isn't new share mechanics (copy-link and
native-share already work, already tracked); it's surfacing what's already there.

The non-obvious part: "surface it near the top" reads differently on mobile vs. desktop because
the bloom view is a 2-column grid that only exists on desktop. On mobile it collapses to one
column, and — this was already true before my change — the checkout/price panel renders FIRST,
above the detail column. On desktop, that same checkout panel is `position: sticky`, so it
rides along in the viewport as the user scrolls the (much longer) detail column. That panel is
therefore the one place in the tree that's reliably close to "immediately visible" at all three
required widths (360/768/1280). I put the new share prompt there, as a second card directly
below the existing checkout/waitlist panel — not merged into it, so the waitlist CTA (the
existing primary conversion action) keeps its own visual space untouched.

## What changed, walking the diff in reading order

### 1. `translations.js` — one new string, both languages
```js
// en.planner, after the existing shareFooter key:
sharePromptHeadline: "Your plan is ready — send it to someone who'd want one too.",

// ko.planner, same position:
sharePromptHeadline: "계획이 완성됐어요 — 이런 계획이 필요할 누군가에게 보내 보세요.",
```
No other new strings. The button itself reuses the pre-existing `shareNative` / `shareLink` /
`shareLinkCopied` keys — same words the footer buttons already use, so the vocabulary is
consistent wherever a user encounters "share" in this view.

### 2. `planner.js` — new element, wired into both bloom layouts
Defined once, right after `checkoutPanelElement` is built and before the archetype branch
(planner.js:2551-2563):
```js
// Share prompt — surfaced at the bloom moment (spec 004): a calm, visible
// nudge that reuses the existing doCopyLink/doNativeShare handlers.
// Prefers native share when available, else falls back to copy-link.
var sharePromptElement = e('div', { className: 'gp-share-prompt gp-animate-in' },
  e('p', { className: 'gp-share-prompt-text' }, t('sharePromptHeadline')),
  navigator.share
    ? e('button', {
        type: 'button', className: 'gp-share-btn gp-share-prompt-btn', onClick: doNativeShare
      }, '↗ ' + t('shareNative'))
    : e('button', {
        type: 'button', className: 'gp-share-btn gp-share-prompt-btn', onClick: doCopyLink
      }, copySuccess ? ('✓ ' + t('shareLinkCopied')) : ('🔗 ' + t('shareLink')))
);
```
Then wired into both return branches by adding it as a second child of the existing
`.gp-bloom-checkout` wrapper (subscription branch, planner.js:2569; target/growth branch,
planner.js:2583) — one-line change in each, `replace_all`-identical:
```js
// before:
e('div', { className: 'gp-bloom-checkout' }, checkoutPanelElement),
// after:
e('div', { className: 'gp-bloom-checkout' }, checkoutPanelElement, sharePromptElement),
```
`doCopyLink`, `doNativeShare`, and `copySuccess`/`setCopySuccess` are pre-existing — I call
into them, I don't touch their bodies. `doCopyLink` already fires
`Analytics.trackShareLinkCreated({ method: 'copy', ... })` (planner.js:1749) and
`doNativeShare` already fires the same with `method: 'native'` (planner.js:1772) — that's the
existing `share_link_created` event, unmodified, now reachable from two places instead of one.

### 3. `planner-styles.css` — new block, tokens only
Inserted after `.gp-checkout-note`, before the `768px` mobile media query
(planner-styles.css:580-600):
```css
.gp-share-prompt {

  font-weight: var(--font-weight-medium);
  color: var(--color-text);
  line-height: var(--line-height-normal);
}
.gp-share-prompt-btn { width: 100%; }
```
The button's className is `'gp-share-btn gp-share-prompt-btn'` — it inherits the pre-existing
`.gp-share-btn` hover/active/disabled rules (planner-styles.css:985-1002), including the
`:active { box-shadow: var(--neuro-shadow-pressed); transform: translateY(0); }` press-physics
CLAUDE.md requires, for free. The card's entrance uses the pre-existing `.gp-animate-in` /
`gpIn` keyframe (planner-styles.css:1155-1167), which is already globally switched off under
`@media (prefers-reduced-motion: reduce)` (planner-styles.css:1632-1636) — so reduced-motion
compliance required zero new CSS from me. No new colors — every value is a `--color-*` /
`--neuro-*` / `--space-*` / `--font-*` custom property, all of which already flip correctly
under `[data-theme="dark"]` (style.css), so dark mode needed no separate handling.

## Deviations from spec
- "Visible without scrolling/hunting" is reasoned through CSS structure (DOM order + `position:
  sticky`), not verified with a screenshot — no browser tool was used, per the task's own
  instruction. I'm confident in the "no hunting" half (it's the second card in the very first
  section painted); "no scrolling" is a structural best-effort, not a pixel-verified guarantee,
  since real viewport heights vary. Flagged in 004-notes.md for the verifier to check visually.
- Left the original 3-button `footElement` row completely in place — additive change, not a
  replacement. Spec doesn't ask for removal, and removing it would touch the one piece
  already proven sound end-to-end (002-notes.md) for no benefit.
- No dismiss/"seen it already" persistence was added. "Prompted once per plan at the bloom
  moment" is satisfied by the prompt living in the bloom view itself (it appears whenever bloom
  renders); a localStorage dismiss flag would be a new mechanic, which the spec explicitly
  rules out.
- No new button-label strings — reused `shareNative`/`shareLink`/`shareLinkCopied` rather than
  minting new ones, to keep the new prompt's vocabulary identical to the existing footer row's.
- Rejected a modal/interstitial reading of "emotional peak" as too close to an interruption
  pattern; used a calm, always-present inline card instead (consistent with "no dark patterns,
  no fake urgency" and with how the existing waitlist modal is opt-in-only, never auto-opened).
