## Goal
NORTH_STAR.md's Signals section says Mixpanel access is "**NOT YET WIRED for Claude Code** (backlog 001)," so every heartbeat runs signal-degraded — it reads a stale `signals/` snapshot instead of live funnels, and is explicitly told to "never invent numbers." This item wires a project-scoped Mixpanel MCP connection into the repo so a `claude -p` heartbeat (or any Claude Code session opened here) can query Mixpanel project defigarden (4042048) directly — the point being the north-star metric itself, the `share_link_opened → plan_created` funnel.

## Intuition
Claude Code already has a standard way to share tool access with an entire team: `.mcp.json` at the repo root, checked into version control, naming a remote MCP server by URL. Mixpanel ships exactly such a server (`https://mcp.mixpanel.com/mcp`, streamable HTTP transport) with two auth modes — OAuth (per-user browser sign-in) and service accounts (static header, meant for headless CI). The hard ban here is on committing any credential, and OAuth is the only one of the two that lets `.mcp.json` itself stay completely credential-free: the URL is public information, and the actual authorization happens out-of-band — browser OAuth, token cached locally by Claude Code, never touching a file this build loop can write. So the file's job is small: point at the server. A human authorizes it once, interactively, entirely outside this diff.

## What changed and why
- **Added `/.mcp.json`** (new file, repo root):
  ```json
  {
    "mcpServers": {
      "mixpanel": {
        "type": "http",
        "url": "https://mcp.mixpanel.com/mcp"
      }
    }
  }
  ```
  This is the literal structure Mixpanel's own Claude Code docs give, and matches what `claude mcp add --transport http mixpanel https://mcp.mixpanel.com/mcp --scope project` would generate on a machine with the CLI installed. `"type": "http"` is not optional — code.claude.com documents that a `url` with no `type` is a hard configuration error (Claude Code otherwise reads the entry as a broken stdio server and skips it). No `headers`, no `env`, no project/org ID in the file: the server resolves which Mixpanel projects are visible from whoever's OAuth session is attached at query time, and project 4042048 is a parameter inside individual tool calls (e.g. `Run-Query`), not part of the connection.
- **Added `product-loop-kit/specs/001-notes.md`** — sources (with URLs), the config rationale, and the exact sequence of human steps required before any of this does something, including two gates that are easy to miss: Claude Code's own project-server approval prompt (separate from Mixpanel auth) and the org-level "MCP enabled" admin toggle on the Mixpanel side.
- **No product code touched.** `app.js`, `planner.js`, `PoolDetail.js`, `home.html`, `translations.js` are all unmodified, so "tests still exit 0" is true by construction — nothing in this diff is in the tests' blast radius.

## Deviations from spec — what couldn't be executed in this sandbox, and why
This iteration ran with `git` unavailable for writes and the `claude` CLI unavailable entirely. Three of specs/001.md's five acceptance criteria are runtime verification steps that need one or both:

1. **"`claude mcp list` run inside the repo shows the Mixpanel server."** No `claude` CLI here. Separately, per code.claude.com, this would show `⏸ Pending approval` even on a machine that has the CLI, until a human interactively approves the project-scoped server once — a Claude Code trust gate that exists independent of whether Mixpanel auth is even set up. No config file, from any build loop, can satisfy this criterion by itself.
2. **"A fresh `claude -p` query for `plan_created` (7d, project 4042048) returns a number, output pasted into specs/001-notes.md."** Needs the CLI plus an already-authorized live connection. Neither exists here. `specs/001-notes.md` has an explicit PENDING block with the exact command for the human to run and paste output into, instead of a fabricated number.
3. **"`git grep` proves no token/secret string entered the repo."** `git` is unavailable in this sandbox. Substituted with a manual, checkable claim: `.mcp.json` contains exactly six string values (`mcpServers`, `mixpanel`, `type`, `http`, `url`, `https://mcp.mixpanel.com/mcp`) and nothing else was added that could hold a credential. A `git grep` regex for post-merge verification is in `specs/001-notes.md`.

None of these three were forced green by inventing output. Spec 001's own "Open questions" section anticipates a version of this gap ("If the official remote Mixpanel MCP endpoint can't be reached... mark BLOCKED"). This is not marked BLOCKED — nothing found here suggests the endpoint is unreachable, since the config is copied verbatim from Mixpanel's own current, generally-available Claude Code setup instructions — but live reachability from the machine that will actually run the heartbeat is genuinely unverified, not quietly assumed.

One more thing surfaced during research, not a spec deviation but worth flagging: spec 001's hypothesis is specifically about **unattended, scheduled `claude -p` heartbeats**. Mixpanel's own docs position OAuth as best for *interactive* use and service accounts as best for headless CI/automated agents — some tension with the heartbeat use case. OAuth tokens auto-refresh per code.claude.com, which should hold up fine most of the time, but a failed refresh surfaces as a `/mcp` prompt that a cron job can't answer. OAuth was kept here because the task and NORTH_STAR's standing decision both call for it explicitly ("credentials are never committed to the repo") — not overridden on my own judgment — but it's called out in `specs/001-notes.md` as something to watch across the first few heartbeat cycles.

## Post-merge human checklist
1. Confirm/enable MCP for org Equitee in Mixpanel (Settings → Org → Overview) — admin-only, off by default, up to 15 min to propagate.
2. Open this repo in Claude Code once, interactively; approve the `mixpanel` project-scoped server when prompted.
3. Run `/mcp` (or `claude mcp login mixpanel`) and complete the Mixpanel OAuth flow in a browser.
4. Run `claude mcp list`; confirm `mixpanel` shows connected, not pending or failed. Paste into `specs/001-notes.md`.
5. Run a fresh `claude -p` query for `plan_created` (7 days, project 4042048); paste the output into `specs/001-notes.md`.
6. Run the `git grep` sanity check from `specs/001-notes.md` for secret-shaped strings.
