# Spec 206: the audit's pool-detail rotation draws from the $10M snapshot, not from the surface users actually arrive on

## Evidence

All measured on `origin/main` @ `c72c90cf6`, 2026-08-02, against the committed
`data/pools-snapshot.json` and a live DefiLlama fetch (15,822 pools). Numbers verbatim from
`signals/2026-08-02.md`.

- `audit-app.js` resolves its pool population from `data/pools-snapshot.json` (`:610`, `:1556`). This
  tick's own run log: `pool rotation: cycle 0, seen 80/734 candidates … rendered 32/32`.
- The generated SEO estate emits **3,669 distinct `?pool=<uuid>` deep links** (extracted from
  `tokens/*.html` + `chains/*.html`; the KO estate emits the **identical** 3,669 — set difference 0).

| population | count | share |
|---|---|---|
| generated `?pool=` deep links | 3,669 | 100% |
| present in `data/pools-snapshot.json` → rotation-reachable | **420** | **11.4%** |

- TVL distribution of the deep-linked set (live feed): median **$515,134**, min **$100,015**, 61.7% below

  **The floors are not the bug. The audit silently inheriting one of them as its population is.**

  `/tokens/jitosol` → `/?pool=fdcccd6a-a491-4c30-8024-5677bd3f0993` (prod `page_view` 7d, query

- Defect history (from `product-audit.md`, item 167): **every** hand-found pool-detail bug — 122, 144, 145,
  165 — was on a non-flagship pool. None was reachable from the flagship end of this population either.

## Hypothesis

We believe **aiming the pool-detail rotation at the deep-linked arrival population (3,669 ids) instead of
the snapshot (736)** will **surface render-only defects on the north-star surface that no current signal
can reach**, because the audit's clean-run claim is currently scoped to the richest 11.4% of pools while
100% of observed arrivals land in the other 88.6%. Confidence: **validated-pattern** — this is items
154/157/167/197's rule (`detector-signal-coverage.md`) on its fourth axis, and each prior instance
converted a "clean" population into real findings.

## Change

Smallest version that tests the hypothesis:

1. `audit-app.js` gains a pool-population source that is the **union of** the snapshot ids and the
   `?pool=` ids extracted from the generated estate (the same extraction `prescanStaticPages`'
   `pool-link-liveness` signal already performs — **reuse it, do not write a second extractor**).
2. Pools not in the snapshot have no snapshot record to drive a fixture from, so their surfaces render via
   the **live-fetch path** the app itself uses for `?pool=` (`snapshotEligible = !urlParams.pool && …`,
   `app.js:1144`) — i.e. the fixture serves `yields.llama.fi/pools` in the **LIVE shape**
   (`{status:'success', data:[…]}`, `apy` per pool), per `product-audit.md`'s fixture-trap #1. Getting this
   shape wrong silently renders 0 results and fabricates a dead-end finding.
3. Rotation/seeding/lens machinery is **unchanged** — reuse `sampleBySeed()` and the existing
   `audit-rotation.json` memory (196), adding the new candidates to the same rotation rather than a
   parallel one. Persist rotation state for the widened population so successive ticks work through it.
4. Emit the population split in the findings JSON (`poolRotation: {snapshotIds, deepLinkIds, union,
   reachable}`) so a future reader can tell coverage from luck.

**OUT of scope:** any change to `DEFAULT_MIN_TVL`, `APY_SANITY_LIMIT`, the snapshot's own floor, the grid,
the planner, ranking, or which pools the product displays. This item changes **what the scanner looks at**,
nothing the user sees. Also out of scope: the kpi-backfill gap (that is 207) and widening the kpi/history
population (208).

## Acceptance criteria

- [ ] `audit-app.js`'s pool rotation candidate count is **> 3,000** (union of snapshot + deep-linked ids),
      verifiable in the run log line `pool rotation: … seen N/M candidates` where M > 3,000.
- [ ] At least one rendered surface in `surfacesCovered` is a pool **absent from
      `data/pools-snapshot.json`** — assert by extracting the rendered pool ids and checking set membership.
      A run that renders only snapshot pools is a FAIL even if M > 3,000.
- [ ] **Positive control (required — a widened population that finds nothing proves nothing):** a scratch
      run with an injected malformed sub-rail pool (e.g. `apyMean30d` above `APY_SANITY_LIMIT`, or a
      non-finite KPI) produces a finding on that pool's surface, and the same run without the injection
      does not. Record both transcripts.
- [ ] The pool-id extraction is the **existing** `pool-link-liveness` extractor, not a second copy —
      verifier greps for exactly one `[?&]pool=` extraction regex in `audit-app.js`.
- [ ] Sub-rail surfaces render via the LIVE-shape fixture; a run must **not** report a wave of
      `empty-table`/dead-end findings caused by the snapshot-shape trap. If sub-rail renders produce >10%
      dead-end findings, treat it as a fixture bug and fix the fixture, never downgrade the finding.
- [ ] Wall-clock stays inside the existing cap (`status: "OK"`, not a timeout); if the widened population
      cannot fit, the rotation budget — not the population — is what shrinks, and the run log says so.
- [ ] `data/pools-snapshot.json`, `app.js`, `PoolDetail.js`, `planner.js`, `translations.js`,
      `compute-kpis.js`, `generate-*.js` and every trust-rail constant are **byte-untouched**.
- [ ] Tests: existing `audit-app.js` test files stay green (`npm test`); per `product-audit.md`'s 154 trap,
      scope any "clean run" acceptance test to the surfaces it was written about rather than filtering a
      true positive away.
- [ ] Instrumentation: none — this is a scanner-side change with no user-facing surface and no event.
      Its observable is `signals/audit-findings.json`'s new `poolRotation` block plus the daily finding count.

## Measurement

Metric: findings raised on **sub-rail** pool-detail surfaces (new `poolRotation` block + finding surface
ids) · Window: 14 days · Decision rule: **keep** if the widened rotation produces ≥1 finding on a
non-snapshot pool that the old population could not have reached, OR completes ≥2 full rotation cycles with
zero findings **and** the positive control demonstrably fires (a proven-non-vacuous clean run is a real
result, per LEARNINGS 2026-07-27 takeaway 2). **Revert-candidate** if it produces a sustained flood of
fixture-caused dead-ends, or pushes the run past its wall-clock cap.
Minimum sample per NORTH_STAR.md — no funnel claim is made by this item.

## Risk tier (builder's guess — verifier assigns independently)

**HIGH.** Not because the blast radius is user-facing (it is not — `audit-app.js` ships no product code),
but because NORTH_STAR's policy says *when in doubt → HIGH* and this item touches the gate that every other
item's "clean" claim rests on. A rotation change that quietly reduces effective coverage, or a fixture
change that makes real findings look like harness noise, is a **relaxation wearing a refactor's clothes**
(`pre-existing-red-triage.md`, Resolution E). The positive-control criterion exists precisely to make that
detectable.
