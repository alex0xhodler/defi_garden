# Spec 065: Waitlist value-prop framings — pitch variants, instrumented

## Evidence
- BACKLOG 065 (heartbeat 2026-07-12, re-scored 2026-07-13): "061 reframed the copy once; test 2-3 honest card pitches (yield-funded framing) pre/post over 14d, EN+KO, instrumented; pick the winner on submit-rate." Gate was "sequence AFTER 064" — 064 (spotlight → waitlist attribution) SHIPPED 2026-07-13, so the sequencing constraint is satisfied.
- NORTH_STAR.md 2026-07-12 interview Q2 (human's own words, the only approved source of pitch substance): yield-funded subscription CARD — "Users deposit with us into the protocol (position always self-manageable), each position gets a DISPOSABLE CARD that pays a subscription from the yield (e.g. $23/mo yield → Claude sub)"; "Card copy stays honest: it's a waitlist for early access, the card does not exist yet — no fake availability."
- Heartbeat 2026-07-13: waitlist funnel verified sound end-to-end but has ~0 entrants; distribution (X spotlights, 060/064) is the traffic source. Building the variant plumbing NOW (no traffic dependency, same reasoning that let 063 ship) means the framing test is armed the moment spotlight posts land traffic — spotlight links can carry a `pitch` param from day one.
- Constraint discovered from 061: item 061 is SHIPPED (measuring until 2026-07-26) on the current copy. The DEFAULT rendered copy must therefore stay byte-identical to 061's copy; new framings ship behind an explicit variant switch only. Anything else corrupts 061's pre/post window.

## Hypothesis
We believe different honest framings of the same card mechanic (flip/"keep the money" vs ownership/"withdraw anytime" vs 061's feature-first framing) will convert waitlist_opened → waitlist_submitted at measurably different rates, because the ICP is trust-driven and the framing is the only variable at that step. Confidence: guess (no framing has ever been compared; 061 itself is still mid-window).

### 2. planner.js — variant resolution
- One module-scope constant, computed once from the URL: `pitch` param, normalized — `'b'`/`'c'` accepted (case-insensitive), anything else → `'a'`.
- A tiny helper mapping a base key to its variant key (`waitlistTitle` → `waitlistTitleB` when variant is `b`, etc.).
- Apply at ALL SIX render sites: bloom modal (title h2, benefits p, backdrop `aria-label`) and quick modal (same three). No other copy varies — `waitlistGarden`, `ctaWaitlist`, `waitlistJoin`, step-2 screen, no-spam line all stay constant across variants so the framing is the only variable.

### 3. Instrumentation — `pitch_variant` on every waitlist event
- analytics.js: the five waitlist trackers (`trackWaitlistOpened/Submitted/EmailEntered/SubmitAttempt/Error`) each add `pitch_variant: context.pitchVariant || null` to the tracked props.
- planner.js: every waitlist tracker call site — BOTH modals (bloom ~planner.js:1576-1643, 2404-2560; quick ~3564-3691) — passes `pitchVariant: <the constant>`. Every waitlist event from either modal must carry `pitch_variant` `'a'|'b'|'c'`, never undefined.
