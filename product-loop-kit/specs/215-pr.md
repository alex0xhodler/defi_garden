# 215 — PR explainer (HIGH tier)

**What shipped:** `audit-app.js`'s pool **prescan** stopped reading `data/pools-snapshot.json` alone
(734 pools) and now reads the **same union population item 206 already computes for the rotation**
(3,958 pools) — the snapshot plus live records for the SEO estate's own `?pool=` deep links. The
records were already in memory; the prescan simply was not pointed at them.

---

## Goal

Make the cheap checks cover the population the expensive checks already draw from.

## Intuition — a population widened in one leg and not the others

Item 206 (shipped one day earlier) fixed a real blind spot: the pool-detail **rotation** was drawing
candidates from the $10M-railed snapshot, so 88.6% of the pool pages our own SEO estate links to could
never be picked. 206 widened that to `snapshot ∪ (estate ?pool= ids ∩ live feed)`.

But "the population" is read by more than one leg. The **prescan** — the pure-record predicates that
need no browser at all (`apy-rail-breach`, `mean30d-rail-breach`, `absurd-magnitude`, `missing-tvl`,
`kpi-nonfinite`) — kept reading the snapshot. The first post-206 tick said so out loud, in one JSON file:

| leg, same run, same file | population |
|---|---|
| `poolRotation.union` | 3,964 |
| `poolPrescan.candidates` | 734 |

Two legs of one checker reporting different sizes for "the pools," 5.4× apart. That gap has a cost with
a number on it: the sub-rail 3,230 pools were reachable **only** through the 32-renders-per-tick
rotation — a ~124-tick (~4-month) full pass — for predicates that require no render whatsoever. Every
absurd-number bug in this backlog's history (122, 144, 165) was hand-found on a non-flagship pool, which
is exactly the population that was waiting four months for a check that costs microseconds.

The data was never missing. `loadLivePoolIds()` has retained the **full** live records since 206 —
kept expressly so `runAudit()` could build sub-rail fixtures "without a second fetch." The prescan just
wasn't handed them.

## What changed, in reading order

1. **The 206 union block moved up** (`audit-app.js:2924-2980`). It computed
   `snapshotIdsArr`/`subRailOnlyIds`/`unionIds`/`deepLinkSource` *after* the prescan; the prescan now
   needs those values, so the block was **hoisted, not rewritten** — byte-identical logic, comments and
   `console.error` degrade notes. (The verifier confirmed this by extracting both copies and diffing
   them: zero differences.) Reuse the set expression, never a second copy — a drifted population is the
   precise failure this whole axis exists to prevent.
2. **Live records for the sub-rail ids** (`:2982-3002`), via a new additive opt `livePoolRecords`,
   forwarded from `liveness.pools` at the `runAudit()` call site (`:4103-4111`). No second fetch.
3. **The prescan input becomes the union** (`:3026-3028`): `pools.concat(subRailOnlyRecords)`.
4. **The correctness trap — promoted sub-rail surfaces are marked `subRail: true`** (`:3113-3117`).
   Until now every promoted id was *guaranteed* to be a snapshot id, so the promotion path never needed
   the marker. Now a promoted id can be sub-rail, and `runAudit()` (`:4314`) builds its live-shape
   fixture set from exactly that marker. Unmarked, a promoted sub-rail pool would render against a
   fixture containing no record for it and the scanner would report a **fabricated dead-end** — a bug in
   the bug-finder, on the north-star surface. One marker, two producers (promotion + rotation), one
   consumer, all reading the same `subRailOnlyIds`.
5. **`kpi-nonfinite` applicability is now explicit** (`:2457-2534`, `:3090-3096`). Live records carry no
   `kpis` object, so they *cannot* trip this signal. That is **"not applicable," not "checked and
   clean"** — the item-197 trap. `poolPrescan` now reports `kpiApplicable` (734, exactly the snapshot
   leg) plus a note, so a zero can never be misread as coverage.
6. **Per-leg counts and the degrade reason ride on `poolPrescan` itself**: `scannedByLeg`
   `{snapshot: 734, deepLinkedLive: 3224}` and `deepLinkSource` — the same string `poolRotation`
   already reports, reused rather than duplicated. A degraded tick falls back to snapshot-only **and
   says so in place**, never silently narrower (206's degrade contract, inherited).
7. **The aggregate finding's wording** (`:3039-3049`) went from "N of M **snapshot** pools match" to
   "N of M **union** pools (X snapshot + Y deep-linked-live)". The old sentence became false the moment
   M stopped being the snapshot count.

## What it bought, measured

| quantity | before | after |
|---|---|---|
| `poolPrescan.scanned` | 734 | **3,958** (= `poolRotation.union` exactly, same run) |
| `mean30d-rail-breach` suspects | 1 | **15** — 14 new, every one verified live-feed-real |
| `missing-tvl` suspects | 0 | **0** (the feared flood did not happen) |
| wall-clock, full `node audit-app.js` | — | 3m22.6s union vs 3m23.4s snapshot-only — **no measurable cost** |

The 14 new suspects are all low-liquidity DEX pairs the $10M snapshot floor excludes (quickswap
WMATIC-USDC at 21,383% `apyMean30d`, uniswap-v3 USDT-ESPORTS at 1,336%, …) — the arrival population,
found same-tick instead of within four months. The true-negative control holds: with the live leg off,
the run reproduces exactly the one previously-known suspect (`201e5f6e`).

**Honest scope note:** this closes *prescan* coverage, not *render* coverage. A sub-rail pool now gets
its numbers checked every tick, but the render-only classes (dead CTA, i18n leaks, 360px clipping,
console errors) still reach it only through the unchanged 32-picks/tick rotation. Raising that budget is
a separate wall-clock decision with its own guard (192), deliberately out of scope here.

## Deviations from the spec

- The spec's acceptance text names `poolPrescan.candidates`; the field is and remains `scanned` (the
  spec's own Change section says `scanned` becomes the union total). Prose mismatch, not a missing field.
- `emptyPoolPrescanResult()` gained the same new fields defaulted to zero — shape consistency with the
  file's "never null-check a result" convention. Additive, not spec-required.
- Pre-existing test A3b gained `poolLiveness: false`. This is a **real behavior change worth knowing**:
  any unscoped `runAudit()` fixture test now pulls real population data into the prescan. The verifier
  examined this specifically and ruled it a legitimate determinism fix that *restores* the test's
  original scope (its assertion was strengthened, not weakened) rather than masking a regression.
- **A documentation defect was caught by the verifier and corrected before merge:** the builder recorded
  `signals/audit-static-rotation.json` as "already dirty before this session — pre-existing drift."
  It wasn't; pickup-time `git status` was clean and this session's own pre-redirect audit run mutated it.
  The operator reverted the file (it is heartbeat-owned run artifact) and corrected both notes files. The
  forward rule now lives in the spec's Territory notes: redirect **both** rotation-state env vars before
  the **first** run, and never attribute a dirty file to prior drift without checking pickup-time status.
