# 156 — PR explainer: the smoke gate was watching a door the product stopped using

## The goal

Make `npm test`'s smoke gate actually guard the route that every non-parameterized visitor lands on,
and stop a permanently-red test suite from training the loop to skim its own output.

## The intuition

On 2026-07-15 the product changed which page lives at `/`. It used to be the planner. It became the
search-first landing. The router grew a third branch to say so:

```js
// home.html:82 — today
window.__APP_MODE = needsAnalytics ? 'analytics' : (needsPlanner ? 'planner' : 'landing');
```

Two tests never got the memo, and kept asserting the two-mode world. They have been red on `main` for
twelve days. Nothing about them was subtle — they were simply pointing at a door the product no longer
uses, and reporting, correctly and uselessly, that nobody was coming through it.

The interesting part is not the fix. It is what a permanent red costs. `package.json`'s `test` script is
one long `&&` chain of **90** files. `test_smoke.js` sits at position **9**. So for twelve days a plain
`npm test` stopped at file 9 and **81 test files never executed at all** — and a suite that dies at file
9 of 90 looks, from the exit code, exactly like a suite that dies at file 90. Every loop in that window
recorded "pre-existing red, not mine, moving on" and was individually right to.

## What changed, in reading order

### 1. `test_hub_pages.js` (+4/-1)

One assertion, repointed at the verbatim current router line, with a comment naming the pivot so the
next reader knows why the string is what it is:

```js
test('the router (__APP_MODE) and canonical logic are untouched by this diff', () => {
  // 2026-07-15 landing pivot: the router grew a third mode ('landing') for
  // bare / — pre-pivot it was a two-mode analytics/planner ternary.
  assert.ok(homeHtml.includes("window.__APP_MODE = needsAnalytics ? 'analytics' : (needsPlanner ? 'planner' : 'landing');"), 'router logic changed');
  assert.ok(homeHtml.includes('window.__canonicalFor(window.location.search)'), 'canonical logic changed');
});
```

The test's *job* is unchanged: go red if a diff alters the router or canonical logic. Only the snapshot
of "current" moved.

### 2. `test_smoke.js` (+15/-4)

The stale bare-`/` case became **two** cases, per viewport:

```js
await test('bare / renders the search-first landing at ' + viewport.width + 'px', async () => {
  const { page, errors } = await loadAndCollectErrors(browser, '/', viewport);
  await page.waitForSelector('[data-testid="landing-search"]', { timeout: 10000 });
  const plannerMounted = await page.locator('#planner-root .gp-app').count();
  await page.close();
  if (plannerMounted !== 0) throw new Error('planner mounted on bare / (expected only the landing)');
  if (errors.length) throw new Error('page errors:\n' + errors.join('\n'));
});

await test('/plan.html renders the planner at ' + viewport.width + 'px', async () => {
  const { page, errors } = await loadAndCollectErrors(browser, '/plan.html', viewport);
  await page.waitForSelector('#planner-root [class*="gp-"]', { timeout: 10000 });
  await page.close();
  if (errors.length) throw new Error('page errors:\n' + errors.join('\n'));
});
```

Three things are deliberate here.

**The second case exists so the gate does not shrink.** The obvious fix — repoint bare `/` at the
landing and stop — would have taken a HIGH-tier gate covering two sacred router paths down to one,
while every test printed green. A pivot *moves* a behavior; it rarely deletes it. `/plan.html` is where
the planner went (planner-mode by path via `isPlannerPath`), so that is where its coverage went.

**The negative assertion.** Asserting the landing mounts is weaker than also asserting the planner does
*not*. It mirrors `test_landing.js:74`, the sibling test that had been asserting the correct behavior
the whole time — and whose existence is the single strongest tell that the failing test was stale
rather than catching a regression.

**`data-testid` over class shapes.** `[class*="gp-"]` is a fragile hook that only worked until someone
renamed a route. The replacement uses a stable test id so this assertion is less likely to become the
next stale one.

And the quiet win: every one of these cases ends with `if (errors.length) throw`. On bare `/` that check
had **never executed**, because `waitForSelector` threw first. The default route now has page-error
collection at three viewports for the first time since the pivot.

### 3. `product-loop-kit/playbooks/pre-existing-red-triage.md`

The playbook from item 147 had already predicted this item — it named `test_smoke.js` as the next
stopper and pre-classified it as rule **B** (stale test). Updated, not duplicated, with the two things
this run actually learned. See "The misdiagnosis" below.

## The misdiagnosis worth reading

LOG.md's 2026-07-25 item-142 entry classified `test_smoke.js` as rule **C** — *"sandbox render-timeouts
CONFIRMED pre-existing at HEAD"* — and that reading held for four more loops. It was wrong, and the
disproof was already printing in every run:

```
network: yields.llama.fi reachable — serving live snapshot captured via curl
  ✗ bare / renders planner UI at 360px      → waiting for '#planner-root [class*="gp-"]'
  ✓ /?token=USDC renders pool cards at 360px
```

The test's own network banner said **reachable**, and the analytics route rendered in the same browser,
at the same viewport, in the same run. A blocked sandbox cannot fail one route and pass another.
Environment reds are indiscriminate; stale-assertion reds are surgical — that is now a trap entry in the
playbook, because a *confident wrong* classification is more durable than an unclassified red. It stops
people asking.

## Verification

Builder-run, then independently re-run by the operator, then independently re-derived a third time by
the verifier subagent:

| | before | after |
|---|---|---|
| `node test_hub_pages.js` | exit 1, 41 passed | **exit 0, 42 passed** |
| `timeout 280 node test_smoke.js` | exit 1, 5 passed / 3 failed | **exit 0, 11 passed** |

Non-vacuity proven by execution in both directions: reverting `home.html:82` to the two-mode router
turns `test_hub_pages.js` red (`router logic changed`) and restoring it turns it green; pointing the
landing selector at a non-existent test id turns `test_smoke.js` red at all three viewports (8 passed)
and restoring it returns 11.

## What this does NOT do

It does not make `npm test` green. The chain now clears position 9 and stops at position **10**,
`test_landing.js` — red on `main` before this diff and still red, failing `page.waitForURL` after typing
into the landing search. **The product is fine**: a direct Playwright probe drove that exact flow this
run and the URL became `/?token=USDC` correctly, so it is a harness artifact in that test. One item, one
red class. It is the recorded next stopper and the next promotion candidate.

## Deviations from spec

1. `test_smoke.js`'s doc-comment (lines 1-8) was rewritten to describe the three current routes. Not
   requested; left alone it would be a stale comment sitting directly above the fix.
2. Mid-run, the builder reverted the operator's concurrent edits to the playbook file, correctly
   following the spec's literal *"if anything else appears, revert it"*. Re-applied afterward. Recorded
   as a coordination hazard: that instruction should be scoped to product code, not "revert on sight".
3. No server-handler change was needed for `/plan.html`; the existing `path.join` already serves it.
   Confirmed by execution rather than inspection.

## Risk

Test-only. `home.html`, `landing.js`, `app.js`, `planner.js`, `translations.js` and every generated SEO
artifact are byte-identical to `main`. No dependency change. No NEVER-list category touched: no trust
rail weakened, no credentials/money, no SEO deletion, nothing in `telegram-bot/`, `whatsapp-bot/` or
`workers/`. The diff *asserts on* the IA router but does not modify it — which is exactly why the tier
question was handed to the verifier rather than assumed.

**Verifier verdict: PASS, 7/7 — tier LOW, disagreeing with the proposed HIGH.** Its reasoning, recorded
because the disagreement is the useful part: the risk policy lists *tests* under LOW (this is 50 lines,
no new deps); the HIGH bucket covers changing router *behavior*, and `home.html` was proven
byte-identical to `main`; and it declined to invoke "when in doubt → HIGH" on the grounds that it was
not in doubt — it had just proven by execution that a real router change still trips this test red, so
the diff strengthens rather than weakens the safety net. Every quantitative claim above was re-derived
independently, including a separate `git worktree` at `origin/main` to confirm `test_landing.js` is red
there too.
