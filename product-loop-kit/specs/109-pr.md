# 109 — HIGH-tier explainer + quiz (Cloudflare Worker pool-history poller)

## What shipped
A Cloudflare Worker that builds the "our own database" leg of the data-layer movement. On an **hourly Cron
Trigger** it fetches `yields.llama.fi/pools`, applies the trust rails, and appends slim rows
`(pool_id, ts, apy, tvl_usd)` to a **Cloudflare D1** SQLite table. An authed `GET /history?days=N` lets the
daily CI (ticket 110) read the window and compute richer KPIs (stability, momentum, TVL-trend, and the 117
Sharpe ratio) over real history instead of the 30-day file-history.

Files: `schema.sql`, `wrangler.toml`, `src/poller-core.js` (pure logic), `src/poller.js` (Worker),
`test_poller.js` (21 offline asserts, in `npm test`), `.gitignore` (+`.wrangler/`).

## Why it's shaped this way
- **Poller/CI store, NOT a request-path backend.** The app FE never calls the Worker — KPIs bake into the
  static snapshot at CI time. So the no-backend tenet holds on the read path; only the CI + the Worker
  touch the DB.
- **Cloudflare (not Turso)** because it's already in the stack, gives a reliable intraday scheduler
  GitHub Actions cron can't, and writes history without a repo commit — avoiding the Vercel deploy-churn
  problem (081/083).
- **Trust rails mirror the shipped snapshot exactly**: $10M TVL floor is the only drop; anomalous >1000%
  pools are KEPT and flagged (never hidden). This preserves byte-equivalence with the file-history path
  (ticket 110). See specs/109-notes.md for the anomaly-handling correction this build made to spec 108.

## Deploy is human-owned (ticket 108)
Loops never handle credentials. The code is ready; the human runs `wrangler login / d1 create / d1 execute
/ deploy / secret put READ_TOKEN`, then adds `HISTORY_ENDPOINT` + `HISTORY_TOKEN` to GitHub Actions
secrets. Until then the Worker is committed but not deployed, and the KPIs keep running on the daily
file-history.

## Risk
HIGH — new Worker infra + a new trust-rail enforcement point whose logic must never drift from the
snapshot. Additive (no product code touched), rails verified byte-equivalent, no credentials committed.

## 5-question quiz (HIGH-tier gate)

1. **Why are anomalous (>1000% APY) pools KEPT in the history store instead of dropped?**
   Because the shipped snapshot keeps + flags them (generate-pools-snapshot.js filters on TVL only), and
   ticket 110 needs the DB population to be byte-equivalent to that file-history. Dropping them would
   silently diverge the two paths and remove flagged pools from the KPI series.

2. **Does the app's front-end read this Worker/D1 at request time? Why does that matter?**
   No. KPIs are computed in CI and baked into the static snapshot the FE already reads. That keeps the
   no-backend tenet intact on the read path — the Worker is a poller/CI store, not a request backend.

3. **What happens to `GET /history` if the `READ_TOKEN` secret is not configured?**
   It returns 503 (fails CLOSED) — it never serves data without a configured token. A missing/wrong
   `Authorization: Bearer` header returns 401. The auth check runs before path routing.

4. **Why must `apy` be `round(apyBase+apyReward, 4)` using compute-kpis.js's exact `round()`?**
   So the values the Worker stores are identical to what `slimPoint` writes to the file-history — required
   for ticket 110's DB path to produce byte-identical KPI series as the file path.

5. **Which single human action unblocks the deploy, and why can't the loop do it?**
   Provisioning the D1 DB + deploying the Worker + setting the `READ_TOKEN`/GH secrets (ticket 108). Loops
   never handle credentials (NORTH_STAR NEVER-list); the Worker also runs on the human's Cloudflare
   account and CI reads via GitHub secrets the human owns — none of which lives in a loop's sandbox.
