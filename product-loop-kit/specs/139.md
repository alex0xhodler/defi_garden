# Spec 139: archetype-aware planner endings — pool-first CTA for target/growth (bet A)

## Evidence
docs/strategy-2026-07-23-pretraffic-bets.md §3, BET A (human-approved 2026-07-23): the planner Bloom
checkout panel (`checkoutPanelElement`, planner.js) shows ONE primary CTA for every archetype —
`t('ctaWaitlist')` "Join the waitlist →", opening the card-waitlist modal whose copy says "your
garden's yield pays your subscription automatically through a simple card." That's the right ending
for SUBSCRIPTION (the card IS the business model, 2026-07-12 standing decision) but goal-incoherent
for TARGET (sneakers, iPhone) and GROWTH (retirement, home) plans — a user who just described saving
for retirement sees copy about a subscription-paying card. The v2 spec's §4.4 primary CTA ("Start
growing on <top pool's project> →" deep-linking the best pool) was never implemented; pool links
survive only as below-the-fold Engine-room cards.

## Hypothesis
We believe routing TARGET/GROWTH plan completions onto the top curated pool's detail page (instead of
the goal-incoherent card waitlist) will (a) repair a trust-damaging copy mismatch and (b) increase
`pool_view` and downstream north-star `pool_click{source∈{garden_cta,protocol_link}}` from planner
sessions, because it moves completers directly onto the pool-detail conversion surface instead of a
dead-end waitlist ask that doesn't match their goal. Confidence: guess (pre-traffic — see Measurement).

## Change
- SUBSCRIPTION archetype: **unchanged**. Card waitlist stays the primary CTA with existing copy.
- TARGET/GROWTH archetypes: primary CTA becomes "Start growing on `<top pool's project>` →", linking to
  `/?pool=<pool.pool>` of `curated[0]` (the same trust-railed pool list the Engine-room cards already
  render — reused, not recomputed). Waitlist demotes to a secondary text link ("Want this automated one
  day? Get early access →") reusing the existing `.gp-share-textlink` component (no new CSS). The modal
  branches its title/benefits copy by archetype: subscription keeps the existing (pitch-variant-aware)
  keys; target/growth get new honest early-access keys that never claim the card pays anything.
- Edge case: if `curated` is empty/unavailable when the panel renders (loading, or genuinely no pools),
  falls back to the waitlist-primary layout — never a dead pool link.
- Instrumentation: the new primary CTA calls `Analytics.trackPoolClick(topPool, 'plan_checkout', {
  archetype })`, which (per `trackPoolClick`'s existing convention of cherry-picking specific `context`
  keys rather than spreading it — confirmed by reading analytics.js, same gap item 125 hit for
  `ctaPlacement`) required one additive line in `analytics.js` to actually emit `archetype`. `source`
  stays a NEW disjoint value (`plan_checkout`) — never reuses `garden_cta`/`protocol_link`/
  `yield_calculator`, so the north-star `source` filter is unpolluted. Waitlist-open tracking for the
  demoted secondary CTA is untouched (reuses the existing `Analytics.trackWaitlistOpened` call).
- OUT OF SCOPE: PoolDetail.js/app.js (untouched), the `__APP_MODE` router, `?token=/?chain=/?pool=`
  semantics (linking TO `/?pool=` is fine, the semantics of that page are untouched), analytics.js load
  order, trust rails (APY_SANITY_LIMIT/DEFAULT_MIN_TVL/anomaly flags/degen haircut — `curated` already
  passed through these before this item touches it).

## Territory notes
- `curated`/`autoCurated` (planner.js ~1480-1520) is the single source of truth for the Engine-room pool
  cards; `curated[0]` after `curatePools`'s sort (APY desc within persona band, tie-broken by Sharpe,
  deduped by project) is the correct "top pool" — confirmed by reading `curatePools` (planner.js ~600).
- `plan.html` loads `translations.min.js` (minified) but raw `planner.js` (unminified); `home.html`
  loads both raw. Neither currently loads `planner.min.js` — this is a PRE-EXISTING gap
  (`test_minified_assets.js` fails identically on unmodified origin/main, documented in prior items'
  specs, e.g. 125-notes.md/136-notes.md) and out of scope here (touching home.html/plan.html script tags
  is not part of this bet and risks the analytics.js-load-order off-limits rule). `planner.min.js` was
  still regenerated and kept fresh per NORTH_STAR convention (test_translations_fallback.js depends on
  it staying byte-identical) even though it isn't the file actually served today.
- Found (not fixed, flagged separately): `mixStats()` (planner.js ~276) can misread a TARGET goal's
  one-time item price (`GOALS[].target`, e.g. iphone=1100) as if it were a $/mo subscription cost,
  because SUBSCRIPTION and TARGET goals reuse the same `target` field for different meanings. This
  previously could render a nonsensical "garden already covers X — a card funded by $91k/mo" line
  inside the waitlist modal for TARGET plans. Gated shut in this item by restricting that line's render
  condition to `archetype === 'subscription'` (it was already only meaningful there) — verified via
  `test_plan_checkout_cta.js`'s "TARGET modal must not render the subscription-mix garden line"
  assertion. The deeper root cause (the shared `target` field name / the unconditional mix-seeding
  effect) is a separate, larger change and was NOT touched here (scope discipline) — flagged as a
  follow-up task.
