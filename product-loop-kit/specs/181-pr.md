# 181 — explainer: the gate that could not be made green

**Tier: HIGH** (verifier-assigned independently — 434-line diff vs LOW's 150-line cap, and it rewrites the
pass condition of a file in `test:serial`, i.e. the merge gate). Verifier verdict: **PASS, 8/8 criteria**,
every measurement independently re-derived, four mutations of its own, NEVER list cleared.

## The goal

`test_seo_cta_targets.js` had been red on `main` every day since item 173 landed. The BACKLOG row filed it
as *"7 token pages have a dead primary CTA again — 173's fix does not self-heal against pool-population
drift"*, and asked the question that made it worth more than a 7-page cosmetic fix: **the daily SEO regen
should have either dropped these pages or refreshed them — find out why it did not.**

## The intuition, in one picture

The generated pages are **committed bytes**, baked about once a day. The gate judged them against
**DefiLlama's live feed, read at the instant the test runs**. A token earns a page by clearing a hard
`tvlUsd >= $100,000` with **zero margin**. So a token sitting at $100,682 has a perfectly valid page and a
perfectly valid CTA at 09:00, and by 23:00 — with nothing committed, nothing deployed, nothing regenerated —
it is at $99,481 and the same CTA returns nothing.

That means the gate's pass condition was **not a function of the repository**. No diff could make it green;
no diff could make it red. It had already cost three consecutive runs (175, 177, 180) a hand-built
`origin/main` worktree baseline to prove "not mine."

## What the investigation actually found

The BACKLOG row listed three lifecycle candidates. All three are **falsified**:

- *Pages are retained when their pool set empties* — no. `generate-token-pages.js:986-991` deletes **every**
  `*.html` in the output dir before writing anything, then writes only what `rankTopTokens()` returns from
  that bake's live fetch.
- *`MIN_QUALIFYING_POOLS` is evaluated only at mint time* — no. There is no mint-time-only predicate; the
  floor is applied on every bake (`:196`, with `MIN_QUALIFYING_POOLS = 1` at `:62`).
- *The regen skipped them* — no. Every scheduled `sitemap-update.yml` run is `success` (runs `30424747605`
  05:19, `30330972196` 05:12, `30240806141` 05:48 UTC). Item 174's bake cleared the then-red gate to 38/38.

What is true instead — measured, not argued. Four live runs in 15 hours, on trees with no relevant commits
between them:

| when (UTC) | dead CTAs | members |
|---|---|---|
| 07-29 ~10:40 | 2 / 2217 | `kvcm`, `ripe` |
| 07-29 ~23:50 | 7 / 2186 | `ankravax`, `gitc`, `mchc`, `n3xt`, `wmetax`, `zeal`, `zro` |
| 07-30 ~01:14 | 5 / 2186 | subset of the above |
| 07-30 03:2x | 8 / 2186 | `cate`, `cnx`, `gitc`, `hahype`, `mchc`, `n3xt`, `wmetax`, `zro` |

The first and last sets share **zero** members. `ankravax` and `zeal` were dead at 23:50 and **alive again**
by 03:20. Best live pool TVL for the 23:50 set: `ANKRAVAX` +0.7%, `WMETAX` −0.3%, `GITC` −0.5%, `ZRO` −4.1%,
`MCHC` −7.0% — five of seven within 7% of the line. **This is oscillation, not decay.**

## What changed, in reading order

One code file: `test_seo_cta_targets.js`. Every page it scans now lands in exactly one class.

1. **Header comment** — the three classes, and the budget's derivation, stated where the next reader lands.
2. **`classifyPage({html, file, surface, pools, today})`** — pure, no fs, no network, `today` injected.
   Returns `skip | contract | stale | drift | ok`:
   - **`contract`** — malformed href · missing its own `?token=`/`?chain=` param · `minTvl` ≠
     `MIN_POOL_TVL` · **NEW:** the CTA's param value doesn't belong to the page it sits on
     (`gen.tokenSlug(paramValue) !== basename`). All decidable from the repo alone; **fatal at any count**.
   - **`stale`** — dead CTA **and** the page's own visible `Last updated <date>` is more than 2 days old
     (or unparseable — a dead page that cannot prove freshness fails). **Fatal at any count.** This is the
     lifecycle failure the BACKLOG row hypothesised: drift cannot produce it, because drift resolves at the
     next bake; only a regen that stopped dropping empty pages can.
   - **`drift`** — dead, well-formed, correct floor, fresh page. Printed with the best live pool's TVL and
     signed distance from the floor, so oscillation (−0.3%) and decay (−78.1%) are distinguishable at a
     glance. **Bounded, not fatal below budget.**
3. **`verdictFor({counts, scannedWithCta})`** — pure. `DRIFT_BUDGET_FRACTION = 0.01`, derived from the four
   measurements above: worst observed 0.37%, so 1.0% is ~2.7× headroom — while item 173's own regression
   (1,749/2,200 = **79.5%**) clears it by ~80×.
4. **`runSelfChecks()`** — 10 assertions over synthetic in-memory HTML and pool fixtures, run **before any
   network call**, aborting with exit 2 on misbehaviour. This is the permanent non-vacuity guard: it proves
   each class can go red without mutating a single committed page.
5. **`main()`** — same scan, now routing through the classifier; the old output lines survive in
   recognisable form so old transcripts stay comparable.

Everything else is unchanged, deliberately: the anti-vacuity rails (no fixture + stale cache + failed fetch
still throws; `data/pools-snapshot.json` still refused), `APP_DEFAULT_MIN_TVL`'s diagnostic, and
`MIN_POOL_TVL` still arriving via `require('./generate-token-pages.js')` — never re-typed (the 159 rule).

## Why this is not "making the red go away"

That is the one real risk in this item, so it was verified as the central question rather than asserted.
All **eight** failure conditions of the old file were enumerated and re-derived by the verifier; seven are
still fatal at count 1 (two of them changed from a hard `throw` to a counted class — same exit code, but
exercisable by the self-checks). Exactly one became bounded: emptiness at the correct floor on a **fresh**
page. And the split **grew** the repo-decidable set — the param-belongs-to-page check is new, and was
confirmed by the verifier's own script to hold on all 2,186 committed pages before it shipped fatal.

Proof the budget cannot swallow a real regression, end-to-end rather than arithmetic-only: the verifier ran
the real gate over the real 2,186-page corpus against a fixture where every pool had `tvlUsd = 1` →
`drift 2186/2186`, **EXIT 1**. Boundary confirmed at 21 pass / 22 fail. And 173's actual mechanism (a
missing `minTvl`) is `contract`, so it never reaches the budget at all.

## What this deliberately does not fix

A reader on `tokens/zro.html` who clicks through while that pool is under the floor still lands on an empty
grid. That is the **app's** empty-state behaviour — long-BLOCKED item **133**, and PR #332's "leg C". It is
a human decision about discovery UX at the floor, and reclassifying a red as drift excuses the *gate*, never
the product. Two obvious generator-side fixes were considered and rejected on documented grounds, both
recorded in `specs/181.md`: **mint hysteresis** (cannot remove the window, only its frequency; makes the
generator stateful; shrinks future SEO surface — the NEVER-list question item 148 sat blocked on for five
runs) and **baking more often** (~4× better, at one Vercel deployment per bake — the exact cost the
2026-07-13 standing decision exists to prevent).

## Deviations

Five, all in `181-notes.md` §8, none undocumented (verifier confirmed): 10 self-check assertions instead of
8 (an extra unparseable-date case + the budget crossing split across `verdictFor`); two contract conditions
expressed as counted data rather than a `throw`; `formatUsdRaw` for the diagnostic table instead of
`gen.formatUsd`'s K/M/B page-copy form; T4's "assert the skipped count stays 0" treated as a proof
obligation rather than a runtime hard-fail (0 skipped, independently re-derived; the count is printed every
run); and `npm ci` to populate the gitignored `node_modules`. The verifier logged one wording gap for next
time: the spec's Change bullet 1 says a missing CTA is `contract` while T4 requires such pages to be
skipped — the implementation follows T4, which is byte-identical to `origin/main` behaviour and therefore
loosens nothing.

## Quiz

1. The gate was red on `main` for three days running. What single observation proves the cause is external
   data drift rather than a product regression or a stale assertion — and why is the failing **count**
   useless for that?
2. `generate-token-pages.js` deletes every `*.html` before it writes. Given that, explain how a page with a
   dead CTA can exist at all — and why running the generator again is not a fix.
3. The `stale` class fails at any count, while `drift` is bounded. Both fire on a page whose CTA returns
   zero pools. What distinguishes them, and what real-world failure would `stale` catch that `drift` is
   designed to forgive?
4. Why would setting `DRIFT_BUDGET_FRACTION` to 0.10 be a bad idea even though today's drift is 0.37% — and
   what in the shipped file would stop that change from passing silently?
5. The new `contract` sub-check (CTA param must belong to its page) shipped as **fatal**. What was the
   precondition for shipping it that way, what was the alternative if the precondition failed, and why does
   that alternative matter more than it sounds?
