# Spec 039: Instrument the static SEO surface (`/tokens/<slug>`, `stories/*.html`)

## Evidence
Direct grep, this session (2026-07-11):
- `grep -l analytics.js tokens/*.html` → **0 of 2,045 files**.
- `grep analytics.js stories/*.html` → **0 of 3 files**.
- Confirmed via full read of `tokens/1inch.html`: `<head>` has title/description/canonical/OG/Twitter meta, `<link rel="stylesheet" href="/style.css">`, zero `<script>` tags anywhere in the file. No Mixpanel bootstrap, no `analytics.js`, no tracking call of any kind.
- `home.html`/`plan.html` (the only pages that DO track) load Mixpanel via a synchronous stub loader (home.html:141-145) + `<script defer src="analytics.js">` (home.html:150), and `analytics.js` self-initializes `Analytics.init()` + fires `session_start` on `window.load` (analytics.js:534-539). `page_view` is NOT auto-fired — every existing call site fires it explicitly (`app.js:1173-1208`).
- These 2,048 pages are exactly the SEO surface built and shipped by backlog items 014 (static token pages), 021 (phase-2 networked rollout + sitemap wiring), 023 (content depth/internal linking), 028 (design system reuse), 029-033 (link/quality gates) — five-plus HIGH-tier ships, all currently unmeasured end to end.
- NORTH_STAR.md's own standing principle: "A bug at a funnel step outranks any experiment at that step." This is upstream of every funnel step the last week of SEO work touched.

## Hypothesis
We believe adding the same Mixpanel + `analytics.js` pipeline already used by `home.html`/`plan.html` to the generated static pages, plus one explicit `Analytics.trackPageView()` call per page, will make organic landings on the SEO surface measurable for the first time — because right now `page_view`/`session_start` cannot fire on these pages at all (no script loads), so heartbeat has zero visibility into whether the SEO investment is drawing any traffic, let alone converting. Confidence: **supported** (code-verified zero instrumentation, not a guess).

## Change
Smallest version that makes the static SEO surface measurable — instrumentation only, zero content/copy/ranking/trust-rail change:
1. Add a shared analytics-bootstrap HTML block (Mixpanel synchronous stub loader, byte-identical to `home.html:141-145`, pointed at the same first-party `mp.defi.garden` proxy + project token) to `generate-token-pages.js`'s `renderTokenPage()` and `generate-stories.js`'s `renderStoryPage()`.
2. Load `analytics.js` via `<script defer src="https://www.defi.garden/analytics.js">` (absolute URL — these pages live at varying path depths, `/tokens/<slug>` and `/stories/<slug>.html`).
3. Fire one explicit `Analytics.trackPageView(path, properties)` call on `window.load` (after `analytics.js` has executed, since `defer` scripts run before `load` fires) with a new path taxonomy entry:
   - Token pages: `path: '/tokens/<slug>'`, `properties: { page_type: 'token_landing', token: '<SYMBOL>', pool_count: <qualifyingCount> }`.
   - Story pages: `path: '/stories/<slug>'`, `properties: { page_type: 'story_landing', persona: '<slug>' }`.
4. No new event names — reuses the existing `page_view` event (fired via `Analytics.trackPageView`, which already exists and is used identically by `app.js`). `session_start` fires automatically via `analytics.js`'s own `window.load` listener (analytics.js:534-539) once the script loads — no separate call needed for that.

OUT of scope: click-through/outbound-link tracking on the CTA or pool-row links. Not needed for the MVP — `document.referrer` is already captured on every event fired once a user lands in the app (`analytics.js:32`, `getBaseContext()`), and same-origin navigation sends the full referrer path under this site's `Referrer-Policy: strict-origin-when-cross-origin` (vercel.json), so click-through from `/tokens/<slug>` → `/?token=X` is already attributable via `referrer` filtering in Mixpanel once this ships — no code needed for that half. Also out of scope: re-enabling the disabled `app.js` analytics calls (042), JSON-LD (040), chain pages (041), any change to `generate-sitemap.js`'s quality gate, canonical logic, or the pages' visible content/design.

## Acceptance criteria
- [ ] Every generated `/tokens/<slug>.html` page includes the Mixpanel bootstrap + `<script defer src=".../analytics.js">` + a `window.load` listener that calls `Analytics.trackPageView('/tokens/<slug>', {...})`. Verified by regenerating sample pages via `--fixture` (network to `yields.llama.fi` may be unavailable in-sandbox; fixture-based regen plus the existing offline test suite is sufficient, per the established pattern used by 013/014/020/022/023) and asserting the emitted HTML string contains the bootstrap block, `analytics.js` script tag, and a `trackPageView` call with the correct path/properties per fixture token.
- [ ] Every generated `stories/<slug>.html` page includes the same bootstrap + a `trackPageView` call with `path: '/stories/<slug>'`, `page_type: 'story_landing'`.
- [ ] No existing token-page or story-page content, meta tag, canonical URL, or CSS is altered — diff to `renderTokenPage`/`renderStoryPage` is additive (new script block only). Verified by diffing a regenerated fixture page against the pre-change version outside the new script block.
- [ ] `node --check` on both generator files; full existing `test_token_pages.js` suite still green (no regression to eligibility/ranking/quality-gate logic, which this change never touches).
- [ ] New assertions added to `test_token_pages.js` (and a new lightweight `test_stories.js` or extension of an existing stories test if one exists) verifying the analytics block's presence and correct `path`/`page_type`/`token` values per a fixture token.
- [ ] Instrumentation: `page_view` fires (via the reused `Analytics.trackPageView`) on page load for both page families, with `path` values `/tokens/<slug>` and `/stories/<slug>` and the `page_type` property distinguishing them from in-app page views.

## Measurement
Metric: `page_view` count where `path` starts with `/tokens/` or `/stories/`, and — since `referrer` is already captured on every subsequent event — the share of app-side `session_start`/`page_view` events whose `referrer` matches `https://www.defi.garden/tokens/%` or `/stories/%`, as a proxy for SEO-surface → app click-through.
Window: 14 days from ship (real pages regenerate on the next `sitemap-update.yml` CI run, same residual as every prior static-page item — sandbox network cannot reach `yields.llama.fi` to produce live production HTML this session).
Decision rule: this is enabling instrumentation, not a product change — success is the events populating as specified. The product call (is the SEO surface driving traffic? converting?) comes from the first heartbeat with real numbers, matching 020's precedent exactly.
Minimum sample per NORTH_STAR.md (≥30 events per claim; below → "insufficient data").

## Risk tier (builder's guess — verifier assigns independently)
HIGH — touches `generate-token-pages.js`/`generate-stories.js`, which NORTH_STAR.md's risk policy explicitly names as "hand-edits to generated SEO surface... changes go through the generate-*.js scripts only" (satisfied — this changes the generator, not hand-edited output) and separately "anything user-facing beyond copy/styling, when in doubt → HIGH." This adds new third-party network calls (Mixpanel) to pages that previously had none, at scale (2,048 pages) — no content/ranking/trust-rail change, but the blast radius (every static SEO page) and new script-loading behavior warrant the HIGH lane: full explainer + 5-question quiz before merge.
