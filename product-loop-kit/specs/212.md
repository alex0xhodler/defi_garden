# Spec 212: every parameterized URL returns the identical generic markdown — the agent asks about one pool and gets the homepage index

## Evidence

Measured live against prod, 2026-08-02, `origin/main` @ `7b64ae5a5`. Prompted by the Resend
agent-readability pattern (zenorocha, 2026-08); **this repo is already well past most of that checklist, so
the findings below are the residue, not the checklist.**

**Already shipped and verified working — do NOT re-build these:**

| surface | status |
|---|---|
| `llms.txt` | **200**, `text/plain`, 6,641 B, proper `##` headings, 9 `?pool=` deep links |
| `llms-full.txt` | **200**, 205,672 B, 16 `?pool=` deep links |
| `.well-known/api-catalog` | **200**, `application/linkset+json`, 513 B |
| `.well-known/mcp/server-card.json` | **200**, `application/json`, 418 B |
| `.well-known/agent-skills/index.json` | **200**, `application/json`, 1,101 B |
| `Link:` headers advertising all of the above | present on every response (`vercel.json`) |
| 2,154-page static estate | genuinely server-rendered — real facts in HTML, no JS needed |
| daily regen | keeps llms + estate in sync from one source (the "one source of truth" rule) |

**THE DEFECT — markdown content negotiation is root-only, and it fails silently.** `vercel.json`'s
markdown rewrite is `source: "/"`. A query string does not change the matched source path, so **every**
parameterized app URL matches `/` and is served the site-wide `llms.txt`. Measured, byte-identical first
lines:

| request (`Accept: text/markdown`) | what comes back |
|---|---|
| `/` | `# Find the Best Yields for Your Tokens…` (correct — the site index) |
| `/?token=USDC` | **the same site index** |
| `/?pool=43641cf5-…` | **the same site index** |
| `/tokens/usdc` | **`<!DOCTYPE html>`** — HTML, 18,814 B; no markdown at all |
| `/chains/solana` | **`<!DOCTYPE html>`** |
| `/plan.html` | `Redirecting...` |

**Why this is worse than returning nothing:** an agent that asks for one pool and receives a generic,
well-formed, plausible-looking site index has **no signal that it got the wrong document**. It will answer
the user from it. A 404 or an HTML response would at least be honest about not having a markdown twin. This
is the precise failure the pattern warns about — the agent recommends whoever it could parse correctly, and
a confidently-wrong parse is indistinguishable from a correct one at the agent's end.

**Compounding it: the one genuinely agent-readable surface has no markdown representation.** The 2,154
static token/chain pages are the best content this product has for an agent — real server-rendered facts,
tables, headings — and `Accept: text/markdown` on them returns HTML. So an agent must parse HTML for the
surface that would parse cleanly, and gets wrong-markdown for the surface that has no facts at all.

**Honest sizing — the case for this item is strategic, not measured.** There is **no measured agent traffic
today**: `src`/`ref` attribution shows `undefined` only, and nothing in Mixpanel distinguishes an agent from
a crawler. This item is a bet on where distribution is going, made cheap because the generators and the
regen pipeline already exist. It must not be scored or reported as a measured-demand item, and its
measurement section says so.

## Hypothesis

We believe **serving a correct per-surface markdown twin — and refusing to serve the generic index when no
twin exists** will **make the estate's facts retrievable in one request by an agent, and stop agents
answering pool/token questions from the homepage index**, because the facts already exist in a structured
generated form and the only thing missing is addressing and honest negotiation. Confidence: **supported**
on the defect (measured byte-identical responses above); **guess** on the traffic effect (no agent traffic
is measured today).

## Change

1. **Generate markdown twins for the static estate**, in the SAME generator run that writes the HTML
   (`generate-token-pages.js`, `generate-chain-pages.js`) so the two can never drift — the one-source-of-
   truth rule is satisfied *by construction*, not by discipline:
   - `tokens/<slug>.md`, `chains/<slug>.md`, and the KO twins under `ko/`.
   - Content = the same facts the HTML page states: H1, the pool table (proper markdown table with labelled
     columns), the TVL-floor claim **using the generator's existing exported constant** (never a re-typed
     literal — the 159/174 rule), the FAQ answers, and the `/?pool=<id>` deep links.
2. **Make negotiation path-aware** in `vercel.json`: `Accept: text/markdown` on `/tokens/<slug>` →
   `/tokens/<slug>.md`; same for `/chains/`; `/ko/` likewise.
3. **Remove the silent generic fallback.** Markdown negotiation on a path with no twin must serve the
   normal HTML response, NOT `llms.txt`. `llms.txt` stays reachable at its own URL and at `/` (its correct
   home). This is the cheapest leg and the one that stops the wrong-answer failure mode — **it is
   independently valuable and must ship even if leg 1 is cut for scope.**
4. Fix `/plan.html`'s markdown response (`Redirecting...`) to serve either the planner's markdown twin or
   the plain HTML — never a redirect stub.

**OUT of scope:** per-pool markdown for `?pool=<id>` — that is **213**, and it is the north-star surface, so
it gets its own item rather than riding along here. Also out: any change to `llms.txt`/`llms-full.txt`
content or to `.well-known/*` (all verified working), any trust rail, any HTML page's rendered content, and
`app.js`/`PoolDetail.js`/`planner.js`.

## Acceptance criteria

- [ ] `curl -H "Accept: text/markdown" https://www.defi.garden/tokens/usdc` returns **markdown**
      (starts `#`, `content-type: text/markdown`), not `<!DOCTYPE html>`.
- [ ] The same for `/chains/solana` and for a `/ko/` twin, with the KO markdown in **Korean** (EN+KO
      together — one language alone is a FAIL).
- [ ] **The silent fallback is gone:** `Accept: text/markdown` on a path with no twin returns that path's
      normal HTML, and **never** `llms.txt`'s content. Assert on at least one such path explicitly.
- [ ] `/` **still** returns `llms.txt` for markdown (unchanged — this is the one correct case today and it
      must not regress).
- [ ] **Twin-vs-HTML fact parity, asserted mechanically, not eyeballed:** for a sample of ≥20 slugs, the
      pool count, the top pool's APY, and the TVL-floor figure parsed out of the `.md` equal the values
      parsed out of the corresponding `.html`. **A drifting twin is worse than no twin** — it puts two
      different numbers in front of a human and an agent, which is the exact thing the source-of-truth rule
      exists to prevent.
- [ ] The floor figure in the markdown comes from the generator's exported constant — verifier greps to
      confirm no second hardcoded literal was introduced (159/174 rule).
- [ ] The markdown uses a real table with labelled columns and `#`/`##` headings — not prose lists.
- [ ] **No page is de-indexed and no HTML changes.** `sitemap*.xml`, `robots.txt`, every `.html` file and
      `stories/` are byte-identical to before, except for the daily-regen churn — and any regen delta is
      separated from this change per `playbooks/seo-surface-regen-delta.md` before anything is claimed.
- [ ] `.md` twins are **not** added to the sitemaps (they are negotiation targets, not indexable pages) and
      do not create duplicate-content pairs — confirm each `.md` is either `noindex` via header or absent
      from all sitemaps, and say which was chosen and why.
- [ ] Both router paths still work (CLAUDE.md): bare `/` → planner, `/?token=USDC` → analytics app with
      pool cards. `vercel.json` edits are the highest-risk part of this item.
- [ ] Tests: `npm test` green; pre-existing reds baselined at `origin/main` first (`playbooks/
      pre-existing-red-triage.md`) — item 185's `test_seo_surface_audit.js` red is known and stays out of scope.
- [ ] Instrumentation: none new client-side. The honest observable is server-side and we do not have it —
      state that plainly in `212-pr.md` rather than inventing a metric (see Measurement).

## Measurement

Metric: **none available today.** There is no server-log access in this stack and no client-side event can
fire for an agent that never runs JS — so agent reads are **structurally unmeasurable** with the current
instrumentation. Window: n/a. Decision rule: **keep** if every acceptance criterion holds and no guardrail
moves; this item is explicitly a **capability bet, recorded as such in `LEARNINGS.md`, not an experiment
with an expected lift.** Do not report a traffic effect. The nearest honest proxy, checkable later: GSC
impressions on the estate, and any future appearance of a non-`undefined` `src`/`ref`. If someone later
wants this measured properly, the item to file is server-side or edge request logging by `Accept` header —
that is a different item and it is the honest prerequisite for ever claiming an effect here.

## Risk tier (builder's guess — verifier assigns independently)

**HIGH.** `vercel.json` is named explicitly on NORTH_STAR's HIGH list (config/infra), and this item edits
its rewrite table — the same table that routes `/` to the planner and every parameterized URL to the
analytics app. A mis-scoped `source` or `has` predicate could serve markdown to human browsers or break the
IA router, which is the SEO lifeline. The generator half is lower risk but writes ~4,300 new files.

## Open questions

None blocking. One decision the builder must make and argue in `212-pr.md`: `noindex` header on the `.md`
twins vs. simply keeping them out of the sitemaps. Recommendation: **both** — out of sitemaps *and*
`X-Robots-Tag: noindex` — since a `.md` twin is a duplicate of an indexed page by design, and this is the
one way this item could accidentally create the duplicate-content problem item 211 exists to remove.

## Territory notes
<!-- Build loop appends findings from the blindspot pass here. -->

Blindspot pass, 2026-08-03, base `origin/main` @ `a40c5c0ff`. Five findings, all of which change what
gets built:

1. **Leg 4's premise is wrong — `/plan.html`'s `Redirecting...` is `cleanUrls`, not a negotiation bug.**
   Re-measured live this session: `/plan.html` → **308**, `location: /plan`, body `Redirecting...` (15 B,
   `text/plain`) — and `/plan` itself returns **200 `text/html`, 8,778 B**, the real planner page, for
   `Accept: text/markdown`. `vercel.json` sets `"cleanUrls": true`, so the 308 fires for *every* request to
   a `.html` URL regardless of `Accept`; the spec's table caught the redirect stub rather than the resource.
   `/plan` already does exactly what leg 3 asks for (no twin → serve the HTML, never `llms.txt`).
   **Resolution: no `vercel.json` change for leg 4** — it ships as an assertion (`/plan` is HTML, and no
   markdown rule matches it) plus this note, not as a fix. Building a "fix" here would have changed
   `cleanUrls` behaviour site-wide for a non-defect.

2. **The defect itself re-confirmed live, unchanged:** `curl -H "Accept: text/markdown" "/?pool=43641cf5-…"`
   → **200, `content-type: text/markdown`, 6,641 B**, first line `# Find the Best Yields for Your Tokens
   Across All Chains | DeFi Garden` — byte-for-byte `llms.txt`.

3. **Vercel cannot express "no query string at all"** — `source` matches the path only, and `has`/`missing`
   query predicates are per-key. So leg 3 is implemented as a `missing` list of the **content-selecting**
   params on the `/` markdown rules. Grepped from `app.js`/`home.html`/`planner.js`
   (`searchParams.get('…')`): `token`, `chain`, `pool`, `protocols`, `poolTypes`, `minTvl`, `minApy`, `lang`.
   `lang` is deliberately EXCLUDED (it selects a language, not a subject — `/?lang=ko` is still the site
   index) and so are `utm_*`/`src`/`ref` (attribution, not content). An enumerated predicate can go stale
   as the app grows — the `ecosystem-shaped-predicate` trap — so the list ships with a **drift-guard test**
   that re-derives the params from the source files and fails if a new content-selecting one appears.
   The `missing` list must go on the markdown **header** rule as well as the rewrite, or `/?pool=…` would
   return HTML labelled `Content-Type: text/markdown`.

4. **Twins must NOT be committed in this PR, and the reason is the parity criterion itself.** Committed
   `tokens/*.html` (2,105 tracked files) are written by `sitemap-update.yml` from one live DefiLlama fetch.
   Generating `.md` here would fetch at a *different* moment, so the committed twin's APYs would disagree
   with the committed HTML on day one — failing "twin-vs-HTML fact parity" the moment it landed. Parity is
   only structural when both files come out of the **same generator run**. `sitemap-update.yml`'s `push`
   trigger already lists `generate-token-pages.js` and `generate-chain-pages.js` in its `paths`, so merging
   this PR *is* the trigger: CI regenerates and commits real twins within minutes. Same convention as
   045/050/051. Honest cost, stated rather than hidden: between merge and that CI run, `Accept:
   text/markdown` on `/tokens/<slug>` returns **404** instead of markdown — strictly better than today's
   confidently-wrong site index, and it is minutes, not days.

5. **Stale-file cleanup is `.html`-only and would strand orphan twins.** `generate-token-pages.js:1021`,
   `:1051`, `:1067`, `:1076` and `generate-chain-pages.js:497`, `:528` each do
   `readdirSync(dir).forEach(f => { if (f.endsWith('.html')) rmSync(…) })`. A token that later fails the
   030 yield gate would lose its `.html` and keep its `.md` forever — a twin of a page that no longer
   exists, which is the drift failure mode this item exists to prevent. Cleanup must cover `.md` too
   (item 031's rule, extended).

Also confirmed, so the build doesn't re-derive it: the test file list has a single source of truth —
`package.json`'s `test:serial` `&&` chain, which `run-tests.js` parses (`parseFileList()`); new tests are
registered by appending there and nowhere else. `MIN_POOL_TVL` (`= 100000`) is already exported from
`generate-token-pages.js` and `test_token_pages.js` has a scratch-run harness (`loadScratchGenerators`)
that patches the constant and re-renders to prove no literal was re-typed — the 159/174 rule's existing
enforcement, which the markdown templates must satisfy the same way.
