# 078 — PR explainer (HIGH tier: full walkthrough + quiz)

## Goal

Re-arm the daily SEO pipeline's only per-run health readout. Every day,
`sitemap-update.yml` regenerates the entire SEO surface (~25k URLs across 116
sitemap files) and commits it with a message that reports how many URLs were
generated. That number has read **0** on every run since `sitemap.xml` was split
into a `<sitemapindex>` — the count greps `<url>` in the index file, but the
`<url>` entries all live in the child `sitemap-*.xml` files now.

## Intuition

A health signal that always reads 0 is worse than no signal: a genuine
catastrophic regen (empty sitemaps pushed to production) would look *identical*
to a healthy run, and the false "0 URLs" already sent one loop run on a
wild-goose investigation (LOG.md 2026-07-13). One honest line in the commit
message makes every future `git log` a health record again.

## What changed and why (diff in reading order)

One line, `.github/workflows/sitemap-update.yml:128`, inside the
"Commit updated files" step's `git commit -m` body:

```diff
-        - Regenerated sitemap.xml with $(grep -c '<url>' sitemap.xml) URLs
+        - Regenerated sitemap index with $( { grep -o '<sitemap>' sitemap.xml || true; } | wc -l ) child sitemaps and $( { grep -o '<url>' sitemap*.xml || true; } | wc -l ) total URLs
```

- **Two numbers instead of one dead one.** `<sitemap>` entries in the index
  (currently 110) tell you the index is intact; total `<url>` occurrences across
  all root `sitemap*.xml` (currently 25,039) tell you the children carry real
  URLs. Rendered against today's tree:
  `- Regenerated sitemap index with 110 child sitemaps and 25039 total URLs`.
- **`grep -o … | wc -l`, not `grep -c`.** `-c` counts matching *lines* per
  file (and prints per-file counts on a glob, which would break the arithmetic);
  `-o | wc -l` counts *occurrences* across the whole glob in one number, and
  stays correct even if a future generator ever emits multiple entries per line.
- **`{ … || true; }` hardening.** GitHub Actions runs `run:` steps under
  `bash -eo pipefail`. `grep` exits 1 when it finds nothing; under `pipefail`
  that becomes the pipeline's status even though `wc -l` still prints `0`.
  Inside a `git commit -m "$(…)"` argument the substitution's status is
  discarded anyway (verified empirically), but in an assignment context
  (`MSG=$(…)`) the unhardened form aborts the step — so the builder hardened it
  to survive both, as defense against a future refactor. `|| true` swallows only
  grep's exit code, never its output: a real zero still renders as `0`.
- **Honesty preserved.** No fallback constants, no clamping. If a regen ever
  produces zero URLs, the message says exactly that — which is the entire point.

Nothing else changed: the `git add` list, change detection, validation, and the
push/rebase-retry loop are byte-identical (verifier confirmed by full-file read).

## Deviations from spec

One, disclosed in `specs/078-notes.md`: the spec's example was plain
`grep -o … | wc -l`; the builder shipped the stricter `{ … || true; }` wrapping
after empirically establishing the `bash -eo pipefail` assignment-context
failure mode. Strictly safer, inside the spec's own acceptance wording.

## Verification

Builder and verifier independently re-derived everything: counts cross-checked
four ways (glob `grep -o`, per-file `grep -o` summed, `awk gsub`, per-file
`grep -c` summed — all 25,039), zero-match safety proven in a scratch dir under
`set -eo pipefail` in both argument and assignment contexts, glob-scope sanity
(only the 116 real sitemap files match `sitemap*.xml`), and the NORTH_STAR test
chain green (`test_planner` 208 assertions + `test_protocol_parsing` +
`test_qualifier_fix`, exit 0). Verifier: **PASS, 6/6, HIGH** (config/infra —
`.github/workflows/` is an explicit HIGH trigger regardless of diff size).

The live proof lands on the next daily `sitemap-update.yml` run: its commit
message should carry real non-zero counts.

## Quiz

1. Why did the old count print 0 on every run, even though ~25k URLs were being
   generated correctly?
2. The substitution sits inside a `git commit -m "…"` argument, where a failing
   command substitution doesn't trip `set -e`. Why harden with
   `{ grep … || true; }` anyway?
3. After a catastrophic regen that wipes every URL, what does the new message
   line say — and why is that the desired behavior rather than a bug?
4. Why doesn't `grep -o '<url>'` overcount by also matching `<urlset>` or
   `</url>` tags?
5. The diff is one line in a commit-message string. Why is the item still tiered
   HIGH?
