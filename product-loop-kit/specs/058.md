# Spec 058: Feasibility study — DefiLlama data wrapper / cache layer (+ custom KPIs)

## This is a STUDY, not a build
Output = a decision doc (`docs/feasibility-data-layer.md`) with an options matrix, measured evidence, a ToS answer, a KPI list, a fallback design, and a RECOMMENDATION + phased plan. It touches the product's foundational **no-backend, static-hosting** tenet (CLAUDE.md / NORTH_STAR "no-backend"), so the BUILD is a **human decision** — a build loop must NOT implement a backend/DB autonomously off this item.

## Motivation (human, 2026-07-12)
Today the FE fetches `https://yields.llama.fi/pools` directly client-side (multi-MB JSON) on the critical path of every analytics/SEO page — slow LCP (see reports/2026-07-12-pagespeed.md) and 100% dependent on DefiLlama uptime/latency. Hypothesis: a thin data layer (we poll DefiLlama ~5 min, store, serve a pre-filtered/optimized payload from our own domain) could (a) speed up the FE, (b) decouple from DefiLlama availability, (c) unlock **custom KPIs** computed on stored snapshots (trends/momentum/history) that the raw `/pools` endpoint can't give. Human floated sqlite as the store.

## Questions the study must answer
1. **Architecture options** — matrix on {complexity, $ cost, latency, ops burden, fits-static-hosting?, gives history/queries?}:
   - **(a) Static snapshot via cron/CI** — a scheduled job polls DefiLlama, filters to qualifying pools + only the fields the app uses, computes KPIs, and publishes a small `pools-snapshot.json` (+ per-chain/token slices) served from our CDN. Fits the existing generator pattern; ~free; no real backend. Cons: cron granularity/reliability (GitHub Actions cron is ≥5 min AND unreliable/delayed — a real edge cron is better); committing a big JSON every 5 min bloats git → use a blob/object store or Vercel Edge Config/Blob, not git; no ad-hoc DB queries.
   - **(b) Serverless + edge DB** — Vercel Cron + Vercel KV/Postgres, OR Cloudflare Worker + **D1** (sqlite-at-edge) + Cron Triggers, OR **Turso/libSQL** (the actual "sqlite" that survives serverless). Poll → store → serve via an edge function. Real queries + history + KPIs + native 5-min cron. Cons: introduces a real (minimal) backend + DB + ops + cost; reverses "no backend".
   - **(c) Hybrid** — edge DB for history/KPIs, but the hot "current pools" payload still served as a static snapshot for FE speed.
2. **"sqlite" reality check** — a raw sqlite file is ephemeral on serverless. The viable "sqlite" = **Turso/libSQL** or **Cloudflare D1**. Confirm and name the concrete choice.
3. **DefiLlama ToS / attribution / rate limits** — is caching + re-serving their data permitted? attribution required? polling cadence limits? This is a GATING legal question — answer it first.
4. **Payload win, measured** — current `/pools` size vs a filtered snapshot (qualifying pools + used fields only). Quantify the transfer/LCP win; ties into the 052–057 perf wave.
5. **Trust rails** — the layer is the natural server-side enforcement point for `APY_SANITY_LIMIT` + `DEFAULT_MIN_TVL`; must NOT weaken them and must stay auditable (every displayed number still derives from live DefiLlama data through the same filters).
6. **Custom KPIs unlocked by storing snapshots over time** — rate momentum, real N-day mean APY without extra llama calls, new-pool detection, TVL trend, an honest "trust score". Which map to the north star / planner honesty (v3 yield-funded framing)?
7. **Failure / staleness** — if our layer is stale or down, the FE MUST fall back to DefiLlama directly and never present stale numbers as live (trust rail). Design the freshness stamp + fallback.
8. **SEO simplification** — the static token/chain generators (014/021/041) could source from our snapshot instead of hitting llama in CI → one source of truth.
