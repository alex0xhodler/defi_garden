# 051 — PR explainer (HIGH tier)

## Goal
Every `/tokens/<slug>` and `/chains/<slug>` static SEO page ships the same
shared `og-image.png` for social/SERP thumbnails today (2,108+ pages, one
generic logo). Spec 051's hypothesis: a unique, data-true card per page
(token/chain name + best honest APY + pool count) is more clickable and
more on-brand than a generic logo, and the pages already declare
`twitter:card = summary_large_image`, a format built to reward exactly
this kind of per-page image.

## Intuition
The repo already generates ~2,000 static HTML pages at build time from
live DefiLlama pool data (`generate-token-pages.js`/`generate-chain-pages.js`).
This item adds one more artifact to that same generation pass: a PNG,
instead of HTML, built from the *same already-gated data* the page's own
headline numbers come from. Because the static-no-backend architecture
rules out a runtime image service, the image has to be a build-time
artifact too — rendered once per generation run, committed like every
other generated file, referenced by a plain `<meta>` tag.

The one new piece of infrastructure is a way to draw pixels without a
browser. `@napi-rs/canvas` is a headless, native Canvas-2D implementation
with prebuilt Linux binaries — no Chromium, no browser process, just a
regular npm dependency that CI's existing `npm install --only=production`
step already picks up.

## What changed and why (diff in reading order)

1. **`package.json` / `package-lock.json`** — added `@napi-rs/canvas` as a
   real `dependencies` entry (not `devDependencies`): CI installs with
   `--only=production`, so a dev-only dependency would silently be absent
   at generation time. Added `test_og_images.js` to the end of the `test`
   script chain.

2. **`generate-og-images.js` (new)** — the actual card renderer:
   - `renderOgCard({label, bestApy, poolCount})`: draws a 1200×630 PNG —
     neuro-surface card on a neuro-bg radial gradient (same hex values as
     `style.css`'s light-mode tokens, mirrored here because canvas can't
     read CSS custom properties), a vector brand dot + "DeFi Garden"
     wordmark, the token/chain name, "Best APY tracked" + the APY in
     accent blue, and the pool count.
   - `generateOgImages(records, kind, labelFor, outRoot)`: the per-run
     driver. For each record it computes `bestApy` as
     `Math.max(...rec.pools.map(poolTotalApy))` — **the exact same
     expression** `renderTokenPage`/`renderChainPage` already use for the
     page's own visible headline APY — writes the PNG to
     `<outRoot>/og/<kind>/<slug>.png`, and returns a `Map<slug, relPath>`.
     A per-record render/write failure is caught and that slug maps to
     `FALLBACK_REL_PATH` (`og-image.png`) instead — one broken card can
     never break a page or the whole run. Also removes stale PNGs for
     slugs no longer in the current ranked set (same staleness class 031
     already fixed for `.html` pages).

3. **`generate-token-pages.js`** — `main()` now calls `generateOgImages`
   right after `ranked` is computed (before any page is written), so the
   fallback decision is known *before* that page's `<head>` is rendered.
   `renderTokenPage` gained a 6th param, `ogImagePaths`, used to build
   `ogImageUrl` (falls back to the existing `OG_FALLBACK_REL_PATH` when the
   map is absent or has no entry for this slug). `og:image`, new
   `twitter:image`, and new `twitter:title`/`twitter:description` all
   point at `ogImageUrl`/the existing `title`/`description`. Hub and A-Z
   pages (no single token/chain to depict) are untouched — still the
   shared image. The `generate-og-images.js` require is **lazy** (inside
   `main()`), because `generate-og-images.js` requires this module eagerly
   for `poolTotalApy`/`formatApy` — a top-level require in the other
   direction would be a load cycle (same reason `generate-chain-pages.js`
   is already lazy-required a few lines below).

4. **`generate-chain-pages.js`** — the same treatment: `generateOgImages`
   called in `main()`, `renderChainPage` gained the same 6th param and the
   same four meta tags. Required eagerly at the top here — safe, since
   `generate-og-images.js` never requires `generate-chain-pages.js` back.

5. **`.github/workflows/sitemap-update.yml`** — added `og` to the `git add`
   list in the "Commit updated files" step, so generated images actually
   land in the next scheduled/triggered run.

6. **`test_og_images.js` (new)** — 18 assertions: real PNG output
   (magic bytes + 1200×630 dimensions via the IHDR chunk), the
   `og/<kind>/<slug>.png` path convention, the anomaly-exclusion trust
   rail (the ANOM fixture's $900M/2100% pool never reaches `rec.pools`,
   so the card's APY computation is structurally 6%, never 2100%),
   real-file generation + stale-file cleanup + the failure→fallback path
   for both `generateOgImages` and the page templates, and a timing
   sanity check for the CI foreground timebox.

## Deviations from spec (full detail in `specs/051-notes.md`)
- One PNG per slug, shared across `en`/`ko` (card data doesn't vary by
  language) — roughly halves the image count vs. one per language pair.
- Dropped the 🌱 emoji from the brand mark after the first render showed a
  tofu box (headless canvas has no bundled color-emoji font) — replaced
  with a plain vector dot, visually confirmed the fix.
- Repo-bloat open question: images committed directly (no build-artifact
  pipeline), consistent with the already-committed `tokens/`/`chains/`
  pattern. Flagged as a future watch-item, not acted on now.
- Stale-PNG cleanup added, mirroring 031's `.html` cleanup (not explicitly
  asked for, but the same staleness class).

## Verification
`node test_og_images.js` (18/18), `node test_token_pages.js` (71/71),
`node test_chain_pages.js` (63/63) all pass. A full end-to-end CLI run
against the existing fixtures produced real PNGs (confirmed via `file(1)`:
1200×630 PNG) and real HTML with the new meta tags; one image was visually
reviewed. `yields.llama.fi` is network-blocked in this sandbox (pre-existing,
documented on 014/021/041/050/044 etc.), so the live-scale run hasn't
executed — real `og/tokens/*.png` + `og/chains/*.png` land on the next
`sitemap-update.yml` CI run after merge. **Needs a human visual spot-check**
once that CI run produces real pages, per this backlog's standing practice
for render-path merges.

Independently verified by the `verifier` subagent: **PASS**, risk tier
**HIGH** (new dependency + diff size), 4/4 acceptance criteria met, no
undocumented deviations, nothing on the NEVER list.
