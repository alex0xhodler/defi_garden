# Spec 019: Pool-detail pages convert SEO landers toward the north star

## Evidence
Human directive: token-search visitors land on pool-detail pages that look sparse and untrustworthy, with only a bare planner link. Pool pages are where the SEO lifeline (`?pool=` URLs) meets the product; today they neither substantiate trust nor route anyone toward a plan.

## Hypothesis
Enriching pool pages with honest, trust-substantiating data plus a concrete personal projection and ONE planner CTA will convert SEO landers toward the north star (plan_created), because the cautious-saver ICP converts on trust and honest numbers, not APY hype.

## Change
PoolDetail.js (+ translations.js, + analytics):
1. **Trust-substantiating data** already in the pools API — TVL, chain, protocol, 30d mean APY, exposure/IL flags. Honest presentation: trust rails intact, anomaly flags VISIBLE, never hidden. Existing neumorphic components/classes only (standing decision 2026-07-10: reuse before inventing; gradients/one-offs are a verifier FAIL).
2. **Honest mini-projection module**: "$200/mo in this pool grows to ~$X in 5y at current rates" using the EXISTING futureValue helpers, degen haircut where applicable. en-US formatting helpers for all numbers.
3. **One CTA — "Garden this pool"** — deep-linking into the planner prefilled with this pool. Exactly one; no competing actions.
4. **All strings** via translations.js, EN + natural KO together.
5. **Instrument the CTA** with the existing analytics pattern — follow trackPlanCreated's shape if a new event is needed (LOW-risk instrumentation per NORTH_STAR).

OUT of scope: router semantics, `?pool=` URL behavior, trust-rail values, planner internals.

## Acceptance criteria
- [ ] Playwright on 3 sample pools, including one anomaly-flagged pool — the flagged pool MUST show the warning prominently, never hype; timeboxed runs (5 min foreground cap)
- [ ] Trust data rendered from data already fetched (no new API calls — code trace); anomaly/exposure/IL flags visible; rails untouched
- [ ] Projection uses existing futureValue helpers + degen haircut where applicable; en-US formatting; no invented rates
- [ ] Exactly one "Garden this pool" CTA, deep link opens the planner prefilled with the pool
- [ ] CTA instrumented per existing analytics pattern; EN + KO for every new string
- [ ] Neumorphic tokens/components only — zero gradients/one-offs (grep-verifiable); full test chain exits 0

## Measurement
CTA click-through from pool pages → plan_created, 14-day window post-ship.

## Risk tier (builder's guess — verifier assigns independently)
HIGH — user-facing SEO surface (`?pool=` pages).

## Open questions
None blocking.

## Territory notes
- PoolDetail.js is React.createElement UMD like app.js; formatUsd/formatNum/formatApy and futureValue helpers already exist — reuse, don't reimplement.
- Deep-link state convention: all planner state lives in URL params (shareable-plan pattern) — prefill via params, not localStorage.
