# 227 — PR explainer (HIGH tier: full walkthrough + quiz)

Branch `claude/loop-227` · PR #425 · spec `specs/227.md` · notes `specs/227-notes.md`
Risk tier **HIGH**, assigned independently by the verifier (the builder guessed HIGH too).

## 1. Goal — what this is for

NORTH_STAR's north star has two legs. Leg **(B)** — pool-detail CTA clicks — has instruments and
history. Leg **(A)** — *agent consumption* — is defined as "read-only API calls (item 227's
Worker) + MCP invocations (item 228) + AI-assistant-referred sessions + verified AI-crawler
reads", and at adoption it read **2 perplexity.ai sessions / 60 days, everything else
0-by-absence-of-instrument**.

That phrase — *absence of instrument* — is the whole point. Three of leg (A)'s four terms could
not be counted because the things they count did not exist. Item 224 built the fourth (edge
telemetry, shipped). **This item builds the API leg.** It is also a hard dependency for two
higher-scored items that cannot start without it: 228 (the MCP server "wraps its handlers") and
234 (agentic commerce, "the x402 layer wraps 227's endpoints", score 9.3).

The strategic bet, in the human's Q4a words: *"curated + railed + explainable beats the raw
firehose for agent citation."* DefiLlama already serves the firehose, faster and more completely
than we ever will. What it cannot serve is a rate that has been **filtered through stated rules**
plus **a machine-readable statement of what those rules are**. That is the entire product
difference, so it is the entire API design.

## 2. Intuition — why the design looks like this

Three constraints did most of the shaping:

**"Same Worker codebase as 224's logger (one deploy)"** — from the backlog row. So there is no
new Worker, no new `wrangler.toml`, no new binding. The API is a branch inside the existing
`edge/agent-log.mjs`. A pleasant consequence: `edge/agent-log-core.js:82` has classified `/api`
and `/api/*` as `path_class: 'api'` since 224 shipped, with the comment *"(future, item 227 — no
routes exist yet)"*. **The instrument for this item's own traffic was already built and waiting.**

**"Rails re-implemented server-side must be read from the SAME constants"** — also from the row,
which invokes RAZOR.md and the item 212 lesson. The strong reading is "copy them carefully and
add a drift test". The weak reading — the correct one — is that *there should be nothing to
drift*. `edge/api-core.js` `require`s `../trust-rails.js`, so it is not a re-implementation at
all. `grep -nE "\b(1000|100000)\b" edge/api-core.js` returns **nothing**. The same reasoning was
applied one level further out: `foreverNumber` is `require`d from the real `../planner.js` rather
than re-typed, so the subscription math in the API and the math in the product are the same
function, not two functions that agree today.

**This Worker sits in front of the sacred URLs.** Once deployed, `www.defi.garden/*` routes
through it — including `?token=`, `?chain=`, `?pool=`, the SEO lifeline. That makes "don't break
the pass-through" the highest-stakes property in the diff, and it is why the dispatch was written
as an **additional branch ahead of the untouched pass-through**, rather than as a restructuring
of it. Byte-parity is preserved *by construction*, and the test asserts **Response-object
identity** — not equal headers, the same object.

## 3. What changed and why — the diff in reading order

**`edge/api-core.js` (new, pure CommonJS, no network, no Cloudflare APIs).** Everything
decidable without I/O lives here so plain-Node tests can `require()` it — the same split
`edge/agent-log-core.js` already uses. It exports `handleApiRequest({pathname, searchParams,
pools})` → `{status, body}`. Read it in this order:

1. the two `require`s (`../trust-rails.js`, `../planner.js`) — the single-source decision;
2. `totalApy()` / `isAnomalous()` / `meetsFloor()` — the rails as predicates. `totalApy` is
   `(apyBase || 0) + (apyReward || 0)`, the expression `app.js` uses at 1965/2066/2166/2930/3694.
   There is no `apy` field in play (see §5);
3. `buildRails()` — the block every response carries, prose included;
4. the route handlers, ending in `build404()`.

**`edge/agent-log.mjs` (modified, +145).** Read the first 20 lines of `fetch()` and stop: the
`/api` check, then the original two lines. `getPools()` below it fetches
`https://yields.llama.fi/pools` with `cf: {cacheTtl: 300, cacheEverything: true}` plus an
in-isolate memo, and **throws** on any failure rather than returning `[]` — an empty array would
render as "zero pools exist", which is a lie; a 503 carrying the rails block is the truth.

**`test_api_worker.js` (new).** Draws its population from `data/pools-snapshot.json` at test time
and asserts **invariants over all 7,339 pools**, not sampled cases.

**`edge/API.md` (new)** — the stable versioned contract. **`edge/DEPLOY.md` §7 (appended)** — the
deploy delta. **`package.json`** — one `&& node test_api_worker.js` appended to `test:serial`,
which `run-tests.js` parses; there is no second list to update.

## 4. Round 1 was a verifier FAIL — the defect and the fix

The verifier found that `/api/pools/100%` (and `/%`, and `/%E0%A4%A`) threw an unhandled
`URIError` straight out of `worker.fetch`. `new URL(...).pathname` preserves a bare `%`, so the
malformed segment reached `decodeURIComponent` unguarded; `handleApi` wrapped only `getPools()`,
so nothing caught it. On Cloudflare that renders a **1101 error page** — no JSON, no `rails` — on
the endpoint whose entire pitch is being the answer an agent can cite. It falsified three shipped
claims at once (the spec's "every response including 404/503 carries rails", `api-core.js`'s own
"every path, success or error", and `API.md`'s "the ONLY case where this API cannot answer").

The verifier also said how *not* to fix it, and it was right: not "reject the string `100%`". The
evidence supports the weaker predicate — **no input to `handleApiRequest` may produce anything
other than `{status, body}` with a rails block** — so the guard went on the decode *and* on the
dispatch, with a hostile-input population in the tests rather than the three observed strings.

Three non-blocking observations were fixed in the same round: a comment that overstated what the
memo does during an upstream outage, `Cache-Control: public, max-age=300` on 503s (an outage
answer publicly cacheable for five minutes), and a test summary line that printed
`${passed}/${passed}` and so could never display a failure.

## 5. Deviations from spec, and what stayed open

- **`require('../planner.js')` for `foreverNumber`** instead of restating the formula. The
  verifier AST-scanned all 104 top-level statements inside planner.js's IIFE and confirmed the
  only eager global reads are guarded; the `window` uses sit in the UMD `else` branch that is not
  taken when `module.exports` exists. It bundles (251 KB) and boots with no `window`/`document`.
  Judged **better than a mirror** under RAZOR: there is now exactly one `foreverNumber` in the
  repo. The builder deliberately did *not* extend the same reuse to `blendedRate` — planner's
  `blendedApy()` is a median computed for a displayed headline, a different job.
- **Not advertised in `llms.txt`**, though the backlog row asks for it. The endpoint does not
  exist until the human deploys; publishing a URL that 404s on the agent surface would be a false
  claim on the one surface whose value is being trustworthy. Deferred explicitly, not dropped.
- **Class NOT closed, with numbers.** This is **1 of 4** agent-pillar legs (224 ✓, 227, 228, 234).
  And the verifier's live sweep surfaced a separate open class this item neither closes nor
  causes: the repo derives total APY as `apyBase + apyReward` and never reads DefiLlama's own
  `apy` field — which the fixture cannot see, because **0 of 7,339** snapshot pools carry it.
  Today exactly **1** live pool of 15,590 (`cafbed21-…`, tortuga/Aptos/TAPT) reports
  `apy = 1017.07` while computing to 0, so it clears the anomaly rail and renders as 0%. Filed as
  **backlog 259**.

## 6. Evidence the rails actually hold

The builder's tests proved five distinct non-vacuity red sites, each restored byte-identical. The
verifier went further and left the fixture entirely, re-running the rails against the **live
15,590-pool** upstream the Worker actually consumes:

- 104 live anomalous pools → **0 leaked** into any scoped list response; all 104 flagged by id.
- All 100 live chains at `limit=200`, 2,737 returned pools → **0** floor or anomaly violations.
- **28 adversarial `minTvl` values** (`0`, `-99999999`, `0x0`, `1e-400`, `" 0"`, `"1,000"`, `NaN`,
  `%00`, duplicate params…) → the lowest `tvlUsd` ever emitted was **$75,491,049**;
  `railsApplied.minTvl` never dropped below 100000. The floor cannot be lowered.
- Four user agents (`python-requests`, `curl`, `GPTBot`, empty) each wrote exactly **1**
  `agent_reads` row with `path_class='api'` — leg (A)'s instrument is real and not UA-gated.

## 7. What this does not do

It is not live. Deploying needs Cloudflare credentials, which loops do not have and must not have
— the same split item 224 shipped under ("loops write the Worker; the human deploys"). Until the
human runs `edge/DEPLOY.md` §7, leg (A)'s API count is structurally **0**, and that zero means
*absence of instrument*, not absence of demand. Saying which is which is the whole reason the
distinction is written down.

## Quiz (5 questions)

1. The API applies the TVL floor *more strictly* than `app.js` does. What exactly is the
   difference, and why was the stricter behavior chosen for this surface rather than parity?
2. `edge/api-core.js` contains no numeric literal `1000` or `100000`. Explain why that specific
   grep is the meaningful check here, and what failure mode it is evidence against — name the
   prior item that established the rule.
3. The pass-through contract claims "byte-parity by construction". What does the test actually
   assert to back that phrase up, and why is that assertion stronger than comparing status codes
   and headers?
4. `getPools()` throws instead of returning an empty array when the upstream fetch fails. State
   the trust argument for that choice, in terms of what an agent would conclude from each option.
5. The verifier said the URIError must not be fixed as "reject the string `100%`". Name the rule
   that forbids it, state the predicate that was implemented instead, and say what that changes
   about the tests.
