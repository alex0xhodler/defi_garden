## Goal

Make the daily product audit capable of seeing a bad pool-detail page.

## The intuition

`audit-app.js` has a P0 `number-sanity` check. It works. For two weeks it reported clean every
single day — and that green meant almost nothing, because of *where it was pointed*.

The scanner renders five pool-detail surfaces per run (`pool-detail`, `-360`, `-dark`, `-ko`, plus
a `dead-pool` control). Four of them resolve to **one** pool id, hardcoded:

```js
// audit-app.js:88-91
const PREFERRED_POOL_ID = '747c1d2a-c668-4682-b9f9-296708a3dd90';  // lido stETH
```

The snapshot it audits against carries **740** pools. So the coverage of the surface
`NORTH_STAR.md` names as the north star was **1/740 = 0.14%** — and the one pool was chosen
precisely *because* it is reliable. A target picked for being reliably good is the strongest
possible guarantee that a check never fires.

The proof it mattered isn't theoretical. **Every** pool-detail bug in this backlog's history was
found by hand, on a non-flagship pool:

| item | what rendered | pool |
|---|---|---|
| 122 | rate-stability score of −900,719,925,474,097.9 | balancer-v2 |
| 144 | `apyMean30d` unclamped as a trusted "30d Mean APY" card | `201e5f6e-…` |
| 145 | KPIs derived from out-of-rail history | `201e5f6e-…` |
| 165 | "$100 grows to ~$49,002,948,093,727,200,000 in 5y" | zeebu ZBU |

Not one is Lido stETH. The scanner could not have caught any of them.

And the blind spot still had a live true positive in it. Re-derived from the committed snapshot
during this run:

```
pools: 740
out-of-rail total APY (>1000): 0
apyMean30d>1000: 1 [ '201e5f6e-cf75-4d0e-b07f-d58da3cee23a', 'balancer-v2', 30282.5457 ]
```

30,282.55% is 30× `APY_SANITY_LIMIT`. The **only** pool in the dataset that can trip a rail
predicate was exactly the one the scanner structurally could not reach.

This is verbatim item **154**'s finding ("audits ONE hand-picked SEO page out of 2,167 — the one
most certain to be fine"), which was diagnosed and fixed for the *static SEO* surface by 154 and
157 — and never applied to the app's own surfaces. So this item doesn't invent a design; it
carries the shipped one across.

## What changed, in reading order

**1. `POOL_PRESCAN_SIGNALS` + budget constants** (`audit-app.js`, constants block) — mirrors
`PRESCAN_SIGNALS`'s single-source-of-truth shape: signal → severity, five signals
(`apy-rail-breach` P0, `mean30d-rail-breach` P0, `kpi-nonfinite` P0, `absurd-magnitude` P0,
`missing-tvl` P1). `APY_SANITY_LIMIT` and `ABSURD_MAGNITUDE` are **read, never redefined** —
a rail mirror would itself be a trust-rail edit.

**2. `prescanPools(pools, opts)`** — pure, no I/O beyond the already-read snapshot, returns
`{ scanned, suspects, bySignal }`. Cheap: no render, no network, a pass over 740 objects.
This is 157's "prescan the population before spending the render budget" lesson.

**3. `buildPoolSurfaces(opts)`** — replaces the single-id block at `:1065-1068`:
- **anchor unchanged** — `PREFERRED_POOL_ID`, same `pools[0]` fallback, and the four existing
  surface names untouched (the heartbeat and five tests read `surfacesCovered`; a rename is a
  regression, not a refactor)
- **promotion** — up to 2 suspects, P0-first, ties by `sampleBySeed` so successive days work
  through a backlog instead of re-rendering the same pool forever (157's rationale verbatim)
- **rotation** — up to 2 more by seed from the non-suspects, excluding anchor and promoted
- new surfaces are named `pool-detail:<8-char-id-prefix>` and use the **existing** pool driver
  with all its **existing** checks — this item aims checks, it does not add any

**4. Kill switches**, named to match 154/157 exactly: `AUDIT_POOL_IDS` (pin exact pools, prescan
off), `AUDIT_POOL_PRESCAN=0`, `AUDIT_POOL_SAMPLE`, `AUDIT_POOL_PRESCAN_MAX`.

**5. `runAudit()` JSON gains `poolPrescan: { scanned, suspectCount, bySignal, promoted }`** —
sibling to the existing `prescan` and `textSurfaces` blocks, so `signals/audit-findings.json`
picks it up with no heartbeat change.

**6. `test_audit_pool_prescan.js`** (new, 207 lines, 9 cases), wired into `test:serial` right
after `test_audit_prescan.js`.

## Verification (the verifier re-derived all of it independently)

  `poolPrescan.promoted = ["201e5f6e-cf75-4d0e-b07f-d58da3cee23a"]`. That surface renders and
  reaches a clean verdict (no `page-error`, no skip — it traced `runAudit()`'s render loop to

- **A3, the one most likely to sink the item** — the verifier neutered each of the five predicates
  one at a time against a 6-pool fixture tripping all five simultaneously, confirming each neuter
  drops exactly its own signal with **zero cross-contamination**, then removed the whole promotion
  guard and confirmed the expected blast radius. Byte-identical restore (`md5sum`) after every
  cycle. This directly answers item 166's precedent — no two signals share a path that could mask
  the other's absence.
- **A4** — its own runs: 6-file browser subset 6/6, plain lane 34/34, anchor names and their
  relative order unchanged.
- **A7** — it built a *true* pre-167 baseline (`git show fac2e30f2:audit-app.js`), ran it, then
  swapped back: 26 → 29 surfaces, ~101s → ~100s. Growth +3, under `MAX_POOL_SAMPLE` (6).
- **A9** — no rail redefinition, no product file in the diff.

## The result worth reading carefully

The promoted pool rendered **clean**. That is not the scanner failing — `PoolDetail.js:161-164`'s
`mean30dSane` gate (item 144) suppresses the value, and all six render sites are behind it, so
30,282.55% cannot enter the DOM. This is the **first confirmation of 144's fix against the real
pool it was filed about**, rather than against a synthetic injection.

The verifier attached an honest caveat worth keeping visible: the pool driver has no
rail-relative percent check of its own (its magnitude check fires at 1e11, nowhere near 30,282),
so the clean render is evidence the **product** gate holds — not that the **audit** could catch
this class independently. That gap pre-exists 167 and Non-goal 2 deliberately forecloses fixing
it here. It is the natural next item.

## Deviations from the spec

Six, all disclosed in `167-notes.md`. The one that changes behavior: **promotion and rotation get
additive budgets** rather than sharing one (157's static leg shares). The builder's reasoning,
which the verifier reproduced numerically: only the additive reading makes the spec's own worked
example ("1 anchor + ≤2 promoted + ≤2 rotated → up to 7") arithmetically true; a shared budget
caps growth at 2 and can never reach 7. Also: `poolPrescan.promoted` stores **full** pool ids
(the builder's first draft stored 8-char prefixes and would have failed A1's literal wording —
found and fixed by the builder, not by the verifier).

## Scope / safety

Audit tooling only: `audit-app.js`, one new test, one line of `package.json`. No product file, no
generator, no generated SEO surface, no new dependency, no trust-rail edit. NEVER list clean.
Risk **HIGH** on size (+317/−8 plus a 207-line test — over 2× the 150-line LOW cap), assigned
independently by the verifier and concurred.
