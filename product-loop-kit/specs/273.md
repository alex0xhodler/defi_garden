# Spec 273 (renumbered from 265 — a concurrent run took 265-268 on main; main's ids win): P0 — analytics header controls overlap the search input at mobile width

Impact: defect-count 1→0 on the analytics header at mobile widths (P0, human-reported); north-star guardrail (parameterized analytics URLs stay usable)

## Evidence
Human live report + screenshot, 2026-08-12 session: analytics app (dark theme, query "STETH"), mobile
width — the KO language toggle and theme toggle render ON TOP of the search input's right end. Human
verdict verbatim: "on mobile width the top nav bar and theme and language switcher are overlapping,
bad ux, fix it immediately."
Instrument note: the audit's occlusion lens covers grid-360 and scored it clean — this overlap either
sits at a width/state the rotation missed or between two interactive elements the lens exempts.
Whatever the cause is, it is an instrument gap; the builder must record it (and close it if cheap).

## Hypothesis
The header row (`.app-header-content` / `.app-header-sticky`, `app.js:3089-3243`;
`.app-header-controls`, `style.css:1638+`) does not reserve horizontal space for the controls at
narrow widths, so the search input and the controls' absolute/flex placement intersect. Confidence:
supported (screenshot shows the intersection; exact mechanism to be measured on the rendered DOM,
not guessed).
- Instance of: fixed-overlay/occlusion class (playbooks/fixed-overlay-occlusion.md — 179/217/218/220
  precedents). Read the playbook BEFORE fixing.
- Class closed by this item: no — this fixes + guards the analytics header instance; the playbook's
  other surfaces keep their existing guards.

## Change
Smallest CSS/layout change that makes search input and header controls disjoint at every viewport
≥320px, both themes, EN + KO. No redesign, no new components (one-header rule, CLAUDE.md). Reuse
existing tokens only.

## Acceptance criteria
- [ ] Rendered Playwright at 320/360/480/768/1280 × light/dark × EN/KO: bounding boxes of the search
  input and EACH control are disjoint (no intersection ≥1px), measured from the DOM.
- [ ] Both controls pressable at every width: `document.elementFromPoint(center)` resolves to the
  control (the 219 lens technique), and the search input is focusable and accepts typed text.
- [ ] With a long query ("STETH" and a 20-char string) the input text does not run under the controls.
- [ ] No layout regression at 768/1280: header height and control positions unchanged vs baseline
  worktree screenshots (pixel-diff or box-compare).
- [ ] Non-vacuity: revert the fix (byte-identical restore of the changed rules) → the new overlap
  assertion goes RED at the failing width; restore → green. Record the red output in notes.
- [ ] Instrument gap named: one sentence in specs/273-notes.md on WHY the occlusion audit missed this
  (width not in rotation / interactive-vs-interactive exemption / state-dependent), and the audit
  check extended if the fix is ≤ ~30 lines; otherwise ticket it.
- [ ] Population: assert on ALL `.app-header-controls` children present in the DOM at test time, not a
  hardcoded pair.
