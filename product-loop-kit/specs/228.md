## Hypothesis

We believe exposing 227's already-railed reads as **installable MCP tools** will produce
countable north-star leg (A) events (MCP invocations), because an agent that can *install* a
tool reaches for it by default, where a REST endpoint must first be discovered and hand-wired.
Confidence: **supported for the build leg, speculative for the traffic leg** — the same honest
position 227 recorded. It pays off in every future where any agent installs the server at all;
otherwise the instrument records the zero honestly. It unblocks 234 regardless of its own
traffic.

- **Instance of**: the **agent pillar** class — surfaces whose consumer is a machine, not a
  browser (llms.txt, md twins, schema.org, `/api`, MCP). Population: 4 planned legs
  (224 ✓, 227 ✓, **228 this**, 234).
- **Class closed by this item: no.** This ships 3 of 4 legs cumulatively; 234 (x402) remains
  open and is ticketed as its own row. Additionally, as with 227, the endpoint is
  **code-complete but not live** until the human deploys (credentials) — until then leg (A)'s
  MCP count is structurally 0, which is *absence of instrument*, not absence of demand.

## Change

Smallest version that satisfies the row, on the **same Cloudflare Worker as 224's logger and
227's API (one deploy)**, exactly as the row instructs. **Zero new npm dependencies** — the
official MCP SDK is deliberately NOT used (see Territory notes).

**New — `edge/mcp-core.js`** (CommonJS, pure, zero network, zero Cloudflare APIs; mirrors
`edge/api-core.js`'s and `edge/agent-log-core.js`'s shape exactly, for the same reason: the
plain-Node test harness must `require()` it directly and the ESM Worker must `import` it):

- `handleMcpMessage({ message, pools })` → `{ status, body }` (`body === null` for a
  JSON-RPC *notification*, which must produce a 202 with no body). Pure function of its inputs.
- JSON-RPC 2.0 methods: `initialize`, `notifications/initialized`, `tools/list`, `tools/call`,
  `ping`. Unknown method → JSON-RPC error `-32601`; malformed envelope → `-32600`; bad tool
  args → `-32602`; anything else → `-32603`. Parse failure (`-32700`) is raised by the Worker,
  which owns JSON parsing.
- **Protocol version negotiation**: `SUPPORTED_PROTOCOL_VERSIONS` (newest first, starting
  `2025-06-18`); `initialize` echoes the client's requested version when supported, otherwise
  returns the server's newest. Server capabilities: `{ tools: {} }` (this server is read-only —
  no resources, prompts, sampling, or logging capability is advertised, because none is
  implemented; advertising an unimplemented capability would be a false claim on the exact
  surface whose pitch is honesty).

**The four tools — DELEGATION, NOT RE-IMPLEMENTATION (RAZOR / item 212's mirror rule).**
This is the defining constraint of the item. No tool computes anything. Each entry in the
single exported `TOOLS` table carries the api-core route it resolves to and a pure
`argsToRequest(args)` that builds `{ pathname, searchParams }`; the dispatcher then calls
`apiCore.handleApiRequest(...)` and returns its body verbatim. There is therefore **no second
copy of any rail, filter, or formula** to drift — the rails reach MCP through the same single
call the REST API uses, which itself reads `trust-rails.js`.

| tool | api-core route it delegates to | args |
|---|---|---|
| `find_pools` | `/api/pools` | `token?`, `chain?`, `project?`, `minTvl?`, `limit?` |
| `get_pool` | `/api/pools/:id` | `pool_id` (required) |
| `forever_number` | `/api/forever-number` | `monthly` (required), `apy?` |
| `explain_rails` | `/api` | *(none)* |

- `tools/call` wraps the delegated body as MCP tool content: `{ content: [{ type: 'text',
  text: JSON.stringify(body, null, 2) }], isError }`, where `isError` is `true` iff the
  delegated `status >= 400` — a tool-level error, per MCP's contract, is a *successful*
  JSON-RPC response carrying `isError: true`, never a JSON-RPC protocol error.
- Each tool's `inputSchema` is a JSON Schema object, and each description **states the rails**
  (the differentiator Q4a names) rather than only the mechanics.

**Changed — `edge/agent-log.mjs`** (Worker): a `/mcp` branch beside the existing `/api` branch,
before the pass-through. `POST /mcp` → `handleMcpMessage`; `OPTIONS /mcp` → 204 CORS preflight;
`GET /mcp` → **405** (MCP's Streamable HTTP transport explicitly permits a server that offers
no server→client SSE stream to answer GET with 405); any other method → 405. Pool data comes
from the **existing** `getPools()` memo/edge-cache — no second fetch path. An upstream failure
returns the same honest 503 shape 227 established. `logAgentRead(...)` is called on the MCP
path exactly as the `/api` path already does it.

**Changed — `edge/agent-log-core.js`**: one new classification, `pathClass: 'mcp'`, for `/mcp`
and `/mcp/*`, inserted after the `api` check with the precedence comment updated in the same
edit. This is what makes leg (A) decomposable into its two documented terms in the D1 log.

**New — `edge/MCP.md`**: the contract + the row's asked-for "README quickstart for
Claude/ChatGPT users" (install snippets, tool reference, rails explanation, the honest
not-yet-deployed status). Linked from `edge/API.md` and `edge/DEPLOY.md`.

**New — `test_mcp_server.js`**, registered in `test:serial` (required — `test_test_registry.js`,
item 205, fails on an unregistered test file).

## Territory notes

- **Why hand-rolled JSON-RPC and not `@modelcontextprotocol/sdk`**: NORTH_STAR's risk policy
  makes "new dependencies" a HIGH-tier trigger, and the entire `edge/` codebase is dependency-
  free by construction so its cores stay `require()`-able by the plain-Node harness with no
  install step. The subset of MCP this server needs (five methods, no SSE, no sessions, no
  sampling) is ~200 lines of pure dispatch. Adding a dependency to buy that would also add a
  bundler surface to a Worker the human deploys by hand.
- **Why `/mcp` and not `/api/mcp`**: mounting under `/api/*` would have been free telemetry
  (already classified) but would make MCP invocations **indistinguishable from REST calls** in
  D1 — and NORTH_STAR leg (A) counts them as two separate terms. The classifier change is the
  choice that follows the metric's defining mechanism rather than a resemblance of it.
- **Pass-through contract**: `edge/agent-log.mjs`'s standing guarantee is that every non-`/api`
  path returns the *identical* Response object from `fetch(request)`. That set now excludes
  `/mcp` too. The existing assertions in `test_api_worker.js` / `test_agent_log.js` must be
  re-read and updated to state the new boundary exactly — a stale assertion that still passes
  is worse than none.
- `edge/api-core.js` exports everything needed (`handleApiRequest`, `ENDPOINTS`,
  `buildRailsBlock`, `API_VERSION`); no change to that file is required and none is made.

## Acceptance criteria

- [ ] `edge/mcp-core.js` exists, is `require()`-able in plain Node, and **declares no rail
      constant, no filter, and no formula of its own** — grep-provable: the file contains no
      numeric rail literal (`1000` / `100000`) and no arithmetic on pool fields.
- [ ] **Delegation is structural, not asserted by comment**: every tool in `TOOLS` carries an
      api-core route, and `tools/call` returns `apiCore.handleApiRequest(...)`'s body verbatim.
- [ ] `initialize` returns `protocolVersion`, `capabilities.tools`, `serverInfo.{name,version}`;
      a supported client-requested version is echoed, an unsupported one falls back to the
      server's newest.
- [ ] `tools/list` returns exactly the four row-named tools — `find_pools`, `get_pool`,
      `forever_number`, `explain_rails` — each with a non-empty description and a valid
      `inputSchema`; required args are marked required.
- [ ] `notifications/initialized` produces **no JSON-RPC body** (202), not a null-id response.
- [ ] JSON-RPC errors: unknown method → `-32601`; malformed envelope → `-32600`; unknown tool
      name and missing/invalid required args → tool-level or `-32602` as specified above; a
      delegated `status >= 400` surfaces as `isError: true` on a **successful** JSON-RPC
      response, never as a protocol error.
- [ ] Worker: `POST /mcp` served by the handler; `OPTIONS /mcp` → 204 + CORS; `GET /mcp` → 405;
      **every non-`/api`, non-`/mcp` path still returns the identical Response object from
      `fetch(request)`** (asserted by object identity, the established technique).
- [ ] `agent-log-core.js` classifies `/mcp` and `/mcp/*` as `pathClass: 'mcp'`, and **every
      pre-existing classification is unchanged** — asserted by re-running the existing
      classifier cases, not by inspection.
- [ ] Tests (`test_mcp_server.js`, plain-Node lane, registered in `test:serial`):
  - [ ] **Population**: pool fixtures drawn at test time from `data/pools-snapshot.json` (the
        real estate, regenerated daily) — never a hardcoded pool list.
  - [ ] **Invariant over the population**: no pool in any `find_pools` result has total APY >
        `APY_SANITY_LIMIT`, and every returned pool has `tvlUsd >= DEFAULT_MIN_TVL`. Asserted
        over all returned pools, not a sample.
  - [ ] **Parity / mirror, both directions**: for a derived set of argument combinations drawn
        from the snapshot (not hand-picked constants), each tool's returned payload is
        **deep-equal** to the body of the corresponding `handleApiRequest` route call, and every
        route in the tool table is reachable from a tool while every tool maps to a real route.
        If a future edit makes an MCP tool compute its own answer, this goes red.
  - [ ] **Positive control**: the anomaly control is derived from the live snapshot (17 of 7,339
        pools exceeded the limit on the 2026-08-10 snapshot per 227's measurement) and asserted
        absent from `find_pools` results; a run that finds **no** anomalous pool in the
        population must **fail loudly**, never pass vacuously. The TVL control is perturbed from
        a real pool (the snapshot is pre-floored), preferring a natural instance when one
        exists, and the test states which kind it used.
  - [ ] `explain_rails` reports the same `apySanityLimit` / `minTvl` values that
        `trust-rails.js` exports — equal both ways.
- [ ] **Non-vacuity, proven in-session and transcribed into `228-notes.md`**: at least three

## Measurement

**Metric**: north-star **leg (A)** — weekly MCP invocations, counted by the 224 D1 log's new
`path_class = 'mcp'` rows. This is the second of leg (A)'s two documented terms and is now
separable from the `'api'` term by construction.

- **Build leg** (calendar-verifiable now): the server exists, delegates, is railed, and the
  tests above pass — verified this session.
- **Traffic leg**: **GATED** — the window opens at **≥30 real (non-crawler-classified) MCP
  invocations**. That gate **cannot open until the human deploys the Worker** (credentials — the
  same split 224 and 227 merged under), and realistically not until the registry-listing leg
  also runs, which is human-owned. Until then the count is **0 = absence of instrument**.
- **Backstop**: if the gate has not opened 60 days after deploy, the heartbeat closes it
  UNEXERCISED per the ledger rule.
- **Decision rule**: any non-loop invocation stream at all validates the pillar link. **Zero after
  60 days says the binding constraint is DISTRIBUTION — the human-owned registry listing — not the
  protocol or this implementation.** That distinction is the whole value of the measurement, because
  the two failures call for opposite responses. Keep regardless of traffic while 234 depends on it;
  revisit only if the human abandons the agent pillar.

## Risk tier (builder's guess — verifier assigns independently)

**HIGH** — new public surface on the edge Worker that sits in front of every request to
www.defi.garden. The pass-through contract is the thing that must not break; a regression there
takes the whole site down, which is strictly worse than the endpoint simply not existing. Also
touches 224's classifier. Mitigations: pure core with plain-Node tests, object-identity
assertion on the pass-through path, no config/route change, no product render path, no new
dependency. Deploy remains human-gated.
