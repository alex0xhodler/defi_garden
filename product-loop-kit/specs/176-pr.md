## Goal

Close the one blind spot `playbooks/product-audit.md` names in writing: the rendered leg of `audit-app.js`
cannot see an out-of-rail **rate**.

## The intuition

`scanNumbers()` — the only number check on every rendered surface — flags a figure when
`|value| >= ABSURD_MAGNITUDE (1e11)`. That threshold was tuned to item 122, whose bug rendered
`−900,719,925,474,097.9`. It is a **magnitude** rule.

Item 144 was a different animal: `apyMean30d = 36452.38798` rendering as a trusted "30d Mean APY" card, on
a pool whose `totalApy = 0.24` meant the product never flagged it as anomalous. That number is only 3.6e4 —
four orders of magnitude under the floor — so the scanner saw nothing. A human found it.

The figure is absurd **relative to the trust rail**, not relative to 1e11. `APY_SANITY_LIMIT = 1000%` is the
product's own definition of not-credible, so rendering `36,452.4%` unflagged is the product contradicting
itself. That is the rule this item teaches the scanner:

> any rendered `%` figure > `APY_SANITY_LIMIT` on a pool that is **not** anomaly-flagged is a finding

The data legs already knew it (`audit-app.js:323` on text surfaces, `:1010`/`:1017` on the pool snapshot).
The rendered leg — the last thing between a bad number and a human's eyes — never did.

## What changed, in reading order

**1. `audit-app.js:1429-1489` — `collectApyPercentCandidates()`**, a self-contained function shipped into
the page via `page.evaluate`. It walks every text node (skipping `SCRIPT`/`STYLE`/`NOSCRIPT`, mirroring
`innerText`'s own exclusions) and emits one record per `"<number>%"` occurrence:
`{value, raw, excluded, anomalous, scope}`. It deliberately makes **no** threshold decision — the rail
decision lives in exactly one place.

Two DOM facts get captured per figure:

- `excluded` — is the figure inside a **non-rate** percent container? The list is
  `.tvl-trend-note, .gp-item-fill`, code-verified rather than guessed.
- `anomalous` — does the figure's **scope** carry the product's own anomaly marker
  (`.apy-anomalous`, `app.js:2744`, or `.calc-warning`, `PoolDetail.js:657`/`:1117`)? Scope is the nearest
  `.pool-card` ancestor when one exists, else the page.

**2. `audit-app.js:1497-1500` — `filterApyRailBreaches(candidates, limit)`**, pure and exported, four
conditions, unit-testable without Playwright. `limit` is passed in rather than closed over so a test can
walk the boundary without touching the trust-rail import.

**3. `audit-app.js:1540-1547` — the wiring**, inside `auditText()` immediately after the existing
`scanNumbers()` loop. One `apy-rail-breach` P0 per surface, `detail` quoting ≤3 examples verbatim — the
same one-finding-per-surface convention items 169 and 172 established.

**4. `audit-app.js:2126-2127`** — both helpers exported alongside `reconcilePrescanFindings`.

**5. `test_audit_apy_percent_sanity.js`** (new, 358 lines, 22 assertions): 8 pure-helper cases, 6 real-
Chromium DOM-fixture cases (`page.setContent`, not jsdom), 8 rendered acceptance cases driving `runAudit()`
against mutated snapshots.

**6. `package.json`** — one line: the new test joins `test:serial`. No dependency change; `package-lock.json`
untouched. **7.** `signals/audit-findings.json` regenerated once, with the locally installed playwright.

`APY_SANITY_LIMIT` is the existing import at `audit-app.js:101`. No second copy exists anywhere — a rail
mirror inside the scanner would itself be a trust-rail edit.

## The design decision worth arguing with

The predicate is an **exclude-list**: every rendered percent is treated as a rate figure *unless* its
container says otherwise. The alternative — an allow-list of "this IS a rate container" classes — was
rejected, and the reason is this repo's own history. `playbooks/product-audit.md` records the same failure
four times (148 → 159 → 166 → 172): *a checker's signals come from the last bug, so the next bug lands in
the class nobody has been bitten by yet.* An allow-list can only see rate sites someone remembered to
register; an exclude-list catches a brand-new rate render site the day it ships.

The cost is the mirror-image failure: a genuinely new **non-rate** percentage would false-positive. That is
the loud direction to fail in, and it is bounded — the verifier independently grepped every percent render
site in `app.js`, `PoolDetail.js`, `planner.js`, `translations.js` and the generated pages, and found every
dynamic non-rate percent is either in the exclusion set or `Math.min(100, …)`-clamped by construction.

## Deviations from the spec

None material. The spec delegated the rate-vs-non-rate predicate explicitly and required both directions be
proven by test (criteria 2 and 4); both were, on real renders.

## What this does NOT do

It ships a **gate, not a repair.** Zero findings on today's data, on both sides of the diff — every rate
render site reachable today is already railed (144's `mean30dSane`, 145's KPI bound, 165's projection
gates, and `apyBase`/`apyReward` transitively via the anomaly flag). The value is regression coverage, and
the true negative was **proven non-vacuous** rather than reported as health.

No product file, generator, generated page, CSS or dependency is touched. NEVER list independently
re-derived clean by the verifier: this only *adds* a bound to a read-only detector, and the NEVER list
covers *weakening* rails.

## Disclosed, not fixed — one candidate ticket the verifier found

`app.js:2963` renders `${minApy}%+` from the URL query param `?minApy=` (`parseInt`, unbounded,
user-controlled). A crafted `?minApy=50000` would render `"50000%+"` in a `.google-nav-label`, which is
neither excluded nor anomaly-flagged. **Unreachable today** — no audit rotation URL sets `minApy` — and it
is a URL-echoed filter label, not pool data, so fixing it would be scope creep inside this item. Recorded
for a future ticket.

## Honest limitation

Per-`.pool-card` suppression scoping is validated against real-Chromium DOM fixtures, not a real product
grid render: today's grid shows one percent per card, and it is the same value that derives the anomaly
flag, so a "breached-but-unflagged card sitting next to a flagged card" is unconstructible from real
markup. The verifier judged this an honest disclosure rather than an unmet criterion, and its V2/V3
mutations independently confirmed the per-card branch is load-bearing.
