# 176 — explainer (risk tier HIGH)

## Goal

The browser lane is the rendered half of the merge gate. Item 170 shipped on 2026-07-28 specifically
to make it runnable; the first full runs after it were **8 files red**. A gate that is red is a gate
nobody reads, so every "tests green" verdict since then has been weaker than it looked. This item does
not "make it green" — it **classifies every red first**, then applies only the repair each
classification licenses.

## The intuition

A red test is a disagreement between two things that both claim to describe the product. Exactly one
of them is stale, and which one it is decides whether you touch product code or test code. Get that
backwards and you either ship a bug (test updated to match a broken page) or revert a feature (product
"fixed" back to satisfy an old assertion). `playbooks/pre-existing-red-triage.md` is the binding
procedure; this run's contribution is applying it to a whole lane at once rather than one red at a time.

The result is the interesting part: **8 reds, 4 causes, 0 product bugs.** Three of the four causes are
a shipped, authorized product change that never updated its witnesses. That is a pattern, not a
coincidence — and it is now written into the playbook.

## What changed and why

### Class 1 — four files were watching a pipe that was welded shut (spec 096)

`test_waitlist_seo_entry.js`, `test_waitlist_funnel.js`, `test_waitlist_pitch.js`,
`test_spotlight_attribution.js` all observe analytics by reading the `window.mixpanel` stub array.
Item 096 (SHIPPED 2026-07-14) put a production-host gate at `analytics.js:96`: `track()` returns
**before** `mixpanel.track()` on any host outside `PRODUCTION_HOSTS`. These tests serve from
`localhost`, so the queue is *structurally* empty — the failures (`pitch_variant … got undefined`,
`no plan_created track call found`) were reporting the gate, not the product.

`grep -ln "window.mixpanel" test_*.js` returns exactly five files: these four plus
`test_analytics_host_gate_render.js`, which reads the queue **to assert it stays empty**. That fifth
file is the negative control for the very gate that rotted the others, and it is untouched.

Two repairs were on the table and the weaker one was rejected. A spy around `Analytics.track` works,
but downgrades every assertion from *"Mixpanel received this"* to *"the product called track()"*.
Instead each test overrides **only** `Analytics.isProductionHost` via `page.addInitScript` — the shape
`test_analytics_host_gate_render.js:74-89` already established — so the event travels the real path
into the same queue and **every existing assertion stays byte-unchanged**. This is the playbook's
rule-C remedy (neutralise the environment, never weaken the assertion) applied to a rule-B cause.

### Class 2 — one file was asserting a CTA that item 139 deliberately replaced

`test_waitlist_microcopy.js` asserted the card disclaimer under the checkout CTA on **every**
archetype. Item 139 (human-approved 2026-07-23, BET A) made the growth/target primary CTA a real
`<a href="/?pool=…">` "Start growing on `<project>` →" (`planner.js:2967`, `:3004-3017`), demoting the
waitlist to a secondary link. So the disclaimer is not missing from a waitlist CTA — there is no
waitlist CTA in that slot.

The honesty question was checked rather than waved through, because item 070's rail is that a user
learns the card does not exist **before** joining: on the growth path the secondary link opens the
same modal, which renders `waitlistBenefitsEarlyAccess` — *"Nothing's live yet."* The disclosure
survives on the path that reaches the card. Had it not, this would have been rule **A** and the
product would have been the thing to fix.

The two growth cases were repointed, and — mandatory, not optional — the displaced honesty coverage
was **re-homed**: a new EN+KO case drives the secondary link into the modal and asserts the "not live
yet" copy. Repointing alone would have silently shrunk the gate.

### Class 3 — two files were still waiting for the planner on bare `/`

The 2026-07-15 pivot made bare `/` mount the landing (`home.html:82`). `test_snapshot_first.js:233`
waited for `.gp-tagline h1` (planner-only) and `test_footer_hub_links.js:172` for
`#planner-root [class*="gp-"]`. Item 156 fixed exactly this class in two *other* files, and
`test_landing.js:74` already asserts bare `/` must not mount the planner — a sibling test contradicting
the failing one, which the playbook calls the strongest stale-test tell.

`test_snapshot_first.js` scenario (f) now targets `/plan.html`, keeping its "no live call" assertion
intact, and gains a bare-`/` scenario so the file still covers both router paths its own name claims.

### Class 4 — one file was hanging on hosts the sandbox blocks

`test_analytics_fires.js:110` used `waitUntil:'load'`, which waits on every subresource. Generated
pages pull `api.fontshare.com` (via `/style.css`'s **blocking** `@import`) and `mp.defi.garden`; in
this sandbox each hangs ~13s, blowing the 15s budget. Rule C. It now uses the blanket-abort pattern
from `test_snapshot_first.js:107-109` rather than a per-host allowlist the next new host would defeat.
Load time went 16.9s-and-failing → **1.8s and green**.

A plausible wrong answer was rejected on the way: `tokens/big.html` genuinely does not exist (items
148/174 churned the slug set), which makes "the slug rotted" irresistible. It is wrong — `:35-38`
synthesises the page in memory and `:44` serves it, so the checkout's `tokens/` never enters the test.
Fixing that invented cause would have left the real hang to return with the next external host.

## Deviations from the spec

One, and it is the most useful thing in the run. The spec told the builder to re-home
`test_footer_hub_links.js`'s coverage onto `/plan.html`, by analogy with 156. The builder implemented
it, found it red, and **refused to adjust the expectation to match observed output**, reporting it as a
candidate product bug. It was right to: `grep -c seo-hub-links plan.html` = **0** — that surface never
existed there, so the case was a feature request wearing a test's clothes and would have held the gate
red forever. It was deleted and filed as item **179**, together with the second thing that surfaced
(the static `.seo-hub-links` block is occluded by the landing's own fixed footer in landing mode).
The coverage was instead re-homed onto the element that actually inherited the behaviour.

**No product code was changed to make anything pass.** All seven product files are byte-identical to
`origin/main` by `md5sum`.

## Risk tier

**HIGH**, on two independent grounds: the diff is ~354 lines against the 150-line LOW cap, and it
modifies the merge gate itself, where a wrong edit makes every future verdict weaker. Policy lists
tests under LOW, so this is a deliberate departure on size and blast radius — "when in doubt → HIGH".
