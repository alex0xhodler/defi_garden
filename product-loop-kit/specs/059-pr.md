# 059 — Static `pools-snapshot.json` data layer (leg 1 of the data-layer movement)

Risk tier: **HIGH** (FE data path in app.js/planner.js, vercel.json headers, CI workflow). Full
explainer + quiz per NORTH_STAR risk policy.

## Goal

Start the human-directed (2026-07-14 sign-off) movement off pure client-side DefiLlama calls:
a CI-generated, trust-rail-filtered static snapshot that the FE prefers when fresh, with the
live `yields.llama.fi/pools` fetch as the always-there fallback. This is feasibility study
058's option (a) — the only option that keeps the no-backend tenet intact — and the foundation
087 (history/KPIs) and 088 (ICP-facing KPIs) build on.

## Intuition

The FE downloads **10.58 MB (2.10 MB gzip)** from DefiLlama on every load and then throws away
~95% of it: it renders at most the ~700 pools above the $10M floor and reads only 13 of ~28
fields per pool. Project those 13 fields, apply the $10M floor upstream (same rail, same
value, applied earlier — never relaxed), and the identical rendered experience costs
**220 KB raw / 51.8 KB gzip** — a 97.6% wire cut, served from our own CDN edge.

The subtlety is that "identical" has three exceptions, each of which the design routes around
by just using the live fetch:

1. The analytics app lets users relax TVL below $10M (`minTvl=0` URLs, 10k/50k chain-mode
   chips) — pools the railed snapshot doesn't carry. → Snapshot is only used when the
   effective floor is ≥ $10M, and if the user relaxes it mid-session, the app refetches live
   once and swaps the data.
2. `?pool=` deep links are sacred and may point at sub-$10M pools; serving them from the
   snapshot could falsely render 072's "no longer tracked" state. → `?pool=` loads always
   fetch live.
3. Anomalous pools (>1000% APY) are *rendered* (demoted + ⚠-flagged), never hidden, in the
   analytics app. → The snapshot keeps them (filter is TVL-only); the flag/demotion logic
   stays client-side, byte-untouched.

Freshness is honesty-gated: the FE reads a ~150-byte meta file first and uses the snapshot
only if `generatedAt` is under 15 minutes old; anything else — stale, missing, malformed,
wrong schema — falls back to today's exact live path. At the current **daily** CI cadence the
snapshot will be stale almost always in production, so today this ships plumbing + proof, not
a realized perf win; raising cadence is a human decision (every snapshot commit = a Vercel
deploy — the 2026-07-13 quota constraint) and/or 087's job. The FE never presents a stale
snapshot as live data.

## What changed, in reading order

1. **`generate-pools-snapshot.js`** (new): fetches `/pools` once; emits
   `data/pools-snapshot.json` (envelope: `schemaVersion:1, generatedAt, source, minTvlUsd,
   count, pools[13-field rows, tvlUsd ≥ $10M, anomalous kept]`), `data/pools-snapshot-meta.json`
   (tiny freshness probe), and per-chain/per-token slices under `data/pools/{chain,token}/`
   (087/088's future input; no consumer yet). 081/083 discipline: byte-identical-modulo-
   `generatedAt` regen skips all writes (no churn commits); stale slices deleted (031 pattern);
   `--out` fully isolates scratch runs (076 lesson).
2. **`data/`** (new, 413 files): a real live run's output — 15,416 fetched → 713 railed,
   generatedAt 2026-07-14T13:02:57Z.
3. **`app.js`**: the background pools fetch now tries meta → snapshot when (no `?pool=` param)
   AND (initial `minTvl ≥ DEFAULT_MIN_TVL`) AND (meta fresh ≤ 15 min, schemaVersion 1, valid
   non-empty payload); otherwise — and on ANY failure — the exact pre-existing live path runs.
   A small effect refetches live once if pools came from the snapshot and `minTvl` later drops
   below the floor (chips, chain modes, popstate). The existing `data_load_time` analytics
   event now carries `source: 'snapshot' | 'live'`, so rollout is observable in Mixpanel.
4. **`planner.js`**: same meta→snapshot→validate / anything-fails→live logic in front of
   `POOLS_API`. Planner rails (50M/10M floors, sanity limit, stable curation, degen haircut)
   apply unchanged to whichever payload loads — they're all ≥ the snapshot floor, so the
   snapshot always covers the planner.
5. **Artifacts**: `app.compiled.js`, `app.compiled.min.js`, `planner.min.js` regenerated
   (061's lesson: the HTML loads the min files).
6. **`vercel.json`**: one added headers rule — `/data/(.*)` gets
   `Cache-Control: public, max-age=300, stale-while-revalidate=600`. Nothing else touched.
7. **`.github/workflows/sitemap-update.yml`**: `node generate-pools-snapshot.js` step before
   the token/chain generators; `data` staged in the commit step; the generator added to push
   trigger paths. The three SEO generators still fetch live themselves — converting them to
   read the snapshot is deliberately out of scope (087 extends the generator first).
8. **Tests**: `test_pools_snapshot.js` (9 pure-Node asserts: projection exactness, floor,
   anomalous-kept, envelope/meta/slices, idempotency, `--out` isolation, stale-slice deletion)
   and `test_snapshot_first.js` (7 rendered-Playwright scenarios: snapshot-path renders
   `?token=USDC` cards with live aborted; missing→fallback; stale→fallback with live actually
   hit; snapshot-vs-live equivalence; below-floor gate; bare-`/` planner on snapshot; `?pool=`
   always live). Both wired into `npm test`.
9. **Existing test harnesses** (11 files, test-only): committing a real `data/` made every
   fixture-routed browser test's local server serve a *fresh* snapshot, which the new FE then
   preferred over the test's `yields.llama.fi` fixture — a time-dependent flake. Each affected
   suite now routes `**/data/pools-snapshot*` to a 200 response with a **stale** (2020)
   `generatedAt`, deterministically forcing the live-fixture path those tests were written to
   exercise. 200-stale over 404 because Chromium logs a console error on 404s, tripping the
   suites' page-error guards. This exercises the real stale→live product code path on every
   suite run — it masks nothing; the snapshot-fresh path has its own dedicated suite.

## Deviations from spec

- Token slices are keyed by full slugified `symbol` (e.g. `wbtc-usdc`), not exploded per
  individual token — this matches the spec's own measured slice count (~411) and the envelope
  the FE would actually filter by. Documented in 059-notes.md.
- The builder could not run the entire `npm test` chain in one ≤5-min pass (it exceeds the
  timebox by design of the chain); every new/affected suite was run individually green, and
  the operator re-ran the remaining patched suites separately. Documented in 059-notes.md.

## Measurement

- `data_load_time.source` (snapshot|live) in Mixpanel shows real-world path split from day one.
- Payload numbers (measured live, 2026-07-14): full 10,575,356 B / 2,095,248 gzip vs railed
  snapshot 220,167 B / 51,763 gzip.
- Guardrails unchanged: `error_occurred` rate, planner conversion, `?token=`/`?chain=`/`?pool=`
  rendering (E2's scenario (a) + the smoke gate keep watching the SEO lifeline).
