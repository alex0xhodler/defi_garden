# 196 — explainer (HIGH tier)

## Goal, in one line

The audit renders 6 SEO pages a tick out of 2,195, and it picks them **with a coin flip every
time** — so it re-audits pages it already checked while thousands have never been rendered once.
This gives that picker a memory, exactly the way item 183 gave one to the pool-detail picker.

## The intuition

Imagine checking a 2,195-page book for typos at 6 pages a day, and choosing those 6 pages by
rolling dice **without ever writing down which pages you already read**. You'd re-read page 400
three times before you ever opened page 12. That is not a hypothetical — measured on this
checkout, over a 180-day horizon:

| | measured on `origin/main` |
|---|---|
| chain pages: renders spent re-reading a page already audited | **276 of 360 — 77%** |
| chain pages never rendered once, after half a year of daily audits | **3 of 87** |
| token pages: wasted re-renders | **101** |

The fix is the obvious one and it costs nothing: **write down what you read**. Same 6 renders a
tick, spent on pages nobody has looked at yet. Full-pass time goes from a coupon-collector
expectation of ~4,338 days (tokens) / ~220 days (chains) to a deterministic **527 / 44** — an
8.2× and 5.0× gain **at an identical render budget**.

## Why this item existed at all

No READY item was on the board — every row 001–195 is terminal. So this run promoted one item
from documented in-repo evidence, per `prompts/build.md`'s no-READY branch. The evidence was
sitting in `specs/154-notes.md`, which recorded its own limitation *and* named the remedy as
unbuilt: *"follow-up (**prefer never-audited slugs** / cheap grep prescan promoting suspicious
pages into the rendered sample) documented, not built."*

Item **157** built the second half (prescan promotion). Item **183 leg (b)** built the first half —
persisted `seen`, never-audited-first, wrap — **for pool-detail only**. Item **191** then argued
the throughput case for pools, and **192** shipped it. Nobody ever walked the same argument back
to the static leg, which is both the older blind spot and the larger population. That is the whole
item: **183's mechanism, applied to the surface it was never applied to.**

It also happens to be where the traffic is. `signals/2026-07-31.md`'s prod `page_view` log for the
week is 11 events, and **8 of the 11 are static SEO leaves**.

## What changed, in reading order

Everything is in `audit-app.js`. No product file, no trust rail, no router, no generated SEO
artifact, no new dependency.

**1. `normalizeRotationLeg(leg)` — new shared helper (~line 2383).**
The `{cycle, seen}` validate-and-default logic was inlined inside `readRotationState()`. It is now
one function, called by both readers. This is the spec's "factor, do not duplicate" rule: two
copies of a degrade-to-empty validator is how the two readers silently drift apart later.
`readRotationState()`'s external contract — it is exported and existing tests use it — is
unchanged; the old inline check and the new helper accept and reject exactly the same inputs.

**2. `readStaticRotationState(statePath)` — new (~line 2404).**
Reads `{ schemaVersion, tokens: {cycle, seen}, chains: {cycle, seen} }` and normalizes **each leg
independently**. That independence is deliberate: a corrupt `chains` leg must not throw away a
perfectly good `tokens` leg. Missing file, corrupt JSON, `{}`, `{tokens: 5}`,
`{tokens: {seen: "nope"}}` all degrade to a fresh cycle-0 state and a normal pick. It never throws.

**3. `STATIC_ROTATION_SEEN_CAP = 6000` — the trap this item had to not fall into (~line 376).**
The pool leg caps its `seen` list at `ROTATION_SEEN_CAP = 2000`, drop-oldest, against ~737 pools.
Reusing that constant here would have been the natural move and it would have **silently destroyed
the entire item**: the token estate is **2,109 pages — already larger than 2000**, so `seen` would
evict its own oldest entries before a cycle could ever complete, `unseen` would never empty, the
wrap branch would become permanently dead code, and evicted pages would quietly come back into the
pick pool. The test asserts the cap exceeds the **real leaf count read off disk** — not a hardcoded
literal — so if the estate ever grows past 6000, the assertion breaks instead of the feature.

**4. `buildStaticSurfaces()`'s rotation tail (~line 2019).**
Two lines changed shape:

```js
- const tokenPicks = sampleBySeed(tokenLeaves, tokenCount, `${seed}:tokens`);
- const chainPicks = sampleBySeed(chainLeaves, chainCount, `${seed}:chains`);
+ const tokenRot = computeRotation(tokenLeaves, tokenCount, `${seed}:tokens`, priorStaticRotationState.tokens);
+ const chainRot = computeRotation(chainLeaves, chainCount, `${seed}:chains`, priorStaticRotationState.chains);
```

`computeRotation()` is 183's function, **called, not copied, not modified**. It already layers
unseen-first + wrap + fill-from-seen on top of the same `sampleBySeed` primitive.

**Why twice rather than once over a combined list** — the one real judgement call. A single
rotation over all 2,195 leaves with one budget would starve chains roughly 96:4, because unseen-first
picking is blind to which directory a page lives in. Chains is the *acute* case (77% waste), so a
"simplification" that made chain coverage worse would have inverted the item. Two calls preserve
spec 154's deliberate 2:1 token:chain split exactly.

**5. Fold everything audited into `seen`.**
The anchor leaf, every prescan-promoted leaf (routed to its leg by `tokens/`/`chains/` prefix), and
every rotation pick. A page rendered for *any* reason has been audited. This mirrors
`buildPoolSurfaces()`'s `thisRunPoolIds` rule.

**6. `runAudit()` — persist + report (~line 3733, ~3756, ~3889).**
A second persist block sitting immediately beside the pool one, sharing its two guarantees: it
writes **only** under `opts.persistRotationState` (set by the CLI entry point alone, so no library
call — no existing `test_audit_*.js` — can ever touch the committed file), and **only** when the
serialized bytes differ. Plus `staticRotation` in the findings JSON next to `poolRotation`, and one
CLI summary line so the heartbeat can read coverage position without re-deriving it.

## What was deliberately NOT built

- **The render budget stays 6.** This item buys throughput at constant cost. Raising the budget is
  a separate, separately-measurable decision — exactly how 191 (argue) and 192 (raise) were split.
- **192's `baseSeen` reconciliation was not ported**, and that omission is the interesting one.
  That machinery exists because pool-detail rotation picks can be *skipped* by the
  `AUDIT_TIME_BUDGET_MS` wall-clock guard, so an un-rendered pick must not be credited as seen. The
  static leg has no such skip — the guard is gated on `rotationPick`, a pool-surface-only marker.
  Porting machinery whose precondition doesn't exist is how a codebase accumulates cargo. There's a
  comment recording that if a time budget is ever added to the static leg, the reconciliation
  becomes required.

## Deviations from the spec — the builder corrected the spec, and was right

**Acceptance criterion 10 as written was arithmetically impossible, and that is the spec author's
error, not the builder's.** It asked for "≥ 1,080 distinct token pages" over 180 days. At the
unchanged 4-token-picks-per-tick budget there are only 4 × 180 = **720 token render slots in the
entire window**. 1,080 is 6 × 180 — the *combined* tokens+chains budget, mis-attributed to the
token leg alone. The builder asserted the true derived ceiling instead: **720 distinct token pages,
zero re-renders** (population 2,107 ≫ 720, so no wrap is even possible in that window), which
recovers all 101 of `origin/main`'s measured token re-renders as new coverage. That is a *stronger*
assertion than the original, not a lowered bar.

Second, criterion 10's "zero chain re-renders before the wrap" needed a one-tick correction: 87
chain candidates at 2/tick leaves a remainder of 1, so the tick that completes coverage necessarily
fills its final slot from an already-seen candidate — `computeRotation()`'s documented
fill-from-seen branch doing exactly what 183 designed it to do. The test asserts the
*dynamically-computed* forced-repeat count rather than a hardcoded zero.

Both deviations are recorded in `specs/196-notes.md` rather than smoothed over.

## Evidence it isn't vacuous

The builder stashed `audit-app.js` and re-ran the new test against reverted code: **11 of 13
assertions went red**, criterion 1 among them, and `git stash pop` restored the diff byte-exact.
The verifier then ran its own independent, differently-shaped mutation. Details of both are in the
notes and the verifier's verdict.

A real end-to-end `node audit-app.js` run completed `status: OK`, wrote the new state file with
non-empty `tokens.seen` and `chains.seen`, and emitted:

```
[audit] static rotation: tokens cycle 0, seen 5/2107 candidates, picked [...], wrapped=false
                       | chains cycle 0, seen 2/87 candidates, picked [...], wrapped=false
```

```bash
node audit-app.js          # look for the "[audit] static rotation:" line
cat product-loop-kit/signals/audit-static-rotation.json   # seen[] grows ~6/tick, no repeats

```

Over the next fortnight the honest signal is: `staticRotation.*.seenCount` advancing by ~6 per tick
with **zero repeats while unseen candidates remain**. Repeats appearing before a wrap would be the
revert trigger.
