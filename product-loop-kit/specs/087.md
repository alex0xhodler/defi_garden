## What

KPIs need history (rate momentum, stability, TVL trend, pool age all require snapshots over time —
058 §6). Two phases:

- **Phase 0 (loop-buildable, no credentials, READY once 059 ships):** retained slim snapshots in CI —
  the 059 generator keeps the last N (e.g. 30 daily) trust-rail-filtered, 13-field snapshots as
  committed artifacts (the sitemap-update.yml pattern; slim = the filtered subset, not the multi-MB raw
  payload; 081/083 freshness discipline applies — no churn commits when content is unchanged). A
  `compute-kpis.js` step derives per-pool KPI fields from the retained window and emits them INTO the
  current snapshot (so 088's FE work reads one file). Poor-man's history, zero backend, zero secrets.
- **Phase 1 (BLOCKED on human):** Turso/libSQL ingestion per 058 §2 — every CI poll appends to a hosted
  SQLite; KPI computation reads the DB instead of retained files; enables intraday granularity and
  longer windows. NEVER-list constraint: loops never handle credentials — the human creates the Turso
  account/DB and installs the token as a GitHub Actions secret; loops then build the ingestion/read code
  against it. Also gated on the human's DefiLlama ToS read (058 §3, still open).

## Trust rails (verbatim intent from 058 §5 — binding on any build)

The pipeline applies `APY_SANITY_LIMIT = 1000%` and `DEFAULT_MIN_TVL = $10M` at snapshot-build time and
must NEVER be the place these rails get relaxed. Anomaly flags ship THROUGH the pipeline (show flagged,
not hide flagged). Every KPI is derived, disclosed, and never overrides the hard rails — ranking within
passing pools only.

## Territory notes (verified in code 2026-07-14 — these BIND the design)

1. **The 059 generator is the extension point.** `generate-pools-snapshot.js` already fetches
   `/pools` once, applies the $10M TVL floor upstream (anomalous KEPT), projects onto the 13 used
   fields, and writes `data/pools-snapshot.json` + `data/pools-snapshot-meta.json` +
   `data/pools/{chain,token}/<slug>.json` slices, all under an all-or-nothing freshness gate
   (`normalizeSnapshotContent` strips `generatedAt`/`bytes` so a no-data-change run writes nothing —
   081/083 discipline). 087 layers history + KPIs ON TOP without disturbing that path.
2. **The churn trap (must be designed around).** If a separate step writes `kpis` INTO the committed
   snapshot, the 059 generator's next run would produce kpi-less content, compare-unequal, and rewrite
   the file (stripping kpis) EVERY run — infinite daily churn = a daily Vercel deploy (2026-07-13
   quota crisis). Fix: extend `normalizeSnapshotContent` to also strip any per-pool `"kpis":{…}` so a
   kpi-enriched committed file still compares equal to a fresh kpi-less generation when the railed
   pools are unchanged. Shared by the full snapshot AND every slice (one normalize fn).
3. **History must piggyback, never add deploys.** After 081 the daily job commits ONLY on real data
   change. A new dated history point is appended ONLY when the slim pool data differs from the most
   recent retained point — identical data day-over-day adds no file, no commit. History is a real
   time series of *changes*, honestly dated; irregular sampling is fine for the KPIs below.
4. **KPIs never touch the rails.** `compute-kpis.js` NEVER filters, drops, reorders, or re-weights a
   pool. It only ADDS a derived, null-safe `kpis` object. Rails (`APY_SANITY_LIMIT`,
   `DEFAULT_MIN_TVL`, anomaly flags) are already applied upstream by the 059 generator and stay
   byte-untouched. KPIs rank within already-passing pools only (058 §5).

## Full acceptance criteria (written by the picking loop, 2026-07-14)

**A. History retention (`data/history/<YYYY-MM-DD>.json`, no credentials, no backend)**
- A1. A slim per-date file: `{ schemaVersion: 1, date, generatedAt, count, pools: { "<poolId>":
  [apyTotal, tvlUsd], … } }` where `apyTotal = round((apyBase||0)+(apyReward||0), 4)` and `tvlUsd`
  is the integer TVL. Keyed by `pool` id for O(1) KPI lookup. Slim = only the fields KPIs need.
- A2. Freshness discipline: append today's point ONLY if its `pools` map differs from the most
  recent existing history file's `pools` map (compare the data, ignore `date`/`generatedAt`).
  Identical data → no new file, no write. A second run on the SAME date overwrites that date's file
  (idempotent within a day) only if the data changed.
- A3. Retention window: keep the N=30 most-recent dated files (lexicographic on `YYYY-MM-DD`); prune
  (delete) older ones — mirrors the 031 stale-deletion pattern.
- A4. `--out <dir>` / injectable dataDir + date for tests: writes NOTHING outside the out dir (076
  lesson). Date is injected (never `new Date()` inside the pure core), so tests are deterministic.

**B. KPI computation (`compute-kpis.js`, Node 18-compatible, zero new deps)**
- B1. For each pool in the current `data/pools-snapshot.json`, gather its series across ALL retained
  history files (ordered by date; the just-appended today point included). Emit a `kpis` object:
  - `historyPoints`: integer count of retained points the pool appears in (track record length).
  - `firstSeen`: earliest `date` (YYYY-MM-DD) the pool appears in the window (pool-age proxy).
  - `apyMomentum`: `round(latestApyTotal − earliestApyTotal, 2)` in pct-points; **null if <2 points**.
  - `apyStdev`: population stdev of `apyTotal` across the series, `round(…,2)`; **null if <2 points**.
  - `tvlTrend`: `round((latestTvl − earliestTvl)/earliestTvl, 4)` fraction; **null if <2 points or
    earliestTvl === 0**.
  Null is honest ("no track record / not enough history yet") — never a fabricated 0.
- B2. `compute-kpis.js` writes the enriched `kpis` INTO `data/pools-snapshot.json` AND the per-chain
  and per-token slices (so 088 reads one file, whichever it opens), under its OWN all-or-nothing
  freshness gate (skip all writes if the enriched content is byte-identical modulo `generatedAt`).
- B3. It NEVER filters/drops/reorders pools and NEVER reads or writes the rail constants — a header
  comment states this. The pool set and order in every output file is exactly what the 059 generator
  produced.
- B4. Pure exported core (`computeKpis`, `appendHistory`, series-building, stdev) so
  `test_compute_kpis.js` asserts against fixtures in `os.tmpdir()` dirs — no network, no browser
  (the 059/test_pools_snapshot.js precedent).

**C. 059 generator idempotency preserved**
- C1. Extend `normalizeSnapshotContent` in `generate-pools-snapshot.js` to strip any per-pool
  `"kpis":{…}` (in addition to `generatedAt`/`bytes`) so a kpi-enriched committed snapshot/slice
  still compares equal to a fresh kpi-less generation when railed pools are unchanged — no churn.
  All existing `test_pools_snapshot.js` assertions still pass unchanged.

**D. CI wiring (`.github/workflows/sitemap-update.yml`)**
- D1. A new step AFTER "Generate pools snapshot" runs `node compute-kpis.js` (which does the history
  append + KPI enrichment). `data/` is already in the `git add` line and the "Check for changes"
  gate, so new history files + enriched snapshot ride the existing daily commit — no extra deploy.
- D2. `compute-kpis.js` added to the `push:`-trigger `paths:` list for completeness.

**E. Tests green**
- E1. `test_compute_kpis.js` added to `package.json`'s `test` chain; the full chain runs to
  completion within the timebox (or the pre-existing in-sandbox failure point is stash-baseline
  documented — never a new failure introduced by this item).
