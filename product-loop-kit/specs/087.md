## What

KPIs need history (rate momentum, stability, TVL trend, pool age all require snapshots over time —
058 §6). Two phases:

- **Phase 0 (loop-buildable, no credentials, READY once 059 ships):** retained slim snapshots in CI —
  the 059 generator keeps the last N (e.g. 30 daily) trust-rail-filtered, 13-field snapshots as
  committed artifacts (the sitemap-update.yml pattern; slim = the filtered subset, not the multi-MB raw
  payload; 081/083 freshness discipline applies — no churn commits when content is unchanged). A
  `compute-kpis.js` step derives per-pool KPI fields from the retained window and emits them INTO the
  current snapshot (so 088's FE work reads one file). Poor-man's history, zero backend, zero secrets.
- **Phase 1 (BLOCKED on human):** Turso/libSQL ingestion per 058 §2 — every CI poll appends to a hosted
  SQLite; KPI computation reads the DB instead of retained files; enables intraday granularity and
  longer windows. NEVER-list constraint: loops never handle credentials — the human creates the Turso
  account/DB and installs the token as a GitHub Actions secret; loops then build the ingestion/read code
  against it. Also gated on the human's DefiLlama ToS read (058 §3, still open).

## Trust rails (verbatim intent from 058 §5 — binding on any build)

The pipeline applies `APY_SANITY_LIMIT = 1000%` and `DEFAULT_MIN_TVL = $10M` at snapshot-build time and
must NEVER be the place these rails get relaxed. Anomaly flags ship THROUGH the pipeline (show flagged,
not hide flagged). Every KPI is derived, disclosed, and never overrides the hard rails — ranking within
passing pools only.
