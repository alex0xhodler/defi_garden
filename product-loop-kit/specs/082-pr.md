# 082 — PR explainer (HIGH tier): planner no longer dies on a missing `translations` global

## Goal
Kill a real, observed production crash at the very top of the north-star funnel. On 2026-07-13 the first-ever `error_occurred` event fired from the bare `/` (the planner): `ReferenceError: translations is not defined`, thrown from `planner.min.js` inside a `useMemo`. For that session the planner render broke — a funnel-top failure, which per NORTH_STAR ("a bug at a funnel step outranks any experiment") is the highest-priority work available.

## Intuition
`home.html` loads `translations.min.js` and then `planner.min.js`, both `defer`, so normally the `translations` global exists before the planner runs. But "normally" isn't "always": a transient network failure, an interrupted request, or a deploy race can leave `translations` undefined at the moment `makeT()` runs. The old code dereferenced the **bare global** (`translations[lang]`) — and in JavaScript, reading an undeclared identifier doesn't return `undefined`, it **throws**. Inside React's `useMemo`, that uncaught throw kills the whole render.

The fix is the standard missing-global idiom: `typeof translations !== 'undefined'` never throws, so wrap all access in a safe accessor and degrade gracefully when it returns nothing.

## What changed and why (diff in reading order)

### 1. `planner.js` — the actual fix (~20 lines, i18n block, lines 794–826)
- **New `safeTranslations()`**: returns the real `translations` object when the global exists; falls back to `window.translations`; else `null`. The `typeof` check is what removes the uncaught `ReferenceError`.
- **`makeT(lang)` rewritten**: the returned `t()` now calls `safeTranslations()` **on every invocation** instead of dereferencing `translations` once at creation time. Two payoffs: (a) if translations never loaded, `t()` returns the key string — the exact same graceful degradation `t()` already used for unknown keys — and the planner still mounts; (b) **lazy recovery**: if `translations.min.js` loads *late* (the most likely real trigger — a deferred-script race), the very next render pass picks up real strings, no remount needed. When translations IS present, resolution is identical to before (per-lang `.planner` dict → `en.planner` fallback → function-valued entries applied with args → key-echo for unknown keys).
- **`rootT(lang, key)` rewritten** the same way. When the global is missing it returns the key (its sole caller renders the result as text, so a string is safe); when present, behavior is byte-identical, including returning `undefined` for keys missing in both dicts.

### 2. `planner.min.js` — regenerated
`plan.html`/`home.html` load the **min** file; editing `planner.js` without regenerating it ships nothing (the 061/068 caught-bug precedent). `test_minified_assets.js` confirms the committed min is byte-identical to a fresh minify, and the `typeof translations` guard survives terser (free global references can't be mangled).

### 3. `test_translations_fallback.js` — new, wired into `npm test` (package.json, one line)
Slices the `safeTranslations`/`makeT`/`rootT` block out of `planner.js` and runs it in a `node:vm` context. 8 assertions: no-throw + key-echo with the global absent; lazy recovery when the global appears later; the `window.translations` branch; identical normal-path semantics against a stub (ko dict, en fallback, function-valued entries, `undefined` for missing root keys); guard present in `planner.min.js`; minify idempotence. The verifier's mutation check proved it bites: reintroducing the bare dereference in a scratch copy fails 5/8 assertions with the exact original `ReferenceError`.

### 4. Bookkeeping (this folder)
Spec status, notes, this explainer, LOG entry — all in the same single commit per the 2026-07-13/14 ship-path decisions.

## Deviations from the spec's literal text
The spec floated an "inline en fallback" dictionary. Deliberately **not** done: it would duplicate `translations.js` (CLAUDE.md single-source rule), and it's impossible anyway — the English strings live *inside* the payload that failed to load. Key-echo + lazy recovery is the honest minimal fallback. No new user-facing string, so no EN/KO change. Documented in `specs/082-notes.md`; the verifier reviewed and accepted the reasoning.

## What this does NOT fix
If the true trigger turns out to be `translations.min.js` permanently 404ing on a bad deploy, sessions would see key-echo text (degraded, not broken) instead of a dead planner. That's a deploy-integrity follow-up, noted in 082-notes; the guard is correct either way.
