# PR: Honest empty states — noindex + real content when a query has zero pools (backlog 012)

**Risk tier (builder's guess): HIGH** — per 012.md's own pre-classification and NORTH_STAR.md's
risk map ("user-facing + SEO surface" and "any parameterized-URL behavior" both apply). Git is
unavailable in this environment (task constraint: no git operations, read-only bash mount aside
from grep/read/test-running), so there is no branch or commit — this file is the PR, reviewable at
the working-tree paths cited below. A second agent worked `home.html`/`canonical.js` (spec 011) in
parallel; this item's surface was scoped to `app.js`/`translations.js` (+ a small, pre-authorized
`style.css` hook) specifically so the two could not collide.

## Goal
`specs/010-diagnosis.md` traced GSC's 3,568 "Soft 404" pages to two mechanisms: dead/delisted
tokens rendering an empty result grid at HTTP 200, and the pools API fetch not completing inside a
crawler's render budget — both produce the same "no content" DOM that Google classifies as a soft
404. Static hosting means there's no way to return a real 404 per query. 012's fix: make the
empty state tell the truth twice — once to search engines (a client-injected `noindex` exactly
when, and only when, a resolved query genuinely has zero results) and once to the human (replace
the bare "no results" message with an honest explanation plus real, live alternatives, so the page
is never a dead end).

## Investigation before writing any code
Two things turned up during research that reshaped the implementation, both documented in full in
`012-notes.md`:

1. **The empty state already renders during the pre-fetch flash, for every query, including
   valid ones.** `pools` starts `[]` and the fetch is async with an explicit "no blocking loading
   state" design; for the first render(s) of any token/chain URL, `filteredPools` is trivially
   `[]`. This is diagnosis's OTHER soft-404 mechanism, hiding in plain sight in the exact code path
   this spec targets. Gating only on `filteredPools.length === 0` (as a literal reading of "if the
   query yields 0 pools" might suggest) would have made the new, stronger content — a specific
   claim about the $10M floor, plus a `noindex` tag — fire on completely valid, popular tokens
   during that window, actively regressing the class this item exists to fix. Both the honest
   sentence and the `noindex` toggle instead gate on `pools.length > 0` (the fetch has actually
   resolved) via one shared `emptyStateResolved` boolean.
2. **`app.js`'s `t()` is a flat lookup**, not namespaced under `planner` the way some of
   `translations.js`'s structure might suggest — confirmed by reading `createTranslationFunction`'s
   body before adding any key, per the dispatch instructions' explicit warning not to assume.

### 2. `app.js:1947-2003` — the empty-state engine
```js
const emptyStateResolved = currentView !== 'pool-detail' && pools.length > 0 && filteredPools.length === 0 &&
  !!(selectedToken || (chainMode && selectedChain));

const getEmptyStateAlternatives = (targetChain) => {
  const passesTrustRails = (pool) => pool.tvlUsd >= DEFAULT_MIN_TVL && !isAnomalousApy(pool);
  const byTvlDesc = (a, b) => b.tvlUsd - a.tvlUsd;

  if (targetChain && targetChain !== 'All' && targetChain !== 'Popular') {
    const sameChain = pools.filter(p => p.chain === targetChain && passesTrustRails(p)).sort(byTvlDesc);
    if (sameChain.length > 0) return { items: sameChain.slice(0, 5), source: 'chain' };
  }

  const stable = pools.filter(p => isStableSymbol(p.symbol) && passesTrustRails(p)).sort(byTvlDesc);
  return { items: stable.slice(0, 5), source: 'stable' };
};

const emptyAlternatives = useMemo(
  () => (emptyStateResolved ? getEmptyStateAlternatives(selectedChain) : { items: [], source: 'stable' }),
  [emptyStateResolved, selectedChain, pools]
);

useEffect(() => {
  let robotsMeta = document.querySelector('meta[name="robots"]');
  if (emptyStateResolved) {
    if (!robotsMeta) {
      robotsMeta = document.createElement('meta');
      robotsMeta.setAttribute('name', 'robots');
      document.head.appendChild(robotsMeta);
    }
    if (robotsMeta.getAttribute('content') !== 'noindex') {
      robotsMeta.setAttribute('content', 'noindex');
    }
  } else if (robotsMeta && robotsMeta.getAttribute('content') === 'noindex') {
    robotsMeta.setAttribute('content', 'index, follow');
  }
}, [emptyStateResolved]);
```
Alternatives: same-chain top-TVL first, else top-TVL stablecoin pools globally — both branches
require `tvlUsd >= DEFAULT_MIN_TVL` (the fixed $10M floor, not the user's own possibly-relaxed
`minTvl`) and `!isAnomalousApy(pool)` (reused, not re-derived), so an anomalous or sub-floor pool
can never appear as a "trustworthy" suggestion — this satisfies the spec's trust-rail acceptance
criterion directly, by construction, rather than by a separate check. Returns `{items, source}` so
the render never has to guess which strategy fired.

Noindex toggle: finds-or-creates `home.html`'s existing `meta[name="robots"]` node (home.html:14
ships it unconditionally; spec 011 explicitly excludes robots meta from its own scope) and mutates
its `content` attribute in place — `appendChild` only ever runs when the node is genuinely absent,
so there is structurally never more than one such tag. Restores `"index, follow"` (matching what
every other page already ships) rather than merely deleting the tag when the condition clears.

## Design decision: a bug I found and fixed before calling this done
`emptyStateResolved` includes `currentView !== 'pool-detail'` (`app.js:1960`). Without it: a user
who reaches a genuine dead-token empty state, sees an alternative pool card, and clicks it, would
land on that pool's real detail page while `selectedToken` (still the dead token) and
`filteredPools` (stale — the filter effect intentionally skips recomputing while
`currentView === 'pool-detail'`, a pre-existing, unrelated guard) still satisfied the "empty"
condition — incorrectly leaving a perfectly valid, indexable page `noindex`ed as a side effect of
where the user came from. Caught this by tracing the click-through path after the feature otherwise
looked complete, not by spec instruction. Verified the fix with a synthetic-DOM Node simulation
(5 scenarios) — see Verification.

## Deviations from spec
- **`style.css` touched.** `012.md`'s acceptance criteria literally reads "no changes outside
  app.js/translations.js"; this run's dispatch instructions explicitly widen that surface to
  "app.js + translations.js (+ pool-detail-styles.css/style.css only if a small style hook is
  unavoidable)" — I judged the `text-align` fix unavoidable (a real rendering bug, not polish) and
  used the wider, more specific grant. 8 lines, tokens only.
- **`?pool=<dead-id>` deep links are not extended to.** They're structurally a soft-404-shaped gap
  (a dead pool id silently falls back to the full homepage DOM, no empty-state ever renders,
  because `selectedToken`/`selectedChain` are never set by that code path) but fixing it would mean
  building a new render path and a new noindex trigger point for a state the app doesn't currently
  visualize at all — drifting into "router semantics," which 012.md explicitly places out of scope
  (as does 011, for symmetry). Documented rather than silently left; candidate for a future item.
- **Alternatives always render as a card grid, independent of the user's list/grid `viewMode`
  toggle** — deliberate: a small, fixed-size "you might also look at these" block reads more
  clearly as distinct content in the grid layout, and the main results grid never coexists on
  screen with the empty state, so there's no visual inconsistency to reconcile.
- Everything else — the pools fetch/filter pipeline, `error_occurred`, pagination, sort controls,
  the pre-existing bare-message copy (`noYieldsFound`/`adjustFilters`/reset buttons) — untouched,
  as OUT of scope in 012.md.
