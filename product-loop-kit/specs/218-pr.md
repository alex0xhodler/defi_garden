# 218 — explainer (HIGH tier)

**One line:** on the pool-detail page the footer stops being a fixed overlay and joins the document flow, because the north-star CTA was sitting behind it — invisible and unclickable — the moment the page loaded on a 360px-wide phone.

## Goal

`pool_click{source=garden_cta}` is half the north-star metric. It is emitted by the "Garden this pool →" anchor on the pool-detail page. At 360×780, at `scrollY = 0` — before the user touches anything — that button was underneath the opaque fixed footer, and `document.elementFromPoint()` at the button's lower band returned a footer element, meaning the footer swallowed the tap. **A metric cannot fire from a button the user can neither see nor press.**

## Intuition

`.app-footer` is `position: fixed; bottom: 0; z-index: 100` with an opaque background. It therefore owns the bottom 58px (≤768px) / 69px (1280px) of the viewport **at every scroll position**.

The app's defence against that is `.app { padding-bottom: 80px }` — "space for footer". That is *clearance*: it keeps the **last** pixels of the document out from under the overlay. Item 217 (shipped hours earlier, same day) restored exactly this clearance on pool-detail after a view-specific `padding: 0` had cancelled it.

Clearance protects the end of the document. It can do nothing for an element in the **middle** of the document that happens to land in the footer band at rest — and where the hero CTA lands depends on the height of the content above it, which varies by pool. On the human's `morpho-blue/SIRLOINUSDC` pool the whole 47px button was buried; on the suite's STETH fixture it was the bottom 28.3px. Same defect, different arithmetic. **No clearance value fixes a content-dependent overlap.** The overlay itself has to go.

## What changed and why

`pool-detail-styles.css` (raw) + `pool-detail-styles.min.css` (the sheet `home.html:167` actually injects — a raw-only fix ships dead, item 136's trap):

```css
.app.pool-detail-view .app-footer { position: static; margin-top: auto; }
.app.pool-detail-view            { padding-bottom: 0; }
```

- **`position: static`** — the footer leaves the fixed layer *on this view only*. Nothing on the page can be occluded or click-intercepted at any scroll position, at any viewport. This is strictly stronger than clearance, which it replaces here.
- **`margin-top: auto`** — the flex sticky-footer idiom, so an unusually short pool-detail render puts the footer at the bottom of the screen rather than floating mid-page. It introduces no new layout mode: `.app.pool-detail-view` is already `display:flex; flex-direction:column` via `.app:not(.has-results)` (pool-detail carries no `has-results` class). Verified inert when content overflows the viewport — geometry at 1280×2400 is identical with and without it.
- **`padding-bottom: 0`** — with the footer in flow, 80px of reserved clearance renders as dead background *below* a footer that carries a top box-shadow. Cancelled on this view only; `.app`'s shared rule and every other surface are untouched (`style.css` has zero diff).

### Why this is not a silent revert of 217

The second declaration restates the line 217 deleted, so the distinction has to be explicit:

| | item 217 | item 218 |
|---|---|---|
| Footer on pool-detail | opaque **fixed overlay** | **in flow** |
| Role of `.app` clearance | the only thing keeping the document's last band visible — deleting its canceller was the fix | protects nothing (footer is after content, not over it); 80px of dead space |
| Defect fixed | end-of-document content permanently behind the footer | mid-document CTA behind the footer **at rest**, click intercepted |

The outcome 217 asserted still holds and is still gated: `test_footer_occlusion.js`'s four bottom-of-scroll geometry cases at 360/768/1280/360-dark are **byte-identical to `origin/main`** and still pass (verifier confirmed via `git diff` hunks, not by reading the notes).

### The one test change, and why it was necessary

`test_footer_occlusion.js`'s **positive control** injected `padding-bottom: 0 !important` and asserted occlusion reappeared. Once the footer is in flow, cancelling padding exposes the page to nothing — the control would go on passing while measuring **nothing at all**, which is worse than a control that can't go red, because it still looks like a check. It now injects the full pre-217/pre-218 state (`position: fixed` restored **and** clearance cancelled) — the only combination that still reproduces that test's defect class. No assertion, tolerance, or other case was touched.

### New gate: `test_cta_at_rest_occlusion.js` (12/12)

Rendered Playwright, real minified sheets, fixture-routed. It **never scrolls** — it asserts `window.scrollY === 0` immediately before every measurement, because computing a clear scroll target is precisely how this defect hid through 217's build. At 360×780, 768×900, 1280×900 and 360×780 dark: (a) the CTA rect does not intersect the footer rect, (b) `elementFromPoint()` at the CTA's centre *and* at 75% of its height resolves to the anchor (or a descendant), never the footer. Plus a positive control that re-fixes the footer in an isolated page and proves the check goes red. Registered in `test:serial` right after `test_footer_occlusion.js` (spec 205's registry invariant).
