# 099 — BUG (human ticket 2026-07-14, HIGH): subscription checkout hero card shows a different forever-number than the headline/forever line

Status: SHIPPED (2026-07-14, verifier PASS HIGH 2/2)
Risk: HIGH (planner bloom/checkout render path — user-facing money numbers on the conversion page; regenerated planner.min.js)
Score: 9.3 — human-reported production trust bug at the card-funnel checkout step (the `waitlist_submitted`
funnel top; SUBSCRIPTION archetype is "the product's front door" per the 2026-07-12 business-model
decision). NORTH_STAR: a bug at a funnel step outranks any experiment; inconsistent money numbers directly
damage the trust-rail moat.

## Report (human, verbatim intent, via screenshot)

Only ChatGPT Plus ($20/mo) selected, blended APY 10.58%. The headline + the bottom forever line correctly
say "≈$2,300 covers $20/mo" ($2,300 × 10.58% ≈ $20/mo ✓). But the right-hand hero (checkout) card shows
"$4,800" ONE-TIME / "generates $42/mo" — that's the forever-number for ~$42/mo, ~2× the picked $20/mo bill.
Three money numbers for the same single pick disagree on the conversion page.

## Root cause (operator triage, confirmed in code)

- The subscription pick handler (`planner.js` ~L3863) skips the amount step and SEEDS a default capital:
  `seedCapital = Math.ceil(foreverNumber(sg.target, guidanceApy) / 100) * 100`, where
  `guidanceApy = stableGuidanceApy || 5.5` (a conservative guidance rate, NOT the live blended rate).
  For $20/mo at ~5.5% that seeds ≈$4,400–4,800.
- At the bloom, the headline (`subHeroWinCovers`, planner.js:2032) and the forever/mix-total line
  (`mixTotal`, planner.js:2120) both derive from `currentMixStats.neededCapital` — recomputed at the
  LIVE blended `apy` (10.58%): `foreverNumber($20, 10.58%)` → ceil-$100 → ≈$2,300.
- The checkout hero card (planner.js:2628-2635) derives from `slideCapital` (`chkBaseCapital = isCapitalPath
  ? slideCapital : …`), which is still the STALE guidance-rate seed (≈$4,800). `chkYield` then recomputes
  the monthly from that stale capital → ≈$42/mo.
- The `slideCapital`⇄mix sync effect (planner.js:1529-1535) only realigned `slideCapital` to the live-apy
  `neededCapital` **after the user touched the mix** (a `!mixTouched` early-return). So the untouched default
  state left the hero card on the stale seed while the headline/forever line already showed the live figure.
- Same class as 085/`coveredBundle`-default: a seeded default computed at one rate leaking onto a surface
  the bloom recomputes at another rate.

## Change

Drop the `mixTouched` gate on the sync effect (planner.js:1529-1535) so `slideCapital` tracks the live-apy
`currentMixStats.neededCapital` from the initial seed on — not only after interaction. This gives the hero
card, headline and forever line ONE source of truth (`neededCapital`, computed at the live blended apy) and
also refreshes the capital on persona/APY change (previously stale until the mix was touched).

```js
useEffect(function () {
  if (archetype !== 'subscription' || !isCapitalPath) return;   // was: || !mixTouched
  var needed = currentMixStats.neededCapital;
  if (needed > 0 && needed !== slideCapital) setSlideCapital(needed);
}, [currentMixStats.neededCapital, archetype, isCapitalPath]);   // dropped mixTouched dep
```

Why this is safe / minimal:
- No user input is lost. The amount step is skipped for subscriptions (planner.js ~L3859 comment), so
  `capital` is ALWAYS a seeded default — there is no user-entered capital to preserve.
- The capital slider still wins. Dragging it changes `slideCapital` but NOT `neededCapital`, so the effect
  (keyed on `neededCapital`) never refires to fight the drag.
- No new/changed user-facing strings → no translations.js change required (EN/KO both already correct).
- `chkBaseCapital` is left reading `slideCapital`: with `slideCapital` now synced, the hero converges on
  `neededCapital` automatically, and the slider remains functional.

## Trust rails

## Territory notes
- `guidanceApy` (planner.js:3592) is the conservative pre-bloom rate; the bloom uses the live blended `apy`.
  The seed/bloom rate split is the mechanism — any surface reading the raw seed rather than `neededCapital`
  will diverge. This fix routes the last such surface (the hero) through `neededCapital` via the synced
  `slideCapital`.
- The strip (planner.js:2758) and make-it-yours summary (2828) also read `slideCapital`; syncing at the
  state level (rather than only patching `chkBaseCapital`) keeps THEM consistent too — a `chkBaseCapital`-only
  patch would have left the strip on the stale seed.
