# 214 — explainer (HIGH tier)

**What shipped:** a `?pool=<id>` arrival now paints its pool detail from the committed
`data/pools-snapshot.json` when that pool is in the snapshot, instead of blocking its first paint on
the multi-MB live `yields.llama.fi/pools` fetch. Plus the instrumentation fix that verification
forced out of hiding: `data_load_time` never actually carried its `source` property to Mixpanel.

## Goal

The north-star surface is pool-detail. The single `?pool=` arrival on record (07-29,
`/?token=USDC&chain=Popular&pool=4438dabc-…`, a ≥$10M pool linked from `tokens/usdc.html`) produced
`page_view` = 1 and `pool_view` = 0 — it left before the page ever rendered a pool detail. n=1, so
this is not a conversion claim; the *mechanism* behind it is the finding, and the mechanism is
measured fact.

## The intuition

Item 059 built a snapshot-first fast path: a small, railed, same-origin JSON of ≥$10M pools that
paints instantly instead of waiting on DefiLlama. It deliberately excluded `?pool=` deep links —
`app.js:1144`, `!urlParams.pool && …` — on the reasoning that a deep-linked pool might not be in the
railed snapshot, and sending it there would break the 072 dead-pool empty state.

That reasoning was right about the risk and wrong about the remedy. It excluded *all* pool arrivals
to protect the *some* that aren't in the snapshot. Meanwhile item 105 later added an effect that
fetches `/data/pools-snapshot.json` on that very same arrival anyway — post-render, to merge KPIs.
So the instant-paint payload was already being downloaded on every pool arrival. It just arrived too
late to paint from.

The fix is to ask the question the original gate never asked: *is this pool actually in the
snapshot?* If yes, paint from it. If no — or stale, or 404, or malformed — fall through to exactly
today's live path, which is what still lands a genuinely dead id on the honest 072 empty state.

## What changed, in reading order

**`app.js` (+44/−9)** — the whole product change.

1. `tryLoadSnapshot(startTime)` → `tryLoadSnapshot(startTime, requiredPoolId)`. After all existing
   envelope validation and *before* `poolsSourceRef.current = 'snapshot'` / `setPools(...)`, a
   truthy `requiredPoolId` must resolve inside `snap.pools` or the function returns `false`. The
   match is the same two-way match the pool-detail resolver already uses (`pool.pool === id`, or the
   legacy `` `${project}-${symbol}-${chain}` `` composite key) — deliberately reusing the resolver's
   semantics so the snapshot can never claim a pool the resolver would then fail to find.
2. Eligibility: `!urlParams.pool && urlParams.minTvl >= DEFAULT_MIN_TVL` becomes
   `urlParams.pool ? true : urlParams.minTvl >= DEFAULT_MIN_TVL`. For non-pool arrivals this is the
   same expression evaluated in the same order — byte-identical behavior. Pool arrivals become
   eligible to *try*; `tryLoadSnapshot` itself declines when the id isn't there.
3. The block comment above the effect was rewritten. It said "no `?pool=` deep link — those ALWAYS
   go live." That sentence is now false, and a false comment on a sacred path is a trap for the next
   reader.

**`analytics.js` (+11/−2)** — forced by verification, see below.

**`test_snapshot_first.js` (+173/−10)** — the acceptance bar. Rendered Playwright driving the real
compiled/minified artifacts, not fixtures-in-isolation. 9 scenarios → 13:
- (g) retitled: its id was always absent from the snapshot fixture, so its assertion (live IS hit)
  stayed true — but its *name* claimed "sacred deep link — always live," which is no longer the
  mechanism.
- (h) snapshot-present id + the live route left **permanently hanging** → detail paints from the
  snapshot, `liveHits() === 0`, live never completes.
- (i) id absent from snapshot *and* live → honest 072 dead-pool empty state, live was hit.
- (j) 7h-stale snapshot + snapshot-present id → falls through to live.
- (k) `data_load_time` reports `source: 'snapshot'` / `'live'` on the delivered payload.

**`app.compiled.js` / `app.compiled.min.js`** — regenerated via `npm run compile && npm run minify`,
house convention (cf. `83e28459e`, `f466a8dcd`). Item 061's lesson: copy that never reaches the
`.min` artifact ships nowhere.

## The instrumentation defect verification dragged out

Attempt 1 was verified **FAIL at 6/7**. The unmet criterion was AC7 — "`data_load_time`
distinguishes `source: 'snapshot'` vs `'live'`" — which the spec wrote on the parenthetical premise
"*(it already carries `source`)*".

It did not. `analytics.js`'s `trackPerformance(metric, value, context)` forwarded `metric_name`,
`metric_value`, `metric_category`, `page_context`, `connection_type`, `is_slow_device` — and dropped
`context.source` and `context.pools_count` on the floor. Both `app.js` call sites have passed
`source` since 059. **Every `data_load_time` event ever emitted was missing it.**

That is worth stating plainly: a property was being passed diligently at the call site, asserted in a
spec, and silently discarded one function later. Nobody noticed because the call site read correctly
and nobody queried the delivered event.

Attempt 2 forwards the two keys additively — explicit keys, never a wholesale `...context` spread
(which risks colliding with reserved `$`-prefixed Mixpanel props), and only when `!== undefined` so
no other caller starts emitting `source: undefined`. `trackPerformance(` has exactly three hits
repo-wide (the definition + the two `app.js` call sites), so the blast radius is closed by
inspection. Scenario (k) was re-pointed from the `trackPerformance` call boundary to a spy on
`Analytics.track` — the delivered payload — because proving the call site passes a value proves
nothing about what Mixpanel receives.

## Deviations from spec

- **The spec was edited.** AC7's false parenthetical was struck and replaced with a factual
  correction; a Territory-notes entry records the discovery. AC7's substantive requirement is
  character-for-character unchanged — the criterion was made *true*, not made *easier*. The verifier
  checked this specifically, since a spec quietly rewritten to match what was built is a FAIL.
- **Scope call:** extending `analytics.js` is normally a drive-by. Here it was the only way a listed
  acceptance criterion could hold, with a three-call-site blast radius. Both the builder and the
  verifier justified it on the merits rather than assuming.
- **Left deliberately unfixed** (flagged, not touched): the spec-105 comment at ~`app.js:1269` still
  says "snapshotEligible is false when urlParams.pool is set," now inaccurate. Its *code* is
  correct — a snapshot-resolved pool already carries `kpis`, so the `!detailPool.kpis` guard
  short-circuits the merge and there is no double-fetch. Also a pre-existing `/ onto` single-slash
  typo in that same block. Both are comment-only and outside this diff's remit.
- **Not provable in-sandbox:** real Mixpanel ingestion (host-gated to no-send on localhost, item
  096). (k) proves the payload assembled at `Analytics.track` carries `source`.
