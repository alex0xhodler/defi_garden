# 221 — the analytics grid stops hiding its own content behind its own footer

*HIGH-tier explainer. Written before the merge, per `prompts/build.md` step 5.*

## The goal in one sentence

On `?token=USDC` and `?chain=Ethereum` — the sacred SEO surfaces — the page's own
footer was painting over pool cards and swallowing clicks on a button, before the
user had touched anything. This makes it stop, on the last of the three routes
where that was still true.

## The intuition

There is one footer element in this app, shared by every route. It is
`position: fixed; bottom: 0; z-index: 100` with an **opaque** background
(`style.css:2616-2627`). "Fixed" means it does not scroll with the page — it is
pinned to the bottom of the *window*, floating above everything. "Opaque" means
whatever is underneath it is invisible. And because it is a real element sitting
on top, it also **eats clicks**: a button underneath it is not just hidden, it is
unpressable.

The app's defence against this has always been a strip of reserved space:
`.app { padding-bottom: 80px }` (`style.css:849-853`, commented "Space for
footer"). That pushes the *end* of the document up by 80px so the last line of
content is never underneath the floating bar.

Here is the thing that took four separate items to learn: **that defence only
protects the end of the document.** If a pool card happens to land in the
footer's band *in the middle* of the page — because you have exactly enough cards
to fill the viewport that far — no amount of `padding-bottom` helps. Padding
makes the document *longer*. It cannot move something that is already sitting
where the bar floats.

That is what was happening. At 1280×780, the "Calculate yield" button on one card
was 98.8% covered, and a hit test at its centre returned the footer, not the
button. At 360×780 a pool's symbol row was 100% covered.

## Why this one was invisible for so long

This is the **fourth** recurrence of this defect class: item 179 (bare `/`), 217
(pool-detail), 218 (pool-detail's north-star CTA), 220 (bare `/` again). Each
time, the diagnosis method was "find the rule that cancelled the 80px clearance."

That method could never find this one. The grid route inherits the clearance
**perfectly** — its root is `.app.has-results`, which matches `.app`, which gets
the 80px. Nothing cancels it. By the existing playbook's checklist, the route read
as clean. In fact, the playbook had declared the whole class "closed" earlier the
same day, on exactly that reasoning.

The lesson, now written into `playbooks/fixed-overlay-occlusion.md` as **step 3c**:
*inheriting the clearance is not the same as being protected by it.* There is no
CSS tell for this variant — the stylesheet looks correct. It shows up only in a
real at-rest render. What found it was item 219's machine occlusion lens, which
measures geometry **and** hit-tests with `elementFromPoint` on every audited
surface, every day.

## What changed, in reading order

**1. `style.css` — the fix itself (2 declarations)**

```css
.app.has-results .app-footer { position: static; }
.app.has-results            { padding-bottom: 0; }
```

`position: static` takes the footer out of the floating layer *on grid views
only* and puts it back in normal document flow. Once it flows with the page,
nothing can be underneath it at any scroll position, on any viewport, for any
pool count — the failure mode is removed rather than dodged. This is the same
resolution items 218 and 220 shipped on their routes.

The second line is the necessary companion: with the footer in flow, the 80px
reserved for it protects nothing and would render as dead background beneath a
footer that carries its own top shadow. It uses the `padding-bottom` longhand
rather than the `padding` shorthand — because the shorthand would reset all four
sides, changing three properties to accomplish one. `padding-left`/`padding-right`
happen to be 0 on this selector today, so the shorthand would be harmless *today*
and silently wrong the moment anyone gives `.app` horizontal padding. That is
surgical-diff discipline, not a cascade rescue.

*(An earlier draft of this explainer — and of the code comment — justified the
longhand by claiming the shorthand would "wipe the `padding-top` overrides that
come later in the cascade." That was **false**, and the verifier falsified it in a
real render: CSS resolves each longhand property by source order among
equal-specificity declarations regardless of whether an earlier rule used a
shorthand, and `.app.has-results { padding-top: 160px }` at `style.css:1173` sits
after the fix at `:969`, so it wins either way. Recorded rather than quietly
deleted, because a confidently-worded mechanism is a testable claim and this one
did not survive testing.)*

**2. The declaration that is deliberately NOT there**

218 and 220 both shipped a third line, `margin-top: auto`, so a short page keeps
its footer at the bottom of the window instead of floating mid-page above empty
background. That line is **absent here, on purpose.**

`margin-top: auto` is a *flex* idiom. It works on 218/220's routes because those
views were already flex columns. `.app.has-results` is `display: block`
(`style.css:865`) — the line would be **inert**: it would read as protection and
fire never.

The builder tried the obvious alternative (make the view a flex column so the
idiom becomes load-bearing) and **measured** the result rather than assuming it:
at 360×780, `.container` moved down 6px, reproducibly. The cause is that
`.theme-toggle`/`.language-toggle` are in-flow siblings on that exact
mobile/has-results combination — item 222's own defect — and flex items never
margin-collapse, while block children do. Six pixels of unrelated layout movement
on a sacred surface is not worth a cosmetic nicety, so the flex switch was
dropped and the idiom omitted. The consequence was measured too: on a short grid
the footer now sits after the content rather than pinned to the bottom edge —
ordinary end-of-document behaviour, and specifically *not* the occlusion bug this
item exists to close.

**3. `style.min.css` — regenerated**

`home.html:134` serves `style.min.css`, not `style.css`. A raw-only fix ships
dead (item 136's trap). Regenerated via `npm run minify` and proven fresh.

**4. `test_grid_footer_occlusion.js` — a new 422-line rendered gate**

Drives real Chromium at 360 and 1280, height **780** (at the audit's default 900
the defect does not exist — a gate at 900 would pass while measuring nothing),
across `?token=` and `?chain=`, light and dark. It asserts `window.scrollY === 0`
immediately before every at-rest measurement, because computing a convenient
scroll target is precisely how item 218 stayed invisible through item 217's
build. And it **hit-tests** with `elementFromPoint` rather than only comparing
rectangles, because click interception is strictly worse than hiding and is
invisible to geometry alone.

**5. `test_audit_app.js` — the quarantine shrinks**

Item 219 quarantined three grid surfaces so its new lens's true positives would
not block the daily tick. Two of them (`grid-token`, `grid-chain`) are now clean
and were removed — after the file's own `QUARANTINE NO LONGER NEEDED` line
printed for exactly those two on an isolated run. `grid-360` stays, because it
still has a *different* defect: a duplicate theme-toggle buried under the sticky
header — a different overlay, a different mechanism, and item 222's ticket, which
this spec explicitly scopes out.

**6. `package.json`** — the new gate joins `test:serial`.

**7. `playbooks/fixed-overlay-occlusion.md`** — the compound step. Adds step 3c
(inherited-but-insufficient), its resolution including the `margin-top: auto`
precondition, and strikes the playbook's own premature "class closed" verdict.

## Deviations from the spec

1. **Acceptance criterion 3 says all three grid surfaces leave the quarantine;
   only two did.** The spec contradicts itself — its own Evidence section scopes
   grid-360's remaining P0 out as item 222. Removing grid-360 would have turned
   the daily tick red on a known, ticketed, out-of-scope defect. Two entries
   removed, one kept, documented in the file.
2. **`margin-top: auto` omitted** (the spec's preferred "Option A" shape), for
   the measured reason above. The spec pre-authorised this fallback.
3. **A false claim in a code comment**, caught in operator review before
   verification: an early draft asserted that `.app:not(.has-results)` never
   renders this footer. It does — `app.js:3533` has no guard. The claim was
   replaced with a *measured* scope boundary (the analytics search-home state at
   `?app=analytics` is reachable, renders the fixed footer, and has zero
   intersecting content at 360 and 1280 — so it is out of scope because it is
   clean, not because it does not exist).

## What is NOT claimed

The full ~140-file `test:serial` was not run (5-minute timebox); the ~12
plausibly-affected files were run individually instead. No widths outside the
360/768/1280 design bar. No KO-localized grid render. The short-content case was
measured on one synthetic 1-pool fixture at one viewport. And there is **no
conversion claim** — at n≈0 traffic this ships under the 2026-07-23 pre-traffic
mandate, where product quality is the loop's job and "a bug at a funnel step
outranks any experiment at that step."

1. The grid route inherits `.app { padding-bottom: 80px }` correctly, and nothing
   cancels it. So why was content still being covered?

2. Why does `position: static` fix this when no `padding-bottom` value could?

3. Items 218 and 220 shipped `margin-top: auto` alongside `position: static`.
   Why would shipping that same line here have been worse than omitting it?

4. The new gate renders at height 780. What would go wrong if it rendered at 900,
   the height the rest of the audit uses — and why is that the more dangerous kind
   of failure?
