## Goal

Three sibling screens (landing `/`, the analytics grid `/?token=`/`/?chain=`, pool-detail `/?pool=`)
rendered three structurally different header chromes and three different content widths, visible within
two clicks of the same product. You named this directly on 2026-08-06 reviewing the #393 preview:
*"re using the same logo bars, same width of content, etc, which are all over the place currently... c'mon
it's only 3 screens!"* This ships the "quick win" you asked for: one header band, one width, everywhere.

## Intuition

Before this change:
- **Landing** had a proper header band (wordmark left, nav links, lang/theme right) — the reference shape.
- **Grid, no-results state** (e.g. right after clicking "Search yields" before typing anything) had NO
  band at all: a giant centered `<h1>DeFi Garden</h1>`, and the language/theme toggle buttons floating as
  unanchored `position: fixed` elements with no visual home.
- **Grid, results state** (after picking a token/chain) had a proper-looking band, but its content column
  was hardcoded to 1200px rather than reading from any shared value.
- **Pool-detail** had its own band, but its content column was set via an inline React style
  (`maxWidth: '1200px'`), not a class or token at all.

The fix: one band, always rendered, wordmark+controls in the same slots everywhere; one CSS custom
property (`--content-max-width`, reusing the existing 1280px `--container-xl` value — no new number
invented) that every surface's content container resolves to.

## What changed and why (diff in reading order)

1. **`style.css`** — `--content-max-width: var(--container-xl)` defined once in `:root` (the single source
   every surface reads). `.app-header-sticky` now renders unconditionally instead of only when a token/
   chain is selected; a new rule keeps it a normal top-of-flow flex item (not `position: fixed`) in the
   no-results state so it doesn't overlap the centered search content below it, and — after round 1's
   fix — the surrounding column's centering was scoped down to the search content only, not the header
   itself, so the band stays pinned at the same y-position in every state.
2. **`app.js`** — the header band's gating condition (`selectedToken || (chainMode && selectedChain)`) was
   removed from the band itself; only the persistent search bar and the category-tabs row beneath it stay
   results-only. The standalone floating theme/language toggle pair and the giant centered `<h1>` wordmark
   were deleted — the band now carries the only theme/language controls on this view, in every state.
3. **`landing-styles.css`** — the existing `.landing-header` (the reference shape, not redesigned) now
   resolves its width from `--content-max-width` instead of its own hardcoded 1200px; two pre-existing
   mobile-breakpoint overrides that had their own hardcoded formula (missed in the first pass, caught by
   round 1's verifier at 360px) were brought into line with the same formula.
4. **`PoolDetail.js` / `pool-detail-styles.css`** — the inline `maxWidth: '1200px'` style became a
   `width: min(var(--content-max-width), calc(100% - 48px))` formula, matching the other two surfaces
   exactly (not just capped the same, inset the same way too). The header row itself needed a
   `margin: -40px -20px 8px; width: auto` correction (round 2's fix) to cancel a double-counted inset that
   the round-1 fix hadn't touched, plus a background fill matching the other two bands' surface color.

## Deviations from spec / verifier findings (the real story, not a clean first pass)

This shipped in 3 verifier rounds against a 3-attempt budget — worth reading, not glossing over:

- **Round 1 FAIL**: landing's mobile breakpoints weren't migrated (16px width mismatch at 360px); the
  no-results header floated vertically centered instead of pinned to the top.
- **Round 2 FAIL**: a NEW defect the first two rounds both missed — pool-detail's band was 40px narrower,
  20px more inset, and 5px too high compared to landing/grid, at every viewport, present since the very
  first commit. Found because round 2's verifier ran a three-way check (landing vs grid vs pool-detail)
  instead of the pairwise landing-vs-grid check the original build and round 1 had both stopped at.
- **Round 3 PASS**: fixed a stacked double-inset (the container's width formula AND its own padding both
  narrowing the box) plus a shared centering rule that had accidentally started matching pool-detail's
  route too. Independently re-measured at the three required breakpoints AND five additional untested
  ones (320/480/640/900/1920px) — exact match at all of them, evidence this is a real algebraic fix, not
  a patch for the specific pixel values that happened to get checked.

Full blow-by-blow: `product-loop-kit/specs/236-notes.md`.

## How to test it

Serve locally (`python3 -m http.server 8000`) and open, at 360/768/1280px, light and dark:
- `/` — landing, unchanged nav links, band now width-matched to the other two.
- `/?token=USDC` — grid results state.
- `/?app=1` — grid no-results/search state (previously had no band at all).
- `/?pool=<any live pool id>` — pool-detail.

All four should show the same wordmark-left / lang+theme-right band, at the same height and the same
horizontal inset from the viewport edge. Confirm no horizontal scroll at 360px and that `?token=`/`?chain=`
still render pool cards exactly as before (sacred SEO surface, routing/data logic untouched by this diff —
only chrome).
