## Part 1 deviations (planner.js share-URL round trip)

**`poolFilters` is local `Bloom` state, not a prop.** The spec's territory notes flagged uncertainty about whether `props.poolFilters` already reaches `doShareImage`/`doCopyLink`/`doNativeShare` and said to "thread it through if not present." On inspection, `poolFiltersState = useState(...)` (planner.js:1239) is `Bloom`'s own local state — the three share functions are *also* defined inside `Bloom`, so the local `poolFilters` variable is already in scope at each call site. I passed the local `poolFilters` variable directly as the 8th `encodePlanToUrl` argument rather than inventing a `props.poolFilters` that doesn't exist anywhere in the codebase. This is simpler than prop-threading and correct — verified via the Playwright test that a share-link-shaped URL with `chain`/`token` actually round-trips.

**Seeding `poolFiltersState` from a shared plan required a NEW prop, not a "read `sharedPlan` directly" pattern.** The spec suggested mirroring `ansState`'s initializer, which reads `sharedPlan` directly — but `ansState` lives in the parent `Planner` component, while `poolFiltersState` lives in the child `Bloom` component; `Bloom` has no access to `Planner`'s `sharedPlan` variable. Fix: added two new props, `initialChain`/`initialToken`, passed from `Planner`'s `Bloom` call site (`sharedPlan ? sharedPlan.chain||token : null`), and `poolFiltersState`'s initializer now reads `props.initialChain`/`props.initialToken`. This is the closest possible mirror of the `ansState` pattern given the two-component boundary.

**Persona classification in the generator needed `minTvl` bands, not just the APY ceilings the spec described.** Spec: "stable-symbol + within the stable band's APY ceiling → stable; else within the rwa band's 20% ceiling → rwa; else degen." But `curatePools` (planner.js:544) gates each persona band on BOTH `maxApy` AND `minTvl`, and `PERSONAS.stable.minTvl` is $50M — five times this generator's own $10M qualifying floor. A literal implementation of the spec's classifier would tag a $12M-TVL stablecoin pool `'stable'`, but the real, live `curatePools` would then reject that exact pool when the persona filter is `stable` (its TVL is short of the $50M stable-band floor) — the share link would render an EMPTY grid, not "a curated pool matching the pack's chain/token." This is exactly the class of bug the spec's own Playwright acceptance criterion exists to catch, and it did: my first fixture (persona `stable`, $15M-TVL pool) failed to render anything until I extended `PERSONA_BANDS` to mirror `minTvl` as well as `maxApy`. Documented in `generate-spotlight.js`'s own comment block. Not a trust-rail change — `PERSONA_BANDS` values are copied verbatim from `planner.js:500-515`, nothing loosened.

**`translations.js`'s exported `createTranslationFunction` does NOT resolve planner strings.** It only resolves the flat top-level key set generator-token-pages.js/generate-og-images.js already use for SEO copy (`translations[lang][key]`). Planner-specific strings like `goalClaude` ("Claude Pro") live nested under `translations[lang].planner`, resolved by planner.js's own local `makeT()` (planner.js:763-773), which is never exported. Caught this via manual smoke-testing — the pack's `goalLabel` field literally read `"goalClaude"` instead of `"Claude Pro"` on the first run. Fixed by importing the raw `translations` object and mirroring `makeT`'s dict-then-en-fallback-then-key lookup locally (`goalLabelText()` in `generate-spotlight.js`).

**`isQualifyingPool` kept to the spec's literal 2-condition definition** (`!isAnomalousApy(pool) && pool.tvlUsd >= DEFAULT_MIN_TVL`) — did not add curatePools's separate `apy > 0` filter. A 0%-APY pool passed via `--pool` would clear this generator's rails but then be silently dropped by the live `curatePools` (which excludes `apy <= 0`). Judged low-risk (auto-pick always sorts by highest APY first, so this only bites a human explicitly forcing a 0%-yield `--pool`) and left as spec-literal rather than adding an undocumented rail; flagging here in case a future spotlight run hits it.

**Curve's DefiLlama project key**: confirmed via a live `yields.llama.fi/pools` sample (2026-07-12, curl — Node/curl egress to this host works in this sandbox per NORTH_STAR.md's 2026-07-12 note) that Curve's DEX project key is `curve-dex` (15,463 live pools scanned). A separate `curve-llamalend` project also exists in live data and is intentionally NOT folded into the `curve-dex` aggregate — Llama Lend is a materially different product (lending market vs AMM) and spec text says "Curve = upper bound" in the DEX-spotlight sense NORTH_STAR.md's distribution-channel decision describes. `CURVE_PROJECT_KEY` is a single named constant, easy to revisit. Live sanity check: `curve-dex`'s trust-rail-qualifying aggregate TVL was ~$1.035B on this pull — the "ceiling" is intentionally generous per the human's "Curve = upper bound, aim lower in general" framing; 169 other protocols were "small enough" by this definition on the same pull.

## Test-file split
Followed the same unit-vs-live-DOM split already established in this repo (`test_token_pages.js`/`test_og_images.js` = pure fixture+require assertions vs `test_search.js`/`test_analytics_fires.js` = real-Chromium live-DOM checks), rather than folding everything into one file:
- `test_spotlight.js`: `require()`s `generate-spotlight.js`'s exports directly for pure-function assertions (trust rails, small-protocol classifier, `pickPool`, `buildPack` shape), PLUS a handful of real `execFileSync` subprocess CLI runs — chosen because the spec's own acceptance criteria are phrased as CLI behavior ("`node generate-spotlight.js --fixture <path>` produces... / produces neither for..."), and a pure require()-only test already caught one real wiring bug in this pass (the `createTranslationFunction` issue above) that only the CLI-level assertions would have caught end-to-end.
- `test_spotlight_url.js`: separate file, mirrors `test_search.js`'s exact structure (local static server, real Chromium, fixture-routed pools API). Kept separate rather than appended to `test_spotlight.js` because it drives a fundamentally different concern (rendered plan.html UI vs generator internals) and a different runtime shape (Playwright browser vs plain Node assertions) — matches this repo's existing precedent of one Playwright-driven file per rendered-UI concern.

### Playwright test findings (test_spotlight_url.js)
- **Port collision**: initially reused port 8793, which collides with the pre-existing `test_analytics_fires.js`'s own hardcoded `PORT = 8793`. Existing ports in use: `test_smoke.js`=8791, `test_search.js`=8792, `test_analytics_fires.js`=8793. Changed to **8794**.
- **`test_search.js`'s reachability flags are hardcoded `false`, not actually probed** — the file defines a `probe()` function but never calls it; `unpkgReachable`/`llamaReachable` are literal `false` constants. Initially I wired a real `probe()` call in my file, which reported both hosts reachable (curl succeeds — matches NORTH_STAR.md's "Node/curl reach them fine" note) — but leaving Chromium to hit them directly then hung every assertion on a `waitForSelector` timeout, because the *browser's* connection to those hosts is blocked even when curl's isn't (confirmed empirically, matches the exact NORTH_STAR.md 2026-07-12 standing decision). Reverted to hardcoded `false` + always-installed fixture routes, matching `test_search.js` exactly.
- **Subscription-archetype goals render a DIFFERENT pool-grid DOM tree than growth/target goals.** `Bloom()` (planner.js:2647) branches its entire return value on `archetype === 'subscription'`: the subscription branch renders `heroElement, planCardElement, subCustomizeElement, askElement, caveatElement` and does NOT include `engineElement`/`.gp-pools-toggle` at all. The pool grid + chain/token filter chips for subscription goals (e.g. `claude` — this generator's own default goal) live inside `subCustomizeElement` instead, behind a **different** toggle (`.gp-sub-customize-trigger` / `planCustomizeOpen`, planner.js:2204), though the revealed inner markup (`.gp-pool-grid`, `.gp-pool-card`, `.gp-pool-chain`, `.gp-pool-symbol`, `.gp-engine-filter-row`, `.gp-chip.is-selected`) is identical between both branches. This was NOT called out in the spec's territory notes (which only names `engineElement`/`curatePools`) and would have made the Playwright test hang indefinitely without inspecting live rendered DOM directly (which is exactly what turned it up). `test_spotlight_url.js`'s `openShareUrl()` helper now opens whichever trigger is present.
- **`localStorage` bleed across navigations in the same Playwright page.** The planner persists a saved plan to `localStorage` once a bloom settles; a second `page.goto()` to a different share URL on the same origin/page then boots straight into "report" mode (`savedPlan` truthy) instead of re-decoding the new URL. Fixed with `page.addInitScript(() => localStorage.clear())` registered once, which reruns before every subsequent navigation.
- **`google.com/s2/favicons` console errors are cosmetic**, matching the exact class 061-notes.md already documented for the same host (subscription-ladder brand icons) — added to `IGNORABLE_ERROR_PATTERN` alongside the existing `mp.defi.garden`/`mixpanel`/`fontshare.com` entries test_search.js already ignores.

## Stale bundle (`plan.html` loads `planner.min.js`, not `planner.js`)
Same class of bug 061-notes.md's Finding 1 already documented for `translations.min.js`: `plan.html` loads the minified bundle, and editing only `planner.js` leaves the live UI running pre-060 code. Ran `npm run minify` after finishing the `planner.js` edits; `node test_minified_assets.js` (part of the existing chain) confirms `planner.min.js` now byte-matches a fresh minify of `planner.js`. This is also WHY the first Playwright pass of `test_spotlight_url.js` failed — the filtered curation test showed all 3 fixture pools regardless of `chain`/`token`, because the browser was still running the old `planner.min.js` with the 7-arg `encodePlanToUrl`/pre-060 `decodePlanFromUrl`. Fixed by the minify run, confirmed by rerunning the test.
