# Spec 051: Per-page dynamic OG images (token/chain social + SERP imagery)

## Evidence
Direct grep, 2026-07-12: every token/chain page ships `og:image` = `https://www.defi.garden/og-image.png` — one shared static image for all 2,108 pages. No per-page social/SERP imagery.
- 2026 SOTA: unique, content-relevant OG images improve social CTR and provide a differentiation/quality signal; `summary_large_image` cards (already declared) reward a real per-page image. A generated card showing the token/chain name + top honest APY + pool count turns every share/SERP thumbnail into an on-brand, data-true artifact.
- The repo already has a share-card canvas renderer (planner.js `renderShareImage`, hardened in 027 with bundled brand logos) — the image-generation capability exists; it just isn't applied to the SEO pages.

## Hypothesis
We believe generating a unique OG image per token/chain page (token/chain name + best honest APY + pool count, neuro-styled) will lift social/SERP CTR versus the single shared image, because a data-specific card is more clickable and on-brand than a generic logo, and the summary_large_image card format the pages already declare rewards it. Confidence: **supported by external CTR data; unvalidated here.**

## Change
Generate a static OG image per page at build time (no runtime image service — keeps the no-backend architecture):
1. Add an OG-image generation step to the token/chain generators (or a sibling script run in the same CI job): render a 1200×630 PNG per page — token/chain name, best non-anomalous APY, pool count, DeFi Garden branding — using the neuro design tokens. Reuse the 027 canvas/asset approach where possible (headless canvas in Node via `canvas`/`@napi-rs/canvas`, OR a pre-rendered template with text overlay — pick the lightest that runs in CI without a browser).
2. Write images to a committed path (e.g. `og/tokens/<slug>.png`) and point each page's `og:image` + `twitter:image` at its own file. Also set `twitter:title`/`twitter:description` (currently omitted on token pages — a smaller gap noted in the 039 audit).
3. Trust rail: the APY on the card must be the same gated (non-anomalous, ≥floor) best APY the page shows — never an anomalous rate on a share card (that's the exact class of bug 027 fixed).
4. Fallback: if image generation fails for a page, fall back to the shared `og-image.png` (never ship a broken `og:image`).

OUT of scope: animated/interactive cards; per-pool images; a runtime OG service (would add a backend — violates the static architecture); regenerating the planner's share-card path (that's the north-star artifact, separate).

## Acceptance criteria
- [ ] Each generated token/chain page references its own `og:image`/`twitter:image` (per-slug PNG), with `twitter:title`/`twitter:description` also set; verified on fixtures.
- [ ] The APY shown on the card is the same gated best-APY the page displays — no anomalous or sub-floor rate on any card. Verified with an anomaly fixture (a $900M @ 2100% pool leaves no trace).
- [ ] Image generation runs in CI without a browser (or documents its dependency) and stays within the 5-min foreground timebox for the verification run; a per-page failure falls back to the shared image (no broken og:image).
- [ ] No trust-rail/ranking/canonical change; tests for the per-page og:image reference + anomaly exclusion in the card data, in the `npm test` chain.

## Measurement
Metric: social/SERP CTR (proxy: referral traffic from social + GSC image-search once 026 unblocks). Window: 2–6wk+. Decision rule: keep (best-practice differentiation) unless it materially bloats the repo/CI.

## Risk tier (builder's guess — verifier assigns independently)
MED — generated SEO surface + a new image-generation dependency at 2,108-page scale (repo size / CI time considerations). No trust-rail change if the anomaly-gate on card data holds. Verifier: confirm the anomaly exclusion on card APY and that CI generation is bounded.

## Open questions
- Rendering approach (headless canvas vs template-overlay) and whether committing 2,108 PNGs is acceptable repo bloat vs generating them into a build artifact — builder evaluates; if repo bloat is a concern, note it and propose generating to a Vercel build step instead. Not architecture-changing for the acceptance criteria.
