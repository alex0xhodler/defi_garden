## Why it matters (the two live consumers)

`kpis.apySharpe` is not decorative — 117.2 and 117.3 shipped it into ranking:

- **`app.js:1828/1918/2018`** — the "Risk-adjusted" analytics sort orders rail-passing pools by `apySharpe`
  DESC, null last. Today this pool carries a *numeric* 0.3, so it sorts **above every honest pool whose
  Sharpe is null** ("not enough history"), on the strength of a number computed from a 260,768% data glitch.
- **`planner.js:84-87`** — `curatePools`'s near-tie-break prefers the higher `apySharpe` among candidates
  within `eps` of each other on APY. A garbage 0.3 can win that tie-break against a genuinely steadier pool.

Both are trust-moat surfaces: the product is telling a cautious saver "this one is steadier" using a number
it should never have computed. Pool-detail's rendered notes read off the same object (`PoolDetail.js:1409`
`apyStdev`, `:1457` `apyMomentum`, `:1503` `tvlTrend`).

## The fix

In `computeKpis()` (`compute-kpis.js`), treat an out-of-rail rate point as **not credible data**, and omit
the KPIs derived from it — honest omission, never a clamped or "cleaned" value (the 122/144 house precedent).

Add one local trust-rail mirror alongside the existing `SHARPE_*` constants:

```js
const APY_SANITY_LIMIT = 1000;  // TRUST RAIL mirror (app.js:800 / planner.js / generate-token-pages.js:61):
                                // a rate above this is not credible, so nothing may be DERIVED from it either.
```

Per-KPI rule (precise about which points each KPI actually reads — no over-nulling):

| KPI | Reads | New rule |
|-----|-------|----------|
| `apyMean`, `apyStdev`, `apySharpe` | the **whole** apy series | `null` if **any** point `> APY_SANITY_LIMIT` |
| `apyMomentum` | **first and last** point only | `null` if **either endpoint** is `> APY_SANITY_LIMIT` |
| `tvlTrend` | TVL only | **unchanged** (rate-independent) |
| `historyPoints`, `firstSeen` | tracking facts | **unchanged** (we did track those days) |

`apyMean` currently has no null path (it is `round(mean, 2)` unconditionally) — it gains one. All the other
fields already have documented `null` paths and every consumer is null-safe today (`app.js` sorts null last;
`planner.js:87` returns null → neutral tie-break; the three `PoolDetail.js` notes are `typeof … === 'number'`
gated and hide honestly).

**Considered and rejected:** *excluding* the out-of-rail points and computing from the survivors (here: 11
clean points → Sharpe ≈ −12.7). It produces a more informative number, but it presents a score as if we had a
clean history, and it forces a semantic change on `historyPoints` (which three render gates and the
"tracking for N days" copy read). Nulling invents nothing and ripples nowhere. Recorded here for the human;
revisit only on an explicit call.

Then **regenerate the committed data** so the fix is live now rather than on the next CI bake:
`node compute-kpis.js` (deterministic on the committed `data/history/` + snapshot; no network needed).

## Acceptance criteria

1. `computeKpis()` returns `apyMean: null`, `apyStdev: null`, `apySharpe: null` for a series containing any
   point `> APY_SANITY_LIMIT`, and keeps `historyPoints` / `firstSeen` / `tvlTrend` intact.
2. `apyMomentum` is `null` when the first **or** last point is out-of-rail, and **retained** when both
   endpoints are sane even if a middle point is out-of-rail (the real pool's case: −0.56 survives).
3. A series with **all** points at or below the rail produces **byte-identical** KPIs to today (no churn on
   the other 739 pools) — proven by regenerating and diffing.
4. The regenerated `data/pools-snapshot.json` contains **zero** pools where `apySharpe`/`apyStdev`/`apyMean`
   is a number while any of that pool's committed history points exceeds the rail; specifically pool
   `201e5f6e-…` carries `apySharpe: null`, `apyStdev: null`, `apyMean: null`, `apyMomentum: -0.56`.
5. **Rendered acceptance** (Playwright, real Chromium, real committed snapshot — never fixtures alone):
   a. the analytics grid's **Risk-adjusted** sort places the affected pool in the null-Sharpe group (last),
      not ahead of null-Sharpe pools;
   b. pool-detail for that pool renders the neutral "we've been tracking this pool's rate for N days" note —
      no steadiness claim, no `NaN`/`undefined`/`null` text, zero page errors.
6. `APY_SANITY_LIMIT`, `DEFAULT_MIN_TVL`, the anomaly demotion/flagging and the degen ⅓ haircut are
   **byte-untouched**. This item only *adds* a bound.
7. New test wired into the `npm test` chain; `test_compute_kpis.js`, `test_kpi_sharpe_sort.js`,
   `test_planner_sharpe_pick.js`, `test_kpi_track_record.js` stay green.
8. No new user-facing string → `translations.js` untouched (EN+KO rule not triggered). Compiled/min assets
   regenerated only if a source they derive from changed.
