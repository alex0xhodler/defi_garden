# Spec 045: De-orphan the SEO surface — hub pages + homepage links

## Evidence
Direct greps, 2026-07-12 (committed live pages):
- `grep -oE 'href="[^"]*/(tokens|chains)/[^"]*"' home.html` → **0 matches**. The homepage links into the static SEO surface zero times.
- No `tokens/index.html`, no `chains/index.html`, no category pillar pages exist — thousands of spokes (2,022 `/tokens/<slug>` + 86 `/chains/<slug>`), zero hubs.
- Each spoke only cross-links within its own surface (token→related tokens, chain→related chains), so the pages form disconnected islands with no root.
- This is the structural root of the original GSC crisis (spec 010-diagnosis.md: "Crawled — currently not indexed" 22,877 + "Discovered — currently not indexed" 10,585). 2026 SOTA: orphan pages (no internal links from indexed, crawlable pages) rarely get indexed no matter how good; critical pages must be ≤3 clicks from the homepage; LLM crawlers read internal-link topology as a topical-authority signal.

## Hypothesis
We believe adding `/tokens/` and `/chains/` hub (index) pages, and linking them from `home.html`, will bring all 2,108 spokes within ≤3 clicks of the homepage and out of the orphan set — because right now there is no crawl path from `/` to any static SEO page, so Googlebot/LLM crawlers reach them only via the sitemap (a weak signal on its own), which is consistent with the "Discovered/Crawled — not indexed" GSC classes. Confidence: **supported** (grep-confirmed orphaning + a documented 2026 indexing mechanism + our own matching GSC failure classes).

## Change
Smallest version that establishes the crawl path — additive, no trust-rail/canonical/ranking change:
1. **Hub generators**: emit `tokens/index.html` and `chains/index.html` — static, server-delivered pages listing all generated `/tokens/<slug>` and `/chains/<slug>` pages as internal links, grouped for scannability (e.g. alphabetical or by TVL tier), each self-canonical (`/tokens/`, `/chains/`), with a real title/description/intro. Reuse the existing neumorphic page shell + `renderAnalyticsBootstrap` (039) + the shared JSON-LD helpers. A hub is itself an `ItemList`/`CollectionPage` candidate (coordinate with 046, don't block on it).
   - If the link count is very large (2,022 tokens), paginate or tier the token hub (e.g. top-N by TVL on the index + A–Z sub-hubs, or a reasonable cap with "see all" tiers) so a single hub page isn't itself a 2,000-link thin dump — 2026 guidance caps links-per-template (~30–100) for programmatic hubs. Decide the exact grouping during build; the acceptance criterion is "every spoke reachable within ≤3 clicks of `/`," not a specific layout.
2. **Homepage links**: add links from `home.html` to `/tokens/` and `/chains/` (e.g. a footer nav block or an SEO-links section) that render server-side in BOTH router modes (they must be in the static HTML, not injected by React after mount — crawlers need them without executing the app). Must not disturb the `__APP_MODE` router logic or the planner/analytics UX above the fold.
3. **Sitemap + robots**: add the two hub URLs to the sitemap index (via `generate-sitemap.js` or the relevant generator) so they're discoverable directly too.

OUT of scope: category/pillar pages ("Best Stablecoin Yields" etc.) — that's a strong phase 2 but larger; ship the index hubs + homepage links first. No change to canonical logic, the `__APP_MODE` router's mode decision, trust rails, or any spoke page's content.

## Acceptance criteria
- [ ] `tokens/index.html` and `chains/index.html` are generated, each self-canonical (`https://www.defi.garden/tokens/`, `/chains/`), with server-delivered title/description/intro and internal links covering every generated spoke (directly or via ≤1 intermediate sub-hub, so every spoke is ≤3 clicks from `/`). Verified by generating from a fixture and asserting on the emitted HTML (link count matches the generated spoke count, or the tiered structure provably reaches all of them).
- [ ] `home.html` contains server-rendered (static, pre-JS) anchor links to `/tokens/` and `/chains/`, present in the raw HTML for BOTH modes. Verified by asserting the links exist in `home.html` source and by a Playwright/curl check that they're in the initial DOM without running the app. **Both sacred router paths still work** (bare `/` → planner, `/?token=USDC` → analytics app with pool cards) — the router change is purely additive markup.
- [ ] The two hubs are added to the sitemap index.
- [ ] No spoke page content, no canonical, no trust rail (`APY_SANITY_LIMIT`, `MIN_POOL_TVL`, anomaly gate), no ranking logic altered — diff additive.
- [ ] Tests: new/extended assertions in the `npm test` chain (hub generator output + home.html link presence). `test_canonical.js`/`test_smoke.js` still green (both router paths) or documented network-blocked per the 5-min timebox standing decision.
- [ ] Instrumentation: hub pages carry the 039 analytics bootstrap firing `page_view` with a `page_type` (e.g. `token_hub`/`chain_hub`) so hub traffic is measurable.

## Measurement
Metric: GSC — the "Discovered/Crawled — currently not indexed" counts for `/tokens/` and `/chains/` should begin draining once the crawl path exists (2–6wk validation cycle, read via GSC once 026 unblocks); proxy = hub `page_view` counts + spoke `page_view` counts appearing as organic indexing arrives. Window: 2–6wk GSC cycle. Decision rule: keep (structural correctness — orphan removal is not an A/B); read the indexing-class trend at the next GSC-enabled heartbeat. Minimum sample per NORTH_STAR.md for any traffic claim.

## Risk tier (builder's guess — verifier assigns independently)
HIGH — touches `home.html` (the `__APP_MODE` IA router surface — NORTH_STAR names this HIGH by rule) and adds generated SEO surface. The router change is additive static markup only, but any edit to `home.html`'s router-adjacent structure + new indexable pages warrants the HIGH lane: full explainer + quiz before merge, and a verifier check that both sacred router paths (`/`, `/?token=`) are byte-unaffected in behavior.

## Open questions
None that block build. One layout judgment call (single paginated token hub vs. top-N + A–Z sub-hubs) is the builder's to resolve within the "≤3 clicks, ≤~100 links/template" constraint — not architecture-changing.
