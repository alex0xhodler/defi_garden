# Spec 190: nothing checks whether the Korean is Korean — 2,201 KO landers close with an English sentence

## Evidence
Measured this tick (2026-07-31) by flattening `translations.js` across all three namespaces and diffing
EN against KO. Reproduce with the script in "Change" below.

- **Key parity is clean and this is the first time it has been measured: 543/543 flattened keys, 0 missing
  in either direction** (top-level 185, `landing` 41, `planner` 319). Recorded as a true negative.
- **Value-level honesty is not clean.** Ten KO values contain **zero Hangul**. Eight are legitimately
  identical by nature — brand/product names (`Claude Pro`, `Apple TV+`, `ChatGPT Plus`, `Uber One`,
  `Leviathan News`, `DefiLlama API`) and the acronym `LP/DEX`. **Two are ordinary English prose that was
  never translated:**
  - `ko.landing.footerPoweredBy` = `"Powered by"` (identical to `en.landing.footerPoweredBy`)
  - `ko.landing.footerMadeWith` = `". Made with AI & Degen Love."` (identical to EN)
- **Blast radius: 2,201 pages.** `landing.js:358-360` composes all three footer strings unconditionally
  inside `e('footer', { className: 'app-footer' }, …)`, and `landing.js` backs
  **2,113 `tokens/*.html` + 88 `chains/*.html`**. Every KO lander closes with an English sentence.
- **It reaches users who never asked for KO in a URL.** `detectLanguage()` (`landing.js:47-55`) resolves
  `localStorage['defi-garden-lang']` → `?lang` → `navigator.language.indexOf('ko') === 0`, so a
  Korean-browser visitor lands on the KO copy automatically.
- **KO traffic is real, not hypothetical:** `?token=BUIDL&lang=ko` appears in this week's prod
  `page_view`-by-URL breakdown (query `3bb75bb7`, 7d).
- **The existing i18n checks cannot see this class.** `test_ko_pool_money_honesty.js` guards KO *currency
  units* (item 137's `원`-on-USD bug); `test_i18n_pages.js` guards page wiring; `test_translations_fallback.js`
  guards fallback behaviour when a key is absent. **No test anywhere asserts that a KO value differs from
  its EN value.**

## Hypothesis
We believe **adding a value-level EN/KO signal to the cheap prescan (plus translating the two strings)**
will **close the last unguarded half of the "EN + natural KO together" hard rule** because **the existing
checks were all specced from item 137, a currency-unit bug, so they inherited its signal set and never
asked the adjacent question ("is this value translated at all?").** Confidence: **validated-pattern** —
this is item 175's documented thesis (*"a checker's signal set is always drawn from the last bug someone
was bitten by, so the next bug is in whatever class no one has been bitten by yet"*) on its Nth instance,
and the two defects were found by asking exactly that question.

## Change
Two legs, smallest version of each. **The gate is the deliverable; the two strings are the repair that
proves it fires.**

**Leg A — repair (translations.js).** Give `ko.landing.footerPoweredBy` and `ko.landing.footerMadeWith`
natural Korean. Keep the sentence composable with the untouched `footerDefillamaApi` link node between
them — `landing.js:358-360` renders `[powered] ' ' <a>DefiLlama API</a> [madeWith]`, so the Korean must
read correctly with the link text in that position, which may mean the two halves are not a word-for-word
translation of the English halves. Do not restructure `landing.js`; do not touch the EN values.

**Leg B — the gate (`audit-app.js` prescan).** Add ONE new signal to the existing text/static prescan
family, reusing its established shape (`PRESCAN_SIGNALS`-style severity map, aggregate finding with ≤10
example keys, never one finding per key). Pure `fs` + regex on `translations.js` — **no render, no
network**, per the playbook's "prescan the cheap way" rule. It must assert both halves:
1. **Key parity** — the flattened EN and KO key sets are identical. Any asymmetry is a finding.
2. **Value honesty** — a KO value that is byte-identical to its EN value AND contains no Hangul
   (`/[가-힯ᄀ-ᇿ㄰-㆏]/`) is a finding, **unless its key is on an explicit allowlist**.

The allowlist is the load-bearing design decision: seed it with the **eight** keys measured above, each
with a one-line reason (brand name / acronym). Put it in `audit-app.js` next to the signal, as data, so
adding a new brand string is a one-line diff and never a reason to weaken the predicate.

**Explicitly OUT of scope:** judging KO *quality* or naturalness (that is human judgment, playbook class
8); the `planner`/top-level namespaces' copy itself (both measured clean today); any change to
`landing.js`, the EN strings, `translations.min.js` regeneration policy beyond whatever the existing build
step already does, or the other i18n tests. Do **not** widen this into a general "i18n audit."

## Acceptance criteria
- [ ] `ko.landing.footerPoweredBy` and `ko.landing.footerMadeWith` contain Hangul and differ from their EN
      counterparts. The EN values are byte-unchanged.
- [ ] The rendered KO footer on a `tokens/*.html` lander reads as one coherent Korean sentence with the
      `DefiLlama API` link inline — verified in the **rendered** app (Playwright, fixture-routed per the
      house pattern), not by reading the dictionary. Per standing decision 2026-07-11, a unit-fixture-only
      check is a FAIL.
- [ ] The new prescan signal exists, runs inside the normal `node audit-app.js` invocation with no extra
      flag, and appears in the run's `bySignal` block.
- [ ] **Positive control — the signal is proven able to fire.** A test injects a fixture dictionary with
      (a) a KO key missing and (b) a KO value byte-identical to EN and non-allowlisted, and asserts the
      signal reports **both**. Per LEARNINGS 2026-07-27 takeaway 2, a filter returning zero is not evidence
      of health until it is shown able to return non-zero. **This criterion is the point of the item.**
- [ ] **Allowlist does not swallow real findings.** A test asserts a non-allowlisted untranslated value is
      still reported when other keys are allowlisted, and that the allowlist is keyed by exact key path
      (not a prefix or substring match).
- [ ] On the real `translations.js` after Leg A, the signal reports **0 suspects** — and the run's own
      output states the allowlist size, so a future reader can tell "clean" from "allowlisted into silence."
- [ ] Tests: `node test_planner.js && node test_protocol_parsing.js && node test_qualifier_fix.js` green;
      the existing i18n tests (`test_i18n_pages.js`, `test_ko_pool_money_honesty.js`,
      `test_translations_fallback.js`) still green; the new test file runs in the same style as
      `test_audit_prescan.js`.
- [ ] Any pre-existing red on `main` is measured on a clean baseline BEFORE the change and reported as
      pre-existing, never silently inherited (playbook `pre-existing-red-triage.md`).
- [ ] Instrumentation: **none — this ships no user-facing behaviour change beyond two copy strings.** Per
      NORTH_STAR's experiment discipline, copy/tooling changes carry no new events. Do not invent one.
