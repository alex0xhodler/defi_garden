## Root cause — TWO independent bugs, both required for the P0

Read from the code this run, file:line. Neither is an occlusion-clearance problem, so
the `fixed-overlay-occlusion.md` playbook's checklist does **not** resolve this one.

**(A) The floating-toggle rules leak onto the header's own buttons.**
`app.js:3062` renders `className: 'google-control-btn theme-toggle'` — it carries BOTH
classes. `style.css:3913-3918` sets `.theme-toggle { position: fixed; top: …; right: …;
z-index: 1000 }` with no scoping, and `style.css:4029-4036` does the same for
`.language-toggle` at ≥641px. So the header's in-flow control buttons are yanked out of
flow and pinned to the same viewport coordinates as the standalone floating pair —
which is why `.google-header-controls` measures `w:0 h:0` at 768px and why the two
pairs coincide exactly.

**(B) The header row cannot fit at ≤640px, so its controls overflow off-screen.**
`.google-header-content` (`style.css:928-936`) is `display:flex` with `gap: var(--space-24)`
and `padding: var(--space-12) var(--space-16)`; there is **no** `@media` override for it
anywhere (`grep -n "google-header-content" style.css` → one match, line 928). Its middle
child `.google-search-container` is `flex: 1` (`style.css:952-956`) and the input inside
it is `flex: 1` (`style.css:973-983`) — neither has `min-width: 0`, so both keep their
automatic min-content width (a bare `<input>`'s intrinsic ~170px + `var(--space-20)`
side padding). The row therefore cannot shrink to 360px and the trailing
`.google-header-controls` is pushed to `x:498.8`, past the viewport edge.

**(C) Why the standalone pair is buried rather than floating**, the third strand:
`style.css:4319-4327` sets `.theme-toggle { position: static }` at ≤640px, and the only
rule restoring `position: fixed` is `.app:not(.has-results) .theme-toggle`
(`style.css:4329-4335`) — which by construction never matches a results page
(`app.js:3001` adds `has-results` whenever a token/chain is selected). The in-flow
buttons then render as the first children of `.app`, whose mobile clearance is only
`padding-top: var(--space-20)` (`style.css:2631-2633`, overriding the 160px at
`style.css:1069-1071`) against a 130px-tall fixed header.

## The fix — reuse the header's own controls, delete nothing from the DOM

Standing decision 2026-07-10 (REUSE COMPONENTS): the header **already** renders a
theme toggle and a language toggle, in the design-system `.google-control-btn` style,
on every results page. That is the one that should work. The standalone floating pair
exists for the analytics **homepage** (bare `/?`-less `.app:not(.has-results)`, which
renders no header at all) and must keep working there.

Three CSS changes in `style.css`. **No JS changes, no new class, no new colour, shadow,
radius, gradient or token.** The React render sites at `app.js:3057/3062/3143/3153` are
NOT edited — deleting the standalone pair would break the analytics homepage, which has
no header to fall back on.

1. **Stop the floating rules from matching the header's buttons.** Scope them so a
   `.google-control-btn` stays in the header's flow (e.g. a
   `.google-header-controls .theme-toggle, .google-header-controls .language-toggle
   { position: static; top: auto; right: auto; margin: 0; z-index: auto; }` reset placed
   after the existing rules, or equivalent `:not(.google-control-btn)` scoping on the
   floating rules themselves — builder's choice, whichever produces the smaller,
   clearer diff; document which and why in the notes).
2. **Hide the standalone duplicates on results pages only** —
   `.app.has-results > .theme-toggle, .app.has-results > .language-toggle
   { display: none; }`. The `>` child combinator matters: it must not match the header's
   buttons (which are grandchildren via `.google-header-sticky`). Scoped to
   `.has-results`, so `.app:not(.has-results)` — the analytics homepage — is untouched.
3. **Let the header row shrink at ≤640px** so its controls stay on-screen:
   `min-width: 0` on `.google-search-container` and `.google-search-input`, plus a
   tighter `gap`/`padding` on `.google-header-content` inside the existing
   `@media (max-width: 640px)` block.

**Pre-registered validation of this shape** (probe run this session, candidate CSS
injected over the real `style.min.css` render, `?token=USDC`): at **360, 480, 640, 768
and 1280px** the result is exactly one visible theme toggle and one visible language
toggle, each `elementFromPoint`-resolving to itself (`hitIsSelf: true`), with
`documentElement.scrollWidth === innerWidth` at every width. Confirmed EN and KO at 360
and 480. The builder is not required to use this exact CSS, but must reach this measured
outcome.
