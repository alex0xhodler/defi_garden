# Spec 048: Freshness signals — visible "Last updated" + dateModified schema on generated pages

## Evidence
Direct grep, 2026-07-12: `grep -iE "last updated|dateModified|datePublished" tokens/*.html chains/*.html` → **0 hits**. The static pages carry no on-page or structured freshness signal, despite being regenerated daily by `sitemap-update.yml` (cron `0 2 * * *`). Sitemaps emit `<lastmod>` (021/041), but that signal never reaches the page itself.
- 2026 SOTA: AI answer engines carry a strong recency bias — citations to content that looks >3 months old drop sharply; a visible "Last updated" date + `dateModified`/`datePublished` schema is a documented cheap, high-ROI freshness signal. We already regenerate daily; we simply don't advertise it, so the pages read as undated/static to a crawler or AI engine.

## Hypothesis
We believe surfacing the generation date (visible "Last updated <date>" line + `dateModified` in the page's JSON-LD) will improve freshness perception for crawlers and AI engines, because the pages are in fact refreshed daily but currently expose no freshness signal, so they're indistinguishable from stale programmatic pages. Confidence: **supported by external 2026 sources; unvalidated here.**

## Change
Additive, no trust-rail/content-logic change:
1. Token/chain/story generators: pass the CI generation date (already computed for sitemap `lastmod` — `new Date().toISOString().slice(0,10)`) into the page and render a small visible "Last updated <human date>" line (near the intro or footer note), in the existing neuro `.note` style. en-US date formatting.
2. Add `dateModified` (and `datePublished` if a stable first-publish date is available; else `dateModified` alone) to the page's JSON-LD — attach to the appropriate node (the `Dataset`/`WebPage`/`Article` type; coordinate with 046 if it lands first so there's one coherent JSON-LD graph rather than duplicate date nodes).
3. Keep the visible date and the schema `dateModified` identical (Google's must-match-visible-content rule).

OUT of scope: any change to the daily-regen cadence itself (that's the `sitemap-update.yml` cron, separate decision); backdating/fabricating a `datePublished`; per-pool timestamps.

## Acceptance criteria
- [ ] Every generated token/chain/story page renders a visible "Last updated <date>" line sourced from the generation timestamp; verified on a fixture-generated page.
- [ ] The same date appears as `dateModified` in the page's JSON-LD, byte-for-byte matching the visible date; verified programmatically.
- [ ] No content/canonical/trust-rail change — additive only; diff confined to the generators (+ shared date helper).
- [ ] Tests: assertions added to `test_token_pages.js`/`test_chain_pages.js`/`test_stories.js` for the visible date + schema `dateModified` match, in the `npm test` chain.
- [ ] Instrumentation: none new (SEO/schema-only change).

## Measurement
Metric: not Mixpanel-isolable; proxy = GSC freshness/re-crawl cadence + AI-citation recency once 026 unblocks. Window: 2–6wk GSC cycle. Decision rule: keep (best-practice freshness signal).
