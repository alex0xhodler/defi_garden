# 219 — PR explainer (HIGH tier): the audit learns to see occlusion

## The goal in one sentence

The daily audit renders 82 real pages in real Chromium and scored **0 blocking findings** on the same page, the same day, that a human found broken by eye — because every check it had was a DOM read of a defect someone had already thought to name. This item gives it the one question a human asks in half a second: *is this element actually visible, and can I actually press it?*

## Intuition — why the existing checks could never catch this

`checkResponsive` (the closest thing the file had) measures the CTA's own box against the **viewport**: is it non-zero, is it inside `0..width`. Item 218's buried button passed both. Its box was perfect. Its box was fully inside the viewport. There was simply another element painted on top of it.

Occlusion is not a property of an element. It is a **relationship** between two elements plus a scroll position plus a viewport height — and that is why it needed a new kind of check rather than a new selector in an old one.

Three live defects in this repo are that same relationship:

| item | victim | overlay | who found it |
|---|---|---|---|
| 217 | pool-detail hero prose, sliced mid-sentence | `.app-footer` | a human, on an iPhone |
| 218 | `garden_cta` — the north-star metric's own emitter | `.app-footer` | 217's verifier, attacking a prose claim |
| 179 | bare `/` content | `.app-footer` | a human; fixed on one route, never ported |

## What changed, in reading order

### 1. `audit-app.js:342-356` — three constants, one of which is the whole trick

```js
const OCCLUSION_HEIGHT = 780;
const OCCLUSION_MIN_COVERAGE = 0.25;
const OCCLUSION_CANDIDATE_CAP = 800;
```

`OCCLUSION_HEIGHT = 780` is the load-bearing number. Every audit page is created at `{ width: s.width, height: 900 }` (`:3527`). At 360×**900** item 218's footer sits at 842..900 and the CTA clears it completely — *the defect does not exist at the height the audit renders at*. At 360×**780**, the height 218 was actually evidenced at, the footer band is 722..780 and the button is inside it. A lens bolted onto the existing pages would have shipped with 218 still in its blind spot, and would have looked like it worked.

### 2. `audit-app.js:3994-4157` — `occlusionPassEval`, the in-page measurement

One `page.evaluate` per pass. Collects **overlays** (visible, `position: fixed|sticky`, non-zero rect, *excluding* anything covering ≥80% of the viewport — an open modal legitimately covers the page), then walks the document for **victims** (interactive: `a[href], button, input, select, textarea, [role=button]`; or text-bearing: a direct child text node ≥3 chars), skipping anything inside an overlay or positioned itself.

A victim is reported only when **geometry and the hit test agree**:

- **geometry** — for text-bearing victims, ≥25% of the victim's area covered *and* the overlay is paint-opaque (background alpha ≥0.5 or a backdrop-filter); for interactive victims, **any** intersection (218 was a 47px button in a 58px band — "mostly buried" is unpressable).
- **hit test** — `document.elementFromPoint` at the victim's centre, plus 75% of its height for interactive victims, must return the overlay or a descendant of it.

Requiring both is what separates a real defect from rect algebra, and it is what makes a *transparent* click-thief detectable: for an interactive victim, opacity is irrelevant because interception is proven directly.

### 3. `audit-app.js:4167-4191` — `pushOcclusionPassFindings`, deliberately quiet

At most one finding per pass per severity class — worst offender by covered fraction, stable-sorted so ties stay in document order — with `+N more occluded element(s) on this pass`. A systemic layout bug therefore costs the report ≤4 findings on that surface instead of forty. The detail string carries victim, overlay, both rects, covered percentage and which hit-point resolved to the overlay, so a ticket is actionable without re-rendering anything.

### 4. `audit-app.js:4193-4270` — `checkOcclusion`, two passes and one asymmetry

- **At rest** (`scrollY = 0`, asserted, polled): any overlay may occlude. First paint is what the user sees. This is 217's and 218's case.
- **At bottom of scroll**: only overlays anchored to the viewport bottom (`rect.bottom >= innerHeight - 2`) may occlude.

That asymmetry is the design decision to scrutinise. Content covered by a **top**-anchored fixed header at max scroll is revealable by scrolling *up* — flagging it would put a false finding on every grid surface carrying `.google-header-sticky`, and a lens that cries wolf gets switched off. Content covered by a **bottom**-anchored overlay at max scroll is revealable at *no* scroll position: that is exactly 217 and 179.

Never throws (wrapped) and never goes silent: a skip, a truncated scan, or an internal throw each emit their own advisory **P2**.

### 5. The same bug, twice, found during the build — and why it mattered

`style.css:2845` sets `html { scroll-behavior: smooth }`, so `window.scrollTo` **animates**. The first implementation read position one tick after issuing the scroll and reported:

```
bottom-of-scroll unreachable after 5 attempts at 360x780:
scrollTop=1663 innerHeight=780 scrollHeight=2504
```

1663 of the 1724 needed — 96.5% of the way there. Not an unreachable document: an animation still in flight, misreported as a skipped measurement. Left alone, the leg built to catch the 217/179 class would have measured **nothing on any page tall enough to have that class**, while emitting a plausible-looking advisory.

The identical vacuity was then found in the *at-rest* pass, where `scrollBehavior='auto'` had not yet been applied: the `planner` driver clicks a `.gp-chip` (`:3717`) before the occlusion call, a click can scroll, and an animated `scrollTo(0,0)` read one tick later would have degraded the 218-catching leg into an advisory on exactly those surfaces. Fix, once, at the top of the check: force `scrollBehavior='auto'`, use `behavior: 'instant'`, poll for arrival, treat a changed `scrollHeight` as "still settling", and settle 150ms after the resize before measuring.

Acceptance criterion 8 exists specifically so this cannot regress silently: the real `pool-detail-360` surface must confirm arrival.

### 6. `test_audit_occlusion_lens.js` (new, 561 lines) — the proof, not the claim

Layer 1 is source-level and cannot be skipped: `checkOcclusion` exists, is exported, is called on exactly 7 non-`loading` branches, `OCCLUSION_HEIGHT === 780`, and the bottom-anchor asymmetry gate is present. Layer 2 drives real Chromium; only the browser launch is skip-tolerant, every assertion sits outside that catch.

The criterion that earns the item is **5, the RED PROOF**: on the real product page, with 218's fix mutated away in-page (`position: fixed` restored on `.app.pool-detail-view .app-footer` + clearance cancelled — the exact pre-218 state), the lens must report a **P0** naming the `garden_cta` anchor. Criterion 4 is the same page unmutated, asserting zero P0/P1. Together they say: it fires on the real defect, and it does not fire on the fixed product.

### 7. `test_audit_app.js` — a split gate, not a softened check

The lens immediately turned this file red, because its case 1 asserts zero P0/P1 across the app surfaces and the lens found real defects on the grid surfaces. Triaged per `playbooks/pre-existing-red-triage.md` as **rule A — a product defect the test correctly caught** (the audit was green only because the class was unmeasured), and handled the way case 1 *already* handled real junk static pages tripping `junk-slug`: narrow the scope, name the defects, keep the check.

- every non-`occlusion` check keeps **ZERO P0/P1**, unchanged;
- `occlusion` findings are permitted **only** on the named, dated quarantine set — a new occlusion defect on any other covered surface still goes red;
- **ZERO occlusion findings on any `pool-detail*` surface, at any severity** — 217/218's regression rail, now machine-watched daily, never eligible for quarantine (and, because P2s count here too, it also permanently enforces criterion 8's non-vacuity);
- a loud `QUARANTINE NO LONGER NEEDED — remove it` line prints the run the quarantined surfaces come back clean.

### 8. `package.json` — one test step appended. No dependency added.

## What it found on its first real runs (tickets, not fixed here)

Every one independently re-measured outside `checkOcclusion` (second `page.evaluate` reading both rects + `elementFromPoint`), resampled to rule out a timing race, with the producing CSS rule identified:

1. **`grid-360`, P0** — a duplicate, non-fixed `.theme-toggle` (`app.js:3139`, distinct from the header's own copy at `app.js:3062`) sits in normal flow directly under the fixed `.google-header-sticky` (`style.css:903`): `.app.has-results` leaves the mobile `position: fixed` override (`style.css:4329`) un-applied, so the base `position: static` (`:4319`) wins. **A control the user can never press.**
2. **`grid-360`, P1** — a `.pool-symbol` row lands inside the fixed `.app-footer`'s band at first paint, purely because enough cards fill a 360×780 viewport to reach it. 218's lesson recurring on a surface 217/218 never touched: clearance protects the document's end, not a mid-page row.
3. **`landing-768`, P1 ×2** — hero span and paragraph under the footer, at rest *and* at true bottom. Root cause: `landing.js:244`'s root is `className: 'landing-app'`, and `grep -n "\.landing-app" style.css` returns **zero matches** — this route never inherited `.app`'s clearance at all. **This is item 179's class, still live, on a different route.**
4. **`grid-token` / `grid-chain` at 1280px** — same class as (1)/(2); `grid-token` is boundary-flaky (clean on 2 of 3 runs) because it depends on how many cards fill the viewport.

Fixing any of them is a separate item — the spec's own scope boundary. The lens's job was to find them, and on its first day it found four things the audit had been reporting clean.

## Deviations from the spec

None substantive. The spec itself was amended twice **during** the build, both times because the implementation surfaced something the spec had assumed: the smooth-scroll vacuity (both passes, plus the resize settle) and the `test_audit_app.js` quarantine policy. Those amendments are in the diff and were made before the code that satisfies them, so the verifier judged the final code against the final spec. The quarantine set grew from `{grid-360}` to `{grid-360, grid-token, grid-chain}` when the resize settle made two more real defects visible.

## What is deliberately NOT here

Leg **(b)**, the visual lens — a screenshot a model actually looks at. `grep -rn "screenshot"` across the diff returns nothing that captures an image. Leg (b) needs its own decisions (which model, cost per tick, where images live, how a judge's verdict becomes reproducible enough to gate on) and so gets its own item. Until it exists, a green audit means "no occluded content and no broken numbers" — **not** "a human would like this page", and `playbooks/fixed-overlay-occlusion.md` now says so in as many words.

Two documented blind spots in leg (a) itself, stated so nobody mistakes silence for health: overlays covering ≥80% of the viewport (modals/scrims) are excluded, and content covered by a top-anchored overlay at bottom-of-scroll is excluded by design.
