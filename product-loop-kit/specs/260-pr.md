## What this attempt fixes: a self-inflicted header/row misalignment

Attempt 2's leg-A fix touched **three** things: `.pools-list .pool-card`'s grid
template (needed), `.pools-list .pool-tvl-section`'s `min-width: 130px` floor (needed),
and `.pool-columns`'s grid template (NOT needed — and actively harmful). `.pool-columns`
(the slim "Pool / APY / TVL" header row) and `.pools-list` (the data rows) are **sibling
grids** — two separate top-level elements in app.js, not the same grid with a shared
row. Changing `.pool-columns`'s track 4 from a fixed `130px` to `auto` let it shrink to
the width of the word "TVL" (a few px) while the data rows' track 4 stayed floored at
130px by the (correct, still-shipped) `min-width` rule. Because track 3's right edge is
a function of track 4's width (`track2 + track3 = R − track4`, where `track2` is the
grid's one flexible `1fr` column absorbing the difference and `R` is the fixed total
width shared by both grids at a given viewport), the two grids' track 4 no longer
matching meant their track 3 no longer matched either: the "APY" header label sat
**~107px** to the right of the APY numerals it labels, on completely normal rows, at
768/1280px, in the default list view, on every `?token=`/`?chain=` sitemap URL — a live
visual regression that shipped in attempt 2.

**Why the existing test didn't catch it:** `test_card_numeral_wrap.js`'s checks (and
both attempts' AC-3 rect-drift re-measurements) only ever looked at `.pool-card`'s own
numeral-cell rects. `.pool-columns`'s header-label rects were never captured by anything
committed, even though the spec's AC-3 wording named header alignment explicitly. This
was the guard gap the verifier flagged, closed by the new check below.

**The fix is a straight revert**, not a modification: `.pool-columns`'s
`grid-template-columns` (and its doc comment) go back to the exact `6a5092661b` text.
`git diff 6a5092661b -- style.css` now touches only `.pools-list .pool-card` and the new
`.pools-list .pool-tvl-section` min-width block — zero `.pool-columns` hunks. This also
answers a question the attempt-2 verifier left open ("was the `.pool-columns` change
inert dead code?") — no: it was the direct, sole cause of the drift.

## Intuition: two sibling grids, one shared invariant

Picture the header row and every data row as two independent 5-column grids stacked on
top of each other, both given the same total width. Four of the five columns are either
truly fixed (icon, the trailing action/CTA column) or floored to the same px value in
both grids (the TVL column, thanks to the `min-width: 130px` rule). The one column that
is genuinely flexible — the pool-name/byline column — silently absorbs whatever
difference is left over. That's *why* an oversized APY numeral can grow its own column
without ever knocking the header out of alignment: the flexible column stretches or
shrinks to compensate, and the APY column's position falls out of the arithmetic, not
out of anything either grid does on purpose. The one way to break that invariant is to
let the *floored* column stop matching between the two grids — which is exactly what
touching `.pool-columns`'s template did, and exactly what reverting it undoes.

## What changed and why

**`style.css` (revert only — no new rule):**
- `.pool-columns`'s `grid-template-columns` reverted from
  `40px minmax(0, 1fr) auto auto 120px` back to the baseline
  `40px 1fr 110px 130px 120px`, and its doc comment reverted to the baseline text.
- `.pools-list .pool-card`'s doc comment was rewritten (it previously said "see
  `.pool-columns` above", which went stale the moment `.pool-columns` stopped
  changing) to explain the two-grid alignment mechanism standalone, since
  `.pool-columns` no longer carries any spec-260 commentary at all.
- Nothing else changed. `.pools-list .pool-card`'s `auto auto` template and
  `.pools-list .pool-tvl-section`'s `min-width: 130px` floor — leg A's actual
  mechanism — are untouched from attempt 2.

**`test_card_numeral_wrap.js` — new check I (header/row column alignment):**
- For every view×theme×viewport combination where `.pool-columns` actually renders
  (detected from the DOM each run — computed `display !== 'none'` — never hardcoded as
  "only ≥768px"), asserts `.pool-columns .col-apy`'s right edge === every non-anomalous
  row's `.pool-apy-hero` right edge, and `.pool-columns .col-tvl`'s right edge ===
  every non-anomalous row's `.tvl-value` right edge, within 1px. "Non-anomalous" is
  derived from the DOM too: a row is skipped only if its hero carries the
  `apy-anomalous` class app.js adds to the anomaly-flagged hero, not from a fixture id.
- Grid-view combinations are exercised too, asserting `.pool-columns` is correctly
  *absent* there (React never renders it outside list view) rather than being skipped
  silently.
- A run-total `COLUMN_ALIGNMENT_COVERAGE` assertion fails the whole run if check I
  never actually asserted on anything — mirroring the existing
  `NUMERAL_CLASS_COVERAGE` non-vacuity pattern.
- Proven non-vacuous two ways (full transcripts in `specs/260-notes.md` "Attempt 3"):
  re-applying the exact shipped `.pool-columns` regression turns check I red, naming
  the APY column, ~107px drift, on every applicable combination; separately, neutering
  the `.pools-list .pool-tvl-section` min-width floor also turns check I red (this is
  what finally makes that floor a rule the committed gate can see break, closing the
  attempt-2 verifier's open point about it being otherwise unguarded).
