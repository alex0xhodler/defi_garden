# 241 — one pinned formatter for every number that reaches the dictionary (HIGH tier explainer)

## Goal

UX audit F6, from the human's own screenshot: the analytics grid renders

```
1,976 results          ← app.js:3131, .toLocaleString('en-US')
1976 pools found       ← translations.js:36, bare `${count}` interpolation
```

two inches apart, on one screen, for the same number. CLAUDE.md's hard rule and standing decision
2026-07-09 pin all money/number formatting to `en-US` via the helpers — but that rule was only ever
enforced in *app code*. `translations.js` was never swept, and it is the one place where a raw number
becomes user-visible text without passing an app-side helper.

## The intuition

The obvious fix is "format inside `showingResults`". That closes the instance and nothing else — the
next added string with a `(count)` param regresses it silently, which is exactly the induced-from-the-
last-bug failure `RAZOR.md` catalogues four times over.

So the question became: what is the weakest predicate that covers the whole dictionary?

The first candidate — sweep every entry, guard it with a test that probes each entry and allowlists the
exceptions — was **measured before it was built**, and the measurement killed it:

```
total function-valued entries (en + ko, flattened):        306
entries emitting a bare 1976 for SOME param position:      293
```

293 of 306 entries take at least one parameter that *callers already format* (`amt`, `apy`, `tvl` arrive
as strings like `"$1,976"`). A probe-every-param test would have to exempt 293 keys to go green — an
allowlist that large is not a guard, it is a 293-line way of writing `assert(true)`. And the dictionary
cannot tell a pre-formatted param from a raw one, because the difference is not in the dictionary: it is
in what the *caller* passes.

But there is exactly one place where that difference is visible — **the accessor**, at runtime, where the
actual argument still has a type. `typeof arg === 'number'` is the defining mechanism, not a resemblance
of it. So the fix goes there, and it needs no allowlist at all.

## What changed, in reading order

1. **`translations.js` — the shared formatter.** `formatCount(value)` returns
   `value.toLocaleString('en-US')` for a finite number and the value **unchanged** for anything else.
   That identity branch is what makes it safe to apply blindly: the 293 pre-formatted params pass
   through untouched. Exported from `module.exports` and left as a bare top-level `function` — the same
   mechanism `translations` and `createTranslationFunction` already use to become browser globals.

2. **`translations.js` — the chokepoint.** `createTranslationFunction`'s returned `t(key, ...params)`
   maps `params` through `formatCount` before invoking the entry, on the normal path *and* the
   English-fallback path. A dictionary entry can no longer see a raw number, so a bare `${count}`
   interpolation cannot render an ungrouped digit run — whether the entry was written yesterday or
   ships next month.

3. **`planner.js` — the second chokepoint.** The planner subtree is not reachable through
   `createTranslationFunction`; `makeT()` reads `translations[lang].planner` directly. It gets
   `applyPinnedCounts(args)`, wired the same way. It honours spec 082's graceful-degradation contract:
   it prefers the shared `window.formatCount` and falls back to an inline identity-safe copy rather than
   throwing if `translations.min.js` has not loaded. `rootT()` is unchanged — its sole call site
   (`rootT(lang, 'loadingError')`) passes no params.

4. **The plurality predicates — the cost of the design, paid in full.** Because entries now receive a
   *string*, every `count === 1` inside the dictionary would be false for `"1"` and render "1 pools".
   Eleven predicates across both trees became string-safe (`String(count) === '1'`): `showingResults`,
   `planner.years`, `planner.speedupDisciplined`, `planner.reportElapsedDays` (EN **and** KO — the KO
   twin branches to a different sentence), `tcpTokenDescription`, `tcpChainDescription`, `tcpTokenIntro`,
   `tcpChainIntro`, `tcpSubLine`, `tcpAnswer`, `tcpFaqA2`. Wording is byte-unchanged; only the predicate
   moved. The KO counterparts of the `tcp*` keys need no fix — Korean has no count-driven plural, and
   each was read individually to confirm no `=== 1` guard exists there.

5. **The `$NaN` trap, and why the diff reaches `PoolDetail.js`.** Five EN + five KO entries did their own
   formatting: `Number(amount || 0).toLocaleString('en-US')`. Pre-format the argument and that becomes
   `Number("1,976")` → **`NaN`** → *"Based on $NaN investment"* on the live pool-detail calculator and in
   the static pool-page markdown twins. Reproduced concretely before it was fixed. Those ten entries now
   reuse the same shared `formatCount` (idempotent — identity on an already-formatted string), and the
   two that used `{maximumFractionDigits: 0}` had their rounding moved to the call sites that own the
   float: `Math.round(projectionAmount)` at `PoolDetail.js:1089` / `:1310` and
   `generate-pool-pages.js:395` / `:425`. `PoolDetail.js`'s non-`t` fallback branch already rounded —
   the `t()` branch now matches a sibling that was always there.

6. **`test_translations_number_format.js`** (new, plain lane) — enumerates the population **fresh on
   every run**: flattens both trees, collects all function-valued keys (prints 306, asserts > 250 so it
   can never silently enumerate nothing), and probes each parameter position of each entry with `1976`
   through the real accessor — 496 invocations. Allowlist is a real keyed object, **size 0**, asserted
   empty. Plus the named-instance controls (`showingResults(1976)` EN/KO, `showingResults(1)` → "1 pool
   found", `years(1)`, `reportElapsedDays(1)`) and an identity check that non-numeric params are
   untouched. A new key with a numeric param is covered with no test-file edit.

7. **`test_results_count_render.js`** (new, browser lane) — the rendered leg the UX-item standing
   decision requires. Fixture-routes `/?token=USDC` to 1,976 synthetic pools and asserts
   `.google-results-count` and `.results-count` both render the grouped form. Under the accessor
   mutation it reproduces the audit defect verbatim, side by side.

8. Regenerated committed twins (`npm run compile && npm run minify`): `translations.min.js`,
   `planner.min.js`, `PoolDetail.compiled.js`, `PoolDetail.compiled.min.js`.

## Non-vacuity — three legs, each seen RED, each restored byte-identical

Per `playbooks/compiled-artifact-mutation-proof.md`, every cycle is edit source → re-minify → run →
restore → re-minify → `md5sum -c` (the pages load `translations.min.js`, never `translations.js`).

| Leg | Mutation | Result |
|---|---|---|
| 1 — entry | `showingResults` reverted to the pre-241 line | RED on the pluralization control (`"1 pools found"`), 13/14 |
| 2 — accessor | `params.map(formatCount)` → `params` | RED with **240 bare-number failures across many keys** — proving the accessor leg is load-bearing and *distinguishable* from leg 1, which stayed green |
| 3 — rendered | same accessor mutation, browser | RED: `"1,976 results"` beside `"1976 pools found"` — the original audit defect, reproduced on demand |

## Deviations from the spec

1. **The spec's per-entry-sweep + allowlist shape was rejected before the build**, on the 293/306
   measurement above, and replaced with the accessor chokepoint. The spec's acceptance criteria are
   unchanged and all still apply — only the mechanism that satisfies them changed.
2. **The bare-digit check is probe-scoped (`(?<!\d)1976(?!\d)`), not a blanket `/\d{4,}/` scan.** Four
   entries carry the static `APY_SANITY_LIMIT` literal in prose ("exclude anomalous (>1000% APY) pools"),
   which a blanket scan would flag on every invocation forever, unrelated to formatting. The probe-scoped
   form cannot match the correctly-grouped `"1,976"` (the comma splits the run), so it is the stricter
   version of the same invariant.
3. **`PoolDetail.js` / `generate-pool-pages.js` / ten dictionary entries changed beyond the spec's file
   list** — forced by the `$NaN` regression in §5, not opportunistic.

## Class rule — answered with a number

**306 of 306** function-valued entries are covered automatically: the sweep derives the population at
test time, so a newly added key with a numeric param is included without touching the test.
**2 of 306** — `landing.returnStatus` (EN + KO) — are reachable only through `landing.js`'s direct dict
read, outside both accessors. Its one call site passes `plantedDate`, a `toLocaleDateString` string,
audited this run. A future `.landing` entry that starts receiving a raw number would need that audit
repeated; it is **not** caught by the automated guard. That is the honest boundary of the class.

## Quiz

1. 293 of 306 dictionary entries emit a bare number when probed. Why does that number kill the
   allowlist-based guard the spec originally proposed, rather than just making it tedious?
2. `formatCount` returns non-numbers unchanged. Name two distinct things that identity branch buys —
   one about the 293 pre-formatted params, one about `planner.js`'s degraded-load path.
3. After the accessor change, `showingResults` receives `"1"` rather than `1`. What did that break, and
   why is `String(count) === '1'` the right repair rather than `Number(count) === 1`?
4. Mutation leg 2 turned 240 assertions red while leg 1's pluralization control stayed green. What
   property of the two-leg design does that specific pattern prove, that a single red would not?
5. The class answer is "306 of 306 covered, 2 of 306 not". What mechanism makes those two entries
   uncoverable by this guard, and what would have to change for the guard to reach them?
