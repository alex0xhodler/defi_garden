# Spec 268: the shipped x402 surface targets a superseded protocol version and a non-protocol payload — no real x402 client or facilitator can transact with it

## Evidence

Item 234 merged 2026-08-11 as `dc9892a45b` (PR #432), verifier PASS round 3, 7/7, HIGH. It ships dark
(`X402_ENABLED` unset) and is honest about a long residue list in `edge/X402.md`. This item is about
**three things that residue list does not mention**, all found by reading the authoritative standard
rather than the announcement blog post.

Sources, fetched raw 2026-08-11 from `https://raw.githubusercontent.com/x402-foundation/x402/main/`
(the Linux Foundation project that now owns the standard — `x402.org`, repo `x402-foundation/x402`):
`specs/x402-specification-v1.md`, `specs/x402-specification-v2.md`, `specs/transports-v2/http.md`,
`specs/transports-v2/mcp.md`.

### Finding 1 — the surface implements x402 **v1**; **v2** is the current standard

`edge/X402.md:94` describes the challenge as an "x402 v1-conformant body"; `edge/X402.md:69` publishes
`"protocol": { "name": "x402", "version": 1 }`; `edge/x402-core.js:322` emits `x402Version:
PROTOCOL_VERSION` = 1 with `maxAmountRequired` (`:328`) and reads the `X-PAYMENT` request header
(`:360`).

**x402 V2 launched 2025-12-11** (`x402.org/x402-v2-launch/`) and is the version in
`specs/x402-specification-v2.md`. V2 changed the wire format substantially:

| Concern | v1 (shipped) | v2 (current standard) |
|---|---|---|
| Challenge location | response **body** | base64 **`PAYMENT-REQUIRED`** response header |
| Client payment | **`X-PAYMENT`** header | **`PAYMENT-SIGNATURE`** header |
| Settlement result | `X-PAYMENT-RESPONSE` | **`PAYMENT-RESPONSE`** header |
| Amount field | `maxAmountRequired` | **`amount`** |
| Network id | free-form (`"base-sepolia"`) | **CAIP-2** (`"eip155:8453"`) |
| `resource` | a string URL | a **`ResourceInfo` object** (`url`, `description`, `mimeType`, `serviceName`, `tags`, `iconUrl`) |
| Extensibility | — | `extensions` object |

V2's launch note says the reference SDKs stay backward-compatible with V1, and Coinbase's migration guide
tells servers to accept **both** header families. So v1 is not dead — but shipping v1-only in 2026-08 on a
surface whose entire pitch is being the well-formed, agent-legible option is the wrong side of that
compatibility bargain. The cheap, correct shape is to **emit v2 and accept both** request headers.

### Finding 2 — the accepted payment payload matches **neither** v1 nor v2 (the load-bearing one)

`edge/X402.md`'s "How to pay" step 2 instructs a client to build
`{ x402Version, scheme, network, resource, amount, payer? }`.

That is not the protocol's `PaymentPayload` in either version:

- **v1** (`x402-specification-v1.md:130-165`): `{ x402Version, scheme, network, payload }` where
  `payload` is a `SchemePayload` — for the `exact` scheme, an **EIP-3009 signed authorization**
  (`signature` + `authorization{from,to,value,validAfter,validBefore,nonce}`).
- **v2** (`x402-specification-v2.md` §5.2): `{ x402Version, resource, accepted, payload, extensions }`,
  `payload` again carrying `signature` + `authorization`.

The shipped shape carries **no signature and no authorization at all** — it is an unsigned assertion that
a payment happened, with a top-level `amount` field neither version defines there.

Two consequences, and the second is why this matters more than a spec-pedantry ticket:

1. **No real x402 client can pay this API.** Every reference SDK builds the protocol payload; it would be
   rejected by our `verifyPayment()` for missing the fields we invented, and our documented payload can
   only be produced by hand-writing against `edge/X402.md`.
2. **No real facilitator can verify it.** A facilitator's `/verify` takes
   `{ x402Version, paymentPayload, paymentRequirements }` where `paymentPayload` is the **spec** type.
   `edge/x402-core.js` POSTs our shape instead, so a live facilitator would reject it on schema. Since the
   gate fails closed, the effect is not a leak — it is that **`X402_MODE=live` can never succeed**. The
   paid path, as merged, cannot transact even after the human does every human-owned leg correctly.

This is not disclosed in `edge/X402.md`'s residue list, which discusses the *absence of settlement* and
*replay* but presents the payload itself as "the x402 payment payload".

### Finding 3 — `/mcp` answers with the HTTP shape; x402 defines an MCP transport

`edge/X402.md` states, deliberately and with a rationale, that `POST /mcp`'s `tools/call` for a paid tool
"gets the SAME 402 shape at the SAME HTTP status — not a JSON-RPC-wrapped error".

`specs/transports-v2/mcp.md` defines the opposite, normatively: a paid tool called without payment MUST
return a **JSON-RPC result** (HTTP 200) with `isError: true`, carrying the `PaymentRequired` object in
**both** `structuredContent` **and** `content[0].text`; payment arrives in `params._meta["x402/payment"]`
and settlement is echoed in `_meta["x402/payment-response"]`.

An x402-aware MCP client — including Cloudflare's own `withX402Client` from the announcement this whole
pillar is built on — looks in `structuredContent`/`content[0].text` and will not find payment
requirements where we put them. An HTTP 402 out of a JSON-RPC endpoint also breaks plain MCP clients,
which expect a JSON-RPC envelope.

The repo's own reasoning ("the resource being purchased is the underlying REST route regardless of which
transport reached it") is coherent but is a claim about *pricing*, not about *signalling*, and the
protocol answers the signalling question differently.

## Hypothesis

We believe emitting x402 **v2** (while accepting v1 request headers), using the protocol's real
`PaymentPayload` type, and answering `/mcp` with the MCP transport's own shape will make the paid surface
**actually transactable** by an off-the-shelf agent — which is the difference between a payment layer that
exists and one that works. Confidence: **supported** for the mechanism (all three are documented wire
formats read raw from the standard, and the divergences are mechanically checkable); **guess** for demand
(unchanged from 234 — nobody has measured agents paying for railed DeFi data).

- **Instance of**: the agent-pillar chain 224 → 227 → 228 → 234, and specifically the class *"we built
  against the announcement instead of the specification"* — the same class 234's own blindspot pass would
  have caught had the standard been read before the build rather than after the merge.
- **Class closed by this item**: no. It fixes conformance for the routes that exist. It does not add a
  conformance test that would catch the NEXT protocol revision — see Acceptance for the weakest guard
  that would.

## Change

Smallest change that makes the surface transactable:

1. **Emit v2, accept both.** Build the `PaymentRequired` object per `x402-specification-v2.md` §5.1
   (`x402Version: 2`, `resource` as a `ResourceInfo`, `accepts[].amount`, CAIP-2 `network`, `extensions`)
   and return it in the base64 **`PAYMENT-REQUIRED`** header. Keep a body copy — the HTTP transport spec
   says response bodies are "a server implementation concern", and the house `rails` block must stay on
   every response with a body. Accept **`PAYMENT-SIGNATURE`** (v2, canonical) and **`X-PAYMENT`** (v1,
   compatibility), v2 winning when both are present.
2. **Use the real `PaymentPayload` type.** Validate the protocol's fields (`accepted` /
   `payload.signature` / `payload.authorization`), not an invented flat shape. Delete the hand-rolled
   shape from `edge/X402.md` in the same commit — a doc teaching a non-protocol payload is worse than no
   doc.
3. **`/mcp` uses the MCP transport shape**: JSON-RPC result, `isError: true`, `PaymentRequired` in both
   `structuredContent` and `content[0].text`, payment read from `params._meta["x402/payment"]`. Build
   both fields from ONE object serialised once so they can never drift.
4. **Facilitator call carries the spec type** so a real facilitator could answer it. Settlement itself
   stays out of scope (234's residue decision stands — money movement is human-owned).

## Acceptance criteria

- [ ] The 402's `PAYMENT-REQUIRED` header base64-decodes to an object asserted against the **spec's own
      canonical example**, not against our reading of it: decode the verbatim base64 example from
      `specs/transports-v2/http.md` (committed as a fixture with provenance: URL + date) and assert our
      object carries every top-level key and every `accepts[0]` key that the spec's example carries.
      Anchoring on the protocol's own artifact is what makes this conformance rather than a lookalike.
- [ ] Payload validation accepts the spec's `PaymentPayload` and REJECTS the old flat shape — with a
      negative case per missing protocol field, each failing for a **distinct** reason.
- [ ] `/mcp` paid-tool-without-payment returns the MCP-transport shape; `structuredContent` and
      `content[0].text` are asserted **byte-identical** after `JSON.stringify`.
- [ ] Both request header names accepted; `PAYMENT-SIGNATURE` wins when both present.
- [ ] **Guard over the class, not the instance**: a test asserting the emitted `x402Version` equals a
      single declared constant AND that the constant matches the version in the committed spec fixture —
      so the next protocol revision fails a test instead of being discovered by a future reader. State
      honestly in the notes that this catches a version bump, NOT arbitrary schema drift within a version.
- [ ] Non-vacuity: mutate the emitted version, the payload validator, and the MCP shape separately →
      each goes RED alone → restore byte-identically (`md5sum`) → GREEN.
- [ ] Ships with the gate still dark; no credential, address, or payout config in the diff.
- [ ] `edge/X402.md`, `edge/MCP.md`, `edge/API.md` updated in the same commit; no doc left describing the
      superseded shape.
