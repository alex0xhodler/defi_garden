# 201 — the 768px lens: explainer (HIGH tier)

## Goal in one line

CLAUDE.md says the product "must be flawless at **360/768/1280px**". Two of those three widths were
audited. This item adds the third — and discovers, on the way, that adding it naively would have measured
nothing at all.

## The intuition

Think of the audit as a camera on a track with two fixed positions: phone (360px) and desktop (1280px).
Every tick it photographs the product from those two spots and reports what it sees. Tablet — the width
where a layout is *neither* stacked-mobile *nor* full-desktop — has never been photographed.

Now the part that makes this more than a chore. The camera has a light meter (`checkResponsive`: "does
anything overflow the viewport? is the primary CTA actually inside the frame?"). The meter is built to
work at any width — it reads the surface's own `s.width` throughout. But every one of its five triggers
is wired shut above 360px:

```js
if (s.width <= 360) await checkResponsive(page, s, findings, '.pool-card');
```

So if you simply parked the camera at 768px, it would take the picture with the meter switched off. The
render would come back clean — not because the layout is clean, but because nothing measured it. That is
the item-166 vacuous-green failure mode, and it is why this ships as two legs that are useless apart.

## Why 768px is a real third state, not an interpolation

Measured across all three stylesheets, evaluating every width-conditioned `@media` block at each width:

| stylesheet | width-media blocks | active @360 | active @768 | active @1280 | @768 but off @360 | @768 but off @1280 |
|---|---|---|---|---|---|---|
| `style.css` | 34 | 14 | 12 | 20 | **4** | **8** |
| `planner-styles.css` | 12 | 12 | 3 | 0 | 0 | 3 |
| `pool-detail-styles.css` | 2 | 2 | 2 | 0 | 0 | 2 |

Sized honestly, because the honest version is the useful one: **no block is 768-only** (measured: zero in
all three files). What is unique at 768 is the *co-activation* — four `min-width` blocks switch on while
eight `max-width` mobile blocks are still on. Concretely:

- `style.css:653` — the `.container { max-width: var(--container-md) }` branch. 768px is **the only one of
  the three audited widths where `md` wins**: at 360 the `sm` branch applies, at 1280 the `min-width:1024px`
  `lg` branch overrides.
- `style.css:3931` / `:4029` — `.theme-toggle` and `.language-toggle` become `position: fixed` at
  ≥641px, the second offset `calc(20px + 200px)` from the right edge. In a 768px viewport that is two
  floating overlays occupying a third of the width, while every `max-width: 768px` mobile rule is
  simultaneously active. That is exactly the overlap/clip class `checkResponsive`'s ancestor-clip
  assertion exists to catch, at a width where it has never been allowed to run.

## What changed, in reading order

**1. `audit-app.js` — leg A, five one-token edits** (`:3346 :3378 :3432 :3477 :3622`)

`if (s.width <= 360)` → `if (s.width <= 768)` at all five `checkResponsive` call sites, plus the stale
"at 360px" comment inside the function corrected to "at the surface's own width" (the code already meant
that; only the comment lied).

Provably non-regressive: the only widths in the file were 360 and 1280. `360 <= 768` keeps every existing
360px surface's check byte-identical; `1280 <= 768` is false, so every desktop surface keeps having no
responsive check. No existing surface changes behaviour — the edit only opens the door for leg B.

A `responsive: true` opt-in flag was considered and **rejected**: the gate is a width predicate, widths
are the policy, and a flag would let some future 768px surface silently opt out of the one check this
item exists to enable.

**2. `audit-app.js` — leg B, five surfaces** appended strictly *after* `plan-bloom-dark`, so no existing
`surfacesCovered` entry moves or is renamed (the 162/164/200 convention):

`pool-detail-768` (the north-star surface), `grid-768`, `landing-768`, `planner-768`, `plan-bloom-768`.
URLs are reused byte-for-byte from their existing siblings rather than retyped (164's precedent). No
dark/ko flag — this item is the width lens only. No new budget knob, for spec 200's recorded reason:
five *fixed* surfaces are not a sampled population, and `--only` plus the existing time-budget guard
already give a caller control.

**3. `test_audit_768_lens.js`** (new) — two layers, mirroring `test_audit_funnel_lens.js`. Source-level
assertions that can never be skipped: the five literals with exact name/url/kind/width, appended after
`plan-bloom-dark`; none is `kind: 'static'`; **all five call sites read `<= 768` and zero read `<= 360`**
(the leg-A regression guard — the assertion that keeps leg B non-vacuous); and, parsed generically from
the surfaces array rather than by name, the property that **every kind — pool/grid/landing/planner/bloom —
has ≥1 surface at width 768**, so a future edit that drops one without replacing its coverage fails here.
Then one skip-tolerant real-Chromium `runAudit({ only: ['landing-768', 'pool-detail-768'] })`, with only
the `runAudit()` call inside the catch and every assertion outside it (the 160 lesson: a check that cannot
go red is not a check).

**4. `test_audit_funnel_lens.js` — one token.** See the next section; this is the interesting part.

## The deviation, and why it is recorded rather than smoothed over

The first draft of `specs/201.md` contained two acceptance criteria that could not both be satisfied:
criterion 2 demanded zero `s.width <= 360` occurrences, and criterion 6 demanded that backlog 200's
`test_audit_funnel_lens.js` keep passing **unmodified** — while that test asserts the landing call site as
a *verbatim source literal* containing `<= 360`. Leg A changes exactly the line it quotes.

The build agent implemented leg A as specified, hit the red, and **reported it as a spec conflict instead
of resolving it on its own** — declining both available shortcuts: weakening leg A to keep an old test
green (which would have left a real `<= 360` in the file), and quietly editing the guardrail. That was the
right call, and it is why the conflict is written down here.

Resolution, applied by the operator as a spec amendment: the literal moves with the line it quotes —
`<= 360` → `<= 768`, one token, in one assertion. The assertion's *intent* ("the landing driver has a
responsive check against `.landing-search-submit`") is unchanged and still enforced. What makes this a
co-move rather than a loosened guardrail is proven, not asserted: `git diff test_audit_funnel_lens.js`
shows a single changed line, the file's other 11 assertions pass untouched, and the assertion was shown to
still go red when the call site it guards is removed.

## Two proofs that matter more than the green checkmarks

**Non-vacuity — the check really executes at 768.** `checkResponsive`'s ancestor-clip branch was forced to
always fire, and a real Chromium render of `landing-768` produced:

```
{ surface: "landing-768", viewport: "768px", check: "responsive", severity: "P2",
  detail: ".landing-search-submit has zero-area box at 768px (ancestor-clipped)" }
```

`768px` in both the viewport label and the message — the check ran at the new width. Mutation reverted,
diff confirmed byte-identical.

**Red-proof — the new test can fail.** One call site reverted to `<= 360`; the test went red on two
independent assertions (`expected exactly 5 call sites reading "s.width <= 768", found 4` and
`expected 0 occurrences of "s.width <= 360", found 1`), then green again on revert.

## The honest null result

The full audit run found **zero findings on all five new 768px surfaces**. The `.container`/fixed-overlay
risk that motivated the lens did not trip on this run. That is a measured null on a five-surface sample,
not a clean bill of health for tablet — the point of the item is that such a defect is now *reachable at
all*, on the north-star surface and the whole conversion funnel, on every future tick. Spec 200's rule
applies: had something been found, it would be filed with severity and left for the next item, because
fixing a defect inside a detector item destroys the positive control.

## A number that turned out to be wrong, and what it revealed

The spec predicted `surfacesCovered` 60 → 65. The real run reported **82**. The prediction was not merely
off — it inherited its baseline from the **committed** `signals/audit-findings.json`, which does not
contain backlog 200's five surfaces at all, i.e. that committed file was already stale relative to `main`
before this item touched anything. A live total also mixes in non-deterministic per-tick rotation entries
(`pool-detail:<uuid>`, `static-page:<path>`), so it was never a certifiable number.

The criterion was amended to the deterministic one: the fixed default-surface-list length **23 → 28**,
proven by a programmatic surface-name array diff against an isolated `origin/main` worktree — baseline
plus exactly five appended names, no rename, no reorder.

## The compound step

`playbooks/detector-signal-coverage.md` gains one subsection under its existing fourth (LENS) axis —
**"The check exists, has a call site, and is still gated shut"** — UPDATED in place, not duplicated. 200's
paired trap was "the driver has no check for the condition." This is the next costume down, and it survives
200's own remedy: the check is there, the call site is there, the body is generic, and the trigger predicate
still excludes the value you are adding. It carries the two rules that fall out (ship the gate and the
surfaces as one item; widen the predicate rather than adding an opt-in flag), the rule that non-vacuity for a
lens must be proved *at the new lens value*, and the co-move rule for a prior test that quotes the line you
are changing.

## Process note: verifier attempt 1 was a FAIL, on this item's own paperwork

Criteria 1–6 passed under evidence the verifier generated itself — its own worktree parser, three adversarial
mutations of the new test, a non-vacuity proof built on a *different* mutation site than the build used, and
its own red-proof of the co-move. It failed the item on scope: the playbook change above was sitting modified
in the tree while the notes' "final diff" line, written earlier in the session, did not list it — a false
accounting, caught by `git diff --name-only`. Bookkeeping (BACKLOG row, LOG entry) was also still missing.
Both are fixed, and the failure is left in the record rather than smoothed away, because the lesson is
reusable: **a diff disclosed in prose is not disclosed** — regenerate the hand-off list from
`git diff --name-only` at the moment of hand-off.
