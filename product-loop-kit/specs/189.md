## The finding

`generate-sitemap.js:242` defines its own `getPoolType(pool)` — a **fork** of the product's pool-type classifier, with
three lists of 8/7/7 protocols and four categories. The product's single source of truth is `getPoolTypeShared`
(`PoolDetail.js:47`, **spec 130**, whose header comment reads verbatim *"SINGLE SOURCE OF TRUTH … do not fork a second
copy of this classifier"*): six categories, ~25/34/28/9/16 protocol lists, plus RWA → Yield-Derivatives → poolMeta-lending
precedence. `app.js:161` delegates to it (`const getPoolType = (pool) => getPoolTypeShared(pool)`), and it is what
`app.js:1847/1936/2036`'s `poolTypeMatch` actually filters on.

Measured this run on the 736-pool committed snapshot — the two classifiers disagree on **90 pools = 12.2%**, every
disagreement in the same direction (the generator over-assigns to `Yield Farming`):

| generator says | product says | pools |
|---|---|---|
| Yield Farming | RWA | 31 |
| Yield Farming | LP/DEX | 27 |
| Yield Farming | Lending | 16 |
| Yield Farming | Yield Derivatives | 10 |
| Yield Farming | Staking | 6 |

The generator emits `?token=<T>&poolTypes=<CAT>` URLs into `sitemap-category-*.xml`, gated by item 013's quality rule
(`≥ SITEMAP_MIN_QUALIFYING_POOLS` = 2 pools at `≥ SITEMAP_MIN_TVL` = $10M, non-anomalous) — but it counts those pools with
the **fork**, while the page the URL opens filters with the **product classifier**. Simulating the real token-first grid
filter (`app.js:2028-2062`: `symbolMatchesToken` substring on `symbol`, `getPoolTypeShared` equality, `tvlUsd >=
DEFAULT_MIN_TVL` = $10M, `tvlUsd > 0`) over all 114 committed category URLs:

- **8 of 114 (7.0%) render ZERO pools** — the "no yields found" empty state, on URLs we submit to Google:
  `?token=WBETH&poolTypes=Yield%20Farming`, `SUSDS`, `USDY`, `SAVAX`, `BEAT`, `XMR`, `SIERRA`, `ECR` (all in
  `sitemap-category-Yield-Farming.xml`).
- **3 more render exactly 1** (`OSETH`, `OUSG`, `RLUSD`) — below the ≥2 bar the gate itself promises.
- All 8 dead + 3 thin live in the one category file the fork over-fills; `Lending` (36), `LP/DEX` (13) and `Staking` (1)
  are clean today, which is luck, not correctness — the fork can misfile in their direction the moment DefiLlama adds a
  protocol on one list but not the other.

This is item **173**'s bug class (*"a page whose primary link lands on an empty grid"*) and item **188**'s bug class (*"the
URLs we submit to Google that no code path can render"*), on the surface neither of them covered.

### Why none of our own checkers caught it

Because all three consumers of the taxonomy inherit the same fork. `generate-llms.js:884-887`'s `gridLinkPoolCount()` and
`audit-app.js:1028-1034`'s `countQualifyingPools()` each `require('./generate-sitemap.js').getPoolType` — the comment in
`generate-llms.js:845` even calls it *"the one classifier"*. So items 175/180/181/184's link-integrity gates and the daily
`audit-app.js` `link-target-integrity` check all score these 8 URLs as live: they ask the fork whether the fork's own
output is right. Fourth instance of the class 166/183/185 each recorded — **a checker that shares the bug it should
catch**. Fixing the fork at its single definition site repairs all three consumers with no change at any call site.

### Second defect, same root: the generator knows 4 of the product's 6 categories

`generate-sitemap.js:543` hardcodes `['Lending','Staking','LP/DEX','Yield Farming']`. The product's own nav taxonomy
(`app.js:114-121`, `CATEGORY_TABS`) is **Lending / Staking / LP-DEX / RWA / Yield Derivatives** (+ All), and both extra
values are real `getPoolTypeShared` outputs that `poolTypeMatch` filters on correctly. So **41 pools (31 RWA + 10 Yield
Derivatives)** can never earn a category URL, and — worse — under a de-forked classifier they would silently *lose* the
(wrong) Yield-Farming URL they have today. Fixing the classifier alone would strip 8 tokens of every category URL; fixing
classifier **and** taxonomy together keeps every token represented under its honest category.

## The fix

**Leg A — de-fork the classifier (`generate-sitemap.js`).** Replace the local `getPoolType` body with the product's
`getPoolTypeShared`, extracted from `PoolDetail.js` at require time via the repo's established `vm`-extraction pattern
(item 084's `extractParser`, `test_translations_fallback.js`, `test_qualifier_fix.js`): read `PoolDetail.js`, slice from
`const LENDING_PROTOCOLS` through the close of `function getPoolTypeShared`, evaluate in a `vm` context, cache the
function at module scope. The exported name **stays `getPoolType`** so `generate-llms.js`, `audit-app.js` and
`generate-token-pages.js` pick up the correction with **zero call-site changes**.

If extraction fails, **throw** a single actionable Error naming `PoolDetail.js` and the two anchors — do NOT fall back to
the old lists. A silent fallback is how this bug survived: the CI pipeline going loudly red is strictly better than three
checkers quietly re-adopting a wrong taxonomy. (The generator already fails loudly on a DefiLlama fetch error; this is the
same posture.)

**Leg B — complete the taxonomy.** Extend `generate-sitemap.js:543`'s `categories` list and `categoryUrlMap` to the
product's six-category set, adding `RWA` → `RWA` and `Yield Derivatives` → `Yield%20Derivatives`. The file naming
(`sitemap-category-<safeCatName>.xml` → `sitemap-category-RWA.xml`, `sitemap-category-Yield-Derivatives.xml`), the index
entry, and `cleanupStaleSitemaps()` are all already generic over the written-filename list — verify, don't rewrite. The
013 quality gate applies unchanged, so a new category file only appears if some token clears ≥2 qualifying pools in it.

**Leg C — regenerate the SEO artifacts** (`npm run sitemap && npm run generate:llms`) and commit the regenerated files.
Never hand-edit them (CLAUDE.md + NORTH_STAR risk policy).

Measured net effect of A+B on the committed snapshot (simulated this run, before any code change):

| | today (fork, 4 cats) | after (shared classifier, 6 cats) |
|---|---|---|
| category URLs emitted | 114 | **116** (15 removed, 17 added) |
| URLs rendering 0 pools | **8** | **0** |
| URLs rendering 1 pool | 3 | **0** |
| pools in a category with no sitemap file | 41 | **0** |
| per category | L36 · S1 · LP13 · YF64 | L38 · S2 · LP20 · YF49 · RWA3 · YD4 |

Four tokens (`OSETH`, `SDAI`, `SOL`, `RLUSD`) end with no *category* URL because their honest per-category count is <2 —
that is item 013's gate working as designed, not a de-indexing: each keeps its `?token=` entry in
`sitemap-tokens-all.xml` and its chain-sitemap entries. **Net URL count goes up (+2), nothing is `noindex`'d, no route,
`app.js`, `home.html`, `vercel.json` or trust-rail constant is touched, and every removed URL is one that renders an empty
or sub-gate grid.** Same reasoning the human resolved for 148 and the loop applied for 188: *which* URLs we submit is item
013's stated purpose.
