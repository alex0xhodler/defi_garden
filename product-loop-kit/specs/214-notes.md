## Attempt 2 (verifier: FAIL, 6/7 — AC7 unmet)

### The finding
The independent verifier found AC7's parenthetical false: `analytics.js:352-361`
`trackPerformance(metric, value, context)` forwarded only `metric_name`, `metric_value`,
`metric_category`, `page_context`, `connection_type`, `is_slow_device` into `this.track(...)`.
`context.source` and `context.pools_count` — passed by both `app.js` call sites — were silently
dropped before reaching Mixpanel, for every `data_load_time` event this codebase has ever
emitted (not just the new pool-arrival path). Attempt 1's test (k) spied on
`Analytics.trackPerformance` itself, one hop before this drop, so it proved the call site
(`app.js`) was correct but could not and did not prove the criterion — that the *delivered*
event distinguishes source. A test that passes against a version of `analytics.js` that drops
`source` proves nothing about AC7.

### Why this is closing an acceptance criterion, not scope creep
AC7 reads: "existing `data_load_time` perf event distinguishes `source: 'snapshot'` vs `'live'`
on pool arrivals." That is a claim about the event as tracked, not about the call site. Given
`trackPerformance`'s pre-fix behavior, AC7 as written could never be made true without touching
`analytics.js` — no amount of correctness in `app.js`'s call arguments changes what
`trackPerformance` forwards. The verifier's instruction was explicit on this point, and the
blast radius is small and checked: `grep -rn "trackPerformance("` over the repo (excluding
node_modules/min/compiled) returns exactly 3 hits — the definition and the two `data_load_time`
call sites (`app.js:1117`, `app.js:1152`), both of which already pass `{ pools_count, source }`.
No other caller of `trackPerformance` exists, so forwarding these two additional keys cannot
affect any other event.

### What changed

**`analytics.js`** (`trackPerformance`, ~line 352) — additive only, explicit keys, guarded:
```js
trackPerformance(metric, value, context = {}) {
  const payload = {
    metric_name: metric,
    metric_value: value,
    metric_category: this.categorizePerformanceMetric(metric),
    page_context: context.page || 'unknown',
    connection_type: navigator.connection ? navigator.connection.effectiveType : 'unknown',
    is_slow_device: this.isSlowDevice()
  };
  if (context.source !== undefined) payload.source = context.source;
  if (context.pools_count !== undefined) payload.pools_count = context.pools_count;
  this.track('performance_metric', payload);
},
```
- No existing property renamed, removed, or reordered — existing saved Mixpanel reports keep
  working byte-for-byte on the fields they already read.
- `source`/`pools_count` forwarded explicitly, never via a wholesale `...context` spread — a
  blind spread of `context` risks colliding with reserved/`$`-prefixed Mixpanel props if some
  future caller's context object happens to carry one.
- Included only when present (`!== undefined` guard) rather than unconditionally, so the many
  other `trackPerformance` call shapes in this codebase (any future non-`data_load_time` caller
  that doesn't pass `source`/`pools_count`) don't start emitting `source: undefined` /
  `pools_count: undefined` into events that never had those keys before. Test (k) asserts this
  choice indirectly by checking the exact keys/values on the delivered payload for both paths;
  I did not add a separate assertion for a hypothetical third caller since none exists in this
  codebase (see blast-radius grep above).
- Cannot throw on a missing/odd `context`: the function signature already defaults
  `context = {}`, and the two new lines only read a property off that object — no chained
  access, no calls into anything that can throw. This preserves the trust-sensitive
  choke-point guarantee the analytics-regression-triage playbook requires (044/096 precedent: a
  throw here breaks every event).
- `analytics.js` has **no minified twin** — confirmed via `ls` (only `analytics.js` exists,
  no `analytics.min.js`) and via `grep -n analytics minify-assets.js test_minified_assets.js
  test_compiled_assets.js`, all empty. `home.html`/`plan.html` both load `analytics.js` directly
  (`<script defer src="analytics.js">`), not a compiled/minified variant. So no artifact
  regeneration was required or performed for this file. Ran `node test_minified_assets.js` and
  `node test_compiled_assets.js` anyway as a sanity check (below) — both pass unchanged,
  confirming `analytics.js` sits outside that pipeline and nothing else needed touching.
