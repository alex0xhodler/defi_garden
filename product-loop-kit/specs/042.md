# 042 — Audit + selectively re-enable disabled `app.js` analytics calls

Status: promoted from BACKLOG (score 6.5, effort S) to READY on 2026-07-12, evidence-backed per this spec.

## Evidence this spec is built on

`reports/2026-07-11-sota-growth.md` flagged 7 `Analytics.*` calls disabled at the call site in `app.js` (`trackFilterChange` x4, `trackFiltersReset`, `trackFilterCombination`, `trackNavigation`) plus two `// TODO: Re-enable with proper safety checks` placeholders on search-input analytics, explicitly noting: *"the disable reason is unknown — needs git-blame/history investigation before re-enabling (could be a prior incident, not just an oversight)."* This spec does that investigation (full, unshallowed history — the checkout started shallow and was unshallowed to do this) and documents the findings that unblock the build.

### Root cause, traced

1. `a9b8550` (2025-08-21, "hotfix: disable all analytics tracking to fix render errors") disabled *every* `Analytics.track*` call app-wide to fix `'Cannot read properties of undefined'` errors breaking rendering.
2. `adc8fd7` (same day, "feat: implement simplified analytics tracking approach") re-enabled the safe ones (pool views, performance, errors, page views) but explicitly kept two categories disabled by name: *"Remove problematic real-time search input tracking"* and *"Removed complex filter combination tracking that caused crashes."* This is the real, specific reason — not a generic oversight.
3. `eff82dda` same day fixed a syntax slip introduced by (2).

Those three commits are the entire history of the disable — nothing since has touched it (confirmed via `git log -S"Analytics disabled" -- app.js`, only these three hits, an unrelated `013` sitemap commit's "new file" diff is `app.js` being re-added to a squashed history segment, not a second disable event).

### Why it's safe to re-enable now (code-level, not a guess)

`app.js` has been substantially rewritten since Aug 2025. At every one of the 7 disabled call sites today, the value passed to `Analytics.*` is a **plain object literal built fresh from React state at the call site**, never a possibly-undefined value:

- `trackFilterCombination(activeFilters, filteredPools.length)` (app.js:1230) — `activeFilters` is a literal `{ selectedChain, selectedToken, minTvl, minApy, selectedPoolTypes, selectedProtocols }` built two lines above. The *exact same object* is already passed live, today, to `Analytics.getFiltersActiveCount(activeFilters)` on the line directly above the disabled call (app.js:1228) — proof by an already-running canary that this object never crashes `Analytics.*`.
- `trackFiltersReset(previousFilters, filteredPools.length)` (app.js:2005) — same literal-object pattern.
- `trackNavigation('pool-detail', 'search', 'back_button')` (app.js:2198) — three string literals, no object at all.
- `trackFilterChange(...)` x4 (app.js:2257, 2280, 2304, 2320) — each passes a freshly-built `fullFilterState` object literal with every field explicitly set (never spreads an unknown/possibly-undefined value).

`analytics.js`'s implementations (`serializeFilters`, `getFiltersActiveCount`, `calculateFilterEffectiveness`) all read properties directly off their `filters` parameter (e.g. `filters.selectedChain`) — this throws only if the parameter itself is `undefined`/`null`, never for a missing/falsy field. Every disabled call site supplies a real object, so this class of crash cannot recur here.

The two `// TODO: Re-enable` placeholders (app.js:1166, 1869) are for the *original* real-time keystroke-level `trackSearchInput` hook that `adc8fd7` removed outright (not commented — deleted) in favor of tracking at search completion instead. That completion-based tracking already ships today via `Analytics.trackSearchSuccess` (app.js:1764) and `Analytics.trackSearchAbandonment` (app.js:1967) — confirmed live in `signals/2026-07-11.md` (`search_success 50, search_abandonment 4` in the last 14d). The keystroke-level hook was a deliberate, superseded design choice, not an outstanding gap — **out of scope for this spec**, the TODO comments are stale and left as-is (removing stale comments that reference no live code is a separate, unrelated cleanup — not bundling it here to keep the diff surgical).

## Change

Uncomment the 7 disabled `Analytics.*` calls in `app.js`, restoring them to fire exactly as originally coded (no logic changes, no new fields):

1. `app.js:1230` — `trackFilterCombination(activeFilters, filteredPools.length)`
2. `app.js:2005` — `trackFiltersReset(previousFilters, filteredPools.length)`
3. `app.js:2198` — `trackNavigation('pool-detail', 'search', 'back_button')`
4. `app.js:2257` — `trackFilterChange('pool_type', poolType, filteredPools.length, fullFilterState)`
5. `app.js:2280` — `trackFilterChange('protocol', protocolFriendlyName, filteredPools.length, fullFilterState)`
6. `app.js:2304` — `trackFilterChange('min_tvl', tvlValue, filteredPools.length, fullFilterState)`
7. `app.js:2320` — `trackFilterChange('min_apy', apyValue, filteredPools.length, fullFilterState)`

## Acceptance criteria

1. All 7 calls uncommented, byte-identical to their pre-disable form (only the `// Analytics disabled: ` prefix removed) — no new parameters, no new events invented.
2. `test_smoke.js` (Playwright, real Chromium, both router paths, 3 viewports) passes with zero `pageerror`/console errors — this is the direct regression test for the exact failure mode (`'Cannot read properties of undefined'` breaking render) that caused the original disable. This is the load-bearing acceptance check, not a nice-to-have.
3. A live-interaction Playwright pass on `?token=USDC` (or similar) that actually exercises each re-enabled path — toggle a pool-type filter, toggle a protocol filter, change min-TVL, change min-APY, trigger "reset filters", open then back-button out of a pool-detail view — with zero thrown errors and the corresponding Mixpanel `track()` call observed to fire (stub/spy `mixpanel.track`, since no live Mixpanel project is reachable in this sandbox).
4. Full existing test suite (`npm test`) still green; no unrelated file touched.
5. Diff stays surgical: `app.js` only, 7 one-line uncomments. No touch to `analytics.js`, no touch to the two stale `TODO: Re-enable` search-input comments (documented as out-of-scope above, not silently dropped).

## Risk tier

LOW — analytics instrumentation is a named LOW-tier example in NORTH_STAR.md's risk policy, diff is ~7 lines (uncomments only), no new dependencies, no trust-rail/canonical/router/SEO-surface touch. The one reason to double-check rather than wave through: this app.js is the sacred parameterized-URL surface, so the render-error regression test (criterion 2) is mandatory, not optional, despite the LOW tier.
