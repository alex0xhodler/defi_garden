# Spec 179: the hub-link surface is dead on `/` and absent on `/plan.html`

Status: written by the build loop 2026-07-30 (the BACKLOG row carried no spec file — written first from
documented evidence, per the loop's no-spec rule, and committed in the same PR as the code).

## Evidence (all of it already in the repo — nothing here is new investigation)

Source: BACKLOG row 179 (filed by item 176's browser-lane triage, "out of its scope, filed rather than
silenced"), `test_footer_hub_links.js` header + case (b2), `style.css:2580-2591`, `home.html:137-148`,
`landing.js:356-367`, spec 045 (static crawler hub links) and spec 086 (analytics-mode dedup).

### Finding (a) — two copies of the hub links on the default route, one of them dead

- Spec 045 put a static `<footer class="seo-hub-links">` with `<a href="/tokens">` + `<a href="/chains">`
  in `home.html`'s raw markup (`home.html:325-329`) so crawlers reach the hub pages without executing JS.
- Spec 086 found that in **analytics** mode the app renders its own `<footer class="app-footer">` carrying
  the same two links, `position: fixed; bottom: 0; z-index: 100` (`style.css:2515-2526`) — which occludes
  the static block (last element in normal flow). The fix was
  `html[data-app-mode="analytics"] .seo-hub-links { display: none }` (`style.css:2589`), mirrored as
  render-blocking inline critical CSS in `home.html:148` (item 131, to kill a first-paint duplicate flash).
- The **2026-07-15 landing pivot** then gave landing mode its own `<footer class="app-footer">` with the same
  two anchors inside `.app-footer-hub-links` (`landing.js:356-367`) — structurally the identical arrangement
  analytics mode has. The 086 hide rule was never extended to `data-app-mode="landing"`.
- Net effect on bare `/` (the default route): **two** `/tokens` + `/chains` link pairs in the DOM; the fixed
  footer occupies the last ~69-84px of the viewport at every scroll offset, so the static pair can never be
  clicked. `style.css:2586`'s own comment — *"Planner mode has no fixed `.app-footer`, so the static links
  stay visible + clickable"* — predates landing mode and is now false about the default route.
- `test_footer_hub_links.js` case (b2) already anticipated this: it asserts the static markup's
  **presence**, explicitly *"not that it is visible/clickable"*, and notes the assertion "keeps holding if
  the block is later hidden with CSS".

### Finding (b) — `/plan.html` has no hub-link surface at all

- `grep -c seo-hub-links plan.html` = **0**. `plan.html` is a separate 102-line static file, not served
  through `home.html`, with no `data-app-mode` attribute and no `.app-footer` (`grep -c app-footer
  planner.js` = 0 — the planner renders no footer of any kind).
- `/plan.html` is real, indexed SEO surface: `<meta name="robots" content="index, follow">` with a
  self-canonical (`plan.html:12-13`), emitted into `sitemap-main.xml` at priority 0.9
  (`generate-sitemap.js:421`), and named 5×/4× in `llms.txt`/`llms-full.txt`.
- So one of the product's two faces publishes **zero** internal links to the `/tokens` and `/chains` hubs
  that specs 045/086 exist to de-orphan. Item 176 briefed a `/plan.html` case for
  `test_footer_hub_links.js`, the builder found it red, and the case was deleted as "a requirement invented
  in error" rather than shipped permanently-red — correct for 176's scope, and the reason this row exists.

## The BACKLOG row's open question, and why it does not block

The row asks: *"extend the hide rule to landing mode, or keep both for the crawler surface and accept the
duplication?"* This is answered by evidence already in the repo, not guessed:

1. **The precedent is exact.** Analytics mode is the same situation (app renders a fixed footer carrying the
   same links) and was resolved by hiding the static block. Landing mode differs in no relevant way. Doing
   the opposite here would make the same condition produce opposite behaviour on two routes.
2. **The crawler purpose is not harmed, and this is checkable rather than assumed.** Non-JS crawlers never
   get `data-app-mode` (set by the IA router at runtime), so the raw anchors stay reachable — the rationale
   already recorded at `home.html:137-148`. A JS-executing crawler renders landing mode and sees the same two
   anchors **visible** in `.app-footer`. Either way the internal links survive, so this is not SEO deletion
   (NEVER list) — an acceptance criterion below asserts both halves.
3. **"Keep both" is not a fix.** It leaves a permanently unclickable element on the default route, which is
   the defect the row filed.

Recorded for the human anyway: leg A is one CSS selector in two places and is trivially revertible if you
want the duplication back.

## Non-goals

- No change to `landing.js`, `app.js`, `planner.js` render logic, or to the IA router's mode computation.
- No change to what any mode's own `.app-footer` renders.
- No new component, class or style — leg A extends an existing selector, leg B reuses `home.html`'s existing
  markup and the existing `.seo-hub-links` styles.
- No generated surface regenerated (`tokens/`, `chains/`, `ko/`, `sitemap*.xml`, `llms*.txt` untouched).

## What to build

### Leg A — extend the 086 dedup rule to landing mode

- `style.css:2589`: selector becomes both modes, e.g.
  `html[data-app-mode="analytics"] .seo-hub-links, html[data-app-mode="landing"] .seo-hub-links { display: none }`.
- `home.html:148` inline critical CSS: the **same** selector, byte-consistent with the style.css rule (the
  existing comment demands "Keep this selector identical").
- Update the two now-false comments (`style.css:2583-2587`, `home.html:137-147`) to say what is true after
  this change: analytics **and** landing render their own fixed `.app-footer` with these links, so the static
  block is superseded there; planner mode (`?goal=…` on `/`, and `/plan.html`, which sets no
  `data-app-mode`) has no fixed footer, so the static links stay visible and clickable there.

### Leg B — give `/plan.html` the static hub-link surface

- Add to `plan.html`, after `<div id="planner-root"></div>` and outside it, the same static footer
  `home.html:325-329` carries (identical markup, identical class, comment pointing at spec 045/179).
- The planner mounts into `#planner-root`; the static footer is outside it, so React never touches it —
  the same arrangement `home.html` uses.
- i18n: the raw anchors ship the EN strings (crawler surface, matching `home.html`), and the planner
  localizes them after mount from the **existing** keys `footerBrowseTokens` / `footerBrowseChains`
  (`translations.js:188-189` EN, `:910-911` KO) so a `?lang=ko` planner does not show English link text.
  No new translation keys. If localization is implemented in `planner.js`, keep it a few lines, guarded
  (missing element or missing `t` must never throw), and run it where the planner already reacts to a
  language change so `?lang=ko` and a live language switch both land.

## Acceptance criteria (rendered product behaviour — Playwright driving the real UI)

Extend `test_footer_hub_links.js` (already registered in `test:serial`, browser lane). Every new case must be
proven non-vacuous by mutation (revert the rule / delete the markup → that exact case reddens, then restore
byte-identically).

1. **A1 — bare `/` has exactly one visible hub-link pair.** With fixtures routed as the file already does:
   `a[href="/tokens"]:visible` count === 1 and `a[href="/chains"]:visible` count === 1, and the visible one
   is inside `.app-footer .app-footer-hub-links`.
2. **A2 — the hide happens at first paint, from the inline critical CSS.** On bare `/`, *without*
   `applyPrintStylesheets`, `getComputedStyle('.seo-hub-links').display === 'none'` and
   `document.documentElement.dataset.appMode === 'landing'` (mirrors the existing pool-detail case (e)).
3. **A3 — crawler surface intact.** The existing case (b2) still passes: both static anchors present in the
   DOM on bare `/`; plus an fs-level assert that `home.html`'s raw source still carries both anchors (the
   existing case (d)).
4. **A4 — analytics mode unchanged.** The existing cases (a), (c), (e) still pass unmodified.
5. **A5 — `/plan.html` renders the hub links, visible and clickable.** Navigate to `/plan.html`, wait for the
   planner to mount, `applyPrintStylesheets`, then: `.seo-hub-links a[href="/tokens"]` and
   `a[href="/chains"]` are **visible**, and a real Playwright click on "Browse tokens" (Playwright refuses to
   click an occluded target — this is the non-occlusion proof) navigates to `/tokens`. No page errors beyond
   the existing `IGNORABLE_ERROR_PATTERN`.
6. **A6 — `/plan.html` raw source carries both anchors** (fs-level, crawler surface).
7. **A7 — KO planner shows KO link text.** `/plan.html?lang=ko` renders the static anchors with
   `토큰 둘러보기` / `체인 둘러보기` (the existing KO keys), while the raw file still carries EN (A6).
8. **A8 — nothing else moved.** `git diff origin/main` is empty for `app.js`, `planner-styles.css`,
   `landing.js`, every `generate-*.js`, `tokens/`, `chains/`, `ko/`, `sitemap*.xml`, `llms*.txt`,
   `package.json`; `APY_SANITY_LIMIT` / `DEFAULT_MIN_TVL` byte-identical; no page or sitemap entry deleted.
9. **A9 — the changed CSS ships in the minified assets the pages actually load.** `plan.html` and
   `home.html` load `style.min.css`; `npm run minify` must be re-run and the regenerated `*.min.css` /
   `*.min.js` committed (backlog 053 rule: edit the source, never the minified file). `test_minified_assets.js`
   / `test_css_minified_render.js` must pass.
