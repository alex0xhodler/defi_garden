# Spec 181: the SEO CTA gate cannot tell a code defect from population drift — so it is red for reasons no diff can fix

## Evidence

`test_seo_cta_targets.js` (in `test:serial`, i.e. the merge gate) has been red on `main` on every day since
item 173 landed. The BACKLOG row filed it as *"7 token pages have a dead primary CTA again — 173's fix does
not self-heal against pool-population drift"* and asked the load-bearing question: **the daily SEO regen
should have either dropped these pages or refreshed them — find out why it did not.**

### 1. The regen is not retaining stale pages. It wipes and re-mints, every bake.

`generate-token-pages.js:986-991` — before writing anything, the generator deletes **every** `*.html` in the
output dir, then writes only the tokens `rankTopTokens()` returns from that run's live fetch:

```js
  // Clean stale pages first so tokens dropped by the gate (030) / renamed slugs
  // don't linger from a previous run. Only *.html is removed …
  if (outDir !== process.cwd()) {
    fs.readdirSync(outDir).forEach(f => { if (f.endsWith('.html')) fs.rmSync(path.join(outDir, f)); });
  }
```

`rankTopTokens()` (`:192-197`) applies the eligibility floor on that same fetch — `if ((p.tvlUsd || 0) <
MIN_POOL_TVL) return;` with `MIN_QUALIFYING_POOLS = 1` (`:62`). A token with zero pools ≥ $100K at bake time
therefore **cannot** get a page, and its previous page is already deleted. The three lifecycle candidates the
BACKLOG row listed (page retained when its pool set empties · `MIN_QUALIFYING_POOLS` evaluated only at mint
time · the regen skipped them) are all **falsified**: there is no mint-time-only predicate, and the CI run
that shipped item 174 cleared the then-red gate to `38/38` on the plain lane (`LOG.md`, 2026-07-29, item 174).

### 2. The dead set is not decaying pages. It is pages **oscillating** across the floor.

Four independent live measurements, four different dead sets, and **no page appears in all of them**:

| when (UTC) | source | dead CTAs | members |
|---|---|---|---|
| 2026-07-29 ~10:40 | PR #332 (item 177) pre-existing-red baseline | 2 / 2217 | `kvcm`, `ripe` |
| 2026-07-29 ~23:50 | item 175 run, isolated `origin/main` worktree | 7 / 2186 | `ankravax`, `gitc`, `mchc`, `n3xt`, `wmetax`, `zeal`, `zro` |
| 2026-07-30 ~01:14 | item 180 run, `origin/main` worktree | 5 / 2186 | subset of the above |
| 2026-07-30 03:2x | **this run**, live fetch, 16,019 pools | **8 / 2186** | `cate`, `cnx`, `gitc`, `hahype`, `mchc`, `n3xt`, `wmetax`, `zro` |

`kvcm` and `ripe` (07-29 morning) share **zero** members with tonight's set. `ankravax` and `zeal` were dead
at 23:50 and are **alive again** now — nothing was regenerated in between.

### 3. Why: the mint predicate is a hard threshold with zero margin, sampled once a day.

Best live pool TVL for the 175 baseline's seven, measured this run against a live 16,019-pool fetch
(`MIN_POOL_TVL` = $100,000):

| token | best live pool TVL | distance from floor | state |
|---|---|---|---|
| `ANKRAVAX` | $100,682 | **+0.7%** | alive again |
| `ZEAL` | $107,959 | +8.0% | alive again |
| `GITC` | $99,481 | **−0.5%** | dead |
| `WMETAX` | $99,652 | **−0.3%** | dead |
| `ZRO` | $95,890 | −4.1% | dead |
| `MCHC` | $92,977 | −7.0% | dead |
| `N3XT` | $21,866 | −78.1% | dead (genuine decay) |

Five of seven sit within **7%** of the floor; two are within **1%**. Re-running the generator's own
`rankTopTokens()` on tonight's live data mints `ANKRAVAX` and `ZEAL` and drops the other five — i.e. the
generator agrees with the gate at every instant; the two are just **read at different instants**.

### 4. And the bake interval is ~24h, so a page is stale for up to a day by construction.

`.github/workflows/sitemap-update.yml` is `cron: '0 2 * * *'`; GitHub actually dispatches it ~05:20 UTC
(runs `30424747605` 05:19, `30330972196` 05:12, `30240806141` 05:48 — all `success`, the workflow is
healthy). Its `push` trigger fires only on a `paths:` list, which does **not** include `generate-llms.js` or
`audit-app.js`, so the 175/176/180 merges (07-29 19:44 → 07-30 01:14) triggered no regen. At 03:20 UTC today
the committed estate is from the 07-29 bake and today's bake has not run yet.

### 5. The consequence, which is the actual defect worth fixing

The gate's pass condition is **"zero pages whose CTA returns 0 pools against live data read now"**. That
condition is not a function of the repository's contents — no diff can make it green, and no diff can make it
red. It has already cost three consecutive runs a manual pre-existing-red baseline (items 175, 177, 180, each
re-deriving it in an isolated worktree), and `playbooks/pre-existing-red-triage.md` exists partly because of
it. A gate that is red for reasons unrelated to every diff trains readers to skip it — and item 173's real
regression class (1,749 dead CTAs, 79.5%) would arrive as the same word, `FAIL`, as tonight's 8 (0.37%).

## Hypothesis

We believe **splitting the gate's verdict into a contract class (always fatal) and a drift class (bounded and
reported)** will **make `test_seo_cta_targets.js` a gate that only reddens for repository-caused defects,
while still catching item 173's regression class at 80× its budget** because the two classes have different
causes: a wrong/missing `minTvl`, a malformed href or a CTA pointing at another page's entity is decided
entirely by generator code and is invariant to live data, whereas emptiness at the correct floor is decided
by DefiLlama's TVL feed between bakes and is invariant to generator code. Confidence: **validated-pattern** —
the four measurements above show the drift class churning its entire membership within 24h with no code
change, and item 174's regen clearing it to 38/38 with no code change either.

Two rejected alternatives, recorded because they are the obvious ones:

- **Mint with margin / hysteresis** (only mint a token whose best pool clears, say, 1.15 × `MIN_POOL_TVL`).
  Reduces the flap rate but cannot remove it, makes the generator stateful (it would have to read the
  pre-wipe directory to avoid dropping pages that qualify today), and *does* shrink future SEO surface —
  which is the NEVER-list question item 148 sat blocked on for five runs. Not worth that cost for a class
  that self-heals every bake.
- **Bake more often** (`cron: '0 */6 * * *'`). Cuts the dead window ~4× and is one line — but every bake is a
  commit to `main` and therefore a Vercel deployment, and the 2026-07-13 standing decision exists precisely
  because the free-tier deployment quota was exhausted. Rejected on that decision, not on merit.

Neither is needed for the user-facing half: the app's own behaviour when `?token=X` resolves to nothing is
**item 133** (BLOCKED on a human decision) and PR #332's *"leg C"*. This item must not pre-empt it.

## Change

`test_seo_cta_targets.js` only. Classify every page it scans, then decide:

1. **`contract` — always FAIL, at any count.** The CTA is missing, is not a valid URL, lacks its own
   `?token=`/`?chain=` param, or carries `minTvl` ≠ `MIN_POOL_TVL` (imported from
   `generate-token-pages.js`, never re-typed — the 159 rule). **New sub-check:** the CTA's param value must
   belong to the page it is on (`tokenSlug(paramValue)` === the page's basename). Verify this holds for all
   2,186 pages today *before* asserting it; if any page legitimately disagrees, report the set and leave the
   sub-check off rather than shipping a red gate (176's precedent).
2. **`stale` — always FAIL.** A page whose CTA is dead **and** whose own visible generation date
   (`<p class="note">Last updated <Month D, YYYY></p>`, rendered by `renderLastUpdatedHtml`, the same string
   as its `dateModified`) is more than **2 days** older than today. Two days allows one missed bake. This is
   the assertion that would actually catch the lifecycle failure the BACKLOG row hypothesised — a page whose
   pool set emptied and that the regen then failed to drop — and drift cannot produce it, because drift
   resolves at the next bake.
3. **`drift` — bounded, reported, not fatal below budget.** CTA well-formed, correct floor, page fresh, 0
   live pools. Print each one with its best live pool's TVL and its signed distance from the floor (so a
   reader can see oscillation vs decay at a glance), and **FAIL if the drift count exceeds 1.0% of scanned
   pages**. Budget derived from measurement, not invented: worst observed is 8/2186 = 0.37%; 1.0% is ~2.7×
   that, and item 173's 79.5% clears it by 80×. The budget and its derivation are stated in the test's
   header comment and in its output line.

The test keeps its existing anti-vacuity rails byte-for-byte: no `POOLS_FIXTURE` + no fresh cache + failed
live fetch still throws (never a silent pass), and `data/pools-snapshot.json` is still refused.

**Self-checks (the non-vacuity proof, and a permanent guard):** before the live scan, run the classifier and
the verdict function over synthetic in-memory page HTML + synthetic pool sets covering: healthy → PASS ·
missing `minTvl` → FAIL(contract) · wrong floor → FAIL(contract) · foreign param value → FAIL(contract) ·
malformed href → FAIL(contract) · dead + stale date → FAIL(stale) · dead + fresh date, under budget → PASS
with a drift report · dead + fresh date, over budget → FAIL(drift). Any self-check not behaving aborts the
run. This proves each class can go red without mutating a single committed page.

**Explicitly OUT of scope:** `MIN_POOL_TVL`, `DEFAULT_MIN_TVL`, `APY_SANITY_LIMIT` and every other rail
(byte-untouched) · both page generators (byte-untouched — no page is added, dropped, or re-rendered) · the
workflow's cron cadence · the app's empty-state behaviour (item 133 / PR #332 leg C) · `audit-app.js`'s
level-3 checker (item 175's, a different surface and a different population).

## Measurement

Metric: **the gate's own signal-to-noise** — number of runs whose `test_seo_cta_targets.js` red is caused by
the diff under test, versus by live drift. Baseline: 0 of the last 3 runs (175, 177, 180 all baselined it as
pre-existing). Window: 14 days of loop runs. Decision rule: **keep** if no run in the window has to
hand-baseline this file as a pre-existing red *and* the drift line is present in the output (proving the
measurement was not simply removed); **revert-candidate** if a genuine dead-CTA regression ships without the
gate reddening. No isolable funnel metric — this is gate integrity under the 2026-07-23 pre-traffic quality
mandate, not a growth change.

## Risk tier (builder's guess — verifier assigns independently)

**HIGH.** It changes the pass condition of a file in the merge gate, which is where a wrong edit weakens
every later verdict (items 166 and 176 are the precedents, both HIGH on exactly this ground). Not on the
NEVER list: no rail moved, no page or sitemap entry deleted, no credentials, no out-of-scope dir.

## Territory notes

- T1 — The generator and the gate use *different* match semantics, and the gate's is deliberately wider:
  `rankTopTokens` splits `pool.symbol` on `[-_/\s]` and matches components (`tokenSymbols`, `:132`), while
  the test does a case-insensitive substring (`symbolMatchesToken`, mirroring `app.js:833`, which is what the
  app actually does). Substring ⊇ component, so the test can never count *fewer* pools than the generator saw
  at the same instant — which is why every dead CTA is provably a time difference, never a semantics
  difference. Do not "fix" this by aligning them; the test must mirror the app, not the generator.
- T2 — The CI fixture is `generate-pools-snapshot.js --seo-out`, a **$1,000**-floored raw transient
  (`:305-308`), not `data/pools-snapshot.json` ($10M, trust-railed). Both generators apply their own $100K
  floor on top. So the fixture cannot be the source of the drift, and the test's refusal to accept
  `data/pools-snapshot.json` stays correct.
- T3 — `chains/` pages go through the same code path in this test and must be classified identically; the
  chain match is exact `pool.chain` equality (`app.js:1872`). Tonight's dead set is all-token, but the chain
  surface oscillates the same way (item 173's table: Cardano 33 pools at $100K, 0 at $10M).
- T4 — `tokens/index.html` and the A–Z hub pages are excluded by `listPages()`/`skippedNoCta` already; the
  new classifier must not start counting them (today: `0 skipped`, because every scanned page has an
  app-bound CTA — assert the skipped count stays 0 rather than assuming it).
