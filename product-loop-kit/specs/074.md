# 074 — Fix critical fast-xml-parser vulnerability (v4 → v5 major bump)

Promoted by the 2026-07-13 build loop (no READY items existed). Evidence is
documented, not invented:

## Evidence

- `specs/003-notes.md` ("Out-of-scope finding (new backlog candidate, not fixed
  here)", 2026-07-10): `npm audit` reports one **critical** vulnerability in
  `fast-xml-parser@^4.4.1` — a production dependency of the SEO generators —
  and explicitly says "Recommend a new backlog item." Nothing was ever filed.
- Re-confirmed live 2026-07-13 in this session: `npm audit --omit=dev` still
  reports **1 critical severity vulnerability** — `fast-xml-parser <=5.6.0`,
  SIX advisories (entity-encoding bypass via regex injection in DOCTYPE,
  DoS via unbounded entity expansion, XMLBuilder stack overflow, numeric-entity
  expansion bypass / incomplete CVE-2026-26278 fix, falsy-zero expansion-limit
  bypass, XMLBuilder comment/CDATA injection). Fix available: `5.10.0`,
  a breaking major.
- Why it matters here: `generate-llms.js` (XMLParser) and
  `validate-sitemaps.js` (XMLValidator) run in the daily `sitemap-update.yml`
  CI job that regenerates the SEO surface — the guardrail metric NORTH_STAR.md
  says we never trade away. A malfunctioning/DoS-able XML pipeline is a direct
  risk to that surface staying fresh.

## Score: 6.8 (justification)

Not a north-star mover (no funnel step), but: critical-severity supply-chain
finding on the pipeline that feeds the SEO lifeline guardrail; explicitly
recommended for the backlog 3 days ago; small, fully verifiable blast radius
(2 call sites, both trivial API usage). Ranked below funnel/distribution items
by design — it is being built only because no READY item exists.

## Change

1. `package.json` / `package-lock.json`: `fast-xml-parser` `^4.4.1` → `^5.10.0`.
2. Adapt the two call sites **only if the v5 API actually requires it**:
   - `generate-llms.js:12` — `new XMLParser({ ignoreAttributes: false })` +
     `parser.parse(xml)` over our own sitemap-index/urlset files.
   - `validate-sitemaps.js:22,32` — `XMLValidator.validate(xml,
     { allowBooleanAttributes: true })`.
   No behavior change is wanted; a byte-identical output on the same input is
   the goal. No other file may change (no product code, no generated SEO
   output regeneration needed — this parses, it doesn't emit).

## Acceptance criteria

1. `npm audit --omit=dev` reports **0 critical** (and no new ≥high) after the
   bump.
2. `node generate-llms.js` run against the committed `sitemap.xml` +
   sub-sitemaps produces `llms.txt`/`llms-full.txt` whose parsed-URL set is
   identical to the v4 baseline (same URL count, same URLs — timestamps/live
   API numbers may differ between runs ONLY if the run hits the live
   DefiLlama API; prefer comparing the sitemap-parsing stage or holding the
   API response fixed. If the sandbox blocks the API, compare the parse stage
   deterministically and say so — do NOT claim a full-output diff you didn't
   run).
3. `node validate-sitemaps.js` passes on the committed sitemaps, same verdict
   as v4 baseline.
4. Full test chain (`npm test` per NORTH_STAR Commands) green, 5-minute
   foreground timebox per standing decision 2026-07-11; any file that cannot
   run in-sandbox gets the documented-precedent treatment (state it, don't
   hand-wave it).
5. No trust-rail, router, translations, or generated-SEO-file diffs. Diff
   touches exactly: `package.json`, `package-lock.json`, and (only if v5
   forces it) the two call-site files.

## Risk tier (proposed)

HIGH — `package.json` dependencies are explicitly HIGH in NORTH_STAR.md's risk
policy. Not on the NEVER list (no trust-rail weakening, no credentials, no SEO
deletion — this *protects* the SEO pipeline).

## Out of scope

- The `renderAnalyticsBootstrap` `</script>`-breakout guard from
  specs/040-notes.md (separate candidate, separate item).
- Any regeneration of `llms.txt`/sitemaps for commit (CI owns that surface).
- npm engine/tooling upgrades beyond this one package.
