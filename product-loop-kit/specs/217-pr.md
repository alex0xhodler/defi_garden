# 217 — PR explainer (HIGH tier: full walkthrough + quiz)

## Goal

The pool-detail page — the surface NORTH_STAR.md names as the north star — had
its bottom band permanently hidden behind the site footer. A human found it on
an iPhone on 2026-08-03 and sent a screenshot: the hero card's rate-steadiness
sentence sliced mid-word, the footer painted over the rest.

## The intuition

The site footer is **opaque, `position: fixed`, `bottom: 0`, `z-index: 100`**
(`style.css:2513-2524`). An element like that will happily cover your content,
so the design system pays for it once, globally:

```css
.app {
  padding-bottom: 80px;
  /* Space for footer */          <-- style.css:849-853
}
```

That 80px is a promise: *however tall the page is, there is always 80px of
nothing at the end, so the footer has something harmless to sit on.*

One file broke the promise for one page:

```css
.app.pool-detail-view {
  padding: 0;                     <-- pool-detail-styles.css:1066-1068
}
```

`padding: 0` is a shorthand — it sets all four sides, including the bottom. So
on pool-detail, and only pool-detail, the clearance was gone. The view's own
container padding (`20px 16px 16px 16px` at ≤768px) left **16px** against a
footer measured at **58px** (≤768px) and **69px** (1280px). The arithmetic
doesn't work, and it can't be scrolled away: at maximum scroll the last slice
of the page is still underneath the footer, at every viewport, forever.

## What changed, and why this way

**The fix is a deletion.** Not a new value:

```diff
 /* Pool Detail View Override for App */
-.app.pool-detail-view {
-  padding: 0;
-}
+/* Backlog 217: this rule used to include `padding: 0`, which cancelled
+   `.app`'s own `padding-bottom: 80px` (style.css:852, "Space for footer") — ...
```

The obvious alternative was `padding: 0 0 80px`. It was rejected because it
duplicates a constant that already lives somewhere else, and duplicated
constants drift. Deleting the canceller is *strictly equivalent* — but only if
`.app` carries no other padding, so that was verified rather than assumed:
`grep -n '\.app {' style.css pool-detail-styles.css` returns exactly two hits,
`style.css:849` (the padding) and `style.css:5227` (a `transition` rule). One
source of truth, nothing restated.

The sibling rule `.app.pool-detail-view .container { max-width: none; padding: 0 }`
was left byte-untouched — that one does real work and is unrelated.

## Deviations from spec

1. **Criterion (5)'s mechanism.** The spec said "can be scrolled to a position
   where its box does not intersect the footer's". The first draft used
   Playwright's `scrollIntoViewIfNeeded()`, which **failed even with the fix
   applied** — Chromium calls an element "in view" when it is inside the raw
   viewport box, with no idea that an opaque fixed footer is painting over
   exactly those pixels. Replaced with an explicit computed scroll target. A
   strengthening, not a weakening: it proves a clear position exists rather
   than trusting a browser API's opinion.

2. **The verifier failed attempt 1 — on a claim, not on the code.** The notes
   asserted as proven fact that the `garden_cta` CTA "was never occluded to
   begin with." It was never measured; the test computes a clear scroll target
   and jumps to it, so it never looks at the at-rest state. The verifier did,
   and found the opposite. **At 360×780, `scrollY=0`, the entire 47px "Garden
   this pool" button sits behind the footer** (CTA `722.7–769.7`, footer
   `722–780`), and `document.elementFromPoint()` at its lower band returns
   `P.app-footer-hub-links` — the footer *intercepts the click* on the north
   star's own emitter. Clear at 390×844 and 414×896, so it is specific to the
   narrowest width in CLAUDE.md's design bar. Proven pre-existing (identical
   geometry with 217's fix mutated back out). The notes were corrected and the
   defect filed as **backlog 218 (9.0)** rather than absorbed — fixing it means
   changing hero-card layout or footer behaviour, which needs its own spec and
   its own risk call.

3. **A process gap was filed, prompted by the human mid-run** — backlog **219**.
   Both verification mechanisms here read the DOM; `grep screenshot audit-app.js`
   returns zero. That is how a daily "82 surfaces, 0 blocking findings" tick
   coexisted with a footer covering the north-star page. 219 proposes an
   occlusion lens (at rest *and* at max scroll, `elementFromPoint`-confirmed —
   which alone would have caught 217, 218 and the never-ported 179) plus a real
   visual lens.

## Risk

**HIGH**, verifier-assigned independently and agreeing with the builder: a
render-path change on the north-star surface, "when in doubt → HIGH". Not on
the NEVER list — no trust rail touched (`APY_SANITY_LIMIT`, `DEFAULT_MIN_TVL`,
anomaly flags, degen haircut all absent from the diff), no credentials/money,
no SEO surface deleted, no out-of-scope directory — so the 2026-07-10
autonomy-(c) decision applies and HIGH auto-merges after PASS.
