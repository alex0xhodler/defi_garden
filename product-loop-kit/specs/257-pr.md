# 257 — PR explainer

**Item:** 257 · *The north star's own denominator is lossy — a third pool-detail entry path fires no `pool_view`.*
**Spec:** `product-loop-kit/specs/257.md` · **Notes:** `product-loop-kit/specs/257-notes.md`
**Branch:** `claude/loop-257` · **Risk tier:** HIGH (verifier-assigned, against the builder's LOW guess — see below)

## The goal in one line

The north star is a ratio, and its denominator was undercounting: one of the three ways a user reaches
pool-detail rendered the page without telling the instrument.

## What was wrong

`app.js` has exactly three `setCurrentView('pool-detail')` transition sites:

| site | entry path | fired `pool_view`? |
|---|---|---|
| `app.js:1293` | `?pool=<id>` landing (`url_direct`) | yes — `app.js:1332` |
| `app.js:2683` (`handlePoolClick`) | grid card click (`card_click`) | yes — `app.js:2670` |
| `app.js:2787` (`handleCalculateYield`) | the card's "calculate yield" button | **no** |

`handleCalculateYield` does a full pool-detail render (`setDetailPool` → `setCurrentView` → `scrollTo`) and
emitted only `trackPoolClick(pool, 'yield_calculator')`. Two of three paths instrumented.

Confirmed in prod, not just in theory: 2026-08-09 recorded `pool_click` 1, `pool_view` **0** — a pool-detail
page rendered and nothing counted it.

The structural consequence is the part that matters. A `garden_cta` click from a calculator-entered
pool-detail lands in the north star's **numerator** with no matching denominator event, so the CTR
`pool_click{garden_cta, protocol_link} ÷ pool_view` was **not bounded by 1**.

## What changed, in reading order

1. **`app.js` — `handleCalculateYield`** (+16 lines, nothing removed). One
   `Analytics.trackPoolView(pool, { source: 'yield_calculator', … })` call, mirroring `handlePoolClick`'s
   context keys (`search_query`, `selected_chain`, `selected_token`, `protocolCtaPresent`) and its
   `urlDirectPoolViewFiredRef.current = pool.pool;` set. The two pre-existing emit sites are byte-untouched —
   saved Mixpanel reports depend on their payloads.

2. **`test_pool_view_transition_parity.js`** (new, plain lane) — the actual point of the item. It reads
   `app.js` at test time, derives the transition-site set and the emit-site set via a brace-depth walk that
   attributes each occurrence to its enclosing named function, and asserts **set-equality in both
   directions**. A transition with no emit is an undercount; an emit with no transition is a double-fire.
   Neither set is hardcoded, so a *fourth* entry path added next month is caught — across the delimiter axis
   (all three JS string delimiters — single, double, backtick — plus a legal trailing comma, arbitrary
   whitespace/newlines, and an interleaved comment; see "What the verifier found" below for how that axis was
   closed across three verifier rounds) — **with the full, disclosed list of caveats below, not "one honest
   caveat"** (that phrasing was itself an under-claim the second verifier flagged and this revision corrects):
   - **Per-named-function resolution, not per-transition.** A fourth transition added inside a function that
     already owns an emit (e.g. a second `setCurrentView('pool-detail')` inside `App`'s existing anonymous
     effect, or inside `handlePoolClick`) does not change either owner-set, so set-equality alone stays green
     on it — only the plain count assertion (transition count === emit count) catches that shape, because it
     adds a transition without adding an emit. The gate depends on both assertions; neither one subsumes the
     other. Permanently regression-locked (variant B).
   - **Literal spellings that ARE textually addressable but are NOT covered today** (found by the third
     verifier pass, which falsified this doc's earlier claim that the delimiter set was "the FULL extent of
     what a textual scan can address"): an escape-spelled literal (`'pool-detail'`), a line continuation
     inside the literal, and a second argument (`setCurrentView('pool-detail', { replace: true })` — the
     pattern covers a trailing comma, not a further argument). Recorded as known gaps, not closed: each is an
     adversarial spelling absent from this codebase, unlike double quotes and backticks, which occurred
     naturally and are now covered.
   - **Five shapes NOT COVERED by the current scan** — an earlier revision called these "structurally
     uncatchable by any textual/regex scan" and said closing them "would need an AST parser". The third
     verifier pass falsified that too: `.call`/`.apply`/`.bind` and computed-property emits fall to a ~22-char
     regex widening, and the alias/named-constant forms fall to a two-pass textual scan. They are a scope
     choice, not an impossibility. Note an uncaught EMIT shape fails LOUD (transition with no emit → RED),
     not silent. The five: an aliased setter
     (`const setViewAlias = setCurrentView; setViewAlias('pool-detail')`); string concatenation or a computed
     argument (`setCurrentView('pool' + '-detail')`); a named constant
     (`setCurrentView(POOL_DETAIL_VIEW)`); an aliased or computed-property emit
     (`const tpv = Analytics.trackPoolView; tpv(...)`, or `Analytics['trackPoolView'](...)`, or
     `Analytics.trackPoolView.call(this, ...)`); and a nested template literal (a backtick string containing
     another backtick inside its own `${...}` interpolation — verified absent from app.js today, not proven
     absent for all future edits — this last one IS a genuine limit of the char-walk, unlike the other four).
     Closing the remaining four would not require a parser, only more scanning than this item bought;
     `257-notes.md` "Attempt 3" records why `acorn` was not reached for. Disclosed rather than left standing.
   Includes a self-defeat sub-check that mutates an in-memory copy and proves the analyzer reports the gap,
   a relative (not hardcoded) proof that a comment mentioning "trackPoolView" cannot inflate the emit count,
   five permanent regression fixtures locking single-quoted, double-quoted, backtick, and trailing-comma
   transitions plus the same-owner (variant B) resolution limit, and a **positive-control fixture**: a
   correctly-paired new transition+emit in a new function must keep the gate green (added because the second
   verifier proved a prior version of this file could go red on CORRECT code — see below).

3. **`test_pool_view_calculator_path.js`** (new, browser lane) — rendered proof, not source reading. Drives
   the real UI, clicks `.calculate-yield-btn-new`, and spies at `Analytics.track` (the delivered boundary,
   per `playbooks/analytics-regression-triage.md`'s 214 addendum — spying at `trackPoolView` would prove
   only that a helper was called, not that an event shipped). Asserts exactly one `pool_view` with
   `source: 'yield_calculator'` plus the full `enrichPoolData` segmentation set, exactly one `pool_click`,
   and that pool-detail actually rendered so a green run can't be a no-op.

4. **`package.json`** — both files appended to `test:serial` (the single list `run-tests.js` parses;
   `test_test_registry.js` fails on an unregistered test file).

5. **`app.compiled.js` / `app.compiled.min.js`** — regenerated via `npm run compile && npm run minify`.
   `home.html` loads the compiled artifacts, so an un-regenerated build would ship nothing.

## Why a set-equality test and not just the one-line fix

Adding the missing call closes the instance. It closes nothing about the class — the defect was never
"a missing line," it was that **nothing related the two sets**. This is the 212 mirror rule: when a fact must
exist in two places and only one is read at runtime, the other is a mirror and gets an equality test against
the original in the same commit. A hand-typed list of three line numbers would have been the same mistake in
new clothing.

## Deviations from the spec

One, recorded in full in `257-notes.md`: the analyzer is a hand-rolled scrubber + brace-depth walk rather
than an AST parse. `acorn` is reachable only as a transitive dependency of `terser` and is not declared in
`package.json`; depending on it would put this test one `npm update` away from breaking for reasons
unrelated to 257. The scrubber deliberately does **not** blank single/double-quoted string contents (the
first version did, and blanked away the very `'pool-detail'` literal under search); this rests on a stated,
verified assumption that `app.js` has no quoted string literal containing a brace or the substrings
`trackPoolView`/`setCurrentView`. The assumption is written into the test file rather than hidden.

## What the verifier found

Two verifier rounds FAILed this item so far, both on the same underlying pattern: each fix closed exactly the
one variant the previous verifier had demonstrated, no wider. Both are recorded here in full — the audit
trail should show that the gate failed twice and why, not just the final state.

### Round 1 (Attempt 1 → Attempt 2)

The verifier FAILed the first build of this item on the gate's own population criterion: *"a fourth entry
path added tomorrow must fail the gate."* It mutated `app.js` three ways and found the gate blind to one of
them:

- Variant A — a new named function calling `setCurrentView('pool-detail')` (single-quoted), no paired emit
  → correctly caught (RED, 2/4).
- Variant B — a fourth transition added *inside `App`'s existing anonymous effect*, no paired emit → caught,
  but **only by the count assertion** — set-equality alone passed, because the extra transition attributes
  to `App`, which already owns an emit. This is the per-named-function resolution limitation stated above,
  not a new defect; it is now stated explicitly in both this doc and the test's own header comment.
- Variant C — a new named function calling `setCurrentView("pool-detail")` (**double**-quoted), no paired
  emit → **not caught**. `GREEN, 4/4, exit=0.` Root cause: the transition/emit scan was a fixed-spelling
  `String.prototype.indexOf` match on the exact single-quoted, fixed-spacing byte string, so any quote-style
  or whitespace variant was invisible to it — a live gap, since the repo has no eslint/prettier/editorconfig
  enforcing quote style and `app.js` already mixes single- and double-quoted literals.

**Fixed before merge**, all in the test file (`app.js` was not touched — the verifier confirmed the product
change itself was correct):

1. The transition scan is now the regex `/setCurrentView\s*\(\s*(['"])pool-detail\1\s*\)/g` over the
   scrubbed source — quote-style tolerant.
2. The emit scan is now `/\btrackPoolView\s*\(/g` — the mandatory `Analytics.` prefix and fixed-spacing
   assumption are dropped. Explicitly re-verified that the `// … trackPoolView call …` comment near
   `app.js:2788` cannot inflate the count (comments are blanked by `scrub()` before either regex runs; a
   dedicated test asserts this).
3. The self-defeat sub-check's `source: 'yield_calculator'` marker lookup is now the same
   quote-/whitespace-tolerant regex, for the identical reason.
4. Two permanent regression fixtures were added — an in-memory-only variant A (single-quoted) and variant C
   (double-quoted) mutated copy of `app.js`, each a new named function with an un-paired transition — and
   both are asserted caught. Variant C additionally re-runs the *old* fixed-spelling scan against the same
   mutation and asserts it stays unchanged (3→3), proving the new regression case is non-vacuous: it would
   have been invisible under the pre-fix scanner and is caught only because of this fix.
5. The header comment's regex-brace-literal count was corrected: the verifier found **four** brace-containing
   regex literals in `app.js` (`:230`, `:321`, `:474`, `:808`), not the one the original comment claimed. All
   four remain brace-balanced within their own statement, so the scrubbing conclusion survives — only the
   count was wrong.

Net: the transition-site/emit-site counts are unchanged (3 and 3), all pre-existing assertions still pass,
and the file now carries three additional tests (7/7 total, up from 4/4).

### Round 2 (Attempt 2 → Attempt 3, this revision)

The verifier's closing note on Round 1 was the important finding: *"Two attempts have now each closed exactly
the one variant the previous verifier demonstrated — that pattern, not the missing regex character, is the
thing to watch."* Concretely, it FAILed Attempt 2 on three points:

**FAILURE 1 (P1) — the backtick transition, and a second, independent scrubbing bug.** Attempt 2's
`(['"])` alternation was quote-tolerant for `'`/`"` only — the SAME single variant Round 1 had demonstrated
(double-quoted), widened by exactly one character class, no further. The verifier appended a new named
function using `` setCurrentView(`pool-detail`) `` (backtick) with no paired emit: **GREEN, 7/7, exit=0 —
MISSED**, a second time. Root cause was TWO bugs, not one: (a) `TRANSITION_RE` had no backtick branch; AND
(b) independently, `scrub()` (the single scrubber attempts 1-2 used for both the depth-walk and the
pattern-scan) unconditionally blanked template-literal BODIES to protect the brace-depth walk from stray
`{`/`}` bytes inside a template — which also erased a backtick transition's own text before either regex
could see it, so widening the regex alone would NOT have been sufficient. The verifier additionally measured
FOUR more uncaught shapes and required each be either covered or explicitly disclosed: an aliased setter, a
concatenated/computed argument, a named constant, and a trailing-comma call (`setCurrentView('pool-detail',)`
— legal JS, silently missed by Attempt 2's regex, which had no `,?` before its closing `\)`).

**FAILURE 2 (P2) — Attempt 2 introduced a hardcoded population count.** The "comment does not inflate the
count" test attempt 2 added ended with `assert.strictEqual(emitIndices.length, 3, ...)` — hardcoding the
exact population the spec's own Population criterion forbids hardcoding, and directly contradicting the
file's own neighboring comment ("a 4th site added later must still pass"). The verifier appended a
**correctly instrumented** fourth path (transition + real `trackPoolView` emit, same new function) and
measured the gate go **RED, 6/7, exit=1** on this single assertion — a gate that fires on CORRECT code, which
is worse than no gate at all.

**FAILURE 3 (P2) — the PR quiz's Q4 answer was self-contradictory.** Q4 asked for the smallest edit adding an
uninstrumented fourth entry path while still passing every assertion; Attempt 2's answer gave variant B (the
same-owner shape) and then said it "would be caught only by the count assertion" — an edit caught by an
assertion does not pass every assertion. The verifier measured variant B at 6/7, exit=1, confirming the
self-contradiction. (Fixed below — see the quiz section; the corrected answer is the alias/named-constant
family from FAILURE 1's disclosed list.)

**Fixed in this revision** (test and docs files only — `app.js` untouched, confirmed unchanged by md5sum
across all three revisions):

1. `TRANSITION_RE` widened to all three JS string delimiters (the FULL space — see this file's own
   "Exhaustive delimiter enumeration" in the test header, and the "one honest caveat" replacement above) plus
   an optional legal trailing comma: `/setCurrentView\s*\(\s*(['"\`])pool-detail\1\s*,?\s*\)/g`.
2. The single `scrub()` function was SPLIT into two position-preserving scrubbers: `scrubForDepth()` (the
   original behavior — blanks comments AND template-literal bodies, used for the brace-depth walk) and
   `scrubForPatternScan()` (blanks comments only, preserves ALL quoted-string content including backtick
   bodies, used for `TRANSITION_RE`/`EMIT_RE`). This was the second, independent half of FAILURE 1 — widening
   the regex alone would not have fixed the backtick miss, because the scrubber was erasing the text first.
3. Three new permanent regression fixtures: backtick (variant D), trailing-comma (variant E), and the
   same-owner limit (variant B, now locked as an executable fixture rather than only prose) — each proven
   non-vacuous against a frozen copy of the exact Attempt-2 regex (`PREV_ATTEMPT2_TRANSITION_RE`), the same
   way variant C was proven non-vacuous against the Attempt-1 scan.
4. A **positive-control fixture**: a correctly-paired new transition+emit in a new named function is asserted
   to keep BOTH the count check and set-equality green — the direct fix for FAILURE 2, and proof the fix
   holds, not just an assertion that it should.
5. The hardcoded `assert.strictEqual(emitIndices.length, 3, ...)` was replaced with a relative comparison:
   deleting only the comment's own line must not change the emit count, whatever that count is — no absolute
   number appears in the assertion.
6. The five structurally-uncatchable shapes (alias, concat/computed-argument, named-constant, aliased/
   computed-property/bound emit, nested template literal) are now named explicitly in the test file's own
   header comment AND in this document's "one honest caveat" replacement above, each with a one-line reason
   it cannot be caught by a textual scan.
7. Quiz Q4 corrected (see below) to the alias/named-constant family, which genuinely passes every assertion —
   unlike variant B, which the count assertion catches.

Net: the transition-site/emit-site counts are still unchanged on real `app.js` (3 and 3), all prior assertions
still pass, and the file now carries eleven tests total (11/11, up from 7/7). Full transcripts — including the
verifier's exact FAIL output reproduced against isolated fixtures — are in `257-notes.md`'s "Attempt 3"
section.

## What this does NOT close

Stated plainly rather than implied away: the class is closed **for pool-detail only**. The same
transition-vs-emission gap can exist for any other tracked view (`plan-bloom`, the planner steps). Nothing
in this item guards those, and nothing was added for them — a future item should file its own ticket rather
than assume this one covers it.

Also unrecoverable, and not to be papered over: the historical `pool_view` series is a **lower bound of
unknown tightness**. Exactly one missed render is confirmed (2026-08-09). No past number is retro-corrected.

## Measurement

- **Build leg (verifiable now, and green):** the rendered test proves the event fires on the third path.
- **Traffic leg:** gate opens at ≥30 real exercised `pool_view` events; real count today is **0**, day 33.
  Crawler-classified events never count.
- **Decision rule:** this is a correctness fix to a metric definition, not an experiment — kept
  unconditionally. There is no "didn't move" outcome that would justify reverting a denominator.
