# 052 — precompile app.js/PoolDetail.js in CI, drop in-browser Babel

Risk tier: **HIGH** (touches home.html's sacred analytics-conditional block,
adds new runtime dependencies, modifies `.github/workflows/sitemap-update.yml`,
changes the render path for every analytics/SEO page). Full walkthrough below,
per NORTH_STAR.md's HIGH-tier merge process.

## Goal

Analytics/SEO pages (`?token=`, `?chain=`, `?pool=`, every `/tokens/`→app
link) loaded `app.js` (119K) + `PoolDetail.js` (52K) as `type="text/babel"`
and fetched `@babel/standalone` (~2.9MB from unpkg) to transpile them on the
main thread at page load. That's the dominant mobile PageSpeed hit (TBT/LCP/
TTI), and it landed on exactly the pages backlog 011–051 spent effort
optimizing for SEO (`product-loop-kit/reports/2026-07-12-pagespeed.md`). Goal:
serve plain, pre-compiled JS instead — same rendered app, no runtime
transpile step.

## Intuition

Two ideas, in the order they were actually tried:

1. **"Maybe we don't need Babel at all."** The whole codebase already uses
   `React.createElement` exclusively — never JSX (CLAUDE.md). If that's true,
   Babel's transform is a no-op and we can just delete it: load `app.js`/
   `PoolDetail.js` as ordinary `<script>` tags, done.
2. **That was wrong**, but not for the JSX reason. `app.js` and
   `PoolDetail.js` are two separate `<script>` tags in one document, and
   browsers don't give each classic script its own top-level scope for
   `let`/`const` the way they give each *module* its own scope — top-level
   `let`/`const` across sibling classic scripts share ONE lexical
   environment. Both files declare `const { useState, ... } = React` at the
   top. Loaded raw, the second declaration is a `SyntaxError`. Separately,
   `app.js` has a `useMemo` (`autocompleteTokens`) that references a `const`
   (`allAvailableChains`) declared *later* in the same function — with real
   `let`/`const` semantics that's a TDZ `ReferenceError`, not just a JS style
   nit. Babel's default transform was silently downleveling every `let`/
   `const` to `var` (no TDZ, redeclaration is a no-op) — masking both bugs
   the whole time the app shipped as `text/babel`. So the fix isn't "delete
   Babel", it's "replace the browser-side, whole-file Babel transpile with
   the ONE transform it was actually load-bearing for (`let`/`const`→`var`),
   done once in CI instead of on every page load in every visitor's browser."

## What changed, in reading order

1. **`compile-app.js`** (new) — reads `app.js`/`PoolDetail.js`, runs
   `@babel/core` with only `@babel/plugin-transform-block-scoping` (the
   specific let/const→var downlevel), writes `app.compiled.js`/
   `PoolDetail.compiled.js` with a "GENERATED, do not hand-edit" header.
   Exports a pure `transform(file, source)` — string in, string out, no disk
   I/O — alongside the disk-writing `compile(file)`, so tests can verify
   freshness without mutating the tree.
2. **`app.compiled.js`, `PoolDetail.compiled.js`** (new, committed) — the
   generated output. `grep -c "\bconst \|\blet "` returns 0 in both (any
   scope, not just top-level) — every `let`/`const` is downleveled, not just
   the two spots that happened to break `test_search.js`.
3. **`package.json`** — `@babel/core` + `@babel/plugin-transform-block-scoping`
   added to `dependencies` (NOT `devDependencies`): CI's
   `sitemap-update.yml` runs `npm install --only=production`, so the compile
   step needs these as real production deps to be present when it runs.
   New `"compile"` script (`node compile-app.js`). `test_compiled_assets.js`
   added at the front of the `test` chain.
4. **`test_compiled_assets.js`** (new) — asserts (a) both compiled files
   exist and are byte-identical to a fresh `transform()` of current source
   (catches drift or hand-edits to the `.compiled.js` files), and (b)
   `home.html` no longer fetches `@babel/standalone` or sets `text/babel`,
   and loads `PoolDetail.compiled.js` before `app.compiled.js`.
5. **`home.html`** — the `__APP_MODE === 'analytics'` block now loads
   `PoolDetail.compiled.js` → (`onload`) → `app.compiled.js` as plain
   `<script>` tags. No `type="text/babel"`, no `@babel/standalone` fetch, no
   `Babel.transformScriptTags()` polling loop. The `onload` chain matters
   independently of the let/const fix: dynamically-inserted `<script src>`
   tags don't guarantee execution order relative to each other by default
   (Babel's `transformScriptTags` used to guarantee DOM order for us).
   `app.js`'s `App` component does `React.createElement(PoolDetail, {...})`
   when `currentView === 'pool-detail'` — the *initial* view on `?pool=<id>`
   deep links, not just after later navigation — so `PoolDetail` must be a
   defined global before `app.compiled.js` runs, or first render on a pool
   deep link throws. The `__APP_MODE` router logic itself and
   `ANALYTICS_PARAMS` are byte-identical to `main` (verified via direct
   diff, not just by eyeballing the change).
6. **`.github/workflows/sitemap-update.yml`** — added `app.js`,
   `PoolDetail.js`, `compile-app.js` to the push-trigger paths; added a
   compile step right after `npm install`; added the two `.compiled.js`
   files to the commit step's `git add` list. Same pattern as the existing
   sitemap/token-page/chain-page generator steps in that workflow.
7. **`app.js`, `PoolDetail.js`** — untouched. Byte-identical to `main`. They
   stay the unbuilt edit surface; only the loader and the generated output
   changed.

## Deviations from the spec

- The spec's open question asked whether app.js/PoolDetail.js need any
  transform at all, suggesting a possible "reduce to load-as-plain-JS, no
  compile step" outcome if there's no JSX. That path was tried first and
  reverted after `test_search.js` (which mounts the real analytics app
  offline via vendored React) caught the redeclaration collision and the TDZ
  bug described above — both transform-dependent, confirmed by reverting to
  the Babel-active baseline and re-running `test_search.js` clean (20/20).
  Shipped the spec's originally-proposed CI-compile path instead, using the
  one specific transform Babel was actually relying on here rather than a
  full ES5-target preset, to keep the diff to exactly what's load-bearing.
- Full investigation trail: `product-loop-kit/specs/052-notes.md`.

## Known gap (disclosed, not a regression)

`test_smoke.js` — the spec's literal named test for "both router paths
render" — can't complete in this sandbox: `unpkg.com` and
`yields.llama.fi` are network-blocked here (`curl` → `CONNECT tunnel failed,
response 403`), and unlike `test_search.js`, `test_smoke.js` has no local
React-vendoring fallback. Confirmed this is pre-existing, not caused by this
diff, by checking out `main`'s files in this same sandbox and re-running
`test_smoke.js` — identical hang/timeout. The untouched bare `/` planner path
(this diff never touches planner.js or any planner code path) fails
identically, which structurally rules out a regression in the changed
surface. This matches the precedented, already-shipped pattern for
render-path merges on 040/044/045/051 pending backlog 003's smoke gate:
flagged `needs human visual spot-check`.

   - B. React doesn't export `useState` from the UMD build
   - C. Top-level `let`/`const` in sibling classic `<script>` tags share one
     lexical environment per realm, so the second declaration collides
   - D. `PoolDetail.js` loads before React itself is ready

2. Why must `PoolDetail.compiled.js` finish executing before
   `app.compiled.js` runs?
   - A. Alphabetical script loading is a browser requirement
   - B. `app.js`'s `App` component renders `PoolDetail` as its very first
     view on `?pool=` deep links, so the global must already be defined
   - C. `PoolDetail.compiled.js` is larger and should load first for caching
   - D. It doesn't matter — `React.createElement` resolves components lazily

   to `package.json`'s `"dependencies"` rather than `"devDependencies"`?
   - A. CI's `sitemap-update.yml` runs `npm install --only=production`, which
     skips devDependencies, and the compile step needs them present
   - B. devDependencies aren't supported by npm workspaces
   - C. It was arbitrary — either would have worked
   - D. `@babel/standalone` (devDependency) already provides them at runtime

4. What was the actual bug class that Babel's default transform was
   silently masking in this codebase (beyond JSX, which isn't used at all)?
   - A. Missing semicolons causing ASI failures
   - B. Undefined global `t()` translation calls
   - C. `let`/`const` TDZ (temporal dead zone) and cross-script redeclaration
     — both eliminated by downleveling to `var`
   - D. CSS-in-JS syntax not supported by browsers

5. Why does `test_smoke.js` failing in this sandbox NOT indicate a
   regression from this PR?

   - B. It fails identically on `main`'s untouched code (confirmed by
     checking out `main`'s files and re-running it here) and the untouched
     bare `/` planner path fails the same way, both due to `unpkg.com`/
     `yields.llama.fi` being network-blocked in this sandbox
   - C. `test_smoke.js` was deleted in this PR
   - D. The test always exits 0 regardless of failures
