# 100 — PR explainer (HIGH tier)

## Goal
Stop the analytics search box from silently narrowing a chain-only query to a token.
`yields on ethereum` should show **all Ethereum pools**, not just pools whose symbol contains ETH.

## Intuition (the one-paragraph version)
`parseNaturalLanguageQuery` turns free text into `{token, chain, protocol, poolTypes}`. Token detection
runs in two passes. The **primary** pass uses a **word-boundary** regex (`\beth\b`), so `eth` inside
`ethereum` never matches — correct. But there's a **second fallback** pass that uses a plain
**substring** test (`"on ethereum".includes("eth")` → true) to catch tokens embedded inside compound
words. That fallback has a guard list of chain names to reject — but the list only had the **long**
names (`ethereum`, `solana`, `arbitrum`, …), not the **short aliases** (`eth`, `sol`, `arb`). So the
short alias slipped through the guard and got assigned as the token. The chain was still detected
correctly, so the user didn't get an error — they got a quietly wrong, over-narrowed result. That's a
trust erosion on the exact surface (the SEO/analytics search) we're trying to convert into the card
funnel.

## What changed and why (reading order)
1. **`app.js`** — one array in the second token fallback of `parseNaturalLanguageQuery`. The guard
   `const chainNames = ['base','ethereum',...8 long names]` became the full set of **24 `chainAliases`
   keys** (short + long: `eth, ethereum, matic, arb, arbitrum, op, optimism, bnb, bsc, ..., moonbeam, cronos`).
   A comment marks it as needing to stay in sync with the `chainAliases` map (which is declared a few
   lines below and is in the temporal dead zone here, so its keys can't be referenced directly). Because
   this fallback only runs when the primary word-boundary loop already found nothing, excluding these
   aliases can never block a *legitimate* token — a real whole-word token (`usdc on ethereum` → USDC) is
   caught by the primary loop and never reaches the fallback.
2. **`app.compiled.js` + `app.compiled.min.js`** — regenerated (`npm run compile && npm run minify`).
   Prod loads `app.compiled.min.js` via `home.html`, so the source edit is inert until recompiled. Verified
   `moonbeam`/`cronos` are present in both.
3. **`test_parser_chain_token.js`** (new) — extracts the **real** parser from `app.js`
   (`test_helpers_parser.js` `extractParser`, the spec-084 pattern — no inline copy that can drift).
   4 leak-fix asserts + 2 regression asserts. Wired into the `npm test` chain.

## Deviations from spec
- Went **robust** rather than **minimal**: excluded all alias keys, not just the three confirmed live
  offenders (`eth`/`sol`/`arb`), so no future chain re-opens the hole. Argued safe above.
- Left the `t.length >= 3` gate and the fallback's substring mechanism intact (spec out-of-scope) — the
  fix is the guard list, not the matching strategy.

## Risk: HIGH
User-facing behavior change on the analytics search path ("anything user-facing beyond copy/styling" +
"when in doubt → HIGH"). NOT on the NEVER list: trust rails untouched (APY_SANITY_LIMIT / DEFAULT_MIN_TVL /
anomaly / haircut), no credentials/money, no SEO deletion, no out-of-scope dirs, no `?token=`/router
change. Pure query-parsing logic — no visual surface — but logged with the advisory "needs human visual
spot-check" per the pre-003 render-path policy.
