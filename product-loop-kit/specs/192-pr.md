# 192 — PR explainer (HIGH tier: full walkthrough + quiz)

## The goal, in one sentence

The scanner that watches the north-star surface could only ever render **6 of 739** pool-detail pages per
tick, because of a ceiling nobody had measured — this raises it to a measured **32** and gives the run a
clock so a bigger budget can never cost a finished scan.

## The intuition — why this was worth a run

Item 191 (yesterday) raised the rotation's *default* from 2 to 6 and, in doing so, produced the number that
makes this item obvious: it measured **106s at sample 2 and 107s at sample 6**. Four extra rendered pages
cost less than run-to-run noise. Its own comment concluded *"the per-pool render cost is not the
bottleneck."*

But 191 set `DEFAULT_POOL_SAMPLE = 6` **equal to** `MAX_POOL_SAMPLE = 6`, and explicitly put raising the
ceiling out of scope. So the product ended the day in a strange state: the thing limiting how much of the
north-star surface we look at was not the 5-minute budget (39% used), not the render cost (~0.19s/page),
but a constant that had never been derived from anything.

The operator measured before writing the spec — three foreground runs on this checkout:

| `AUDIT_POOL_SAMPLE` | wall-clock | exit | findings |
|---|---|---|---|
| 6 (old default) | 111s | 0 | 1 total, **0 blocking** |
| 16 | 111s | 0 | 1 total, **0 blocking** |
| 32 | 116s | 1 | 3 total, **2 blocking** |

Two things fall out. First, the arithmetic: 26 extra rendered pages cost **5 seconds**. Second — and this is
the part worth pausing on — **the sample-32 run surfaced two blocking findings that the 6-wide rotation had
never once rendered.** Not because the widening broke anything, but because those two pages had never been
looked at. Both were triaged before this spec was written (see below); the point stands either way: at 6
pages a tick, "no findings" was partly a statement about our coverage, not about the product.

## What changed, in reading order

**1. `audit-app.js` — the two constants (`DEFAULT_POOL_SAMPLE` 6 → 32, `MAX_POOL_SAMPLE` 6 → 64).**
The justification lives in the comment block above them, not only in the spec, so the next person to touch
this doesn't have to go find a markdown file to learn where 32 came from. Two deliberate choices:
- **32, not 64**: it is the largest value actually *measured* (116s = 39% of the 300s cap), against this
  item's own ≤180s (60%) target. Picking the ceiling because it is there is the exact mistake this item
  exists to correct.
- **ceiling above default this time**: 191's default==ceiling meant `AUDIT_POOL_SAMPLE` could only ever
  *lower* the sample. 64 is bounded by the same measurement (~0.19s/render → ~122s), so the override can
  now go up as well as down and the next person isn't blocked the way this run was.
191's own reasoning is kept verbatim above the new paragraph, with the one sentence 192 supersedes marked
**SUPERSEDED** rather than deleted.

**2. `audit-app.js` — the wall-clock guard (`AUDIT_TIME_BUDGET_MS`, `FOREGROUND_CAP_MS`).**
The 300s foreground cap had been prose repeated across comments and never a number the code could read;
it is now one constant, and the time budget defaults to it (identity, not an invented fraction). Before
rendering each rotation-picked surface, if the run has already spent its budget, that surface and every
rotation surface after it is skipped. **Only rotation picks are skippable** — the anchor pool-detail block,
prescan-promoted surfaces, and every other named surface (static, text, i18n, planner, landing, bloom) do
not carry the marker the guard checks, so they are structurally unreachable by it. This matters: the guard
exists to protect the run's completion, so it may only ever drop the leg that is explicitly best-effort.

The marker is a real field (`rotationPick: true`) set only where rotation picks are pushed — not an
inference from the surface name. Rotation-picked and prescan-promoted surfaces are otherwise byte-identical
in shape (`pool-detail:<prefix>`, `kind: 'pool'`), so a name-shape guard would have been able to skip
promoted surfaces. The spec's territory notes named this as the most likely way to build the guard subtly
wrong, and it is the reason the marker exists.

**3. `audit-app.js` — the honesty reconciliation (the load-bearing part).**
The rotation state is computed *before* rendering (`buildPoolSurfaces()`) and persisted *after*
(`runAudit()`), which means an unguarded truncation would write "we covered this pool" for a pool that was
never rendered. The coverage number would inflate itself exactly where it is supposed to be honest, and the
error would compound across cycles. So `runAudit()` now strips skipped ids from the persisted `seen` before
writing — **except** ids that were already legitimately seen in an earlier run and merely got re-picked
this run (183's "fill from seen once unseen is exhausted" path); their prior coverage is real and must not
be erased. `poolRotation` gained `renderedCount`/`truncated`/`timeBudgetMs`, and the console's full-pass
line is derived from the **rendered** count, so a truncated run reports the slower true rate rather than
the optimistic planned one.

**4. The tests.** Three new cases for the guard (fires; inert on a normal budget; the honesty round-trip),
one more added after verification (below), plus five fixtures rescaled to interpolate the exported
constants. That rescaling is not cosmetic: `computeRotation()` caps `picked.length` at the candidate count,
so a fixture with 20 candidates and a sample size of 32 passes *for the wrong reason* — not because the
logic is right, but because there weren't enough candidates to tell. The spec pre-authorized this fix at
one named line; four more instances of the identical trap existed and were fixed the same way.

## The verifier caught something real — worth reading

Attempt 1 came back **FAIL, 12/13**. The verifier mutated the reconciliation to delete the "already seen in
a prior run" protection and **every one of the 45 tests stayed green**. The implementation was correct — it
confirmed that separately, by hand — but the shipped test only ever exercised a *fresh* state, where the
correct code and the broken code produce identical output. The spec had called that line the single
highest-risk line of the item, and the test could not have caught its removal.

Attempt 2 added a test that builds a genuinely mid-cycle prior state (4 of 5 candidates already seen, so
the fill-from-seen branch engages), trips the guard so an already-seen pick is skipped, and asserts the
persisted state **keeps** that id while a never-before-seen skipped id stays absent. It goes red on exactly
the verifier's mutation, and only it goes red. The notes' earlier claim that the honesty requirement was
"proven directly" by the original test is corrected there rather than quietly dropped — it had proved one
half of the property.

## Two findings this run originated but did NOT fix

Both came out of the sample-32 measurement, and both were triaged before being written down:

- **The "P0" is a scanner false positive** — the more useful of the two. `pool-detail:3075a746`
  (`sanctum-infinity` INF, Solana, $150M TVL) reported *astronomical value "111…112" (1.11e+40)*. The page
  is correct: that digit run is the tail of `So11111111111111111111111111111111111111112`, the wrapped-SOL
  mint address, rendered as an underlying-token link. `scanNumbers()`'s regex has no left-boundary
  assertion, so it pulls digits out of a base58 address — and its sibling constant `ABSURD_MAGNITUDE_TEXT`
  already carries the fix, added by spec 157 with the note *"do NOT revert to the loose form."* The lesson
  was never ported one surface over. Filed as **row 193**.
- **The P1 contradicts today's own report.** `pool-detail:13392973` (sdai) reported `degraded-cta … kind=defect`,
  while `reports/2026-07-31.md` records the same sdai fallback as the honest, deliberate rendering for the
  one genuinely unreachable pool. One of the two is wrong. Filed as **row 194**, to be diagnosed before it
  is fixed.

**Known cost of this merge, stated up front:** raising the default to 32 puts `3075a746` inside the ordinary
rotation, so the next heartbeat tick will exit non-zero on that false P0 until 193 ships. That is a
documented consequence of widening, not a surprise — and 193 lands with the root cause and the one-line
fix already diagnosed.

## What this does and does not buy

Full pass over the north-star surface: **124 ticks → 24**. That is another constant factor, roughly 5×, and
it is **not closure** — 24 days is still 24 days, and a given pool-detail defect still has single-digit-%
odds of being rendered on any given day. Whether the widened rotation *originates* a P0/P1 inside the 14-day
window is the read that would actually validate the hypothesis, and at these odds **a null result there is
uninformative, not negative.** Real closure is an architectural question (parallel contexts, browser reuse)
that this item deliberately does not answer.

1. The audit run takes ~111s at sample 6 and ~116s at sample 32. Given that, why is `MAX_POOL_SAMPLE` set
   to 64 rather than to 32 — and why is the *default* not also 64?
2. The guard skips rotation-picked surfaces but never prescan-promoted ones, even though both render as
   `pool-detail:<prefix>` with `kind: 'pool'`. What mechanism enforces that distinction, and why would the
   obvious alternative implementation have been a bug?
3. A run is truncated by the time budget and three rotation picks never render. One of those three was
   already in `seen` from an earlier run. What must the persisted `seen` contain afterwards, and what breaks
   if the code strips all three?
4. The verifier deleted one filter from the reconciliation and all 45 tests still passed, yet it also
   concluded the implementation was correct. What exactly was being reported as broken, and why does that
   distinction matter more than it might first appear?
5. The widened run produced a P0 on `pool-detail:3075a746`. Why is that finding *not* evidence that the
   coverage gap was hiding product bugs — and what is it evidence of instead?
