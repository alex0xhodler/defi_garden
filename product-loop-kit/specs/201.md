# Spec 201: 768px — the design bar's third breakpoint has never been rendered, and `checkResponsive` is hard-gated so it never could be

**Promoted by the build loop, 2026-08-01** — `BACKLOG.md` had **no READY item** at pickup (199 and 200,
the last two rows, both shipped earlier today; every other row parses SHIPPED / DONE / PARKED / BLOCKED /
CULLED). Promotion follows build.md's no-READY rule, from documented evidence already in the repo — two
sources, both naming this item:

1. **CLAUDE.md, the repo's design bar, verbatim:** *"Must be flawless at **360/768/1280px** and in dark
   mode."* Three widths are repo law. Two of them are audited.
2. **Spec 200's own "Out of scope" section**, which names it and hands it forward:
   > *"**768px.** CLAUDE.md names 360/768/1280, but the audit's established responsive lens is 360px and
   > `checkResponsive` is written against `s.width` as the single breakpoint. A third width is a separate
   > sizing question with its own render budget."*

200 closed the `dark`/`ko`/360 holes on the funnel. This closes the width hole — and finds, on the way,
that adding a 768px surface alone would have been **vacuous**: the responsive check cannot run above 360px.

## Evidence (all measured in-repo, this session, before any change)

### 1. `768` does not appear anywhere in `audit-app.js`

```
$ grep -c 768 audit-app.js
0
```

Zero hits in 4,257 lines. Every `width:` literal in the file is `1280` or `360` — the full list is
`audit-app.js:2032, 2067, 2157, 2234, 2765, 2860, 2892, 2919-2921, 3780-3803, 3818-3822`. So of the
three widths CLAUDE.md requires to be flawless, **one has a 0% chance of ever being rendered by any
signal**, on every future tick, on every surface — including `pool-detail`, the north-star surface.

### 2. The load-bearing finding: `checkResponsive` is gated to `s.width <= 360` at **all five** call sites

```
audit-app.js:3346   if (s.width <= 360) await checkResponsive(page, s, findings, '.pool-card');
audit-app.js:3378   if (s.width <= 360) await checkResponsive(page, s, findings, '.landing-search-submit');
audit-app.js:3432   if (s.width <= 360) await checkResponsive(page, s, findings, '.gp-chip');
audit-app.js:3477   if (s.width <= 360) await checkResponsive(page, s, findings, '.gp-checkout-cta');
audit-app.js:3622   if (s.width <= 360) await checkResponsive(page, s, findings, '.cta-button-primary');
```

The **function body**, by contrast, is already fully width-parameterized (`audit-app.js:3634-3652`) — it
reads `s.width` for the scroll comparison, for the CTA-box bound and for both message strings, and
contains no `360` literal at all (only a stale comment saying "at 360px"). The generality is already
written; the gate throws it away.

**Consequence, stated precisely:** appending a 768px surface *without* touching the gate would render the
page and assert **nothing about its width** — the surface's only checks would be the width-independent
ones (page errors, number-sanity, dead-ends). That is the item-166 vacuous-green failure mode, and it is
why this item has two legs that ship together.

### 3. 768px is a real, distinct layout state — not an interpolation between 360 and 1280

Measured by evaluating every width-conditioned `@media` block in the three stylesheets at each of the
three widths (script + full output in `specs/201-notes.md`):

| stylesheet | width-media blocks | active @360 | active @768 | active @1280 | active @768 that are OFF @360 | …that are OFF @1280 |
|---|---|---|---|---|---|---|
| `style.css` | 34 | 14 | 12 | 20 | **4** | **8** |
| `planner-styles.css` | 12 | 12 | 3 | 0 | 0 | 3 |
| `pool-detail-styles.css` | 2 | 2 | 2 | 0 | 0 | 2 |

Honest sizing, stated rather than glossed: **no block is exclusively 768-only** (measured: 0 in all three
files). The gap is the *combination* — at 768px, four `min-width` blocks are on **while eight `max-width`
blocks are still on**, a co-activation that occurs at neither audited width. The four:

- `style.css:647` — `@media (min-width: 640px) { .container { max-width: var(--container-sm) } }`
- `style.css:653` — `@media (min-width: 768px) { .container { max-width: var(--container-md) } }` — the
  **`md` container branch, the only width at which it wins**: at 360 the `sm` branch applies, at 1280 the
  `min-width: 1024px` `lg` branch overrides it.
- `style.css:3931` — `@media (min-width: 641px) { .theme-toggle { position: fixed; top: 20px; right: 20px } }`
- `style.css:4029` — `@media (min-width: 641px) { .language-toggle { position: fixed; top: 20px; right: calc(20px + 200px) } }`

The last two are the concrete tablet risk this lens exists to catch: two `position: fixed` controls become
overlays at ≥641px, one of them offset **220px from the right edge of a 768px viewport**, while every
`max-width: 768px` mobile rule is simultaneously active. That is precisely the overlap/clip class
`checkResponsive`'s ancestor-clip assertion was written for — and it has never been evaluated there.

### 4. The surfaces this covers are the north star and the funnel

`pool-detail` is the north-star surface (NORTH_STAR.md 2026-07-23: `pool_click{garden_cta|protocol_link}`);
`grid`, `landing`, `planner`, `bloom` are the arrival → `plan_created` path. Current 768px coverage on all
five: **zero**.

## Hypothesis

The audit reports "responsive clean" while it has only ever evaluated one of the two non-desktop widths
the design bar names. Rendering the north-star + funnel surfaces at 768px, **with the responsive check
actually able to run there**, either (a) surfaces a real tablet-layout defect that 24 clean ticks could
not have seen, or (b) converts an assumption into a measured null on the widths repo law requires. Both
outcomes are worth the ~5 extra renders; neither is reachable today.

## Change

Two legs, shipped together — **either alone is useless** (leg B without leg A is vacuous per evidence 2;
leg A without leg B is a no-op, since no surface exists between 361px and 1279px).

### Leg A — ungate `checkResponsive` (5 one-token edits, `audit-app.js:3346/3378/3432/3477/3622`)

Change each `if (s.width <= 360)` to `if (s.width <= 768)`.

**Provably non-regressive for every existing surface:** the only widths in the file today are 360 and 1280
(evidence 1). `360 <= 768` → every existing 360px surface keeps its check, byte-identically. `1280 <= 768`
is false → every existing 1280px surface keeps having no responsive check. No existing surface changes
behaviour; the edit only opens the door for leg B. Also fix the two stale "at 360px" comments in
`checkResponsive` (`audit-app.js:3635`) to say "at the surface's own width" — the code already means that.

Do **not** introduce a new `responsive: true` flag: the gate is a width predicate today, the widths are
the policy, and a flag would let a future 768 surface silently opt out of the very check this item exists
to enable.

**AMENDED mid-build (2026-08-01), after the build agent surfaced a genuine self-conflict in this spec's
first draft.** `test_audit_funnel_lens.js:~150` (backlog 200's test) asserts the landing driver's call
site as a **verbatim source literal**:

```js
assertT(landingBlock.includes("if (s.width <= 360) await checkResponsive(page, s, findings, '.landing-search-submit');"), …)
```

Leg A changes exactly that line, so the literal goes permanently absent and 200's test goes red. The
first draft's criteria 2 ("zero `s.width <= 360`") and 6 ("`test_audit_funnel_lens.js` still passes
unmodified") were therefore **unsatisfiable together** — the build agent implemented leg A as specified
and reported the red honestly rather than weakening leg A or silently editing a guardrail, which is the
correct behaviour and is why the conflict is recorded here instead of being papered over.

**Resolution: leg A also updates that one literal to `<= 768`.** The assertion's *intent* — "the landing
driver has a responsive check against `.landing-search-submit`" — is unchanged and still enforced; only
the width in its string match was stale, and it was stale precisely because leg A moved the line it
quotes. This is the minimum edit: one token, in one string, in one assertion. **Nothing else in
`test_audit_funnel_lens.js` may be touched** — its other 11 assertions must keep passing untouched, which
is what proves this is a co-move and not a guardrail being loosened to fit.

### Leg C — acceptance test `test_audit_768_lens.js`

Mirror `test_audit_funnel_lens.js`'s two-layer shape (source-level assertions that can never be skipped +
one skip-tolerant real-Chromium integration):

1. **Source layer** (no browser): the five literals exist with the exact name/url/kind/width above,
   appended after `plan-bloom-dark`; none is `kind: 'static'`; **all five `checkResponsive` call sites read
   `s.width <= 768`** and **zero read `<= 360`** (the leg-A regression guard — this is the assertion that
   makes leg B non-vacuous, so it is the load-bearing one); and, asserted as a *property* of the parsed
   surfaces array rather than by name, **every one of the five kinds `pool`/`grid`/`landing`/`planner`/
   `bloom` has ≥1 surface at width 768** — so a future edit that renames or drops one of these without
   replacing its 768 coverage fails here.
2. **Integration layer**: a real `runAudit({ only: ['landing-768', 'pool-detail-768'] })` run asserting
   both surfaces actually rendered and the findings array is well-formed. Per the 160 lesson, **only** the
   `runAudit()` call is wrapped in the skip-tolerant timeout/catch; every assertion sits outside it.

## Acceptance criteria

1. `grep -c 768 audit-app.js` > 0 and the five surface literals match the leg-B table exactly (name, url,
   kind, width), appended **after** `plan-bloom-dark` — proven by a programmatic surface-name array diff
   against an isolated `origin/main` worktree showing **baseline + exactly five appended names**, no
   rename, no reorder (200's proof method, reused).
2. All five `checkResponsive` call sites read `s.width <= 768`; `grep -c 's.width <= 360' audit-app.js`
   returns **0**.
3. **Non-vacuity, demonstrated not asserted:** a real Chromium render of a 768px surface is shown to
   actually execute `checkResponsive` at 768 — e.g. by temporarily mutating the scroll/CTA-bound
   comparison (or injecting an over-wide element) and showing a `responsive` finding appear whose message
   contains `768`, then reverting. Record the exact mutation, the finding text and the revert in
   `specs/201-notes.md`. A 768 surface that renders clean *because the check never ran* is a FAIL.
4. A full `node audit-app.js` run completes with all five new names present in `surfacesCovered`. **AMENDED
   mid-build:** the first draft predicted `surfacesCovered` 60 → 65. That prediction was wrong, and wrong
   for a reason worth recording — it inherited the number from the **committed** `signals/audit-findings.json`,
   which was already stale relative to `main` (its array does not contain backlog 200's five surfaces at
   all, so the committed 60 never described the code at `HEAD`). A live total also mixes in
   non-deterministic per-tick rotation entries (`pool-detail:<uuid>`, `static-page:<path>`), so it is not
   a certifiable number in the first place. The criterion is therefore the **deterministic** one: the
   fixed default-surface-list length moves **23 → 28** (+5, no rename, no reorder), proven by criterion 1's
   worktree diff, and all five new names appear in a real run's `surfacesCovered`. Any product finding the
   new lens surfaces is **filed in the notes with severity, not fixed** (spec 200's rule: fixing a defect
   inside a detector item destroys the positive control — the next item builds the fix).
5. `node test_audit_768_lens.js` passes, and its source layer is shown to be able to go red (mutate one
   call site back to `<= 360`, show the test fail, revert — recorded in the notes).
6. Guardrail: `node test_audit_app.js`, `node test_audit_funnel_lens.js`, `node test_audit_planner_surface.js`
   and `node test_audit_runner.js` all pass — the surface list is shared state and 162/164/200's tests
   assert against it. `test_audit_funnel_lens.js` passes **with exactly the one-token literal co-move
   described in leg A and no other change**, verified by `git diff test_audit_funnel_lens.js` showing a
   single changed line.
7. No product code outside `audit-app.js` is touched (the `test_audit_funnel_lens.js` co-move is a test,
   not product code, and is bounded to one token by criterion 6). No `translations.js` change (no
   user-facing string is added). No new dependency.
8. Bookkeeping in the SAME commit (2026-07-13 rule): BACKLOG.md row 201, `specs/201-notes.md`,
   `specs/201-pr.md`, LOG.md entry.
