# Spec 135: Don't pin the default `minTvl=10000000` into generated URLs

## Evidence
- `updateUrl` (app.js:945) writes `minTvl` to the URL whenever `minTvl > 0`. The
  default floor is `DEFAULT_MIN_TVL = 10000000` (app.js:801), so **every**
  token/chain URL the app generates carries `&minTvl=10000000` even though the
  user never changed the floor.
- On read, `minTvl` is only taken from the param when present:
  `params.has('minTvl') ? parseInt(...) : DEFAULT_MIN_TVL` (app.js:927) — an
  **absent** `minTvl` already resolves to the same $10M default. So writing the
  default is pure noise; omitting it round-trips to identical behavior.
- LIVE EVIDENCE 2026-07-24 (heartbeat `query_id 09fd9fb9`): crawlers are now
  re-walking indexed noisy URLs — 2026-07-23 sessions landed on
  `?token=AVICI%E2%9C%A8&minTvl=10000000` and `?token=INFINIFIUSDC&minTvl=10000000`.
  The pinned default has leaked into externally-held / indexed URLs exactly as
  predicted. SEO-surface hygiene, no longer hypothetical (score 4.5 → 5.5).

## Hypothesis
We believe omitting `minTvl` from the URL when it equals `DEFAULT_MIN_TVL` will
produce cleaner canonical URLs and stop pinning the default floor into
shared/bookmarked/indexed links, because the read path already treats an absent
`minTvl` as the default — so the change is behavior-preserving while removing
noise. Confidence: validated-pattern (mirrors item 077's `?minTvl` clean-URL
work and item's own documented read-path default).

## Change
Smallest version:
- In `updateUrl` (app.js), change the guard from `if (minTvl > 0)` to also skip
  the default: only write `minTvl` when `minTvl > 0 && minTvl !== DEFAULT_MIN_TVL`.
- Recompile + re-minify (`npm run compile && npm run minify`) so the prod bundle
  `app.compiled.min.js` reflects the change (home.html loads the min bundle).

OUT of scope:
- The `DEFAULT_MIN_TVL` value itself stays $10M (trust rail untouched — this only
  changes URL serialization, never the effective floor).
- Non-default floors (e.g. the $10k/$50k "feeling degen" / all-chains presets at
  app.js:3408/3423, or any user-chosen TVL chip) are still written — they are
  `!== DEFAULT_MIN_TVL`.
- No change to the read path (app.js:927), snapshot-eligibility
  (`urlParams.minTvl >= DEFAULT_MIN_TVL`, app.js:1133 — an absent param still
  resolves to the default, so snapshot-first stays eligible), or filtering.

## Open questions
None — the read path already defaults an absent `minTvl` to `DEFAULT_MIN_TVL`, so
omission is provably behavior-preserving. No architecture decision required.

## Territory notes
- Read path: app.js:927 `params.has('minTvl') ? parseInt(...) : DEFAULT_MIN_TVL`.
- Write path (the fix): app.js:945 inside `updateUrl`.
- URL-write effect fires post-initial-load (app.js:2056-2065, gated on
  `!isInitialLoad`); `isInitialLoad` flips false 100ms after first parse
  (app.js:1011), so a plain `/?token=USDC` landing pushes a fresh URL once settled —
  that's the rendered reproduction point.
- Snapshot-first eligibility (app.js:1133) reads `urlParams.minTvl` which already
  defaults to `DEFAULT_MIN_TVL` when the param is absent → omitting the default does
  NOT disqualify the snapshot fast path.
