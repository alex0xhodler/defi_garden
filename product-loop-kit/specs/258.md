# Spec 258: `pool_click`/`pool_view` name the widget, never the surface — the only prod click in 33 days took a three-property join to attribute

## Evidence

**The event, measured (Mixpanel defigarden 4042048):**
- Prod 30d by `source` (`12fdcdad`): `pool_click` = 3 — `garden_cta` 1 (08-07, operator), `undefined` 1
  (pre-123 legacy), **`yield_calculator` 1 (08-09)**. The last is the only prod pool click since 08-07 and the
  only non-operator one on record.
- That event (`c21d823d`): `source=yield_calculator`, `$region=Iowa`,
  `$current_url=https://www.defi.garden/?token=USDC%60`.
- Its pool (`c0c75d6f`): `pool_symbol=USDT`, `pool_project=aave-v3`, `pool_chain=Ethereum`.

**The attribution, which the event could not give up on its own.** `app.js:840`:
```js
const symbolMatchesToken = (poolSymbol, token) =>
  String(poolSymbol).toUpperCase().includes(String(token).toUpperCase());
```
`"USDT".includes("USDC`")` → **false**. A USDT/aave-v3 pool therefore **cannot** be a search result on a
`?token=USDC`` page. The only other grid on that route is `getEmptyStateAlternatives()`'s rescue set
(`app.js:3578`, top-TVL stablecoin pools through the trust rails), rendered by the **same** `renderPoolCard`
and so carrying the **same** `.calculate-yield-btn-new` (`app.js:3048`).

**So the click landed on item 012/072's honest empty state — the rescue surface — and establishing that
required joining three event properties against a matcher function read out of the source.** The event says
`source: 'yield_calculator'`, which is true of a click on a real search result and of a click on a rescue
card alike. `source` names the **widget**; nothing names the **surface**.

**Why this is not a curiosity.** The rescue empty state is the app's answer to the item-133 dead-end class,
and it is reachable from a large share of the indexed estate (any `?token=` with no pool clearing the floor).
Whether it converts is a first-order product question, and today the loop cannot answer it even with an
event in hand.

## Hypothesis

We believe **attaching the rendering surface to every `pool_click` and `pool_view` at the call site** will
make click attribution readable from one property instead of a three-property forensic join, because the
information exists at render time (`renderPoolCard` already knows whether it is drawing results, empty-state
alternatives, or dead-pool alternatives) and is simply discarded. Confidence: **supported**.

- **Instance of:** the same shape as item 252 (*the loop cannot tell its own traffic from demand*) one level
  down — an event whose properties do not carry the distinction the question turns on. Population: every
  `pool_click`/`pool_view` emitted from a `renderPoolCard` instance; three distinct rendering contexts today
  (results grid `app.js:~3048` path, empty-state alternatives `:3578`, dead-pool alternatives `:3591`).
- **Class closed by this item:** **no.** It closes the surface question for pool cards only. The general class
  — *an event property names the component rather than the context* — is open across the app and is **not**
  ticketed here; naming it is the honest move, widening this spec to chase it is not.

## Change

Smallest version that tests the hypothesis:

1. `renderPoolCard` takes (or derives) a **surface** value and passes it through to `trackPoolClick` /
   `trackPoolView`, emitted as a new property (proposed: `surface`, values `results` |
   `empty_state_alternatives` | `dead_pool_alternatives`).
2. `analytics.js`'s `trackPoolClick`/`trackPoolView` forward the key **explicitly and guarded**
   (`if (context.surface !== undefined) payload.surface = context.surface`) — never a `...context` spread
   (`playbooks/analytics-regression-triage.md`, 214 addendum, decision rule).
3. A test asserting the property reaches `Analytics.track` from **each** of the three rendering contexts.

**Explicitly OUT of scope:** renaming or re-valuing `source` (three disjoint values today, saved reports
depend on them — NORTH_STAR's rename decision stands); changing the north-star definition; the missing
`pool_view` on the calculator path (**item 257**, which must land first or concurrently — 258's `pool_view`
leg is untestable on a path that emits no `pool_view`); any surface outside pool cards.

## Acceptance criteria

- [ ] `pool_click` and `pool_view` emitted from a card in the **results grid** carry `surface: 'results'`.
- [ ] The same two events emitted from an **empty-state alternatives** card carry
      `surface: 'empty_state_alternatives'`; from a **dead-pool alternatives** card,
      `surface: 'dead_pool_alternatives'`.
- [ ] Every pre-existing property on both events is byte-identical to before the change (`source`,
      `click_type`, `pool_id`, `pool_project`, `pool_chain`, `total_apy`, position, and the base context) —
      diff the assembled payloads, not the source lines.
- [ ] The set of `surface` values the code can emit is derived at test time from the `renderPoolCard` call
      sites, and the test fails if a call site exists that passes no surface — a fourth grid added later must
      not emit `surface: undefined` silently.
- [ ] Tests: rendered-Playwright, spying at the **`Analytics.track`** boundary (not the helper argument),
      driving all three contexts on the real app — the results grid via `?token=USDC`, the empty state via a
      token with no qualifying pool, the dead-pool state via a dead `?pool=<id>` (the fixture
      `test_dead_pool.js` already builds).
- [ ] **Non-vacuity:** remove the `surface` forwarding from `analytics.js` alone (leave every call site
      intact) → all three assertions must go **RED**; restore byte-identically → **GREEN**. Record both runs
      in `specs/258-notes.md`. This exact mutation is the 214 defect, where correct call sites sat above an
      emitter that dropped the key.
- [ ] Population: the three rendering contexts are enumerated from `app.js` at test time, not hardcoded.

## Measurement

rendered test proves emission — shippable now. · **Traffic-gated question this unlocks (do not conflate with
the build leg):** does the rescue empty state convert? Window opens at **≥30 real** `pool_view` events

the one event that motivated this spec is itself crawler-classified (10 of 10 sessions on 08-09 were
crawler-shaped). · Backstop: gate unopened 60d after ship → close UNEXERCISED. · Decision rule for the build
leg: keep unconditionally (a property that makes an existing question answerable is not an experiment).

**Stated so no one reads this spec as evidence the rescue surface works:** one crawler click is not demand.
The claim here is about the **instrument**, not about the surface's performance, and it is deliberately
independent of who clicked.
