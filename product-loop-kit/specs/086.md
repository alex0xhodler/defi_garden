# 086 — BUG (human ticket 2026-07-14): footer "Browse tokens/chains" links occluded by the fixed Powered-by footer

Status: IN_PROGRESS (2026-07-14)
Risk: HIGH (render-path change in both app footers + home.html static markup + compiled/minified artifacts)
Score: 7.0 — human-reported UX bug that also undermines 045's de-orphan intent: the links exist but a
user can never click them, so the SEO hub surface gets zero human navigation.

## Report (human, verbatim intent)

"Browse tokens and browse chains from the footer are under the Powered by Defillama API footer and
cannot be accessed — move Browse links to the Defillama disclosure footer."

## Root cause (operator triage, read-only)

- `home.html:289-292` — item 045's static `<footer class="seo-hub-links">` with the two links, placed
  in normal document flow AFTER the React mount roots, deliberately outside them for crawlers.
- `.app-footer` (style.css:~2410-2447) is position: FIXED at the viewport bottom (style.css's own 045
  comment at 2448 contrasts: "Normal document flow (not fixed like .app-footer above)"). A fixed
  overlay at the viewport bottom permanently covers the last in-flow element of the document — the
  static links render underneath it and can never be clicked in analytics mode.

## Change (per the human's directive: the links live IN the disclosure footer)

1. `app.js` — BOTH `.app-footer` instances (~app.js:2486 and ~app.js:3009) gain the two links
   (`/tokens`, `/chains`) rendered inside the footer, after the Powered-by sentence. Reuse the existing
   footer link styling (`.app-footer a` already styled); a small separator/class is fine but
   neumorphic-token-only, no new one-off visual language (standing decision 2026-07-10).
2. Every user-facing string via translations.js EN + natural KO together (hard rule): new keys
   (e.g. `browseTokens` / `browseChains`) used by the rendered links. The static home.html anchors keep
   their English text (raw-HTML crawler surface, pre-dates this item, English-only like the rest of the
   static SEO pages).
3. The static `.seo-hub-links` footer in home.html STAYS in the raw markup (crawler de-orphan surface,
   045's whole point, and the ONLY footer in planner mode where no fixed .app-footer exists) — but gets
   hidden when the ANALYTICS app mounts, where its links are now duplicated inside the visible footer:
   the same links visible to every audience, no cloaking. Mechanics: the analytics bootstrap already
   distinguishes modes (window.__APP_MODE router in home.html) — add e.g. a `body.analytics-mode` class
   at analytics boot (or hide via a CSS rule scoped to a class the analytics app sets on mount) +
   `body.analytics-mode .seo-hub-links { display: none; }`. Pick the smallest mechanism consistent with
   the router; document the choice in 086-notes.md.
4. Planner mode: verify the static links are actually visible and clickable below the planner content
   (they are in normal flow; if the planner viewport/overflow makes them unreachable there too, fix
   visibility there as well and note it — the human's report was analytics-mode, don't silently ignore a
   planner-mode occurrence).
5. Artifacts regenerated: `app.compiled.js` (CI-compile pattern — npm run compile), minified assets
   (npm run minify: app.min, translations.min, style.min if style.css changes), idempotent.
