# Spec 263: the in-flight check runs once, at pickup — make it an executable check that also runs immediately before the first push

## Evidence
Verbatim from BACKLOG.md row 263 (filed 2026-08-11):

> On 2026-08-11 a build run picked 227, ran build.md §1's check (`git ls-remote origin 'refs/heads/claude/loop-227'` → nothing; `origin/main` at `9c73efd36b`, which does not contain 227), built the entire item across four agents, and discovered only at push time that `main` had moved to `13712adc4e` and 227 had merged as `d4f7b3cf3c` (PR #425) hours earlier. Roughly half that run's token spend went to already-merged work; the duplicate was discarded (see LOG 2026-08-11).

The row states the blind spots as a class, not as that instance:
1. a branch merged-and-deleted leaves NO remote ref, so `ls-remote` reads clean for a FINISHED item;
2. the base commit goes stale the moment the run starts, and nothing re-reads it;
3. PR state is never consulted at all — a closed-and-merged PR is invisible to a branch-name grep.

Three recorded occurrences of the same class in this repo: row 260's renumber (a concurrent run landed
its own 259 while 246 built), PR #419 (open, titled "COLLIDES with a concurrent run on
claude/loop-257"), and the 227 duplicate above.

Fourth occurrence, measured by THIS run at pickup (2026-08-11, before any code was written): the
highest-scored READY row, 266 (8.4), reads `READY` on `main` while `claude/loop-266` exists on the
remote and PR #434 is open and PARKED. The pickup check caught it only because the branch still exists —
had #434 been closed and its branch deleted, the prose check would have read clean and this run would
have rebuilt a parked item.

## Hypothesis
We believe replacing build.md's prose in-flight rule with an executable check that runs **twice** — at
pickup and again immediately before the first push — will stop build runs from spending a full session
on already-landed or already-in-flight work, because two of the three recorded blind spots (stale base,
merged-and-deleted branch) are only observable at push time, and the third (PR state in any state) is
not observable through `git ls-remote` at all. Confidence: **supported** — three recorded instances,
each of which at least one of the three legs would have caught at push time.

- Instance of: **loop-process invariants enforced by prose in a prompt rather than by an executable
  check** — the exact class `test_test_registry.js` (item 205) was built to retire for the test
  registry, and `pr-orphan-detector.js` (item 245) for PR terminal states. Population = the imperative
  rules in `prompts/build.md` + `prompts/heartbeat.md` that a run is trusted to follow from memory.
- Class closed by this item: **no.** This item makes exactly ONE prose rule executable (the in-flight
  check). The builder must count the remaining memory-enforced imperative rules in `prompts/build.md`
  and `prompts/heartbeat.md` and record the number in `specs/263-notes.md`; the residue is ticketed as a
  new BACKLOG row in the same commit if the count is > 0.

## Change
Smallest version that tests the hypothesis:

**(a) `product-loop-kit/check-item-inflight.js`** — a Node script, zero new dependencies, following the
`pr-orphan-detector.js` (item 245) architecture: a **pure core** (exported functions over injected data,
no I/O) plus a thin CLI that gathers the git-side data itself and takes the GitHub-side data injected,
because a script cannot call the GitHub MCP tools the loop uses.

Three legs, each answering "has item `<id>` already been built, landed, or claimed?":

- **Leg A — remote branch refs.** `git ls-remote --heads origin`, match any ref whose name contains the
  item id as a **bounded token** (`claude/loop-263`, `claude/loop-263-operator` match; `loop-2630`,
  `loop-1263` must NOT).
- **Leg B — landed commits on a FRESHLY FETCHED `origin/main`.** The CLI runs `git fetch origin main`
  itself (skippable with `--no-fetch` for tests) and scans commit **subjects** for the id at
  subject-start in either convention this repo actually uses — verified against real history:
  `268: file the x402 protocol-conformance gaps ... (#433)` and `fix(266): derive WebMCP trust rails ...`.
  So: leading `<id>:` **or** a conventional-commit scope equal to `<id>` (`type(<id>):`,
  `type(<id>)!:`). An id appearing anywhere else in the subject (`123: fix inspired by 263`) is NOT a
  match — that is the blind spot's opposite failure, a false positive that would block a legitimate run.
- **Leg C — pull requests in ANY state.** Injected via `--prs=<path.json>` (an array of
  `{number, title, state, ...}` as returned by the GitHub MCP `search_pull_requests` /
  `list_pull_requests` tools; extra fields ignored). Title matched with the SAME bounded id rule as
  leg B. When `--prs` is absent the leg is **UNAVAILABLE**, printed loudly, and the exit code says so —
  it never silently counts as clean.

Exit codes (the loud failure the row asks for):
- `0` — CLEAR: all three legs ran and found nothing.
- `1` — COLLISION: at least one leg matched. Prints every match with its leg, ref/sha/PR number and
  subject/title.
- `2` — usage or environment error (not a verdict).
- `3` — CLEAR on the legs that ran, but ≥1 leg was UNAVAILABLE (no `--prs` data). The caller must either
  supply the data or record that it shipped with a leg unchecked.

Informational, non-failing: `--base=<sha>` prints whether `origin/main` moved since that sha and by how
many commits (blind spot 2, made visible even when the item itself has not landed).

**(b) `prompts/build.md`** — two steps, replacing the prose rule:
- §1 pickup: run the script with `--prs` (the run fetches PR data with the GitHub MCP tool first);
  non-zero → skip the item, per the existing rule.
- **New: immediately before the FIRST push** — re-run the same script (it re-fetches `origin/main`).
  Non-zero exit → STOP, do not push, reconcile against what landed. This is the step that did not exist.

**(c) `product-loop-kit/test_item_inflight_check.js`** — the gate (see acceptance criteria).

**(d) `playbooks/loop-container-contention.md`** — UPDATE (never duplicate) the existing "Unmerged PRs
hold IDs invisibly" trap to point at the executable check and its push-time re-run.

OUT of scope: any product render path; auto-fetching PR data inside the script (no network/credentials
in the loop's scripts — 245's precedent); auto-renumbering; changing `heartbeat.md`'s id-allocation
rule; touching `run-tests.js`/`package.json` (this test lives in `product-loop-kit/` beside
`test_pr_orphan_detector.js`, so the root registry — `test_test_registry.js`, which scans the repo root
only — is deliberately unchanged).

## Acceptance criteria
- [ ] `product-loop-kit/check-item-inflight.js` exists, runs on Node 22 with **no new dependency**, and
      exposes a pure core (importable functions taking injected refs/subjects/PRs) plus a CLI.
- [ ] Leg A detects a live `claude/loop-<id>` remote branch; leg B detects a landed commit whose subject
      starts with the id in either repo convention (`<id>:` and `type(<id>):`); leg C detects a PR whose
      title carries the id in ANY state (open, closed, merged).
- [ ] Bounded-token matching: `2630`, `1263`, and a mid-subject/mid-title mention of the id are NOT
      matches, on all three legs.
- [ ] Exit codes exactly as specified: 0 CLEAR / 1 COLLISION / 2 usage / 3 CLEAR-WITH-UNAVAILABLE-LEG.
      Running with no `--prs` never returns 0.
- [ ] Positive control against the REAL repo: `node product-loop-kit/check-item-inflight.js 266`
      exits 1 and names `refs/heads/claude/loop-266` (leg A) — and, when the real PR list is injected,
      PR #434 (leg C). Command + output pasted into `specs/263-notes.md`.
- [ ] Negative control against the REAL repo: an id guaranteed unclaimed (max BACKLOG id + 1) exits 3
      with no `--prs`, and 0 with an empty `--prs` array.
- [ ] `prompts/build.md` carries BOTH steps: the pickup run and the **pre-first-push** re-run, each
      naming the exact command and what a non-zero exit obliges the run to do.
- [ ] Tests: `product-loop-kit/test_item_inflight_check.js`, run green in-session, output in the notes.
- [ ] Population: the test drives the pure core over the population **derived at test time** — every id
      in `BACKLOG.md`'s table, crossed with the repo's REAL `git ls-remote --heads origin` refs and the
      REAL `origin/main` subject list — and asserts the invariant *every match's own extracted id equals
      the queried id* (independently re-extracted, not the matcher's own claim). The 227/266 instances
      are positive controls, never the definition.
- [ ] Non-vacuity: each of the three legs neutered SEPARATELY (so "three working legs" is distinguishable
      from "one working leg and two dead ones"), test re-run red for that leg each time, then a
      byte-identical restore proven with `md5sum` before/after and `git diff --quiet`. All three
      mutation→red→restore→green cycles pasted into `specs/263-notes.md` with the hashes.
- [ ] `playbooks/loop-container-contention.md` updated in the same commit, not duplicated.
- [ ] `specs/263-notes.md` records the count of remaining memory-enforced imperative rules in
      `prompts/build.md` + `prompts/heartbeat.md` (the open residue of the class), and a BACKLOG row is
      filed for it if > 0.

## Measurement
Metric: **build-run duplicate rate** — runs that discover at push time that their item already landed.
This is a BUILD-LEG item (loop tooling, not a product funnel), so per NORTH_STAR.md's experiment
discipline it is verified as a build leg, not on a traffic gate: the check exists, runs, and provably
fails on the three recorded instances. Decision rule: if a future run still ships a duplicate **with the
pre-push step run and green**, the predicate is wrong and the item reopens with that run as evidence.
No ≥30-event traffic gate applies — no user-facing step is claimed to move.

## Risk tier (builder's guess — verifier assigns independently)
**LOW.** Loop tooling only: a new script, a new kit-local test, a prompt edit, a playbook edit. No
product render path, no user-facing string, no trust rail, no generated SEO surface, no dependency. The
one thing to watch: the check gates pushes, so a **false positive** blocks legitimate work — hence the
bounded-token criteria and the negative controls above.

None that change the architecture. (The PR-data injection boundary is settled by 245's precedent: loop
scripts stay offline; the prompt fetches.)
