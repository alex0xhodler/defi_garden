# Spec 279: citation-ready rate-stability answers on token pages

Impact: north-star leg A — every eligible token page answers the canonical token-yield question with a trust-railed, citation-ready comparison

## Evidence
- Human interview 2026-08-13 selected agent adoption, a two-track developer+citation slice, existing token pages, all eligible tokens, and the public label `rate stability`.
- Existing `generate-token-pages.js` already produces EN/KO HTML + Markdown twins, direct answers, FAQPage JSON-LD, pool tables, rails, and a rate-behaviour section only for the curated Google head.
- Current direct answers lead with one representative high rate; they do not answer which candidates have steadier rate history.
- Numeric Sharpe/history are computed KPI value under the current paid boundary. x402 remains dark; static citation surfaces must remain free.

## Hypothesis
We believe a concise ordinal rate-stability comparison on the already-indexed token estate will improve retrieval and citation for “safest yield for TOKEN” queries because agents receive an answer matched to intent without an unsupported principal-safety claim. Confidence: guess until retrieval/citation evidence exists.
- Instance of: citation page answers a rate query but not the user's risk-oriented comparison intent.
- Class closed: every eligible EN/KO HTML/Markdown token twin gets the same answer or the same honest insufficient-history state.

## Change
- Extend the existing generator; do not create `/answers` pages.
- Rank only pools already admitted by the page's existing rails.
- Use retained rate history to derive an ordinal `more stable / less stable` ordering. Publish no Sharpe number or raw history series.
- Label the block `Rate stability`, with visible language that it measures APY history only—not protocol, exploit, depeg, liquidity, governance, or principal-loss risk.
- Show TVL, current APY, protocol, and chain beside each ranked candidate so the ordinal is not presented as a complete safety score.
- When fewer than two pools have sufficient comparable history, render an honest insufficient-history answer; never fall back to TVL/APY while calling it stability.
- Generate visible HTML, Markdown twin, and structured answer facts from one data object; EN/KO together.

## Acceptance criteria
- [ ] Every token record generated by `rankTopTokens(..., 0)` receives one rate-stability block or one insufficient-history block in EN/KO HTML and Markdown.
- [ ] Ranking population is a subset of the page's already-railed displayed pools; anomalous/sub-floor/zero-display-rate pools cannot enter.
- [ ] Ordering is deterministic and derived from historical rate variability with a documented minimum history threshold.
- [ ] No numeric Sharpe value or history series appears in generated public pages.
- [ ] Copy never says `safe`, `safest`, or implies principal protection; it names excluded risk dimensions.
- [ ] HTML, Markdown, and structured facts are generated from one object and remain fact-identical.
- [ ] Fixtures cover: two comparable histories, tie, missing history, one eligible history, anomalous pool, EN/KO, and every-eligible-page population.
- [ ] Non-vacuity: invert the stability order and admit one anomalous pool separately; each mutation makes its invariant fail, then restores byte-identically.
- [ ] Generator runs twice with no diff beyond existing honest freshness behavior.

## Instrumentation
No claim from generation alone. Layered gate: representative-agent retrieval correctness → ≥30 qualified non-loop reads in `agent_reads` → ≥3 observed citations OR ≥5 qualified AI-referred sessions. Report each layer separately.

## Risk tier
HIGH — estate-wide generated SEO/agent content and a financial-risk framing; generator-only clean cutover.

## Open questions
None blocking. Conservative boundary for this cycle: ordinal stability is public; numeric computed KPIs and history remain paid.
