# 248 — PR explainer (LOW tier)

**What:** Two-line fix to `audit-app.js`'s `I18N_UNTRANSLATED_ALLOWLIST` — added `resultsColApy` and
`resultsColTvl`, both `'acronym, same in KO'`, matching the seven existing APY/TVL acronym precedents
already in the same allowlist (including `tcpColApy`/`tcpColTvl`, the same semantic object — a
results-table column header for APY/TVL — on the token/chain-page surface).

**Why:** The 2026-08-07 audit run flagged a live P1: `i18n:en-ko-parity` found 2 of 544 translation
keys with byte-identical EN/KO values. Both keys (`resultsColApy: "APY"`, `resultsColTvl: "TVL"`)
were added by item 225's design reset and are genuinely correct as-is — Korean doesn't gloss these
acronyms anywhere else in the dictionary — but the allowlist wasn't updated alongside the new key
family, so the honest, intended-bare rendering tripped the gate.

**Result:** `i18n.suspectCount` 2 → 0. `translations.js` byte-unchanged (no product-facing string
changed — this only restores the gate's own exemption table). Allowlist grew 24 → 26.

**Not closed:** the allowlist is now 34.6% "APY/TVL acronym on some surface" (9 of 26 entries — this
item's own `resultsColTvl` is that 9th entry, the exact trigger the spec's Open Questions section
named for re-asking the exemption-design question). The next new surface with an APY/TVL column
header needs its own allowlist line. Exempting by value (`{"APY","TVL"}`) instead of exact key path
would close this permanently but trades away per-key auditability. The decision stays deferred: the
metric that actually gates it is exemption rate against the 391-string-key population the gate
protects (6.6%, well under the ~⅓ `guard-exemption-rate.md` threshold), not the allowlist-internal
fraction — left as an open question for the human/next builder, not resolved here (spec's explicit
call).
