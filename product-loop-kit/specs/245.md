# Spec 245: a loop-opened PR can end in no terminal state at all — finished work, no verdict, no owner, and an ID that goes stale while it waits

## Evidence

`list_pull_requests` on 2026-08-06: **11 open PRs**. Ten of them carry a recorded terminal state in the
title or body — PARKED (#386, #392, #396, #397, #322), awaiting a named human decision (#393 screenshot
review, #332 rail relaxation, #309 direction call, #316 directive record), or BLOCKED (#331).

**#399 (item 239) carries none.** Three facts, each checked this tick:

1. **The defect it fixes is live on `main`.** Verified in the tree, not taken from the PR body: the
   default-view comparator's `sortBy === 'tvl'` branch carries item 092's `hasNoSupplyYield` demotion at
   all three sites (`app.js:1987`, `:2077`, `:2177`); the `sharpe` branch (`:1968`, `:2058`, `:2158`) has
   the anomaly rail, Sharpe-desc null-last, and a `b.tvlUsd - a.tvlUsd` tie-break, and **no yield
   partition**. No pool carries `kpis.apySharpe` today, so every comparison falls to that tie-break and
   Risk-Adjusted degenerates into plain TVL — where the largest pools are exactly the 0%-yield collateral
   ones. PR-stated population: 247 pools, $30.1B TVL, 28 chains above the $10M floor.
   (Scope correction recorded in `signals/2026-08-06.md`: `sortBy` defaults to `'tvl'` at `app.js:857`, so
   this is one interaction deep — the Risk-Adjusted toggle — not a first-paint defect.)
2. **No verifier verdict exists.** `specs/239-notes.md` on `origin/claude/loop-239` records the build's own
   red-first control and 17/17 rendered assertions but no verifier PASS/FAIL; the PR's only comment is
   Vercel's deploy bot. Autonomy (c) merges on **verifier PASS + tests green**, so not merging was
   correct. Nothing then flagged it, and nothing is scheduled to finish it.
3. **The wait corrupted its bookkeeping.** The branch commit adds a BACKLOG row numbered **242** for its
   own residual; `main` allocated 242 to a different item and shipped it 2026-08-06. Merging #399
   unchanged puts two different items at id 242. `loop-container-contention.md` already documents
   "unmerged PRs hold IDs invisibly" — this is that trap firing in the reverse direction: `main` took the
   ID while the PR sat.

Net effect: a completed, self-tested repair for a live defect on the sacred analytics surface has been
sitting for ~15 hours, is invisible to every existing report line, and can no longer merge cleanly.

## Hypothesis

We believe **requiring every loop-opened PR to reach a recorded terminal state, and having the heartbeat
detect the ones that have not**, will stop finished work from disappearing, because today the only way an
un-merged PR becomes visible is if a build run happened to write PARKED into its title — a convention with
no enforcement and no detector. Confidence: **supported** for the detection gap (n=1 today, but the gap is
structural: nothing in the tree reads PR state); **guess** for how often it recurs.

- **Instance of:** *loop-produced work whose completion depends on a step that may never run.* The
  population is **every PR the loop opens** — not merge-stalls specifically. The weakest predicate is
  therefore "PR is open AND has no recorded terminal state", not "PR has no verifier verdict": a PR could
  equally stall after a PASS, before the merge, or after a human question nobody routed. A detector keyed
  to *this* instance (missing verdict) would miss the other three shapes, which is the item-212 error.
- **Class closed by this item:** partially. Detection closes; **remediation does not** — the heartbeat is
  triage-only and must not merge or re-verify. The residual is that a detected orphan still needs a build
  run or the human to finish it, and nothing here schedules that. Say so with the number of orphans found
  each tick.

## Change

Smallest version that tests the hypothesis, in two independent legs:

**Leg A — the detector (loop tooling, LOW).** A check the heartbeat runs each tick: list open PRs, and for
each, classify into `{merged, PARKED, BLOCKED, human-gated, ORPHAN}`. ORPHAN = open, authored by the loop,
and carrying none of the other markers. Emit the count and the list into the signals snapshot; a non-zero
count is a report line. Derive the marker set from the statuses BACKLOG.md actually defines — do not
re-type a literal list of title prefixes.

**Leg B — the ID-collision guard (LOW).** Before a build run writes a new BACKLOG row, the next id must be
computed from `main`'s max **and** the ids claimed by open PR branches (`loop-container-contention.md`
already prescribes `list_pull_requests` + `git ls-remote 'refs/heads/claude/loop-*'`, but nothing checks
it). The guard makes the existing playbook rule executable. Symmetrically, a heartbeat that detects an
ORPHAN whose BACKLOG row now collides reports the collision explicitly.

**Explicitly OUT of scope:**
- Merging, re-verifying, or re-running any PR — including #399. The heartbeat is triage-only, and #399
  needs a verifier verdict it never got. Its disposition is the human's call and is in today's report.
- Changing the ship path, the branch-vs-direct-to-main rule (2026-07-13), or autonomy (c).
- Product code of any kind. This item touches `product-loop-kit/` and loop tooling only.
- Auto-closing or auto-renumbering anything. Detection and reporting only; a detector that mutates other
  runs' branches is strictly worse than no detector.

## Acceptance criteria

- [ ] Given a fixture set of PR records covering all five classes, the classifier returns exactly one class
      per PR, and returns `ORPHAN` for the #399 shape (open, loop-authored, no PARKED/BLOCKED/human-gate
      marker, no verdict).
- [ ] **Non-vacuity:** a fixture where every PR is properly terminal returns **0** orphans, AND the #399
      fixture returns **1** — both asserted. A detector that has never been shown to go red is not
      evidence (LEARNINGS 2026-07-27).
- [ ] **Population, derived at test time:** the marker set is parsed from BACKLOG.md's own status legend
      (lines 2-6), not re-typed. Assert set-equality both directions, so a new status added to the legend
      fails the test rather than being silently unclassified (item 212's rule).
- [ ] Leg B: given `main` max id = N and an open PR branch whose diff adds a row with id ≤ N, the guard
      reports the collision and names both items. Fixture-driven; no live GitHub call in the test.
- [ ] The heartbeat prompt (`prompts/heartbeat.md`) gains the orphan check as a numbered step, and the
      signals snapshot template gains the line. No other kit prompt changes.
- [ ] Runs offline in CI-less conditions: the live-GitHub path is injectable so tests never hit the network.

## Measurement

Metric: **orphan-PR count at each heartbeat**, and **days-to-terminal-state** for loop-opened PRs ·
Gate: build-leg verification only — this is loop tooling with no user-facing funnel step, so the
traffic-gate regime does not apply (NORTH_STAR: "calendar windows remain only for build-leg
verification") · Decision rule: keep if the detector reports a correct non-zero count on the tick it
ships (#399 is the live positive control) and 0 false positives across the ten properly-terminal open PRs.
