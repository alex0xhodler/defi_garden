# Spec 041: Static chain landing pages, `/chains/<slug>` — 014/021 pattern extended to chains

## Evidence
`specs/010-diagnosis.md`'s largest GSC class is **Crawled — currently not indexed = 22,877**, caused by 20k+ near-identical thin JS shells (one `home.html` per parameterized URL; real content only appears after client JS + a DefiLlama fetch). Fix 014 addressed this for tokens (top-100, later uncapped) and shipped end-to-end: `generate-token-pages.js` → real static `/tokens/<slug>.html` pages, wired into `sitemap-token-pages.xml` → included in the sitemap index (021) → CI-generated on every `sitemap-update.yml` run. `reports/2026-07-11-sota-growth.md` (#041, score 7.5): the SAME mechanism applies to chains — `generate-sitemap.js` already emits 111 `sitemap-chain-*.xml` files, each pointing only at thin `?chain=<Chain>` shell URLs (confirmed: `ls sitemap-chain*.xml | wc -l` → 111). This is the largest remaining category from the 010 diagnosis still unaddressed by a real static page.

## Hypothesis
Serving a real, static, server-delivered HTML page per chain (title/description/canonical/content all present without JS) gives crawlers genuine content instead of the thin `?chain=` shell, draining "Crawled — not indexed" for chain URLs the same way 014 did for token URLs. Confidence: supported — identical mechanism, already proven end-to-end on `/tokens/`.

## Change
New `generate-chain-pages.js` (Node, mirrors `generate-token-pages.js` — no build step, no new deps). Per CLAUDE.md/NORTH_STAR's "reuse before inventing" standing decision (2026-07-10), it `require()`s `generate-token-pages.js` and reuses its exported pure helpers (`poolTotalApy`, `formatUsd`, `formatApy`, `renderAnalyticsBootstrap`, `tokenSlug` for slugging, `escapeHtml` — the last newly exported, additive-only) instead of re-implementing them:

1. **Data**: same `--fixture <path>` / `POOLS_FIXTURE` offline path as `generate-token-pages.js` (this sandbox cannot reach `yields.llama.fi`).
2. **Ranking + quality gate**: aggregate `tvlUsd` per `pool.chain` (chains are single-valued per pool, unlike token symbols — no splitting needed). Keep only pools with `tvlUsd >= MIN_POOL_TVL ($100K)` and non-anomalous (`APY_SANITY_LIMIT` 1000%, trust rail, untouched). A chain qualifies with **≥1 qualifying pool** (014's amended eligibility, not the original ≥2). Rank by aggregate qualifying TVL desc, no cap by default (`--limit N` still supported). Same 030/032/033 quality bar: the **displayed** top-`POOLS_PER_PAGE` (8) slice must include ≥1 pool whose formatted APY is not `"0.00%"` — a chain whose visible table is all-zero-yield is dropped, exactly like a token.
3. **Trust rails intact**: identical to 014 — anomalous pools never counted, never shown; `$100K` floor applied at generator level (this generator's own SEO-traffic-capture floor, same divergence from the app's `$10M` `DEFAULT_MIN_TVL` that 014 documented and justified — untouched here).
4. **Per page** `chains/<slug>.html`:
   - server-delivered `<title>`, `<meta name="description">`, self-canonical `<link rel="canonical" href="https://www.defi.garden/chains/<slug>">`.
   - `BreadcrumbList` JSON-LD (040 pattern): Home → Chains (unlinked, no hub page) → `<Chain>` (linked, self-canonical) — same reasoning as the token pages' "Tokens" crumb.
   - content differentiated from the `?chain=<Chain>` app view (standing decision 2026-07-11, "keep both surfaces distinct, no consolidation" — the same rule 021 applied to tokens): a written intro naming the chain's top pool/protocol/token, distinct token count, and total qualifying TVL — not just a re-rendered table.
   - table of the chain's top qualifying pools: **Token / Protocol / Chain-specific APY / TVL** (adds a Token column vs. the token page's Protocol/Chain/APY/TVL, since a chain page spans multiple tokens) — each row links to its pool-detail page (`/?pool=<id>`, falls back to `?chain=<Chain>` if no id).
   - one prominent CTA into the live app at `https://www.defi.garden/?chain=<Chain>` ("See live pools on `<Chain>` →").
   - Related-chains nav (023/internal-linking pattern): up to 6 other ranked chains, chains sharing a token with this one first, then top-TVL others.
   - reuses the app design system (`/style.css` + neuro tokens only, no hardcoded hex) — same scoped-style block pattern as `generate-token-pages.js`.
   - analytics bootstrap (039 pattern, reused via `renderAnalyticsBootstrap`) fires `page_view` with `page_type: 'chain_landing'`.
5. **Pure functions exported** (`rankTopChains`, `renderChainPage`, `relatedChainsFor`, `renderChainSitemap`, `chainSlug`) under the `require.main === module` guard, mirroring 014's testability pattern.
6. `test_chain_pages.js` (mirrors `test_token_pages.js`'s assert style) runs against a new fixture (`test_fixtures/pools-chain-sample.json`, fictional chain names `Big/Mid/Anom/Dust/Zero/Tiny/Trunc/Multi Chain` — mirrors the token fixture's `BIG/MID/ANOM/...` naming so each branch of the gate is independently exercised) and asserts: ranking by TVL desc, ≥1-qualifying-pool gate, anomaly exclusion, the display-truncation quality gate (033-style), slug safety (space→dash), self-canonical + server-delivered title/description, BreadcrumbList shape, app-CTA link, pool-row deep links, related-chains ordering, and the analytics bootstrap. Added to the `package.json` test chain.
7. **Wiring (both phase 1 and phase 2 in one PR)** — unlike 014/021's original two-PR split, 021 already proved the full CI pattern end-to-end for tokens, so there is no exploratory risk left to de-risk by splitting:
   - `generate-chain-pages.js --sitemap sitemap-chain-pages.xml` emits a urlset of every generated `/chains/<slug>` page (`renderChainSitemap`, mirrors `renderTokenSitemap`).
   - `generate-sitemap.js`'s index gains a third `existsSync('sitemap-chain-pages.xml')` guard block (mirrors the existing `sitemap-token-pages.xml` block) so crawlers discover the chain pages once generated.
   - `.github/workflows/sitemap-update.yml` gains a "Generate chain landing pages" step (mirrors the existing token step) before the sitemap step; the `push.paths` trigger list and the final `git add` file list both gain `generate-chain-pages.js` / `sitemap-chain-pages.xml` / `chains`.
   - `package.json` gains a `"chains": "node generate-chain-pages.js"` script (mirrors `"tokens"`) and `test_chain_pages.js` joins the `test` chain.

**Explicitly out of scope**: no changes to `sitemap-chain-*.xml` (the existing 111 thin per-chain token-combo sitemaps — those stay as-is, still useful for token+chain combo discovery, separate concern from this single per-chain landing page), no canonical-consolidation changes to `?chain=` (it remains the interactive app view, self-canonical, untouched), no `vercel.json` routing changes (static files under `chains/` are served as-is, same as `tokens/`).

## Acceptance criteria
- [ ] `generate-chain-pages.js` runs against a committed fixture (`--fixture`) with zero network and writes `chains/*.html`; sample output committed for review
- [ ] Ranking by aggregate qualifying TVL desc; a chain qualifies with ≥1 qualifying pool (`$100K` floor, non-anomalous); no cap by default, `--limit N` caps to top-N
- [ ] Anomalous pools (>1000% total APY) never appear in a page's pool list and never count toward its gate or TVL (trust rail); `$100K` per-pool floor applied
- [ ] A chain whose displayed (top-8-by-TVL) pools are all `"0.00%"` formatted APY is dropped (030/032/033 quality bar, chain-level)
- [ ] Every emitted page has: self-canonical `https://www.defi.garden/chains/<slug>`, server-delivered `<title>` + `<meta description>` (present in raw HTML, no JS), a valid 3-item `BreadcrumbList` JSON-LD, ≥1 real pool row, and a CTA link to `https://www.defi.garden/?chain=<Chain>`
- [ ] Each pool row links to its pool-detail page (`/?pool=<id>`), falling back to the chain app view when a pool has no id
- [ ] Related-chains nav present when related chains exist, co-token chains ordered first, self excluded, omitted when empty
- [ ] Slugs are URL/filesystem-safe (space → dash, lowercase); all numbers via en-US helpers; reuses `generate-token-pages.js`'s exported helpers rather than duplicating them
- [ ] Page reuses `/style.css` + neuro design tokens only — no hardcoded hex in the scoped style block
- [ ] Content is genuinely different from the `?chain=<Chain>` app view (written intro, distinct HTML), not a duplicate — per the 2026-07-11 "keep both surfaces distinct" standing decision
- [ ] Analytics bootstrap fires `page_view` (`page_type: 'chain_landing'`) on every generated page
- [ ] `renderChainSitemap` emits a valid urlset, one `<loc>` per ranked chain, pointing at `/chains/<slug>`
- [ ] `generate-sitemap.js` includes `sitemap-chain-pages.xml` in the index only when the file exists (`existsSync` guard, mirrors the token block)
- [ ] `.github/workflows/sitemap-update.yml` generates chain pages+sitemap before the sitemap step, commits `chains/` + `sitemap-chain-pages.xml`, and triggers on `generate-chain-pages.js` changes
- [ ] No changes to trust rails, `sitemap-chain-*.xml` (the existing per-chain token-combo files), `?chain=` app logic, or `vercel.json`
- [ ] `node test_chain_pages.js` + the full existing chain (`npm test`) exit 0; every run timeboxed 5 min foreground

## Territory notes
- `generate-token-pages.js` is the direct precedent for structure, trust-rail mirroring, and the offline-fixture verification pattern; this spec reuses its exported pure helpers rather than re-deriving them (CLAUDE.md/NORTH_STAR "reuse before inventing").
- `generate-sitemap.js:386-408` is the exact index-assembly block the `sitemap-chain-pages.xml` guard slots into, right after the existing `sitemap-token-pages.xml` guard.
- `app.js:1448-1456` confirms `?chain=<Chain>` matches `pool.chain` by exact string — the CTA URL must use the raw chain name (`encodeURIComponent`), not a slugified form.
- The existing 111 `sitemap-chain-*.xml` files (`generate-sitemap.js:300-322`) are a different, pre-existing concern (per-chain sitemaps of `?token=&chain=` combo URLs) — not touched or renamed by this spec, to avoid an unrelated naming collision with the new `sitemap-chain-pages.xml` single index file this spec adds.
