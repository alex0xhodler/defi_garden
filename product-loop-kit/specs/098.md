# Spec 098 — NL search: a bare protocol name searches the PROTOCOL, not a same-named token

Status: SHIPPED (2026-07-14) · Score 6.5 · Risk HIGH (NL-search behavior on the sacred `?token=/?chain=/?protocols=` surface)

## Source / evidence
Human ticket 2026-07-14 (follow-up to 091). Typing "pendle" in the analytics search produced a dead end: "No yields found for PENDLE / No live pools for PENDLE clear our $10M minimum-TVL safety floor". The human traced it to the constructed URL `?token=PENDLE&poolTypes=Yield+Derivatives&protocols=Pendle` and noted: this should return **pendle-protocol** yields, not the **PENDLE token**, and must not be token-restricted at all — Pendle's pools are built on many different underlying tokens.

## Root cause
`parseNaturalLanguageQuery` (app.js) extracts a token by exact/word match FIRST. "pendle" is both a token symbol (29 live pools carry PENDLE in the symbol, none above the $10M floor) AND a protocol (160 live pools, 6 above the floor). So the parser returned `token='PENDLE'` (dominant in the handler) alongside `protocols=['Pendle']`/`poolTypes=['Yield Derivatives']`. The handler's token-first path then filtered to pools whose symbol contains PENDLE → below the floor → empty state. The protocol/category signal was set but never got to drive the result. (Pre-existing; 091 added the category signal but not this fix.)

## Fix (surgical, ~4 lines)
At the end of `parseNaturalLanguageQuery`, before the return:
```js
if (token && protocols.some(p => p.toLowerCase() === token.toLowerCase())) {
  token = '';
}
```
A word that names a detected protocol is a protocol search, not a token search — drop the token so the protocol (+ any category) filter drives the results. The handler then routes a token-less protocol query into "All chains" mode filtered by the protocol (existing behavior, app.js `effectiveChain` logic).
