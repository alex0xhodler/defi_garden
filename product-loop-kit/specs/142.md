# Spec 142: `audit-app.js` — mechanize the §2b product audit as a Playwright scanner

## Evidence
- NORTH_STAR.md 2026-07-23 PRE-TRAFFIC MANDATE names the candidate build verbatim: *"Candidate build to automate it: audit-app.js (Playwright scanner emitting findings the heartbeat tickets)."*
- `playbooks/product-audit.md` closes with **Automatability**: *"Checks 1–6 are deterministic and mechanizable — a `audit-app.js` Playwright scanner could render each surface and emit a findings JSON the heartbeat tickets, so regressions like −900T / `$0.1` can never ship unnoticed again."*
- BACKLOG.md row 142 (score 6.5, READY, LOW): *"today's tick hand-ran all of it — third consecutive manual pass, mechanizable end-to-end."* Three heartbeats in a row (2026-07-23/24/25) hand-drove the same surface rotation and checklist.
- The class of bugs this catches, all found manually and expensively: **122** (rate-stability −900,719,925,474,097.9 on stable pools), **126** (`$0.1` unformatted money), **132** (loading-flash empty-state ternary), **133** ($10M dead-end), **136** (mobile CTA ancestor-clip), **137** (KO `원` stamped on raw USD). Every one is mechanically detectable per the playbook.

## Hypothesis
We believe a committed `audit-app.js` scanner that drives the real rendered surfaces and emits a findings JSON will let the heartbeat ticket regressions automatically (and let CI/local runs catch them pre-merge), because the six deterministic bug classes are exactly the ones the human keeps finding by hand and re-deriving each tick. Confidence: supported (the manual checklist already works; this codifies it, and the fixture-trap section proves the detection logic).

## Change
Add ONE new file `audit-app.js` at repo root (a Node script, run `node audit-app.js`), plus its acceptance test `test_audit_app.js`. No product-code changes — the scanner is read-only tooling, it never edits app.js/PoolDetail.js/CSS.

**Scanner contract:**
- Starts a local static server (house pattern: serve repo files, `/` → `home.html`) and launches Chromium (`/opt/pw-browsers/chromium` when present).
- Fixture-routes the sandbox-blocked externals exactly like `test_northstar_cta_fires.js`: vendored unpkg React/ReactDOM/Babel from `node_modules`, abort `icons.llamao.fi`, and — critically — route `**/data/pools-snapshot-meta.json` with a **fresh `generatedAt` (`new Date().toISOString()`)** so the snapshot-first path (059) is exercised and the committed `data/pools-snapshot.json` renders verbatim instead of silently falling through to the live path (playbook "Snapshot staleness gate" trap). Snapshot BODY is served real (unmodified committed file) so findings are about real data (that's how 122's −900T would surface).
- Drives a **surface rotation** (the playbook's "Surfaces to drive"): `?token=USDC` (grid), `?pool=<real id from the committed snapshot>` (pool-detail = north-star surface), `?chain=Ethereum`, a **dead** `?pool=<bogus id>` (072 empty-state), and at least one static page (`/tokens/<slug>` or `/chains/<slug>` if present in the build; skip-with-log if not generated). Each pool-detail + grid surface is additionally driven at **360px width, dark mode (`data-theme=dark`), and KO (`?lang=ko`)** for checks 5 & 7.
- Runs the deterministic **checks 1–7** from `playbooks/product-audit.md` on each surface, each with the playbook's fixture-trap guards baked in:
  1. **Number sanity** — scan rendered text for `NaN`/`Infinity`/`undefined`/`null` tokens; absurd magnitude (a bare number with `|value| > 1e4` that is NOT a legitimately-large TVL/USD figure → flag; use the K/M/B/T-suffix + thousands-separator context to avoid false positives); money regex that flags `$0.1`-style 1-decimal money **only when NOT followed by a `[KMBT]` suffix** (playbook "Money-format regex" trap — `$11.2K`/`$273.3M` are legal house style).
  2. **Dead-end** — for a VALID query surface (grid/pool-detail with real data), the main region must NOT be an empty/error/"no results"/all-`$0.00`/all-`0%` state. (The dead `?pool=` surface is EXPECTED to show the empty state — asserted as a positive, not flagged.)
  3. **Loading flash** — the pre-data view must not assert "no results"; must show a loading state. (Exercised on the live path with delayed/empty data, per playbook check 3 / item 132.)
  4. **Console/page errors** — zero `pageerror` / `console.error` on every driven surface, using the established `IGNORABLE` allowlist (mixpanel/llamao/fontshare/unpkg/snapshot/"Failed to load resource").
  5. **i18n** — no raw `t('…')`-shaped or camelCase key text leaking; KO renders when `?lang=ko`; **KO currency truth** — the KO money figure for a value must not relabel a raw USD number as `원` without conversion (compare KO figure vs EN `$` figure for the same pool — item 137).
  6. **Dead CTAs** — the two north-star CTAs on pool-detail (`.cta-button-primary` "Garden this pool", `.cta-button-protocol` "Start Earning") render and are visible; primary links resolve.
  7. **Responsive/dark** — no horizontal body scroll at 360px (`document.body.scrollWidth <= 360`) AND the primary CTA's bounding box is fully inside the viewport (ancestor-clip check — item 136: a `scrollWidth`-only check passes while an `overflow:hidden` ancestor clips the CTA invisible).
- **Async guard**: poll up to ~10s before claiming an empty-state/noindex/CTA "didn't render" (playbook "Async meta reads" trap — babel-standalone compile + data fetch land seconds after `load`).
- **Emits findings JSON** to stdout AND writes `product-loop-kit/signals/audit-findings.json`: `{ generatedAt, surfacesCovered: [...], findings: [ { surface, viewport, check, severity (P0|P1|P2), detail } ] }`. Severity mapped per the playbook's "Severity → score" table (P0 broken number/page error → 9+, P1 dead-end/flash/dead CTA → 7–8, P2 format/label/responsive → 5–6). Exit code non-zero if any P0/P1 finding, zero otherwise (so it can gate CI later — advisory now).
- Rotation logging: print which surfaces were covered this run (playbook "Rotate a subset … log which surfaces you covered").

OUT of scope: any product-code change; wiring into `package.json` `test` (the heartbeat/human invokes it on demand — adding it to the 80-test `npm test` chain would be a separate item); auto-filing backlog rows (the heartbeat reads the JSON and tickets — human/heartbeat-owned); check 8 (honest-label JUDGMENT — playbook explicitly says flag-don't-automate, so the scanner does not attempt it).

## Acceptance criteria

- [ ] `audit-app.js` exists at repo root, runs via `node audit-app.js`, exits 0 against the **current committed snapshot** (the real data is presently clean — no P0/P1), and writes `product-loop-kit/signals/audit-findings.json` with the documented shape (`generatedAt`, `surfacesCovered` non-empty, `findings` array).
- [ ] It drives ≥4 real surfaces including `?pool=<real snapshot id>` (north-star surface) and a dead `?pool=` — verifiable in `surfacesCovered`.
- [ ] Fixture-trap correctness (this is the load-bearing acceptance — the scanner must not fabricate findings, per the playbook's three false-alarm warning): the money regex does NOT flag `$11.2K`/`$273.3M`; the snapshot renders via the FRESH-meta route (not the live fall-through); the CTA/empty-state checks poll before asserting absence.
- [ ] **Positive control (rendered)** — `test_audit_app.js` proves the scanner CATCHES a real bug class, not just that it runs: with a fixture snapshot mutated to inject a `−900...T`-style absurd number (122 class) OR a `$0.1` unformatted-money string (126 class) into a pool-detail render, the scanner emits a P0 number-sanity finding for that surface; with the unmutated snapshot, zero P0/P1 findings for that surface. Acceptance is the scanner's behavior on a **real Chromium render** (npm run dev + chromium fixture pattern), never a unit fixture of the regex alone.
- [ ] Tests: `node test_audit_app.js` green; full `npm test` still green (unchanged — no product code touched).
- [ ] No product file (`app.js`, `PoolDetail.js`, `planner.js`, `*.css`, `home.html`, `translations.js`, generated SEO surface) is modified by this item. No trust-rail constant touched. No new npm dependency (Playwright is already a devDependency).
- [ ] Instrumentation: none new — this is a build-tool, not a product surface; it READS the rendered product, emits no user-facing events.
