## The goal in one sentence

The daily audit renders 2 pool-detail pages per tick out of 739 candidates — a 370-day full pass over the
north-star surface — so this raises that budget to 6 and makes the resulting coverage rate say itself out
loud instead of leaving a reader to compute it.

## The intuition

Item 183 gave the pool-detail rotation a memory: it now prefers pools it has never audited before, so
coverage accumulates instead of re-rolling the same dice every day. That fixed **which** pools get picked.
Nobody asked the next question: **how many**.

`DEFAULT_POOL_SAMPLE = 2`. With 739 rotation candidates, one full pass takes `ceil(739/2)` = **370 ticks**
— at daily cadence, a bit over a year. Put the other way round: a defect that only shows up when a
pool-detail page is actually *rendered* has a ~0.27% chance of being caught on any given day.

That last clause is the whole reason this matters. The cheap `poolPrescan` does sweep all 736 snapshot
pools every tick — but only for five **numeric** signals (APY rail breach, mean30d rail breach, non-finite
KPI, absurd magnitude, missing TVL). The classes that need a browser — a dead CTA, a leaked i18n key, a
control clipped at 360px, a console error — reach 2 pools a day. And those render-only classes are exactly
what found items **136** (CTA clipped at 360px), **137** (`원` stamped on USD) and **182** (the dead "Start
Earning" CTA, found on a pool the rotation happened to reach by luck).

The interesting part: **the machinery to fix this already shipped.** `MAX_POOL_SAMPLE = 6` and the
`AUDIT_POOL_SAMPLE` env override have existed since item 167. The ceiling was built; only the default was
conservative. So this item is a budget change, not new machinery — which is why the spec's hard requirement
was *measure before choosing*, not *pick the ceiling because it is there*.

## What changed, in reading order

### 1. `audit-app.js` — the constant (and its justification, in the code)

```js
const DEFAULT_POOL_SAMPLE = 6;      // rotation sample size
```

The comment above it carries the measurement, because a number without its justification is how the *next*
person ends up re-deriving this:

| Run | Wall-clock | Rotation result |
|---|---|---|
| default = 2 (before) | **106s** | `seen 18/739, picked [2 ids]` |
| `AUDIT_POOL_SAMPLE=6` (override) | **107s** | `seen 22/739, picked [6 ids]` |
| default = 6 (after, in place) | **104s** | `seen 22/739, picked [6 ids]` |

Method: `time node audit-app.js` with `AUDIT_ROTATION_STATE` redirected to a scratch copy so the tracked
`product-loop-kit/signals/audit-rotation.json` was never mutated, `audit-findings.json` restored after each
run. The 5-minute (300s) foreground cap is a standing decision (2026-07-11); 6 lands at ~35% of it.

The striking result is that **four extra pool-detail renders cost about a second** — the ~1-3s spread across
the three runs is run-to-run noise. Page boot, the live 15,873-pool fetch and server setup dominate; the
per-surface render is close to free. That is why there was no reason to stop at an intermediate value:
3/4/5 would have left measured, verified headroom on the table for no benefit.

### 2. `audit-app.js` — the coverage rate, made legible

`poolRotation` gains a `sampleSize` field (and `emptyPoolRotationResult()` gains `sampleSize: 0`), so the
CLI summary can derive the throughput at runtime rather than re-typing the constant (the item-159 rule):

```
[audit] pool rotation: cycle 0, seen 22/739 candidates, picked [ecf788e3…, …], wrapped=false
[audit] rotation throughput (rotation-only, excludes anchor + prescan-promoted ids): 6 pool-details/tick
        over 739 rotation candidates -> full pass ~124 ticks (~days)
```

**This is where the item could most easily have gone quietly wrong**, and the spec's territory notes said
so in advance. The obvious denominator is `seenCount` — and it is the wrong one. `buildPoolSurfaces()`
folds three different reasons into the `seen` array it persists:

```js
const thisRunPoolIds = [anchorPoolId, ...promotedIds, ...rotationPicks].filter(Boolean);
```

The anchor pool and the prescan-promoted ids are **not members of `rotationCandidates`** — they are
excluded from it by construction. So `seenCount` grows faster than the rotation itself does (it read 16
after three days at 2 picks/tick, not 6), and a full-pass figure derived from it would flatter the
scanner. The line divides `candidateCount / sampleSize`, never `seenCount`, and both the wording and the
code comment say the figure is rotation-only. Both inputs are guarded: at `sampleSize` or `candidateCount`
of 0 (the `AUDIT_POOL_IDS` override path, which returns `emptyPoolRotationResult()`) it prints
`n/a (rotation disabled)` rather than `Infinity`.

### 3. `audit-app.js` — exports and one stale comment

`DEFAULT_POOL_SAMPLE` and `MAX_POOL_SAMPLE` are now exported so tests interpolate them instead of re-typing
`6`. And the `buildPoolSurfaces()` header comment claiming "additive growth is `DEFAULT_POOL_PRESCAN_MAX +
DEFAULT_POOL_SAMPLE` = 4, comfortably under `MAX_POOL_SAMPLE` (6)" became arithmetically false the instant
the default became 6 (2 + 6 = 8). It is corrected in place, with the reason the new number is fine:
`MAX_POOL_SAMPLE` is a ceiling on the **rotation leg's own override clamp**, never a bound on the
promotion+rotation sum.

### 4. Tests — the selection contract is the thing under guard

Eight cases added to `test_audit_cta_provenance.js` (the existing home of the rotation tests — no new file,
since the runner enumerates tests from `package.json`'s `test:serial` chain). The load-bearing one is the
**golden fixture**: `computeRotation(candidates, 2, seed, state)` must still return its exact pre-191 pick
list. `computeRotation()` and `sampleBySeed()` are byte-unchanged by this item, and that test is what keeps
them that way — a regression there would silently degrade item 154's same-day-reproducibility guarantee
while every other test stayed green.

The rest: the default applies (interpolated, never a literal 6); `AUDIT_POOL_SAMPLE=3` still overrides; a
value **above** the ceiling (99) is clamped rather than accepted, on both the opts and env paths;
determinism at the new default; and a state round-trip that drives an 8-candidate fixture until it wraps —
asserting `cycle` increments by exactly 1 and `seen` resets to just that run's ids — rather than waiting
124 days for a real wrap.

`test_audit_pool_prescan.js:165` asserted `extraSurfaces.length === 2` with the old default named in its
own failure message; it now interpolates `DEFAULT_POOL_SAMPLE`. Budgeting for that was the spec's explicit
instruction — a test that re-types the constant it is meant to be checking is the fourth trap in the
`product-audit.md` playbook's class 11.

## The honest part: this buys a constant factor, not closure

`ceil(739/2)` = 370 ticks → `ceil(739/6)` = **124**. That is **3×**, and it is all it is. 124 days is still
not "audited daily." A render-only defect on an arbitrary pool still has a ~0.8%/day chance of being seen,
up from ~0.27%. The spec required this be said plainly and not let a 3× read as a fix, so: **the coverage
gap is narrowed, not closed.** If the loop wants closure it needs a different shape — parallel browser
contexts, or a cheaper render path — and the spec explicitly says to file that as its own item rather than
smuggle it in here.

Two consequences worth knowing, both in `191-notes.md` as well:

- **The stride caveat.** `sampleBySeed`'s stride is `floor(list.length / count)`, so it depends on `count`.
  Raising the default does not simply *add* four picks to what a 2-pick run would have chosen — only the
  first pick is stable across sample sizes (same start index, different stride). Item 154's contract
  (same seed + same state ⇒ same picks) is untouched and pinned by two tests; it just holds **per** sample
  size, not **across** sample sizes.
- **The default now equals the ceiling**, so `AUDIT_POOL_SAMPLE` can from here only *lower* the budget.
  Going above 6 requires raising `MAX_POOL_SAMPLE`, which spec 191 puts out of scope. Stated in three
  places: the constant's comment, the usage-doc block, and the notes.

## Measurement

`poolRotation.seenCount` growth per tick, read from each heartbeat's `audit-findings.json`, plus total
wall-clock. Window 14 days, due **2026-08-14**. **Keep** if `seenCount` advances by the new sample size
each tick and the run stays inside the 5-minute cap; **revert-candidate** if the run starts timing out or
the loop begins skipping the audit — a scanner that does not finish is strictly worse than one that covers
2 pools. The read that would actually validate the hypothesis (a P0/P1 originating on a pool the *widened*
rotation reached) remains unlikely inside one window at 0.8%/day: **a null result there is not evidence the
change failed**, and will not be reported as one.

No product event, no user-facing change — this is loop tooling, and the spec's instrumentation line is
"none" for exactly that reason.

2. Three timing runs are on the record: 106s at sample 2, 107s at 6, 104s at the new default. What does
   that spread tell you about where the scanner's wall-clock actually goes — and why does it make 3, 4 or 5
   the wrong choice?
3. `computeRotation()` and `sampleBySeed()` are byte-unchanged by this item. So why does the change still
   alter which pools a given day's rotation reaches, beyond the first pick?
4. `DEFAULT_POOL_SAMPLE` is now equal to `MAX_POOL_SAMPLE`. What capability does that remove from the
   `AUDIT_POOL_SAMPLE` env override, and what would have to change to get it back?
