# 170 — explainer (HIGH tier: full walkthrough + quiz)

## Goal

Make the browser test lane — the rendered half of this loop's merge gate — actually runnable, by letting
it run more than one file at a time without ever letting two files fight over the same TCP port.

## The intuition

`run-tests.js` splits 100 test files into two lanes: `plain` (36 files, pure Node, seconds) and `browser`
(64 files, real Chromium, ~30s each and up). The plain lane has run on a worker pool since item 163. The
browser lane was pinned to a single worker by one line:

```js
if (lane === 'browser') return 1; // forced — fixed-port real-Chromium files must serialize.
```

That comment is true. Browser tests each start an HTTP server on a hard-coded port, and the literals
collide across files: seven files declare `const PORT = 8796`, five declare `8799`, five `8795`, and so
on. Two of those running at once means `EADDRINUSE` — or worse, a green run against the *other* file's
server, a false pass in the merge gate. Serialising was the safe answer.

The cost of that safety became the real problem. 64 files × ~30s ≈ half an hour, and worse in practice
(`specs/163-notes.md:180` records `test_smoke.js` blowing a 120s cap; `test_search.js` needs ~550s). No
session can wait that long under the 5-minute timebox, so **five consecutive build runs shipped with
"Browser lane NOT run" in `LOG.md`** and a hand-picked `--only` subset standing in as merge evidence.
Each item's own surface was checked; nothing checked that item N hadn't broken item N-30's.

The fix is to stop treating the constraint as a property of the *lane* and start treating it as a
property of each *pair of files*. Two files conflict only if they want the same port. Most pairs don't.

## What changed, in reading order

**1. `extractPorts(fileName)` — `run-tests.js` ~line 178.** Reads a file's own source and unions two
regex scans into a `Set<number>`: `const|let|var <IDENT containing PORT> = <digits>` (the declaration
form every port-declaring file in this repo uses) and `localhost:<digits>` / `127.0.0.1:<digits>` URL
literals. This mirrors how `classifyLane()` already reasons statically about source text.

The scan is deliberately **non-transitive** — it does not follow `require`s. That looks like a bug and
isn't: `test_audit_app.js` requires `audit-app.js`, which listens on `AUDIT_PORT` (default 8821). If we
chased requires, that file would get a port and stop being exclusive. We *want* it exclusive, because a
port that arrives through a helper is exactly the kind we can't be sure we've found.

**2. `conflictKeysFor(fileName)` — ~line 213.** Returns `{ keys, exclusive }`. `keys` is `port:<n>` per
extracted port plus `res:audit-findings` for any file mentioning `audit-findings.json` / `DEFAULT_OUT` —
that file is `audit-app.js`'s `DEFAULT_OUT` and is *committed to the repo*, and `specs/169-notes.md`
records a run silently overwriting it. Ports aren't the only shared resource, so the mechanism is keys,
not ports. `exclusive` is true iff the port set is empty: **a file we couldn't read a port out of runs
alone.** Undetected ports can then never collide, by construction.

**3. `defaultJobsFor` — ~line 264.** `jobsOverride` now wins for both lanes (the browser lane used to
silently discard `--jobs`); with no override the browser lane defaults to `max(1, min(3, cpus - 1))`.

**4. `runQueue(entries, jobs, timeoutSec, onResult, opts)` — ~line 372.** With no `opts.getConflict` —
the plain lane's call site, unchanged — it is the original shared-index worker pool. With conflict
metadata (the browser lane) it becomes a greedy, event-driven scheduler: on every free slot it scans
not-yet-started entries **in list order** and starts the first whose key set is disjoint from every
in-flight file's; if none is eligible it waits for a completion rather than reordering into a conflict.
Ordering otherwise stays `test:serial` order, so output remains comparable run to run.

**5. `main()` — ~line 519.** Builds conflict info for browser entries only and passes it to that lane's
`runQueue` call. The plain lane's call is untouched.

## Why the tests are the interesting part

A scheduler that ignores the whole feature and runs everything serially satisfies "no two conflicting
files overlap" perfectly. So the proof has two halves, and the second is load-bearing:

- conflicting pairs must **never** overlap, and
- a non-conflicting pair must **actually** overlap when `jobs > 1`.

`test_run_tests.js` drives the real `runQueue` with a stub runner that records start/stop intervals and
asserts both, plus that an exclusive file overlaps nothing. The verifier defeated the implementation
three separate ways in a scratch mirror — killing the conflict check, killing the exclusive branch, and
collapsing `while (activeCount < workerCount)` to `while (activeCount < 1)` (i.e. silently serialising
everything). All three went RED, the third on exactly that non-vacuity line. Port extraction is asserted
against the **real files on disk** — the 7-file 8796 group and the 5-file 8799 group — not fixtures.

## Numbers

| run | wall-clock | result |
|---|---|---|
| 4 browser files, `--jobs=1` | **142.3s** | 4/4 pass |
| same 4 files, default `--jobs=3` | **87.6s** | 4/4 pass |

The verifier reproduced the concurrent run independently: `1m26.898s`, 4/4, against a per-file duration
sum of 144.75s — ~40% below serial, correctly bottlenecked on the single longest file. The set spans
three conflict groups and includes the real shared-port 8799 pair (`test_default_sort.js` +
`test_hero_copy.js`), so the conflict path is exercised, not bypassed.

`--lane=plain` stays 36/36. `test_run_tests.js` is 26/26 (was 16), run five times with no flakiness.

## Deviations and honest limits

- **The full 64-file browser lane was NOT run** — it exceeds the timebox, which is the very problem this
  item exists to shrink. It is recorded as not run, never implied green. The first 8-file measurement set
  was killed at the 290s cap and is recorded as truncated; three files in it have unknown status.
- **Exclusive files are deferred, not drained-to.** The spec says an exclusive file makes the scheduler
  drain in-flight work first; the implementation skips it and keeps filling slots with later files, so an
  exclusive entry at position 2 of 8 starts last. The safety invariant holds and today's impact is nil
  (all 8 real exclusives are the mutually-exclusive `test_audit_*` family), so this was **disclosed
  rather than fixed after the verifier's PASS** — changing code post-verdict would invalidate the
  verified diff. The inline comment `// must drain first.` is inaccurate as shipped; ticketed in
  `170-notes.md`.
- Port extraction's false-negative surface was walked file by file by the verifier: exactly 8 browser
  files reach a listening helper, and those 8 are precisely the already-exclusive set. No non-exclusive
  file inherits a helper port today. The residual is future-only — a new test that declares its own
  `const PORT` *and* requires a listening helper would be non-exclusive and undetected.

## Scope

`run-tests.js` + `test_run_tests.js` only. Trust rails (`APY_SANITY_LIMIT`, `DEFAULT_MIN_TVL`, anomaly
flags, degen haircut), the `home.html` router, `?token=/?chain=/?pool=`, generated SEO surface and
`package.json` dependencies are all untouched — verified by `git diff --name-only` and by `-S` searches on
the rail constants, not by assertion. Nothing on the NEVER-auto-merge list. Tier **HIGH**, assigned
independently by the verifier: 399 changed lines (LOW caps at 150) in the merge-gate harness itself,
where a scheduling bug would produce false-greens for every future item.

## How to see it yourself

```
node run-tests.js --list | tail -3                       # 100 files, 36 plain / 64 browser
node run-tests.js --lane=browser --only=test_default_sort.js,test_hero_copy.js,test_pool_logo.js,test_northstar_cta_fires.js
node run-tests.js --lane=browser --jobs=1 --only=<same>   # the old behaviour, for comparison
node test_run_tests.js                                   # 26/26
```
