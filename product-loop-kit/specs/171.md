# 171 — a prescan alarm must respect its own rendered verdict

Status: READY → IN_PROGRESS (2026-07-29)
Score: 6.2 · Risk (author guess): HIGH — the verifier assigns independently
Promoted by the build loop 2026-07-29 (no takeable READY item existed; see LOG.md)

## Why this item exists (evidence, measured this run — not read from a report)

`node audit-app.js` on a clean `npm ci` checkout of `main`, 2026-07-29:

```
[audit] surfaces covered: … pool-detail:201e5f6e … (29 surfaces)
[audit] findings: 6 total, 6 blocking (P0/P1)
exit=1
```

The six break into two kinds, and only one kind is real:

| # | finding | promoted to a rendered check? | rendered verdict | honest? |
|---|---|---|---|---|
| 5 | `static-prescan:junk-slug` (P1) + 4× rendered `junk-slug` | 4 of 7 pages promoted | **CONFIRMED** — `<h1>8OCT2026 DeFi Yields</h1>` etc. | ✅ real, item 148, human-gated PR #306 |
| 1 | `pool-prescan:mean30d-rail-breach` (P0) | pool `201e5f6e` promoted → surface `pool-detail:201e5f6e` | **CLEAN — zero findings** | ❌ false alarm |

The P0 is `balancer-v2 WSTETH-AAVE`, `apyMean30d = 27421.09636` (27× `APY_SANITY_LIMIT`).
It is upstream DefiLlama garbage, and **the product already handles it correctly**: item 144 added
`mean30dSane` (`PoolDetail.js:161-164`) and every one of the five render sites that reads
`pool.apyMean30d` is gated behind it — the "30d Mean APY" card (`:1298`) and the four
volatility/track-record/momentum/TVL-trend note conditions (`:1384`, `:1412`, `:1460`, `:1506`).
Verified by `grep -n apyMean30d` across all product files: `PoolDetail.js` is the only render site.

So the audit renders the pool, finds nothing wrong, and then reports a **blocking P0 anyway**.

**Why that matters and is not cosmetic.** `audit-app.js:1702` is
`process.exit(blocking.length > 0 ? 1 : 0)` — a red gate. This particular P0 can never go green:
the snapshot regenerates daily from the same upstream feed, the pool keeps its garbage mean, and
144's gate keeps correctly suppressing it. A detector that reports a defect its own rendered check
just disproved is the `ci-signal-honesty` failure mode: it trains every future reader to discount
the number, and a genuinely new P0 lands invisibly inside a count that was already non-zero.

This is NOT the same as item 148's five findings. Those are red because the product **is** broken
and a human has not yet decided; they must stay blocking. This item does not touch them.

## The bug, precisely

`buildPoolSurfaces()` (`audit-app.js:894-979`) and `buildStaticSurfaces()` (`:650-733`) each build
their aggregate `<family>-prescan:<signal>` findings **before** any browser opens
(`:926` and `:690`), then `runAudit()` merges them with the rendered findings at `:1631`. Nothing
ever reconciles the two. The aggregate finding's severity is fixed at emit time from
`POOL_PRESCAN_SIGNALS` / `PRESCAN_SIGNALS` and is never revisited in light of what the promotion it
triggered actually found.

Promotion exists precisely to answer "does this data suspicion show up on screen?" — the answer is
computed and then thrown away.

## The fix

After the rendered pass, reconcile each aggregate prescan finding against the surfaces its own
suspects were promoted into. Per signal:

- **every** suspect carrying that signal was promoted, **and** every one of those promoted surfaces
  produced **zero** rendered findings → the aggregate finding is **downgraded to non-blocking**
  (`severity: 'P2'`) and its `detail` gains an explicit reason naming the surfaces that cleared it.
- **any** suspect carrying that signal was **not** promoted (promotion cap, unrenderable, promotion
  disabled) → severity **unchanged**. Unverified is not clean. This is the load-bearing rule.
- **any** promoted surface produced **≥1** rendered finding → severity **unchanged**.

Applies symmetrically to the pool leg and the static leg, through one shared helper — they are the
same shape and must not drift. **Text-surface prescan is explicitly out**: it has no promotion
mechanism at all (`textSurfaces` result carries no `promoted` array), so no suspect there is ever
render-verified and nothing may be downgraded.

`blockingFindings()` (`:1664`) already filters `P0|P1`, so `P2` becomes non-blocking for free — the
finding is still emitted, still counted in `findings.length`, still written to
`signals/audit-findings.json`. Nothing is hidden; it stops being an alarm.

## Territory notes

- Severity strings are compared literally in several `test_audit_*` files — grep before adding
  `P2` and update any exhaustive-enum assertion in the same commit.
- `opts.only` allowlisting (`:1577`, `:1591`, `:1621`) filters aggregate findings by
  `f.surface` (`'static-prescan'` / `'pool-prescan'`). Reconciliation must run AFTER that filter or
  a filtered run will look for surfaces that were never scheduled.
- Promoted surface names: pool → `pool-detail:${id.slice(0, POOL_ID_PREFIX_LEN)}` (`:964`,
  `POOL_ID_PREFIX_LEN = 8`); static → `static-page:${slugFromRel(rel)}` (`:709`). Match exactly —
  the multi-viewport siblings (`pool-detail-360`, `pool-detail-dark`, `pool-detail-ko`) are
  different surfaces and belong to the ANCHOR pool, not to a promoted one. Attributing them to a
  promoted suspect would be a false clear.
- `prescanPools()` returns `suspects` with `{poolId, signal, severity, detail}`; the static leg's
  suspects are keyed by rel path. The shared helper needs both a "suspect → key" and a
  "key → surface name" adapter rather than assuming one shape.
