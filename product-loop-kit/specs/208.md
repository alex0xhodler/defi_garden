# Spec 208: widen the kpi/history population to the deep-linked set — MEASURE THE COST FIRST, then decide

## Evidence

Same measurement session as 206/207, `origin/main` @ `c72c90cf6`, 2026-08-02. Verbatim from
`signals/2026-08-02.md`.

- `compute-kpis.js` derives its slim per-date history point *from* `data/pools-snapshot.json` (header
  `:9-11`), retains `HISTORY_RETENTION = 30` dated files, and writes `kpis` back into the snapshot and its
  slices. Its population is therefore exactly the snapshot's **736** $10M-railed pools.
- The estate deep-links **3,669** distinct `?pool=` ids; **3,249 (88.6%)** are outside that population, so
  no history — and therefore no `kpis` — can ever exist for them (item 207's root cause).
- Snapshot floor rationale is on the record: 059 railed it to $10M **for front-end payload reasons**.
  Naively re-widening the snapshot would undo that, which is why this item is measure-then-decide rather
  than build-now.
- 105 already demonstrates the shape that avoids the payload cost: a **separate fetch performed only on
  pool-detail** (`app.js:1253-1273`), not part of the initial page payload.

## Hypothesis

We believe **a separate lean `id → kpis` artifact covering the deep-linked population, fetched only on
pool-detail**, will **let the three trust notes (088.1/103/087) render for SEO arrivals they structurally
cannot reach today**, without touching the main snapshot payload 059 exists to protect. Confidence:
**guess** on the cost side (the artifact size and history growth are unmeasured), **supported** on the
mechanism (105 already fetches an auxiliary artifact on this exact surface and 182 already ships a
CI-baked id-keyed artifact, `data/protocol-urls.json`, as precedent).

## Change

**Phase 1 — measurement only. Phase 2 does not start until Phase 1's numbers are in the spec and the
decision rule below has been applied.**

Phase 1 (this item's first deliverable, a measurement written into `specs/208-notes.md`):
1. Byte cost of one widened `data/history/<date>.json` at ~3,669 pools vs the current ~736, measured by
   actually generating one against the live feed — not extrapolated.
2. That figure × `HISTORY_RETENTION` (30) = the repo-size delta, plus the daily git-commit delta (the
   history append piggybacks the existing daily commit; confirm it still adds no extra Vercel deploy, per
   the 2026-07-13 quota decision).
3. Serialized size of the proposed lean `id → kpis` artifact for the deep-linked set, gzipped, as it would
   be fetched on pool-detail.
4. Whether `compute-kpis.js` can even source a series for sub-rail pools: it slims from the snapshot today,
   so widening requires a second input (the live feed at the estate's $100K floor, or the D1 `/history`
   endpoint already wired at `DB_WINDOW_DAYS = 90`). **Answer this before designing anything** — if the D1
   endpoint already covers them, the cost collapses and the shape changes entirely.

Phase 2 (only if Phase 1 clears the decision rule): build the lean artifact + extend 105's lookup to fall
back to it. Reuse 182's baked-artifact conventions (`schemaVersion` guard, fail-silent fetch, never wedge
the render path — note 182's own trap: `app.js:1293` hard-rejects a `schemaVersion` it does not know, so a
version bump silently drops the whole tier).

**OUT of scope in both phases:** changing `DEFAULT_MIN_TVL`, `APY_SANITY_LIMIT`, anomaly flags, the degen
haircut, or which pools the grid/planner/rankings display. KPIs stay **derived, disclosed, null-safe, and
ranked only WITHIN already-passing pools** (`compute-kpis.js` header invariants, 087 §Territory 4). A
sub-rail pool gaining a `kpis` object must **not** make it eligible for the grid, the planner, or any
ranking — verifier treats any such leak as a trust-rail breach and an automatic FAIL.

## Measurement

Metric: repo-size and payload deltas from Phase 1 · Window: n/a for Phase 1 (a measurement, not an
experiment); 14 days for Phase 2 · **Decision rule (Phase 1 → Phase 2):** proceed only if the widened
history costs **< 5 MB** total across the 30 retained points **and** the lean pool-detail artifact is
**< 250 KB gzipped** **and** the initial grid payload is provably unchanged. If any threshold fails, the
honest outcome is to **stop at 207** — the blank becomes an honest note and the trust notes stay a
≥$10M feature, documented as a deliberate limit rather than an unnoticed one. Park this item with the
measurements recorded; that is a successful outcome, not a failure.

## Risk tier (builder's guess — verifier assigns independently)

**HIGH.** Phase 1 alone is read-only measurement and would be LOW, but the item as filed touches the data
layer that feeds every derived number the product shows, and the failure mode — a sub-rail pool leaking
into a ranked surface — is a trust-rail breach on the NEVER list. Tiering the whole item HIGH is the
conservative and correct read of NORTH_STAR's *when in doubt → HIGH*.
