# 228 — PR explainer (HIGH tier)

**What shipped:** a remote MCP server for defi.garden, on the same Cloudflare Worker as 224's
telemetry logger and 227's REST API. Four tools an agent can install: `find_pools`, `get_pool`,
`forever_number`, `explain_rails`. No new npm dependency, no product render path touched.

**Risk tier: HIGH**, assigned independently by the verifier and agreed by the operator. Not
because the code is fragile, but because of *where it lives*: this Worker sits in front of every
request to www.defi.garden. A mistake in it does not degrade a feature — it takes the site down.

---

## 1. The goal

NORTH_STAR's leg (A) counts "read-only API calls (item 227's Worker) + **MCP invocations (item
228)**". 227 shipped the first instrument yesterday. This is the second. It is also the last
blocker on item 234 (score 9.3, the highest-scored row in the backlog), which wraps these
endpoints in x402 micropayments.

The strategic bet, from the 2026-08-04 agent-first interview: *curated + railed + explainable
beats the raw firehose for agent citation.* DefiLlama has more data. What it cannot emit is a
`rails` block explaining which pools were excluded and why.

## 2. The intuition — why this item is mostly about what it *doesn't* contain

The obvious way to build an MCP server is to write four tool handlers that query pool data and
apply the rails. That would have been wrong, and the reason is the mirror rule (RAZOR / item
212): **a second copy of a rule is free to drift from the first.**

This is not hypothetical here, and the honest version of this paragraph is worse than the one it
replaces. An earlier draft said a hand-rolled MCP layer "would have" created a third place the
sanity limit lives, "checked by nobody" — as though two were the status quo. **A third copy
already exists and is live.** `home.html:269-270`, inside the WebMCP tools this site registers on
every page load, hardcodes `p.tvlUsd < 100000` and `p.apy > 1000` — the rails re-typed as
literals, correct today only by coincidence, ~20 lines below a comment (`home.html:246-249`) explaining that a neighbouring
*description string* was tokenised because "that literal drifted once already" — same tool
object, so the pairing is real, but they are not adjacent.
Filed as **backlog 266**; found by this item's verifier, not by this item.

So the accurate framing is: `app.js` and `api-core.js` share one source (`trust-rails.js`),
`home.html`'s WebMCP does not, and this item declined to become the **fourth** site.

The item is therefore built inside-out. `edge/mcp-core.js` contains **no rail, no filter, and no
arithmetic at all**. Each tool declares which `api-core.js` route it *is*, and the dispatcher
calls that route:

```js
const request = tool.argsToRequest(args || {});
const delegated = apiCore.handleApiRequest({
  pathname: request.pathname, searchParams: request.searchParams, pools: pools,
});
return { result: { content: [{ type: 'text', text: JSON.stringify(delegated.body, null, 2) }],
                   isError: delegated.status >= 400 } };
```

The rails reach MCP through the same single call the REST API makes, which itself reads
`trust-rails.js`. There is no second copy to drift.

**How we know that's true rather than just intended.** The load-bearing non-vacuity cycle
mutates **`api-core.js`** — deleting `!isAnomalous(p)` from the list filter — and the *MCP* test
goes red, naming a real pool (`aerodrome-slipstream`/Base, total APY 135,830.05%). If MCP had its
own copy of the rails, that mutation would have passed. The constraint proves itself instead of
asserting itself.

The verifier then attacked the claim harder than the build did: it re-implemented `find_pools`
so that it looked correct and evaded both purity greps (no numeric literal, no dot-access, reusing
`apiCore.meetsFloor`/`isAnomalous`). The deep-equal parity assertion still went red. It also ran
**2,474 MCP-vs-REST tool calls** (round 3's sweep, the largest of the three and the figure quoted
everywhere in this document): all 89 chains, all 440 projects, 300 symbols, 407 pool ids including
hostile ones (`''`, `'%'`, `'%zz'`, `'../api'`, `'__proto__'`, `'constructor'`), plus
floor-lowering `minTvl ∈ {0, −1, 1, 99999, −1e9}` on every chain, `limit ∈ {0, −5, 1, 1e9, 10000}`
on 60 projects, case/whitespace chain variants, 300 triple-filter combinations and 72
`forever_number` combinations. Result: **zero divergences** from `apiCore.handleApiRequest`,
**zero rail violations** across **22,051** returned pools, zero unexpected protocol errors.
(`get_pool` percent-encodes the id at `edge/mcp-core.js:111`, so `'../api'` cannot traverse.)

## 3. The one genuinely interesting design decision: `/mcp`, not `/api/mcp`

Mounting under `/api/*` would have been free — `agent-log-core.js:82` already classifies those
as `pathClass: 'api'`, so telemetry would have worked with no change to 224's code.

We did the opposite, and paid for a classifier edit, because **leg (A) counts API calls and MCP
invocations as two separate terms**. Sharing the `'api'` class would have made the north-star
metric unable to decompose into the two things it is defined as. Choosing the mount point that
follows the metric's defining mechanism, rather than the one that merely resembles working
telemetry, is the whole of RAZOR's guard rule applied to a URL.

## 5. The tests, and what they are allowed to claim

Fixtures are **derived at test time** from `data/pools-snapshot.json` (7,332 pools, regenerated
daily) — never a hardcoded pool list, because the estate churns.

- **Invariant over the population**, not a sampled few: no pool in any `find_pools` result exceeds
  `APY_SANITY_LIMIT`; every returned pool meets `DEFAULT_MIN_TVL`.
- **Positive control is the motivating instance, not the definition**: 17 naturally-anomalous
  pools are derived from the snapshot and asserted absent. If a future snapshot contains **no**
  anomalous pool, the run fails loudly (`VACUITY GUARD TRIPPED`) rather than passing vacuously —
  the verifier proved this by de-anomalizing all 17 and watching it exit 1.
- **Non-vacuity, three rules neutered separately** so "three working rules" is distinguishable
  from "one working rule and two dead ones". Each red, each restored byte-identically by md5sum,
  each green. The verifier reproduced all three plus two harder variants of its own.

## 6. Deviations from the spec

1. `SUPPORTED_PROTOCOL_VERSIONS` is a **single** entry (`2025-06-18`), where the spec's wording
   invited a list. RAZOR cuts against claiming compatibility with revisions nothing exercised.
2. HTTP status mapping for JSON-RPC was **unspecified** by the spec; pinned explicitly in the
   code header (body-carrying response → 200; notification → 202; `-32700` → 400; Worker-caught
   escape → 500).
3. `validateArgs` is a minimal hand-rolled checker, not a general JSON Schema validator — the
   alternative was a dependency.
4. `edge/DEPLOY.md` got a 5-line §8, not the literal "one line", matching the file's per-item
   convention.
5. `test_api_worker.js` was edited though the spec's Change section didn't list it — required *by*
   the spec's own Territory notes.

## 7. What this does NOT do — read this part

**Code-complete, NOT deployed.** `wrangler deploy` needs Cloudflare credentials: human-owned,
NEVER-list, the same split 224 and 227 merged under. Until the human deploys, leg (A)'s MCP count
is **0 = absence of instrument, not absence of demand**, and the ≥30-invocation traffic gate
cannot open.

**Class NOT closed.** The agent pillar is 4 legs. This closes the 3rd (224 ✓, 227 ✓, 228 ✓).
Item **234** (x402) remains open — and is now unblocked.

**The verifier FAILed round 1, and it was right.** The docs shipped in that round claimed "no
`.well-known/` discovery document exists — deferred with the registry listing." That was false,
and the operator wrote it into the spec by trusting the BACKLOG row's phrase "the stubs already
live" without opening the stubs. In fact `.well-known/mcp.json` and
`.well-known/mcp/server-card.json` both advertise `https://www.defi.garden/api/mcp` with `"type":
"sse"` and a `prompts` capability, and `vercel.json:171` broadcasts that card in a `Link` header
on **every response the site serves**. All three facts disagree with this server (`/mcp`; 405 on
GET; tools only).

Worse, the `/api/mcp` mismatch **defeats §3's own rationale**: an agent following the published
card is logged `path_class = 'api'`, so its invocations would not be separable after all. The
mismatch is *pre-existing* — the card has pointed at a 404 since item 223 — but the docs denying
it was this item's fault, and is corrected. Reconciliation is filed as **backlog 265** (HIGH), to
land **at or before** the human's deploy, with the real choice left open rather than guessed:
correct the cards to `/mcp`, or serve `/api/mcp` as an alias classified as `mcp`.

**Known-narrow gate, stated with a number.** The committed parity combos derive from one pool
(Ethereum/lido/STETH), so a divergence confined to another chain would not be caught by the
committed gate. The verifier closed that gap **by hand, this session only** — the same 2,474-call
sweep quoted in §2 (89 chains / 440 projects / 300 symbols / 407 ids → zero divergence). So the
code is clean *today*, but **that sweep is not committed and will not run again**: the gate that
ships is narrower than the class it guards, and the difference is one pool's neighbourhood versus
the whole estate. Not claimed otherwise.
