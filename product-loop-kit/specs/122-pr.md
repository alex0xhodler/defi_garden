# 122 — HIGH-tier explainer + quiz: rate-stability Sharpe no longer renders −900T

## Goal
The pool-detail page (now the north-star surface) showed **Rate-stability score −900,719,925,474,097.9**
on SUSDS. A −900-trillion number on the flagship conversion page reads as "broken" and sabotages the CTA
clicks we're trying to grow. Fix it, and make sure no pool can ever show a garbage score again.

## Intuition
The 117 rate-stability Sharpe is `(mean_apy − 4%) / stdev(apy)`. SUSDS holds a flat ~3.6% rate, so its
stdev across the (now D1-backed, 10-day) history is **floating-point dust** — about `1e-16`, not exactly
zero. The old guard was `sd > 0`, and `1e-16 > 0` is true, so it computed `(3.6 − 4) / 1e-16 ≈ −9e14`.
The bug was latent until the D1 backfill gave the KPI real multi-day history to divide by.

## What changed and why (reading order)
1. **compute-kpis.js** (the real fix): two new bounds —
   - `SHARPE_MIN_STDEV = 0.05` — the rate must have actually *moved* ≥ 0.05 percentage points to score;
     below that it's flat and the Sharpe is undefined/noise → `null`. This is what kills the dust case.
   - `SHARPE_ABS_MAX = 50` — even above the floor, keep only a sane magnitude; beyond ±50 it's noise (or
     an anomalous >1000%-APY pool with tiny vol) → `null`. Also requires `Number.isFinite`.
2. **PoolDetail.js** (117.1 render gate): the annotation now renders only when `apySharpe` is
   `Number.isFinite && Math.abs(...) <= 50`. Critical subtlety: −9e14 **is finite**, so `isFinite` alone
   wouldn't catch it — the gate is a *magnitude* check. This hides any value in the **already-committed**
   snapshot immediately on deploy, before the daily CI regenerates the KPIs.
3. **PoolDetail.compiled.js / .min.js**: regenerated from source (byte-identical fresh compile/minify,
   freshness gates pass).
4. **test_compute_kpis.js**: +4 cases — float-dust series → null (the exact bug), |Sharpe|>50 → null,
   and a proof that genuine variation (stdev 0.5) still scores 2.0 (not over-suppressed).

## Deviations from spec
None. The spec proposed an epsilon floor + render clamp; both shipped. Copy of the note (item 127) is a
separate ticket and untouched here.

## Trust rails
Untouched. `apySharpe = null` for a flat pool is honest (no fabricated value); the KPI stays derived,
disclosed, and ranked within rail-passing pools. `APY_SANITY_LIMIT`/`DEFAULT_MIN_TVL`/anomaly/haircut
unchanged; app.js not touched.

## Measurement
No isolable funnel metric (a trust/correctness fix). Proxy: the score line renders a sane value or
nothing on pool detail; watch the north-star `pool_click{garden_cta|protocol_link}` CTR now that the page
no longer shows a broken number. Regenerates on the next daily CI run reading D1.

## 5-question quiz (HIGH gate)

1. **Why did a `sd > 0` guard fail to prevent the −900T score?**
   A near-constant rate produces stdev ≈ 1e-16 (floating-point dust), which is > 0, so the guard passed
   and `(mean−4)/1e-16` exploded. The value was finite, just astronomically large.

2. **Why is the PoolDetail render gate a magnitude check (`|x| <= 50`) and not just `Number.isFinite`?**
   −900,719,925,474,097.9 is a finite number, so `isFinite` returns true. Only a magnitude bound hides it.

3. **Why keep the render gate at all if compute-kpis.js already returns null now?**
   The committed snapshot still carries the old bad value until the next daily CI regeneration; the render
   gate protects users immediately on deploy, before that regen.

4. **Does the fix null out KPIs for genuinely stable-but-real pools?**
   No — only when stdev < 0.05pp (essentially no movement). A pool with real variation (e.g. stdev 0.5)
   still scores; the test asserts (5−4)/0.5 = 2.0.

5. **Is `apySharpe = null` for a flat pool honest, and does it weaken any trust rail?**
   Yes and no weakening: null means "not enough variation to score" — no fabricated number — and the hard
   rails (sanity limit, TVL floor, anomaly, haircut) are untouched.
