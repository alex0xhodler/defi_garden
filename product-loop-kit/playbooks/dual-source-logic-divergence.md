# Playbook — dual-source logic divergence (a value renders differently on two surfaces)

**When:** a rendered-audit finding shows the SAME derived value (a category badge, a risk tier, a formatted number, a label) rendering CORRECTLY on one surface and WRONG on another — e.g. the analytics grid classifies a pool as "Lending" but the pool-detail hero badge says "Yield Farming" for the same pool (item 130: SUSDS on sky-lending, venus-core-pool). **Also when a GENERATED surface (sitemap/llms/static page) publishes something the app contradicts** — item 189: the sitemap's own `getPoolType` fork disagreed with the product's classifier on 12.2% of pools, so 8 of 114 published category URLs opened an empty grid. That variant has no rendered symptom on any app surface, so it only surfaces if you go looking (§7).

**Answer in one line:** the two surfaces are running two FORKED copies of the same helper that have drifted; find both, confirm which surface calls which, then collapse to one shared definition (don't just patch the wrong copy — it will drift again).

## Steps
1. **Name the value + both surfaces.** Grid card vs pool-detail hero are the usual pair. Grid render lives in `app.js`; pool-detail in `PoolDetail.js`.
2. **Grep for the helper in BOTH files**, e.g. `grep -n "getPoolType\|<lists it uses>" app.js PoolDetail.js`. Two definitions of the same-named/same-purpose function = confirmed fork. Decision rule: if only ONE file defines it and the other imports/calls a global, it's not a fork — look elsewhere.
3. **Diff the two copies' logic**, not just their data. Item 130: `app.js:193` `getPoolType` had 5 category lists + RWA/Yield-Derivatives ordering + `.replace(/\s+/g,'-')` normalization; `PoolDetail.js`'s inline copy had a 7-entry lending list, no RWA/YD, `.toLowerCase()` only. The narrower copy is usually the stale one.
4. **Also check the DATA lists for a gap present in BOTH** — item 130's `sky-lending` was missing from app.js's list too, so that pool was wrong on BOTH surfaces (grid included). Fix the shared list once.
5. **Collapse to one source.** Pick the file that loads FIRST as the owner (home.html script order: `PoolDetail.compiled.min.js` runs before `app.compiled.min.js`, so PoolDetail can own a global the later app.js calls). A top-level `function name(...)` declaration is a cross-script global AND survives terser (`mangle:true` without `toplevel:true` preserves top-level names — same reason the global `PoolDetail` works). The second-loaded file delegates: `const x = (a) => sharedX(a);`. Verify the owned list-consts have NO other callers before deleting them (`grep -n CONST_NAME file.js`).
6. **Rebuild:** `npm run compile && npm run minify` (source app.js/PoolDetail.js are the edit surface; home.html ships the `*.compiled.min.js`). Commit the regenerated outputs. Confirm the shared name survives: `grep sharedName *.compiled.min.js`.

7. **Check the BUILD SCRIPTS too, not just the two render surfaces (item 189).** A generator that has to reason about what the app would show carries its own copy of app logic. `grep -n "getPoolType\|<helper name>" generate-*.js audit-app.js` — a `function` definition in a generator is a fork by default; only a `require`/extraction of the product file is not. **Decision rule:** if a generator defines the helper, diff it against the product's copy over the WHOLE population before anything else: `node -e` over `data/pools-snapshot.json`, print the disagreement count and a `from -> to` histogram. 189's was 90/736 = 12.2%, entirely one-directional — a one-directional histogram is the signature of a stale list, not of two legitimate features (contrast the item-146 trap below).
8. **Count who ELSE requires the fork before you touch it — the blast radius is the reason it went unnoticed.** `grep -rn "require.*generate-sitemap" --include=*.js .` found `generate-llms.js` and `audit-app.js` both pulling the same `getPoolType` for their link-integrity checkers. That is why four shipped link gates (175/180/181/184) scored the dead URLs as live: **they asked the fork whether the fork was right.** Fixing the single definition site repaired all three consumers with zero call-site edits — so keep the exported NAME and SIGNATURE identical, and make that an acceptance criterion (`git diff --stat` on the consumers must be empty).
9. **In Node, extract — don't re-implement, and don't relocate the source.** Browser-global product code (`PoolDetail.js`, `app.js`) is reachable from a generator with the anchor-slice-`vm` pattern (item 084's `extractParser`): slice from a named start anchor to the function's column-0 closing brace, `vm.runInContext`, cache at module scope. **Do NOT** move the classifier into a new shared module to make the require "clean" — that drags in `home.html`/`plan.html` script order and the compiled/minified bundle pipeline, i.e. HIGH-risk router-shell surface for zero extra correctness.
   **Decision rule for the failure path: THROW, never fall back.** A silent fallback to the old copy is precisely how the fork survives; a red pipeline is visible, a wrong sitemap is not. Extract at require time so the failure lands on `require()`, and give the Error the file path plus both anchor names so the next person can fix it without reading this playbook.

## Resolution
One classifier, both surfaces delegate. Acceptance = rendered Playwright on `/?pool=<id>` reading the DOM (`.pool-type-badge-hero` textContent), not a unit fixture (2026-07-11 UX-acceptance decision). Assert the primary fix + a regression case + the default/negative case + zero page errors, and re-run the OTHER surface's existing test (grid: `test_category_taxonomy.js`) to prove it's unchanged.

## Traps
- **Confirm it is a fork before you collapse it (item 146).** Two copies that look alike but read DIFFERENT sources are not a fork — they are two features. `doShare()`'s subscription-capital branch derives its bundle from `coveredBundle(subCapital, apy, goal)` ("what the parked capital covers"); the post-waitlist share functions derived theirs from `selectedSubs` ("what the user toggled in the mix UI"). They coincide only while the mix is untouched, so "reuse the shared helper" would have silently dropped a user-selected service from their own share card. Decision rule: diff the two copies' INPUTS first; identical logic over different inputs → keep both, branch explicitly, and pin the untouched path with its own test (including a manually-toggled/non-default state, not just the default one).
- Patching only the surface in the screenshot leaves the fork alive → the bug reappears on the next protocol. Always collapse.
- Cross-script global reachability depends on load order — verify it in home.html and PROVE it with zero page errors on the render (a `ReferenceError` would surface as a page error the acceptance test catches).
- `const` at top level is NOT a cross-script global (spec 044's footgun); only `function` declarations are.

- **A generator fork can be "correct" on every rendered surface and still publish lies (189).** Nothing on the app was wrong — the *sitemap* was. Rendered audits (`audit-app.js`) cannot see this class by construction, and neither can the link checkers if they share the fork. The only detector is the population diff of step 7, so run it whenever you touch a generator that classifies pools.
- **A helper's CATEGORY SET can be stale even when its LOGIC looks fine (189 Leg B).** The sitemap knew 4 of the product's 6 categories (`app.js:114-121` `CATEGORY_TABS`), so 41 pools could never earn a URL — and de-forking the classifier ALONE would have silently stripped 8 tokens of every category URL. Diff the enumerations, not just the branches, and land both legs together or the fix reads as a de-indexing.
- **Verify the repair's OWN output against the same simulation that found the bug.** 189's acceptance re-ran the app-filter simulation over the regenerated URL set (0 dead, 0 thin) — 188's trap: a repair whose own URLs get classified dead by our own checkers.
- **Reconcile the snapshot against live before calling a leftover a defect.** One URL read "thin" against the ~6h-old committed `data/pools-snapshot.json` and fine against a fresh 15,873-pool fetch. The live population is what a crawler hits; say which population produced each number.
