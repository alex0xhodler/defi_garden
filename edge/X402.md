# DeFi Garden agentic commerce — the x402 + Web Bot Auth contract (backlog 234, spec 234)

**Status: code-complete, pricing DARK.** Everything on this page is real,
tested code (`edge/x402-core.js`, `edge/web-bot-auth-core.js`, the gate in
`edge/agent-log.mjs`, `test_x402_core.js`, `test_web_bot_auth.js`,
`test_x402_gate.js`). Nobody is being charged. `X402_ENABLED` ships unset
(false) — see "Availability, honestly" below before assuming any of this is
live.

This is the payment layer over the [read-only Yield API](API.md) (item 227)
and the [MCP server](MCP.md) (item 228) — same Worker, same deploy, zero new
data, zero new rails. It answers three questions: what's free vs. paid, what
a `402` looks like, and how an agent actually pays.

## The free/paid boundary, in plain terms

**Free: current APY data.** The live railed rates DeFi Garden already
serves — `GET /api/pools`, `GET /api/pools/:id`, and everything about the
API's own self-description (`GET /api`, `GET /api/health`,
`GET /api/pricing` itself). This is the commodity DefiLlama-derived feed,
curated through DeFi Garden's trust rails, and it costs nothing to read —
today, and for the foreseeable future. Charging for it would be charging for
what everyone else already gives away; the value DeFi Garden adds there is
the curation, not gatekeeping.

**Paid: computed KPIs.** Anything DeFi Garden *computes* rather than
passes through — starting with `GET /api/forever-number` (the SUBSCRIPTION-
archetype "capital whose yield pays a recurring bill forever" math) and,
going forward, the historical series DeFi Garden retains and any future
computed field (Sharpe ratio, stability scores, etc.). This is the human's
own boundary (NORTH_STAR, 2026-08-05): *"free stops at getting the apy
data, not the historical ones that we are computing and all other computed
kpis."*

**The default is PAID, not free.** A route this document doesn't explicitly
list as free is paid by construction (`edge/x402-core.js`'s
`DEFAULT_TIER = 'paid'`) — a future computed-KPI route can never ship free
by simple omission from the schedule. This holds for any route
`edge/api-core.js`'s single declarative `ROUTES` dispatch table actually
serves, not merely for the routes this document happens to already list:
`edge/x402-core.js`'s `matchRoute()` delegates directly to that table (via
`api-core.js`'s own `matchRouteId()`), so a route reaching a real HTTP
request through `api-core.js`'s dispatcher is always classified — default-
paid included — whether or not `PRICE_SCHEDULE` has an entry for it yet
(verifier round 1, backlog 234 — see `edge/x402-core.js`'s header comment
for the failure this closes). See `GET /api/pricing` below for the live,
machine-readable version of this table — it is generated from the same
schedule this prose describes, never a second hand-typed copy.

**Nothing about the static site (llms.txt, the `.md` twins, the story
pages) is ever gated.** That's deliberately out of scope forever — citation
is the moat, and paywalling it would work against the whole reason it
exists. See `CLAUDE.md`'s "Trust rails are the moat".

MCP tools follow the exact same boundary, since every tool is a thin
delegate to one of these REST routes: `find_pools`, `get_pool`, and
`explain_rails` are free; `forever_number` is paid (it delegates to
`/api/forever-number`).

## `GET /api/pricing` — the machine-readable version

An agent should never have to pay to find out what costs money. This route
is always free (see `edge/x402-core.js`'s own header comment for why) and
returns:

```json
{
  "name": "DeFi Garden agentic-commerce pricing document",
  "protocol": { "name": "x402", "version": 1 },
  "asset": { "symbol": "USDC", "decimals": 6 },
  "boundary": "Current APY data is free ... every other computed KPI ... are paid ...",
  "routes": [
    { "route": "/api/pools", "method": "GET", "tier": "free", "priceUsdcAtomic": null, "reason": "..." },
    { "route": "/api/forever-number", "method": "GET", "tier": "paid", "priceUsdcAtomic": "1000", "reason": "..." }
  ],
  "mcpTools": [
    { "tool": "forever_number", "route": "/api/forever-number", "tier": "paid", "priceUsdcAtomic": "1000" }
  ],
  "availability": { "enabled": false, "mode": "test", "statement": "Pricing is currently DISABLED. ..." }
}
```

`availability.enabled`/`availability.mode` are never hardcoded — they are
read from the SAME `X402_ENABLED`/`X402_MODE` env vars the gate itself
reads (`x402Core.readConfig(env)`, once per request), so this document can
never claim a state it cannot actually see (the 2026-07-12 "no fake
availability" precedent). See "Availability, honestly" below for what it
says today.

## The `402` shape

A `GET`/`POST` to a paid route without a valid payment gets HTTP `402
Payment Required` with an [x402](https://blog.cloudflare.com/wallets/)
v1-conformant body:

```json
{
  "x402Version": 1,
  "error": "Payment required for /api/forever-number, but no payment recipient is configured yet (X402_PAY_TO / X402_ASSET unset) — this route cannot actually be paid for right now. ...",
  "accepts": [
    {
      "scheme": "exact",
      "network": "base-sepolia",
      "maxAmountRequired": "1000",
      "resource": "https://www.defi.garden/api/forever-number?monthly=20",
      "description": "...",
      "mimeType": "application/json",
      "payTo": null,
      "maxTimeoutSeconds": 60,
      "asset": null,
      "extra": { "name": "...", "version": "0.1.0", "docs": "/api/pricing", "freeAlternatives": ["/api", "/api/health", "/api/pools", "/api/pools/:id", "/api/pricing"] }
    }
  ]
}
```

`payTo`/`asset` are `null` (never an invented address) until a human
configures `X402_PAY_TO`/`X402_ASSET` — see `edge/DEPLOY.md`'s "Deploy
delta — x402 + Web Bot Auth" section for exactly which env vars gate what.
The `402` is never publicly cacheable (`Cache-Control: no-store`) and
carries the same CORS headers every other `/api/*` response does.

`POST /mcp`'s `tools/call` for a paid tool (`forever_number`) gets the
SAME 402 shape at the SAME HTTP status — not a JSON-RPC-wrapped error —
because the resource being purchased is the underlying REST route
(`/api/forever-number`) regardless of which transport reached it.

## How to pay

1. `GET /api/pricing` (or the `402` itself) to learn the exact price
   (`accepts[0].maxAmountRequired`, atomic USDC — 6 decimals), network
   (`accepts[0].network`), and resource URI (`accepts[0].resource`).
2. Build the x402 payment payload: `{ x402Version, scheme, network, resource, amount, payer? }`.
   `scheme`/`network`/`resource` must match the challenge exactly; `amount`
   must be `>=` `maxAmountRequired` (overpayment is accepted, underpayment
   is rejected).
3. Base64-encode that JSON object and send it back as the `X-PAYMENT`
   request header, retrying the SAME request.
4. An accepted request gets `200` + the real data, plus an
   `X-PAYMENT-RESPONSE` header stating honestly what happened:
   `settled=false; verified=false; checked=structural; mode=test` for an
   accepted TEST-network payment, and `settled=false; verified=true;
   mode=live` for a real live-mode payment. These two are NOT the same
   claim: in live mode, `verifyPayment()` actually calls the configured
   facilitator's `/verify` endpoint and requires an explicit
   `isValid:true` back — a real third party vouched for the payload, so
   `verified=true` is earned. In test mode, `verifyPayment()` never calls a
   facilitator, checks a signature, or touches a chain at all — it only
   checks that the payload is well-formed and STRUCTURALLY matches the
   challenge (decodable, scheme/network/resource match, amount `>=`
   required, network is a test network), so the header says
   `verified=false; checked=structural` — nobody verified anything, we
   merely matched fields against our own challenge. **`settled` is `false`
   on every branch, including live mode**, because this Worker never calls
   a facilitator's `/settle` endpoint (see `edge/x402-core.js`'s
   `verifyPayment()` and "What this deliberately does NOT do" below). A
   live-mode payment is verified, never settled, by this Worker; a
   test-mode payment is neither verified nor settled — only structurally
   checked.
5. A rejected/underpaid/mismatched payment gets the SAME `402` back, never
   partial data.

## Web Bot Auth: identity, not access

Every `/api` and `/mcp` request is also checked for an RFC 9421 HTTP
Message Signature (`Signature`/`Signature-Input` headers, the
`web-bot-auth` tag — see `edge/web-bot-auth-core.js`). The verdict
(`unverified`/`invalid`/`verified`, plus the signer's `keyid` when
resolvable) is logged into 224's D1 `agent_reads` table as
`identity_status`/`agent_identity`.

**A verified identity never unlocks paid data.** This is a deliberate,
conservative reading of spec 234 (recorded in
`product-loop-kit/specs/234-notes.md`, Territory note 6): treating a valid
signature as equivalent to payment would let anyone who can generate an
Ed25519 keypair read paid data for free. Identity is telemetry — a realness
proof for north-star leg (A) — and nothing else. Only a payment that passes
`verifyPayment()` (`X-PAYMENT`) unlocks a paid route — live-mode
facilitator verification or test-mode structural matching, per "How to
pay" step 4 above; never an identity signature alone.

## Availability, honestly

**Pricing is dark today.** `X402_ENABLED` ships unset/false — every route
above is served FREE right now, including the ones this document lists as
"paid" in the schedule. No `cloudflare.pay` handle is claimed, no
Monetization Gateway is enabled, no wallet is configured, and nobody is
being charged for anything. `GET /api/pricing`'s own `availability` field
states this live, in the same words: `enabled: false`, and a `statement`
that says exactly this. When a human eventually flips `X402_ENABLED` to
`true`, `X402_MODE` defaults to `"test"` (a well-formed TEST-network
payment is accepted but nothing settles) — `X402_MODE=live` is a second,
separate, explicit human decision on top of that.

## What this deliberately does NOT do (v0)

- No wallet custody, no payout configuration, no `cloudflare.pay` handle
  claim, no Monetization Gateway enablement — all human-owned, money/org-
  admin actions a loop never performs (see `edge/DEPLOY.md`'s "HUMAN-OWNED"
  list).
- **No settlement, ever — live mode included (verifier round 1, backlog
  234).** `verifyPayment()` POSTs only to a configured facilitator's
  `/verify` endpoint (fail-closed on anything short of an explicit
  `isValid:true`); no code path in `edge/` ever calls a facilitator's
  `/settle` endpoint. In the x402 protocol, `/verify` validates a payment
  payload and `/settle` is the separate call that actually broadcasts the
  transfer. Implementing settlement is explicitly out of scope — it is
  money-movement, on the human-owned NEVER-list, same as wallet custody and
  payout configuration above. The practical consequence: **a live-mode
  payment is verified, but never settled, by this Worker — no funds move on
  our side even when `X402_MODE=live`.** `X-PAYMENT-RESPONSE`'s `settled`
  field is `false` on every branch for exactly this reason (see "How to pay"
  above); a human/off-Worker settlement path is a separate, future,
  human-owned decision, not silently implied by anything shipped here.
- **No replay/nonce protection.** The same `X-PAYMENT` header can be
  replayed indefinitely against the same resource URL — `verifyPayment()` is
  stateless (no record of a payload having been "spent" is kept anywhere),
  so nothing here rejects a second request that resends an already-used
  payment header for the identical resource. It IS resource-scoped, which
  limits but does not close this gap: a payment payload's `resource` field
  is checked against the exact request URL, so a payment built for
  `?monthly=20` correctly `402`s when replayed against `?monthly=999999` (a
  different resource) — but replaying it against `?monthly=20` again
  verifies again, every time. Closing this (a nonce/idempotency-key store,
  presumably in D1) is a real gap for live-mode traffic and is left for a
  follow-up item, not implemented here.
- No key discovery for Web Bot Auth — verification is only ever against an
  env-configured keyring (`WEB_BOT_AUTH_KEYS`); it never fetches a
  `Signature-Agent` directory or `/.well-known/http-message-signatures-directory`.
- Not advertised in `llms.txt` or the sitemaps yet — publishing a pricing
  surface that describes a state nobody can act on would be premature; a
  follow-up item does that once a human has actually flipped the flag.
